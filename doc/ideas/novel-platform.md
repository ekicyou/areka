## 調べて分かったこと（2026-10-28）

- **pasta の取り決め**: `novel-areka-contract`（pasta の `.kiro/specs/`）は brief だけで未着手。命令の語彙・イベント・設定の名前と、取り決めの版の番号は、どれも決まっていない。決まっている方針は次のとおり。
  - 演出は `\![名前,引数…]` に載せ、areka は `Custom{command, params}` の 1 本で運ぶ。
  - ノベル用のイベントはすべて GET で送る（NOTIFY には台本を返せない）。応答は 5 秒以内（超えると 204）。areka の `ALLOWED_EVENT_IDS` に足してもらう。
  - バックログの一覧（顔・話者・文）は areka が持ち、pasta は台本に目印の ID を埋める。選ばれた行の直近の ID を areka がイベントで知らせ、pasta はその時点の状態へ戻す。areka は目印を通った時点の画面と音を控え、演出なしで再現する。既読は台本を直さない限り変わらない ID で覚える。
  - セーブはスロットごとに areka が控え（画面・音・直近の ID）と縮小画像を持つ。
  - クリック送り・早送り・オート・既読とスキップは areka が持つ。自動の改ページ待ちは採らず、`\x` だけで待つ。
  - システム画面（タイトル・セーブ・ロード・設定）は、areka が部品だけを出し、シェルとして組み、pasta の場面が動かす。
  - 音: 曲（再生・停止・ループ・フェード・曲から曲への移り変わり・同じ曲は鳴らし直さない）・効果音（重ねる・ループ）・声（台詞に結び付く・次の台詞で止める・バックログから聞き直す）・区分ごとの音量・再生の終わりを待つ。
  - ほかに頼むこと: サーフェスの替わり方（瞬間・クロスフェード・ルール画像のワイプ）・揺れ・フラッシュ・色調・バルーンの話者名の欄・ルビ・`\f[…]`・縦書きの `\n[N]`・`\_l`・キーボード入力。
  - 「背景もトークの場所もシェルでありアクター」（pasta の 2026-10-10 の決定）。
- **pasta の多アーキと SHIORI4**: pasta に `pasta-dll-multiarch`（`pasta.x64.dll`・`pasta.arm64.dll`・LuaJIT の ARM64 は確かめていない危険）・`shiori4-v4-host`・`shiori4-v4-lua-api` が起票済み。入口は COM ではなく shiori4 の C ABI。
- **areka の SHIORI4**: `shiori4-api`（v0.2.0）が、COM の `IShiori`・`IShioriHost` と JSON-RPC の紙の契約をやめ、shiori4 の C ABI へ移る。SHIORI はどの版でも別プロセスの helper で動かす（2026-10-23）。DLL の選び方は shiori4 の `doc/textbook/distribution.md`。
- **areka の今**: 窓はキャラクター 1 人に 1 枚で、スコープは 2 人まで（`emo2_boot/mod.rs` の `derive_scopes`）。全画面と枠つきの普通の窓は無い。音を鳴らす所は 0（`\_v`・`\_V`・`\![sound,…]` は受け手が居ない）。目録の `Identity` は 7 項目で `craftmanurl` を持たない。正典の descript には `id`・`craftman`・`craftmanw`・`craftmanurl` がある。

## 決めたこと（2026-10-28・議題 1〜12）

1. **段**: 新しい段「ノベルゲーム基盤」を v0.4.0 の後ろに作る。番号は pasta の依頼書が届いてから振る。利用統計は「ノベルゲーム基盤と並走してよい（dola の整備の後）」の段。
2. **S1・P1 は起票しない**。S1 は `shiori4-api` と、P1 は pasta の 3 本と重なる。`shiori4-api` への書き足しも無し（演劇の種別を新しくする場合だけ戻る）。
3. **今 brief を書くのは 3 本**（`sound-canon-tags`・`shell-multi-compose`・`ghost-material-metadata`）。残りは依頼書を待つ。`shell-multi-compose` には場面転換も入れ、重ければ要件の段で切る。
4. **演劇は、pasta.dll を SHIORI とする、ゴーストと同じ形のパッケージ**。開発者「ノベルゲームエンジンとして『舞台をさくらスクリプトで制御する』という枠組みを崩さなければ対応可能と考えます。pasta.dll が、play の基盤として、同じく shiori インターフェースで動くものとします」。
   - `ghost/master` に SHIORI、`shell/` に舞台のシェルたち、それにバルーン。舞台は SHIORI が返すさくらスクリプトで動かす。
   - SHIORI は v4 を推すが、SHIORI/3.0 でも同じ台本で動く（P1 の前提「台本は SHIORI3 でも SHIORI4 でも同じ結果」）。選び方は今の descript の `shiori` のまま。
   - インストールの種別は、当面 `type,ghost` に「演劇である」印を足す見立て。新しい種別にするかは依頼書の「起動の形」と突き合わせて決める。
   - 別のゴーストの SHIORI を呼ぶ出演（cameo）は持たない。
   - SSP に入れられた場合の知らせ方（「areka で遊んでね」の台詞）は pasta への申し送り。
   - 開発者の追記「play についてはさくらスクリプトやキャラクター管理の拡張が必要だと考える。原則として任意のゴーストの任意のシェルを呼び出せるのが play の立場」。借りるのはシェル（見た目）だけで SHIORI は呼ばない。3 体以上の役者と、役者ごとのシェルの割り当ては `shell-multi-compose`、宛名は `ghost-material-metadata` の素材 ID、命令の名前は依頼書待ち。
5. **借りてよいか**: オプトアウト。どのシェルも借りられ、作者が descript に「借りないで」の印を書いたものだけ借りない。借りたシェルの作者表記（`craftman`・`craftmanurl`）を演劇の中で見られるようにする。利用者による差し替えも同じ規則。演劇の作者が「この席は替えさせない」と錠をかける側は要件の段で。
6. **メタデータのキー**: 正典のキー（`id`・`craftman`・`craftmanw`・`craftmanurl`）をそのまま使い、足りない分（ライセンス・支援先・シェルの role・「借りないで」・「演劇である」・席の要件）だけを areka の独自キーとして descript.txt に足す。席の要件は `surface*` ブレスと同じ書き方。「提供する能力」は使う側が現れるまで外す。開発者「まああとの議論で変わるかもしれないけど」。
7. **素材 ID の規則**: areka（`ghost-material-metadata`）が先に決め、U1 は後でそれを写して登記簿を足す。形は `種別:id`・同梱には親の前置き。id の元は descript の `id`、空ならインストール先のフォルダ名。探す順は要件の段で決める。開発者の叩き台（演劇 {play} から {shell} を探すとき）:

   2. `/free-shell/{shell}/`（開発者「シェルだけ公開したい人がいるかもしれないので」）
   3. `/ghost/{shell}/shell/master/`
   最初に当たったもので確定し、当たらなければ既定へ戻して未導入と記録する。「一度決めたら変えない」を作者向けに書く。
8. **音**: 正典の音のタグから作る（`sound-canon-tags`）。再生の土台は Media Foundation。置き場はノベルゲーム基盤の段の先頭。音楽 CD と動画は外す。ノベルの拡張（BGM のクロスフェード・区分の音量・声）は依頼書の後に積む。
9. **利用統計**: areka には `areka-usage-stats` の brief だけ。U1〜U3 は `usage-stats.md` で外のリポジトリへ渡す。
10. **原文の置き場**: この `doc/ideas/` の 2 文書。開発者は `doc` と `docs` の散らかりを指摘し、片付けの spec `doc-tree-tidy` を v0.2.0 に起票した（開発者「このspecだけは0.1.0の直後、doraとかの基盤整備に置きます」）。
11. **P2**: 検査だけが残る（descript のキーは `pasta_check release` が何もしなくても .nar に載る）。`ghost-material-metadata` がウェーブに載ったら、areka のセッションから pasta のセッションへ相談して決める（開発者「spec が次のウェーブに載ったタイミングで、areka セッションから pasta セッションを呼び出す形で相談して決めることにしましょう」）。
12. **`doc/PASTA_PROFILE.md`**: 作例の `\w[N]` 6 か所を `\_w[N]` に直し、「pasta が出す `\w[N]` は上流の欠陥」の注記を正しい出どころに書き直した（2026-10-28・pasta の取り決めの brief「依頼に添える訂正」に当たる）。

### M1:素材 ID とメタデータ契約 [areka。U1 の ID 規則に従う]

areka の素材(ゴースト、シェル、バルーン、演劇)に、安定した ID とメタデータ契約を導入したい。

要望:
- 種別は ghost / shell / balloon / play。同梱素材は親の ID を前置、単体のフリー素材は前置なし。
- シェルに role(character / background / stage=トークの出る場所)を持たせる。背景は独立した種別にせず、role=background のシェルとして扱う(pasta の決定: 背景もトークの場所もシェルでありアクター)。
- メタデータ: ID、種別、作者、配布ページ、支援先 URL、ライセンス、swappable(差し替え許可)、cameo(出演許可)、slots(要求。アスペクト比、配置人数、サーフェス要件など)、提供する能力。
- 差し替えは呼ばれる側のオプトイン(既定は不可)。呼ぶ側がスロット要件を宣言し、満たさない素材は警告して既定の素材に戻す。
- フリーゴースト、フリー演劇は持たない。演劇は最上位の単位で、入れ子にしない(将来「章」で拡張する余地は残す)。
- 既存の素材(ID なし)を後方互換で扱う移行方針。
- 起動画面や About から、作者の配布ページ・支援先へ誘導できる。

抜けてはいけない検討項目:
- ID の決め方と安定性(作者の命名、登録簿との関係、改名・移管時の扱い)。ID の衝突と偽装への対処。
- メタデータの置き場所(.nar 内の記述、descript 系の独自キー、別ファイル)。SSP など他ベースウェアとの互換を壊さない。
- ゴーストの cameo は既定で不可。許可の宣言方法と、演劇側からの確認方法。
- ライセンスと作者表記の持ち方(素材ごと、再配布可否、商用利用可否)。
- U1 の登録簿と、素材側メタデータの項目の整合。

### M2:演劇(play)のパッケージと素材契約 [areka。M1 に依存]

pasta で書いたノベルゲームを、複数のシェル(role: background / character / stage)とバルーンで組み合わせて遊ぶ、作品の単位「演劇(play)」の素材モデルとパッケージ形式を、areka に導入したい。台本の進行と巻き戻しは pasta が持つ(Phase 13)。areka は素材のまとまりと契約を扱う。

要望:
- 構成要素: シェル、バルーン、台本(pasta の辞書)、使う SHIORI。同梱素材は演劇の ID を親とし、フリー素材(フリーシェル / フリーバルーン)は ID で参照する。
- 演劇は最上位で入れ子にしない。フリーゴースト、フリー演劇は持たない。
- 呼ぶ側(演劇)がスロット要件を宣言し、呼ばれる側の swappable / cameo と突き合わせる。満たさない素材は警告して既定に戻す。
- 依存するフリー素材の解決(未導入の検出、取得先 URL の提示)。

抜けてはいけない検討項目:
- 最初の調査項目: 「演劇に含まれるゴースト」が、pasta のアクター(演劇の辞書で定義するもの)なのか、別のゴーストの SHIORI を呼ぶ出演(cameo)なのか。後者なら、ゴースト側の cameo 許可がある場合に限る。
- 使う SHIORI の指定方法(pasta の SHIORI3 / SHIORI4、他の SHIORI)。S1 と整合させる。
- パッケージ形式: 既存の .nar(areka-nar)の拡張か、別形式か。pasta_check が作る NAR との整合。版と互換性の扱い。
- 既存のゴーストカタログ、インストール、更新との整合。
- 利用統計向けの信号(再生開始、シーン到達、再生完了、利用した素材と via、override)を定義する(U4 向け)。
- 異常終了や素材欠落時に、areka 本体が落ちないこと。

### N4:pasta との契約の窓口 [areka。pasta の novel-areka-contract を実装する]

areka に、pasta との取り決め(novel-areka-contract)を実装する窓口を作りたい。他リポジトリからの依頼は、この discovery を起点に受ける。

- システム画面(タイトル、セーブ、ロード、設定)をシェルとして組むための部品の提供と、見本の同梱。
