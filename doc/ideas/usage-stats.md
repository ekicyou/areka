# 利用統計の案（U1〜U4）

2026-10-28 の `/kiro-discovery`（利用統計・ノベルゲーム基盤の 16 案）で開発者から受けた案のうち、利用統計の 4 案の原文と、そのとき決めたことを残す。

- areka の持ち場は U4 だけで、`.kiro/specs/areka-usage-stats/brief.md` に起票した。
- U1〜U3 は areka の外の新しいリポジトリの持ち物。リポジトリを作ったら、この文書を持ってそちらで `/kiro-discovery` を回す。
- 段は「ノベルゲーム基盤と並走してよい（dola の整備の後）」（`roadmap.md` の版の段）。

## 決めたこと（2026-10-28）

### 要件（開発者の言葉）

> 要件だけ、ユーザーを秘匿しつつ、ユーザーごとに識別して、1日単位で利用状況を集計し、結果をGithub Pagesで集計サイトとして公開したい、です。

- 版は「ノベルゲーム基盤の後ろ」。ただし「利用集計は play とは独立して進められるので、dola が終わったタイミングでノベルゲームと並走するかもしれません」。
- 細かい作り（下の A〜G）は「実装のときに考えればよい」。要件にはしない。

### 原文の前提から変わったこと

- 開発者「nostr の集計は、誰の投票なのかを特定せず、投票があったことも秘匿しつつ、集計を行いたい。具体的には、個人特定 ID として 256bit の乱数、投票は集計アカウントの公開鍵で暗号化する感じ、集計後の一時ファイルはすべて削除、などのアイデアを聞いています」。
- これで次の 3 つの前提が裏返る。
  - U1「受信専用の宛先公開鍵は持たない」→ 集計者の鍵（期ごと）を持つ。
  - U3「Secrets は原則ゼロ」→ 期の秘密鍵を Secrets に置く。
  - U3「誰でも生データから再計算で検証できる」「ブロックリストを PR で」→ 中身は集計者しか読めない。受けた外側のイベントの ID と件数だけを公開する。
- U1 の題の「匿名」は、U4 の「『匿名』と書かない」とぶつかる。文言は「誰が送ったかは集計者にも外の人にも分からない。ただし接続元の IP は中継の運営者に見える（Tor で隠せる）。集計者は期の間だけ中身を読める」の形で正確に書く。

### 実装のときの候補（A〜G・決定ではない）

- **A. 方式**: 公開の再計算での検証をやめ、集計者を信頼する暗号化の方式にする。外側のイベントは NIP-59（gift wrap）、中身は集計者の公開鍵へ NIP-44 で暗号化する。外側は 1 回ごとの使い捨ての鍵で署名する。
- **B. 鍵**: 集計者の鍵は期ごとに作る。期の集計が済んだら期の秘密鍵を壊す（前方秘匿）。期の公開鍵には、手元だけに置く長く持つ鍵（集計者の身元の鍵）で署名して告知し、U2 はその署名を確かめてから使う。
- **C. 期の長さ**: 30 日。期の長さが「不正が見つかったときに再計算できる窓」になる。
- **D. 文言**: 上の「原文の前提から変わったこと」の文言。
- **E. 日の切り方**: 中継の留め置き期間には決まりが無い（NIP-11 の `retention` は名乗るだけ）。中身に「利用した日（UTC）」を入れ、毎日の実行は前の日の分だけを数える。取りに行くのはここ 4 日ほど（NIP-59 の時刻のずらし最大 2 日＋1 日＋余裕）。同じイベントは ID で、同じ利用者は 1 日 1 回にまとめる。送る側は NIP-40 の期限を 7 日ほどにする。これで中継に求めるのは「1〜2 日持っていてくれること」だけになる。
- **F. 日をまたぐ控え**: 継続日数の控えは `HMAC-SHA256(期の秘密, 利用者 ID)` と「出た日」だけを持つ（素の SHA-256 では、生の ID を手にした人が突き合わせられる）。継続は期の中だけで数える。期の秘密を壊せば、控えのファイルが残っていても、どの ID とも結び付かない（暗号学的消去）。期をまたぐ継続は、送る側の粗い自己申告で軽く補う。復号した中身はディスクに書かず、メモリーの中だけで扱う。
- **G. Secrets**: 期ごとに 1 つ（期の秘密鍵）だけを、`main` の枝に限った Environment に置く。HMAC の鍵はそこから HKDF で導く（2 つに分けると期をまたいで数えられるが、漏れたときに過去の控え全部と結び付く）。身元の鍵は手元だけ。期の鍵は手元で作り、ディスクに書かずに `gh secret set` の標準入力へ流す。期の終わりに `gh secret delete` で消す（GitHub の内側で本当に消えたかは確かめられない＝GitHub を信頼する前提）。書き込める人は Secrets を抜き出せるので、外の PR には Secrets を渡さない（`pull_request_target` を使わない）。Action は SHA で固定する。
- **ほか**: 使い捨ての鍵が安く作れるので、外側のイベントに PoW（NIP-13）を必須にするのが水増しの費用を上げる一番手。kind 1059 を宛先の認証（NIP-42）なしに渡さない中継が多い見込みで、集計者は期の鍵で認証して取りに行く。2 つの集計者に票を分けて持たせる方式（Prio／DAP）や局所差分プライバシーは、サーバー 2 台が要る・伺かの界隈の数では揺らぎが答えを呑み込む、ので採らない見込み。
- **確かめていないこと**: NIP-59・NIP-44・NIP-13・NIP-11 の `retention`・kind 1059 の読みの制限の細かい点は記憶で書いた。U1 を書く段で原文と実際の中継に当たり直す。

### 軽い代わり（将来の候補）

- 正典のプロパティ `rateofuselist.*`（手元に残る使用率・登記だけ済み・`property-catalog-lists`）。
- 「使ってます」を Mastodon・Misskey で共有する、共有 URL 方式のボタン（U4 の任意の検討の項）。

## 原文（2026-10-28 開発者）

### U1:利用統計の仕様と素材登録簿 [新規の公開リポジトリ。U3 の集計サイトと同居]

伺か系ベースウェア横断の、匿名の利用統計イベント仕様と、素材登録簿を、公開リポジトリで定義したい。areka 以外のベースウェアも同じ仕様で送れること、素材作者が「使われている」ことを実感できることが目的。成果物は Markdown の仕様書と JSON Schema。実装は含めない。

要望:
- 送信基盤は nostr。利用者1人につき、アドレス指定可能イベント1件(kind 30078)に、利用した素材を列挙する。
- 受信専用の宛先公開鍵は持たない。kind とタグだけでイベントを識別する。
- 素材種別は ghost / shell / balloon / play の4つ。背景は種別にせず、shell の role(character / background / stage)で表す。
- 素材 ID は「種別:id」。ゴースト等への同梱素材は親の ID を前置(例 shell:foo/default)。単体のフリー素材は前置なし。
- 利用の文脈を表せること。演劇経由・ゴースト経由(via)と、利用者による差し替え(override)を、作者が意図した組み合わせと区別して数えられること。
- 部分対応を許す。areka 以外のベースウェアは ghost / shell / balloon だけ送ってよい。play は areka 固有。
- フリーゴースト、フリー演劇は当面持たない。将来 via の値を拡張すれば足せる形にしておく。
- 素材登録簿: 既知素材の ID、種別、作者、swappable(差し替え許可)、cameo(出演許可)、slots(要求)など。未登録 ID の扱いを決める。

抜けてはいけない検討項目:
- d タグの値の命名規則と版数(例 areka-usage/1)。kind 30078 は他アプリも使う汎用なので、衝突しない接頭辞を決める。d が pubkey+kind+d の置換単位であることを前提に設計する。
- t タグ: フィルタで検索できるのは1文字タグの最初の値だけ。2番目以降の要素(via など)は保存されるが検索できない。検索したい情報は最初の値に入れる。
- 1イベントのタグ数の上限(NIP-11 の max_event_tags などに収まる範囲)。直近利用から上限件数までに絞る規則。
- 置換可能イベントはリレー上に最新1件しか残らない。履歴(継続日数など)は集計側の日次スナップショットで作る前提を明記する。
- expiration タグ(NIP-40)は削除の保証にならない。集計側で created_at により古いデータを切る。
- client タグ(ベースウェア名・版)と alt タグ(人が読める説明)の付与規則。nonce(NIP-13 PoW)を将来要求できる余地。保護イベント(NIP-70 の「-」タグ)を使うかどうかの検討。
- content は JSON で、版(v)と粗い値(継続日数、利用時間の区間など)だけ。個人情報、ローカルパス、PC 固有の識別子を禁止する。
- 鍵の運用モード(永続 / 日ごと / 使い捨て)を、イベントのタグで区別できること。モードごとの集計上の重み(継続性を満たせないモードは軽くする)を決める。
- created_at はクライアントの自己申告。許容範囲を決める。
- プライバシー文言: 「公開鍵のみで送るが、接続元 IP はリレー運営者に見える」を正確に書く。鍵のリセット、鍵の使い回しの禁止(areka 専用鍵)。
- 素材 ID の安定性と、偽装・水増しへの対処(登録簿との突き合わせ)。
- 仕様の版管理と、後方互換の方針。

### U2:利用統計の発信コンソールアプリ [新規リポジトリ。Rust・単体バイナリ。U1 に従う]

利用統計を発信する専用のコンソールアプリを作りたい。ベースウェアは CLI で呼ぶだけにして、鍵・同意・送信をこのアプリに集約する。areka 以外のベースウェアも使える。

要望:
- 利用者ごとの鍵の生成と保存。OS の資格情報ストアを優先する。
- オプトイン状態の管理。同意の正はこのアプリの設定とし、ベースウェア側の UI と食い違わないようにする。
- U1 の仕様に従ったイベントの作成、署名、複数リレーへの送信、再送。
- ベースウェアからは CLI(引数または標準入力の JSON)で呼ぶ。都度起動が基本で、常駐は不要。
- 送信内容のプレビュー(dry-run)、送信の一時停止、鍵のリセット、運用モード(永続 / 日ごと / 使い捨て)の切り替え。
- 送信先を抽象化し、将来 nostr 以外(HTTP API など)へ差し替えられる、または併送できる。
- 秘密は持たない設計。共通の鍵や API キーを埋め込まない。

抜けてはいけない検討項目:
- リレー一覧は設定ファイルで外出しし、更新できること。送信前に NIP-11 を取得し、制限(最大タグ数、PoW、認証要否、created_at の許容幅)を守る。守れないリレーは自動で外す。
- 送信頻度は1日1回程度。起動直後に一斉送信しないよう、ランダム遅延を入れる。拒否(OK false)やレート制限の応答でバックオフし、再試行を控える。
- 複数リレー(例 3〜5個)へ送る。どれかが落ちても成立すること。置換可能イベントなので、定期的な再送でリレー側に最新を残す。
- プロキシ(SOCKS5 / Tor)指定。
- 失敗しても呼び出し元のベースウェアに影響しないこと(終了コードと標準出力の規約を決める)。
- 依存の重さ(nostr / nostr-sdk、非同期ランタイム、TLS)。ライセンスは MIT / Apache 系の範囲に収め、cargo-deny でゲートする。
- ターゲットは x64 と arm64(Windows)。
- ログに鍵や素材の一覧、ローカルパスを出さない。

### U3:利用統計の集計とランキング公開サイト [U1 と同じ公開リポジトリ。GitHub Actions だけで完結]

nostr のリレーから利用統計イベントを取得し、素材別のランキングを集計して公開する、サーバーレスの集計サイトを作りたい。不正に強く、誰でも再計算で検証できること。

要望:
- 取得は読むだけで、秘密鍵は不要。Secrets は原則ゼロ。
- 生イベントを追記のみで日次スナップショットとして保存し、リレーの保持に頼らない。
- 集計は毎回、生データから全期間を再計算する(決定的)。ルールとしきい値は git 管理して公開する。後から不正が見つかったら、ブロックリストに鍵を足して再実行すれば過去分も正される。
- ブロックリストは PR で提案し、根拠を残す。
- 指標: 素材別の継続利用者数、新着、更新頻度。フリー素材は「使った親の数」。直接利用、演劇経由、override を別軸で出す。シェルは role 別にも出す。
- 公開物は静的ページと JSON。生の公開鍵は出さず、素材別の数だけを出す。

抜けてはいけない検討項目:
- 検証: 署名、kind、d タグの形式、タグ数、created_at の範囲(未来・遠い過去は除外)、素材 ID の形式と登録簿との突き合わせ。
- 不正対策: 鍵の継続性(複数日にわたる出現)を要件にする。1鍵あたりの上限。継続している鍵ほど重く、新しい鍵は軽く数える。運用モード別の重み。異常検知(特定素材の急増、同時刻の新規鍵の大量出現)と保留。母数が小さい素材は順位でなく区間表示(k 匿名性のしきい値)。PoW 要求は将来の選択肢。
- 取得は礼儀正しく: kind とタグで絞り、since と limit を使う。複数リレーから取り、タイムアウトと再試行を設ける。取得漏れを許容する。
- 蓄積データの肥大化対策(コミットの運用、別ブランチ、Releases、Artifacts の使い分け)。保存期間と、集約・間引きの方針。
- 集計は DuckDB 等の SQL で宣言的に書く。ローカルでも Actions でも同じ動作にする。
- Actions: schedule(日次)と workflow_dispatch。concurrency で直列化。失敗時は前回の公開結果を維持する。60日無活動でスケジュールが止まる件への対策。
- セキュリティ: pull_request_target で外部コードを実行しない。permissions を最小にする。Action は SHA 固定。ログに秘密を出さない。
- 将来、規模が増えたときに移行できるよう、集計ロジックを独立したスクリプトにしておく。
- 公開物にベースウェア別の内訳を出すか、個人が特定されないかの確認。

### U4:areka の利用統計連携 [areka]

areka に、利用統計の発信連携を追加したい。発信そのものは別リポジトリのコンソールアプリ(U2)に任せ、areka は CLI で呼ぶだけにする。nostr の依存は areka 本体に入れない。依存: U1、U2、M1、M2。

要望:
- 初回起動時と設定画面で、オプトインを明示的に取る。既定は無効。
- 「使った」の判定。一定時間以上の利用を条件にする。演劇は再生完了やシーン到達(場面への到達)などを条件にする。
- 利用した素材(ghost / shell / balloon / play)と via、override を、M1 の ID で収集し、1日1回、上限件数までまとめて渡す。
- 鍵のリセット、運用モードの切り替え、送信内容のプレビュー、送信の一時停止を、設定画面から行える。
- 発信器が未導入・失敗でも areka の動作に影響しない。失敗時は黙ってスキップする。

抜けてはいけない検討項目:
- 同意の正は発信器側の設定。UI の表示と食い違わない仕組み。
- 説明文は「公開鍵のみで送るが、接続元 IP はリレー運営者に見える」と正確に書く。「匿名」と書かない。
- ログや統計に、ローカルパス、個人名、PC 固有の識別子を含めない。
- 素材の ID が無い既存素材の扱い(送らない、または未登録として扱う)。
- 任意の検討: 「使ってます」を SNS(Mastodon / Misskey)で共有する、共有 URL 方式のボタン。OAuth は実装せず、本文は利用者が確認して送る。
- 起動画面や About から、作者の配布ページ・支援先へ誘導できること(M1 と整合)。
