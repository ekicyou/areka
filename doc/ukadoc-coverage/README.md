# ukadoc 網羅調査の台帳の手引き

この `doc/ukadoc-coverage/` は、SSP 公式仕様書（ukadoc）の全 1,749 項目について
「areka はこれをどこまで実現しているか」を 1 か所で読めるようにするための一式である。

読み手として想定しているのは、調査 spec 4 本（shiori・assets・sakura-script・property）の
担当者で、これから自分のドメインの台帳を埋める人である。**この文書を上から一度読めば、
台帳 1 項目を正しく書けるようになる**ことを目指して書いてある。

書いてあるのは次の 5 つである。

1. [台帳の形式と状態の語彙](#1-台帳の形式と状態の語彙)
2. [仕訳の規則](#2-仕訳の規則)
3. [正典 URL の書き方](#3-正典-url-の書き方)
4. [報告の扱い](#4-報告の扱い)
5. [調査 spec と道具の合流](#5-調査-spec-と道具の合流)

**形式そのものは凍結されている。** 台帳の項目形式・状態の語彙・ドメインの分割を変えるには、
要件（`.kiro/specs/completed/areka-P0-ukadoc-survey-toolkit/requirements.md`）の改訂が要る。
思い付きで欄を足したり語を言い換えたりはできない。この文書は凍結された取り決めの案内であって、
取り決めそのものではない（正本は要件 2.1・2.2・2.6 と付録 A）。

## この一式に入っているもの

| ファイル | 誰が書くか | 中身 |
| --- | --- | --- |
| `catalog.toml` | 機械だけ | 正典 1,749 項目の写し。1 項目 1 行 |
| `ledger/<ドメイン>.toml` | **人が書く**・機械が検査する | areka 側の判定。1 項目が複数行の塊 |
| `values.md` | 人が書く | 「伺からしさ」のテーマ 8 つの定義 |
| `report/<ドメイン>.md` | 機械だけ | 台帳 1 本から作り直す網羅状況 |
| `report/summary.md` | 機械だけ | 4 台帳をまとめた全体の網羅状況 |
| `README.md`（この文書） | 人が書く | 手引き |

道具は `crates/ukadoc-survey` にある。副手続きは 8 つで、いずれも引数を取らない。

```
cargo run -p ukadoc-survey -- catalog          # 正典のカタログを作り直す（スナップショットが要る）
cargo run -p ukadoc-survey -- ledger-init      # 初期の台帳を作って既存の台帳へ差し込む
cargo run -p ukadoc-survey -- report           # ドメイン別の報告 4 本を作り直す
cargo run -p ukadoc-survey -- report-summary   # 全体の報告を作り直す
cargo run -p ukadoc-survey -- check            # 台帳と正典とソースの食い違いを調べる
cargo run -p ukadoc-survey -- evidence         # 項目ごとの証拠を並べる
cargo run -p ukadoc-survey -- candidates       # 正典 URL を置く場所の手掛かりを並べる
cargo run -p ukadoc-survey -- diff             # 今のカタログと新しいスナップショットの差（スナップショットが要る）
```

同じ検査は標準のテスト実行にも入っている。**台帳を触ったら `cargo test -p ukadoc-survey` を
走らせること。** ネットワークにも実機にもスナップショットにも触らないので、どの環境でも同じ
結果になる。

各ドメインの持ち分は次のとおり（要件 3.1・実データで確認済み）。

| ドメイン | 台帳 | 担当ページ数 | 項目数 |
| --- | --- | ---: | ---: |
| shiori | `ledger/shiori.toml` | 12 | 677 |
| assets | `ledger/assets.toml` | 24 | 542 |
| sakura-script | `ledger/sakura-script.toml` | 1 | 342 |
| property | `ledger/property.toml` | 1 | 188 |
| 合計 | | 38 | 1,749 |

**あなたが編集するのは 3 か所だけである。** 自分の台帳 1 本と、自分のドメイン別報告 1 本
（機械で作り直す）と、ソースに置く正典 URL のコメント。他のドメインの担当者と取り合うファイルは
1 つも無い。

## 1. 台帳の形式と状態の語彙

### 1 項目の書き方

台帳は TOML で、1 項目が 1 つのキー付きテーブルになる。実物（`ledger/property.toml` の
初期状態）はこうなっている。

```toml
[entry."ukadoc:list_propertysystem:system.year:1"]
status = "unclassified"
introduced = ""
owner = ""
priority = ""
values = []
links = []
note = ""
```

1 項目を 1 行に詰める形は採らない。人が手で書き換える文書なので、差分を項目単位で読めることを
優先している。

ファイルの先頭にはコメント 3 行と前置きの `[ledger]` が付く。

```toml
# doc/ukadoc-coverage/ledger/property.toml
# 人手で記入・機械で検査する台帳。形式の正本は
# .kiro/specs/completed/areka-P0-ukadoc-survey-toolkit/requirements.md 付録 A。

[ledger]
domain = "property"
pages = ["list_propertysystem"]
```

`domain` はファイル名と同じでなければならない。`pages` は担当ページの一覧で、ここに無い
ページの id は置けない。

### 欄の意味

| 欄 | 型 | 必須 | 書き方 |
| --- | --- | --- | --- |
| （テーブル名） | `[entry."<項目 id>"]` | 必須 | カタログの id をそのまま写す。二重引用符で囲む。1 ファイル内で重複禁止。**id の文字順に厳密な昇順で並べる**（同じ id が隣り合うのも誤り） |
| `status` | 文字列 | 必須 | 下の 7 語のいずれか |
| `introduced` | 文字列 | 必須 | 登場した SSP の版番号（例 `"2.3.53"`）。分からなければ `""` |
| `alias_of` | 文字列 | `status = "alias"` のときだけ書く | 正典側の id。指す先が また `alias` であってはならない |
| `supersedes` | 文字列の配列 | 任意 | この項目が置き換えた旧 id の一覧 |
| `owner` | 文字列 | 必須 | 担当 spec 名（`areka-P0-...`）。未定なら `""` |
| `priority` | 文字列 | 必須 | 段階 1 文字（A〜E）＋数値（例 `"C1"`）。仮置き。未定なら `""` |
| `values` | 文字列の配列 | 必須（空でよい） | `values.md` にあるテーマ名だけ |
| `links` | インラインテーブルの配列 | 必須（空でよい） | `{ kind = "<種別>", to = "<相手 id>" }` |
| `note` | 文字列（複数行可） | 必須（空でよい） | 備考。壊れ方の根拠・縮退の写し・テーマを付けた理由など |

書き終えた 1 項目は、たとえばこうなる（id と `queries` の相手 id は実物のカタログから取った。仕分けの中身は説明のための作り物である）。

```toml
[entry."ukadoc:list_propertysystem:currentghost.balloon.scope_28ID_29.validwidth:1"]
status = "absent"
introduced = ""
owner = "areka-P0-ukadoc-survey-property"
priority = "C2"
values = ["装い"]
links = [
  { kind = "queries", to = "ukadoc:list_sakura_script:_5c_21_5bget_2cproperty_2c_30a4_30d9_30f3_30c8_540d_2c_30d7_30ed_30d1_30c6_30a3_540d_2c_30d7_30ed_30d1_30c6_30a3_540d_2c:1" },
]
note = """
壊れ方: 値を返せないと辞書側が空文字を前提に進み、何も言わずに変な位置で改行する。
ログは出ない（黙って壊れる）。
"""
```

### 状態の 7 語

`status` に書けるのはこの 7 つだけである。綴りが違えば読み込みの段で失敗し、どのファイルの
どの id かを名指しで教えてくれる。

| 語 | 日本語の呼び名 | いつ使うか |
| --- | --- | --- |
| `implemented` | 実装済み | areka が正典どおりに動く。**ソース側に正典 URL の証拠が要る**（下の 3 章） |
| `vocabulary-only` | 語彙のみ | 名前だけ登記してあり、受け取っても何もしない |
| `degraded` | 縮退 | 動くが正典どおりではない。どう違うかを `note` に書く |
| `absent` | 未対応 | まだ何も無い |
| `alias` | 別名 | 同じ機能の古い書き方。`alias_of` に正典側の id を書く |
| `not-applicable` | 対象外 | areka の作りでは意味を持たない項目 |
| `unclassified` | 未分類 | まだ調べていない。初期状態 |

`alias` の行が持つのは「正典側の id への写像があるか否か」だけである。**実装しているかどうかの
判定はその行に書かない**——写像先の正典行に委ねる。だから `alias` の行の `status` を見ても
実装状況は分からないし、分かるべきでもない。

### カタログと台帳は別の責務

* `catalog.toml` は**機械だけが書く**。正典の写しであって、areka の意見は 1 文字も入らない。
  手で編集しない。作り直すのは `cargo run -p ukadoc-survey -- catalog` で、スナップショットが要る。
* `ledger/*.toml` は**人だけが書く**。areka 側の判定はここにしか無い。機械がするのは検査だけで、
  値を書き換えることはしない（唯一の例外が `ledger-init` の「欠けている id を初期値で差し込む」で、
  これは既存の塊のバイト列に一切触れない。5 章）。

この分け方があるので、正典が新しくなったときに何が変わったかは `diff` で分かり、あなたの判定は
そのまま残る。**台帳に証拠の欄は無い**（要件 2.3）。実装済みの根拠はソース側の 1 行コメントで、
それを集めるのは検査の仕事である。ソースを整理してファイルが動いても、台帳を書き直さずに済む。

### ⚠ id は符号化済み——見た目で直さず、カタログから写す

id の 3 番目の区切りは正典ページの見出しから機械で作られた文字列で、**ASCII の記号も日本語も
`_28`（`(`）・`_5c`（`\`）・`_30a4`（`イ`）のように符号へ置き換えられている**。実データの id
1,749 件のうち、丸括弧をそのまま含むものは 0 件、逆斜線をそのまま含むものも 0 件である
（実物 1,749 行を全件突き合わせて確認した）。

たとえば `\![get,property,…]` のタグの項目の id は
`ukadoc:list_sakura_script:_5c_21_5bget_2cproperty_2c_30a4_...:1` と綴られ、`currentghost` の
バルーンの文字描画に使える幅は `...currentghost.balloon.scope_28ID_29.validwidth:1` と綴られる。

ここから 2 つの決まりが出る。

* **id は必ずカタログから写す。** 見た目で書き下したり、読みやすいように直したりしない。
  1 文字でも違えば検査が `LedgerIdNotInCatalog` で失敗する。
* **台帳の id で逆斜線を書く場面は 1 度も無い。** 逆斜線を含むのは*見出し*（1,749 件中 316 件）
  であって id ではない。見出しは台帳に写さないので、台帳で逆斜線を書くのは `note` の中だけであり、
  そこでは TOML の決まりどおり `\\` と 2 つ重ねる（要件 付録 A.3）。

要件の付録 A.1 の記入例は、2026-09-05 まで実在しない綴りの id（`balloon.scope(ID).width` など）を
挙げていた。同日に実在する id へ差し替え済みである。要件と この README の TOML の囲みに現れる id が
すべてカタログに実在すること、付録 A.1 の記入例が台帳の読み手でそのまま読めて id 順に並んでいることは
`crates/ukadoc-survey/tests/consistency/examples.rs` が常時確かめている。

自分のドメインの id 一覧は `catalog.toml` から取るのが確実である。

```bash
grep -o '^"ukadoc:list_propertysystem:[^"]*"' doc/ukadoc-coverage/catalog.toml
```

## 2. 仕訳の規則

判断がドメインごとにばらつかないように、規則は全部ここに書いてある。迷ったらここへ戻る。

### 新旧の書式は、どちらを正典にするか

同じ機能に複数の書き方があるときは、**最も新しい書き方を正典とし、それ以外を別名（`alias`）とする**。
どちらが新しいかは、次の順番で決める。**上の根拠が使えるときは、下の根拠を見ない。**

1. **正典本文の注記** — 「廃止予定」「旧」「〜に統合された」と書いてあれば、それが答え。
2. **SSP の版番号** — カタログの `versions` 欄が持っている。後から出た方が新しい。
3. **人の判断** — 上の 2 つでは決まらないとき。なぜそう決めたかを `note` に書く。

正典側の行にはふつうの状態（`implemented` など）を書き、別名側の行に `status = "alias"` と
`alias_of = "<正典側の id>"` を書く。**別名の指す先がまた別名になってはいけない**。2 段の連鎖に
なると検査が `AliasChain` で失敗する。3 つ以上の書き方があるときは、全部が同じ 1 つの正典を
指すようにする。

### 版番号が無い項目を、最も古いと決めつけない

`introduced` が `""` の項目は「**世代不明**」であって、「最も古い世代」ではない。実データで数えると、
カタログ 1,749 件のうち版番号を 1 つ以上持つのは **406 件**、**1,343 件は 1 つも持たない**。
持たないものが古いという意味ではなく、正典本文がその情報を書いていないだけである。

* 版番号を 1 つだけ持つ項目は、`introduced` にそれを写せばよい。
* **版番号を 2 つ以上持つ項目が 23 件ある。** 機械はどちらか一方に絞らない（要件 1.2 が意図して
  そうしている）ので、**人が正典本文を読んで選ぶ**。たとえば
  `ukadoc:descript_ghost:shiori.logo.file_2c_30d5_30a1_30a4_30eb_540d:1` は
  `versions = ["2.4.26", "2.8.56"]` を持つ。登場が 2.4.26 で、2.8.56 は仕様が変わった版かもしれない
  ——本文を読まなければ決まらない。選んだ根拠を `note` に書くこと。
* 版番号を 1 つも持たない項目は `""` のままにする。埋めない方が正しい。

`introduced` に書いた値は検査が守る。カタログ側が版番号を 1 つ以上持つのに、書いた値がその中に
無ければ `IntroducedNotInCatalogVersions` で失敗する。カタログ側が空なら何も言わない。

### 関連の種別は 6 つ

`links` の `kind` に書けるのはこの 6 つだけである。

| 種別 | 向き | 意味 |
| --- | --- | --- |
| `alias_of` | 旧 → 新 | 古い書き方から新しい書き方へ |
| `supersedes` | 新 → 旧 | 新しい書き方から古い書き方へ |
| `triggers` | 操作・タグ → イベント | これをすると、あのイベントが飛ぶ |
| `configures` | 設定キー → 挙動・タグ・イベント | この設定が、あれの動きを決める |
| `queries` | タグ・イベント → プロパティ | これがあの値を読む |
| `same-feature` | 双方向 | 同じ機能の別の面 |

**⚠ 束に出したい繋がりは、専用の欄だけでなく `links` にも書くこと。**
報告に出る「関連が閉じている束」は `links` だけから組み立てる（設計 D-11）。
`alias_of` の欄だけで結んだ対は「別名の一覧」に出るので目には入るが、**`supersedes` の欄だけで
結んだ対はドメイン別報告のどこにも現れない**。書いたのに読めない、という形になる。
両方に書いても構わない（付録 A.2 が許している）ので、繋がりとして見せたいなら `links` にも
1 行足しておく。

### ⚠ ドメインを跨ぐ `links` は、機械が 1 つも検証しない

これは仕組み上そうなっていて、直せるものではない。**あなたは必ずここに踏み込む**ので、先に書いておく。

`links` の相手 id が、カタログには在るが**別のドメインの台帳の持ち物**である場合——

* 相手が実在するかの検査（`LinkEndpointMissing`）は**通る**。カタログに在るから。
* ドメイン別報告の束は、**構成 id の全員がその台帳に居るときだけ**載る。1 人でも他所の台帳なら束ごと落ちるので、**報告にも現れない**。
* 全体報告（`summary.md`）はドメインを跨いだ束を載せるが、その新しさは常時の検査に入っていない。

結果として、**綴りが間違っていても、相手の状態が矛盾していても、何も失敗しない**。
（`alias_of` は別で、こちらはドメインを跨いでも検査される。台帳 4 本すべてを見て
別名の鎖をたどるためである。検証されないのは `links` と `supersedes` の側だけ。）
だからドメインを跨ぐ関連を書くときは、次の 2 つを自分でやること。

1. 相手 id を**カタログから写す**（自分で打たない）。
2. 相手のドメインの担当者に一言伝えて、向こうの台帳にも対になる関連を書いてもらう。

同じ理由で、`summary.md` の「ドメインを跨いだ束」の一覧は、統合担当（`ukadoc-coverage-roadmap`）が
作り直したときにだけ更新される。跨いだ関連を書いたら、そのことを統合担当に申し送ること。

### 伺からしさのテーマ

`values` に書けるのは `values.md` に見出しとして並ぶ 8 つの名前だけである
（気配・触れ合い・掛け合い・装い・記憶・交わり・気配り・更新）。他の綴りは `UnknownTheme` で失敗する。

付与の規則は 1 つだけ。

> 「この項目が無いと利用者はゴーストの何を失うか」に答えられるテーマだけを付け、
> 答えられなければ何も付けない。

迷ったら付けない。空欄は「まだ答えていない」ことをそのまま表すので、無理に埋めるより正しい。
定義と代表項目は `values.md` にある。

### 優先度 — 根拠は 4 つ、序列は固定

どの項目から手を着けるかは、次の 4 つで決める。**この並びは固定で、上が下より必ず強い。**

1. **壊れ方** — 黙って壊れる（誤った結果を正常な顔で見せる場合を含む）＞ 明示的なエラー ＞ 見た目の差
2. **伺からしさのテーマ** — `values.md` の 8 つ
3. **影響する既存資産の広さ** — 世に出ているゴースト・シェル・バルーンのうち何割が使うか
4. **依存する基盤の共有度** — 直すと他の何本が一緒に前へ進むか

1 で差が付いたら 2 以下は見ない。1 が同じなら 2 を見る、という読み方をする。

### 段階（A〜E）の最終決定はここでは行わない

`priority` の頭 1 文字（A〜E）は**仮置き**である。最終的な段階を決めるのは統合担当
（`ukadoc-coverage-roadmap`）で、4 本の台帳が出揃ってから全体を見て決める。
調査 spec は「自分のドメインの中での見立て」を置くだけでよく、他ドメインと段階を揃えようとして
待つ必要は無い。後ろの数値（`C1` の `1`）は同じ段階の中での並びで、これも仮置きである。

### 壊れ方の根拠は備考に書く

上の根拠 1「壊れ方」は、読む人が後から検算できなければ意味が無い。だから `note` に**根拠**を書く。
書くのは「どのログが出るか・出ないか」である。

```toml
note = """
壊れ方: 黙って壊れる。未知のキーは既定値に落ちるが、ログが 1 行も出ない。
（明示的なエラーなら、どのログ行がどう出るかをここに書く）
"""
```

`note` は複数行を許すので、縮退の内容・テーマを付けた理由・版番号を選んだ理由も同じ欄に足してよい。
欄を増やすことはできない（形式が凍結されている）ので、文章で書く。

## 3. 正典 URL の書き方

`status = "implemented"` と書いた行には、**ソース側に根拠が実在すること**が求められる。
根拠が無ければ検査が `ImplementedWithoutEvidence` で失敗する。

### 何を証拠と呼ぶか

証拠は「**ソースの定義箇所に置かれた、正典 URL 1 行のコメント**」だけである。

```rust
/// ukadoc: https://ssp.shillest.net/ukadoc/manual/list_shiori_event.html#OnSecondChange:1
```

行番号も内部 ID も証拠には使わない。だから実装を書き直しても、URL の行さえ定義箇所に残っていれば
検査は失敗しない。**「ukadoc」の語だけあって URL の無いコメントは証拠にならない**——
現に作業ツリーにそういうコメントが 152 件あり、語だけで判定すると全件が誤検出になる。

### 書く場所は定義箇所だけ・呼び出し側には書かない

置いてよいのは次の 3 か所である。

* 許可表の要素
* 分岐の腕
* 語彙表の 1 行

**呼び出し側には書かない。** 呼び出し側に書くと、同じ項目の URL が実装を追うたびに増えていき、
どこが定義なのか分からなくなる。これは人が守る規約で、機械は判定できない（どちらも同じ形の
コメント行に見えるため）。

### 1 項目 1 行・説明文を伴わない

* 1 つの項目につき 1 行。
* `ukadoc:` の後は URL 1 語だけ。説明文を続けると証拠として拾われない。
* 行の先頭（字下げを除く）が `///`・`//!`・`//` のいずれかで始まること。
  コードの尻尾に付けた `let x = 1; // ukadoc: ...` は拾われない。
* 実装済みの項目に、定義行 1 行を超える書き足しは求めない。

機械が拾う形はこれだけなので、**書いたのに拾われないときは、ほぼ必ず「URL の後ろに語が続いている」
か「行頭がコメント記号でない」のどちらか**である。`cargo run -p ukadoc-survey -- evidence` で
拾えている一覧を確かめられる。

なお、複数行の生文字列やブロックコメントの中で**行頭から**始まる `// ukadoc:` は、行単位では
区別が付かないので拾われてしまう。作業ツリーに該当する行は現在 0 件だが、規約の側で避けること。

### 語彙表は先頭にページ URL を 1 つ置く

正典の名前をそのまま並べた表（スライス定数）には、**表の先頭にページ URL を 1 つ**置けばよい。
1 要素ごとに URL を書く必要は無い。

```rust
/// ukadoc: https://ssp.shillest.net/ukadoc/manual/list_shiori_resource.html
pub const SHIORI_RESOURCE_IDS: &[&str] = &[
    "version",
    "craftman",
    // ...
];
```

（`crates/areka-sylphya/src/vocab/shiori_resource.rs` の実物の表を例に借りた。
いまその表にページ URL の行は置かれていないので、置くとしたらこの形になる、という見本である。）

機械はページ URL の行の**直後に始まる最初のスライス定数**を見て、要素ごとの最初の文字列リテラルを
名前として取り出し、そのページの正典見出しと突き合わせて個々の項目へ対応付ける。
突き合わせは全角と半角の差を吸収したうえでの完全一致で、**1 件に定まったときだけ**証拠にする。
0 件のときと 2 件以上のときは証拠にせず、検査の出力に「突き合わせできなかった名前」として並ぶ
（失敗にはしない。どう扱うかは人が決める）。

この形（`= &[` から `];` まで）でない語彙——`match` の腕や連想配列——は語彙表として扱わない。
そちらは「定義箇所に 1 項目 1 行の URL」で書く。

### 未実装の項目には、ソース側に何も書かない

未対応であることは台帳が持つ。ソースに「まだ無い」と書き足す必要は無い。

### どこに URL を置けばよいか分からないとき

`cargo run -p ukadoc-survey -- candidates` が手掛かりを並べる。イベント名の文字列・
`\![...]` の消費側の名前・設定キーの表・「縮退」「無視」「未知」などを含むログ行を、
証拠とは別の出力として出す。**これは証拠ではない**——状態の判定は人がする。

## 4. 報告の扱い

### 手で編集しない・食い違いは作り直して直す

`report/` の 5 本はすべて機械が作る。**手で書き換えない。手で突き合わせもしない。**
台帳を直したら報告を作り直す。それだけである。

```
cargo run -p ukadoc-survey -- report          # ドメイン別 4 本
```

ドメイン別報告 4 本は、対応する台帳から作り直した本文と**バイト単位で一致**していなければならない。
食い違うと `DomainReportStale` で失敗し、どのドメインを作り直せばよいかを教えてくれる。
台帳と報告は同じコミットに入れること。

### 誰が何を作り直すか

| 対象 | 作り直す人 | 常時の検査に入るか |
| --- | --- | --- |
| `report/<自分のドメイン>.md` | あなた | 入る |
| `report/summary.md` | **統合担当（`ukadoc-coverage-roadmap`）** | 入らない |
| `catalog.toml` | 道具の担当（スナップショット更新時） | 内容は正本として使われる |

`summary.md` を常時の検査に入れないのは、4 本の台帳を跨ぐ成果物だからである。入れてしまうと、
1 人が台帳を直すたびに他の 3 人の検査が失敗し、4 本の調査 spec が同じファイルを取り合うことになる。

### ⚠ 世代別の表が全部「世代不明」なのは、正しい状態である

いまドメイン別報告の「SSP 世代別の対応表」を開くと、どのドメインも 1 行だけで、全件が「世代不明」に
入っている。**これは不具合ではない。台帳の `introduced` がまだ全部 `""` だからで、
表はそのとおりを映している。**

この表が読むのは**台帳に手で書いた `introduced` だけ**である。カタログの版番号は見ない。
なぜかというと——

* カタログから取ると、**カタログを作り直すたびにドメイン別報告 4 本が一斉に古くなる**。
  並走している 4 本の調査 spec の検査が同時に失敗し、誰も自分の落ち度でないのに直す羽目になる。
* それに、検査は「手で書いた `introduced` がカタログの版番号と矛盾しないか」を見ている。
  カタログから取ってしまえば、その検査は自分自身と比べるだけの空回りになる。

だから世代の表を埋めるのは**あなたの仕事**である。候補はカタログの `versions` 欄にあり、
1,749 件中 406 件が 1 つ以上を持ち、うち 23 件は 2 つ以上を持つので人が選ぶしかない。
残る 1,343 件は版番号を持たず、**世代不明のままが正しい**（最も古い世代と決めつけない）。

### テーマの並びは名前順で、`values.md` の順ではない

報告のテーマ別の表は、テーマ名を**名前順（UTF-8 のバイト順）**で並べる。

```
交わり・掛け合い・更新・気配・気配り・装い・触れ合い・記憶
```

`values.md` の見出し順（気配・触れ合い・掛け合い・装い・記憶・交わり・気配り・更新）とも
五十音順とも違うが、**これで正しい**。凍結されているのは「どの 8 つか」であって表示の順ではなく、
順序が意味を持つ `values.md` の側では要件どおりの順が守られている。
状態の表だけが「実装済み → … → 未分類」の順なのは、状態には並びがあるからである。

### ⚠ 全体報告は黙って古くなる

`summary.md` の末尾にある「ドメインごとの証拠あり件数」の表だけは、台帳ではなく**ソース木を歩いて**
数えている。つまりソースが変わればこの 4 行は古くなるが、**常時の検査には入っていないので
何も失敗しない**。気づく仕組みが無い。

これは意図した設計（そうしないと 4 本が同じファイルを取り合う）だが、読む側は気をつけること。
証拠の件数を根拠に何かを決めるときは、先に統合担当に作り直してもらうか、
`cargo run -p ukadoc-survey -- evidence` で今の値を直接見ること。

### 束 id は人の文書から引用する

報告に出る「関連が閉じている束」には、構成 id だけから決まる安定した id が付く
（構成 id のうち文字順で最も小さいもの）。束の**名付けと解説は道具が出さない**——
それは統合担当が `doc/ukadoc-coverage/linkage.md` に人の言葉で書く。

機械の一覧と人の文章を別のファイルに分けてあるので、報告を作り直しても人の文が消えることは無い。
束について何か書きたくなったら、報告に出た束 id を `linkage.md` から引用する形にすること。
逆向き（報告の中に説明を書き足す）は、次の作り直しで消える。

## 5. 調査 spec と道具の合流

道具（この `crates/ukadoc-survey`）と調査 spec 4 本は同時に進んでいる。**道具と台帳のどちらが
先に出来上がっても成り立つ**ように作ってあるので、順番を気にせず作業を始めてよい。
手順だけ両方向で書いておく。

### 道具が先に出来上がっている場合（いまはこちら）

台帳 4 本は既に `catalog.toml` の全 1,749 id ぶんが `unclassified` で並んでいる。やることは
**その場で値を書き換えるだけ**である。

1. `git pull` して `ledger/<自分のドメイン>.toml` を開く。
2. 項目の塊を上から埋めていく。id・並び順・`[ledger]` の前置きには触らない。
3. `cargo run -p ukadoc-survey -- report` で自分の報告を作り直す。
4. `cargo test -p ukadoc-survey` が通ることを確かめて、台帳と報告を一緒にコミットする。

### 台帳を先に書いてしまった場合

道具が出来上がる前でも、id はスナップショットから決まるので正確に写せる
（手順は要件の付録 B にある）。そうやって書いた台帳は**壊されない**。道具が使えるようになったら
次をやる。

1. `cargo run -p ukadoc-survey -- ledger-init` を 1 度走らせる。
   これは**既存の塊のバイト列をそのまま写し**、カタログにあって台帳に無い id だけを、
   id 順の正しい位置へ初期値で差し込む。並べ替えも、書き直しも、`note` の整形もしない。
   （手で書いた奇妙な空白・複数行の備考・埋めた `status` を混ぜた台帳で、
   バイト単位で不変であることを確かめてある。）
2. `cargo run -p ukadoc-survey -- report` で報告を作る。
3. `cargo test -p ukadoc-survey` を走らせる。

このとき失敗しやすいのは次の 3 つである。

* **並び順** — 項目は id の厳密な昇順でなければならない。同じ id が隣り合うのも誤り。
  `ledger-init` は並べ替えず、**順序を破っている id を名指しして止まる**。手で直す。
* **`[ledger]` の前置き** — `domain` はファイル名と同じに、`pages` は担当ページと同じ集合に。
  なお `pages` の**並び順は一度書いたら以後そのまま写される**（集合が合っていれば検査は通る）ので、
  最初に書くときに名前順にしておくと後の差分が読みやすい。
* **id の綴り** — 見た目で直さず、カタログから写す（1 章の警告）。

### どちらの順でも共通に守ること

* 触るのは**自分の台帳 1 本と自分の報告 1 本だけ**。他ドメインの台帳・`catalog.toml`・
  `values.md`・`summary.md` には手を出さない。
* 台帳と報告は**同じコミットに入れる**。片方だけを入れると次の人の検査が失敗する。
* 形式に足りないものを見つけたら、**その場で欄を足さない**。要件 2.6 により形式の変更には
  要件の改訂が要る。まず spec の担当者に上げること。

## 検査が失敗したときの読み方

`cargo test -p ukadoc-survey` や `cargo run -p ukadoc-survey -- check` が出す所見は 15 種ある。
所見にはどのファイルのどの id かが必ず付く。

| 所見 | 意味 | だいたいの直し方 |
| --- | --- | --- |
| `LedgerIdNotInCatalog` | 台帳の id がカタログに無い | id をカタログから写し直す |
| `CatalogIdMissingFromLedgers` | カタログの id がどの台帳にも無い | `ledger-init` を走らせる |
| `CatalogIdInMultipleLedgers` | 同じ id が 2 つ以上の台帳にある | 担当ページの側の台帳に 1 つだけ残す |
| `LedgerIdPageMismatch` | その id のページは別ドメインの担当 | 正しい台帳へ移す |
| `LedgerDomainMismatch` | `[ledger].domain` がファイル名と違う | 前置きを直す |
| `LedgerPagesMismatch` | `[ledger].pages` が担当ページと違う | 前置きを直す |
| `LedgerOutOfOrder` | 項目が id の厳密な昇順でない | 名指しされた id の位置を直す |
| `PageNotAssigned` | カタログに担当の無いページが現れた | 道具の担当者へ（割り当て表の追加が要る） |
| `SourceUrlNotInCatalog` | ソースの正典 URL がカタログに無い | URL の綴りを直す |
| `ImplementedWithoutEvidence` | `implemented` なのに証拠が 1 件も無い | 定義箇所に URL を置くか、状態を見直す |
| `LinkEndpointMissing` | 関連・別名・置き換えの相手がカタログに無い | 相手 id を写し直す |
| `AliasChain` | `alias_of` の指す先がまた別名 | 正典の行を直接指す |
| `IntroducedNotInCatalogVersions` | 書いた登場版がカタログの版番号に無い | カタログの `versions` から選び直す |
| `UnknownTheme` | テーマ名が `values.md` に無い | 綴りを直す |
| `DomainReportStale` | 報告が台帳と食い違う | `report` を走らせ直す |

状態の語・テーマ名・関連の種別の**綴り違い**は、これより手前の読み込みの段で落ちる。
その場合もファイルと id が出るので、そのまま直せばよい。
