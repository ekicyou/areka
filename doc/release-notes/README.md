# リリースの見どころの書き方

GitHub のリリースの頁の本文は、その版の**見どころ**（特に注目に値する内容）を日本語で紹介する文章である。見どころは版ごとに 1 つのファイルに書いてこのフォルダに置き、リリースの自動の処理（`.github/workflows/release.yml`）がそれを本文に使う。

見どころの書き方の決まりは、この文書の 1 か所だけに在る。ほかのリポジトリの文書を読まなくても、この文書だけで書ける。

その版に入ったすべての変更の一覧（詳しいリリースノート）は、道具が作ってリリースの頁に添付する。見どころに全部を書く必要は無い。

## 置き場所と名前

- 版ごとに 1 つ、`doc/release-notes/v{版}.md` に置く。`{版}` は `v` を付けない版である（版 `0.0.3` のファイルは `doc/release-notes/v0.0.3.md`）。
- 文字コードは UTF-8、文章は日本語。
- 版を上げる PR で、その版のファイルを 1 つ足す。ほかの版のファイルは触らない。
- その版のファイルが無いと、リリースの自動の処理は組み立てを始める前に止まり、何も公開しない。

## 形

ファイルは「挨拶の段落」と、その後ろの「見どころ」の並びである。

```markdown
ごきげんよう、[Claudia](https://github.com/ponapalt/claudia) ですわ。この版では、吹き出しの中のリンクが働くようになりましたの。設定のファイルの置き場所が変わりますので、3 つ目の見どころは必ずお読みくださいまし。

### 吹き出しの中のリンクを押せるようになりましたわ(#301)

吹き出しの文字に、押せるリンクを置けるようになりましたわ。ゴーストを作る方は、さくらスクリプトの `\_a[ID]` と `\_a` で文字を挟んでくださいまし。押されたことは、イベント `OnAnchorSelect` でゴーストへ届きますの。

### 口の動きが、おしゃべりに合うようになりましたわ(#305, #312)

話している間だけ口を動かす指定（`talk`）に対応しましたわ。これまで口が動かなかったシェルも、作り直さずにそのまま動きますわよ。

### 設定のファイルの置き場所が変わりますわ(#318)

設定のファイル `settings.toml` の置き場所が、`areka.exe` と同じフォルダから、フォルダ `data` の中に変わりますわ。前の版から使い続ける方は、`settings.toml` を `data` の中へ移してくださいまし。移さずに起動すると、既定の設定で始まりますわ。

お手数をおかけしますけれど、これで設定とプログラムを分けて持ち運べますの。
```

この見本の中身と PR の番号は、形を見せるための作り物である。

### 見どころ 1 つの形

- 見どころ 1 つは、**`### ` で始まる見出し 1 行**と、**次の見出しまでの紹介の文章**である。
- 見どころを 1 つ以上書く。
- 紹介の文章の中は自由に書いてよい（段落・箇条書き・コードの表記）。
- `### ` で始まる行は、すべて見どころの見出しとして扱われる。見どころの外に `### ` の見出しを置かない。
- `#` と `##` の見出しは使わない（頁の題は GitHub が付ける）。

### 見出しの末尾の PR の番号

見出しの行の末尾に、その見どころの元になった PR の番号を書く。GitHub が本文の `#番号` を PR へのリンクに変えるので、読む人が見どころから変更の中身へたどれる。

| 元になった PR | 見出しの末尾 | 例 |
|---|---|---|
| 1 つ | `(#番号)` | `### 吹き出しの中のリンクを押せるようになりましたわ(#301)` |
| 複数 | `(#番号, #番号)` | `### 口の動きが、おしゃべりに合うようになりましたわ(#305, #312)` |

- 括弧・`#`・数字・コンマは半角で書く。番号の区切りは「半角のコンマと半角の空白 1 つ」である。3 つ以上も同じ形で続ける（`(#305, #312, #320)`）。
- 番号の括弧は行の最後に置く。後ろに句点や言葉を続けない。
- 1 つの機能が、本体の PR と、その後の直しの PR に分かれているときは、複数の形で並べる。
- 見出しにできるのは、PR の番号を持つ変更が元になった内容だけである。PR を通さずに入った古い変更だけが元になった内容は、見出しにせず、紹介の文章の中で触れる。

## 口調

全文を Claudia（令嬢）の口調で書く。語り手は「Claudia」と名乗ってよい。挨拶の段落も、見出しも、紹介の文章も口調で書く。

- 一人称は「わたくし」。「私」「わたし」「僕」は使わない。
- 冒頭の挨拶は「ごきげんよう」。
- 文末は、丁寧な形に「わ」「の」を添える: 「〜ですわ」「〜ますわ」「〜ましたわ」「〜ませんわ」「〜ですの」「〜ますの」。
- 念を押すとき・呼びかけるとき: 「〜ですわね」「〜ですわよ」「〜でしてよ」。
- 問いかけるとき: 「〜かしら」。
- 頼むとき: 「〜くださいまし」（「〜してください」は使わない）。
- 「〜だ」「〜である」の言い切りと、「〜だよ」「〜だね」のようなくだけた語尾は使わない。
- 口調は飾りである。機能の名前・ファイルの名前・タグ・イベントの名前は、言い換えずに正しい綴りで書く。

### 出典のリンク

Claudia は、他の作者のゴースト「悪役令嬢クローディア」の人物を借りている。出典は次の URL である。

```
https://github.com/ponapalt/claudia
```

- ファイルの中で**最初に現れる「Claudia」だけ**を、出典へのリンクにする。書き方は `[Claudia](https://github.com/ponapalt/claudia)` で、1 字も変えない。
- 2 回目からの「Claudia」は、リンクにしない。
- 出典の断り書きの段落は書かない（リンクだけで足りる）。
- この URL を変えるときは、検査の道具 `tools/release-notes.ps1` が持つ同じ URL も同時に直す。

## 必ず載せるもの

- **動きが変わる点**: その版に、使う人やゴーストを作る人が何かを直さなければならない変更が在るときは、それを必ず見どころにする。書き方は次のとおり。
  1. 先に、事実の文で言い切る:「何が」「どう変わるか（変わる前と後）」「何を直せばよいか」。直さないとどうなるかも、分かっていれば書く。
  2. 「何がどう変わるか」の文は「〜ますわ」「〜ですわ」の言い切りで書く。「何を直せばよいか」の文は「〜くださいまし」で終えてよい。どちらにも、たとえ・ほのめかし・「〜かしら」を混ぜない。
  3. その後ろに、口調の一言を添えてよい。

  上の見本の 3 つ目の見どころがこの形である（1 文目が何がどう変わるか、2 文目が直すこと、3 文目が直さないとどうなるか、最後の段落が口調の一言）。
- **不具合の修正だけの版**: 新しい機能が無い版では、修正のうち使う人に効くものを 1 つ以上、見どころにする。

## 数の目安

見どころは 3〜5 つを目安にする。検査が見るのは「1 つ以上」だけなので、数は書く人が決める。入った変更が少ない版は、少なくてよい。

## 書かないもの

- **spec 名**（開発の中で使う仕様の名前。`areka-P0-` で始まる）。見出しにも文章にも書かない。PR の題名を写すときは、頭の「種類(spec 名): 」を外し、使う人の言葉に書き直す。
- **詳しいリリースノートへのリンク**。リリースの自動の処理が、本文の末尾に区切りの線とリンクの文を足す。見どころのファイルには書かない。
- **出典の断り書きの段落**（上の「出典のリンク」）。

## 材料の出し方

見どころは、一つ前のタグからその版までに入った変更の一覧を読んで選ぶ。一覧は道具で出す。リポジトリの根で、版を上げた後に次を回す（版 `0.0.3`・一つ前のタグ `v0.0.2` の例）。

```
pwsh -NoProfile -File tools/release-notes.ps1 -Notes -Version 0.0.3 -Repository ekicyou/areka -PrevTag v0.0.2 -Out target/release-notes/release-notes-v0.0.3.md
```

| 引数 | 意味 |
|---|---|
| `-Version` | `v` を付けない版 |
| `-Repository` | `持ち主/名前`（PR へのリンクを作るのに使う） |
| `-PrevTag` | 一つ前のタグ。省くと、最初のコミットからの全部を並べる |
| `-To` | 一覧の先。省くと `HEAD`（今の枝の先頭） |
| `-Out` | 書き出す先のファイル（`target/` の下に置く）。相対パスは、回した場所から数える |

- 出てくるのは、リリースの頁に添付される詳しいリリースノートと同じ形の Markdown である。1 つの変更が 1 行で、PR の番号が付く。
- 製品の変更が種類ごと（新しい機能・不具合の修正・性能の改善・そのほか）に並び、開発の内部の作業は末尾の別の見出しにまとまる。見どころは、製品の変更の中から選ぶ。

## 検査の回し方

書き終えたら、版を上げる PR を出す前に、形の検査を回す（版 `0.0.3` の例）。

```
pwsh -NoProfile -File tools/release-notes.ps1 -Check -Version 0.0.3
```

- 通ると `OK highlights v0.0.3 (4 item(s))` の形の 1 行を出し、終了コード 0 で終わる。
- 欠けが在ると、欠けをすべて `FAIL {欠けの名前} line {行の番号}: {説明}` の形で出し、終了コード 1 で終わる。行の番号 0 は、ファイルの全体を指す。
- 検査は読むだけで、ファイルを書き換えない。その版の名前のファイルだけを見る。

| 欠けの名前 | 意味 | 直し方 |
|---|---|---|
| `missing-file` | `doc/release-notes/v{版}.md` が無い | 名前と置き場所を確かめる |
| `no-highlight` | `### ` で始まる行が 1 つも無い | 見どころを 1 つ以上書く |
| `heading-no-pr` | 見出しの行末が `(#番号)`・`(#番号, #番号)` の形でない | 「見出しの末尾の PR の番号」の形に直す |
| `spec-name` | `areka-P0-` が現れる | その名前を外し、使う人の言葉に書き直す |
| `no-source-link` | `[Claudia](https://github.com/ponapalt/claudia)` が無い | 最初の「Claudia」を出典へのリンクにする |
| `first-name-not-linked` | 最初に現れる「Claudia」がリンクでない | リンクより前に在る「Claudia」を外すか、そこをリンクにする |

同じ検査を、リリースの自動の処理も、組み立ての前に回す。タグは打った後に動かせないので、PR を出す前に手元で通しておく。このフォルダの `v*.md` は、全体テスト（`tools/test-all.ps1`）でも同じ検査にかかる。

検査が見るのは形だけである。口調と「必ず載せるもの」は機械では見ない。書いた側が「必ず載せるもの」を読み直して確かめ、開発者はリリースの最後の報告で文章を読む（直しは公開の後に頼める）。
