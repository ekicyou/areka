# 二坑モデル

> **配置方針**: 本ファイルが**二坑規律の正本（single source of truth）**。`inclusion: manual` ゆえ毎セッションの自動ロードはされず（コンテキスト最小化・要件 1.5）、常駐文書（`workflow.md`（`inclusion: always`）の二坑節・`focus.md` の「参照先」）から辿る。`workflow.md` は二坑規律を**重複記述せず本ファイルを参照**する（規律の唯一の正本）。

## 概要

エージェント駆動開発には次の本質的痛点がある。①**見てから違う**（出てきた物を見て初めて方向の誤りに気づく反応型）、②**コード肥大でやり直し地獄**（気づいた時には実装が育って絡み合い手戻りが高い）、③**エージェントは消さず足す**（負の遺産が累積する）。

二坑モデルはこれを「**先進坑（pilot・使い捨て）**」と「**本坑（main・完成品）**」の二系統に分け、方向が怪しい所を先に細粒度・並列で掘って確かめてから本坑を慎重に掘る規律である。

### 可逆性最優先方針（要件 1.2）

**最適化対象は「手応えの速さ」ではなく「誤った方向の可逆性（reversibility）」である。** 速く動く物を出すことより、誤りに気づいたときに低コストで引き返せる構造を保つことを優先する。先進坑を使い捨て前提・葉ノード隔離に保つのは、この可逆性を構造的に担保するためである。「見てから違う」の発覚を実装後（コード肥大後）から実装前へ前倒しし、誤りのやり直しコストを最小化する。

## 先進坑と本坑

### 定義と役割分担（要件 1.1）

- **先進坑（pilot・使い捨て）**: 手順の正当性・方向性・実現可能性を確認する坑。**捨てる前提**。成果物はコードではなく**知見**（go／違う／直す ＋ 学び）。細粒度・独立ゆえ多重並列で掘れる。コードは知見クレート `crates/pilot` の `examples/<spec-name>/` に隔離する。
- **本坑（main・完成品）**: 既存 kiro spec ライフサイクル（requirements → design → tasks → implementation → complete）。直列・慎重・PR ベースの squash マージで `main` に統合する。出荷対象。

役割分担: 先進坑は「方向を確かめる」ことに徹し、本坑は「確定した方向を完成品として掘る」ことに徹する。両者を混ぜない。

### 何を先進坑にするかの判断基準（要件 1.3）

**方向・実現可能性・手順が怪しい所だけを先進坑にする。** よく分かっている所（方向・実現可能性・手順が十分確実な所）は先進坑を経ず**直に本坑**へ着手する。先進坑を掘ること自体が目的化して掘りすぎることを防ぐ（直行許容＝要件 6.5・ハードゲート節参照）。判断は開発者が下す。

## 命綱と削除/隔離規律

**命綱（不変条件）**: 出荷グラフ上のいかなるクレートも先進坑コードに依存しない（**葉ノード隔離**・要件 5.1）。これにより先進坑コードはいつでも安全に捨てられる（可逆性の構造的担保）。

### 命綱の構造的担保と inbound 依存の人手レビュー規律（要件 4.3）

命綱は専用の機械ゲートではなく `crates/pilot` の**構造**で担保する。すなわち **空（または最小）の `lib.rs` ＋ 探索コードは `examples/<spec-name>/` のみ** という構造を保つ。Cargo の `examples/` は他クレートから依存できず、空 lib は依存しても意味のある公開 API を持たないため、先進坑コードへの被依存は構造的に発生しない。

先進坑コードへ被依存が混入し得る**唯一の inbound 経路**は、誰かが他クレートの `Cargo.toml` に `pilot = { path = ... }` を一行追加することである。これはレビューで可視な一行変更であり、かつ空 lib ゆえ実効果がない。この一行を**変更レビューで捕捉する人手レビュー規律**で命綱を守る。機械ガード（`cargo metadata` 走査 / `cargo-deny` 等）は用いない。

### 機械チェックは defer（要件 4.4）

将来 inbound 依存の混入が現実の問題になった場合は、機械チェック（`cargo metadata` 走査による依存方向ガード・`cargo-deny`・examples 腐敗検出等）の追加を**別途依頼できる**。本仕様ではこれを実装しない（YAGNI 方針）。構造的隔離＋人手レビューで足りる間は追加しない。

### 隔離保全許可（要件 5.2）

葉ノード隔離の不変条件が満たされている限り、先進坑コードを**物理削除する代わりに**知見クレート `crates/pilot` へ**隔離保全**してよい。捨てるべきは「production への依存」であって「知見」ではない。隔離されている限り残しておける。

### 掘り直し禁止（要件 5.3）

本坑は先進坑の知見を**見てクリーンに掘り直す**。先進坑コードを**コピペ donor として流用することを禁止する**。先進坑は使い捨て前提で品質が緩いため、そのまま production に持ち込むと負債が紛れ込む。本坑 design は README の検証結果（知見）を参照し、実装は一から綺麗に掘る。

### 品質基準（要件 5.4）

先進坑コードの品質基準は**使い捨て前提ゆえ緩くてよい**（整形・命名・テストの厳格さを求めない）。ただし**葉ノード隔離だけは厳守する**。本仕様では葉ノード隔離を機械（CI）で自動執行せず `crates/pilot` の構造（空 lib ＋ examples-only）と人手レビューで担保する（要件 4.3／NFR-3。機械自動執行は defer＝要件 4.4）。緩めてよいのは品質であって隔離ではない、という線引きを徹底する。

### 検疫所効果（要件 5.5）

探索的残骸を知見クレート**一葉**（`crates/pilot`）へ集約することで、production を常時クリーンに保ち、不要になった先進坑の**定期剪定**を可能にする（検疫所効果）。残骸が production 各所に散らばらず一箇所に検疫されるため、剪定の判断と実行が容易になる。

## ハードゲート

方向が未確定なまま本坑を掘ることを構造的に不可能にするゲート規律。

### go 前提依存（要件 6.1）

各本坑 spec は、その方向を確定する先進坑の **go 判定を前提依存（prerequisite）として持つ**。先進坑が「この方向で行ける（go）」と判定して初めて、対応する本坑が着手可能になる。

### BLOCKED（要件 6.2）

前提の先進坑が go 判定に至っていない間、当該本坑 spec は**着手不能（BLOCKED）**として扱う。go 前の本坑着手は規律違反であり、許さない。これにより「見てから違う」の発覚を本坑実装前へ前倒しする。

### 人間判断（要件 6.3）

go 判定は**開発者が先進坑の出力を見て下す（人間判断）**。自動判定にはしない。「見て初めて方向の誤りに気づく」反応型の痛点に対する応答であるため、判定の主体は人間である。

### 記法 `_Depends(confirmed):`（要件 6.4）

go 判定の前提依存は spec 上で次の記法で表現する。

```
_Depends(confirmed): pilot/<spec-name>
```

この依存記法の**宿主は `roadmap.md`**（spec の pilot/main 種別と go ゲート依存を表現する場所）。本坑 spec が、どの先進坑の go を前提とするかを `_Depends(confirmed):` で名指しすることで、ゲート関係を可視化する。

### 直行許容（要件 6.5）

本坑 spec の方向・実現可能性・手順が十分に確実な場合は、**先進坑を経ず直接本坑に着手することを許容する**（掘りすぎ防止）。全ての本坑に先進坑を強制しない。先進坑は「怪しい所だけ」（要件 1.3 と整合）。

## 依存マップ重点検証（手動チェックリスト）

spec 分解時に先進坑↔本坑の依存関係の健全性を厳密に検証する**手動チェックリスト規律**。自動チェックツールは作らない（被覆判断・合否基準の妥当性は本質的に人間の判断であり、対象グラフも小規模ゆえ目視で足りる）。

### 適用タイミング（要件 7.1）

本チェックリストは **spec 分解時（discovery / `/kiro-spec-batch`）** に開発者/AI が目視で適用する。

### チェック項目

- **被覆（要件 7.2）**: 不確実な本坑は必ず対応する go ゲート（前提の先進坑）を持つ。go ゲートを持たない不確実な本坑がないことを確認する。
- **孤児なし（要件 7.3）**: どの先進坑・本坑も依存関係上で孤立しない。対応する本坑を持たない先進坑、参照されない先進坑がないことを確認する。
- **循環なし／DAG（要件 7.4）**: 依存グラフが **DAG（有向非巡回グラフ）**であり、循環依存が存在しないことを確認する。
- **合否基準明示（要件 7.5）**: 各エッジ（先進坑→本坑のゲート）に **go／違う／直す を判定する合否基準**が明示されていることを確認する。

### 不適合時 not-ready（要件 7.6）

チェックリストのいずれかの項目を満たさない場合、当該本坑 spec を **ready にしない**（not-ready）。健全性が確認できない依存関係のまま本坑を進めることを許さない。

## 先進坑の一次記録（README 3 幕）

各 `crates/pilot/examples/<spec-name>/README.md` を、当該先進坑の**一次記録（正本）**として位置づける。

### 3 幕構成

README は次の 3 幕構成で記述する。

1. **動機**: なぜ掘るか。**対応する本坑 spec を名指し**する（先進坑↔本坑の traceability を確立）。
2. **概要**: 何を作ったか・実行法（例: `cargo run -p pilot --example <spec-name>`）。
3. **検証結果**: **go／違う／直す** ＋ 学び ＋ 日付。

### 本坑 design は README を参照し二重化しない（要件 3.5）

本坑 spec の design が先進坑の知見を参照する場合、**README の検証結果を参照**し、同じ検証結果を design 側に重複して記述しない。検証結果の正本は README 側に一本化する（No Hidden Shared Ownership）。

### subagent の `.md` ハーネス制約の代替手順（要件 3.6）

subagent は `.md` を Write/Edit できないハーネス制約がある。並列先進坑が README.md を生成する運用では、次の代替手段で確実に書き込む。

- **親エージェントによる書き込み**: subagent が内容を生成し、親エージェントが `.md` を書き込む。
- **PowerShell here-string**: `Set-Content`／`Add-Content` に**単一引用符の here-string**（`@'` … `'@`、リテラル展開なし）で UTF-8 書き込みする。閉じる `'@` は**列 0**（先頭空白なし）に置く。長い本文はセクションごとに `Add-Content` で分割して書き継ぐ。

いずれの手段でも、書き込み後に内容を読み戻して 3 幕が揃っていること・切り詰めがないことを確認する。
