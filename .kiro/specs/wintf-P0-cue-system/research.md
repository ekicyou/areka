## 1. さくらスクリプトの基本設計モデル

### 1.1 概要

さくらスクリプト（Sakura Script）は、伺か（ukagaka）プラットフォームにおける**演出記述言語**である。ベースウェア（SSP等）がさくらスクリプトを受信・解釈し、キャラクターの表情変更、テキスト表示、サウンド再生等の演出を逐次実行する。

### 1.2 基本モデル: タグ埋め込み型逐次解釈

さくらスクリプトの根幹は「**テキストストリームにタグ（制御命令）を埋め込む**」モデルである。

```
\0\s[0]こんにちは。\w[500]今日はいい天気ですね。\1\s[5]そうだね。\e
```

このスクリプトは以下のように逐次解釈される:

1. `\0` — スコープをキャラクター0（メインキャラ）に切替
2. `\s[0]` — サーフェス（表情）を0番に変更
3. `こんにちは。` — 一文字ずつ表示（デフォルト間隔）
4. `\w[500]` — 500ミリ秒待機
5. `今日はいい天気ですね。` — 一文字ずつ表示
6. `\1` — スコープをキャラクター1（サブキャラ）に切替
7. `\s[5]` — サーフェスを5番に変更
8. `そうだね。` — 一文字ずつ表示
9. `\e` — スクリプト終了

### 1.3 コマンド構造

さくらスクリプトのタグ形式は統一されていない。歴史的経緯により複数のパターンが混在する：

| パターン             | 構文                    | 例                          |
| -------------------- | ----------------------- | --------------------------- |
| 単純タグ             | `\X`                    | `\n`, `\e`, `\x`            |
| 数字タグ             | `\N`                    | `\0`, `\1`                  |
| パラメータ付き       | `\X[param]`             | `\s[0]`, `\w[500]`          |
| アンダースコア接頭辞 | `\_X[param]`            | `\_w[500]`, `\_q`           |
| 拡張コマンド         | `\![command,param,...]` | `\![play,sound,file.wav]`   |
| アンカー（リンク）   | `\_a[id]{text}`         | `\_a[choice1]{選択肢1}`     |
| インライン画像       | `\_b[path,...]`         | `\_b[image.png,inline,...]` |

この非統一性はさくらスクリプトの主要な弱点のひとつである。

## 2. コマンドカテゴリ一覧

### 2.1 テキスト表示制御

テキスト表示はさくらスクリプトの最も基本的な機能である。タグでない通常の文字はすべて「表示対象文字」として扱われ、一文字ずつ順次表示される（タイプライター効果）。

| コマンド           | 構文           | 説明                                     | 例                         |
| ------------------ | -------------- | ---------------------------------------- | -------------------------- |
| テキスト文字       | *(任意の文字)* | デフォルト間隔で一文字ずつ表示           | `こんにちは`               |
| 改行               | `\n`           | バルーン内で改行                         | `一行目\n二行目`           |
| 半改行             | `\n[half]`     | 半行分の改行                             | `テキスト\n[half]テキスト` |
| クリア             | `\c`           | バルーンの表示内容をクリア               | `\c新しいテキスト`         |
| ウェイト（簡易）   | `\w1`〜`\w9`   | 50ms単位の簡易ウェイト（`\w5` = 250ms）  | `こんに\w5ちは`            |
| ウェイト（精密）   | `\_w[N]`       | Nミリ秒の精密ウェイト                    | `こん\_w[300]にちは`       |
| クイックセッション | `\_q`          | 以降のテキストを即時表示（ウェイトなし） | `\_qこの文は即座に表示`    |
| タイムクリティカル | `\t`           | 以降のテキストを可能な限り高速で表示     | `\tこの文は高速表示`       |
| クリック待ち       | `\x`           | ユーザーのクリックを待つ                 | `続きを見るにはクリック\x` |

### 2.2 サーフェス（表情）制御

キャラクターの外見（表情・ポーズ）を切り替えるコマンド群。

| コマンド               | 構文         | 説明                                              | 例      |
| ---------------------- | ------------ | ------------------------------------------------- | ------- |
| サーフェス変更         | `\s[N]`      | 現在スコープのキャラクターのサーフェスをN番に変更 | `\s[5]` |
| サーフェス変更（簡易） | `\s0`〜`\s9` | 一桁サーフェスの省略記法                          | `\s3`   |

### 2.3 スコープ（キャラクター切替）

伺かの核心的な機能「ドコイツ」（複数キャラクター掛け合い）を実現するコマンド。

| コマンド      | 構文    | 説明                                               | 例                |
| ------------- | ------- | -------------------------------------------------- | ----------------- |
| キャラ0に切替 | `\0`    | メインキャラクター（さくら側）のスコープに切替     | `\0こんにちは`    |
| キャラ1に切替 | `\1`    | サブキャラクター（うにゅう側）のスコープに切替     | `\1やあ`          |
| キャラNに切替 | `\p[N]` | N番目のキャラクターのスコープに切替（3人以上対応） | `\p[2]三人目だよ` |

#### スコープの意味

「スコープ」は**現在どのキャラクターに対して命令を発行しているか**を示す。スコープ切替後のすべてのコマンド（テキスト表示、サーフェス変更等）は、そのキャラクターに対して適用される。

```
\0\s[0]今日は暑いね。\1\s[2]そうだね、アイス食べたい。\0\s[3]いいね！
```

この例では:
- `\0` → キャラ0がスコープ → `\s[0]` でキャラ0の表情変更 → テキストはキャラ0のバルーンに表示
- `\1` → キャラ1がスコープ → `\s[2]` でキャラ1の表情変更 → テキストはキャラ1のバルーンに表示
- `\0` → キャラ0に戻る → `\s[3]` でキャラ0の表情変更

### 2.4 サウンド・メディア制御

| コマンド     | 構文                  | 説明                         | 例                       |
| ------------ | --------------------- | ---------------------------- | ------------------------ |
| サウンド再生 | `\![play,sound,file]` | 指定ファイルのサウンドを再生 | `\![play,sound,se.wav]`  |
| サウンド停止 | `\![stop,sound]`      | サウンド再生を停止           | `\![stop,sound]`         |
| BGM再生      | `\![play,bgm,file]`   | BGM再生                      | `\![play,bgm,music.mp3]` |

### 2.6 選択肢・インタラクション

| コマンド           | 構文                   | 説明                                   | 例                            |
| ------------------ | ---------------------- | -------------------------------------- | ----------------------------- |
| 選択肢             | `\q[label,id]`         | 選択肢を表示（クリックでイベント発火） | `\q[はい,yes]\n\q[いいえ,no]` |

### 2.7 同期・終了制御

| コマンド         | 構文            | 説明                              | 例                       |
| ---------------- | --------------- | --------------------------------- | ------------------------ |
| スクリプト終了   | `\e`            | スクリプトの実行終了を宣言        | `さようなら。\e`         |

## 3. さくらスクリプトの実行モデル

### 3.1 逐次ストリーミング解釈

さくらスクリプトは**単一の文字列**として SHIORI からベースウェアに渡される。ベースウェアはこの文字列を先頭から1文字ずつ読み進め、以下のルールで処理する:

```
┌─────────────────────────────────────────┐
│ SHIORI (里々, 華和梨, YAYA 等)          │
│   イベントに応じてさくらスクリプトを生成 │
└──────────────┬──────────────────────────┘
               │ さくらスクリプト文字列
               ▼
┌──────────────────────────────────────────┐
│ ベースウェア (SSP 等)                    │
│   文字列を先頭から逐次解釈・実行         │
│                                          │
│   通常文字 → 表示キューに追加            │
│   \タグ     → 即座にコマンド実行          │
│   \w[N]    → Nミリ秒間停止               │
│   \e       → 解釈終了                    │
└──────────────────────────────────────────┘
```

### 3.2 タイミングモデル

さくらスクリプトのタイミングは**逐次・ブロッキング**モデルである。

| 概念               | 説明                            | デフォルト値                                    |
| ------------------ | ------------------------------- | ----------------------------------------------- |
| 文字表示間隔       | 通常文字1文字の表示に要する時間 | ベースウェア設定による（SSPデフォルト: 約50ms） |
| ウェイト（簡易）   | `\w1`〜`\w9` で挿入する停止     | `\wN` = N × 50ms                                |
| ウェイト（精密）   | `\_w[N]` で挿入する停止         | Nミリ秒                                         |
| タイムクリティカル | `\t` 後の文字はウェイトなし     | 0ms                                             |
| クイックセッション | `\_q` 後の文字はウェイトなし    | 0ms                                             |
| クリック待ち       | `\x` でユーザー入力まで停止     | 無限（ユーザー操作待ち）                        |

**重要な特性**: さくらスクリプトの実行は**単一スレッド・単一タイムライン**である。ウェイト中にサーフェス変更やサウンド再生を「同時に」行うことはできない。すべてのコマンドは直列に処理される。

```
時間軸 →

[文字表示] [文字表示] [\w[500]........] [文字表示] [\s[3]] [文字表示]
  50ms       50ms        500ms停止         50ms     即座     50ms
```

### 3.3 複数キャラクター間の協調

さくらスクリプトでは、複数キャラクターの掛け合いは**単一スクリプト内のスコープ切替**で実現される。

```
\0\s[0]ねえ、おやつ何がいい？\w[500]
\1\s[5]うーん……\w[300]クッキーかな。\w[200]
\0\s[3]了解！
\e
```

この設計の意味:
- **1つのスクリプトが複数キャラクターの演出を統括する**
- スクリプトの主体（発言者）はスコープ切替で都度変わる
- 各キャラクターが独立して動くのではなく、**1本の台本（スクリプト）が全員の演技を記述する**
- つまり「セリフの書かれた脚本」のメタファーに近い

### 3.4 スコープの暗黙状態

スクリプト開始時のデフォルトスコープはキャラクター0（`\0`）である。スコープは明示的に切り替えない限り維持される。これは直感的だが、スクリプトが長くなると「現在どのキャラクターがスコープか」を追跡するのが困難になるという問題がある。

## 4. 保存すべき強み（cue-system へのオマージュ）

### 4.1 テキスト内インラインコマンドの直感性

さくらスクリプトの最大の強みは、**テキストと演出指示が自然に混在できる**ことである:

```
こんにちは。\w[500]今日は\s[3]いい天気ですね。
```

テキストの流れを読みながら「ここで間を置く」「ここで表情を変える」が直感的に理解できる。これは演出家や脚本家の思考モデルに合致している。

**cue-system での継承方針**: pasta DSL 層でこの直感性を保持する。cue-system 自体は構造化されたコマンド列を受け取るが、pasta DSL から cue-system への変換時にこの書きやすさを失わないようにする。

### 4.2 シンプルなタイミングモデル

3種類のタイミング制御だけで豊かな演出が可能:

| 機能     | さくらスクリプト | 演出効果                                       |
| -------- | ---------------- | ---------------------------------------------- |
| 間（ま） | `\w[N]`          | 発話の自然なリズム、ためらい、思考の表現       |
| 停止     | `\x`             | 重要な発言の前の「溜め」、ユーザーへの問いかけ |
| 高速表示 | `\t`, `\_q`      | 慌てた発言、ツッコミ、システムメッセージ       |

**cue-system での継承方針**: Wait コマンドとユーザー入力待ちのセマンティクスを型安全に再実装する。

### 4.3 複数キャラクターの単一台本モデル

「1つの台本が全キャラクターの演技を記述する」というモデルは、「掛け合い」「漫才」「会話劇」を自然に表現できる。各キャラクターが独立したAIとして動く現代的アプローチとは根本的に異なるが、**演出の確実な制御**という点で優れている。

**cue-system での継承方針**: 外部（pasta DSL / SHIORI / LLM）が生成するコマンド列は、複数のターゲットエンティティへのコマンドを含むことができる。ただし、cue-system 内部では各エンティティ独立のキューとして管理する（さくらスクリプトのスコープ概念を脱構築する）。

### 4.4 「演出」のメタファー

さくらスクリプトは本質的に**舞台演出の台本**である。テキスト表示、表情変更、SE再生、間合いの取り方——これらはすべて「登場人物がどう演じるか」の指示である。この「スクリプト = 演出指示書」というメタファーは、cue-system の名前にも反映されている（cue = 舞台での出演合図）。

## 5. 克服すべき弱点（cue-system での再設計対象）

### 5.1 文字列ベース解析の脆弱性

さくらスクリプトはプレーンテキスト文字列として表現されるため:

- **パースエラーが実行時まで検出されない**: `\s[abc]` のような不正パラメータは実行時エラー
- **エスケープの曖昧さ**: `\` が通常文字なのかタグ開始なのかの判定が文脈依存
- **閉じ忘れの検出困難**: `\f[bold,true]` に対応する `\f[bold,false]` の欠落を検出できない

**cue-system での解決**: コマンドは Rust の enum として型定義される。不正なコマンドはコンパイル時に排除される。

### 5.2 型安全性の欠如

さくらスクリプトのパラメータはすべて文字列であり:

- サーフェス番号が存在しない場合のフォールバックは実装依存
- ウェイト値の負数や異常値に対する挙動は未定義
- コマンドとパラメータの型の不一致を事前検出できない

**cue-system での解決**: 各コマンド型がパラメータの型を持ち、Rust の型システムで保証する。

```rust
// さくらスクリプト: \s[0] — "0" は文字列
// cue-system: 型安全な enum バリアント
enum CueCommand {
    ChangeSurface { surface_id: SurfaceId },
    Wait { duration: Duration },
    // ...
}
```

### 5.3 拡張性の制約

さくらスクリプトのタグ形式は以下の制約を持つ:

- 新しいコマンド追加には `\!` 拡張メカニズムを使うが、構文が冗長
- パラメータの構造化（ネストしたオブジェクト等）が不可能
- ベースウェア間の互換性問題（SSP固有の拡張タグ等）

**cue-system での解決**: コマンド型は trait ベースまたは enum ベースで拡張可能にする。各消費者（balloon, animation 等）が独自のコマンド型を定義できる。

### 5.4 コンテンツと制御フローの密結合

さくらスクリプトでは「何を表示するか」と「いつ・どのように表示するか」が分離されていない:

```
\0\s[0]こんにちは\w[500]\s[3]今日はいい天気ですね\e
```

このスクリプトから:
- テキスト内容だけを抽出するのが困難
- タイミングだけを変更するのが困難  
- 表情変更だけを変更するのが困難

**cue-system での解決**: コマンドは独立した構造体であり、フィルタリング・変換・並べ替えが可能。

### 5.5 構造化データモデルの欠如

さくらスクリプトには「ドキュメント」という概念がない。1つの発話は1つの文字列であり:

- メタデータ（作者、バージョン、対象キャラクター等）を付与できない
- 複数の発話をまとめた「セッション」「シーン」等の上位構造がない
- デバッグ情報（ソースマッピング等）を埋め込めない

**cue-system での解決**: コマンドキューは ECS コンポーネントとして構造的に管理される。各コマンドにメタデータを付与可能。

### 5.6 プログラマティック生成の困難さ

さくらスクリプトを動的に生成するには文字列連結が必要:

```python
# 里々やスクリプトエンジンでの典型的なパターン
script = f"\\0\\s[{surface}]{text}\\w[{wait}]\\e"
```

文字列テンプレートは:
- エスケープ処理が煩雑
- 組み立てミスが実行時まで検出されない
- コード補完やIDE支援を受けられない

**cue-system での解決**: コマンドはビルダーパターンまたは直接のコンストラクタで生成。型システムによる補完とバリデーション。

### 5.7 並列トラックの不在

さくらスクリプトは**完全に逐次的**である:

- テキスト表示中にBGMフェードを「同時に」行えない
- キャラクター0の表情変更とキャラクター1のテキスト表示を同じ瞬間に実行できない
- 複雑な演出（同時多発的なイベント）を記述するには工夫が必要

**cue-system での解決**: 各エンティティが独立したコマンドキューを持つため、本質的に並列実行が可能。さらに、dola との統合により同期的な並列タイムラインの記述も可能になる。

## 6. 関連: 里々（Satori）DSL と pasta DSL

### 6.1 里々の位置づけ

里々（Satori）は伺かエコシステムにおける**最も普及した SHIORI 実装**（ゴーストスクリプトエンジン）である。里々は以下の関係で動作する:

```
┌─────────────────┐     SHIORI プロトコル     ┌──────────────┐
│ ベースウェア     │ ←──────────────────────→ │ 里々 (SHIORI) │
│ (SSP等)          │    さくらスクリプト        │              │
│                  │ ←────────────────────── │  会話辞書     │
│ さくらスクリプト │                           │  変数管理     │
│ を解釈・実行     │                           │  条件分岐     │
└─────────────────┘                           └──────────────┘
```

つまり:
- **里々はさくらスクリプトの「生成者」**である
- 里々自体はさくらスクリプトを解釈しない
- 里々は独自の DSL（辞書ファイル形式）でユーザーが会話を記述し、それをさくらスクリプトに**コンパイル**（トランスパイル）して出力する
- ベースウェアが最終的にさくらスクリプトを受け取り、演出を実行する

### 6.2 里々が提供する抽象化

里々の DSL は、さくらスクリプトの煩雑さを隠蔽し、会話記述に特化した構文を提供する:

```
＊ランダムトーク
：さくら
こんにちは。
\w5
今日はいい天気だね。
：うにゅう
そうだね。
```

この里々スクリプトは以下のさくらスクリプトに変換される:

```
\0\s[0]こんにちは。\w5今日はいい天気だね。\1\s[10]そうだね。\e
```

里々が提供する主な抽象化:

| 里々の機能                    | さくらスクリプトでの等価操作 | 抽象化の価値                   |
| ----------------------------- | ---------------------------- | ------------------------------ |
| `：キャラ名` で発言者指定     | `\0`, `\1`, `\p[N]`          | 名前で指定でき直感的           |
| `＊イベント名` でイベント定義 | SHIORI レスポンス            | イベント駆動の会話を自然に記述 |
| ランダム選択（空行区切り）    | 自前でランダム処理           | 複数の応答パターンを簡潔に記述 |
| `（変数名）` で変数展開       | `%variable%` 等の構文        | テンプレート的な使い方が容易   |
| 条件分岐（`＄` 系構文）       | スクリプト内分岐なし         | 状況に応じた会話の出し分け     |
| 単語群展開 `（＠食べ物）`     | 自前で辞書管理               | 語彙のバリエーションを簡潔に   |

### 6.3 pasta DSL と里々の関係

pasta DSL は里々にインスピレーションを得た areka プラットフォーム用の会話記述 DSL であり、以下の関係にある:

| 観点                 | 里々 (Satori)                      | pasta DSL                               |
| -------------------- | ---------------------------------- | --------------------------------------- |
| 対象プラットフォーム | 伺か (SSP等)                       | areka                                   |
| 出力形式             | さくらスクリプト（文字列）         | **構造化コマンド列**（cue-system 経由） |
| 設計世代             | 2000年代（テキストベース）         | 2020年代（型安全・ECS指向）             |
| 互換性               | 既存の伺かベースウェアで動作       | areka 専用（伺か互換は非目標）          |
| 変数管理             | 独自の変数システム                 | Rune スクリプトエンジン経由             |
| パーサー実装         | C++                                | Rust                                    |
| 拡張構文             | さくらスクリプトタグを直接埋め込み | コマンド enum の拡張（型安全）          |

**重要な違い**: 里々はさくらスクリプト（文字列）を出力するが、pasta DSL は**型付きコマンド列**を出力する。これは cue-system の存在意義そのものである——さくらスクリプトという「文字列プロトコル」を、ECS コンポーネントキューという「構造化プロトコル」で置き換える。

## 7. 比較表: さくらスクリプト vs 提案する cue-system

| 観点                       | さくらスクリプト                   | cue-system（設計方針）                       |
| -------------------------- | ---------------------------------- | -------------------------------------------- |
| **データ形式**             | プレーンテキスト文字列             | 型付き enum コマンド列（Rust）               |
| **コマンド構文**           | `\tag[param]` 混合形式             | `CueCommand::Variant { field: Type }`        |
| **型安全性**               | なし（すべて文字列）               | コンパイル時型チェック                       |
| **パース**                 | 実行時文字列パース                 | コンパイル時型構築（パース不要）             |
| **エラー検出**             | 実行時（サイレント失敗もあり）     | コンパイル時 + 挿入時バリデーション          |
| **実行モデル**             | 単一スレッド逐次処理               | エンティティごとの独立キュー（並列可）       |
| **スコープ**               | グローバル状態（`\0`, `\1`で切替） | エンティティ固有（各キューが独立）           |
| **タイミング**             | ブロッキングウェイト               | ECS システムによる非同期タイミング           |
| **拡張性**                 | `\!` 拡張・ベースウェア固有タグ    | trait/enum ベースの型安全な拡張              |
| **並列性**                 | 不可（完全逐次）                   | エンティティ間で本質的に並列                 |
| **構造化**                 | フラットなテキストストリーム       | ECS コンポーネント（メタデータ付き）         |
| **プログラマティック生成** | 文字列連結・テンプレート           | ビルダーパターン / 直接構築                  |
| **変更検出**               | なし                               | `Changed<T>` / `Mut<T>` による ECS 変更検出  |
| **デバッグ**               | 文字列ダンプ                       | `Debug` derive / 構造化ログ                  |
| **複数キャラクター**       | スコープ切替で暗黙管理             | 各キャラクターが独立エンティティ・独立キュー |
| **DSL 連携**               | SHIORI が文字列出力                | pasta DSL が型付きコマンド列を直接生成       |
| **メタファー**             | 台本（テキストに演出を埋め込む）   | キューシート（構造化された演出指示列）       |

## 8. 設計への示唆

### 8.1 cue-system が解くべき本質的な問題

さくらスクリプトが解いた問題を、ECS アーキテクチャの原則に沿って再定義する:

| さくらスクリプトの問題領域           | cue-system での再定義                                                    |
| ------------------------------------ | ------------------------------------------------------------------------ |
| 「テキストを一文字ずつ表示したい」   | テキストコマンドをキューに入れ、消費者（Typewriter）が一定間隔で取り出す |
| 「間（ウェイト）を入れたい」         | Wait コマンドが消費ペースを制御する                                      |
| 「表情を変えたい」                   | サーフェス変更コマンドが対象エンティティのキューに入る                   |
| 「複数キャラが掛け合いたい」         | 外部が複数エンティティのキューにそれぞれコマンドを投入する               |
| 「演出全体のタイミングを制御したい」 | dola との統合でグローバルタイムラインを管理                              |

### 8.2 pasta DSL → cue-system 変換の責務分離

```
┌──────────────┐
│ pasta DSL    │  会話記述（人間が書く）
│ ：ぱすたさん │
│ こんにちは   │
│ \w[500]      │
│ 元気？       │
└──────┬───────┘
       │ pasta パーサー（外部リポジトリ）
       ▼
┌─────────────────┐
│ 構造化コマンド列  │  Vec<CueCommand> 相当
│ [Text("こんにちは"), Wait(500ms), Text("元気？")]
└──────┬──────────┘
       │ cue-system（wintf 内）
       ▼
┌──────────────────────────────────┐
│ ECS コマンドキュー               │
│ Entity(balloon) ← CommandQueue  │
│   .push(Text("こんにちは"))     │
│   .push(Wait(500ms))            │
│   .push(Text("元気？"))          │
└──────────────────────────────────┘
       │ 消費者システム（Typewriter等）
       ▼
┌──────────────────┐
│ 画面上の描画      │
│ 「こんにちは」    │
│   ↓ 500ms 待機   │
│ 「元気？」        │
└──────────────────┘
```

### 8.3 既存 TypewriterToken との関係

現在の wintf には既に `TypewriterToken`（Stage 1 IR）が存在する:

```rust
pub enum TypewriterToken {
    Text(String),
    Wait(f64),
    FireEvent { target: Entity, event: TypewriterEventKind },
}
```

cue-system はこれを**汎用化・上位互換化**する存在であり:
- `TypewriterToken` は cue-system のバルーン向けコマンド型のサブセットになる
- cue-system は Typewriter 以外の消費者（animation-system 等）にも同一メカニズムを提供する
- 既存の `TypewriterToken` → `TypewriterTimeline` への変換パイプラインは、cue-system の消費者側実装として再整理される

## 付録A: さくらスクリプト頻出パターン集

### A.1 基本的な掛け合い

```
\0\s[0]ねえ、今日何食べたい？\w[500]
\1\s[5]うーん…\w[800]パスタがいいな。
\0\s[3]いいね！\w[300]じゃあ作るよ。
\e
```

### A.2 感情表現を伴う独白

```
\0\s[0]今日は一日中雨だったなぁ。\w[500]
\s[2]……でも、\w[300]雨の音って、\w[200]けっこう好きかも。\w[800]
\s[0]えへへ。
\e
```

### A.3 選択肢の提示

```
\0\s[0]何か飲む？
\n\n
\q[コーヒー,choice_coffee]
\q[紅茶,choice_tea]
\q[いらない,choice_none]
```

### A.4 タイムクリティカル（システムメッセージ風）

```
\0\_q\f[size,10]---システムメッセージ---\n
新しいアップデートがあります。\n
詳しくは\_a[update_info]{こちら}\_aをご確認ください。\f[default]
\e
```

### A.5 複数キャラクターの同時アクション風（擬似並列）

```
\0\s[5]せーの…\w[100]
\1\s[5]\w[100]
\0いっせーの\w[50]\1せっ！\w[50]
\0\s[8]\1\s[8]
\e
```

> **注記**: 上記は厳密には並列ではなく、高速なスコープ切替による擬似的な同時アクションである。人間の知覚閾値（約50ms）以下の切替で「同時」を演出している。
