# ギャップ分析: areka-P0-budoux-reveal-reflow

> 2026-10-05 `/kiro-validate-gap`。確定済みの requirements.md と、今のコード（ブランチ `claude/budoux-reveal-reflow-468f2b`）の差を調べた記録。
> 本書は情報と選択肢を並べるもので、決定はしない。コードの引用は「何の定義か」で指し、行番号は補助（調査時点の値）。

## 1. まとめ

- **原因は 1 か所**。提示の本体 `present_actor`（`crates/areka-emo-text/src/actor_present.rs`・250 行付近）が、文節の折り返しのときだけ、毎フレーム `segment_plan(actor_state.items())` で「その時点までに届いた字の全部」から区切りを計算し直している。区切りが変われば、同じ字でも配置の結果が変わる。字が後から増える経路で、前の区切りを覚えている場所はどこにも無い。
- **配置の本体は「区切りが同じなら、前の字の行は後ろの字で変わらない」作りになっている**（3 章で根拠）。つまり、届いた字の区切りを後から変えなければ、配置の関数（`layout*.rs`）は 1 行も触らずに約束が成り立つ。
- **覚える単位の候補は 2 つ**。「届いた字」（合図 1 つごと）と「表示された字」（フレームごと）。前者は合図の列だけで結果が決まり、後者はフレームの時刻と、別スレッドから届く合図との前後で結果が変わる（5 章）。
- **1 字ずつの折り返し（`budoux_newline` 無し）は、合図が分かれて届いても行が動かない**（要件 3.3）。コードの構造から確かめた（3 章）。実行はしていない。
- **「字が後から増える」経路を踏む検査は今 1 本も無い**（4 章）。既存の検査は合図を全部先に積んでからフレームを回すか、同じ字の列で見える数だけを変えている。
- 規模の見立て: 案 A なら S、案 B なら M（8 章）。

## 2. 今の作り（関係する部品）

| 部品 | 場所 | していること |
|---|---|---|
| 台本の字 → 合図 | `compile` の `Instruction::Text` の腕（`crates/areka-sakura/src/compile.rs` 75 行付近） | タグとタグの間の字を 1 つの `CueCommand::Text` にする。`\_w` のほか `\s`・`\![bind,…]` でも切れる |
| 合図を時刻で配る | `CuePlayer::tick`（`crates/dola/src/cue/runtime.rs` 182 行付近） | 予定の時刻に達した合図だけを、登録された受け口すべてへ渡す |
| 受け口 | `EmoTextSink::emit`（`crates/areka-emo-text/src/sink.rs`） | 再生側のスレッドから UI スレッドの待ち行列へ積む（待たない） |
| UI スレッドでの適用 | `spawn_emo_text` の handler → `TextLayerRuntime::apply_cue`（`actor.rs` 308 行付近）→ `TextLayerState::apply_cue`（`state.rs` 425 行付近） | 字を `items` の末尾へ足し、1 字ごとの表示の時刻を決める。幅もフォントも知らない |
| 毎フレームの提示 | `present_frame` → `present_actor`（`actor_present.rs`） | 見える字の数 → 区切り（文節の折り返しのときだけ）→ 配置 → あふれの窓 → 選択肢 → 描画 |
| 区切りの計算 | `segment_plan`（`segment.rs` 95 行付近） | `items` を改行と `\_l` で区切った範囲ごとに BudouX へかけ、字の通し番号の上の「まとまり」の列にする。状態を持たない |
| 配置 | `LayoutEngine::layout_styled` → `layout_inner`（`layout_scan.rs`）→ 字の腕 `Scan::glyph`（`layout_scan_glyph.rs`） | 字を先頭から順に 1 つずつ置く。フレームをまたぐ状態を持たない |

押さえておく事実:

- **合図の適用とフレームは別々に進む。** 合図は再生側のスレッドから待ち行列を通って UI スレッドへ届く（`sink.rs` の冒頭の説明）。1 フレームの間に合図が 0 個のことも複数個のこともあり、その割れ方は実行のたびに変わりうる。
- **状態の層は幅を知らない。** `TextLayerState` は純粋な層で、バルーンの幅・フォント・折り返しの方式（`ResolvedBalloonText`・`TextLayerRuntime::layout_input`）は実行時の側にある。だから「何行目か」は合図が届いた時点では決められず、フレームの時点でしか出せない。一方「どこで区切るか」は字だけで決まるので、届いた時点でも出せる。
- **`segment_plan` は毎フレーム、届いた字の全部を BudouX にかけている**（キャッシュ無し）。
- 完了済み `areka-P0-budoux-newline` の design（`.kiro/specs/completed/areka-P0-budoux-newline/design.md` の INV-1・INV-2）と `segment.rs` の冒頭の注記「入力は常に全 `items`（可視 prefix ではない）」は、「全 items ＝ 台詞の全文」を暗黙の前提にしている。INV-2 が保証するのは「**同じ items** に対して、見える数だけを変えても行が動かない」まで。

## 3. 配置の本体は「前だけ」で決まるか（要件 3.3 と、直し方の土台）

字の腕 `Scan::glyph`（`layout_scan_glyph.rs`）を読んだ結果。

### 3.1 1 字ずつの折り返し（要件 3.3）＝成り立つ

- 行を送るかどうかの式は `WrapPlan::CharByChar` の腕の `!self.current.is_empty() && self.inline_pos + advance > self.soft`（80〜84 行付近）と、描画範囲の端の判定 `over_hard`（134 行付近）の 2 つだけ。
- 式が読むのは、今の行に置いた字（`current`）・今の行内の位置（`inline_pos`）・この字の送り幅（`advance`）・基準の幅（`soft`・`hard`）。前の 3 つは「この字より前の項目を順に処理した結果」と「この字そのもの」だけから決まる。後ろの字は読まない。
- この字の送り幅は `glyph_style_advance`（`layout_styled.rs`）が、その字の通し番号の装飾番号から決める。装飾番号は字を足したときに付き（`push_current_style`・`state_decoration.rs`）、後から書き換えない（同ファイル冒頭「戻す操作は既に追記済みの文字の番号を書き換えない」）。
- 改行（`Scan::line_break`）と `\_l`（`Scan::cursor_move`）も、届いた時点までの位置だけを読んで保留に積む（`layout_scan.rs`）。
- 走査は `layout_inner` の `for item in items` で先頭から順に進み、見える数に達したら止まる。字が後ろに足されても、前の字を処理する時点の状態は同じになる。
- したがって、**1 字ずつの折り返しでは、合図がいくつに分かれて届いても、置いた字の行と行内の位置は変わらない**。`present_actor` の `WrapMode::CharByChar` の腕は `segment_plan` を呼ばないので、区切りの計算し直しも起きない。
- 根拠は読み取りで、実行はしていない（検査を 1 本足すには crate のテストの建て直しが要り、安くない）。要件 5 の検査に「1 字ずつの折り返しで合図を分けても行が同じ」を 1 本足せば実行でも固定できる。

### 3.2 文節の折り返し＝後ろの字に左右される入口は 1 つ

- `WrapPlan::Segmented` の腕は、まとまりの先頭で `plan.segment_starting_at(self.placed)` を引き、まとまり全体の幅 `segment_advance_sum`（`layout_line_ops.rs`）を先に足し合わせて、行の残りに収まるかを決める（85〜122 行付近）。
- ここで後ろの字を読むのは「同じまとまりの残りの字」だけ。まとまりの列（`SegmentPlan`）が同じなら、3.1 と同じ理由で前の字の行は動かない。
- 後ろの字で結果が変わるのは、**まとまりの列そのものが変わるとき**だけ。今は毎フレーム全部を計算し直すので、次の 2 通りで変わる。
  1. 届いた字が、表示済みの字と同じまとまりに入る（「‥‥」＋「ええと、」→「‥‥ええと、」）。まとまりが長くなり、行の残りに収まらなくなって、まとまりごと次の行へ送られる。
  2. 届いた字で、前のほうの区切りの位置が変わる（BudouX は前後の字を見て区切りを決める）。
- 逆に言うと、**すでに届いた字のまとまりを後から変えない**（足すだけにする）なら、配置の関数は今のまま、置いた字の行と行内の位置が動かなくなる。

### 3.3 見つけた端の事例（行の割り当てには影響しない）

- 行の丈を追う `LineHeights`（`layout_styled.rs`）は、字の無い行を閉じるときにだけ「そのスコープの今の見た目の大きさ」（`GlyphStyles::current`）を使う。これはフレームの時点の値なので、後から `\f[height,…]` が届くと変わる。当たるのは「改行だけの行＋`\_l`」のような字の無い行の送りの量だけで、変わるのは行の上下の位置（画素）。どの字が何行目の何番目かは変わらない。要件の「行の割り当て」の定義（Introduction）には入らないので、本 spec の対象外と読める。記録だけ残す。

## 5. 覚える単位: 「届いた字」と「表示された字」

| | 届いた字（合図 1 つごと） | 表示された字（フレームごと） |
|---|---|---|
| 覚えるもの | 区切り（または「どこまでが 1 つの合図で届いたか」の境目） | 行の割り当て（どの字の前で行を送ったか）と、どこまで表示したか |
| 覚える時点 | 合図を適用した時点（`apply_cue`） | 提示した時点（`present_actor`） |
| 置ける場所 | 状態の層（`ActorTextState`）にも実行時の側にも置ける | 実行時の側（`TextLayerRuntime`）だけ。幅が要るので状態の層には置けない |
| 結果が何で決まるか | 合図の列だけ。フレームの時刻にも、合図とフレームの前後にもよらない | 合図の列＋フレームの時刻＋合図とフレームの前後（別スレッドなので実行ごとに変わりうる） |
| まだ表示されていない字 | 届いた時点で区切りが固まる。まとめて届いた合図どうし（早送りなど）も、合図の境目では 1 つのまとまりにならない | 表示されるまでは組み直せる。まとめて届いた合図は全部を見て区切れる |
| 要件 1.5（同じフレームにまとめて届く） | 合図ごとに足すだけなので自然に満たす | 満たす（フレームの時点で表示済みだった字だけ固定） |
| 要件 1.6（最初から最終位置に出す） | 満たす（届いた字の行は以後動かない） | 満たす（表示した字の行は以後動かない） |
| 要件 2.6（同じ字・同じ区切り・同じ時刻なら同じ結果） | そのまま満たす | 「フレームの時刻も入力に数える」と読まないと満たせない |
| 要件 3.1（1 つの合図で全文なら今と同じ） | 満たす | 満たす |
| 既存の検査の形 | `actor_scroll_retain_tests.rs` の「同じ合図を新しい実行時に積んで 1 フレームだけ出した面と一致」がそのまま使える | 合図を途中で足す検査では、この突き合わせが成り立たなくなる（1 フレームだけ出す側は全部を見て区切る） |
| 後続の `talk-fast-forward` | 残りの字が一度に届いても、合図の境目ごとに折り返しうる（最終形が「全文を一度に」と違うことがある） | 残りの字を全部見て区切れる（表示済みの字の後ろだけ） |

補足:

- ふつうの再生では 2 つの差はほとんど出ない。次の合図の予定の時刻は、前の合図の字が出終わった後（`compile` が `offset += 再生時間` で並べる）なので、次の合図が届く時点で前の合図の字は表示済みになっている。差が出るのは、合図がまとまって届くとき（フレームの遅れ・長さ 0 の合図の連続・早送り）。
- 「表示された字」を単位にすると、まとまりの途中まで表示した時点で後ろの字が届いたとき、**元は 1 行に収まると決めてあったまとまりが、表示済みの字の直後で割れる**ことがある（残りと新しい字が 1 つの塊になり、行の残りに収まらなくなるため）。「届いた字」を単位にすると、届いたまとまりは割れない。
- 中間の案として「予定の時刻で見て、次の合図の `at` より前に出る字だけを固定する」も考えられる（合図の列だけで決まる）。ただし合図の適用とフレームが別々に進むため、予定の時刻では未表示のはずの字が実際には表示済み、という食い違いが起こりうる（長さ 0 の合図が同じ時刻に並ぶ場合など）。約束を破る穴になるので、採るなら配る順の保証を先に調べる必要がある。

## 6. 覚えたものを捨てる場所と、行の割り当てを使う側

### 6.1 内容が消える・入力が変わる場所（調べた全部）

| 出来事 | コードの場所 | 今していること |
|---|---|---|
| `\c`（その場所だけ） | `TextLayerState::apply_cue` の `Clear` の腕 → `ActorTextState::clear_content`（`state_decoration.rs` 242 行付近）。実行時の側は `TextLayerRuntime::apply_cue` の `Clear` の腕（`actor.rs`） | 字・表示の時刻・選択肢・装飾番号を空にする。実行時の側は描画の全消し要求と、選択肢の hover・当たり行の写しを外す |
| 台詞の頭（全部の場所） | 同 `ClearAll` の腕 | 全部の場所で同上＋行き先を既定へ戻す |
| シェルの切替で箱の束が替わる | `TextLayerState::set_box_index`（`state_route.rs` 59 行付近）・`TextLayerRuntime::set_box_layout`（`actor_box.rs` 43 行付近） | 箱の場所の状態を**項目ごと**捨てる。実行時の側は箱の面・登録・写しを全部外す |
| 箱が今の絵に無くなる | `TextLayerRuntime::unregister_box`（`actor_box.rs` 428 行付近） | 登録と面を外す。**字は保つ**（また出れば同じ字を配置し直す） |
| バルーンの付け直し・拡大率や描画範囲の変化 | `TextLayerRuntime::register_actor`・`refresh_actor_binding`（`actor_attach.rs`） | 配置の入力（幅・フォント・折り返しの方式）を差し替え、描画の資源を捨てる。**字は保つ**。次のフレームで新しい幅で全部配置し直す |
| 字の行き先の切替（`\b[名前]`・`\s`） | `route_select`・`route_surface`（`state_route.rs`） | 以後の字の宛先が替わるだけ。前の場所の字はそのまま |

- 場所ごとの独立（要件 1.8）: 状態は場所の鍵（`PlaceKey`＝スコープ×「普通のバルーン／箱の名前」）ごとの `ActorTextState`、実行時の表もすべて `PlaceKey` が鍵。合図は届いた時点の行き先 1 つにだけ足される（`apply_cue` の `dest`）。覚えるものを場所ごとに持てば、ほかの場所へは及ばない。
- **覚える場所による違い**:
  - `ActorTextState` の欄にする場合: `clear_content` に 1 行足せば、上の表の上 3 つ（`\c`・台詞の頭・箱の束の差し替え）で必ず一緒に消える。字と同じ寿命になるので、捨て忘れが構造上起きない。下 3 つ（字を保つ出来事）では残る。
  - `TextLayerRuntime` の表にする場合: 上の表の 5 か所（`Clear`・`ClearAll`・`set_box_layout`・`unregister_box`・`register_actor`）それぞれに消す行が要る。既存の `choice_snapshot` が同じ形で 4 か所から消されている。
- **幅が変わる出来事（バルーンの付け直しなど）の扱い**: 覚えるのが「区切り」なら、新しい幅で配置し直すだけで、幅を超える字は出ない。覚えるのが「行の割り当て」なら、古い幅で決めた行が新しい幅を超えうる（要件 2.2 に反する）ので、ここで捨てて決め直す必要がある。なお、この出来事で行が変わること自体は要件 1 の対象（「新しい合図の字が届く」）の外。
- 既存の `state_cue_apply_tests.rs` の `clear_resets_actor_state_to_initial`・`clear_resets_choices_alongside_items` は「`\c` の後の状態が初期値と等しい」を見ている。`ActorTextState` に欄を足すなら、`clear_content` で必ず初期値へ戻す（戻さないとこの 2 本が赤になる＝見張りとして働く）。

### 6.2 行の割り当てを使う側（すべて `present_actor` の中・同じ `lines` から）

| 使う側 | 関数 | 行の割り当ての使い方 | 自分で覚えているもの |
|---|---|---|---|
| あふれのスクロール | `LayoutEngine::visible_window`（`layout.rs`） | 最後の行が欄に収まる最小の「先頭の見える行」を毎フレーム決め直す | 無し |
| 描き直す範囲 | 行の指紋（`viewbox_diff.rs` の `line_fingerprint`）と確定済みのスクロール量 | 前のフレームと行の中身・位置が違う行だけ描き直す | 前のフレームの行の指紋・スクロール量（`\c` で全消し） |
| 選択肢の行への割り付け | `annotate_lines`（`choice.rs`） | 選択肢の字の通し番号の範囲と、行ごとの字数の積み上げを突き合わせる | 無し |
| 選択肢の強調 | `line_bands`・`decorate_canvas` | 行ごとの帯 | hover の番号だけ |
| 選択肢のクリックの範囲 | `derive_hit_rows` → `to_window_physical` → `choice_snapshot` | 同じ `lines`・同じ帯から | 提示できたフレームの写し |
| 箱の字のクリックの範囲 | `glyph_cells` → `set_hit_cells` | 見えている字 1 字ずつの矩形 | 面の側の写し |

- どれも「そのフレームの `lines`」だけを源にしていて、行の割り当てを別に覚えてはいない。**`lines` が安定すれば、要件 4.2・4.3・4.4 は使う側に手を入れずに成り立つ**（スクロールは行をまとめて送るだけ、強調とクリックは表示と同じ `lines` から出る）。
- 選択肢の字も `Choice` の合図として `items` に足される（`apply_cue` の `Choice` の腕）。合図 1 つ＝選択肢 1 つなので、「届いた字」を単位にすると選択肢 1 つが 1 回ぶんの区切りの対象になる。
- 明示の改行と `\_l` は、今も区切りの範囲の境目（`segment_plan` の `LineBreak`・`CursorMove` の腕）。要件 2.4・4.5・4.6 は今の規則を保てば足りる。

## 8. 直し方の選択肢

brief の案 2（全文を先に渡す）と案 3（続きを待つ）は、要件の Introduction（台本のコンパイルと合図の語彙を変えない・表示を遅らせない）で外れている。残る案 1 の中の作り方を並べる。

### 案 A: 届いた字を単位に、区切りを足すだけにする（今ある部品を広げる）

- **作り**: 合図で字を足すたびに「ここから新しい合図の字」という境目を、場所ごとの状態（`ActorTextState`）に覚える。区切りの計算に、境目を受け取る入口を足す（今の `segment_plan(items)` は残す）。境目をまたいで 1 つのまとまりにしない。`present_actor` の文節の折り返しの腕だけが新しい入口を呼ぶ。配置（`layout*.rs`）と `WrapPlan` は触らない。
- **触るファイル**: `state.rs`（`Text`・`Choice` の腕で境目を足す）・`state_decoration.rs`（`clear_content` で消す）・`segment.rs`（入口の追加と冒頭の説明）・`actor_present.rs`（呼び先の差し替え・説明）・`layout.rs`（説明だけ）。新しい検査のファイル 1〜2 本。
- **中で分かれる点（設計で決める）**:
  - 新しい合図の字を BudouX にかけるとき、(i) その合図の字だけを渡すか、(ii) 範囲の先頭からその合図の末尾までを渡して、境目より後ろの区切りだけ採るか。(ii) は前の字を文脈に使えるので区切りが自然になりやすいが、計算量が増える（合図の数 × 範囲の長さ）。どちらも範囲に合図が 1 つなら今と同じ結果。
  - 覚えるのを「境目の位置だけ」にして毎フレーム区切りを出し直すか、「区切りそのもの」を覚えて合図ごとに足すか。後者は BudouX の呼び出しが合図ごと 1 回に減る（今は毎フレーム全部）。ただし状態の層は折り返しの方式を知らないので、区切りそのものを状態に持つなら「1 字ずつの折り返しでは区切りを計算すらしない」（完了済み spec の構造の約束）と両立する置き場所を選ぶ必要がある（実行時の側のキャッシュにする、など）。
- **良い点**: 結果が合図の列だけで決まる（フレームにも、スレッドの前後にもよらない）。配置を触らないので要件 2.2・2.3・3.2・4.2〜4.6 と後続 3 spec の足場がそのまま。消去は `clear_content` の 1 行で済む。幅が変わっても破綻しない。
- **悪い点**: まとめて届いた合図（早送りなど）でも、合図の境目で文節が分かれうる。`ActorTextState` に欄が増える（`state.rs` の `clears` の説明に「内容の状態の形と等しさを変えないため」とあり、形を変えることへの配慮が既にある。等しさを見る既存の検査は 4 本あるが、同じ合図の列どうしの比較と「`\c` の後は初期値」の比較なので、消去で戻せば成り立つ見込み）。
- **規模 S／リスク 低〜中**: 既存の型の延長で、触る判断の分岐は区切りの 1 か所。残るリスクは、BudouX が短い断片（「‥」1 字など）をどう区切るかと、既存の検査の期待値への波及（9 章）。

### 案 B: 表示された字を単位に、行の割り当てを固定する（新しい部品を足す）

- **作り**: 実行時の側に、場所ごとの「どこまで表示したか」と「表示済みの範囲で行を送った位置」を覚える。配置に「この位置までは覚えた行送りに従い、区切りの判定をしない」入口を足す（`WrapPlan` に形を足すか、引数を足す）。表示済みの字にまたがるまとまりは、表示済みの直後で切って、残りを新しい塊として判定する。
- **触るファイル**: `actor.rs`（表と、`Clear`・`ClearAll` での消去）・`actor_present.rs`（更新と受け渡し）・`actor_box.rs`（2 か所の消去）・`actor_attach.rs`（幅が変わるときの消去）・`layout.rs`／`layout_scan.rs`／`layout_scan_glyph.rs`（固定の入口と判定）。
- **良い点**: まだ表示していない字は全部を見て区切り直せる（早送りの最終形が「全文を一度に」に近い）。要件の言葉（「表示済みの字」）にそのまま対応する。
- **悪い点**: 結果がフレームの時刻と、合図とフレームの前後に左右される（要件 2.6 の読み方が要る・検査はフレームの時刻の列まで固定する必要がある）。配置の判定に分岐が増え、後続の `text-typesetting`（同じ字の腕に禁則を足す予定）と重なる。消す場所が 5 か所。まとまりの途中で割れる場合がある（5 章の補足）。既存の「1 フレームだけ出した面と一致」の突き合わせが、合図を途中で足す検査では使えない。
- **規模 M／リスク 中**: 配置の本体に新しい分岐、実行時の状態に新しい寿命の管理。

### 案 C: 案 A の記録を土台に、未表示の字だけ組み直しを許す（組み合わせ）

- **作り**: 案 A と同じく合図の境目を状態に覚える。そのうえで「次の合図の予定の時刻より前に出る字」だけを固定し、まだ出ない予定の字は新しい合図と一緒に区切り直す（5 章の補足の中間案）。
- **良い点**: 合図の列だけで決まる。まとめて届く場合の最終形が案 A より良い。
- **悪い点**: 予定の時刻と実際の表示が食い違うと、表示済みの字が動く穴になる。合図の配り方（再生側のスレッド → 待ち行列 → UI スレッド）とフレームの時刻の関係を先に確かめる必要がある。
- **規模 S〜M／リスク 中〜高**: 約束（要件 1）そのものに穴が残りうる。

## 9. 設計の段へ持ち越す調べもの

- **BudouX の断片への反応**: 「イイジャン！」「‥」「‥」「ええと、」を (i) 1 つずつ渡したとき、(ii) 前の字を付けて渡したときの区切り。要件の例（「イイジャン！‥‥ ／ ええと、」）は幅しだいでもあるので、検査では決まった字幅と欄の幅を「ええと、」が 1 行目に収まらない値に選ぶ必要がある。
- **既存の検査への波及**: 文節の折り返しで、1 つの範囲に合図が複数ある台本を通している検査（`tests/emo2_fixture_e2e_test.rs`・`tests/kero_menu_capacity_test.rs` の実台本・`crates/areka/tests/emo2_real_run.rs`）の期待値が動くか。動くなら要件 3.4 と当たるので、設計の前に全体を 1 回回して確かめる価値がある。
- **切り出し口**: 「状態＋解決済みの入力＋字幅の注入 → 区切り → 配置」を 1 つの関数にして `present_actor` と検査の両方から呼ぶ形が取れるか（`present_actor` は字幅を `render.metrics` から取るので、引数は `&dyn GlyphMetrics` にできる見込み）。
- **「本番と同じ経路」の範囲**（要件 5.1）: `CuePlayer` を検査のスレッドで回して時刻で配らせるか（`areka-ghost` の検査に先例）、`compile` の合図を予定の時刻で順に `apply_cue` するか（`kero_menu_capacity_test.rs` の先例）。
- **計算量**: 今は毎フレーム全部を BudouX にかけている。案 A の (ii) をキャッシュ無しで作ると合図の数だけ増える。長い台詞での 1 フレームの時間を測るか、合図ごと 1 回に減らす形にするか。
- **新しいファイルの登録**: `areka-emo-text` に本番のファイルを足すなら、`lib.rs` の `PURE_SOURCES`（純粋な層）か `SOURCES_OUTSIDE_THE_PURE_SCAN` へ載せる（載せるまで赤になる検査がある・`.kiro/steering/structure.md`）。検査は兄弟ファイルへ置き、1 ファイル 1,000 行以下。

## 10. 要件の討議へ出す項目

1. **覚える単位**（「届いた字」か「表示された字」か）。5 章の表のとおり、前者は合図の列だけで決まり配置を触らない、後者はまとめて届く字を全部見て区切れるがフレームと前後に左右される。要件 1 は「表示済みの字」で書かれているが、「届いた字」を固定しても要件 1 は満たす（より強い）。要件 2.6 の「同じ時刻に届いたとき」をどちらの読みで確定するか。
2. **まとめて届いた合図の折り返し**。「届いた字」を単位にすると、早送りなどで残りが一度に届いても合図の境目で文節が分かれうる（例: 最終形が「イイジャン！‥‥ ／ ええと、」のまま）。後続 `talk-fast-forward` はこれを当てにしてよいか、それとも早送りの最終形は「全文を一度に」と同じにしたいか。
3. **新しい字を区切るときの文脈**。その合図の字だけで区切るか、前の字を文脈として BudouX に見せるか（8 章 案 A の (i)(ii)）。見た目の自然さと計算量の交換。
4. **覚える場所**。字と同じ寿命で状態の層に置く（消し忘れが構造上起きない・状態の形が変わる）か、実行時の側に置く（状態の形は変わらない・消す場所が 5 か所）か。
5. **幅が変わる出来事**（バルーンの付け直し・拡大率や描画範囲の変化）で行が変わることを、本 spec の約束の外と明記するか。要件 1 の引き金は「新しい合図の字が届く」なので外と読めるが、要件には書かれていない。
6. **検査が歩く経路の範囲**（要件 5.1・5.5）。決まった字幅で `present_actor` の配線ごと歩くには切り出し口が要る（4 章）。切り出しを本 spec の範囲に入れるか、検査の側で区切りと配置を並べる形（配線は歩かない）で足りるとするか。
7. **1 字ずつの折り返しの検査**（要件 3.3）。読み取りでは成り立つ。実行で固定する検査を本 spec で 1 本足すか。
8. **既存の検査の期待値が動いた場合の扱い**（要件 3.4）。範囲に合図が複数ある台本の最終形は、約束どおり直すと変わりうる（「イイジャン！ ／ ‥‥ええと、」→「イイジャン！‥‥ ／ ええと、」）。これを見ている既存の検査があれば、「内容を書き換えずに」と当たる。9 章の確かめの結果しだいで議題になる。
