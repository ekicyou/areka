# Implementation Plan

- [x] 1. 基盤: 重なり関係の宣言と判断の中核
- [x] 1.1 窓の重なりを OS へ問い合わせ、owner 関係を張り外す手段を用意する
  - ある窓の 1 つ手前／1 つ背後にある窓を OS へ問い合わせる手段を追加する
  - ある窓の owner を設定する手段と、owner を外す手段を追加する
  - いずれも失敗を握り潰さず呼び出し側へ返し、記録できる形にする
  - 観測: 既知の 2 窓を生成して重なり順を実測し、期待どおりの前後関係が返ることを確かめる単体テストが緑になる
  - _Requirements: 5.9, 7.2_

- [x] 1.2 (P) ペア関係の宣言・再断行要求・確立記録・実行時ストラテジの状態を定義する
  - 「この窓は相手の窓のすぐ手前に居るべき」という永続宣言の状態を定義する
  - 重なりを断行し直す一回限りの要求（適用済み・検証待ちの段階を持つ）を定義する
  - owner を張った事実の記録と、案 A／案 B を実行時に切り替える設定を定義する
  - 宣言と再断行要求を**他のクレートから付けられる公開到達性**を持たせる（表示制御を所有する仕様が再表示時に再断行要求を入れる契約点になるため）
  - 観測: 別クレート側のテストから宣言と再断行要求を実体へ付けられ、各状態が読み書きできることを確かめるテストが緑になる
  - _Requirements: 1.1, 2.6, 3.4, 5.6_
  - _Boundary: zorder_pair 状態定義_

- [x] 1.3 是正判断を実機不要の純粋な判断として実装し、全分岐をテストで固定する
  - 「トリガ種別・両窓の生存・実測した前後関係」から「何もしない（理由つき）／バルーンを相手のすぐ手前へ／キャラを相手のすぐ背後へ」を決める判断を実装する
  - トリガ種別は「バルーン側の重なりが動いた」「キャラ側の重なりが動いた」「確立」「再断行」を区別できる形にする
  - 既に隣接しているときは必ず何もしないと決める同値の歯止めを入れる
  - 片方の窓が存在しないときは理由つきで見送り、残る窓に一切書き込まない
  - 判断の結果が座標や寸法を持ち得ない形にし、常時最前面の指定を決して返さないことをテストで固定する
  - 動かす対象が宣言されたペアの 2 窓に限られることをテストで固定する
  - 観測: 全分岐（見送り 5 種・手前へ・背後へ・最上位の縁）を網羅した単体テストが緑になり、常時最前面を返す経路が存在しないことを対照ケース込みで確かめられる
  - _Requirements: 1.2, 1.3, 1.5, 1.6, 3.1, 3.2, 3.3, 3.4, 4.3, 7.1, 8.1_
  - _Depends: 1.2_

- [x] 1.4 診断記録の語彙を実装する
  - 宣言・owner 確立・是正・見送り・検証不一致・確立失敗・沈降観測の各記録を出せるようにする
  - 是正の記録には出した指令と、その後に実測した前後関係を同じ 1 行へ載せる
  - 見送りは必ず理由を伴わせ、記録の無い見送りが起きない形にする
  - 失敗と検証不一致は error 水準で記録する
  - 観測: 記録捕捉のテスト支援で各記録が期待する語で拾えることを確かめ、対照ケース（記録されないはずの状況）も併置した単体テストが緑になる
  - _Requirements: 6.1, 6.2, 6.3_
  - _Depends: 1.2_

- [x] 2. 案 A（本線）: owner による重なり保証の確立と維持
- [x] 2.1 両窓のハンドルが揃った時点で owner を一度だけ張る確立処理を実装する
  - 両方の窓に OS のハンドルが付いた巡で、バルーン窓の owner をキャラ窓に設定する
  - 成功したら確立の記録を残し、初期の隣接を確定させるため再断行の要求を一度入れる
  - 失敗したら error 水準で記録し、同じハンドルでの再試行は繰り返さない（窓は現行どおり表示され続ける）
  - 観測: ヘッドレスで両窓のハンドル付与を再現し、確立が 1 回だけ走ること・片方欠けでは走らず見送りが記録されることを確かめるテストが緑になる
  - _Requirements: 1.1, 6.1, 6.2_
  - _Depends: 1.1, 1.2_

- [x] 2.2 維持処理を実装する（トリガ受理 → 観測組立 → 判断 → 適用 → 次巡での実測検証）
  - 再断行の要求を受け、両窓の実測前後関係を採って判断へ渡す
  - 是正は位置・寸法・活性化を伴わない形で発行し、重なりだけを動かす
  - 適用の次の巡で実測と期待を突き合わせ、一致なら是正の記録、不一致なら error 記録を残す（再試行の輪は作らない）
  - 適用が失敗しても利用者の操作を継続可能に保ち、異常終了しない
  - 観測: 要求の挿入から適用・検証・要求の消滅までの状態遷移をヘッドレスで辿るテストが緑になり、既に隣接している場合に一切の指令が出ないことも確かめられる
  - _Requirements: 1.2, 1.4, 1.5, 2.6, 6.1, 6.2, 6.3, 6.4, 7.6_
  - _Depends: 1.3, 1.4_

- [x] 2.3 破棄時に owner を切り離し、重複破棄でも異常終了しない状態を作る

  - 同一スコープの 2 窓が対で消えること自体は許容する
  - 観測: キャラ先行・バルーン先行の双方の破棄順をヘッドレスで再現し、切離しが走ること・残る窓や他スコープの窓が消えないこと・処理が継続することを確かめるテストが緑になる

- [x] 2.4 他アプリ活性化時の沈降を、遅延させた実測で記録する

### ✅ (6.3→6.4) 欠陥を発見し是正した: 挿入位置が他アプリの常時最前面窓だとバルーンが帯へ引き込まれた

6.3 の対照テストが **OS の性質を実測で確定させ、そこから本番の穴が出た**。
開発者裁定により本仕様で是正（タスク 6.4）。以下は発見時の記録。

**OS の性質（実測）**: `SetWindowPos` の `hWndInsertAfter` に常時最前面の窓を指定すると、
対象窓が常時最前面の帯へ**引き込まれる**（`WS_EX_TOPMOST` が付き、以後外れない）。
レビューが独立に再現——この機械の実デスクトップは可視窓 33 枚（常時最前面 6・通常 27）で、
帯の境界が実在し、その境界の窓を挿入位置に渡すと対象に印が付いた。

**本番の穴**: 是正の挿入位置は**実測**（`measure_window_above(character)`＝キャラ窓の最も近い
可視の手前）で決まる。キャラ窓が「可視の通常窓のうち最前面」のとき、これは**システムで
最も背面の可視な常時最前面窓**を返す。すると `place_above` が他アプリの常時最前面窓を挿入位置に
渡し、バルーン窓が黙って帯へ入る。所有は `zorder_pair.rs:326-336`。

**気づけない**: 引き込まれた後もバルーンは帯の最下・キャラは通常帯の最上なので**隣接は成立し、
次巡の検証も一致する**。`fix` が正常に出て `verify-failed` も error も出ない。表面化するのは
他アプリ活性化時の `sink-observed` で `adjacency_ok=false` になる形だけ（要件 4.1／4.2 の破れ）。

**実機ゲートが見逃した理由**: 案 A では是正の契機が確立と再断行だけで、G6 の時点で既に隣接
していたため `Skip(AlreadyAdjacent)` になり指令が 1 本も出ていない。

**次のウェーブで確率が上がる**: `balloon-visibility` が要件 2.6 の再表示を結線すると、
不可視のバルーンは可視限定の実測で読み飛ばされ、ゴーストが活性のときキャラ窓は
「可視の通常窓のうち最前面」そのものになる。

### (6.4) 是正の中身: 指令は実測で `HWND_TOP` に決まった・隣接を保っているのは owner 関係

採ったのは **`HWND_TOP`**（`ZOrder::Top`）。実測で idx 10 → idx 4・上の通常窓 0 枚・

### ✅ 是正済み: 複数ペアの是正が同一 flush で干渉する欠陥（2.2 の remediation）

**修正**: 1 巡で実際に指令を出すのは高々 1 ペアとし、残るペアの `ReassertZOrder` は消さずに次巡へ持ち越す（次巡は新しい実測から計算し直すので陳腐化しない）。持ち越しの分岐は `record_decision` の**後**にあるので、見送り 5 種は到達前に理由つきで記録されて消える——記録されていないのは「適用を 1 巡遅らせたこと」だけであり、要件 6.3 が禁じる「記録の無い見送り」ではない。

**収束の証明**（レビューが独立に検算）: 挿入位置は必ず「自分のキャラ窓の**最も近い可視の手前**の窓」。既に隣接しているペア Y を壊すにはその挿入位置が Y のバルーンである必要があり、それは `C_X = C_Y`（両ペアが同じキャラ窓を指す）を要求する。areka の spawn はスコープごとにキャラ 1 枚・バルーン 1 枚を作るので構造的に起こらない。窓の除去側も隣接を壊せないため単調で、上限は **ペア数 N の是正 ＋ 検証 1 巡 = N+1 巡**。**前提は 2 つ**——ペアどうしがキャラ窓を共有しないこと、および**キャラ窓が可視であること**（「最も近い可視の隣」関係が可視窓どうしで対称に成り立つことが土台）。

**採らなかった案**: (b) 先行指令の z 変化を模擬して後続の観測を補正——**OS が我々の指令に付随して別の窓を勝手に動かすことが実測で判明した**ため、OS 側の z 変化を完全に模擬できないことが確定した。(c) 実測と適用を交互にして毎回 flush——`SetWindowPosCommand` の flush 経路の改造は design「Revalidation Triggers」が `dpi-transition-atomicity` との再突合トリガに挙げている箇所に触れる。

**残る所見**: 1 巡 1 本の枠は本 system が積む指令にしか効かない。同じフレームに他の system が z を動かす `SetWindowPosCommand` を積めば実測は依然陳腐化しうる（本欠陥以前からの性質・実機では未再現）。

| 矩形 | `0,0,0,0`（0x0） |
| owner | **キャラ窓そのもの**（`verify-failed` の `expected_below` と毎回完全一致） |
| プロセス／スレッド | areka 自身・ゴースト 4 窓と**同一スレッド** |
| スタイル | `WS_POPUP \| WS_DISABLED \| WS_CLIPSIBLINGS` |
| 存続 | 一時的ではなく**居座る** |

**なぜ片方のスコープだけ失敗するのか**: 既定 IME 窓は**スレッドに 1 個**しか存在しない（`EnumThreadWindows` でプロセス全窓を列挙してもゴースト 4 窓＋IME の計 5 窓）。その 1 個の owner がスコープ 0 のキャラ窓なので、割り込みはスコープ 0 のペアにしか起きない。スコープ 1 は `GetWindow(GW_HWNDNEXT)` 1 歩でキャラ窓に到達し、割り込み 0 件。

**機序（推論・直接計測はしていない）**: IME 窓もバルーン窓も同じキャラ窓を owner に持つ被 owner 窓であり、Windows は被 owner 窓を owner の手前に保つ。よってキャラ窓の直上には被 owner 窓が 2 枚並び、その内部順序は我々の制御外——これが「すぐ手前」が 1 枚ぶんずれる構造的原因と考えられる。`owner-established` 時点では IME 窓はその位置に居ない（`measured_prev` はもう一方のキャラ窓）ので、確立と検証の間に入り込んでいる。

**タスク 4 の G6 の判定基準（裁定を反映した確定形）**: 「**各キャラ窓をクリックした後**に、そのキャラ窓の**最も近い可視の手前**がそのスコープのバルーン窓である」ことを実測レコードで確かめる。起動時の記録ではない。不可視窓の割り込みは読み飛ばして判定する。

### 3.2 の実機起動で見つかった欠陥（記録・上の 2 項の出所）

**症状**: 実ゴースト（emo2・2 スコープ）を起動すると、**起動のたびに決定論的に** scope 0 が `[zorder-pair] verify-failed`（error）になる。3 回の実行で 3 回とも再現（実装者 1 回・レビュー 2 回）。

**根因**: 維持系が**全ペアの実測を同一スナップショットから採り、flush を挟まずに同じ巡で全部の指令を積む**。後から適用される側の `insert_after` が、先行適用によって陳腐化する。実測ログの並びで説明すると——

- 起動直後の重なりは 手前から `balloon0, char1, char0`（`balloon1` は更に背後）
- scope 0 の指令: 「`balloon0` を `char0` のすぐ手前へ」＝ `insert_after=char1`
- scope 1 の指令: 「`balloon1` を `char1` のすぐ手前へ」＝ `insert_after=balloon0`
- 両方を同じ flush で適用すると `char1, balloon0, balloon1, char0` になり、**`balloon0` と `char0` の間に `balloon1` が割り込む**

**設計の穴**: design「System Flows > 維持系の判断と適用」の収束の議論（エコー遮断＋同値ガードの二重の停止条件）は**単一ペアしか論じていない**。1 巡内の複数ペア間で観測が陳腐化することを覆っていない。design 側の補筆も要る。

**要件 3.2／3.4 には抵触しない**（動いたのは自スコープの窓 1 枚のみで、scope 0 のペアの相対順も保たれている）。壊れたのは要件 1.1 の「すぐ手前」の隣接だけである。

**タスク 4 での誤読リスク（重要）**: ゲート G6 の判定基準は「**キャラ窓クリック後**の隣接実測」であって起動時の記録ではない。起動時の `verify-failed` を「owner による隣接保証の不成立」と読んで案 B へ倒すと、design と 5.7 に従って owner 機構が丸ごと撤去される。同じログの `fix entity=4v0 … measured_next_after_fix=<char1>` が、**owner 機構自体は真正面の隣接を作れている**ことを示している。

**`owner-detached` が 1 本も出ないこと**は別件で、既知（下の 2.3 の項）。終了時は 4 窓が 1 バッチで despawn するため標準機構では検知できない——G8 の判定対象であり、是正は 5.2 の担当。

- (1.1) `GetWindow` の対応は **`GW_HWNDPREV` = 1 つ手前（前面側）／`GW_HWNDNEXT` = 1 つ背後**。独立オラクル（`GetTopWindow`）で実測確認済み。以降の判断・適用でこの向きを取り違えると不変条件が丸ごと反転する。
