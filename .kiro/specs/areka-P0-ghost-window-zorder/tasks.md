## Implementation Notes

### ✅ 是正済み: 複数ペアの是正が同一 flush で干渉する欠陥（2.2 の remediation）

**修正**: 1 巡で実際に指令を出すのは高々 1 ペアとし、残るペアの `ReassertZOrder` は消さずに次巡へ持ち越す（次巡は新しい実測から計算し直すので陳腐化しない）。持ち越しの分岐は `record_decision` の**後**にあるので、見送り 5 種は到達前に理由つきで記録されて消える——記録されていないのは「適用を 1 巡遅らせたこと」だけであり、要件 6.3 が禁じる「記録の無い見送り」ではない。

**収束の証明**（レビューが独立に検算）: 挿入位置は必ず「自分のキャラ窓の 1 つ手前の窓」。既に隣接しているペア Y を壊すにはその挿入位置が Y のバルーンである必要があり、それは `C_X = C_Y`（両ペアが同じキャラ窓を指す）を要求する。areka の spawn はスコープごとにキャラ 1 枚・バルーン 1 枚を作るので構造的に起こらない。窓の除去側も隣接を壊せないため単調で、上限は **ペア数 N の是正 ＋ 検証 1 巡 = N+1 巡**。

**採らなかった案**: (b) 先行指令の z 変化を模擬して後続の観測を補正——**OS が我々の指令に付随して別の窓を勝手に動かすことが実測で判明した**ため、OS 側の z 変化を完全に模擬できないことが確定した。(c) 実測と適用を交互にして毎回 flush——`SetWindowPosCommand` の flush 経路の改造は design「Revalidation Triggers」が `dpi-transition-atomicity` との再突合トリガに挙げている箇所に触れる。

**残る所見**: 1 巡 1 本の枠は本 system が積む指令にしか効かない。同じフレームに他の system が z を動かす `SetWindowPosCommand` を積めば実測は依然陳腐化しうる（本欠陥以前からの性質・実機では未再現）。

### ⚠ 裁定待ち: スレッド既定の IME 窓が「すぐ手前」の判定を通さない（タスク 4 の G6 判定の前に裁定が要る）

多ペア干渉の是正後も、実機起動で **scope 0 の `verify-failed` が残っている**（修正後 5 回の実行すべてで再現）。

**割り込んでいる窓の正体は実測で確定した**（ゴースト起動 3 回・run3 は約 72 秒にわたり 6 回反復計測・全回同一）:

| 項目 | 実測値 |
|---|---|
| ウィンドウクラス | `IME`（タイトル `Default IME`） |
| 可視性 | **不可視**（`IsWindowVisible` = False） |
| 矩形 | `0,0,0,0`（0x0） |
| owner | **キャラ窓そのもの**（`verify-failed` の `expected_below` と毎回完全一致） |
| プロセス／スレッド | areka 自身・ゴースト 4 窓と**同一スレッド** |
| スタイル | `WS_POPUP \| WS_DISABLED \| WS_CLIPSIBLINGS` |
| 存続 | 一時的ではなく**居座る** |

**なぜ片方のスコープだけ失敗するのか**: 既定 IME 窓は**スレッドに 1 個**しか存在しない（`EnumThreadWindows` でプロセス全窓を列挙してもゴースト 4 窓＋IME の計 5 窓）。その 1 個の owner がスコープ 0 のキャラ窓なので、割り込みはスコープ 0 のペアにしか起きない。スコープ 1 は `GetWindow(GW_HWNDNEXT)` 1 歩でキャラ窓に到達し、割り込み 0 件。

**機序（推論・直接計測はしていない）**: IME 窓もバルーン窓も同じキャラ窓を owner に持つ被 owner 窓であり、Windows は被 owner 窓を owner の手前に保つ。よってキャラ窓の直上には被 owner 窓が 2 枚並び、その内部順序は我々の制御外——これが「すぐ手前」が 1 枚ぶんずれる構造的原因と考えられる。`owner-established` 時点では IME 窓はその位置に居ない（`measured_prev` はもう一方のキャラ窓）ので、確立と検証の間に入り込んでいる。

**裁定の論点**: 割り込む窓は**不可視で 0x0** である。要件 1.2 の字面（「そのキャラ窓との間に他のいかなる窓も入らない」）は、この窓がある限り Windows 上で構造的に達成できない。一方、要件の趣旨は Introduction が述べる「会話が読める」＝**可視の遮蔽**であり、可視の窓だけを見ればバルーンはキャラのすぐ手前に居る。**我々の「配置」は 1.2 を満たしており、過剰に落としているのは「測り方」の側**である（測り方は要件 7.2 が我々に委ねている）。

**タスク 4 での誤読リスク（重要）**: ゲート G6 の判定基準は「**キャラ窓クリック後**の隣接実測」であって起動時の記録ではない。起動時の `verify-failed` を「owner による隣接保証の不成立」と読んで案 B へ倒すと、design と 5.7 に従って owner 機構が丸ごと撤去される。**この裁定が済むまで G6 を判定しないこと。**

### 3.2 の実機起動で見つかった欠陥（記録・上の 2 項の出所）

**症状**: 実ゴースト（emo2・2 スコープ）を起動すると、**起動のたびに決定論的に** scope 0 が `[zorder-pair] verify-failed`（error）になる。3 回の実行で 3 回とも再現（実装者 1 回・レビュー 2 回）。

**根因**: 維持系が**全ペアの実測を同一スナップショットから採り、flush を挟まずに同じ巡で全部の指令を積む**。後から適用される側の `insert_after` が、先行適用によって陳腐化する。実測ログの並びで説明すると——

- 起動直後の重なりは 手前から `balloon0, char1, char0`（`balloon1` は更に背後）
- scope 0 の指令: 「`balloon0` を `char0` のすぐ手前へ」＝ `insert_after=char1`
- scope 1 の指令: 「`balloon1` を `char1` のすぐ手前へ」＝ `insert_after=balloon0`
- 両方を同じ flush で適用すると `char1, balloon0, balloon1, char0` になり、**`balloon0` と `char0` の間に `balloon1` が割り込む**

**設計の穴**: design「System Flows > 維持系の判断と適用」の収束の議論（エコー遮断＋同値ガードの二重の停止条件）は**単一ペアしか論じていない**。1 巡内の複数ペア間で観測が陳腐化することを覆っていない。design 側の補筆も要る。

**要件 3.2／3.4 には抵触しない**（動いたのは自スコープの窓 1 枚のみで、scope 0 のペアの相対順も保たれている）。壊れたのは要件 1.1 の「すぐ手前」の隣接だけである。

**タスク 4 での誤読リスク（重要）**: ゲート G6 の判定基準は「**キャラ窓クリック後**の隣接実測」であって起動時の記録ではない。起動時の `verify-failed` を「owner による隣接保証の不成立」と読んで案 B へ倒すと、design と 5.7 に従って owner 機構が丸ごと撤去される。同じログの `fix entity=4v0 … measured_next_after_fix=<char1>` が、**owner 機構自体は真正面の隣接を作れている**ことを示している。

**`owner-detached` が 1 本も出ないこと**は別件で、既知（下の 2.3 の項）。終了時は 4 窓が 1 バッチで despawn するため標準機構では検知できない——G8 の判定対象であり、是正は 5.2 の担当。

- (1.1) `GetWindow` の対応は **`GW_HWNDPREV` = 1 つ手前（前面側）／`GW_HWNDNEXT` = 1 つ背後**。独立オラクル（`GetTopWindow`）で実測確認済み。以降の判断・適用でこの向きを取り違えると不変条件が丸ごと反転する。
- (1.1) `SetWindowPos` の `hWndInsertAfter` は、指定窓の**背後**へ対象を置く（手前ではない）。テスト下拵えでも実装でも取り違えやすい。
- (1.1) `windows` 0.62 の `GetWindow` は「隣が無い」場合も `Err` を返す。`SetLastError(ERROR_SUCCESS)` で先にクリアし `err.code() == S_OK` を「不在＝`Ok(None)`」へ写像して失敗と切り分けている。

- (1.2) `ExpectedOrder` は design.md の State ブロックが型として参照するだけで定義していないため実装側で補完した（`above`／`below` の 2 HWND・座標フィールド無し）。`ZOrderPairStrategy` にも `Default`（案 A・raise assist 無効）を足している——**`init_resource` で暗黙に案 A が入りうるため、areka main 側では必ず明示 `insert_resource` で選択結果を入れること**（タスク 3.2／5.1 の前提）。
- (3.1) **2 段 grep の結合キーは `Entity` の `{:?}`**。areka の `declared`（`char_entity=`／`balloon_entity=`）と wintf 側 6 種（`entity=`／`peer=`）が同じフォーマット指定子で、bevy 0.18 の `Entity: Debug` は `Display` へ委譲するので `1v0` 形式（`Entity(...)` の包みは付かない）。両側が独立に自分の書式をテストで固定する形で、跨いで固定するテストは構造上作れない（wintf の `*_line` は private）。**どちらかの entity 表現を変えるなら両側を同時に見ること。**

- (1.3) 案 A・raise_assist=false では z 変化検知そのものを結線しないため、`RaisedAbove`／`RaisedBelow` とも供給者が居ない（両方 `StrategyDisabled`）。design.md「Testing Strategy > Unit Tests」1 が `RaisedBelow` しか挙げていなかったのは記述漏れで、本タスクで design 側を訂正済み。
- (1.3) 隣接の同値ガードは正準判定（`measured_below_of_above == below`）に加え逆向き実測（`measured_above_of_below == above`）でも止める。線形な兄弟列では整合入力で到達不能な防御であり、**要件 1.4 の反転隣接（キャラがバルーンの手前）は掛からない**ことを検算済み。ただし実測 2 値が引き裂かれた不整合スナップショットが真の隣接と同じ `AlreadyAdjacent` に畳まれる——1.4 で不整合を別レコードとして識別したいなら、`zorder_pair.rs` の隣接判定がその唯一の分岐点。
- (1.2) HWND を内包する `ExpectedOrder`／`OwnerLink` には手動 `unsafe impl Send + Sync` が**必須**（windows 0.62 は HWND に Send/Sync を実装せず、bevy の `Component` は Send+Sync を要求する）。一方 `ReassertZOrder` 自身には不要（`Option<ExpectedOrder>` 経由で自動導出）。冗長な `unsafe` を足さないこと。テスト側の `assert_send_sync::<T>()` がこの落ちを型検査で拾う。
- (1.1) **検証時は `target/` の成果物キャッシュを疑うこと**。古い成果物が fresh と誤判定され、健全なソースに対して決定論的な赤が 8 回連続再現した事例あり。疑わしいときは対象ファイルへ touch するか `cargo clean -p wintf` から測り直す。
