## Implementation Notes

- 1.2: help の `command` は渡されたパスを `to_string_lossy` でそのまま載せる。1.3 で渡す `exe_location()` の結果が `\\?\` で始まる形にならないことを、受け口のテストか実機で 1 度見る（そのまま設定例に載るため）。
- 1.3: `exe_location`（`boot_config.rs`）はリンクの先が `\?\` のとき起動した exe のパスへ戻すので、help の `command` に `\?\` が載るのは areka 自体を `\?\C:\…` の綴りで起こしたときだけ（補助 exe・記憶の置き場と同じ綴り＝D-14 のとおり・手当てなし）。実機確認（7）で help の `command` の綴りを一緒に見る。
- 1.3: この木は CRLF。`cargo fmt --all` が書き直したファイルは LF になるので、整形をかけたら行末を見直す（`git ls-files --eol`）。
- 2.1: 新しい外部のクレート 0 個の記録＝`Cargo.lock` の名前 273 → 274（増えたのは `areka-mcp-bridge` だけ）・`cargo tree`（全ターゲット）の名前 120 個のうち前の `Cargo.lock` に無いのも自身だけ・`Cargo.lock` の差は新しい塊 18 行。cargo は `Cargo.lock` を LF で書き直すので、動かしたら CRLF へ戻す。
- 2.1: `tokio-util` は直接の依存にしない。`serve_directly`（3 引数）か `serve_directly_with_ct(.., Default::default())` で `CancellationToken` の名前を書かずに呼べる。待つ口は `RunningService::waiting()`。
- 2.1: `serde` は直接の依存に無い。控えは呼び手で `serde_json::to_vec`／`from_slice` を rmcp の型に直に使う（総称の補助関数は書かない）。本番の `tokio::select!` は rmcp が `macros` を有効にしているので建つが、`futures` か `timeout` で書くほうが設計の機能の並びに素直。
- 2.1: 偽の受け口は `lib.rs`（`cfg(test)`）と `tests/exe_test.rs` の両方から `#[path]` で読む。中の項目は `pub`、中継の項目を `crate::` で引かない（根が違う）。`real_receiver_test.rs` に要るなら 5.1 が自分のファイルに 1 行足す。`errors` のテストは 2.2 が `errors_tests.rs` と `errors.rs` 末尾の宣言を足す。
- 2.2: 行の形のエラー（`-32700`・`-32600`）は要件 1.6・1.7 のとおり `"id": null`。rmcp 3.5.0 の `JsonRpcError` は `id` の欄を省くことしかできないので、`errors::parse_error`／`invalid_request` は `serde_json::Value` を返し、輸送（3.1）が `serde_json::to_vec`＋`\n` で自分で書く（設計の署名を要件に合わせて直した）。文は JSON-RPC 2.0 の綴り `Parse error`・`Invalid Request`。
- 2.2: `LOCALAPPDATA` は絶対パスのときだけ使う（空・相対は「取れない」＝起こされた場所の下へ黙って書かない）。`AREKA_PROFILE_DIR` の空は areka 本体と同じく「設定あり」。
- 2.2: SSE の応答の文は `Invalid JSON response from server: HTTP <状態> content-type text/event-stream`（3.4 は `NotJson.head` に `content-type text/event-stream` を入れ、本文は読まない。D-16 を直した）。ほかの `head` は本文の頭 256 バイトを `from_utf8_lossy` でそのまま（絞らない）。D-9 の候補と名乗りの整形は 4.3 の仕事。
- 2.3: 偽の受け口（`tests/common/fake_server.rs`）は自分のスレッドと自分の tokio で回る。テストは `current_thread` の `#[tokio::test]` のままでよく、子プロセスを同期で待つ間も答える。届いたこと・閉じたことは `wait(|log| …)` で待ってから数える（`connections()` を直に見ると早すぎる）。「1 バイトも届かない」は `Conn { bytes: 0, closed: true }`。
- 2.3: rmcp のクライアント（`ClientConfig::default()`）は `initialize` に `2026-07-28` を載せ、本物の受け口も偽の受け口も `2025-11-25` で答える（旧式の作法のまま進む）。偽が版をそのまま返すと rmcp は黙って `initialize` なしの版の作法へ切り替わり、全要求の `_meta` が変わるので、偽の既定の答えは本物と同じ版の決まりにしてある。
- 2.3: `Reply::Text(状態, 文)` で 200 以外の平文を作れる。`rescript` の前に `wait` で「その要求が記録に載った」を待てば、答えている途中の要求は元の台本で答える（4.5 の長い要求の土台）。既定の `initialize` の結果を `Delayed`／`Chunked` で包む口は無い（要るテストは結果の JSON を `SERVER_NAME` と `2025-11-25` で自分で書く）。確かめの `initialize` と rmcp の手順の `initialize` は `Received.body` の `clientInfo` か `notifications/initialized` の数で見分ける。
- 3.1: rmcp の `serve_inner` は `transport.receive()` を `tokio::select!` で回して捨てては呼び直す。輸送は読みかけの行を持ち越し、行の形のエラーの行は別の仕事で書いて次の読みの前に待つ（設計の LineTransport に追記）。
- 3.1: `id` の形が違う要求（`"id":{}`・`1.5`・`null`）は rmcp 3.5.0 の型では通知として読まれ、中継は通知として届けて標準出力に何も出さない。本物の受け口へ直接 POST しても 202・本文なしなので要件 1.2 と合う（6.2 の差の記録に 1 行載せる）。形の違う `params` の `tools/call` は `CustomRequest` として通るので、直接との一致は 4.2 の届け方と 5.1 の比較で確かめる。
- 3.1: `close` は書き手の鍵を待つ。相手が標準入力だけ閉じて標準出力を読まないと rmcp の 5 秒の後も `close` が戻らないので、4.6 の入口で終了の作法を決めるときに頭に置く。
- 3.2: 控えの書きは全部同期の `std::fs`（`.await` なし）。一時の名前は `<名前>.<pid>.tmp` なので、同じプロセスの中で 2 つが同時に書くと混ざりうる。`main`（4.6）は `current_thread` のまま、`service_tests.rs`（4.x）は `multi_thread` で書かない・`spawn_blocking` から控えを書かない。
- 3.2: 控えが無い（初回）は記録なしで `None`、読めない・書けないときだけ `warn!`。この `warn!` を判定するテストは無い（設計が `log-capture-kit` を使わないと決めている）。5.2 の「記録は標準エラーに出る」で、壊れた控えを置いて起こした exe の標準エラーに理由が出ることを 1 つ見る。
- 3.3: D-4 の根拠（本物の受け口が 1 本の接続で 2 要求に答え、`Connection: close` の後に閉じる）は `http_tests.rs` の `real_receiver_answers_two_requests_on_one_connection_then_closes` で固定した（初回から緑）。
- 3.3: `verify` の約束＝読めた名乗りは areka でもそうでなくても `Ok(name)`（`SERVER_NAME` との比較は呼び手）・名乗りを読めない相手（HTTP でない・JSON でない・途中で切れた・202／SSE）は `Err(NotAreka{name: ""})`・黙る相手は `Err(VerifyTimeout)`。読めなかった理由は送り手の `debug!` にしか出ないので、番号ごとの理由の `info`（要件 2.3）は 4.1 が残す。名乗りが空の相手を `others` と D-9 の文にどう出すかは 4.1／4.3 で決める。
- 3.3: rmcp の失敗から送り手の失敗へ戻す道は 2 つとも通る（レビューの試しで確認）: 要求の失敗は `ServiceError::TransportSend` の `error` を、`serve_client` の失敗は `ClientInitializeError::TransportError { error }` の `error` を `downcast_ref::<StreamableHttpError<HttpError>>()` → `Client(e)`。この机では止めた受け口への接続は断りでなく `Connect(TimedOut)`（上限 300 ms）。rmcp が要求を時間切れで取り消すと送り手の未来が落ちて接続も閉じる。
- 3.3: rmcp の型は `params` の無い `tools/list` を `"params": {}` 付きで書き出す（意味は同じ・5.1 の比較と 6.2 の差の記録で頭に置く）。本文そのものが `initialize` のときの往復も上限 `verify` で見切る。204 は「受け取った」にしない（設計は 202 だけ）。
- 3.4: 送り手の失敗の読み分けは `http_tests.rs` の節「失敗の読み分け」で固定した（変異 22 本が赤・`http.rs` は 3.3 のまま）。偽の受け口の `hold`（`Reply::Never`／`EventStream` の後）は、黙っている間に届いたバイトも `Conn.bytes` に数える（4.1 の「1 バイトも届かない」はこの数に頼れる）。
- 3.4: この机では、誰も待ち受けていない番号への接続は約 2 秒後の断りより先に上限 300 ms が切れて `Connect(TimedOut)` になる。その場で失敗する枝は番号 0（10049）で固定した。「誰も居ない番号」が要るテストは、止めた受け口の番号でなく、束ねたまま待ち受けない `TcpSocket` の番号を使う（並んで走るテストに番号を取り直されない）。
- 3.4: 全体テストの負荷で偽の受け口のスレッドが 3 秒動けないと、既定の `verify` のまま `NotAreka` を待つテストが `VerifyTimeout` で赤になりうる（出たらここを疑う）。
