# Requirements Document

## Project Description (Input)

- **だれが困っているか**: areka の利用者。起動の直後に、キャラクターの窓が画面（作業領域＝タスクバーなどを除いた矩形）からはみ出したり、隣のモニタへ渡ったりする。ぱすた（「窓際のぱすたさん」）の実機の走りで見えた。
- **今の状況**:
  - 件 1: 起動の並べ直し（記憶に位置の無い相方を本体の隣へ並べる）は隣に詰めた位置を返すだけで作業領域を見ない。実機で相方が x=−1108 へ置かれ、左隣の 150% のモニタへ渡った。拡大率が変わったあとの詰め直しも同じく作業領域を見ない。
  - 件 2: 吸着の無い（`seriko.alignmenttodesktop,free`）窓が起動のトークで大きい面へ切り替わると、左上を保って下へ伸び、作業領域の下へはみ出す（ぱすた・200%: 下端 2232、作業領域の下端 1704）。
  - 件 3: 記憶から戻した位置を作業領域へ寄せる今の規則は窓ごとに別々に寄せるので、組の 2 つの窓が離れるかもしれない（確かめていない）。
  - 件 4: バルーンだけが作業領域へ寄せられ、シェルとの組がずれて、ぱすたの縦書きのバルーンの 1 列目にシェルの「×」と横線がかぶる（SSP では起きない）。
  - 件 5: 初回起動のトークの最中にぱすたの窓あわせ（見た目の調整）が効かず、トークの後にずれる（SSP では起きない）。
- **何を変えるか**: 起動の並べ直し・拡大率の後の詰め直し・起動の表示・記憶からの戻しで、キャラクターの窓を作業領域の中に収める。組の窓を寄せても組を離さない。シェルとバルーンの組を崩さない。初回起動のトークの最中から窓あわせの結果の並びで見せる。寄せ方のうち正典が黙る点は SSP で測ってから決め、決定論のテストと実機で確かめる。

出どころは `brief.md`（2026-10-23 起票・2026-10-24 の件 4・件 5 の追記と開発者の裁定・棚卸㉚の再測定を含む。後の節が前の節を上書きする）。区分は **B（バグ）**、版は v0.1.0（ゴール「ゴースト『窓際のぱすたさん』が SSP と同じに動く」）。

## Introduction

正典（ukadoc）は、起動のときに窓を作業領域の中へ寄せるかどうかを書いていない。SSP のヘルプは、初回の起動の時点で位置がおかしい場合はゴーストの作者にかけあうよう書いており、SSP がいつも寄せるわけではない見込みである。そこで brief は「寄せ方は SSP で測ってから決める（測る前に areka の独自の決まりを作らない）」とした。

ただし 2026-10-24 に開発者が件 2 について裁定した: **「起動の表示位置は画面（作業領域）の中に収まっていればよく、SSP と同じ規則である必要はない」**。件 2 は SSP の測りを待たずに、収める規則を areka で決めてよい（測るのは任意）。

この spec は、どの件でも動かない結果（作業領域の外へ置かない・組を離さない・× を 1 列目にかけない・トークの後にずらさない）を必須の要件として先に決め、SSP の振る舞いで細部が変わる点（並びの順を保つか・組をどう寄せるか・バルーンをどう扱うか・ずれの原因）は「測ってから決める」義務として書き、具体の規則は要件の話し合いの議題に残す。

### 件ごとの決め方の段

| 件 | 必須の結果（この要件で決める） | 測ってから決める点 |
| ---- | ---- | ---- |
| 件 1（起動の並べ直し） | 並べ直した窓を、並べる基準の窓（2 体では本体）が属するモニタの作業領域の中に置く（隣のモニタへ渡さない） | 寄せるときに並びの順（本体の隣に相方・左右の側）を保つか（SSP の測り ⑴） |
| 件 1 の足し（拡大率の後の詰め直し・記憶からの隣り合わせ） | 件 1 と同じ寄せを当てる（`dpi-realign-remembered-chain` からの申し送り） | 件 1 と同じ |
| 件 2（`free` の窓の面の拡大） | 起動の表示の間は作業領域の中に収める（開発者の裁定） | 起動の表示を過ぎた後に面が大きくなってはみ出すときの扱い（議題・SSP の測り ⑵ は任意） |
| 件 3（記憶からの組の戻し） | 寄せても組を離さない | 組の寄せ方の細部（SSP の測り ⑶）・古い記憶に書き足す隣り合いの印をどの矩形から決めるか |
| 件 4（バルーンだけの寄せ） | ぱすたの縦書きのバルーンの 1 列目に × と横線がかからない | 件 2 の直しの後にも残るか・残るなら SSP の扱い（SSP の測り ⑷） |
| 件 5（初回起動のトークの窓あわせ） | 初回起動のトークの最中から窓あわせの結果の並びで見せ、トークの後にずらさない | ずれの原因（SSP の測り ⑸）・原因が起動のイベントの順なら切り出すか |

### 要件の話し合いへ持ち越す議題

この要件を書いた時点では SSP をまだ測っていない。次の点は測りの結果か開発者の判断で決まるので、要件の話し合いの議題とする（決まったら該当の要件の文へ規則を書き込む）。

1. **件 1: 寄せるときに並びの順を保つか**。候補は「組をまとめて内側へずらし、本体の隣に相方の並びを保つ」「相方を本体の反対の側へ並べ替える」「窓ごとに作業領域の端へ寄せる（重なりうる）」。SSP の測り ⑴（2 人並べると本体の隣が作業領域の外になるとき、SSP はどのモニタのどこへ置くか）で決める。
2. **件 2: 起動の表示を過ぎた後に `free` の窓が大きい面へ切り替わってはみ出すときの扱い**。候補は「寄せない（今の決まり＝左上を保つ）」「いつも寄せる」。推奨は「寄せない」（開発者の裁定は起動の表示位置についてであり、表情の差し替えでキャラクターが勝手に動かない約束〔`areka-P0-scope-chain-gap` 要件 7.4〕とも当たらない）。SSP の測り ⑵ は任意。
3. **件 3: 組の寄せ方の細部**。候補は「組をまとめて同じだけ動かす」「片方を寄せてもう片方をその隣へ付け直す」。SSP の測り ⑶（記憶の位置が作業領域の外にあるとき、SSP は寄せるか・組の 2 つをどう寄せるか）で決める。
4. **件 3 の足し: 古い記憶に書き足す隣り合いの印を、どの矩形から決めるか**。`dpi-realign-remembered-chain` は、印の無い古い記憶へ隣り合いの印を表示した矩形から書き足す。記憶の位置を寄せて表示した起動では、表示の矩形と記憶の位置が食い違う。候補は「表示した矩形から」「記憶の位置の矩形から」「寄せた起動では書き足さない（寄せずに起動した回に書き足す）」。推奨は「寄せた起動では書き足さない」（記憶の位置と印が食い違わない）。
5. **件 4: 件 2 の直しの後にもバルーンだけが寄せられる場面が残るか、残るなら SSP の扱いに合わせる形**。`descript-window-keys`（起動の測りを descript の既定の面にした・10-24 着地）を取り込んだ版で測り直してから決める。
6. **件 5: ずれの原因と持ち場**。原因が起動の配置（件 2 と同じ所）ならこの spec で直す。起動のイベントを送る順や時機（kanade の持ち物）なら、この spec で直すか別の spec へ切り出すかを決める。
7. **利用者がドラッグで作業領域の外へ置いた窓**。この spec では勝手に戻さない（要件 7.6）とした。確認だけの議題。

## Boundary Context

- **In scope**:
  - 起動の最後の並べ直しで置いた窓を作業領域の中に収めること（件 1）。
  - 拡大率が変わったあとの詰め直しで動かした窓と、記憶から戻すときに隣り合わせた窓に、件 1 と同じ寄せを当てること（`dpi-realign-remembered-chain` の要件の「作業領域への寄せ」の節からの申し送り）。
  - 起動の表示の間に `free` の窓が大きい面へ切り替わっても作業領域の中に収めること（件 2）。
  - 記憶から組の窓を戻して寄せるとき、組を離さないこと（件 3）と、古い記憶に書き足す隣り合いの印の決め方。
  - バルーンだけが寄せられてシェルとの組がずれる件（件 4）。
  - 初回起動のトークの最中の窓あわせのずれ（件 5）の原因の測りと、持ち場がこの spec の内なら直し。
  - SSP での測り（⑴〜⑸）・寄せ方の決め・記録（ログ）・`doc/COMPAT_ARCHITECTURE.md` §8 の行・決定論のテスト・実機の確かめ。
- **Out of scope**:
  - 起動の測りの面を descript の既定の面にすること（`descript-window-keys`・10-24 着地済み）。この spec はその後の版の上で測り直す。
  - `seriko.alignmenttodesktop` の `top`／`left`／`right` の起動の位置と、作業領域が変わったときの沿わせ直し（`window-snap` の件 1）。
  - 拡大率が変わったあとの詰め直しの対象の決め方そのもの（`dpi-realign-remembered-chain`・完了）。この spec は詰め直した後の位置に寄せを当てるだけ。
  - 表情の差し替えで絵の大きさが変わったときにキャラクターが横へ動かない約束（`areka-P0-scope-chain-gap` 要件 7.4・`areka-P0-dpi-transition-atomicity` 要件 6.6）。変えない。
  - 利用者がドラッグで作業領域の外へ置いた窓を勝手に戻すこと（要件 7.6）。
  - ゴーストが台本（`\![move]` など）で置いた窓の位置を寄せること（要件 1.4）。
  - バルーンを動かせない指定（`descript-window-keys` が足した所）。
  - ゴーストを複数同時に動かすこと（`multi-ghost-runtime`）・3 体目以降のキャラクター窓を出すこと（`extra-character-windows`）。この spec の決めはキャラクターの数を 2 体に決め打ちしない。
- **Adjacent expectations**:
  - 記憶から戻した位置を作業領域へ寄せるかどうかの今の判定（`areka-P0-position-persist` 要件 5＝作業領域とまったく交わらない窓だけを寄せ、寄せた位置を記憶に書き戻さない）は保つ。この spec はその判定で寄せる窓が組に入っているときの寄せ方だけを足す。
  - 窓の組の相手が連れ動くのはドラッグと瞬間の `\![move]` だけで、吸着の当て直し・大きさの変化・作業領域の変化では相手を動かさない今の決まり（`areka-P0-window-link-directives`・§8 の行）は保つ。
  - バルーンは今までどおりキャラクター窓に付いて動く（寄せで窓が動けばバルーンも同じだけ動く）。バルーンを作業領域の中に収める今の決まり（`areka-P0-windowposition-limit`）は、件 4 の測りで変える必要が出たときだけ改め、改めた事実を §8 に残す。
  - `dpi-realign-remembered-chain`（完了）は「詰め直した位置は寄せない。寄せる働きは `window-work-area-clamp` が作り、詰め直しの位置にも同じ寄せを当てる」と決めている。この spec はその申し送りを受け取る。
  - 着地の後の通しの確かめは、ぱすたの手順書 `doc/pasta-real-run.md` で回す（`pasta-in-windows-verification` は 10-23 に着地済み）。

## Requirements

### Requirement 1: 起動の並べ直しで置いた窓を作業領域の中に置く（件 1）

**Objective:** As an areka の利用者, I want 起動の直後に相方の窓が画面の外や隣のモニタへ置かれないこと, so that 起動したあとに窓を探して手で戻さずに済む

#### Acceptance Criteria

1. When 起動の最後の並べ直しで、記憶に位置の無いキャラクター窓を並べる基準の窓（隣へ並べる元の窓。2 体では本体）の隣へ並べた位置が、基準の窓が属するモニタの作業領域からはみ出すとき, the areka shall その窓を基準の窓が属するモニタの作業領域の中に収めて置き、隣のモニタへ渡さない。
2. When 要件 1.1 で窓を収めるとき, the areka shall 並びの順（本体の隣に相方・左右の側）を、SSP の測り ⑴（要件 8.1）の結果で決めた規則に従って扱う（規則は要件の話し合いの議題 1 で確定し、この文へ書き込む）。
3. If 並べ直した位置が基準の窓が属するモニタの作業領域の中に収まっているとき, the areka shall 並べ直しの位置を変えない。
4. If ゴーストが台本（`\![move]` など）で置いた窓であるとき, the areka shall その窓を並べ直しの寄せで動かさない（台本で置いた窓が並べ直しから外れる今の決まりを保つ）。

### Requirement 2: 拡大率の後の詰め直しと記憶からの隣り合わせにも同じ寄せを当てる

**Objective:** As an areka の利用者, I want 拡大率を変えたあとや起動し直したあとに隣り合わせ直された窓も、画面の外へ出ないこと, so that 拡大率の違う画面を使っていても窓を見失わない

#### Acceptance Criteria

1. When 拡大率が変わったあとの詰め直しで動かした窓が、組の動かさない側の窓が属するモニタの作業領域からはみ出すとき, the areka shall 要件 1 と同じ規則でその窓を作業領域の中に収める。
2. When 起動・読み直し・切り替えで記憶から戻し、覚えたときに隣り合っていた組を今の絵の幅で隣り合わせた位置が、組の動かさない側の窓が属するモニタの作業領域からはみ出すとき, the areka shall 要件 1 と同じ規則でその窓を作業領域の中に収める。
3. If 詰め直しや隣り合わせで動かさなかった窓（離れていた組・重なっていた組・一緒に動く組の窓・台本で置き直した窓・ドラッグの最中の窓）であるとき, the areka shall その窓をこの要件の寄せで動かさない。
4. The areka shall 要件 2.1・2.2 で寄せた位置を記憶に書かない（詰め直した位置・隣り合わせた位置を記憶に書かない今の決まりを保つ）。

### Requirement 3: 起動の表示の間に大きい面へ切り替わった `free` の窓を作業領域の中に収める（件 2）

**Objective:** As an areka の利用者, I want ゴーストを起動したとき、起動のトークで面が切り替わってもキャラクターが画面の中に収まっていること, so that 起動の直後から全身が見える

> 開発者の裁定（2026-10-24）: 「起動の表示位置は画面（作業領域）の中に収まっていればよく、SSP と同じ規則である必要はない」。

#### Acceptance Criteria

1. While 起動・読み直し・切り替えでキャラクター窓を既定の位置（記憶から戻していない位置）に置いてから、その起動のイベントの台本（`OnBoot`・`OnFirstBoot` など）を流し終えるまでの間, when 吸着の無い（`free`）窓が大きい面へ切り替わって作業領域からはみ出すとき, the areka shall その窓を、その窓が属するモニタの作業領域の中に収める。
2. When 要件 3.1 で窓を収めるとき, the areka shall はみ出した向きにだけ、はみ出した分だけ動かし、はみ出していない向きには動かさない。
3. When ゴーストの台本が、要件 3.1 で収めた窓を基準にほかの窓を置く（例: `\![move,--base=0,…]` で相方を本体の左上へ寄せる）とき, the areka shall 収めた後の位置を基準にして置く。
4. The areka shall 要件 3.1 で窓を収めるときに、組の並べ直しをやり直さない（相方は台本や連れ動きで置かれる分だけ動く・`areka-P0-scope-chain-gap` 要件 7.4 を保つ）。
5. The areka shall 起動の表示を過ぎた後に `free` の窓が大きい面へ切り替わってはみ出すときの扱いを、要件の話し合いの議題 2 で決め、決めた扱いで置く（決まるまでは今の決まり＝左上を保つ）。

### Requirement 4: 記憶から組の窓を戻して寄せても組を離さない（件 3）

**Objective:** As an areka の利用者, I want モニタの構成が変わって記憶の位置が画面の外になっても、本体と相方が離ればなれにならずに画面へ戻ること, so that 組で使っていた並びのまま使い続けられる

#### Acceptance Criteria

1. When 起動・読み直し・切り替えで記憶から戻した窓が今の判定（`areka-P0-position-persist` 要件 5）で作業領域へ寄せられ、その窓が覚えたときに隣り合っていた組・重なっていた組・一緒に動く組（`\![set,sticky-window,…]` で組にした窓）の窓であるとき, the areka shall 寄せた後も組を離さない（隣り合っていた組は隣り合ったまま、重なっていた組・一緒に動く組は覚えたときの互いの位置のまま）。
2. When 要件 4.1 で組を寄せるとき, the areka shall 組の寄せ方の細部（組をまとめて動かすか・片方を寄せてもう片方を付け直すか）を、SSP の測り ⑶（要件 8.1）の結果で決めた規則に従って扱う（規則は要件の話し合いの議題 3 で確定し、この文へ書き込む）。
3. If 記憶から戻した組の窓がどれも作業領域と交わっている（一部でも見えている）とき, the areka shall 組のどの窓も寄せず、記憶の位置のまま置く。
4. If 記憶の組が覚えたときに離れていた（隣り合わず・重ならず・一緒に動く組でもない）とき, the areka shall 窓ごとに今の判定で寄せる（今の振る舞いを保つ）。
5. The areka shall 要件 4.1 で寄せた位置を記憶に書き戻さず、記憶の位置（利用者が最後に決めた位置）を保つ（`areka-P0-position-persist` 要件 5.4 を保つ）。
6. When 記憶の位置を寄せて表示した起動で、隣り合いの印の無い古い記憶へ印を書き足すとき, the areka shall 要件の話し合いの議題 4 で決めた矩形から印を決め（または書き足さず）、どの矩形から決めたかを記録（ログ）に残す。

### Requirement 5: バルーンだけを寄せてシェルとの組をずらさない（件 4）

**Objective:** As a ぱすたの利用者, I want 縦書きのバルーンの 1 列目にシェルの「×」と横線がかからないこと, so that SSP と同じに、最初の字から読める

#### Acceptance Criteria

1. The areka shall ぱすたを拡大率 200% の画面で記憶の空の状態から起動したとき、縦書きのバルーンの 1 列目にシェルの × と横線がかからないようにする（SSP の同じ台本の表示と同じ）。
2. The 開発者の机での測り shall 要件 3 の直しを取り込んだ版で、ぱすたの起動のバルーンが作業領域へ寄せられてシェルとの相対の位置が崩れるかを測り直し、結果を記録に残す。
3. If 測り直しの後もバルーンだけが作業領域へ寄せられてシェルとの相対の位置が崩れる場面が残るとき, the areka shall SSP の測り ⑷（要件 8.1）で SSP の扱い（バルーンを寄せるか・寄せるならシェルも一緒に動かすか）を確かめ、その扱いに合わせる（規則は要件の話し合いの議題 5 で確定する）。
4. If 要件 3 の直しでバルーンが寄せられなくなり、要件 5.1 が満たされるとき, the areka shall バルーンを作業領域の中に収める今の決まり（`areka-P0-windowposition-limit`）を変えない。

### Requirement 6: 初回起動のトークの最中から窓あわせの結果で見せる（件 5）

**Objective:** As a ぱすたの利用者, I want 初回起動のトークの最中から、ぱすたと窓の枠が SSP と同じ並びで見えること, so that トークが終わってから見た目がずれて驚かずに済む

#### Acceptance Criteria

1. The 開発者の机での測り shall 記憶の空のぱすたを初回起動したとき、SSP が SHIORI へ送る要求の並びと時機（`ghost\master\ssp_shiori_log.txt` の差分）と areka が送る要求の並びと時機を比べ、窓あわせ（窓を動かす・重なりの順を決める・組にする指令）がどのイベントのどの指令で流れるかと、ずれの原因を記録に残す（SSP の測り ⑸）。
2. When 初回起動のトークの台本で窓あわせの指令が流れたとき, the areka shall トークの最中から窓あわせの結果の並びで表示し、トークが終わった後に並びをずらさない（SSP と同じ）。
3. When 2 回目以降の起動のトークで窓あわせの指令が流れたとき, the areka shall 要件 6.2 と同じに、トークの最中から窓あわせの結果の並びで表示する。

> 原因が起動のイベントを送る順や時機（kanade の持ち物）にあると分かったときは、この spec で直すか別の spec へ切り出すかを要件の話し合いの議題 6 で決め、決めた結果を `brief.md` と `roadmap.md` に残す。

### Requirement 7: 寄せの共通の決まり

**Objective:** As an areka の利用者, I want 窓を作業領域へ寄せる働きが、どこで寄せても同じ決まりで動くこと, so that 寄せた窓がちらついたり、寄せた位置が記憶を狂わせたりしない

#### Acceptance Criteria

1. The areka shall 窓が属するモニタの決め方を今の決まり（窓の中心で決め、どのモニタにもいなければ一番近いモニタ）のまま使い、作業領域はそのモニタのタスクバーなどを除いた矩形とする。
2. If 窓が作業領域より大きく、両端を同時に収められないとき, the areka shall 左辺・上辺を優先して収める（キャラクター窓とバルーンを収める今の式と同じ）。
3. The areka shall 寄せた位置を窓を置くその時点で決め、作業領域の外の位置で一度表示してから次の時点で寄せ直すこと（1 フレーム遅らせる形）をしない。
4. If 窓が属するモニタの作業領域を取り出せないとき, the areka shall 窓を寄せずに置き、寄せなかったことと理由を記録（ログ）に残す（ありもしない作業領域を作らない）。
5. When 起動の最後に並べ終えた時点で、記憶に位置の無いキャラクター窓の位置を記憶に書くとき, the areka shall 要件 1・要件 3 で寄せた後の表示の位置を書く（はみ出した位置を書くと、次の起動でも記憶の位置からはみ出して立つため）。
6. If 寄せの対象が、利用者がドラッグしている最中の窓か、利用者がドラッグで置いた位置（記憶から戻したドラッグの位置を含む）にある窓であるとき, the areka shall この spec の寄せでその窓を動かさない（記憶から戻すときの今の判定・要件 2.2 の記憶からの隣り合わせ・要件 4 を除く）。
7. When この spec の寄せでキャラクター窓が動いたとき, the areka shall その窓のバルーンを今までどおり窓に付いて同じだけ動かす。

### Requirement 8: SSP での測りと、決めた寄せ方の記録

**Objective:** As a 開発者, I want 寄せ方のうち正典が黙る点を SSP で測ってから決め、決めた理由と出どころが開発の記録に残ること, so that 後から「なぜこの寄せ方か」を確かめられ、測る前に areka の独自の決まりを作らずに済む

#### Acceptance Criteria

1. The 開発者の机での測り shall 開発者の機械の SSP（SSP の MCP・`ghost\master\ssp_shiori_log.txt`）で次を測り、手順・測った版・結果を spec の記録に残す: ⑴ 2 人並べると本体の隣が作業領域の外になるとき、SSP はどのモニタのどこへ置くか（並びの順を保つか） ⑶ 記憶の位置が作業領域の外にあるとき、SSP は寄せるか、組の 2 つをどう寄せるか ⑷ 要件 5.3 の場面で、SSP はバルーンを作業領域へ寄せるか、寄せるならシェルも一緒に動かすか ⑸ 要件 6.1 の要求の並びと時機。⑵（`free` の窓が大きい面へ切り替わってはみ出すとき SSP は寄せるか）は任意とする。
2. If SSP の振る舞いが、この spec の必須の結果（要件 1.1・2.1・2.2・3.1・4.1・5.1・6.2）と食い違うとき, the areka shall 必須の結果を保ち、SSP との違いとその理由を互換の記録に残す。
3. The areka shall 決めた寄せ方（件 1〜件 5 のそれぞれ）を、正典が黙る点・SSP の測りの結果・areka の決め・出どころの spec と要件の番号とともに、`doc/COMPAT_ARCHITECTURE.md` §8 の行として残す。
4. If この spec の決めが完了 spec の要件を改めるとき（例: 件 4 でバルーンを収める今の決まりを改める）, the areka shall 改めた事実と理由を `doc/COMPAT_ARCHITECTURE.md` §8 の、完了 spec の要件を改めた記録として残す（アーカイブ済みの spec の本文は書き換えない）。

### Requirement 9: 寄せの判断の記録（ログ）

**Objective:** As a 開発者, I want 窓を寄せたか・寄せなかったかとその理由がログに残ること, so that 「窓がはみ出した」の報告を受けたときに、寄せが走らなかったのか、走って寄せないと判断したのかをログから見分けられる

#### Acceptance Criteria

1. When この spec の寄せでキャラクター窓を動かしたとき, the areka shall どの窓を・どの場面（起動の並べ直し・拡大率の後の詰め直し・記憶からの隣り合わせ・起動の表示の面の切り替え・記憶からの組の戻し）で・どの作業領域へ・どこからどこへ動かしたかを、記録（ログ）に残す。
2. When 寄せの判定で窓を動かさなかったとき（作業領域の中に収まっていた・台本で置いた窓・ドラッグの窓・記憶の組が見えていた）, the areka shall 動かさなかったことと理由を、実機の確かめで開けられる詳しさの記録（ログ）に残す。

### Requirement 10: 受け入れの確認（決定論のテストと実機）

**Objective:** As a 受け入れを判定する人, I want この直しが決定論のテストで固定され、実機でも確かめられること, so that 窓のはみ出しが後から戻ってきたら気付ける

#### Acceptance Criteria

1. The areka shall 次の形を決定論のテストで確かめられるようにする: ⑴ 本体が主のモニタの左端の近くにいて、相方を本体の左へ並べると作業領域の外（左隣の 150% のモニタ）になる並び（実測の x=−1108 の形）→ 相方が本体の属するモニタの作業領域の中に置かれる ⑵ 拡大率の後の詰め直しと、記憶からの隣り合わせで、動かした窓が作業領域の外になる並び → 作業領域の中に収まる ⑶ 拡大率 200% で `free` の窓が y=864 に 640×840 で置かれ、起動のトークで 1108×1368 へ切り替わる（作業領域の下端 1704）→ 窓の下端が 1704 以下で、横へは動かない ⑷ 記憶の位置が作業領域の外（どのモニタとも交わらない）にある、隣り合っていた組・重なっていた組・一緒に動く組 → 寄せた後も組が離れない ⑸ 窓が作業領域より大きい → 左辺・上辺が収まる ⑹ 作業領域を取り出せない → 動かさない ⑺ 作業領域の中に収まっている並び → どの窓も動かない ⑻ 起動の最後に並べ終えた時点で記憶に書く位置が寄せた後の位置であり、寄せた記憶の位置・詰め直しの位置は記憶に書かれない。
2. The areka shall 今あるテストのうち、表情の差し替えでキャラクターが横へ動かないこと（`areka-P0-scope-chain-gap` 要件 7.4）・記憶から戻した位置の寄せと書き戻さないこと（`areka-P0-position-persist` 要件 5）・バルーンを作業領域へ収めること（`areka-P0-windowposition-limit`）を確かめるテストを保つ（要件の話し合いで改めた点は、改めた決まりに合わせて書き換える）。
3. The areka shall 要件 1.2・3.5・4.2・4.6・5.3 で決めた規則を、決まった後に決定論のテストで確かめられるようにする。
4. The 受け入れの判定 shall 実機で次を開発者の机（主の画面 2880×1800・拡大率 200%、左の画面 150%）で、排他テストの机を持って確かめることを必達とする: ⑴ 記憶の空のぱすたを初回起動すると、起動のトークの間も後も、本体と窓の枠が作業領域の中に収まり、トークの後に並びがずれず、縦書きのバルーンの 1 列目に × と横線がかからない ⑵ 窓あわせの無いゴースト（例: emo2）で、記憶の位置が作業領域の外にある組を起動すると、組が離れずに作業領域の中へ戻る ⑶ 起動の並べ直しで相方が左隣のモニタへ渡らない。実機の根・一時フォルダはワークツリーの `target\` の下だけを使う。
