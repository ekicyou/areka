# Brief: areka-P0-impl-watch

## Problem
実装を同時に何本も進めると、次の 2 つが衝突する。

- **マージ**: roadmap.md・台帳の数・生成した報告は 1 リポジトリに 1 つしかないので、同時にマージすると競合する。
- **負荷テスト**: 計測は静かな CPU が前提なので、他のセッションが cargo を回していると数字が乱れる。

いまは、調停役の Claude セッション（スキル `kiro-watch`）が、他のセッションとメッセージをやり取りして机を貸し出している。この方式には次の弱点がある。

- 他のセッションへ送れるのが、開発者の入力 1 回につき約 10 通まで（アプリの安全装置・設定では変えられない）。上限に達すると、貸し出しが止まり、開発者のひと言を待つ。選択肢への回答では数え直されないことも実測した（2026-10-09）。
- 調停役のセッションが 1 本、常に生きている必要がある。落ちる・再起動すると、待っているセッションへ「再開してよい」が届かない。
- 状態の置き場がワークツリーの `target/` なので、掃除で消える（2026-10-08 に実際に消え、参加者を並べ直した）。
- 判断は決まった手順なのに、LLM を通すので、1 件ごとに時間とトークンがかかる。

## Current State
- `.claude/skills/kiro-watch/`（SKILL.md・kiro-watch.ps1・messages.json）が、机 2 種類（マージはリポジトリごとに 1 つ、負荷テストはマシンに 1 つ）と、停止要請・再開を、PowerShell の状態機械で持っている。コマンドは join / leave / merge / merged / loadtest / loadrunning / loaddone / stopped / unstop / cancel / note / status / next。
- `kiro-impl`（参加・負荷テスト・停止要請）と `kiro-complete`（マージの机）が、Claude セッションへのメッセージ送信で調停役とやり取りする手順を持つ。
- 規則（開発者・2026-10-08）は、スクリプトが守っている。この spec はその規則を作り直さず、そのまま引き継ぐ。
  1. 机はどちらも 1 度に 1 人。
  2. 負荷テストは、ほかの参加者全員が「いまのタスクをコミットした」ところで止まってから。実行の途中では止めない。
  3. 参加を申し出たセッションだけを調停する。
  4. 負荷テストの申し込みはマージより先。負荷テストが持たれている・待たれている間は、どのリポジトリでもマージを始めない。
  5. マージの机を持っている者は、「済んだ」と言うまで止めない。
  6. リポジトリ内のマージの順は、バグ優先、次に申し込み順。負荷テストは申し込み順。
  7. すでに走っている負荷テストは、停止要請を出さずに記録だけできる（`loadrunning`）。停止要請の取り消しもできる（`unstop`）。

## Desired Outcome
コンソールアプリ `areka-impl-watch` があり、各セッションが Bash から直接呼ぶだけで机の貸し出しが回る。LLM のメッセージは 1 通も使わない。

- **待つ**は、バックグラウンドで実行するコマンドが、机が取れるまで終わらないことで表す。Bash のバックグラウンド実行は時間の上限なく待ち続け、終わると呼んだセッションが自動で起こされる。この「終わる」が、いまの「どうぞ」の代わりになる。
- **止まる**は、作業中のセッションが走らせておく見張りのコマンドが、停止要請の発生で終わることで表す。終わりがセッションを起こし、コミットの切れ目で止まる。再開は、再開を待つコマンドが終わることで表す。
- 状態はマシン共通の 1 つの JSON ファイルにあり、ワークツリーの掃除やビルドの影響を受けない。
- 調停役のセッションは要らなくなる。

## Approach
専用の小さなクレート `crates/areka-impl-watch`（bin・`publish = false`・配布の zip には入れない）として作る。

- 状態は JSON 1 ファイル。読み書きの間だけ短い排他ロック（ミリ秒）をかける。SQLite は、依存が増えるうえ扱うデータ量に対して大きすぎるので使わない。
- 机の保持（何十分も続く）は、ロックではなく JSON の「持ち主の記録」（保持者の識別とプロセス番号）で表す。持ち主のプロセスが死んでいれば、次の呼び出しが回収する。
- **実行ファイルは `%AREKA_IMPL_WATCH_HOME%\areka-impl-watch.exe` に置く**。`cargo build --release -p areka-impl-watch` で作ったものをそこへコピーし、各セッションとスキルは `%AREKA_IMPL_WATCH_HOME%\areka-impl-watch.exe` を直接呼ぶ。areka 以外のリポジトリ（pasta など）のセッションも同じ場所を呼べる。`cargo install`（`~/.cargo/bin`）にしないのは、Rust を入れ直したり `~/.cargo` を消したりしても、実行ファイルと状態が無傷で残るようにするため。ほかの理由は、待っているあいだ `target/` の中の実行ファイルが開かれたままになってビルドを邪魔すること、cargo を通る起動が静かな机の計測を乱すこと、`target/` の掃除で消えること。`cargo run` は開発中に試すときだけ使う。誰かが待機中は実行ファイルを置き換えられない（Windows）ので、更新は机が空いて見張りも止まっているときに行い、手順書に書く（更新前に `status` で待機者がいないことを確かめる）。
- **置き場所は環境変数 `AREKA_IMPL_WATCH_HOME` だけで決める**（`AREKA_` 名前空間・ドメイン語命名の決まりに沿う）。既定の場所は持たない。この変数が無い・空・指す先が作れないときは（実行ファイルを別の場所から直接呼ばれた場合に限る）、「この変数を作って（設定して）ください」という警告（ASCII の 1〜2 行）を出し、何も読み書きせずに終了コード非 0 で終わる。利用者の想定は、ユーザー環境変数に `%USERPROFILE%\.areka-impl-watch` のような場所を 1 度だけ設定すること。テストは、この変数をワークツリーの `target\` の下の一時フォルダへ向ける（実際のユーザーフォルダを触らない）。
- 設定ファイルは作らない。持つのは状態のファイル・ロック・ログだけ。リポジトリは、呼び出し側が名前（`--repo pasta` など）で渡し、登録は要らない。
- 公開（crates.io）はしない。出すのは areka の外でも使える汎用のライブラリだけ、という `tech.md` の決まりに従う。

却下した案: example にする案（持ち主になるクレートが結局要る・実行ファイルが開かれたままになる・毎回 cargo を通る）／ SQLite（過大）／ 常駐サーバー（落ちたときの回復が要る・MCP のツール呼び出しでは長い待ちが続かない）／ 調停役セッションを残す案（送信の上限が残る）。

## Scope
- **In**:
  - 置き場所の環境変数（`AREKA_IMPL_WATCH_HOME`）の解釈と、無いときの警告終了。
  - 机の取得・返却（マージはリポジトリごと、負荷テストはマシンに 1 つ）と、待ち行列（上の規則 1・3・4・6）。
  - 参加・離脱、停止要請の発生と取り消し、止まった旨の報告、再開の待ち（規則 2・5・7）。
  - すでに走っている負荷テストの記録（停止要請なし）。
  - 状態の確認（人が読める形）。
  - 持ち主のプロセスが死んでいるときの机の回収。
  - 状態ファイルが消えた・壊れたときの扱い（黙って空にしない・記録を残して回復）。
  - 入れ方・更新の手順書（ビルドして `AREKA_IMPL_WATCH_HOME` へコピー・環境変数の設定・待機中は更新できないこと）。
  - 決定論テスト（時刻を注入する）と、明示したときだけ走る実機テスト。
- **Out**: 下の「Out of Boundary」。

## Boundary Candidates
- 状態の型と、机・待ち行列・停止要請の判断（純粋なロジック。時刻とプロセスの生死を外から注入する）。
- 状態ファイルの読み書きと排他ロック（ファイル境界）。
- 待機の仕組み（取得待ち・停止の見張り・再開待ち）。
- 引数の解釈と端末への出力（コマンド境界）。
- 入れ方・更新の手順書。

## Out of Boundary
- **スキルの書き替え**（`kiro-impl`・`kiro-complete`・`kiro-watch` を、メッセージ送信からこのアプリの呼び出しへ）。アプリが動いてからの続きの spec にする。この spec が終わるまで、`kiro-watch` のスキルとスクリプトは触らず、そのまま動かし続ける。
- Claude セッションへのメッセージ送信（使わない）。
- セッション一覧の読み取り（使わない）。
- 常駐サーバー・crates.io への公開・GUI。
- 机の種類を増やすこと（マージとマシン負荷の 2 種類のまま）。
- 作業の中身の判断（いつテストするか・どの spec を先にするか）。これは開発者とスキルの仕事。
- 貸し出しの履歴の分析・集計。

## Upstream / Downstream
- **Upstream**: なし（外部サービスなし）。呼び出し元は areka と pasta など複数のリポジトリのセッション。ワークスペース（Rust・同期）、ファイルの排他ロックとプロセスの生死の確認に使う Windows の機能。
- **Downstream**: スキル 3 本の書き替え（続きの spec）。`tools/test-all.ps1`（フルテストに常時テストが入る・実機テストは入らない）。

## Existing Spec Touchpoints
- **Extends**: なし。
- **Adjacent**: `release-cycle`（`tools/` の道具と手順書の置き方）／ `test-roots-under-target`（テストの一時フォルダはワークツリーの `target\` の下だけ・`C:\` 直下や `C:\tmp` は使わない）。

## Constraints
- **設計で決める論点**（ブリーフでは決めない）:
  - 待機の方式（短い間隔で見に行くか・OS の待機の仕組みを使うか）。間隔の長さ・待機の最大時間（無期限でよいか）。
  - 持ち主のプロセスの確認の方法。プロセス番号の使い回し（別のプロセスに同じ番号が付く）への備え。
  - 状態ファイルの形式の版・壊れたときの回復（置き場所は環境変数で決まる）。
  - 更新の手順（待機中は実行ファイルを置き換えられない）。
  - 「止まる」の合図を、作業中のセッションがどのタイミングで見るか（見張りを走らせる側の手順）。
- 端末へ出す文は ASCII だけにする（`tools/*.ps1` と同じ決まり。コンソールの文字コードは変えない）。人が読む日本語は状態ファイルから別の読み物（`status`）で出す方法を設計で決める。
- 失敗の経路は黙らせない（`logging.md`: ログを出して `Err` を返す。`panic` は致命の場合だけ）。
- テストの一時フォルダ・状態ファイルは、ワークツリーの `target\` の下だけ。決定論テストは時刻とプロセスの生死を注入し、`sleep` に頼らない。実機（子プロセスを実際に立てて、取得待ち・返却・見張りの起床を通す）は `#[ignore]` で、明示したときだけ走らせる。
- `publish = false` とその理由を `[package]` の中ほどに書く（最後の行に置かない・新しいクレートの決まり）。
