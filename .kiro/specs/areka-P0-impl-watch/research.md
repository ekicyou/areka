## 3. 進め方の案

### 案 A: 今の PowerShell スクリプトを広げる（待ちのループを pwsh で足す）

- `kiro-watch.ps1` に `wait`・`watch`・`resume-wait` を足し、`AREKA_IMPL_WATCH_HOME` を読むようにする。
- 長所: 判断の移植が要らない。
- 短所: 要件 1.5（実行ファイル 1 つ・`cargo` を通さない）・11.1（Rust のクレート）に反する。pwsh の起動は 1 回 200 ms 前後で、静かな机の計測中に見張りが何度も起きると雑音になる。複数プロセスの排他を pwsh で正しく書くのは Rust より難しい。範囲外（`kiro-watch` を触らない）とも衝突する。
- **採らない**（要件が Rust の実行ファイルを求めているため。比較のために書いた）。

### 案 B: 新しいクレート `crates/areka-impl-watch`（推奨）

ファイルの割り方（1 本 1,000 行以下・各本に兄弟のテスト）:

| ファイル | 持つもの | 流用元 |
|---|---|---|
| `main.rs` | 引数 → `cli::run` → 終了コード（薄い） | `ukadoc-survey/src/main.rs` |
| `cli.rs` | コマンドの表・`--help`・標準出力/標準エラーの振り分け・終了コードの対応表 | `ukadoc-survey/src/cli/mod.rs` |
| `state.rs` | 状態の型（版・参加者・机・待ち行列・直前のマージ・走っている待ち・回収と復旧の記録）と `serde` の派生 | `kiro-watch.ps1` の `New-State` |
| `plan.rs` | **純粋な判断**: `apply(state, command, now, alive) -> (state, events)`。規則 1〜7・回収・再計画 | `Invoke-Plan`・`switch ($Command)`・`SylphyaCore::apply` |
| `store.rs` | 置き場所の解決・ロックファイルの排他・読み（版の検査・壊れたファイルの退避）・置き換え書き・ログの追記 | `boot_config.rs`・`sylphya/persist/io.rs` |
| `alive.rs` | プロセスの生死の口（トレイト）と Windows の実装・偽物 | `areka-update/src/procedure.rs` の口の形 |
| `wait.rs` | 3 種の長い待ち（番・停止要請・再開）: 読む → 判定 → 寝る、の繰り返し。自分の待ちの記録の登録と抹消 | 新規 |
| `status.rs` | 人が読む形の組み立て（ASCII の端末向けと UTF-8 のファイル向け） | `Write-Status` |

- 長所: 判断（`plan.rs`）が時刻と生死を引数で受けるので、要件 12.1 の決定論テストが `sleep` 無しで書ける。ファイル・プロセス・時計の 3 つの口を偽物にすれば、同時書き・故障・死んだ持ち主を全部テストで再現できる。
- 短所: 新しいクレート 1 つ分の骨組み（`Cargo.toml`・`publish` の行・手順書）が要る。`Cargo.lock` の席を 1 つ使う。

### 案 B の分かれ道: 生死の確認を「Windows の API」でするか「ロックファイル」でするか

| | B-win: プロセス番号＋作成時刻 | B-std: 参加者ごとのロックファイル |
|---|---|---|
| 仕組み | 待ち・見張りのプロセスが自分の番号と `GetProcessTimes` の作成時刻を記録。確認は `OpenProcess`→`GetExitCodeProcess`（`STILL_ACTIVE`）→作成時刻の一致 | 待ち・見張りのプロセスが `<置き場>/alive/<識別>.lock` を**排他で開いたまま**にする。確認は `try_lock` が成功するか（成功＝持ち主は居ない） |
| 使い回しへの備え（7.4） | 作成時刻の照合で防ぐ | ロックはプロセスと一緒に OS が解くので、使い回しの問題がそもそも無い |
| 依存 | `windows`（`Win32_Foundation` をクレート側で足す）。lock に新しいクレートは増えない | 標準ライブラリだけ |
| 状態の確認（9.4）で「居ない」の印 | 番号を開いて答える | `try_lock` して成功したら即 `unlock`。読み取りだけで状態は変えない |
| 弱み | 権限の違うプロセス（管理者で動く Claude など）を開けないと「居ない」に倒れる危うさ | ロックファイルが置き場に増える（参加者ごとに 1 つ・離脱で消す）。「ロックを持つプロセスが居るか」は分かるが「どのプロセスか」はログでしか追えない |

どちらも要件を満たす。B-std は書く量が少なく、使い回しの備えが要らず、外の依存も 0 で、要件の「外の依存を増やさずに書ける見込み」に最も近い。設計の論点 2 に送る。

### 案 C: 案 B ＋ 今のスクリプトも残して二重に動かす（移行の段）

- アプリが動いたあともスキルが書き替わるまで `kiro-watch` を動かす、という移行の形。
- しかし両方が別の状態を持つので、どちらが正しいか分からなくなる。しかも調停の節はいま一時停止で、スクリプトは動いていない。**採らない**。移行は「続きの spec でスキルを書き替えたら、その日から exe だけ」で足りる。

## 4. 規模と危うさ

- **規模: M**（brief の見立て 15〜19 タスクの内）。判断の移植は 1 対 1 で写せる（`Invoke-Plan` 80 行＋コマンド 100 行）。新規は排他・生死・待ち・版と退避・手順書。
- **危うさ: 中**。理由: 同じファイルを何本ものプロセスが読み書きする並行の正しさと、「セッションを代表するプロセス」の決め方（論点 1）がまだ無い。並行の方は、ロックの中で「読む → 判断 → 書く」を 1 塊にすれば形は単純で、決定論テストで固定できる。論点 1 は要件の討議で決めないと設計に入れない。

## 5. 設計へ持ち越す論点（要件の討議の議題）

1. **セッションを代表するプロセスは何か（要件 7.1・7.2）**。待ちのコマンドは番が来ると終わる。すると**机を持っている間、そのセッションに走っているプロセスが無い**（マージの番の間、`/kiro-complete` を回すセッションは待ちも見張りも走らせていない）。候補:
   - (a) 番が来たら呼び出し側が「持っている印」のコマンド（例 `hold`）をバックグラウンドで走らせ、`merged`／`loaddone`／`cancel` で終える。生死＝このプロセス。要件 7.1 の「机を持つ」に合う。スキルの手順が 1 行増える（続きの spec）。
   - (b) 待ちのコマンドが番が来ても終わらず、番の到来は別の合図（ファイル・標準出力の 1 行）で伝える。brief の「終わりがどうぞの代わり」に反する。
   - (c) 持ち主の生死は見ない。回収は待ち・見張りのプロセスだけを対象にし、持ち主は開発者が手で外す（7.6）。要件 7.1・7.2 の「持ち主」の語を弱める必要がある。
   **裁定（2026-10-10 要件の討議 議題 1）: (a) を改め、別の `hold` は置かず見張り `watch` そのものを「居る印」にする**。作業中・待ち・持ち主の間は見張りを走らせ続けるのが参加者の約束。回収は「作業中なのに見張りが無い者」だけ。「停止要請中」「止まった」は自動では回収しない（要件 7.1・7.2・7.7・5.3 に反映）。あわせて **Claude のアプリを閉じたときにバックグラウンドの子プロセスが一緒に終わるか**（Windows のジョブオブジェクトに入れているか）は確かめる必要がある（Research）。一緒に終わらないなら、(a) の印が残って机が塞がるので、7.6 の手動の取り下げが要る場面が増える。
2. **生死の確認の方式**: B-win（番号＋作成時刻）か B-std（参加者ごとのロックファイル）か。上の表。推奨は B-std（標準ライブラリだけ・使い回しの備えが不要）。
3. **待ちの方式（要件 6.1・6.6）**: (a) 一定の間隔で状態を読み直す（例 1 秒。読む前に更新時刻を見て変わっていなければ中身を読まない）／(b) Windows の名前つきイベント（書く側が `SetEvent`・待つ側が `WaitForSingleObject`）で起こし、間隔の読み直しを保険にする。(a) は標準ライブラリだけで書け、1 秒に 1 回の小さなファイルの読みは静かな机の計測を乱さない見込み。(b) は起床が即時だが `windows` の機能が要る。推奨は (a)。間隔の長さは設計で決める（要件は「時間の上限なし」だけを定める）。
4. **排他の形（要件 8.1・8.2）**: 状態ファイルとは別の `state.lock` を 1 つ置き、状態を変えるコマンドは排他ロックの中で「読む → 判断 → 書く（置き換え）」、状態の確認は共有ロックで読むだけ。置き換え（`rename`）の相手をロックできないので、ロック用のファイルを分ける。ロックの待ちに上限を置くか（例: 10 秒で諦めて失敗）も決める。
5. **状態ファイルの版（要件 8.6・8.7）**: 最上位に `"version": 1`。知らない版は読まず上書きせず終了コード非 0。壊れたファイルの退避名（例 `state.json.broken-<時刻>`）。
6. **終了コードの表（要件 6.5・9.5）**: 前例の 0＝成功 / 1＝失敗 / 2＝使い方の誤り に、待ち・見張り用の「番は来なかった（取り下げ・離脱・回収で消えた）」を足す（例 3）。環境変数の無い失敗を 1 と分けるか（例 4）も決める。Bash の `$?` で読み分ける前提。
7. **日本語の値の読ませ方（要件 9.2・9.3）**: (a) `kiro-watch` と同じく置き場の下に `status.md`（UTF-8）を書き、端末にはその道筋と ASCII の要約だけ出す／(b) ASCII の外の字を `\u{…}` に逃がして端末に出す。(a) は Claude が Read で読めるので扱いやすい。待ちのコマンドの出力（直前のマージ・止まった参加者・停止要請の理由）にも日本語が混ざるので、同じ決まりを当てる。
8. **ログの形（要件 10）**: (a) `tracing`＋`fmt::layer().with_writer(Mutex<File>)`（ANSI 無し・`logging.md` の規約どおり）／(b) 標準ライブラリで 1 行ずつ追記。(a) は規約に沿うが subscriber の初期化が要る。(b) は短い。どちらも依存は増えない。ログの大きさの上限（回し・切り詰め）は要件に無いので、置かない（置くなら設計で）。
9. **時刻の持ち方と表し方**: 状態には UNIX 秒（整数）を置き、テストでは注入する。人が読む形は、(a) UTC を自前で `YYYY-MM-DDTHH:MM:SSZ` に組む（20 行ほど）／(b) `chrono` を直接の依存に足す（`Cargo.lock` には既に在るので新しいクレートは増えないが、直接の依存が 1 つ増える）／(c) `GetLocalTime` でローカル時刻（`windows` の機能）。推奨は (a)。
10. **手順書の置き場（要件 11.3）**: (a) `doc/impl-watch.md`（`doc/crates-io-publish.md` の前例）／(b) クレートの `README.md`／(c) `lib.rs`／`main.rs` の冒頭の文書（`temp-path-kit` の前例＝doctest で古びない）。あわせて書く中身として、「待っている間は exe を置き換えられない」の代わりに **Windows は動いている exe の名前の変更はできる**（`areka-impl-watch.exe` → `.old` に改名してから新しいものを置く）ので、待機者が居ても更新できる手順を書くかどうか。
11. **識別（`--id`）の決め方**: アプリは渡された文字列をそのまま使う。何を渡すか（ワークツリーの道筋・spec 名・セッションの題）は続きの spec（スキルの書き替え）で決める。ここでは「ASCII・空でない・`/` を含まない」などの形の決まりだけを置くか。
12. **コマンド名の対応**: 今の 13 個（`note`・`next` を除く 11 個）に、待ち 3 種（`wait`／`watch`／`resume-wait` など）と、論点 1 の (a) を採るなら `hold` を足す。名前と引数（`--id`・`--repo`・`--spec`・`--bug`・`--purpose`・`--pr`・`--sha`）は設計で表にする。
13. **実行ファイルを置き換えてよいかの確かめ方（要件 9.1・11.3）**: 状態ファイルの「走っている待ち・見張り」の記録で示すか、実行ファイル自体を書き込みで開けるか（開けなければ誰かが走らせている）で示すか。後者は記録の抜け（途中で殺された待ち）に左右されない。
14. **要件 11.3 の文言の追随**: 論点 10 の「動いている exe の改名」の手順を採るなら、11.3 の「更新の前に走っている待ち・見張りが無いことを確かめる」を「改名してから置く手順」へ書き替える（設計の討議で要件へ戻す）。

## 6. Research Needed（設計で確かめる）

- Claude Code の Bash のバックグラウンド実行に時間の上限が無いこと（要件 6.1 の前提）。道具の説明は「ターンをまたいで走り続ける」とだけ言っている。
- Claude のアプリを閉じたときにバックグラウンドの子プロセスが終わるかどうか（論点 1）。終わらないなら、回収の仕組みは「待ち・見張り・持っている印」のプロセスが残ったままになる場面を想定し、手順書に `cancel --id` の手動の外し方を書く。
- `std::fs::File::lock` が Windows で `LockFileEx` の**強制ロック**（別のプロセスの読み書きも止める）になること。状態ファイルそのものではなくロック用のファイルに掛けるので、置き換え（`rename`）には影響しない見込みだが、1 度実機で通す。
- 管理者権限で動くプロセスと通常権限のプロセスが混ざったとき、ロックファイル／`OpenProcess` のどちらが素直に動くか（B-std なら問題にならない見込み）。

## 7. 設計への申し送り

- 推奨: **案 B**、生死は **B-std**（参加者ごとのロックファイル）、待ちは**間隔の読み直し**、排他は **別ファイルの短いロック**、時刻は **UNIX 秒＋自前の UTC 表記**。外部クレートの追加 0・`windows` クレートも不要の見込み（B-win を採るときだけ `windows` を `Win32_Foundation` 付きで足す）。
- 判断の移植は `Invoke-Plan` を 1 対 1 で写し、テストは「規則 1〜7 の分岐ごとに 1 本」を先に赤で書く。既存の挙動のうち要件に無いもの（`note`・開発者への「空になった」）は写さない。
- 論点 1（セッションを代表するプロセス）は要件の討議で決まった: 見張り `watch` のプロセスが印。`alive.rs` は見張りのプロセスの生死だけを答えればよく、`hold` コマンドは要らない。
