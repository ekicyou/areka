### 2.1 SET の突合（要件 6.4）— 実測で両方向のずれが出た

本文に `[SET有効]` の印がある項目は **14 件**。

`currentghost.mousecursor`／`currentghost.seriko.cursor.scope(ID).mouse????list(当たり判定名).path`／同 `.index(ID2).path`／`currentghost.seriko.tooltip.scope(ID).textlist(当たり判定名).text`／同 `.index(ID2).text`／`currentghost.seriko.sticky-window`／`currentghost.seriko.zorder`／`menu`／`sakura.bind.menu`／`kero.bind.menu`／`char*.bind.menu`／`position`／`playing`／`pause`

一方、sylphya の 21 名は相対名（`currentghost.` や `scope(ID).` を省いた形）で書かれている。突き合わせると:

**⑴ 21 名のうち、正典の見出しに対応が付かないもの**

- `seriko.cursor.path`／`seriko.cursor.name`／`seriko.tooltip.text`／`seriko.tooltip.name` の 4 名。正典側の実名は `currentghost.seriko.cursor.scope(ID).mouse????list(...).path` のような長い形で、しかも 2 つの形（当たり判定名で指す形と番号で指す形）に分かれる。**1 名が 2 id に対応するか、あるいは対応先が無い**（`seriko.tooltip.name` に当たる `[SET有効]` の項目は見当たらない。`textlist(...).name` は存在するが印が無い）。
- `mousecursor` は単独で書かれているが、正典側では `currentghost.mousecursor` と `currentghost.balloon.mousecursor` の 2 つに当たる。**相対名のままでは一意に定まらない。**
- `surface.num`／`animation.num`／`seriko.defaultsurface` は正典側に `currentghost.scope(ID).` 付きで実在するが、本文に `[SET有効]` の印が無い（sylphya が先取りしているのか、正典の印の付け方が家族の頭にしか無いのかは本文の読みで決まる）。

**⑵ 正典では SET が有効なのに 21 名に無いもの**

- `currentghost.seriko.zorder`・`currentghost.seriko.sticky-window`（2.8.78）
- `position`・`playing`・`pause`（サウンドの要素葉・2.8.72）

この ⑵ は channels brief の「21→26」の中身とちょうど重なる（5 件）。つまり**channels brief の主張は正典の実測で裏付けられる**。同時に `zorder-property` brief の「`dotted.rs` に入れない」とは正面から衝突する。

| `areka-P0-zorder-property` | `zorder` の読み書きの実装は自分が単独で持つ。**sylphya の 21 項には入れない**（「動かない名前の先行登録はしない」・本 brief が語彙の正本） | 同 brief の「Current State」節と末尾の 2026-09-02 追記 |
| `areka-P0-currentghost-property-tree` | `currentghost.seriko.*` 14 項を一括で持つ（`zorder`・`sticky-window` を明示的に列挙） | 同 brief の Scope In |
| `areka-P0-property-query-channels` | SET 経路の所有者として sylphya の SET 表を 21→26 へ追随させる。その 5 件に `seriko.zorder`・`seriko.sticky-window` を含む | 同 brief の Scope In と Current State |

**食い違いの形は 2 層に分かれる。**

1. **値を作る側**（読んだら実際の設定が返る・書いたら反映される）を誰が持つか → `zorder-property` と `currentghost-property-tree` の争い。
2. **語彙表の 1 行**（`SET_EFFECTIVE` に名前を載せるか）を誰が触るか → `zorder-property`（載せない）と `channels`（載せる）の争い。

要件 4.7 は「値を導出する側を担当 spec 欄に書き、語彙表だけを触る側は備考に書く」と既に決めているので、**2 層に分けて書くこと自体は要件の中で片が付く**。残るのは 1 の争いだけ。

裁定案として並べうる形（本 spec は選ばない）:

- **案 甲**: 値の導出は `zorder-property` が単独で持ち、`currentghost-property-tree` は `seriko.*` から `zorder` と `sticky-window` を外す。語彙表の 1 行は `channels` が持つ。
  - 採ると: 3 本の食い違いが全部消える。tree の範囲が 14→12 に減る。zorder-property の brief 本文（「21 項に入れない」）は**是正候補の対象になる**（channels が入れるため）。
  - 採らないと: 完了済み spec `scope-zorder-pinning` の追跡先が宙に浮く。
- **案 乙**: `currentghost-property-tree` が `seriko.*` 14 を一括で持ち、`zorder-property` は畳む。
  - 採ると: 枝の単位で持ち主が揃い、台帳の担当 spec 欄が読みやすい。
  - 採らないと（＝乙を採らない場合）: `zorder-property` に書かれた完全語彙（読みの書式・完全置換・2 個未満は無視など）の移し替えが要る。
- **案 丙**: 裁定を保留し、当該 2 id の担当 spec 欄を空文字のままにする（要件 5.4 の既定）。
  - 採ると: 本 spec の成果物としては要件どおりに閉じる。
  - 採らないと（＝丙を採らない場合）: 所有者なしの一覧に 2 件が残り続け、統合担当が同じ議論を再度開く。

`sticky-window` は `zorder` と同じ形の食い違い（tree が一括所有・channels が SET 表で主張）だが、**`zorder-property` は `sticky-window` を主張していない**。要件 5.5 は「同じ扱いで並べ、同じ裁定案の対象に含める」と言うので、案の適用範囲を 2 id にそろえるか `zorder` だけにするかは書き方の問題として残る（→ 議題 9）。

## 4. 進め方の選択肢

### 案 A: 完全に人手で 188 件を書く（スナップショットから id を写し、状態を 1 件ずつ判断）

- 使うもの: 付録 B の手順で得た id の一覧のみ。
- 良い点: 道具に一切依存しない。上流 3.3a により、後から道具が来ても成果は壊れない。要件の文面どおり。
- 悪い点: 188 件 ×（状態・版・担当・優先度・備考）を手で打つ量が大きく、id の写し間違い（符号化された 67 件）が入り込む余地がある。
- 向く場面: 判断の質を最優先し、量が現実的に収まる場合。

### 案 B: 骨組みを機械で書き出し、判断だけ人手で埋める

- 使うもの: 使い捨ての短い手順（本 spec のリポジトリには残さない、または `doc/ukadoc-coverage/` の外の一時領域）で、id・版番号（`5.19.0` を除く）・`status = "unclassified"` までを付録 A の形で出力し、そこから人手で状態・担当・優先度・備考を埋める。
- 良い点: 写し間違いが構造的に起きない。版番号の抽出（98 件）と `5.19.0` の除外が確実。id の文字順の並び（要件 1.5）も自動的に満たされる。
- 悪い点: 「道具を作らない」という境界（要件 10.1・上流が道具の持ち主）との線引きを明示する必要がある。使い捨ての手順を repo に残すと、上流の道具と二重になる。
- 向く場面: **本命**。生成物は台帳 1 本のままで、生成の手続きを残さなければ境界は保てる。

### 案 C: 上流の道具の着地を待ち、初期台帳の上に書く

- 良い点: 初期台帳の生成が上流の責任で行われ、id の正しさが上流の検査で担保される。
- 悪い点: **要件 1.8 が明示的に否定している**（道具の完成を待たない）。並走の利点を失う。
- 向く場面: 上流が本 spec の設計フェーズ中に着地してしまった場合の合流の形としてだけ。

**比較の要点**: 案 A と 案 B は成果物が同一（`property.toml` 1 本）で、違うのは「id と版番号を手で写すか、機械で写すか」だけ。要件 1.4 の「逐語で写す」と 1.5 の「文字順」を確実に満たす点で案 B が有利。案 B を採るときは、使い捨ての手順を成果物に含めない（＝上流の道具と重複しない）ことを設計で明言すべき。

### 規模と危うさ

| 観点 | 見積り | 理由 |
|---|---|---|
| 規模 | **M（3〜7 日相当）** | 実装は 0 行。作業量は 188 件分の判断と、4 本の brief との突合表・裁定案・是正候補の文章。判断の型は少数（値なし縮退／SET 非反映／未対応）に収束する見込み |
| 危うさ | **低〜中** | 実行時の挙動を変えないので壊す先が無い。中に振れる要因は ⑴ 名前での突き合わせが 21/188 しか働かないため状態の根拠が台帳の文章に集中すること ⑵ 上流の整合検査が 4 本の台帳を前提にしており、単独では確かめられない項目があること |

## 5. 調べが要る事項（設計フェーズへ持ち越し）

1. **`mouse????list` の正体** — 正典の生ページでこの見出しが実際にどう書かれているか（ワイルドカードの記号か、スナップショット化での文字落ちか）。本文には `mouseuplist・mousedownlist・mousehoverlist・mousewheellist` と列挙があるので、見出しは「その 4 つの総称」と読める。**id は逐語で写すので台帳の正しさには影響しない**が、ブリーフィングでの説明の書き方が変わる。
2. **`seriko.tooltip.name` に当たる正典項目の有無** — sylphya の 21 名に含まれるが、`[SET有効]` の印が付いた `textlist(...).name` が見当たらない。正典側で SET が有効なのか、sylphya の先取りなのかは本文の精読で決まる（要件 6.4 ⑴ の一覧に載せる根拠になる）。
3. **`surface.num`／`animation.num`／`seriko.defaultsurface` の SET 有効性** — sylphya は SET 有効と扱うが、本文に印が無い。印が家族の頭にしか付かない書き方（`currentghost.mousecursor` の本文が「以下のプロパティに共通：」と述べている形）なのかを確かめる必要がある。
4. **`values.md` が存在しない間のテーマ名の扱い** — 上流要件 4.4 の 8 語を直接引くほか無い。綴りの一致は上流の検査 6.8 が後から確かめる。
5. **上流の整合検査 6.4／6.7 が本 spec 単独では満たせないこと** — 台帳 4 本と相手ドメインの id が揃うまで確かめられない。設計でこの依存を明記するか、ブリーフィングの末尾に注記するか。

## 6. 設計判断として開発者に渡す議題

以下は本 spec が決めてはいけない事柄。要件ディスカッションへ渡す。

1. **brief の記述 → 正典 id の対応表をどこに置くか。** ブリーフィングの中に節として持つか、`doc/ukadoc-coverage/` の下に別ファイルを立てるか。要件 8.1 は「ブリーフィングに 6 つを載せる」と言うだけで、表の分量（4 本 × 枝の記述 × 展開後の id 群）については何も決めていない。別ファイルを立てると本 spec の編集ファイルが 1 本増える（要件 10 の「触るファイルは 3 つ」の宣言に影響する）。

2. **見出しが重複する `name`／`path` の書き分けの深さ。** 本文で確実に分けられることは確認済み（サウンドの要素葉が `:2` 側）。⑴ 台帳の備考に一言だけ書く ⑵ ブリーフィングに 4 行の表を置く ⑶ 両方、のどれにするか。上流の research が「突き合わせが複数の id に当たったときどうするか」を未決の課題として挙げているため、本 spec の書き方が先例になる。

3. **「語彙のみ」と「未対応」と「縮退」の振り分けの基準。** 要件 2.3〜2.5 は語彙表への登記の有無で分けると読めるが、sylphya の表はルート枝 10・汎用名 17・SET 有効 21 という**塊**で持っており、188 件の個々の id が「登記されている」かどうかは自明でない。たとえば `system.year` は「ルート枝 `system` が登記されている」ことをもって語彙のみとするのか、「`system.year` という葉は表に無い」ことをもって未対応とするのか。**この 1 つの決めで 188 件中 160 件以上の状態が入れ替わる。**

4. **担当 spec 欄が空の項目に、まだ起票されていない spec の名前を書いてよいか。** 要件 4.6 は「憶測で既存の brief に押し込まない」と言うが、「新しい spec 名を提案として書く」ことは禁じていない。書けば所有者なしの一覧が短くなるが、実在しない spec 名が台帳に入る。

5. **正典 URL の doc コメントの置き場所。** 要件 9.2 は `dotted.rs` の点付き語彙表の頭に 1 つ、9.3 は `flat.rs`／`shiori_resource.rs` に置かないと定める。ただし `dotted.rs` には表が 4 つある（ルート枝 `:17`・汎用名 `:37`・SET 有効群 `:72`・イベント名 `:106`/`:109`）。**「表の頭」がファイルの頭なのか、4 つの表それぞれの頭なのか**が文面では一意に読めない。上流 5.4 の「表の先頭にページ URL を 1 つ」に忠実なら 4 か所になりうるが、9.2 の「1 つだけ置き」とは読み方が割れる。

6. **`currentghost.seriko.*` にテーマ（装い）を付けるか。** 要件 7.1 は原則として空、7.3 は「答えが書ける項目がある（例: `currentghost.seriko.*`）」と例示する。付けるなら 14 件すべてか、着せ替えに直接関わるもの（`surfacelist.*` 2 件）だけか。付ければ優先度の序列で 2 番目の根拠が働き、この 14 件が段階 C の既定より前に出る。

7. **`currentghost.balloon.scope(ID).*` の 17 件にテーマを付けるか。** 6 と同じ問いだが、こちらは完了済み spec の縮退登記（`doc/COMPAT_ARCHITECTURE.md:184`・`:185`）が既にあり、「ゴーストが縦書きを判定して字数計算を変える」利用者向けの筋書きが文書として残っている。テーマの根拠としてはむしろ `seriko.*` より強い。

8. **件数の差の表（`currentghost` 69 対 ≈65／`history` 12 対 8／`headlinelist` 3 対 2／`pluginlist` 5 対 4）を、ブリーフィングだけに置くか、各 brief への是正候補としても書くか。** 差の正体は特定済み（本書 1.4）で、いずれも「`.count` や `mousecursor` 系を数え落とした」形。是正候補として書けば brief の担当者がそのまま直せるが、要件 8.2 の「どの記述をどの id の一覧へ書き換えるか」の粒度で 4 本分を書く量が増える。

9. **二重所有の裁定案の出し方。** ⑴ 案を 1 つに絞って推奨を明示するか、⑵ 甲・乙・丙を並べて優劣だけ書くか。要件 5.2 は「裁定案を 1 つ出す」と言うので ⑴ が文面に近いが、要件 5.3 は「採った場合と採らなかった場合」の併記を求めており、実質は選択肢の比較になる。あわせて、`sticky-window` を同じ案の対象に含める範囲（`zorder-property` は `sticky-window` を主張していない）も決めが要る。

10. **`mouse????list` を含む 5 件の id の説明。** 逐語で写すことは確定（要件 1.4）だが、ブリーフィングで「正典の記号が写しの過程で失われた可能性がある」と書くか、「正典の表記どおり」と書くか。前者を書くには生ページの確認が要る（研究事項 1）。

11. **SET の突合の基準をどちらに置くか。** 本文の `[SET有効]` の印（14 件）を正とするか、sylphya の 21 名を正とするか。要件 6.4 は双方向の一覧を求めるだけで、どちらを基準にするかは書いていない。印を正とすると `surface.num` などの 3 名が「印の無い項目を SET 有効として先取りしている」側に並ぶ。

12. **上流の整合検査が 4 本の台帳を前提にしている件をどう記録するか。** 上流要件 6.4（全 id がちょうど 1 つの台帳に 1 回）と 6.7（関連の両端の id が実在）は、本 spec の台帳 1 本だけでは満たせない（他 3 ドメインの台帳が未作成・相手の id が置かれる台帳も未作成）。⑴ ブリーフィングの末尾に注記する ⑵ 設計の前提条件として書く ⑶ 何も書かない（上流の初期台帳生成が解消するため）のどれにするか。
