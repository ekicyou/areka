## 1. 要約

- **穴の場所は確かめた。** 表示の判定 `decide_content`（`crates/areka/src/emo2_boot/balloon_visibility.rs`）は、scope ごとに「前のフレームに数えた見える文字の数」（`ScopeVisibility::last_glyphs`）だけを覚えていて、表示は「今の数がそれより大きい、かつ今は隠れている」ときだけ出す。判定へ届く観測は**数だけ**で、「このフレームの間に内容が消された」という事実は届いていない。前の台詞の残りが 1 文字・新しい台詞の最初のフレームも 1 文字なら、比べる数は 1 と 1 で、増えていないと読まれる。
- **今ある値では代わりにならない。** 文字の層（`crates/areka-emo-text/src/state.rs` の `TextLayerState`）には、消去が起きたことを数える値が無い。文字の総数・最初の文字の現れる時刻（どちらの台詞も 0.0 秒）でも、1 文字の台詞どうしは区別できない。したがって、文字の層から判定へ「消去があった」ことを渡す口を新しく作る必要がある。
- **有力な案は「文字の層に scope ごとの消去の回数を持たせ、判定がその回数の変化を見る」形。** 回数が前のフレームから変わっていれば、比べる相手を 0 とみなす。表示を後のフレームへ遅らせず、状態の持ち方を変えて同じフレームで解ける。台詞の途中の `\c`（要件 1.5）も同じ規則で拾える。会話開始の合図（`TalkStarted`）を使う案は、`\c` を拾えないうえ、合図と全消去が別々の線で届くため取り違えの余地がある。
- **既存の規則は崩れない見込み。** 隠す側の条件（ゼロへの下降）は変えない。切替の後（`forget_scope`）は文字の層の状態も消去の回数も変わらないので、台詞の外で現れることは無い。利用者の中断の掛け金は、会話開始の合図が最初の文字より必ず先に UI 側の受け口へ入る（後述 2.3）ため、1 文字の台詞でも同じフレームで解ける。
- **赤のテストの段に注意が要る。** 判定の入口（`decide`）の観測の形が変わるので、判定の段だけのテストは修正の前にはコンパイルが通らず「赤」にならない。本物の cue（全消去と文字）を文字の層へ流して配線の段から判定まで通すテストで、修正の前の失敗を示す必要がある。規模は S・危うさは低い。

### 2.2 全消去と文字が判定へ届く経路

1. **台本の組み立て**: `crates/areka-sakura/src/compile.rs` が、内容のある台本の先頭へ `ClearAll`（時刻 0.0・長さ 0.0）を 1 件だけ置く。最初の `Text` も多くは時刻 0.0。
2. **配り**: `crates/dola/src/cue/runtime.rs` の配りの輪は「cue 1 件ごとに、登録された全部の受け口へ順に渡す」。受け口の並び（`crates/areka/src/emo2_boot/mod.rs` の `GhostBootOptions.sinks`）は、2 番目が文字の受け口（`ClockedTextSink`）、4 番目が表示の合図の受け口（`BalloonLifecycleSink`）。
3. **文字の層への適用**: `ClockedTextSink` が会話の時刻の起点を取り直してから `EmoTextSink` へ渡し、UI スレッドの受け口（`areka-emo-text` の `spawn_emo_text`）が `TextLayerRuntime::apply_cue` → `TextLayerState::apply_cue` で状態を変える。`ClearAll` は既にある全 scope の中身を空にし（`clear_content`）、`Clear`（`\c`）はその scope だけを空にする。文字は「現れる時刻の列」（`RevealSchedule`）として積まれ、最初の文字は `cue.at` で現れる。
4. **観測**: 毎フレーム、可視性の段（`balloon_visibility_phase.rs` の `collect_observations`）が、文字の層を**読むだけ**（`try_borrow`）で借り、scope ごとに `visible_glyphs(actor, 会話の時刻)` を数えて `ScopeObservation` に載せる。表示の合図の線（`lifecycle_rx`）は同じ段の冒頭で全件取り出す（`drain_lifecycle`）。
5. **判定**: `decide` が観測と記憶だけから行動を決める。

要点: 判定へ届くのは「今見えている文字の数」だけで、その数が**消去の前の文字か後の文字か**は区別されていない。

### 2.3 合図と文字の届く順（中断の場面に効く）

配りの輪が cue ごとに全受け口へ渡すので、全消去の cue については「文字の受け口へ渡す（UI へ投函）→ 合図の受け口が `TalkStarted` を線へ送る」の順になり、そのあとで最初の `Text` が文字の受け口へ渡る。したがって、**最初の文字が文字の層に入った時点で `TalkStarted` は必ず線に入っている**。可視性の段は線を先に取り出してから文字を数えるので、最初の文字を数えるフレームより遅れて掛け金が解けることは無い（静的に確かめた。実機の記録では未確認）。

逆向き、つまり `TalkStarted` が全消去の適用より前のフレームで取り出されることはありうる（UI の受け口が投函を処理する前にフレームが回る場合）。このとき会話の時刻の起点は既に取り直されているので、古い台詞の文字の数は前のフレームより減る側にしか動かない。

### 2.4 取りこぼしの起き方（3 つの場面）

前の台詞が scope 0 に 5 文字残し、バルーンが隠れた後、新しい台詞が「ん」1 文字の場合：

| フレーム | 文字の層 | 観測した数 | `last_glyphs` | 今日の判定 |
|---|---|---|---|---|
| 隠れた後 | 前の台詞の 5 文字 | 5 | 5 | 何もしない |
| 新しい台詞の最初 | 全消去＋「ん」 | 1 | 5 | 1 > 5 が偽 → **出さない** |
| 次のフレーム | 「ん」のまま | 1 | 1 | 1 > 1 が偽 → **出さない**（台詞が終わるまで出ない） |

- 時間切れの後・中断の後・切替の後のどれでも、`last_glyphs` は前の台詞の数のまま残る（時間切れは `prev_visible` だけを倒す・中断の掛け金は次の会話開始で解ける・切替は `forget_scope` がわざと残す）。だから 3 つの場面とも同じ形で取りこぼす。
- 最初のフレームで全文が見え、その数が前の残り以下の台詞（例: 残り 5・新しい台詞 3 文字を一度に表示）も同じ。
- 2 文字以上でも、2 文字目以降が後のフレームで現れれば、その増加で出る（今日、気付きにくい理由）。
- 時刻の起点の取り直しと全消去の適用の間にフレームが挟まると、古い文字の数が一度 0 まで下がり、次の 1 文字が増加として出ることがある。**出るか出ないかがフレームの巡り合わせで決まる**ので、本番での再現は揺れる。決定論のテストは文字の層へ cue を直接入れて巡り合わせを固定する必要がある。

### 2.5 切替の後の文字の層

`frame/switch.rs` の `finish_balloon` は、scope ごとに背景色・文字の模型を差し替え、`forget_scope` を呼ぶだけで、文字の層の状態（`TextLayerState`）には触らない。したがって、切替の前後で文字の数も、仮に新しく作る消去の回数も変わらない。

## 4. 足りないものの中身

1. **消去の事実を判定へ渡す口が無い。** `TextLayerState` にも `TextLayerRuntime` にも、消去の回数・世代のような値は無い（`clear_count`・`generation`・`epoch` にあたるものは文字の層に 0 件）。数・文字の総数・最初の文字の現れる時刻では、1 文字の台詞どうしを区別できない（どちらも 1 文字・どちらも 0.0 秒）。
2. **観測の形が変わる。** `ScopeObservation` に項目が 1 つ増え、`ScopeVisibility` に「前に見た消去の回数」が 1 つ増える見込み。これに伴い、構造体の字面で組んでいる道具とテスト（`test_support` の `seen`・`unobserved`、`forget_tests` の `kept`、`phase_tests` の 2 か所、`timeout_suppression_tests` の 1 か所）が追随する。
3. **修正の前に赤を示す段。** 判定の段のテストは観測の新しい項目を使うので、修正の前にはコンパイルが通らない。修正の前の失敗は、文字の層へ `ClearAll`・`Clear`・`Text` を本物の cue として流し、可視性の段（`run_balloon_visibility_phase`）から判定まで通すテストで示すことになる。配線の段の道具は `balloon_visibility_phase_tests.rs` に私有なので、共有のしかたを決める必要がある（steering `structure.md` の Unit Tests は、テーマ間で共有する道具を `<stem>_test_support.rs` へ集約し、写しを作らないことを求めている）。

## 5. 実装の選択肢

### 案 A: 文字の層に scope ごとの「消去の回数」を持たせ、判定がその変化を見る（拡張）

- **文字の層**: `Clear`（その scope）と `ClearAll`（既にある全 scope）のたびに回数を 1 つ進める。読み口は `visible_glyphs` と並ぶ読むだけの関数（例: scope ごとの消去の回数）。可視性の段は今と同じく読むだけで借りられる。
- **観測**: `ScopeObservation` に回数を足す（観測できないフレームは数と同じく「無し」）。
- **判定**: `ScopeVisibility` に「前に見た回数」を足す。回数が変わっていれば、表示の比べる相手を 0 とみなす（`glyphs > 0 && !visible && !break_latch` で出す）。非表示の条件は今のまま（ゼロへの下降・見えている）。
- **場面ごとの答え**:
  - 1 文字の台詞（残り 5 → 全消去＋1）: 回数が変わり、1 > 0 で同じフレームに出る（要件 1.1〜1.4）。
  - 台詞の途中の `\c`＋文字（`\b[-1]` の後）: その scope の回数が変わり、同じ規則で出る（要件 1.5）。
  - 見えているバルーンで全消去＋文字: 見えているので表示も非表示も出ない（要件 2.4・明滅なし）。
  - 全消去の後に文字が無い: 数が 0・前の数が正・見えている → 今日どおり隠す（要件 2.5）。
  - 切替の後: 文字の層に触らないので回数は変わらず、表示の済んだ文字は増加にならない（要件 2.1）。
  - 中断の後: 掛け金が先に効き、会話開始の合図は最初の文字より遅れない（2.3）ので、新しい台詞の最初のフレームで出る（要件 1.3・2.2）。
- **気を付ける点**: 初めて見る scope は、今の回数をそのまま「前に見た回数」として覚える（初見を消去と読まない）。中断の段（`decide_user_break`）が初見の scope の記憶を作るときも同じ。観測できなかったフレームでは回数も据え置く（次に観測できたフレームで変化に気付ける）。`forget_scope` は回数の記憶も残す。
- **回数の置き場の 2 通り**:
  - A-1: scope の状態（`ActorTextState`）の欄にする。読み口が素直。ただし `ActorTextState` は等しさの比較を持ち、`state_cue_apply_tests.rs` の 2 か所が「`Clear` の後＝初期状態」を比べている。回数が進むので、この 2 か所の比べ方を改める必要がある（比較の意味が変わる）。
  - A-2: `TextLayerState` の中に scope ごとの回数の表を別に持つ。scope の状態の比較は変わらない。`ClearAll` は「既にある scope」だけを空にするので、表の範囲も同じに揃える必要がある。
- **長所**: 1 フレームも遅らせない。`\c` も拾う。届く順の巡り合わせに左右されない（消去と文字は同じ文字の層の状態から同時に読む）。読むだけで済む。
- **短所**: 文字の層（別の crate）の公開の読み口が 1 つ増える。観測と記憶の構造体が 1 項目ずつ増え、字面で組んでいるテストが追随する。

### 案 B: 会話開始の合図（`TalkStarted`）で比べる相手を 0 にする（判定だけで閉じる）

- **中身**: `apply_lifecycle_signals` の `TalkStarted` で、各 scope に「次に観測した数は 0 と比べる」印を立てる。文字の層には触らない。
- **短所**:
  - 台詞の途中の `\c`（要件 1.5）を拾えない。`\c` には合図が無い。
  - 2.3 のとおり、`TalkStarted` が全消去の適用より前のフレームで取り出されることがある。そのフレームで印を使うと、古い台詞の文字を 0 からの増加と読み、**消える直前の古い文字のバルーンを出してしまう**（要件 2.1〜2.3 に反する）。印を「数が 0 へ下がるまで持ち越す」などの工夫を足すと、今度は全消去の後の最初のフレームで数が 0 にならない場合（1 文字の台詞がまさにそれ）に印が使えず、元の穴に戻る。
  - 冒頭の全消去で隠すために `last_glyphs` を残している今の設計（2.1 の表）と、印の扱いが絡み合う。
- **長所**: 判定の中だけで済み、文字の層の crate に触らない。

### 案 C: 文字の層が「消去をまたいでも減らない累計の数」を出す（数え方の変更）

- **中身**: 消去のたびに、消した文字の数を足し込んだ累計を持ち、判定はその累計の増加を見る。
- **短所**: 消去の時点では「消した文字のうちいくつが見えていたか」が分からない（文字の層は今の時刻を知らずに cue を適用する）。消した全部（まだ現れていない文字を含む）を足すと、消去だけで累計が増え、文字が 1 つも見えていないのにバルーンを出す。防ぐには結局「今の数が 0 より大きい」も別に要り、案 A より持ち物が増える。
- **長所**: 判定の比較の式（増えたか）を変えずに済む。

### 案 D: 配線の段が「このフレームに消去された scope の集合」を文字の層から取り出す（合成）

- **中身**: 文字の層の `apply_cue` が消去された scope を集合に積み、可視性の段が毎フレーム取り出して空にする。判定へは「消去があったか」の真偽を渡す。
- **短所**: 取り出して空にするので、文字の層を書き換えで借りる必要がある（今は読むだけ）。借りられなかったフレームに積まれた分の扱いが要る。積む口は `actor.rs`（975 行）側に置くことになり、長さの上限に近い。取り出しの副作用があるぶん、同じ観測を 2 度読むと答えが変わる。
- **長所**: 判定へ渡すのは真偽 1 つで、記憶の構造体は増えない。

### 比べた結果（判断ではなく材料）

| 観点 | A（回数） | B（合図） | C（累計） | D（集合の取り出し） |
|---|---|---|---|---|
| 1 文字の台詞（要件 1.1〜1.4） | ○ | △（届く順に依る） | ○（0 より大の条件が別に要る） | ○ |
| 台詞の途中の `\c`（要件 1.5） | ○ | × | ○ | ○ |
| 古い文字で出してしまう恐れ（要件 2.1〜2.3） | 無し | 有り | 無し | 無し |
| 文字の層の crate への変更 | 読み口 1 つ＋回数 | 無し | 累計＋読み口 | 集合＋取り出し口（`actor.rs` 側） |
| 読むだけで観測できるか | ○ | ○ | ○ | ×（書き換えで借りる） |

案 A が要件と制約を最も素直に満たす。置き場は A-1 と A-2 で既存テストへの波及が違う（議題 2）。

## 6. 制約との照合

- **1 フレーム遅らせない**: 案 A・C・D は、消去の事実と文字の数を同じフレームの観測として読むので、表示は最初の文字が見えたフレームで出る。案 B も遅らせはしないが、2.3 の巡り合わせで正しさが揺れる。
- **状態の持ち方を変えて解く**: 案 A は「scope ごとに前に見た消去の回数を覚える」という記憶の形の変更で解く。
- **`shell-balloon-switch` 要件 3.3**: 切替は文字の層に触れず、`forget_scope` は記憶の数（と新しい回数）を残すので、切替の後に台詞の外で現れることは無い。新しい赤のテストの 1 本（切替の場面）がこれを同時に確かめる形が取れる。
- **`balloon-break` 要件 4.8**: 掛け金の判定は表示の条件の中に残り、掛け金が解けるのは会話開始の合図だけ。合図は最初の文字より遅れて届かない（2.3）。
- **記録（要件 1.6）**: 表示の分岐が積む記録は今と同じ `Transition { trigger: Content, visible: true }`。新しい記録の種類は要らない。
- **1,000 行**: `balloon_visibility.rs`（895 行）に足すのは判定の分岐の数行と構造体の欄。新しいテストは新しい兄弟のファイルへ置く。`balloon_visibility_tests.rs`（982 行）・`actor.rs`（975 行）・`balloon_visibility_phase_tests.rs`（919 行）へ大きく足すことは避ける。

## 7. 規模と危うさ

- **規模: S（1〜3 日）** — 変えるのは判定の表示の分岐 1 か所・観測の 1 項目・文字の層の回数と読み口、それに新しいテスト 1〜2 本と記述の追随。既にある型と道具の延長で済む。
- **危うさ: 低** — 判断は純関数に閉じていて、既存の判定の網羅表（内容・中断・時間切れ・切替）がそのまま残りの規則の守りになる。気を付けるのは字面で組んでいるテストの追随と、A-1 を選んだ場合の「消去の後＝初期状態」の比較の改め方だけ。

## 8. 設計へ持ち越す調べもの

1. **巡り合わせの実測（任意）**: 2.3 の「`TalkStarted` は最初の文字より遅れない」は、配りの輪の順と受け口の並びから静的に導いた。実機の記録（`RUST_LOG` を判定の分岐まで開けた状態）で、中断の後の 1 文字の台詞が同じフレームで出ることを確かめるかは設計で決める。
2. **`ClearAll` の範囲**: `ClearAll` は「既にある scope」だけを空にする。まだ一度も喋っていない scope は回数も 0 のまま、数も 0 から始まるので問題は無い見込みだが、案 A-2 で表を別に持つ場合は範囲を揃える書き方を設計で確かめる。
3. **観測できないフレームを挟んだ場合**: 文字の層を借りられないフレームに消去と文字が入ると、次に観測できたフレームで出る（今日の規則でも同じ縮退）。要件 1.4 の「遅らせない」の例外として扱ってよいかを設計で書き分ける（議題 5）。
4. **統合テストの台詞**: `shell_balloon_switch_session_balloon_tests.rs` の `CHANGE_1` を 1 文字へ戻したときに、実 GPU の統合テストで切替の場面の 1 文字の台詞が出ることを確かめられるか（2.4 のとおり本番の巡り合わせでは揺れるので、統合テストで確実に赤になるかは要確認）。

## 9. 設計の分かれ目（要件討議への議題）

1. **消去の事実の渡し方**: 案 A（文字の層の消去の回数）・案 B（会話開始の合図）・案 D（消去された scope の集合の取り出し）のどれにするか。案 B は台詞の途中の `\c`（要件 1.5）を拾えず、届く順によって古い文字のバルーンを出す恐れがある。案 A が最も素直。答えによって触る crate（文字の層を触るか）が変わる。
2. **回数の置き場**: A-1（scope の状態の欄＝`state_cue_apply_tests.rs` の「`Clear` の後＝初期状態」の比較 2 か所を改める）か、A-2（`TextLayerState` に別の表＝既存の比較は変わらない）か。答えによって直すテストが変わる。
3. **修正の前の赤をどの段で立てるか**: 判定の段のテストは観測の形が変わるため修正の前に赤にならない。文字の層へ本物の cue を流す配線の段のテストで赤を示す。そのための道具（`Harness` など・今は `balloon_visibility_phase_tests.rs` に私有・同ファイル 919 行）は、steering（`structure.md` の Unit Tests「テーマ間で共有するヘルパは `<stem>_test_support.rs` へ集約する・複製は本文の同一性を壊す」）に従うなら、新しいテストのファイルへ写すのではなく共有の道具のファイルへ出すことになる。出す先（既存の `balloon_visibility_test_support.rs` に足すか、配線の段の道具のファイルを新しく作るか）と、その移し替えを赤のテストより先の手順に置くかが分かれ目。
4. **切替の統合テストの台詞**: `CHANGE_1` を 1 文字へ戻して統合テストでも穴が塞がったことを示すか、doc の注記を事実に合わせて改めるだけにするか（要件 3.6 はどちらでも満たせる）。前者は実 GPU の統合テストで本番の巡り合わせに左右される恐れがある。
5. **観測できないフレームを挟んだ場合の扱い**: 文字の層を借りられないフレームに消去と文字が入った場合、次に観測できたフレームで出ることを、要件 1.4 の例外として要件か設計に明記するか。
6. **COMPAT §8 の追随の形**: 「バルーンが現れる契機」の行の判定の文を「消去の後に置かれた文字は空の状態からの増加として数える」へ改め、古い参照の行番号を定義の名前で指し直す。既存の行を改めるか、本 spec の上書きとして別の行を足すか。

### 9.1 要件討議での扱い（2026-10-01）

- 議題 5（観測できないフレーム）は要件の文の補いで閉じた: 要件 1.4 に「文字の層を観測できなかったフレームを挟んだ場合は、次に観測できたフレームで表示する」を足した（観測の失敗をログへ記録して判定を見送る、今もある縮退。表示を遅らせる解ではない）。
- 議題 1〜4・6 は「どう作るか」の分かれ目なので、設計（`/kiro-design`）で決める。要件討議の時点の見立ては次のとおり（設計で覆してよい）。
  1. 消去の事実の渡し方: 案 A（文字の層の scope ごとの消去の回数）。案 B は要件 1.5 を満たせず、届く順によって要件 2.1〜2.3 に反しうるので採らない見込み。
  2. 回数の置き場: A-1／A-2 は既存テストへの波及で選ぶ。
  3. 修正の前の赤: 文字の層へ本物の cue を流す配線の段のテストで立てる。道具は写さず共有のファイルへ出す（steering `structure.md`）。
  4. 切替の統合テストの台詞: 要件 3.6 はどちらでも満たせる。実 GPU のテストの揺れを避けるなら、注記の是正にとどめ、1 文字の台詞の確かめは決定論のテストに任せる。
  6. COMPAT §8: 生きた文書なので既存の行を改め、行番号の参照は定義の名前で指し直す（完了 spec のアーカイブ本体は書き換えない）。
- 要件 1.2（全文が一度に見える短い台詞）と要件 1.5（台詞の途中の `\c`）は、brief の 1 文字の台詞より広いが、根は同じ取りこぼしで、案 A なら追加の仕組み無しに塞がる。あるべき姿として要件に残した。
