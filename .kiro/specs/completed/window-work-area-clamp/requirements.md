# Requirements Document

## Project Description (Input)

- **だれが困っているか**: areka の利用者。起動の直後に、キャラクターの窓が画面（作業領域＝タスクバーなどを除いた矩形）からはみ出したり、隣のモニタへ渡ったりする。ぱすた（「窓際のぱすたさん」）の実機の走りで見えた。
- **今の状況**:
  - 件 1: 起動の並べ直し（記憶に位置の無い相方を本体の隣へ並べる）は隣に詰めた位置を返すだけで作業領域を見ない。実機で相方が x=−1108 へ置かれ、左隣の 150% のモニタへ渡った。拡大率が変わったあとの詰め直しも同じく作業領域を見ない。
  - 件 2: 吸着の無い（`seriko.alignmenttodesktop,free`）窓が大きい面へ切り替わると、左上を保って下へ伸び、作業領域の下へはみ出す（ぱすた・200%: 下端 2232、作業領域の下端 1704）。
  - 件 3: 記憶から戻した位置を作業領域へ寄せる今の規則は窓ごとに別々に寄せるので、組の 2 つの窓が離れるかもしれない（確かめていない）。
  - 件 4: バルーンだけが作業領域へ寄せられ、シェルとの組がずれて、ぱすたの縦書きのバルーンの 1 列目にシェルの「×」と横線がかぶる（SSP では起きない）。
  - 件 5: 初回起動のトークの最中にぱすたの窓あわせ（見た目の調整）が効かず、トークの後にずれる（SSP では起きない）。
- **何を変えるか**: 起動の並べ直し・拡大率の後の詰め直し・面の切り替え・記憶からの戻しで、キャラクターの窓を作業領域の中に収める。組の窓を寄せても組を離さない。シェルとバルーンの組を崩さない。起動のトークの位置の指令を、トークの最中から正しく当てる。どれも特定のゴーストに向けた扱いでなく、どのゴーストにも同じに効く一般の決まりとして作り、決定論のテストと実機で確かめる。

出どころは `brief.md`（2026-10-23 起票・2026-10-24 の件 4・件 5 の追記と開発者の裁定・棚卸㉚の再測定を含む。後の節が前の節を上書きする）。区分は **B（バグ）**、版は v0.1.0（ゴール「ゴースト『窓際のぱすたさん』が SSP と同じに動く」）。

## Introduction

正典（ukadoc）は、起動のときに窓を作業領域の中へ寄せるかどうかを書いていない。SSP のヘルプは、初回の起動の時点で位置がおかしい場合はゴーストの作者にかけあうよう書いており、SSP がいつも寄せるわけではない見込みである。

開発者の裁定と方針:

- 2026-10-24: **「起動の表示位置は画面（作業領域）の中に収まっていればよく、SSP と同じ規則である必要はない」**（件 2 について）。
- 2026-10-29（要件の話し合い）: **「あくまでも汎用の対策を入れる。SSP が何もせずにゴーストを画面内にとどめている以上、ぱすたさん独自の対応は不要なはず」**。この spec の要件は、どれも特定のゴーストを名指しした扱いを持たない一般の決まりとして書く。ぱすたは症状が見えた一例であり、確かめの一例である。
- 2026-10-29（要件の話し合い・議題 1）: 10-24 の裁定を件 1・件 3 にも広げ、寄せ方は SSP を測る前に areka の規則としてここで決めた。SSP の測りのうち ⑴⑶ は必須でなく、記録のための任意の測りとする。

### 件ごとの決め

| 件 | 決めた規則（要件） |
| ---- | ---- |
| 件 1（起動の並べ直し） | 並べた窓が基準の窓のモニタの作業領域からはみ出すなら、基準の窓の反対の側へ並べ替える。反対の側にも入らなければ作業領域の端へ寄せる（重なってよい）。基準の窓は動かさない（要件 1） |
| 件 1 の足し（拡大率の後の詰め直し・記憶からの隣り合わせ） | 件 1 と同じ規則（要件 2） |
| 件 2（`free` の窓の面の拡大） | 既定の位置にいる間（利用者も台本も動かしていない窓）は、大きい面へ切り替わってはみ出したら作業領域の中に収める。SSP には無い足し物として §8 に残す（要件 3） |
| 件 3（記憶からの組の戻し） | 記憶の位置と今の大きさから隣り合い・重なりを推し、寄せる窓と同じ量だけ組の窓を動かす。記憶の書式は変えない。寄せた起動では古い記憶へ隣り合いの印を書き足さない（要件 4） |
| 件 4（バルーンだけの寄せ） | キャラクター窓が作業領域に収まっている間は、バルーンだけを寄せてシェルとの相対の位置を崩さない。シェルを収める直し（件 1〜3）で、バルーンだけが寄せられる場面を無くす。それでもバルーンだけが横にはみ出すときは、SSP と同じくキャラクター窓の反対の側へ並べ替え、反対の側にも入らなければ今の押し込みに倒す（2026-10-30 の裁定・要件 5） |
| 件 5（起動のトークの位置の指令） | 起動のトーク（初回を含む）の位置の指令は、2 回目以降のトークと同じく、正しい拡大率とその時点の面の大きさで当たる。原因は測ってから決め、この spec で直す（要件 6） |

### 要件の話し合いで決めたこと（2026-10-29・一括承認）

1. **SSP の測りの扱い（議題 1）**: 件 1・件 3 は SSP を測る前に areka の規則で決める。⑴⑶ は任意。⑷ は要件 5.3 の場面が見つかったときだけ、⑸ は必須。
2. **件 1 の並べ方（議題 2）**: 反対の側へ並べ替え、それでも入らなければ作業領域の端へ寄せる（重なってよい）。組をまとめて内側へずらす形は、基準の窓（本体）を動かすので取らない。
3. **件 2 の寄せる期間（議題 3・S4）**: 起動の間に限らず、既定の位置にいる間はいつでも寄せる。SSP は何もしない見込みだが、10-24 の裁定に沿う一般の安全網として入れ、SSP との違いを §8 に残す。
4. **件 3 の組（議題 4）**: 記憶の位置と今の大きさから隣り合い・重なりを推す。離れて置かれていた一緒に動く組（`\![set,sticky-window,…]`）は拾えない。この限界を記録に残す。
5. **古い記憶への印の書き足し（議題 5）**: 記憶の位置を寄せて表示した起動では書き足さず、寄せずに起動した回に書き足す。
6. **件 4（議題 6・S2）**: ぱすたで再現しなくなったかで決めず、一般の崩れとして扱う。シェルを収める直しで、バルーンだけが寄せられる場面を無くし、決定論のテストで固定する。それでもバルーンだけが寄せられる場面が見つかったら、SSP の測り ⑷ の後に一般の決まりとして扱いを決める。
7. **件 5 の持ち場（議題 7・S3）**: 切り出さず、この spec で直す。直すのは areka の一般の道で、初回起動や特定のゴーストを名指しした扱いは入れない。原因が kanade の起動のイベントの順でも、同じウェーブの spec とファイルが重ならなければこの spec で直す。`emo2_boot/consumer_ledger.rs` に行を足す形が要るときだけ別の spec へ切り出し、その結果を `brief.md` と `roadmap.md` に残す。
8. **実機の確かめ（議題 8・S5）**: 必達は、emo2 を写した検体（ワークツリーの `target\` の下）で件ごとの道を通すこと。ぱすたの初回起動は、v0.1.0 のゴールの通しの一例として同じ机で 1 回回す。
9. **ドラッグで作業領域の外へ置いた窓（議題 9）**: 勝手に戻さない（要件 7.6）。
10. **要件の文言（S1）**: ぱすたの症状をそのまま要件にしていた所（旧 5.1・6・10.4）を一般の決まりに書き直し、ぱすたは確かめの一例へ下げた。

### 実装の後に決めたこと（2026-10-30・タスク 4.4 の通しと SSP の測り ⑷）

11. **バルーンだけがはみ出す場面（要件 5.3〜5.8）**: 4.4 の通しで、キャラクター窓は収まっているのに相方のバルーンだけが窓の左隣で作業領域の外へ出て、押し込まれて窓に重なった。SSP 2.9.26 は同じ形でバルーンを窓の反対の側（右隣）へ並べ替えていた（`research.md` 13 節）。開発者の裁定「この spec で直す」により、旧 5.3（測ってから決める）・旧 5.4（見つからなければ変えない）を、並べ替えの決まりへ書き直した。完了 spec `areka-P0-windowposition-limit` の押し込みは、反対の側にも入らないときの倒し先として残す。どのスコープにも同じに当て、ゴーストを名指ししない（要件 7.8）。

## Boundary Context

- **In scope**:
  - 起動の最後の並べ直しで置いた窓を作業領域の中に収めること（件 1）。
  - 拡大率が変わったあとの詰め直しで動かした窓と、記憶から戻すときに隣り合わせた窓に、件 1 と同じ寄せを当てること（`dpi-realign-remembered-chain` の要件の「作業領域への寄せ」の節からの申し送り）。
  - 既定の位置にいる `free` の窓が大きい面へ切り替わっても作業領域の中に収めること（件 2）。
  - 記憶から組の窓を戻して寄せるとき、組を離さないこと（件 3）と、古い記憶に書き足す隣り合いの印の扱い。
  - バルーンだけが寄せられてシェルとの組がずれる崩れ（件 4）と、キャラクター窓が収まっていてもバルーンだけが横にはみ出すときの反対の側への並べ替え（完了 spec `areka-P0-windowposition-limit` の押し込みの決まりを改める・2026-10-30 の裁定）。
  - 起動のトークの位置の指令がトークの最中に正しく当たらない崩れ（件 5）の原因の測りと直し。
  - SSP での測り（⑸ は必須・⑴⑶ は任意・⑷ は条件つき）・記録（ログ）・`doc/COMPAT_ARCHITECTURE.md` §8 の行・決定論のテスト・実機の確かめ。
- **Out of scope**:
  - 特定のゴースト（ぱすたを含む）を名指しした扱い。
  - 起動の測りの面を descript の既定の面にすること（`descript-window-keys`・10-24 着地済み）。この spec はその後の版の上で作る。
  - `seriko.alignmenttodesktop` の `top`／`left`／`right` の起動の位置と、作業領域が変わったときの沿わせ直し（`window-snap` の件 1）。
  - 拡大率が変わったあとの詰め直しの対象の決め方そのもの（`dpi-realign-remembered-chain`・完了）。この spec は詰め直した後の位置に寄せを当てるだけ。
  - 表情の差し替えで絵の大きさが変わったときにキャラクターが横へ動かない約束（`areka-P0-scope-chain-gap` 要件 7.4・`areka-P0-dpi-transition-atomicity` 要件 6.6）。変えない（要件 3.2 のはみ出した向きの寄せだけが例外）。
  - 利用者がドラッグで作業領域の外へ置いた窓を勝手に戻すこと（要件 7.6）。
  - ゴーストが台本（`\![move]` など）で置いた窓の位置を寄せること（要件 1.4）。
  - 記憶の書式を変えること（要件 4.2）。
  - バルーンを動かせない指定（`descript-window-keys` が足した所）。
  - ゴーストを複数同時に動かすこと（`multi-ghost-runtime`）・3 体目以降のキャラクター窓を出すこと（`extra-character-windows`）。この spec の決めはキャラクターの数を 2 体に決め打ちしない。
- **Adjacent expectations**:
  - 記憶から戻した位置を作業領域へ寄せるかどうかの今の判定（`areka-P0-position-persist` 要件 5＝作業領域とまったく交わらない窓だけを寄せ、寄せた位置を記憶に書き戻さない）は保つ。この spec はその判定で寄せる窓が組に入っているときの寄せ方だけを足す。
  - 窓の組の相手が連れ動くのはドラッグと瞬間の `\![move]` だけで、吸着の当て直し・大きさの変化・作業領域の変化では相手を動かさない今の決まり（`areka-P0-window-link-directives`・§8 の行）は保つ。
  - バルーンは今までどおりキャラクター窓に付いて動く（寄せで窓が動けばバルーンも同じだけ動く）。バルーンを作業領域の中に収める今の決まり（`areka-P0-windowposition-limit`）は、要件 5.3〜5.5 で改める（キャラクター窓が収まっていてバルーンだけが横にはみ出すときは反対の側へ並べ替え、押し込みは倒し先に残す）。改めた事実を §8 に残す（要件 8.4）。利用者がバルーンをドラッグして離したときの補正（解放の補正）と `windowposition.limit=0` の扱いは変えない。
  - `dpi-realign-remembered-chain`（完了）は「詰め直した位置は寄せない。寄せる働きは `window-work-area-clamp` が作り、詰め直しの位置にも同じ寄せを当てる」と決めている。この spec はその申し送りを受け取る。
  - 着地の後の通しの確かめは、ぱすたの手順書 `doc/pasta-real-run.md` で回す（`pasta-in-windows-verification` は 10-23 に着地済み）。

## Requirements

### Requirement 1: 起動の並べ直しで置いた窓を作業領域の中に置く（件 1）

**Objective:** As an areka の利用者, I want 起動の直後に相方の窓が画面の外や隣のモニタへ置かれないこと, so that 起動したあとに窓を探して手で戻さずに済む

#### Acceptance Criteria

1. When 起動の最後の並べ直しで、記憶に位置の無いキャラクター窓を並べる基準の窓（隣へ並べる元の窓。2 体では本体）の隣へ並べた位置が、基準の窓が属するモニタの作業領域からはみ出すとき, the areka shall その窓を基準の窓が属するモニタの作業領域の中に収めて置き、隣のモニタへ渡さない。
2. When 要件 1.1 で窓を収めるとき, the areka shall その窓を基準の窓の反対の側の隣へ並べ替え、反対の側の隣も作業領域からはみ出すときは、作業領域の中で一番近い位置（作業領域の端）へ寄せる（基準の窓と重なってよい）。
3. The areka shall 要件 1.1・1.2 で基準の窓を動かさない（並べ直しで先頭の窓を動かさない今の決まりを保つ）。
4. If ゴーストが台本（`\![move]` など）で置いた窓であるとき, the areka shall その窓を並べ直しの寄せで動かさない（台本で置いた窓が並べ直しから外れる今の決まりを保つ）。
5. If 並べ直した位置が基準の窓が属するモニタの作業領域の中に収まっているとき, the areka shall 並べ直しの位置を変えない。

### Requirement 2: 拡大率の後の詰め直しと記憶からの隣り合わせにも同じ寄せを当てる

**Objective:** As an areka の利用者, I want 拡大率を変えたあとや起動し直したあとに隣り合わせ直された窓も、画面の外へ出ないこと, so that 拡大率の違う画面を使っていても窓を見失わない

#### Acceptance Criteria

1. When 拡大率が変わったあとの詰め直しで動かした窓が、組の動かさない側の窓が属するモニタの作業領域からはみ出すとき, the areka shall 要件 1.1〜1.3 と同じ規則でその窓を作業領域の中に収める。
2. When 起動・読み直し・切り替えで記憶から戻し、覚えたときに隣り合っていた組を今の絵の幅で隣り合わせた位置が、組の動かさない側の窓が属するモニタの作業領域からはみ出すとき, the areka shall 要件 1.1〜1.3 と同じ規則でその窓を作業領域の中に収める。
3. If 詰め直しや隣り合わせで動かさなかった窓（離れていた組・重なっていた組・一緒に動く組の窓・台本で置き直した窓・ドラッグの最中の窓）であるとき, the areka shall その窓をこの要件の寄せで動かさない。
4. The areka shall 要件 2.1・2.2 で寄せた位置を記憶に書かない（詰め直した位置・隣り合わせた位置を記憶に書かない今の決まりを保つ）。

### Requirement 3: 既定の位置にいる `free` の窓が大きい面へ切り替わっても作業領域の中に収める（件 2）

**Objective:** As an areka の利用者, I want 面が切り替わってもキャラクターが画面の中に収まっていること, so that 起動の直後からも、その後も全身が見える

> 開発者の裁定（2026-10-24）: 「起動の表示位置は画面（作業領域）の中に収まっていればよく、SSP と同じ規則である必要はない」。SSP はこの場面で何もしない見込みで、この要件は areka の一般の安全網として足す（要件 8.3 で §8 に残す）。

#### Acceptance Criteria

1. When 既定の位置（利用者のドラッグでも台本の位置の指令でも動かされていない位置）にいる吸着の無い（`free`）キャラクター窓が、大きい面へ切り替わって、その窓が属するモニタの作業領域からはみ出すとき, the areka shall その窓を作業領域の中に収める。
2. When 要件 3.1 で窓を収めるとき, the areka shall はみ出した向きにだけ、はみ出した分だけ動かし、はみ出していない向きには動かさない。
3. When ゴーストの台本が、要件 3.1 で収めた窓を基準にほかの窓を置く（例: `\![move,--base=0,…]` で相方を本体の左上へ寄せる）とき, the areka shall 収めた後の位置を基準にして置く。
4. The areka shall 要件 3.1 で窓を収めるときに、組の並べ直しをやり直さない（相方は台本や連れ動きで置かれる分だけ動く）。
5. If 利用者がドラッグで置いた窓か、台本の位置の指令で置いた窓が大きい面へ切り替わってはみ出すとき, the areka shall その窓を寄せず、今の決まり（左上を保つ）で置く。

### Requirement 4: 記憶から組の窓を戻して寄せても組を離さない（件 3）

**Objective:** As an areka の利用者, I want モニタの構成が変わって記憶の位置が画面の外になっても、本体と相方が離ればなれにならずに画面へ戻ること, so that 組で使っていた並びのまま使い続けられる

#### Acceptance Criteria

1. When 起動・読み直し・切り替えで記憶から戻した窓が今の判定（`areka-P0-position-persist` 要件 5）で作業領域へ寄せられ、その窓が、記憶の位置と今の窓の大きさから隣り合っていた、または重なっていたと分かる組の窓であるとき, the areka shall 組の全員が寄せられる（どの窓も作業領域と交わらない）ときは全員を同じ量だけ動かして組の互いの位置を保ち、作業領域と交わる（見えている）窓が組にあるときはその窓を動かさない（隣り合っていた組の寄せられた窓は、起動の並べ直しが見えている窓の隣へ付け直し、要件 2.2 の規則で作業領域の中へ置く。重なっていた組の寄せられた窓は今の判定のまま窓ごとに寄せる）（設計の話し合い 1・2026-10-29）。
2. The areka shall 要件 4.1 の組を、記憶にある位置と隣り合いの印と今の窓の大きさだけから決め、記憶の書式を変えない。
3. If 記憶から戻した組の窓がどれも作業領域と交わっている（一部でも見えている）とき, the areka shall 組のどの窓も寄せず、記憶の位置のまま置く。
4. If 記憶の組が、記憶の位置で隣り合わず重ならない（離れて置かれていた）とき, the areka shall 窓ごとに今の判定で寄せる（今の振る舞いを保つ。離れて置かれていた一緒に動く組〔`\![set,sticky-window,…]` で組にした窓〕もこの扱いになる）。
5. The areka shall 要件 4.1 で寄せた位置を記憶に書き戻さず、記憶の位置（利用者が最後に決めた位置）を保つ（`areka-P0-position-persist` 要件 5.4 を保つ）。
6. If 記憶の位置を寄せて表示した起動であるとき, the areka shall 隣り合いの印の無い古い記憶へ印を書き足さず、書き足さなかったことを記録（ログ）に残す（印は、寄せずに起動した回に表示の矩形から書き足す）。

### Requirement 5: バルーンだけを寄せてシェルとの組をずらさない（件 4）

**Objective:** As an areka の利用者, I want シェルとバルーンが、ゴーストの作者が descript で決めた相対の位置のまま見えること, so that シェルの絵とバルーンの字が重なって読めなくなることがない

#### Acceptance Criteria

1. While キャラクター窓が作業領域の中に収まっていて、バルーンが descript のずらし（`balloon.offsetx`・`balloon.offsety` など）どおりの位置で作業領域の中に収まるとき, the areka shall バルーンを作業領域へ寄せず、シェルとの相対の位置を保つ。
2. The areka shall 要件 1〜4 でキャラクター窓を作業領域の中に収めることで、シェルが作業領域からはみ出したためにバルーンだけが寄せられる場面を起こさない。
3. When キャラクター窓がそれの属するモニタの作業領域の中に収まっていて、バルーンが今の位置（descript のずらしどおりの位置、またはキャラクター窓に付いて動いた位置）では作業領域から横にはみ出すとき, the areka shall どのスコープのバルーンも、キャラクター窓の反対の側へ並べ替えて置く（2026-10-30 の裁定・`research.md` 13 節・SSP 2.9.26 の測り ⑷）。
4. When 要件 5.3 でバルーンを並べ替えるとき, the areka shall 反対の側の位置を、キャラクター窓の縦の中心線についてバルーンを左右に映した位置（並べ替えた後のバルーンの左端＝キャラクター窓の左端＋キャラクター窓の右端−今のバルーンの右端）とし、縦の位置は変えない（シェルからの横の間合いは左右で同じになる。ukadoc の「横のずらしの＋はどちらの側でもシェルに近づく向き・縦の＋は下向き・左右に出すときの縦の基準はシェルの上端」に沿う）。並べ替えた位置が縦にだけはみ出すときは、横の位置を保ったまま縦だけを作業領域の中に収める。
5. If 並べ替えた位置も作業領域から横にはみ出すとき、映しても横の位置が変わらない（バルーンがキャラクター窓の真上・真下にある `windowposition.x` の `center`／`top`／`bottom` など）とき、またはバルーンが縦にだけはみ出すとき, the areka shall 並べ替えず、バルーンを作業領域の中に収める今の決まり（`areka-P0-windowposition-limit` の押し込み＝作業領域の端へ寄せる・キャラクター窓に重なってよい）で置く。
6. If キャラクター窓が作業領域からはみ出しているとき・`windowposition.limit` が 0 のスコープであるとき・利用者がバルーンをドラッグして離したときの補正（解放の補正）であるとき, the areka shall 並べ替えない（はみ出した窓と解放の補正は今の押し込みのまま、`limit=0` は今どおり収めない）。
7. The areka shall 要件 5.3 の並べ替えを表示の位置だけに当て、バルーンの相対の位置（配置の `balloon_offset`・追従のずらし・記憶の `BalloonOffset`）に焼き付けない（キャラクター窓が作業領域の余裕のある所へ戻れば、元の側の位置へ戻る）。バルーンを利用者のドラッグで動かさない指定（`balloon.dontmove`・`\![lock,balloonmove]`）は並べ替えを止めない（SSP の測りで、`balloon.dontmove,true` のゴーストの相方のバルーンが並べ替えられていた）。
8. When 要件 5.3〜5.5 でバルーンを動かしたとき, the areka shall 今の記録の語 `[balloon-limit] Clamp` に、並べ替えたか（`how="flipped"`）押し込んだか（`how="pushed"`）を分ける欄を足して残す。

### Requirement 6: 起動のトークの位置の指令を、トークの最中から正しく当てる（件 5）

**Objective:** As an areka の利用者, I want 起動のトークの台本が窓を動かしたり重ねたりするとき、トークの最中から作者の意図どおりの並びで見えること, so that トークが終わってから見た目がずれて驚かずに済む

#### Acceptance Criteria

1. The 開発者の机での測り shall 起動のトークで位置の指令を流すゴースト（症状が見えた例はぱすたの初回起動）について、SSP が SHIORI へ送る要求の並びと時機（`ghost\master\ssp_shiori_log.txt` の差分）と、areka が送る要求の並びと時機・位置の指令が当たった時点の拡大率と面の大きさを比べ、ずれの原因を記録に残す（SSP の測り ⑸）。
2. When 起動のトーク（初回の起動のトークを含む）の台本で位置の指令（`\![move]`・重なりの順の指令・窓を組にする指令）が流れたとき, the areka shall 2 回目以降のトークと同じく、そのモニタの正しい拡大率とその時点の面の大きさで指令を当て、トークの最中から指令の結果の並びで表示する。
3. The areka shall 起動のトークが終わった後に、要件 6.2 で当てた並びをずらさない。
4. The areka shall 要件 6.2・6.3 を、初回起動や特定のゴーストを名指しした扱いを持たない一般の道の直しで満たす。

> 原因が起動のイベントを送る順や時機（kanade の持ち物）にあっても、同じウェーブの spec とファイルが重ならなければこの spec で直す。`emo2_boot/consumer_ledger.rs` に行を足す形が要ると分かったときだけ別の spec へ切り出し、その結果を `brief.md` と `roadmap.md` に残す（要件の話し合いの議題 7）。

### Requirement 7: 寄せの共通の決まり

**Objective:** As an areka の利用者, I want 窓を作業領域へ寄せる働きが、どこで寄せても同じ決まりで動くこと, so that 寄せた窓がちらついたり、寄せた位置が記憶を狂わせたりしない

#### Acceptance Criteria

1. The areka shall 窓が属するモニタの決め方を今の決まり（窓の中心で決め、どのモニタにもいなければ一番近いモニタ）のまま使い、作業領域はそのモニタのタスクバーなどを除いた矩形とする。
2. If 窓が作業領域より大きく、両端を同時に収められないとき, the areka shall 左辺・上辺を優先して収める（キャラクター窓とバルーンを収める今の式と同じ）。
3. The areka shall 寄せた位置を窓を置くその時点で決め、作業領域の外の位置で一度表示してから次の時点で寄せ直すこと（1 フレーム遅らせる形）をしない。
4. If 窓が属するモニタの作業領域を取り出せないとき, the areka shall 窓を寄せずに置き、寄せなかったことと理由を記録（ログ）に残す（ありもしない作業領域を作らない）。
5. When 起動の最後に並べ終えた時点で、記憶に位置の無いキャラクター窓の位置を記憶に書くとき, the areka shall 要件 1・要件 3 で寄せた後の表示の位置を書く（はみ出した位置を書くと、次の起動でも記憶の位置からはみ出して立つため）。
6. If 寄せの対象が、利用者がドラッグしている最中の窓か、利用者がドラッグで置いた位置（記憶から戻したドラッグの位置を含む）にある窓であるとき, the areka shall この spec の寄せでその窓を動かさない（記憶から戻すときの今の判定・要件 2.2 の記憶からの隣り合わせ・要件 4 を除く）。
7. When この spec の寄せでキャラクター窓が動いたとき, the areka shall その窓のバルーンを今までどおり窓に付いて同じだけ動かす。
8. The areka shall この spec のどの寄せも、特定のゴーストを名指しした扱いを持たず、どのゴーストにも同じ決まりで当てる。

### Requirement 8: SSP での測りと、決めた寄せ方の記録

**Objective:** As a 開発者, I want 寄せ方の決めと SSP との違いが、出どころとともに開発の記録に残ること, so that 後から「なぜこの寄せ方か」「SSP とどこが違うか」を確かめられる

#### Acceptance Criteria

1. The 開発者の机での測り shall 開発者の機械の SSP（SSP の MCP・`ghost\master\ssp_shiori_log.txt`）で次を測り、手順・測った版・結果を spec の記録に残す: ⑸ 要件 6.1 の要求の並びと時機（必須） ⑷ 要件 5.3 の場面が見つかったときの、SSP のバルーンとシェルの扱い（その場面が見つかったときだけ）。⑴ 2 人並べると本体の隣が作業領域の外になるときの SSP の置き方 ⑵ `free` の窓が大きい面へ切り替わってはみ出すときの SSP の扱い ⑶ 記憶の位置が作業領域の外にある組の SSP の寄せ方は任意とし、測ったときは記録のためだけに残す（規則は要件 1〜4 のとおり）。
2. If SSP の振る舞いが、この spec の決めた規則（要件 1〜6）と食い違うとき, the areka shall 決めた規則を保ち、SSP との違いとその理由を互換の記録に残す。
3. The areka shall 決めた寄せ方（件 1〜件 5 のそれぞれ）を、正典が黙る点・SSP の測りの結果（測ったものだけ）・areka の決め・SSP との違い（要件 3 の安全網を含む）・出どころの spec と要件の番号とともに、`doc/COMPAT_ARCHITECTURE.md` §8 の行として残す。
4. If この spec の決めが完了 spec の要件を改めるとき（要件 5.3〜5.5 でバルーンを収める今の決まりを、反対の側への並べ替えと倒し先の押し込みへ改めた）, the areka shall 改めた事実と理由を `doc/COMPAT_ARCHITECTURE.md` §8 の、完了 spec の要件を改めた記録として残す（アーカイブ済みの spec の本文は書き換えない）。

### Requirement 9: 寄せの判断の記録（ログ）

**Objective:** As a 開発者, I want 窓を寄せたか・寄せなかったかとその理由がログに残ること, so that 「窓がはみ出した」の報告を受けたときに、寄せが走らなかったのか、走って寄せないと判断したのかをログから見分けられる

#### Acceptance Criteria

1. When この spec の寄せでキャラクター窓を動かしたとき, the areka shall どの窓を・どの場面（起動の並べ直し・拡大率の後の詰め直し・記憶からの隣り合わせ・面の切り替え・記憶からの組の戻し）で・どの作業領域へ・どこからどこへ動かしたか（並べ替えたか・端へ寄せたか）を、記録（ログ）に残す。
2. When 寄せの判定で窓を動かさなかったとき（作業領域の中に収まっていた・台本で置いた窓・ドラッグの窓・記憶の組が見えていた・既定の位置にいない窓）, the areka shall 動かさなかったことと理由を、実機の確かめで開けられる詳しさの記録（ログ）に残す。

### Requirement 10: 受け入れの確認（決定論のテストと実機）

**Objective:** As a 受け入れを判定する人, I want この直しが決定論のテストで固定され、実機でも確かめられること, so that 窓のはみ出しが後から戻ってきたら気付ける

#### Acceptance Criteria

1. The areka shall 次の形を決定論のテストで確かめられるようにする（数値は合成の例）:
   - ⑴ 本体が主のモニタの左端の近くにいて、相方を本体の左へ並べると作業領域の外（左隣の 150% のモニタ）になる並び（x=−1108 の形）→ 相方が本体の右の隣へ並べ替えられる。右の隣にも入らない並び → 作業領域の端へ寄せられる（本体と重なってよい）。どちらでも本体は動かない
   - ⑵ 拡大率の後の詰め直しと、記憶からの隣り合わせで、動かした窓が作業領域の外になる並び → 要件 1 と同じ規則で作業領域の中に収まる
   - ⑶ 拡大率 200% で既定の位置にいる `free` の窓が y=864 に 640×840 で置かれ、1108×1368 の面へ切り替わる（作業領域の下端 1704）→ 窓の下端が 1704 以下で、横へは動かない。同じ切り替えでドラッグや台本で置いた窓 → 動かない
   - ⑷ 記憶の位置が作業領域の外（どのモニタとも交わらない）にある、隣り合っていた組・重なっていた組 → 寄せた後も組の互いの位置が保たれる。離れて置かれていた組 → 窓ごとに寄せられる。寄せた起動では隣り合いの印が書き足されない
   - ⑸ 窓が作業領域より大きい → 左辺・上辺が収まる
   - ⑹ 作業領域を取り出せない → 動かさない
   - ⑺ 作業領域の中に収まっている並び → どの窓も動かない
   - ⑻ 起動の最後に並べ終えた時点で記憶に書く位置が寄せた後の位置であり、寄せた記憶の位置・詰め直しの位置は記憶に書かれない
   - ⑼ キャラクター窓が作業領域に収まり、バルーンがずらしどおりの位置で作業領域に収まる → バルーンはずらしどおりの位置に立ち、寄せられない
   - ⑽ 起動のトークの位置の指令が、表示の前（拡大率が決まる前）や面の切り替えと別の時点に届く形 → 正しい拡大率とその時点の面の大きさで当たる（要件 6.1 の測りで原因が決まった形を固定する）
   - ⑾ キャラクター窓が作業領域の左端にあり（例: 0〜1108）、バルーンが窓の左隣（例: x=−872・幅 872）で外へ出る → バルーンが窓の右隣（x=1108）へ並べ替えられ、縦の位置は変わらない。作業領域の右端の窓の右隣で外へ出る → 左隣へ並べ替えられる。両方の側に入らない（作業領域が窓とバルーン 2 つ分より狭い）→ 今の押し込みで置かれる。縦にだけはみ出す・真上の中央揃え・キャラクター窓がはみ出している・`limit=0`・解放の補正 → 並べ替えない。`balloon.dontmove` の窓でも並べ替えられる。並べ替えでバルーンの相対の位置は変わらず、窓が戻れば元の側へ戻る。記録の欄 `how` が `flipped`／`pushed` を分ける
2. The areka shall 今あるテストのうち、表情の差し替えでキャラクターが横へ動かないこと（`areka-P0-scope-chain-gap` 要件 7.4）・記憶から戻した位置の寄せと書き戻さないこと（`areka-P0-position-persist` 要件 5）・バルーンを作業領域へ収めること（`areka-P0-windowposition-limit`）を確かめるテストを保つ（この spec で改めた点は、改めた決まりに合わせて書き換える）。
3. The 受け入れの判定 shall 実機で次を開発者の机（主の画面 2880×1800・拡大率 200%、左の画面 150%）で、排他テストの机を持って確かめることを必達とする。使うのは emo2 を写した検体（実機の根・一時フォルダはワークツリーの `target\` の下だけ）で、件ごとの道を通す:
   - ⑴ 本体を主の画面の左端に置き、記憶に位置の無い相方を起動の並べ直しで並べる → 相方が左隣のモニタへ渡らず、作業領域の中に並ぶ
   - ⑵ 起動の台本で、既定の面より大きい `free` の面へ切り替える → 窓が作業領域の中に収まる
   - ⑶ 記憶の位置が作業領域の外にある組を起動する → 組が離れずに作業領域の中へ戻る
   - ⑷ 起動のトーク（初回の起動のトークを含む）で `\![move]` を流す → トークの最中から指令の結果の並びで表示され、トークの後にずれない
4. The 受け入れの判定 shall v0.1.0 のゴールの通しの一例として、同じ机で記憶の空のぱすたを初回起動し、起動のトークの間も後も、本体と窓の枠が作業領域の中に収まり、トークの後に並びがずれず、縦書きのバルーンの 1 列目に × と横線がかからず、窓が作業領域の左端にあるときの相方のバルーンが窓に重ならずに窓の右隣へ並べ替えられる（要件 5.3）ことを 1 回確かめる。
