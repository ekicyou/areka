# 設計の確かめ: emo-text-dwrite-fidelity

- 日付: 2026-10-29
- 対象: `design.md`（確定版）・`requirements.md`（承認済み）・`research.md` §10
- やり方: 静的な読みだけ（cargo・SSP・MCP・画面には触れていない）。設計の主張を `crates/areka-emo-text/src` の `draw.rs`・`draw_catalog.rs`・`draw_metrics.rs`・`draw_line_store.rs`・`viewbox_draw_decoration.rs` と、その呼び手（`viewbox_draw_render.rs`・`actor_decoration.rs`・`actor_present.rs`・`actor_attach.rs`・`choice.rs`・`layout.rs`）で照らした。

## 確かめの要約

設計は、3 つの件の原因を測りで突き止めている（件 1＝縦書きで既定の機能の組が `vpal` と同じ位置の調整を当てる・件 3＝既定の行間で組んだ列の箱が行の矩形の書き始めの辺に揃う）。そのうえで、直しを今ある部品の 1 か所ずつ（`FontCatalog`・`FontFace`・`create_line_layout`）に置いている。コードと照らすと、書式・TextLayout・範囲指定を作る所の数と形は設計の記述どおりだった。本番で TextLayout を作るのは `draw_metrics.rs` の 2 か所と `draw_line_store.rs` の 1 か所だけで、試験用書式の設定の写しも実在する。実装へ進める出来だが、下の 3 点は設計の討議で決めておくべき。

## 重い指摘（3 件）

### 🔴 指摘 1: 束縛書式の記憶の鍵が、新しく書式を左右する値を見ていない

- **何が**: `viewbox_draw_render.rs::ensure_format` の鍵は `(font.name, font.height, mode)` だけ（511 行）。本書の後、束縛書式は「候補列全体から解決した顔」と `looks.default.bold`／`italic` でも変わる。それなのに鍵は今のままで、名前と大きさが同じで太字の指定だけ違うフォントを渡されると、古い書式を使い続ける。
- **影響**: 今の本番では起きない。`actor_attach.rs` は `resolved` が変わると描画資源ごと捨てて作り直す（299 行）。ただ「鍵が同じなら書式を使い回してよい」という不変条件は破れる。同じ実行部でフォントを替える試験（`viewbox_draw_frame_render_tests.rs` 418 行の型）や、新しい G5 を 1 つの実行部で書くと、黙って古い太さで描かれる。設計は「この行は変えずに済む」とだけ書いていて、この依存に触れていない。
- **直し方**: 鍵を `(font.looks.default.font_key(), mode)` に替える（候補列・大きさ・太字・斜体を全部含む。1 行の直し）。C12 のほかの 7 本は `viewbox_draw_render.rs` に触らない（重なり 0）。要件 5.3 と記憶「約束を理由に回避の形へ逃げない」に沿って、知らせてから直す。直さないなら、少なくとも Revalidation Triggers に「同じ実行部が別の束縛フォントを受ける経路ができたら鍵を広げる」と書く。
- **要件**: 4.1・4.8・4.9
- **根拠**: design.md「FormatFactory」Implementation Notes・「触らないファイル」

### 🔴 指摘 2: `\f[name]` の候補が全部無いとき、計測と描画の食い違いが太さ・斜体にまで広がる

- **何が**: 設計は、計測鍵の書式を `face_or_default(&key.name)`（全部無ければＭＳ ゴシック Regular）で作る。範囲指定のほうは、当たらなければ「束縛の顔のまま」にする。research.md §10.6 はこれを今からある食い違いとして範囲の外に置いた。しかし本書は、この 2 つの関数を同じ `FontFace` の規則へ書き直す。その結果、束縛が中太なら、描画は 500 の束縛の書体、計測は 400 のＭＳ ゴシック になる。家族名に加えて太さまで食い違い、それを本書の新しいコードが書き直すことになる。
- **影響**: そういう台本では、折り返しと列の位置が描いた字とずれる（要件 4.1 の「描く字と計測に同じに当てる」と同じ趣旨の破れ）。範囲の外とした件の起票（`/kiro-discovery`）も、design.md には約束として書かれていない。
- **直し方**: 推奨は本書で直すこと。全部無いときの区間の顔を「束縛の顔」に揃え（SSP の `\f[name,無い名前]` は今の書体のまま、の見込み）、`probe_format_for` と `apply_font_ranges` が同じ小さな関数を通るようにする。どちらも本書が書き直す関数で、触るファイルは増えない。完了 spec の R11.3（計測はＭＳ ゴシック）を上書きする決めになるので、討議で裁定を取る。直さないなら、design.md に起票の約束と担当を書く。
- **要件**: 3.6・4.1・4.6
- **根拠**: design.md「DWriteMetrics（変更）」`probe_format_for`・「FontRanges」・Non-Goals 最後の行・research.md §10.6

### 🔴 指摘 3: 列のレシピの後も、純粋層の模型と向き違いの枝が古い列の置き方（±s/2）を語り続ける

- **何が**: 列のレシピの下では、em の箱は構造上いつも行の矩形の真ん中に来る（research.md §10.3＝全書体 0）。それでも設計は次の 2 つを残す。(a) `DWriteMetrics::vertical_em_box_left` の「束縛と違う向き」の枝の既定の実装 `column_centred_em_box_left`（±(行の箱−em)/2）。(b) `layout.rs` の trait の doc（130〜135 行・158〜161 行の「DirectWrite は列の箱を書き始めの辺に揃え、反対側へはみ出させる」）。測れないときの縮退だけは 0 に直すので、同じ問いに 2 つの答えが残る。
- **影響**: 今の呼び手（`choice.rs` の `line_bands`）は束縛した向きでしか問わないので、見た目は崩れない。ただ doc と純粋層の模型が本番と逆のことを言う。後の変更（下流の `text-typesetting` など）がこれを信じて、ずらしを持ち込む恐れがある。
- **直し方**: `DWriteMetrics` では縦書きならどちらの向きでも 0 を返す（向き違いの枝も 0 にする）。`layout.rs` は doc の 2 か所だけを「列のレシピの下では 0・前の振る舞いは research.md §10.3」に直す（コードの行は変えない。触る前に知らせる）。純粋層の偽の計測器の模型を残すなら、その旨を doc に 1 行書く。
- **要件**: 5.1・5.3・5.4
- **根拠**: design.md「DWriteMetrics（変更）」・「Out of Boundary」1 行目・「File Structure Plan」の触らないファイル

## 良い点

1. **原因を測ってから直し方を選んでいる**。件 1 では、既定・`vpal` だけ・空の組・機能 1 つずつ・明示の 10 個を表で比べている（research.md §10.1）。字を個別にずらす最後の手段（要件 2.3）を使わずに済む根拠と、横倒しの英字の詰めや合字を落とさない組の選び方まで示してある。GDI の名前も、見つからない名前が置き換えでなく失敗することを測っている（§10.2）。手作りの名前の読み解き（G3）を避けたのも妥当。
2. **振る舞いを 1 か所ずつに寄せ、重複を減らしている**。TextLayout の生成口を `create_line_layout` 1 つにし、計測と行の送り幅の一致（2.4）を構造と字面の檻 L2 で守る。試験用書式が `try_create_format` の設定を字面で写していた既知の弱点も、同じ関数を呼ぶ形にして消している。新しいファイル・依存は 0。

## 判定

- **判定: GO**
- **理由**: 層の境目・依存の向き・ログの規律は今の形に沿っており、要件はすべて部品と檻に結び付いている。上の 3 件はどれも直しが小さく（1〜数行と小さな関数 1 つ）、触るファイルもほぼ今の一覧の中に収まるので、設計の討議で決めれば実装の段に持ち込める。
- **次の手**: 設計の討議（`kiro-design-discussion`）で上の 3 件を議題にする（指摘 2 は完了 spec の決めの上書きになるので裁定を取る）。そのあと `/kiro-spec-tasks emo-text-dwrite-fidelity`。

## 補足（重くない気づき・討議に出すかは任意）

- 檻 L2 が見るのは 3 ファイルだけなので、「crate の本番で `create_text_layout(` を呼ぶのは 1 か所」（Revalidation Triggers）を crate 全体では見張れない。`src` の非テストのファイルを実行時に読んで数える形にすれば、主張と檻が揃う。
- 要件 1.4 の「手本と ±1px」は、G3 では書体の寸法から出した値（約 2.1px）で比べる。手本がずらさないことからの導き方は筋が通っている。手本の実測値を記録に 1 つ添えておけば、トレースがはっきりする。
- 絵文字（ZWJ 列・旗）を縦書きで描く場合に、明示の 10 個で既定と同じ並べになるかは測っていない（`ccmp`・`liga`・`rlig` が入っているので、崩れない見込み）。
