# 設計の検証: seriko-talk-clock-fidelity

- 対象: `design.md`（2026-11-27 生成）・`requirements.md`（承認済み）・`research.md` §9
- 進め方: `kiro-validate-design` の手順（分析 → 重大な指摘 → 良い点 → GO/NO-GO）。対話は行わず、議題は設計の討議へ回す。

## 設計の検証のまとめ

設計は、件 8（消去の後に数えた数が減る）と件 5・印の件（seriko の「前の字」が文字の層と違う）を、「数えた字の数を持つ数え」と「場所ごとの前の字・印は前の字だけを進める字の列」の 2 つの形で解いている。行き先の決め方は文字の層から `areka-emo-compose` の純粋な型へ移して両方が呼ぶので、写しは増えない。根拠にしている主張はコードと一致した。残る危うさは、門が閉じている間とシェルの切替という 2 つの境目で、文字の層と同じ答えになる保証が仮定のまま残っていることと、要件 2.8 の SSP での測りがまだ無いことである。

### コードと照らした主な主張（全部一致）

- `TalkCursor { base, seen }` の `realign_talk(total)` は `base.saturating_sub(dropped)` で 0 で止まり、数えた数が減る（`trigger.rs:194-202`・`ponytail:` の注も在る）。新しい式 `prev_seen + (k×every − 1 − counted)` は今の `base + k×every − 1` と同じ値になる。
- 50 ms の食い違い 2 件（`\s[10]\q[はい,yes]\s[0]つづき` で口が遅れる・`あ\![*]いう` で口が早まる）は、`chunk_reveal_offsets` の本文（`reveal.rs:9-27`）と文字の層の `extend_chunk`（場所の列の最後の字を前の字にする・`state.rs:296`）、印の腕（`state.rs:579-586`・1 字・長さ `duration`）に当てて求め直した結果と合う。
- 行き先の規則（既定の箱・`\s` で箱を保つか戻す・`Unresolved` では記録を作らない・名前の形の `\b`）は `state_route.rs` だけに在り、`resolve_for_text`（`shell_box_assets.rs:118-128`）が面の表で絞る。`areka-seriko` と `areka-emo-text` はどちらも `areka-emo-compose` に `[dependencies]` で依存していて、`Cargo.toml` に依存を足さずに済む。
- `looper.rs` は 855 行、`looper_trigger.rs` は 218 行。振り分けを後者に置く計画で、1,000 行の上限を守れる。`observe_cue` の門（`has_talk` の真偽 1 つ）と、門が閉じたときの `feeds.clear()`（`looper.rs:320-323, 801-804`）も主張どおり。
- 印を見分ける `MARKER_COMMAND` は `areka-parsers` に在る。消費者の台帳（`consumer_ledger.rs`）は担当を文字の層のまま保ち、seriko は合図を読むだけで受け口にはならないので、台帳の一致のテストには触れない。

## 重大な指摘（3 件・設計の討議へ）

🔴 **重大な指摘 1**: 門が閉じている間は `\s` を追わず、門が開いたときに表示中の面から種を蒔く形は、文字の層と同じ答えになる保証が無い
**懸念**: 文字の層は、そのスコープに `\s` が届くまで番号を持たない（普通のバルーン）。面の表に無い番号への `\s` は「解決できない」として扱う。これに対し、seriko の種は表示中の面（起動の既定の面や、解決器が絞らずに通した番号）から蒔くので、箱の在る面では行き先が食い違う。台詞の頭の全消去は、行き先を「今の番号の既定」へ戻すだけなので、食い違いは次に `\s` が届くまで続く。
**影響**: `talk` の無いシェルから、箱と `talk` の在るシェルへ切り替えた後に、要件 2.1 の一致が崩れうる。対のテスト（5.3）は起動の時から門が開いた構成だけを通すので、この道を捕まえられない。
**提案**: どちらかに決める。⒜ 表示の側が今も合図ごとに回している `\s` の処理（`ScopeStates`）に、「文字の層の規則での答え」（`for_text` の結果と「`\s` が届いたか」）を 1 欄だけ持たせ、種はその欄から蒔いて正確にする（字ごとの仕事は増えない。要件 4.1 の「`talk` の仕事を増やさない」をこの形でも満たすと読めるかを確かめる）。⒝ 仮定 1 のまま残し、食い違いの起きる条件を台帳の note に書く。推奨は ⒜（答えが正確になり、増えるのは既に走っている道の欄 1 つだけ）。
**トレーサビリティ**: 要件 2.1・2.6・4.1
**根拠**: design.md「State Management（seriko の行き先と門）」の仮定 1・Open Questions 1

🔴 **重大な指摘 2**: シェルの切替で箱の字を捨てる境目を「seriko の最後の刻みの時刻」にしていて、時刻を刻みの境目に寄せている
**懸念**: `rebase_boxes(after, …)` の `after` は、seriko がその前に処理した刻みの時刻である。文字の層は、`hand_to` が `set_box_index` を当てた瞬間に箱の字を全部捨てる。2 つの受け手は同じ時刻を共有していないので、どの字を捨てるかが刻みの位相で決まってしまう。また `replace_shell_table` は Shell の窓の数えを `forget_slot_kind` で全部捨てる。そのため、ここで捨て方が効くのは、生き残るバルーンの窓の数えと、この後の序数だけになる。
**影響**: 要件 4.2（刻みの境目へ丸めない）の字面に触れる。切替の直後の字の数え方を、決定論のテストで固定できる 1 つの値に決められない。
**提案**: 切替が効く時刻を 1 つ決めて、文字の層と seriko の両方に同じ値を渡す（例: `SerikoReplace::Shell` に、`hand_to` を呼ぶ相の時刻を 1 欄足す）。もう 1 つの道は「箱の場所のまだ数えていない字（序数 ≥ `seen`）を全部捨てる」で、こちらは時刻を使わない。どちらにするかを仮定 2 と一緒に討議で決め、`looper_talk_route_tests.rs` で境目の両側を固定する。
**トレーサビリティ**: 要件 2.3・4.2・5.4
**根拠**: design.md「State Management」の仮定 2（`after`＝最後の刻みの時刻）・Open Questions 2

🔴 **重大な指摘 3**: 要件 2.8 の「設計の段で SSP の MCP で測って確かめる」を果たしていない
**懸念**: 印を口の数えに入れないことは要件の討議で決めた。要件 2.8 は、それに加えて「測れるときは設計の段で測る」と求めている。設計は測らずに討議へ回し（Open Questions 3）、測れない理由も、測る手順も決めていない。
**影響**: 印を数えるかどうかで区切りの字の序数が変わる。後から SSP と違うと分かると、`push_mark` の形（序数を作らない）、台帳の note、§8 の 1 行をまとめて直すことになる。
**提案**: 討議で ⒜ か ⒝ のどちらかに決める。⒜ 測る: SSP で `talk,1` を持つ面に `あ\![*]いう` を流し、口のコマの回数を数える（字 3 なら 3 回、印を数えるなら 4 回）。画面の操作は排他テストの机で順を取り、兄弟には事前に知らせる。⒝ 測れないとして決める: 理由を research.md に書き、要件 2.8 の決めを「正典は『数値分の文字』・印は絵」の読みで確定する。どちらに決めても、結論は台帳の note に書く。
**トレーサビリティ**: 要件 2.8・6.1
**根拠**: design.md「Open Questions」3・research.md §9.1 の最後の項

## 設計の良い点

1. **件 8 を、0 で止まる天井の扱いではなく、型そのものを変えて無くしている**。`TalkCursor { seen, counted }` にして、揃えのときは `seen` だけを捨てた序数の分だけ下げ、`counted` には触れない。これで「数えた数は減らない」が式の形から保証され、件 1.3 の道（遅れて届いた置き直しの知らせの後に消去が来る）も同じ 1 つの規則で解ける。捨てた序数の列で揃える形は、場所だけの消去（2.3）にもそのまま当てはまる。
2. **写しを増やさない一般化**。件 5 と印の件を「前の字の違い」という 1 つの問題として捉え、行き先の規則を下のクレートの純粋な型 `TextRoute` へ移して、文字の層と seriko が同じ型を同じ合図の順で当てる。`dola-interrupt-ticks` が字の時刻の式を 1 本にした先例と同じ向きである。場所が 1 つの台詞では列に末尾から積むだけになるので、既存のテストを変えずに通せるという回帰の見通しも、コードと合っている。

## 最終の判断

- **判断: GO**
- **理由**: 根拠にしている主張はコードで確かめられた。依存の向き（`Cargo.toml` を変えない）、`talk` の門、記録の出し先、1,000 行の上限、兄弟のファイルに置く決まり、spec の名をコードに書かない決まりのどれにも反していない。3 件の指摘はどれも、境目の仮定をどちらに決めるかという議題で、形の作り直しは要らない。
- **次の段**: `/kiro-design-discussion seriko-talk-clock-fidelity` で、上の 3 件と設計の Open Questions 4〜6 を議題にする。指摘 1 と 2 は仮定 1・2 と合わせて 1 件ずつ決める。決まった形を design.md と research.md に反映した後、`/kiro-spec-tasks seriko-talk-clock-fidelity` へ進む。
