## 4. 重大な論点（最大 3・設計ディスカッションへ）

### 論点 1: 語彙表から「どの文字列を要素として拾うか」の規則が書かれていない（要件 5.4・6.6）

**現状**: D-5 は突き合わせの規則（NFKC＋空白の畳み込み・完全一致・1 件に定まるときだけ採る）を厳密に決めているが、その手前の「ソースのどの範囲のどの文字列を語彙表の要素とみなすか」が設計のどこにも無い。`evidence::resolve(hits, sources, catalog)` はファイル本文全体を受け取るだけで、ページ URL のコメントの後に続く何を拾うのかは実装者の裁量に落ちる。

**影響**: 語彙表経路は小さくない。`SHIORI_RESOURCE_IDS`（159 件）は shiori 台帳の 677 件のうち約 2 割を占める。拾う範囲の解釈が変われば、⑴ どの id に証拠が付くかが変わり ⑵ 要件 6.6（`implemented` には証拠が要る）の合否が変わる。つまり常時走るテストの色が実装の細部で決まってしまう。

**提案（いずれか 1 つを設計へ明記）**:
- ⒜ 範囲を構文で固定する: 「ページ URL の行の直後に始まる `pub const NAME: &[&str] = &[ … ];` の中の文字列リテラルだけ」。開始と終了が字面で決まるので実装が割れない。
- ⒝ 範囲を距離で固定する: 「ページ URL の行から、空行または次の項目宣言までの間に現れる文字列リテラル」。
- いずれでも、較正として `shiori_resource.rs` の 159 件が全件対応付くことを逐語で確かめるテストを 1 本置き、非空テスト（要件 6.13）にも「語彙表経路で解決した件数が 0 でない」を足すこと。

### 論点 2: `[ledger].pages` の突き合わせが判定の一覧に無い（要件 3.1・3.2・3.5）

**現状**: `assignment` の節は「台帳の `[ledger].pages` はこの表から書き出し、検査でも突き合わせる」と書いているが、`FindingKind` の 13 種にも `ledger::read` の検証項目（状態語彙・`alias_of`・テーマ・関連の種別）にも、`pages` の食い違いを拾う口が無い。`LedgerIdPageMismatch` の説明「id のページがその台帳の担当でない」も、担当の正本が `assignment` なのか `[ledger].pages` なのかを明示していない。

**影響**: 3.3a は前置きをバイト列のまま写すので、調査 spec が手書きした台帳の `pages` が古いまま（あるいは書き間違いのまま）永久に残り、誰も赤にしない。同じ値を 2 か所に持つ設計の利点（機械が一致を守る）が半分しか効いていない。

**提案**: `FindingKind` に `LedgerPagesMismatch`（`[ledger].pages` が `assignment::canonical()` の一覧と集合として一致しない）と `LedgerDomainMismatch`（`[ledger].domain` がファイル名と違う）を足し、`LedgerIdPageMismatch` の判定基準は `assignment` 側であると 1 行で明記する。判定は 3 行程度で書ける。

### 論点 3: ワークスペース全域の見張りテストは 3 本あり、設計は 1 本しか把握していない

**現状**: 設計は行数上限テスト（`file_length_guard_test.rs`）だけを「新クレートが即座に対象になる」ものとして挙げている。実際には同じ走査器を共有する見張りが**もう 2 本**ある。
- `crates/log-capture-kit/tests/temp_path_guard_test.rs`: `std::env::temp_dir` の呼び出しは、窓口クレートと例外表の外に 1 件も存在してはならない。
- `crates/log-capture-kit/tests/with_default_guard_test.rs`: 捕捉 API の直接呼び出し禁止、共有クレートを製品側依存に持たない、`env-filter` フィーチャ宣言は `wintf` だけ。

**影響**: 設計のテストはすべて見本データの文字列とファイル読み取りだけなので現状は抵触しない。ただし実装時に「台帳の書き出しを本物のファイルで確かめたい」と考えて一時ディレクトリを使うと、**例外表（既存クレートの中）への追記が必要になり要件 9.1（既存クレート非接触）が破れる**。設計の Boundary Commitments にこの制約が書かれていないと、実装フェーズで気付かず踏む可能性がある。

**提案**: 「新クレートのテストはファイルを 1 つも作らない（読むだけ・書き出しは文字列を返す関数として確かめる）」を設計の制約として 1 行で明記する。設計の 2 層構成はもともとこれを満たしているので、宣言するだけで足りる。

## 5. 設計の強み

1. **自前実装 3 件のすべてに「別の道具で確かめる」較正が用意されている**。ハッシュは公表テストベクタ、TOML の書き出しは `toml` での読み戻し一致（しかも実データの見出し 1,749 件全部）、塊の切り分けは `toml` が読んだ鍵集合との一致。「借りなかった理由」も 3 件とも実測にあり（謝辞の再生成 6 クレート分／凍結済み書式との食い違い／既存部品が `tests/` にあり用途が逆向き）、思い付きの自作になっていない。
2. **「ドメイン別報告はその台帳 1 本だけの純関数」という 1 つの決定で、要件 3.4（4 本の独立編集）と要件 7.4（報告の常時検査）の両立を成立させている**。証拠を報告に載せない判断まで含めて筋が通っており、調査 spec 4 本の編集集合が「自分の台帳＋自分の報告＋ソースの URL コメント」に閉じることが構造として保証される。要件の意図を写しただけでなく、両立の条件を言語化できている点が良い。

## 6. 軽微な気づき（任意対応・議論の材料）

- **調査 spec 4 本は今日から台帳を書けるか**: 書ける。付録 A（形式）と付録 B（id 一覧の取り出し手順）だけで足り、B の Python 例の `sorted()` は id が全件 ASCII なので道具側の byte 昇順と一致する。実際に 4 本とも現在 `brief.md` のみで未着手。なお付録 A.1 の記入例の id 2 本が実在しないことは設計 D-10 が注意として拾っており、README にも書く計画になっている（整合検査 6.3 が最終的な網になる）。
- **合流の手順が誰の担当か書かれていない**: 調査 spec が先に台帳を書き、後から toolkit が着地する（またはその逆）場合、rebase 後に `ledger-init` と報告の再生成をどの順で回すかが設計にも README の記載項目にも無い。要件 7.7 は報告の手 merge を禁じているので、台帳側の同じ手順（1 行）を README の目次に足すと、4 本の担当者が迷わない。
- **塊の切り分けの較正が「id の集合」比較である点**: 備考の複数行文字列の中に行頭 `[entry."…"]` が現れると切り分けが誤る。未知の id なら集合が食い違って失敗するが、既存 id と同じ綴りだと集合は一致してしまう。並び順の判定を**厳密な昇順**（同値も失敗）にしておけば重複として落ちるので、その一言を D-12 か `blocks` の節に足すと隙が無くなる。
- **`lib_test_support.rs` の共有範囲**: `structure.md:176` の作法は同じ stem のテーマ間の共有を想定している。ここでは `catalog/`・`ledger/` など別ディレクトリのテストからも参照する形になるため、`lib.rs` に `#[cfg(test)]` の接続宣言を置いて `crate::lib_test_support` で引く前提であることを 1 行添えると誤解が無い。
