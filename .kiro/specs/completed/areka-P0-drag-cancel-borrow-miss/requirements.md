# Requirements Document

## Project Description (Input)
まれな条件で、キャラクターやバルーンのドラッグを取り消しても位置が保存されず、その直後に動かさずにクリックすると 1 回だけ位置が保存される。条件は、wintf が画面更新の処理の最中（窓や部品の状態をまとめて更新している間）に、OS から同期で届いたメッセージ（再入）を受けたときで、実機ではまだ見ておらず、ソースを読んで確かめたもの。wintf のキー・取り消し系の 4 つのハンドラ（ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化）と、左ボタンを離したときのハンドラは、再入の最中だと wintf の ECS の世界（World）を使えず、ドラッグの終了の知らせの種を積まないまま、ドラッグの状態だけを休む状態へ移す。そのため、wndproc から ECS へ知らせを渡す箱（ドラッグの累積器）に「ドラッグ中の対象」が置き去りになり、(1) 閾値を越えたドラッグの取り消し・離しの終了の知らせが落ちる、(2) 次の動かさないクリックの終了の知らせが、`drag-click-without-move` で入れた「開始の知らせの無い終了は捨てる」判断を 1 回だけ通って位置が保存される、の 2 つが起こりうる。あわせて、左ボタンを離したときのハンドラは再入の最中だと「離した窓とドラッグの準備をしている窓の一致」を調べられず、ドラッグの準備の状態とマウスの捕捉が離した後も残り、その後ボタンを押さずに動かすとドラッグが始まりうる。再入の条件でも、取り消し・離しで「ドラッグ中の対象」が置き去りにならず、閾値を越えたドラッグの終わりは今どおり 1 件保存され、動かさないクリックはどの条件でも位置を保存しないようにする。1 フレーム遅らせる解は取らず、状態の持ち方を変えて 0 フレームで解き、直す前に赤になる決定論のテストを立てる。種別はバグ。

> 上の入力は起票時の筋。ギャップ分析（`research.md` §0）で前提の食い違いが見つかり、2026-10-04 の要件ディスカッション議題 1 の裁定（案 (b)＝本番の道を直す・境界を広げる）で、本書の Introduction 以下を書き直した。

## Introduction

ドラッグの知らせには、完了 spec が決めた 2 つの約束がある。

- ドラッグの終了の知らせは、開始の知らせを配ったドラッグにだけ配る（完了 spec `areka-P0-drag-click-without-move` 要件 3）。
- 閾値を越えたドラッグは、離しても取り消しても終了の知らせを 1 回配り、利用者から見ると取り消しでもその時点の位置が保存される（同 spec 要件 2.5・3.3、完了 spec `event-drag-system` 要件 4・5）。

起票時は「画面更新の最中に届いたメッセージを wintf のハンドラが受け取り、World を使えないので終了の知らせの種を積まずにドラッグの状態だけを進める」と見ていた。ところが本番では、窓のメッセージの入口（wintf の wndproc のクロージャ）が、World を借りられないときにハンドラを呼ぶ前にメッセージをまるごと捨てる（完了 spec `wintf-winmsg-executor` 要件 4.3 を実装した「安全スキップ」）。ハンドラの中の「World を借りられなかった枝」は、本番では通らない。

本番で実際に起こりうるのは次の形である（本書ではこれを「再入」と呼ぶ）。画面更新の最中に wintf が窓を作る・動かす・捕捉を手放すなどの OS 呼び出しをすると、OS はドラッグ中の窓へ「マウスの捕捉の喪失」「窓の非活性化」「メニューやダイアログの割り込み」を同期で送ってくることがある。そのメッセージは入口で捨てられ、ドラッグは終わらずに残る。

利用者から見える症状は次のとおり（実機では未観測・ソースを読んで確かめたもの）。

- 閾値を越えて動かしている最中に取り消しのメッセージが再入で届くと、ドラッグが終わらず、終了の知らせも配られず、その時点の位置が保存されない。ドラッグ中の印も窓に残る。
- 捕捉の喪失が捨てられると、その後に左ボタンを離した知らせは別の窓へ行き、ドラッグの状態は残ったままになる。その後ボタンを押さずにキャラクターの上を通るだけで、窓がカーソルに付いて動きうる。
- 閾値に届く前のドラッグの準備でも同じく状態とマウスの捕捉が残り、その後ボタンを押さずに動かして閾値を越えると、ドラッグが始まりうる。

本 spec は、ドラッグに関わるメッセージ（ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化・左ボタンを離す）だけは、再入で届いても入口で捨てずに、World を使わないドラッグの扱いを行わせることで、上の 2 つの約束を再入の条件でも守らせる。ESC キーと左ボタンを離すメッセージは、OS が同期で送るのではなく待ち行列を通るため、画面更新の最中にはまず届かない見込みだが、扱いを揃えるために 5 種とも含める（届くかどうかは設計で確かめる）。新しい約束は足さず、ドラッグの知らせの約束を定めた完了 spec の要件も上書きしない。入口の安全スキップは、ドラッグに関わる 5 種についてだけ扱いを変える（要件 1）。

brief は「閾値を越えたドラッグの取り消しは、この条件でも今どおり 1 件保存される（または、落とすならそれを決めて記録に残す）」としており、本書は主の案である「今どおり 1 件保存される」を採る。落とす案は、保存されない位置が利用者に見えて残るうえ、「状態の持ち方を変えて 0 フレームで解く」という制約で解けるため取らない。

## Boundary Context

- **In scope**:
  - wintf の窓のメッセージの入口が、World を借りられないときに、ドラッグに関わる 5 種のメッセージ（ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化・左ボタンを離す）を捨てずに、World を使わないドラッグの扱いへ渡すこと。
  - 上の 5 種を扱う wintf のハンドラ（キー・取り消し系の 4 つ・マウスのボタン）が、World を使えないときの、終了の知らせの種・「ドラッグ中の対象」・ドラッグの準備の状態・マウスの捕捉の扱い。
  - 決定論の自動テストと、ふつうの条件での振る舞いが変わっていないことの実機での確かめ。
- **Out of scope**:
  - ESC キー・メニューやダイアログの割り込みを受け取った窓と、ドラッグ中の窓の一致を確かめない件（完了 spec `areka-P0-drag-click-without-move` の調査で範囲の外と記したもの）。
  - ドラッグに関わる 5 種以外のメッセージの、再入のときの扱い（今どおり入口で捨てる）。左ボタンを押したとき・マウスを動かしたときのメッセージもここに入る（ドラッグの準備に入らない・閾値と比べない）。
  - ドラッグに関わる 5 種のメッセージの、ドラッグの扱い以外の処理（窓の非活性化のときの沈降の観測の目印など）の、再入のときの扱い（今どおり行わない）。
  - ドラッグの状態機械の移り変わり（押して準備 → 閾値で開始 → 離すか取り消しで休む）、ドラッグの閾値の値、ドラッグ中の窓とバルーンの追従。
  - areka のキャラクターとバルーンのドラッグの終了の受け手、位置の記憶の形式と保存先、受け手の縮退（開始時の記録が先に落ちたときの扱い）。
  - 触るのは wintf の窓のメッセージの入口（`crates/wintf/src/runtime/wndproc_bridge.rs`）と、`crates/wintf/src/ecs/` の下のハンドラ（キー・取り消し系、マウスのボタン）・ドラッグの部分・World を組み立てる所の 1 行と、それぞれのテストだけとする。入口まで広げたのは 2026-10-04 の議題 1 の裁定による（同じウェーブ C3 で wintf を触る他の spec は無い）。
- **Adjacent expectations**:
  - areka のキャラクターとバルーンのドラッグの終了の受け手は、wintf の終了の知らせを受けて位置を保存する。本 spec は受け手を変えず、受け手へ届く知らせを、再入の有無に関わらず同じにすることで、利用者から見た保存の振る舞いを揃える。
  - ドラッグの状態が離した後に休む決まり（完了 spec `areka-P0-wintf-drag-state-rest-contract`）と、右クリックメニューがドラッグの状態を読む作りは変えない。
  - 入口の安全スキップが守る「画面更新の最中のメッセージで、デッドロックや二重の画面更新を起こさない」（完了 spec `wintf-winmsg-executor` 要件 4.3）は、ドラッグに関わる 5 種についても守る。OS のセッションの終了の記録（同じ入口の `WM_ENDSESSION` の扱い）は変えない。
  - `areka-P0-mouse-drag-events`（同じウェーブ）は wintf の開始・終了の知らせを使う側で、本 spec の修正の後も知らせの約束は同じなので、互いに待たない。

## Requirements

### Requirement 1: 再入で届いたドラッグのメッセージを入口で捨てない

**Objective:** As a wintf を使う開発者, I want 画面更新の最中に届いたドラッグに関わるメッセージが、入口で捨てられずにドラッグの扱いを受けること, so that 再入のせいでドラッグが終わらずに残ることがない

#### Acceptance Criteria

1. When ドラッグに関わる 5 種のメッセージ（ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化・左ボタンを離す）のいずれかが、World を借りられない状態で窓のメッセージの入口に届いたとき, the wintf ドラッグ機能 shall そのメッセージを捨てずに、World を使わないドラッグの扱い（要件 2〜4）を行う。
2. The wintf ドラッグ機能 shall 前項の扱いを、画面更新の処理が握っている World の借用を待たず、横取りもせずに行い、デッドロックや二重の画面更新を起こさない。
3. When 前 1 項の扱いを行ったとき, the wintf ドラッグ機能 shall そのメッセージの、ドラッグの扱い以外の処理を、今どおり行わない。OS への戻り値と既定の手続きへの委ね方は、今の再入のとき（既定の手続きへ委ねる）と同じにする。
4. If 窓のメッセージの入口が、World を借りられない状態でドラッグに関わる 5 種以外のメッセージを受けたとき, then the wintf ドラッグ機能 shall 今どおり捨てる（OS のセッションの終了の記録も今どおり）。

### Requirement 2: 再入の条件でも、閾値を越えたドラッグの終わりを落とさない

**Objective:** As a wintf を使う開発者, I want 閾値を越えたドラッグの取り消しや離しが再入で届いても、ふつうと同じ終了の知らせが届くこと, so that 終了の受け手がドラッグの終わりを取りこぼさず、窓をドラッグ中のまま扱い続けない

#### Acceptance Criteria

1. When 閾値を越えたドラッグ（開始の知らせを配ったもの）が ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化のいずれかで取り消され、そのメッセージが再入で届いたとき, the wintf ドラッグ機能 shall ドラッグの状態を休む状態へ移し、マウスの捕捉を解放し、取り消しの印つきの終了の知らせを 1 回配る。
2. When 閾値を越えたドラッグで、ドラッグしている窓の上で左ボタンが離され、そのメッセージが再入で届いたとき, the wintf ドラッグ機能 shall ドラッグの状態を休む状態へ移し、マウスの捕捉を解放し、取り消しの印の無い終了の知らせを 1 回配る。
3. The wintf ドラッグ機能 shall 前 2 項の終了の知らせの中身（対象・位置・取り消しの印）を、同じ操作が再入でなく届いた場合と同じにする。位置は画面の座標とし、窓の中の座標と取り違えない。
4. The wintf ドラッグ機能 shall 前 2 項の終了の知らせを、同じ操作が再入でなく届いた場合と比べて遅らせずに配る（画面更新を 1 回余計に待たない）。
5. When 前 2 項の終了の知らせを配ったとき, the wintf ドラッグ機能 shall 再入でない場合と同じく、ドラッグ中の印（ドラッグの対象と、それを含む窓に付くもの）を外し、以後その窓をドラッグ中として扱わない。

### Requirement 3: 再入の後も、開始の知らせの無いドラッグには終了の知らせを配らない

**Objective:** As a wintf を使う開発者, I want 再入の後の動かさないクリックや取り消しが、終了の知らせを生まないこと, so that 終了の受け手が「本当にドラッグしたか」を自分で見分けなくてよい

#### Acceptance Criteria

1. When 再入で届いた取り消しまたは離しでドラッグが終わった後、利用者が左ボタンを押して閾値に届かないまま離したとき, the wintf ドラッグ機能 shall ドラッグの終了の知らせを配らない。
2. If 閾値に届く前のドラッグの準備が、ESC キー・メニューやダイアログの割り込み・マウスの捕捉の喪失・窓の非活性化のいずれかで取り消され、そのメッセージが再入で届いたとき, then the wintf ドラッグ機能 shall ドラッグの状態を休む状態へ移してマウスの捕捉を解放し、ドラッグの終了の知らせ（取り消しの印つきのものを含む）を配らない。
3. When 再入で届いた取り消しまたは離しでドラッグが終わった後、利用者が次に閾値を越えてドラッグして離したとき, the wintf ドラッグ機能 shall 開始の知らせを先に、終了の知らせを後に、どちらも 1 回ずつ、その新しいドラッグの対象について配る。

### Requirement 4: 離した後に、ドラッグの準備とマウスの捕捉を残さない

**Objective:** As a areka の利用者, I want ボタンを離した後や捕捉を失った後は、どの条件でもドラッグが終わっていること, so that ボタンを押していないのに窓がカーソルに付いて動かない

#### Acceptance Criteria

1. When 閾値に届く前のドラッグの準備中、または閾値に届いた直後でまだ一度も動かしていないときに、ドラッグの準備をしている窓の上で左ボタンが離され、そのメッセージが再入で届いたとき, the wintf ドラッグ機能 shall 再入でない場合と同じく、ドラッグの状態を休む状態へ移し、マウスの捕捉を解放する。
2. If 左ボタンを離した窓が、ドラッグの準備またはドラッグをしている窓と違うとき, then the wintf ドラッグ機能 shall 再入の有無に関わらず、今の窓の一致の判断どおりそのドラッグを終えない。
3. While 左ボタンが押されていないとき, the wintf ドラッグ機能 shall マウスを動かしてもドラッグを始めず、開始の知らせを配らず、窓を動かさない（再入で届いた取り消しや離しの後も同じ）。

### Requirement 5: 利用者から見た位置の保存を、再入の有無で変えない

**Objective:** As a areka の利用者, I want まれな条件でも、動かした位置は今どおり保存され、動かさないクリックでは保存されないこと, so that 次の起動で、意図して動かした窓が戻らず、意図せず動いた窓も残らない

#### Acceptance Criteria

1. When 利用者がキャラクターまたはバルーンを閾値を越えて動かした後に ESC キーなどで取り消し、その取り消しが再入で届いたとき, the areka shall 再入でない場合と同じく、その時点の位置を記憶へ 1 件書く。
2. When 利用者がキャラクターまたはバルーンを閾値を越えて動かして離し、その離しが再入で届いたとき, the areka shall 再入でない場合と同じ最終位置へ窓を置き、その位置を記憶へ 1 件書く。
3. When 前 2 項のいずれかの後に、利用者がキャラクターまたはバルーンを動かさずにクリックしたとき, the areka shall 窓の位置とバルーンの相対位置を記憶へ書かない（位置の保存の記録は 0 件）。

### Requirement 6: ふつうの条件での振る舞いを変えない

**Objective:** As a wintf を使う開発者, I want 再入でない、ふつうの条件での知らせとドラッグの振る舞いが修正の前と同じであること, so that 修正がまれな条件の穴埋めにとどまり、ふだんの操作に影響しない

#### Acceptance Criteria

1. The wintf ドラッグ機能 shall 再入でない条件での開始・終了の知らせの配り方（配るかどうか・中身・順・時機）を、本 spec の修正によって変えない。
2. The wintf ドラッグ機能 shall 再入でない条件での、ドラッグの状態の移り変わり、ドラッグの閾値の値、ドラッグ中の窓とバルーンの追従、離したときと取り消したときのマウスの捕捉の解放を、本 spec の修正によって変えない。
3. The wintf ドラッグ機能 shall 左ボタンを押したとき・マウスを動かしたときのメッセージが再入で届いた場合の今の扱い（入口で捨てる＝ドラッグの準備に入らない・閾値と比べない）を、本 spec の修正によって変えない。

### Requirement 7: 再入でドラッグの扱いをしたことを黙って流さない

**Objective:** As a 開発チーム, I want 再入のために World を使わずにドラッグの扱いをしたことと、そのとき読めなかった情報が記録に残ること, so that 実機で再入が起きたとき、記録から気付ける

#### Acceptance Criteria

1. When 要件 1.1 の扱いを行ったとき, the wintf ドラッグ機能 shall メッセージの種類・ドラッグの対象・行った扱い（終えた・取り消した・何もしなかった）を記録に 1 行残す。
2. If 要件 1.1 の扱いの中で、ドラッグの扱いに要る情報（窓の位置・窓の一致など）を読めなかったとき, then the wintf ドラッグ機能 shall 何を読めなかったかを記録に残し、黙って先へ進まない。

### Requirement 8: 検証

**Objective:** As a 開発チーム, I want 穴が塞がったことと、ふつうの条件の振る舞いが崩れていないことを、本番がたどる道の決定論のテストで示すこと, so that 同じ穴が再び入り込めば赤で気付ける

#### Acceptance Criteria

1. The 開発チーム shall 再入の状態（World を借用したまま）を作り、本番の窓のメッセージの入口（wndproc のクロージャ）からメッセージを渡し、本物の知らせを配る段を回す形の決定論の自動テストで、要件 1.1・2.1（4 種の取り消しのそれぞれ）・2.2・2.3・2.5・3.2・4.1・4.3 を確かめ、それらが修正の前に失敗し、修正の後に通ることを確かめる。ハンドラを入口を通さずに直に呼ぶテストは、本書の要件の証拠にしない。
2. The 開発チーム shall 同じ形の決定論の自動テストで、要件 1.4・3.1・3.3・4.2 を確かめ、それらの修正の前後での結果を記録する（修正の前から通るものは、前後とも通ることを確かめる）。
3. The 開発チーム shall 要件 2.4 を、再入で届いたメッセージの終了の知らせが、再入でない場合と同じ回の知らせを配る段で配られることとして、決定論の自動テストで確かめる。
4. The 開発チーム shall 要件 6.1〜6.3 と要件 1.2・1.3 が崩れていないことを、既存または新しい決定論の自動テスト（完了 spec `areka-P0-drag-click-without-move`・`event-drag-system`・`wintf-winmsg-executor` のテストを含む）で確かめる。入口の安全スキップのテストのうち、ドラッグに関わる 5 種の扱いが変わることで主張が変わるものは、本書に合わせて書き換え、5 種以外のメッセージの安全スキップの主張は保つ。要件 5 は、要件 2・3 の終了の知らせのテストと、areka のキャラクターとバルーンのドラッグの終了の受け手の既存のテスト（終了の知らせ 1 件で保存 1 件・知らせ 0 件で保存 0 件）を合わせて確かめる。
5. The 開発チーム shall 前各項のテストを、注入した入力と画面更新の並びで駆動し、実時間の待機に依存させない。新しいテストは本番ファイルの兄弟ファイルへ置き、本番ファイル・テストファイルのどれも 1,000 行以下に保つ。
6. The 開発チーム shall 再入の条件そのものは実機で狙って起こせないため、その証拠を前各項の決定論のテストとし、実機ではふつうの条件で、閾値を越えたドラッグで保存 1 件、動かさないクリックで保存 0 件、閾値を越えた後の ESC キーの取り消しで今どおりの保存になることを確かめる。このとき記録の level を、位置の保存・ドラッグの終了の知らせ・要件 7 の記録まで開け、実機の根と一時フォルダはワークツリーの `target\` の下だけに置く。
7. Where 本 spec の修正が完了 spec の要件と食い違うことが判ったとき, the 開発チーム shall その上書きを `doc/COMPAT_ARCHITECTURE.md` §8 へ記録し、完了 spec のアーカイブ本体は書き換えない。入口の安全スキップの扱いを 5 種について変えたことは、入口のソースの説明（安全スキップの規律の節）にも書く。
8. When 本 spec の完了を判定するとき, the 開発チーム shall ワークスペース全体のテストが緑であることを確かめる。
