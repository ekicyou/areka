# 設計の検証: wintf-visual-damage-redraw

> 2026-11-14・`/kiro-validate-design`（非対話）・対象は `design.md`（2026-11-14 生成）・基準は作業ブランチ `claude/kiro-start-wintf-visual-damage-redraw-29b21f`。読むだけで、テストも計測も回していない。

## 設計の検証の要約

純粋な計算（比べの項・比べ・合成の計画）と D2D の手順（範囲版の合成・平行移動の写し）を分け、不変条件 I1（控えが在るとき入れ物の画素は前の描く列を毎回全部描いた答えとバイトで同じ）を軸に、決められない回は 7 種の理由で全部の合成へ倒す、という作りで、要件 1〜7 のすべての項に部品と口が対応している。コードと突き合わせた主張（`Clear` は軸に沿う切り抜きに従う・同じ入れ物の中の写しは使えない・写しは `BeginDraw` の前・入れ物を捨てる道が控えも捨てる・完了 spec の Revalidation Triggers が本 spec を名指ししている）はどれも正しい。残る論点は、作業用の絵の扱い・実 GPU での答えの一致・平行移動の写しが効く木の形の 3 つで、どれも設計の討議で決めれば直せる。

## 確かめたこと（Analysis）

- **既存の作りとの整合**: `render_surface`（`systems/render.rs`）は `Changed<SurfaceGraphicsDirty>` の描画面だけを回し、入れ物は `set_surface`・`clear`・大きさの違い・`compose_or_drop` の失敗で捨てられる（`components.rs:235-256`・`render.rs:141-161`・`composite.rs:71-86`）。控えを `SurfaceComposite` に持たせれば、捨てる道がそのまま 3.1・3.3・4.3 になる、という設計の読みは正しい。WUC の `BeginDraw` の失敗（失いでない）は今 `request_redraw` だけで入れ物を残すので、`presented = false` から次の回に `PresentOnly` で写す（2.8）道も今の作りと噛み合う。
- **完了 spec の Revalidation Triggers**: `wintf-d2d-composite-rules` は「`DrawItem` の欄・`DrawCommand` の命令の増減（`wintf-visual-damage-redraw` が列を読む）」、`wintf-visual-tree` は「`DrawCommand`／`DrawItem` の欄 … → `wintf-visual-damage-redraw`」を挙げており、本 spec が欄を足す持ち主であることと合う。命令の構造体を字面で作る所は `builder.rs`・`emit_blend_tests.rs`・`emit_layer_tests.rs` だけで、Modified Files に全部載っている（ほかのクレートからの字面の構築は 0）。
- **D2D の制約**: `emit` は層をどれも恒等の変換で `outward_physical`（整数へ外向きに丸めた矩形）に積み、矩形の切り抜きは `PER_PRIMITIVE` で積む（`emit.rs`）。描く矩形の切り抜きを恒等の変換・整数の物理ピクセル・`PER_PRIMITIVE` で外側に積む設計は、旗の混在を避けており、層の範囲（`bounds`＝`exact` の外向きの丸め）とも一致する。入れ物は `D2D1_BITMAP_OPTIONS_TARGET` の B8G8R8A8・α 掛け済み（`composite.rs:51-67`）で、作業用の絵を同じ形式・`OPTIONS_NONE` で作り `CopyFromBitmap` で 2 度写す手順は形式の一致の条件を満たす。
- **比べの正しさ**: 件の同一性は `hash_draw`（実体・版・補間・混ぜ方・世界の行列）に親の層の鎖を足したもので、描く中身の差し替えは `fill_world_visuals` の版の上がり（`Visual` か描く中身の変化）で拾える。同じ `id` の対は前と今で `bounds` が同じになるので、動いた件を今の `bounds` だけで数えてもよい。並びの入れ替わった対の少なくとも片方は最長増加部分列の外に出るので、動いた件の範囲の和が入れ替わりの重なりを必ず覆う。
- **C20 の約束**: crate を足さない（最長増加部分列は std で自前）・記録は新しい target `wintf::damage` の `debug!` の別の行で `[tick]`・`perf(…)` の文言と欄に触れない・`tools/perf/` は Modified Files に無い。`tools/perf/` の `RUST_LOG` の既定（`info,…,areka_emo_present=debug` ほか）は `wintf::damage` を含まないので、計測の走行に新しい行は出ない。
- **決まりごと**: 1,000 行（今の最大は `builder_tests.rs` 642 行・`composite.rs` 243 行・`render.rs` 239 行で余裕がある）・兄弟の `*_tests.rs`（`composite_tests` と同じく `graphics/mod.rs` で宣言・`diff_tests` は `draw/mod.rs`）・1 フレーム遅らせない（範囲だけの描き直しは同じ回・写しの失敗の後の `PresentOnly` は今の失敗の道の次の回）・黙った失敗の道を作らない（D2D の失敗は `compose_or_drop` → `on_stage_failure` の `error!`、全部へ倒すのは失敗でなく理由つきの記録）のどれにも外れていない。ただし `damage_tests.rs`（理由 7 種＋S1〜S9 の 1 つずつの外し）と `composite_damage_tests.rs`（15 種前後 × 拡大 2 つ）は 1,000 行に近づきうるので、タスクの段で分け方を決めておくとよい。

## 重大な指摘

### 重大な指摘 1: 平行移動の写しの作業用の絵が、完了 spec の「入れ物で増えるメモリは 1 枚分まで」と毎回の確保の費用の両方に当たる

- **懸念**: 写しの回ごとに `R_in` の大きさ（描画面の全面に近いこともある）の作業用の絵を `CreateBitmap` で作って捨てる（決め D6）。`wintf-d2d-composite-rules` 要件 4.3 は「入れ物で増えるメモリは描画面と同じ大きさの 1 枚分まで」と書いており、一時の分を数えるかは書かれていない。設計自身も research.md §10.4 の 1 で開発者に確かめる点として残している。加えて、スクロールが続くあいだは毎フレーム GPU のテクスチャの確保と解放が走る。
- **影響**: 開発者が「一時の分も数える」と答えれば D6 の作りが崩れ、`compose_partial` の手順と Revalidation Triggers が変わる。数えないとしても、毎フレームの確保が写しで浮かせた描き直しの費用を食う恐れがあり、効きを記録（`compose_us`）で見るまで分からない。
- **提案**: 設計の討議で次のどれかに決める。(a) 一時の分は 4.3 の外とみなし、その旨を design の Boundary Commitments に書く。(b) 作業用の絵を決まった高さの帯（例: 幅×64 行）にして、写す順を移動の向きで決め（上へ動くなら上から）、帯ごとに 2 度写す。一時の分が小さく抑えられ、4.3 との衝突が無くなる。(c) 作業用の絵を入れ物と同じ寿命で持つ（4.3 の改めが要る）。推すのは (b)。どれを取っても、確保の費用は `compose_us` で見られるようにしておく。
- **関わる要件**: 5.1・5.4（あわせて `wintf-d2d-composite-rules` 4.3）
- **根拠**: design.md「SurfaceComposite」の `compose_partial` の手順 (1)・「Supporting References」の D6・「Performance & Scalability」の 3 つ目、research.md §10.1 R4 と §10.4 の 1

### 重大な指摘 2: 範囲だけの描き直しと平行移動の写しが全部の答えとバイトで一致することを、実 GPU で確かめる段が無い

- **懸念**: 要件 2.4 は「ずれは欠陥」とし、設計はバイトの一致を WARP のテスト（7.3）だけで固める。実 GPU のテスト（7.5）は「節を 1 つ動かした回の画素が今の答えになる」「変えない回は前のまま」を見るだけで、範囲だけの道の答えと全部の道の答えを比べない。平行移動の写しは「f32 の物理の行列で原点の差が整数なら、写した絵と描き直した絵が同じ」に頼っており（R5）、座標の大きさが違う所で頂点の位置を f32 で計算し直す実 GPU では、WARP と違う丸めになりうる。範囲だけの道を通ったときの切り抜きの有無で描き分けが変わる場合も同じ。
- **影響**: 差分の描き直しは誤りを次の全部の合成まで入れ物に残し続ける（自分では直らない）。実機でだけ 1 段の差が出ると、範囲の縁や写しの帯の境に消えない線が残り、WARP のテストは緑のまま見逃す。
- **提案**: `tests/graphics/composite_systems_test.rs` に、実 GPU で同じ最後の木を「前の木を全部描いてから範囲だけで描き直した描画面」と「初めから全部描いた描画面」の 2 枚に作り、`CopySurface` で読んだ画素をバイトで比べる件を足す（小数の位置の `LINEAR` の件・矩形の縁をまたぐ不透明度の層・拡大 1.25 で整数になる平行移動の写しの 3 つ）。ずれたら R1・R5 の決めどおり、その組み合わせを全部へ倒すか条件を狭める（テストは緩めない）。7.5 の文言の範囲（入れ物を通した描画面が画面に出ることを実 GPU で確かめる）に収まる足し方なので、要件は変わらない。
- **関わる要件**: 2.4・5.1・7.3・7.5
- **根拠**: design.md「Testing Strategy」の E2E Tests・「Risks」の R1 と R5・「ScrollCheck」の R5 の決め

### 重大な指摘 3: 平行移動の写しが効く木の形が狭く、下に背景の絵がある普通のスクロールでは使われない

- **懸念**: 写してよい条件の S1（根の命令の列を持たない）と S8（部分木の外の項が `R_out` と交わらない）により、スクロールする切り抜きの下に背景の件（描画面の持ち主の描く中身や、背景の節）が 1 つでもあれば写しは使われず、普通の範囲の描き直しになる。描画面に描く普通のスクロールの区画は背景の上に置くことが多く、条件を満たすのは「スクロールする区画が自分の描画面を持ち、その描画面にほかの絵が無い」形だけになる。要件の討議の議題 1 は「どうせすぐ開発することになる」として写しを入れたので、最初の使い手の木がこの形に当たるかで、要件 5 の作りが効くかが決まる。設計自身も research.md §10.4 の 3 で確かめる点に挙げている。
- **影響**: 使い手の木の形に条件が合わなければ、S1〜S9 の判定と作業用の絵の写しは使われない作りとして残り、テストの手間だけがかかる。後の spec が条件を広げようとすると、I1 の根拠（下に重なる絵が無い）から組み直しになる。
- **提案**: 設計の討議で、条件はこのまま（答えを崩さない側）とし、写しが効く木の形（スクロールする区画を `OwnSurface` で自分の描画面にし、背景は下の描画面に置く・その描画面は根の命令の列を持たない）を `draw/README.md` と `VisualDrawContent` の文書に書くことを決める。あわせて、最初の使い手になる見込みの spec（例: `balloon-scroll-fade`）の木がこの形を取れるかを 1 行で確かめ、取れないなら写しを使い手が出るまで据え置く（要件 5.2 の道だけを使う）かを開発者に仰ぐ。
- **関わる要件**: 5.1・5.2
- **根拠**: design.md「ScrollCheck」の S1 と S8・「Supporting References」の D8、research.md §10.4 の 3

## 設計の強み

- **純粋な計算と D2D の手順の分け方**: 比べの項（`DamageEntry`）は COM を持たず、鍵と範囲の規則を素の値を受ける小さな関数に置くので、比べ・計画・理由 7 種・S1〜S9 のすべてを GPU 無しのテストで固められる。不変条件 I1 と、それが範囲だけの描き直しで保たれる理由（描く矩形の外の画素に効く項は全部動かなかった項）が文書に書かれており、テストの的がはっきりしている。
- **今の道をそのまま使う作り**: 全部の合成（`compose`）を毎回全部描いた答えの作りとして残し、失敗の道（`compose_or_drop`・`on_stage_failure`）と世代の数え方と読み戻しの控えを変えない。控えを入れ物と同じ寿命にしたので、入れ物を捨てるどの道でも次の回は理由つきの全部の合成になり、黙って古い答えを出す道が生まれない。

## 最終の判定

- **判定: GO**
- **理由**: 既存の作り・完了 spec の境・C20 の約束と食い違う所は無く、要件のすべての項に実装の道がある。3 つの指摘は作業用の絵の持ち方・実 GPU のテストの足し方・写しの使い方の書き方の決めで、設計の骨格（項・比べ・計画・範囲版の合成）を変えずに設計の討議で直せる。
