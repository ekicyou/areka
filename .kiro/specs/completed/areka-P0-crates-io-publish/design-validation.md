## 検証の要約

設計は、実物のファイルとよく合っている。30 クレートの `publish` の行、`wintf`・`dola` の依存の行、`tools/test-all.ps1` の段の足し方、`.github/` が無いこと、README の Status 節の文は、設計の「今の状態」の記述どおりだった。要件 1.1〜5.6 の 45 項目は、どれも具体の部品（スクリプトの判定・workflow の段・手順書の節・文書の節）に落ちており、表に並ぶだけで受け手のいない要件は見つからなかった。

直すべき点は 2 つで、どちらも設計の骨組みは変えずに文と小さな選択で片づく。判定は **GO**（議題 2 件を設計討議で決めてからタスクへ進む）。

## 重要な指摘（2 件）

### 指摘 1: 全体テストの新しい段はネットが要る。「新しい前提ではない」という設計の説明は事実と違い、`tech.md` の決めごととも食い違う

- **懸念**: 設計は「全体テストは既に `rustup target add` と cargo の取得でネットを使うので、新しい前提ではない」と書く。実測では、ネットを塞いだ状態（届かない代理サーバーを指定）で次のとおりだった。
  - `rustup target add i686-pc-windows-msvc`（導入済み）: 終了コード 0（「up to date」・ネットを使わない）。
  - `cargo metadata --locked`（依存は取得済み）: 終了コード 0。
  - `cargo publish --dry-run --no-verify --allow-dirty --locked -p dola`: **終了コード 101**（「failed to update registry `crates-io`」）。
  つまり、今の全体テストは一度そろえた手元ではネットなしで緑になり、新しい段だけがネットを必要とする。`tech.md` の Testing 節には「ネットへ出るテストは常時テストに入れない」とある。
- **影響**: ネットが切れているとき・crates.io の索引が落ちているときに、コードに問題が無くても全体テストが赤になる。`kiro-complete` は全体テストの緑を完了の門にしているので、ほかの spec の完了が crates.io の都合で止まりうる。設計が `tech.md` の Testing 節に触らないと決めているため、決めごとと実物が食い違ったまま残る。
- **提案**（設計討議でどちらかを選ぶ）:
  - (a) ネットが要ることを受け入れる。設計の該当の文を事実に合わせて改め、`tech.md` に足す新しい節「crates.io への公開」に「全体テストのこの段だけは crates.io の索引を読む」と書く（Testing 節の文との関係も 1 行で示す）。
  - (b) 全体テストの包むだけの形は索引を読まない形にする。実測で `cargo package --no-verify --allow-dirty --locked --offline -p dola -p wintf` は、設計の変更を当てた写しで、ネットを塞いでも終了コード 0 で 2 クレートを包めた（`.crate` も出る＝大きさの判定はそのまま使える）。この形では「その版は既に在る」の警告（要件 2.10）が出ないので、既に在ることの表示は `-Verify` の形（手順書・公開の段）に任せるか、要件 2.11 の包むだけの形の範囲から 2.10 を外す読み替えが要る。
- **対応する要件**: 2.10・2.11・2.12（全体テストの段）・5.4（決めごと）。steering: `tech.md` Testing 節「ネットへ出るテストは常時テストに入れない」。
- **設計の該当箇所**: 「Components and Interfaces › 全体テストの段」・「確認スクリプト › Dependencies」（索引は `-Pending` のときだけ、と書いているが、cargo 自身が包むときに索引を読む）・「Modified Files」の `tech.md` の行。

### 指摘 2: 「main で直して同じ版で起動し直せる」は workflow のファイルにしか当たらない。スクリプトの誤りと「記録」の段の赤の扱いが書かれていない

- **懸念**: 決定 6 は「初回で誤りがあっても何も上がらずに止まり、main で直してから同じ版で手で起動し直せる」とする。一方で設計は「既定の枝の workflow のファイルが使われ、コードとスクリプトはタグのコミットの物が使われる」とも書く。したがって、
  - `crates-io.yml` の誤りは main で直せば効く。
  - `tools/crates-io.ps1` の誤り（ランナーでだけ出る物を含む）は、タグのコミットに固定されているので main で直しても効かない。同じ版では公開の段を通せず、予備の手順（手元から出す）か次の版で出すしかない。
  - 判定「公開の段の形」（要件 4.2・4.6）が公開の段の中で見るのはタグのコミットの `crates-io.yml` の写しで、実際に動いている main の物ではない（main の物は全体テストが見張るので穴ではないが、設計に書かれていない）。
  - 「記録」の段は「必ず走る」とあるが、取り出しより前（版の形・タグが無い）で止まった回はスクリプトがまだ無い。また、上げた直後に索引の反映が遅れると、上がっているのに「残りあり」で赤になる。設計は反映の遅れを「やり直しのとき」の危うさとしてしか書いていない。
- **影響**: 公開の段は本 spec の中で一度も走らせられず、初めての実走が本番の `v0.0.2` になる（設計も認めている）。その場で止まったとき、開発者は「main で直せば同じ版で出せる」と読んで時間を使うおそれがある。`release-cycle` の brief は「赤なら同じ版で再実行しない」と書いており、公開の段のやり直し（要件 3.3・4.8）との使い分けも手順書で示す必要がある。
- **提案**: 骨組みは変えない。決定 6 と手順書の「止まったときのやり直し」に、次の切り分けを書く。
  - workflow のファイルの誤り → main で直して同じ版で起動し直す。
  - スクリプトの誤り → 同じ版は予備の手順で出す（要件 3.5）。直したスクリプトは次の版から効く。
  - 「記録」の段だけが赤で、公開の段が緑だった回 → 索引の反映待ち。時間を置いて `-Pending` を手元で走らせる（要件 3.4）か、同じ版で起動し直す（残りが 0 なら何も上げずに緑で終わる）。
  - 「記録」の段は、スクリプトが取り出せていない回では「取り出しより前で止まった・何も上げていない」とだけ書く。
- **対応する要件**: 3.3・3.4・3.5・4.8・4.9。
- **設計の該当箇所**: 「設計の決定 › 決定 6」・「公開の段 › Implementation Notes」・「System Flows › 公開の段」の「記録」・「手順書 › 5. 止まったときのやり直し」。

## 精査した点と結果（指摘にしなかったもの）

- **`cargo publish --no-verify` で上げること（決定 5）**: 妥当。同じ取り出し・同じコミット・`--locked` で、直前の段が組み立てまで確かめている。本番の `cargo publish` には `--allow-dirty` を付けない設計なので、取り出しが汚れていれば cargo が上げる前に止める。2 クレートを 1 回で出す形は、cargo が `dola` の索引への反映を待ってから `wintf` を上げる。鍵の期限（30 分ほど）にも余裕がある。
- **既に在るクレートの検出と飛ばし方**: 索引を読んで `vers` を比べる方式は要件 4.5・4.8 を満たす。反映の遅れで「まだ無い」と読んでも、cargo が「既に在る」で上げずに止まるので安全な側に倒れる。
- **途中まで上がった回のやり直し（`dola` は出た・`wintf` は落ちた）**: 設計の変更を当てた写しで、`dola` 0.0.1 が実際に crates.io に在る状態のまま `cargo publish --dry-run --no-verify --allow-dirty --locked -p wintf`（`wintf` だけ）を走らせ、終了コード 0 を確かめた（実測）。`wintf` だけを包む経路は `--locked` でも通る。本番の上げる動作そのものは試せない（設計の「試せないもの」と同じ）。
- **根の `Cargo.toml` と各クレートの記述**: `[workspace.package] publish = false` を受け継ぐクレートは 0（30 本とも自分の行を持つ）。`wintf` の版の指定を持つのは `areka`・`areka-emo-present`・`areka-emo-text` の 3 行、`pilot` は版の指定なし。設計の記述どおり。`deny.toml` は `allow-wildcard-paths = true` なので、版の指定を外しても `cargo deny check` の扱いは変わらない。
- **隣の spec との取り決め**: `release-ci-workflow` の brief に、Release の公開の後に `gh workflow run crates-io.yml -f version={版}` で呼ぶこと・`actions: write` を足すことが既に書かれている。入力の名前 `version` も一致。
- **タスクへ渡す覚え書き（設計の変更は要らない）**:
  - 判定「公開の段の形」は `secrets.` の参照を禁じる。`gh release view` に渡す鍵は `secrets.GITHUB_TOKEN` でなく `github.token` と書く必要がある。
  - `-Pending` と `-Version` を一緒に渡したときの意味（版の不一致で失敗させるのか）を、スクリプトの実装で 1 行に決める。

## 設計の良い点

- **自分で書く判定を、cargo が見ない物だけに絞っている**。版の指定の漏れ・不一致・依存の順・仮の置き場は cargo に任せ、一覧・欄・理由・大きさ・版・残りだけを自前で判定する。その判定を正しい見本と誤った見本で毎回確かめる作り（較正の内蔵）は、道具が壊れたまま緑を出すことを防ぐ。
- **版上げで動く行を根の 2 行に閉じた（決定 1・2）**。出さない 3 クレートの版の指定を外すことで、`release-cycle` の手順が単純になり、動かし忘れは cargo が即座に止める。隣の spec への申し送りも具体の文で書かれている。
