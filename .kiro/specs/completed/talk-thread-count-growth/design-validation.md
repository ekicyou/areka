# 設計の検証: talk-thread-count-growth

- 対象: `design.md`（2026-11-27 生成）・`requirements.md`・`research.md`
- 手順: `kiro-validate-design`（分析 → 重大な指摘 → 良い点 → GO／NO-GO）。非対話で実行。
- 実物で確かめたこと: `thread_registry.rs` とそのテスト、`api.rs` の複製と `get_thread_times`、`perf_thread_report.rs`（`take_and_emit`・`delta` の呼び手）、名簿の呼び手 5 か所（`runtime/mod.rs`・`tick_bridge.rs`・`clickthrough/monitor.rs`・`thread_roles.rs`・`perf_thread_report.rs`）と `snapshot()` の呼び手、`areka-actor` の `spawn_actor` のフックの走る場所、`perf-rank.py` の段②と検体、`judge-perf.py` の行の読み方。

## 設計の検証の要約

既存の「登録による名簿」をそのまま広げ、掃除・畳み・読み出しを 1 つの錠の中に集める作りで、依存も機能も足さず、要件 2〜5 を筋よく満たしている。系統の合計の差で区間を取る規則（D5）は、今の検体 4 つで今の出力と同じ値になることを手元で確かめた。直すべきは、消灯時の積み上がりを固定するテスト（7.6）が共有の名簿の上では決定的に赤にならない点と、実機の数え直し（7.8）の「終わったトークの数」の数え方が決まっていない点の 2 つで、どちらも設計の中で小さく直せる。

## 確かめた事実

- **段②の区間の差（D5）と古いログ（5.3）**: 自己テストは今のまま `SELFTEST RESULT ok=22 ng=0`。`full_ok`・`tid_reused`・`talk_threads_folded`・`thread_missing_cpu_us` の `run.log` に、系統の合計の差 `max(F(後) − F(前), 0)`（系統＝`^(.+)-[0-9]+$` → `\1-*`）を当てた写しを別に組んで計算し、役割別の値は 4 つとも今の `thread_delta`＋D8 の結果と同じだった（`tid_reused` は TID 100 の前後が同じ系統 `actor:sakura-talk-*` に入るので 0 に止まり、名簿外の残りは今と同じく 2.000）。設計の「期待の出力は変わらない見込み」は検体の上で成り立つ。
- **錠の中の仕事と順序（D3）**: 錠の中で呼ぶのは `WaitForSingleObject(h, 0)` と `GetThreadTimes` だけで、どちらも利用者の錠を取らない。`ThreadEntry::cpu_times` は `api` を呼ぶだけで名簿の錠を取り直さない。今の作りで錠の取り直しによる死に錠は起こらない（外の錠と絡むのは錠の中の `warn!` だけ・下の小さな指摘 1）。
- **刻みの経路に入らないか（2.5）**: `register_current_thread` の呼び手は、UI スレッドの `WinApp::with_exit_policy` の 1 度、vblank・カーソル監視・報告器のスレッドの走り始め、アクターの走り始めのフック（`spawn_actor` は新しいスレッドの中でフックを呼び、呼び手へはすぐ返る）だけ。本番で `snapshot()` を呼ぶのは報告器だけ。UI スレッドと描画の刻みは錠を待たない。
- **Rust の `delta`（D6）**: 本番の呼び手は無い（`perf_thread_report_tests.rs` だけ）。消してよい。
- **`judge-perf.py`（5.4）**: `perf(thread)`／`perf(process)` は行の印の文字列で数えるだけで、欄の集合を照らさない。`exited=` を足しても止まらない。
- **TID の使い回し（R1）**: 名簿が複製したハンドルを持つ間は OS がその TID を使い回さない前提で、本物のスレッドでは 3.4 が起こらず、偽の芯で固定する設計は妥当。`snapshot()` の複写が `Arc` でハンドルを持つ間も使い回しが遅れるだけで、害は無い。

## 重大な指摘

🔴 **重大な指摘 1**: 消灯時の積み上がり（7.6）のテストが共有の名簿では決定的に赤にならない
**懸念**: 7.6 のテストは本物の名簿（プロセス共有）で「読み出しを 1 度も呼ばずに」登録と終わりを繰り返すが、同じテストの実行体の中では `tick_bridge.rs`・`monitor.rs`・`runtime/mod.rs` のテストが `snapshot()` を 5ms ごとに呼び、他のテストも `register_current_thread` を呼ぶ。どちらも掃除を走らせるので、「登録の時点の掃除」（2.2 の芯）を外した誤りの実装でも、たまたま他のテストの掃除が間に入れば緑になりうる。
**影響**: 2.2 は本 spec の不具合の本体（報告器が消えた既定の運転で積み上がる）で、その檻が走らせ方しだいで効いたり効かなかったりする。決定論テストの網羅の約束に反する。
**提案**: 7.6 は局所の `Registry` に `Win32Probe` を差して行う（本物のスレッドが走り始めに `duplicate_current_thread_handle` で自分のハンドルを複製して `ThreadEntry` を組み、テストが `Registry::insert` だけを呼ぶ。`read` は呼ばない）。項目の数が「生きた 1 本＋系統の合計 1 つ」を超えないことを毎回確かめる。共有の名簿での `peek_family` の確かめは、結線の確かめとして残してよい。
**対応する要件**: 2.2, 7.6
**根拠**: design.md「Testing Strategy › Unit Tests（名簿）」3 つ目の箇条、「Registry › Implementation Notes › Validation」

🔴 **重大な指摘 2**: 実機の数え直し（7.8）の「終わったトークの数」の数え方が決まっていない
**懸念**: 数え直しは「`role=actor:sakura-talk-*` の畳んだ行の `exited=` が終わったトークの数と合う」ことを記録するが、比べる相手の数をどこから取るかが書かれていない。MCP から流したトークの回数だけを数えると、起動の挨拶（要件の「今の様子」にある、MCP の前に終わった分）、ゴーストの切り替えで起きるトーク（新しいゴーストの起動の挨拶など）、時刻やランダムのトークが `exited=` には入るので数が合わない。
**影響**: 直しが正しくても数え直しの判定が「合わない」になり、7.8 と 4.2 の実機の確かめで迷う。逆に回数を後から合わせ込むと記録の信用が落ちる。
**提案**: 「終わったトークの数」は、走行のログから `sakura-talk-<番号>` のスレッドが起きた本数を数え、記録の時点でまだ話している 1 本（`get_status` の `talking`）を引いたもの、と手順に書く。数える元のログの行（スレッドの名・アクターの span など、今のログに在る行）を手順の中で 1 つ決め、記録には MCP から流した回数とログから数えた本数の両方を並べる。
**対応する要件**: 7.8, 4.2
**根拠**: design.md「System Flows › 実機の切り分けと数え直し（要件 1・7.8）」の「数え直し（7.8）」

## 小さな指摘（設計の明らかな直しで足りるもの）

1. **錠の中の `warn!`**: 掃除の `warn!` を錠を持ったまま出すと、購読側の書き出し（標準出力・`log_history` の層の錠）の間ずっと名簿の錠を持ち、名簿の錠 → 購読側の錠という順序の結び付きができる。掃除は記録の材料（tid・role・family・error）を集めて返し、錠を放した後に出す形にすると、錠の時間も短く、順序の結び付きも残らない。あわせて、掃除は登録した側のスレッド（例: 別のトークのスレッド）で走るので、その `warn!` はそのスレッドの `actor{actor=…}` の span の中に出る。対象のスレッドは `tid`・`role` の欄で示す（設計どおり）ことを説明に 1 行書く。
2. **段②のスレッド別の表と `tid=0`**: 畳んだ行も名簿外の残りの行も `tid=0` なので、`thread_delta` の `before = {row.tid: row}` に畳んだ行が混じると残りの行と鍵がぶつかる。「スレッド別の表は生きた行と残りの行だけ」を、`thread_delta` に渡す前に前後両方から畳んだ行を外すこととして明記する。`ThreadRow` に足す `exited` は既定値 `None` にして、`thread_delta` の中の組み立てが今のまま通るようにする。
3. **CPU を読めずに手放したスレッド（3.3）と段②**: 区間の前に生きた行で値 a を持っていたスレッドが、読めずに手放されると系統の合計 F から a が消え、系統の差が負に寄って同じ系統の他のスレッドの区間の CPU を食う（0 で止まる）。起こるのは開いたハンドルで `GetThreadTimes` が失敗するときだけで、`warn!` も残るので、README の段②の既知の限り（未決 6 と並べて）に 1 行書けば足りる。
4. **プロセス CPU を読む順**: 今の `take_and_emit` はプロセス CPU を先に読み、名簿は後で読む。後で読んだ名簿の合計がプロセスを越えると名簿外の残りが 0 に止まる。`compose_snapshot` に渡す前に `read_cpu()` を先に、プロセス CPU を後に読めば、終わったスレッドの CPU もプロセスの値に含まれ続けるので、残りが負に寄らない。行の意味は変わらない。
5. **`tid_reused/case.txt` の note**: 期待の出力が系統の規則でも変わらないことは確かめた。note を直すときは「前後の TID 100 が同じ系統に入るので系統の差は 0 に止まる」と、系統の規則の言葉で書く。

## 設計の良い点

- **系統の合計の差（D5）**: 1 本のスレッドが 1 つの読み出しの組の中で生きた行か畳んだ行のどちらか一方にだけ入るという不変条件を錠の中の 1 時点で作り、区間の差をその合計の差で取るので、区間の中の終わり・区間の前の終わり・手放した後の TID の使い回しのどれでも区間の CPU が崩れない。古い形のログでも今の検体 4 つで同じ値になることを確かめた。
- **差し替えられる芯（`Registry`＋`ThreadProbe`）**: 本物のスレッドでは起こせない場面（TID の使い回し・最後の CPU を読めない）を偽の芯で固定でき、公開の口（`register_current_thread`・`snapshot`）の形を保ったまま呼び手 5 か所とテスト 8 か所に手を入れずに済む。依存も `Cargo.toml` の機能も足さない。

## 最終判断

**判断: GO**

**理由**: 既存の作りとの整合・依存の向き・刻みの経路の外という制約・古いログの読み方まで実物で裏が取れており、重大な指摘 2 つはどちらもテストの置き場所と実機の手順の書き足しで閉じる（作りの見直しは要らない）。

**次の手順**:
1. 設計の議論（`kiro-design-discussion`）で重大な指摘 1・2 と小さな指摘 1〜5、設計の未決 1〜8 を扱い、design.md へ反映する。
2. その後 `/kiro-spec-tasks talk-thread-count-growth` でタスクを作る。タスクの順は、実機の切り分け（要件 1）を直す前のビルドで最初に行う。
