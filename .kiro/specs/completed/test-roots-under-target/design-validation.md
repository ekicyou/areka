# 設計の検証: test-roots-under-target

> 2026-11-01・`kiro-validate-design` の手順（分析 → 重大な問題 → 良い点 → GO/NO-GO）で、対話なしに行った。読んだもの: `spec.json`（言語 ja）・`requirements.md`・`design.md`・`research.md`・steering の `product.md`・`tech.md`・`structure.md`、コード `crates/temp-path-kit/src/{lib,lib_tests}.rs`・`crates/log-capture-kit/tests/temp_path_guard_test.rs`・`crates/log-capture-kit/tests/workspace_scan/mod.rs`・`crates/sample-ghost-kit/src/devroot.rs`・`crates/areka-ghost/tests/ghost/real_pasta_test.rs`・`snapshot_capture_test.rs`、完了 `areka-P0-shiori4-test-ghost` の `tasks.md`（6.2 と Implementation Notes）。回したもの: `cargo test -p temp-path-kit`（9 本＋doctest 1 本が緑）・`cargo test -p log-capture-kit --test temp_path_guard_test`（16 本が緑）。どちらも今のコードのままの確かめで、設計の形を試しに当てたものではない。

## まとめ

設計は小さく、今のコードの形（入口 → `in_base` → `target_test_roots()`）をそのまま使っていて、要件のすべてに担い手と確かめがある。見張りの案 B（窓口の除外をなくす）で今の緑が保たれることは、コードを読んで確かめた。ただ、要件 3.2 の実物の `pasta.dll` の走行は、今のフィクスチャのままでは「パスの長さで落ちないか」の肝心の部分（`pasta.dll` の中の Lua がゴーストの下のファイルを開くこと）を確かめられない。設計はこの限界を書いておらず、読み方が言い過ぎになっている。直しは記録の書き方と静的な見積もりの足し算だけで済むので、**GO** とする。

## 分析

### 案 B で見張りが緑のまま保たれるか（確かめた）

- 走査器 `strip_comments` は `//`・`///`・`//!` の行コメントと塊コメントを取り除いてから語を探す（`workspace_scan/mod.rs` の 170 行目）。文字列の中身は取り除かない。
- 窓口の 2 ファイルで入口の綴りが出るのは、`lib.rs` の 13 行目（crate doc「なぜ要るか」の `//!` の行・コメント）と 102 行目（`new` の本体・コード）だけ。`lib_tests.rs` には 1 つも無い（文字列の中にも無い）。設計どおり 102 行目を `target_test_roots()` に替えれば、窓口の 2 ファイルの当たりは 0 件になる。13 行目はコメントなので数えられない。
- そのため、窓口のファイルを走査に入れても、主検査・「実測の集合が表と一致する」・「表の全項目に当たりがある」・較正の 1 件外しは、今と同じ結果になる。列挙の件数の検査（500 件より多い）は 2 件増えるだけ。
- `read_source` は読めないファイルで panic する（`mod.rs` の 120 行目）ので、窓口のファイルが読めずに黙って 0 件になることは無い。
- 消す名前（`GATEWAY_DEFINITION_PREFIX`・`gateway_sources`・`the_gateway_is_the_only_excluded_region_and_it_really_holds_the_entry_point`）と改名する主検査の名前を、ほかのコードや文書が引いている所は無い（`git grep`。完了の spec の記録と本 spec の文書を除く）。姉妹の `sample_path_guard_test.rs` は自分の定数を持っていて、こちらに頼っていない。

### 窓口の自己テスト（確かめた）

- `in_base` に置き場が無ければ作る `create_dir_all` があり、要件 1.4 は変更 0 で満たされる。
- 2 つの入口を表で回す 1 本は、今の `under_target` の 1 本と同じ 4 つの確かめ（親が `test-roots`・その親が `target`・そのまた親に `crates/temp-path-kit/Cargo.toml`・破棄で消える）を `new` にも当てる。入口が OS の一時フォルダへ戻ると親の名前が `test-roots` でなくなって赤になるので、要件 4.1 を満たす。本数 9 本のままも正しい。

### 実物の `pasta.dll` の走行（要件 3.2）で分かること・分からないこと

- `real_pasta_test.rs` の `write_real_pasta_ghost_fixture` は `pasta.dll` を 1 つだけ `ghost\master\` へ写す。辞書（`dic/`・`scripts/`・`pasta.toml`）が無いので、pasta は答えられず、観測の 60 秒で切れて赤になる（完了 `areka-P0-shiori4-test-ghost` の `tasks.md` の 6.2 と Implementation Notes に記録あり。今のコードも同じ）。
- このワークツリーで数えると、置き場の移動の後の `pasta.dll` のパスは約 198 字（根 81 字＋`\target\test-roots\` 19 字＋名前 約 75 字＋`\ghost\master\pasta.dll` 23 字）。260 字の上限より十分短いので、helper の作業フォルダと `LoadLibraryW` が通ることは、走らせなくても数で分かる。
- `research.md` の R1 が気にしていたのは、`pasta.dll` の中の Lua（C の実行時ライブラリの `fopen`）が `ghost\master\` の下のファイルを長いパスで開けるか、だった。今のフィクスチャには開くファイルが無いので、走行はこの点に一度も触れない。
- 一方、ゴーストの木はリポジトリの中にある（`vendors/sample_ghost/emo2.nar`。設計自身も `nar-sample-path` から `pasta.dll` を取る）。書庫の中身を数えると、`ghost/master/` の下で最も長い相対パスは 35 字（`scripts/pasta/shiori/event/boot.lua`）だった。`research.md` の「木はリポジトリの外にあり、深さはまだ測っていない」は、もう当てはまらない。

## 重大な問題

### 🔴 重大な問題 1: 実物の `pasta.dll` の走行は、パスの長さの肝心の部分を確かめられないのに、設計の読み方がそれを確かめたように書いている

- **何が問題か**: 設計の「実物の `pasta.dll` の走行」の項は、「前と後が同じ所で同じ色なら、パスの長さのせいではないと読める」と書く。だが `pasta.dll` 1 つだけを写す今のフィクスチャでは、走行が確かめるのは helper の作業フォルダと `LoadLibraryW`（約 198 字で、数で既に分かる）だけ。R1 が気にした Lua の `fopen` は一度も走らない。前と後の両方が観測の 60 秒切れで赤になっても、言えるのは「DLL の読み込みはパスの長さで落ちない」までで、「パスの長さで落ちない」とは言えない。
- **なぜ大事か**: 要件 3.2 の記録が「パスの長さは確かめた」と読まれると、ゴーストの中の深いファイルを長いパスで開く経路が確かめられないまま閉じたことになる。後で別のワークツリーや深いゴーストで赤が出たとき、原因を取り違えやすい。
- **どう直すか**（コードの変更 0・要件の変更 0）: ⑴ 記録の項に「この走行が確かめるのは helper の作業フォルダと `pasta.dll` の読み込みまで。フィクスチャが辞書を写さないので、pasta の中の Lua がファイルを開く経路は確かめていない」と書く決まりを足す。⑵ 静的な見積もりに 1 つ足す: `emo2.nar` の `ghost/master/` の下で最も長い相対パス（今は 35 字）を数え、`snapshot_capture_test.rs` の `ghost\master\` まで約 183 字と足して約 218 字、`real_pasta_test.rs` の約 189 字と足して約 224 字（どちらも 260 字未満）と記録する。pasta が走行中に新しく書くファイル（保存など）の深さは測っていない、とも書く。⑶ 読み方の文「パスの長さのせいではないと読める」を「DLL の読み込みはパスの長さのせいではないと読める」に狭める。前の 1 度（較正）は残してよい（後だけが `boot` で落ちたときに読み分けられる）。
- **要件との対応**: 要件 3.1・3.2・3.4
- **設計の場所**: `design.md` の「実物の `pasta.dll` の走行（要件 3.2）」の項（回す回数・記録の段落）と「設計の討議で選べること」の 3

（重大な問題は上の 1 件だけ。下の 2 点は直すと良いが、無くても実装は進められる。）

### 補足（重大ではない）

- **要件 4.3 の陽性の対をもう一段固くできる**: 設計の対は「窓口の 2 ファイルが走査の一覧に在る」と、既にある合成入力の検査の組み合わせで、これで筋は通っている（`read_source` は読めなければ panic する）。もう一歩、置き換える 1 本の中で「窓口の 2 ファイルを `TOKEN_PROCESS_ID` で走査すると `lib.rs` に 1 件以上当たる」（121 行目の `std::process::id()` はコードの行）を確かめると、「その 2 ファイルの中身を本当に走査している」ことが窓口のファイルそのもので示せる。数行で済む。
- **見張りの例外表の doc に残る「窓口の `src/` を除き」**: `ALLOWED_ENTRY_POINT_USES` の doc（2026-08-27 の実測の方法を書いた段落）は、案 B の後は「当時はこう測った」という記録になる。設計は表を変えないとしているので中身は直さなくてよいが、module doc を書き直すときに、それが過去の測り方だと分かる一言があると、後の読み手が今の規則と取り違えない。

## 良い点

1. **差分が最小で、しかも今の形をそのまま使っている**: 入口 2 つが共通の `in_base` を通る今の作りのおかげで、働きの変更は `new` の本体 1 行だけ。呼び出しの 240 か所・例外表・ほかのクレートに触らず、ウェーブ C15 の約束（触るファイル 4 本）と 1,000 行の番人の両方に収まる。新しい部品・依存・設定は 0。
2. **見張りが恒真にならないことへの手当てが行き届いている**: 案 B で規則を「例外表の中にしか無い」の 1 つに縮め、何も外さない除外を残さない。そのうえで、入口を一時的に OS の一時フォルダへ戻して自己テストと見張りの両方が赤になるのを見る一度きりの確かめを置き、自己テストの置き場の確かめも置き場の式とは別の手がかり（`Cargo.toml` の在りか）で測る。今の緑が保たれることもコードで裏が取れた。

## 判定

- **判定: GO**
- **理由**: 設計は要件のすべてを担い手と確かめに結び付けていて、案 B で今の見張りと自己テストが緑のまま保たれることもコードで確かめられた。重大な問題 1 は、走行の記録の書き方と静的な見積もりの足し算で直せ、コードの形も要件も変えない。
- **次の一手**:
  1. 設計の討議（`kiro-design-discussion`）で、重大な問題 1 の直し（記録の決まり・`emo2.nar` の深さの見積もり・読み方の文を狭める）を議題に挙げ、`design.md` の該当の項へ反映する。補足の 2 点は討議で採るかを決める。
  2. そのうえで `/kiro-spec-tasks test-roots-under-target` でタスクを作る。
