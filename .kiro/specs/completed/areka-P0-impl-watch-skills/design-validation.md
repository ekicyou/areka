## まとめ

設計は「決まった Bash の 1 行を 2 つのスキルに同じ字で写す」形で、包みのスクリプトを足さず、アプリのソースに触らない。終わり方の表の出力の文と終了コードは、アプリのソースと 1 行ずつ合っている。直したいのは、試しで本物の置き場所を守る手当てが文だけで仕組みになっていないこと、前景のコマンドの 3 と 1 の行が表に足りないこと、前のセッションの見張りを外す立て直し（2.8）と「参加を終えた」の印がぶつかること、の 3 点である。

## ソースと突き合わせて確かめたこと

- **Git Bash からの呼び方**: 受け継いだ Windows 形の値（`C:\…`）に `/areka-impl-watch.exe` をつないだ形で、`[ -f … ]` も起動も通る（`C:\Windows\System32` で同じ形を試して 0）。値を書き替えないので、アプリの `Path::is_absolute`（`home.rs`）も通る。机の前置きの式は、この作業木で `id=areka-p0-watch-skills-7d4d4c repo=areka` を出した。
- **終わり方の表と出力の文**: `stop requested by <X>`＋`details:`（見張りの 0）・`already stopped; run stopped --wait or resume`・`resumed`・`stop requested again by <X>`・`granted load; stopped: …`・`granted merge repo=<R>; last: …`・`gone: removed`／`gone: request gone`（3・標準エラー）・`a {watch|merge|load|resume} wait for <id> is already running`（1）・`not applied: not the merge holder`（`merged` の 3）は、どれも `wait.rs`・`cli.rs`・`error.rs`・`plan.rs` の文と同じ。`clear` は引数を受けないので、今の実行ファイルの `clear --repo` は使い方の誤りの 2 で終わる（設計の 12.4 の読みどおり）。`--help` は置き場所を決める前に答えるので、置き方の道具の最後の確かめに使える。
- **起きるのは 1 回**: 待つコマンドは終わるまで何も出さず、終わったときに 1〜2 行を出す。バックグラウンドのコマンド 1 本につき起きるのは 1 回。4.4 のように 2 本が同時に終わると 2 回起きるが、どちらも待ちの終わりで、要件 10.1 の内側である。
- **見張りの無い時間**: アプリは「作業中」で見張りの居ない参加者を、ほかの呼び出しのたびに外す（`plan.rs` の `reclaim`）。停止要請中・止まった間は外さず、再開と番の受け取りの後は「見張りの立て直し待ち」の印で守る。設計の「再開したら見張りを立て直してから進む」「`merge` の前に `watch`」は、この決まりに合っている。
- **入れ替え**: Windows では走っている実行ファイルの改名はでき、消すことはできない。「新しいものを `.new.exe` に写す → 今のものを `.old-<UTC>.exe` へ改名 → `.new.exe` を改名 → 消せない古いものは `KEEP`」の順は成り立つ。改名と改名の間の一瞬だけ実行ファイルが無いが、そこへ当たった前置きは `skip no-exe` で終わるだけで、状態は壊れない。

## 重要な問題（3 点）

### 問題 1: 試しで本物の置き場所へ書かない手当てが仕組みになっていない

- **何が**: 設計は「試しの端末の中だけ環境変数を一時の置き場所へ向ける」と書くが、Claude Code の Bash と PowerShell の呼び出しは 1 回ごとに新しい殻で、毎回、開発者の本物の値（`C:\home\maz\store\.areka-impl-watch`）を受け継ぐ。バックグラウンドで立てる `watch` も同じ。1 回でも上書きを書き忘れると、本物の机へ書く。置き方の道具の試し（11.2）で忘れると、本物の置き場所へビルドして置いてしまう。これは要件が「運用の操作で、試しではない」と分けたものである。
- **なぜ困る**: 2026-10-10 の `impl-watch` の実装で、同じ種類の取り違え（Git Bash の形の値で `C:\c\…` にフォルダができた）が実際に起きている。本物の机は、着地の後に開発者が使う。
- **直し方**: `verification.md` の作り方に次を決まりとして書く。(a) 試しの呼び出しは 1 回ごとに、同じコマンドの頭で値を一時の置き場所へ向ける（Bash は `export AREKA_IMPL_WATCH_HOME='<作業木>\target\impl-watch-skills-trial\home'`、PowerShell は `$env:AREKA_IMPL_WATCH_HOME=…`）。(b) 走らせる前に、値が `<作業木>\target\` の下の Windows 形であることを同じコマンドの中で確かめ、違えば何もせずに止まる。(c) 試しの前と後に、本物の置き場所の中身の一覧が変わっていないことと、`C:\c\` ができていないことを記録する。
- **要件**: 11.1、7.5
- **設計の箇所**: 「確かめの記録（`verification.md`）」・Testing Strategy「置き方の道具の実走（11.2）」「スキルの書き方どおりのコマンドの並び（11.3）」

### 問題 2: 前景のコマンドの 3 と 1 の行が終わり方の表に無い

- **何が**: 表は待つコマンドの終わりを細かく書くが、前景のコマンドは「`merged` の 3（5.7）」「どれでも `state.lock is busy`」「どれでも 2」しか無い。アプリのソースでは、次の終わり方が実際に起きる。
  - `loaddone` の 3（`not applied: not the load-test holder`）: 計測の間に机の記録が消えたとき。この spec が足す `kiro-next` の `clear --repo` でも起きる。
  - `loadrunning` の 3（`not applied: the load-test desk already has a holder`）: 4.6 で、すでに誰かが机を持っているとき。
  - `leave`・`cancel`・`loaddone`・`merged` の 1 のうち、ロックの混み以外のもの（状態ファイルの版の食い違い・壊れ・入出力）。
- **なぜ困る**: 表は 2 つのスキルへ同じ字で写す約束で、11.3 の確かめも「表と合うか」で見る。行が無いと、2 つのスキルの書き手がそれぞれ別の扱いを書く。`loaddone` の 3 を失敗と読んで机の段を止めると、残りのタスクの間、停止要請を取りこぼす。
- **直し方**: 表に 3 行を足す。`loaddone` の 3 → 机はもう無いので何もしない（1 行だけ伝える）。`loadrunning` の 3 → 持ち主にならず、開発者へ 1 行伝え、走っている負荷テストは記録なしのまま（4.6）。前景のコマンドの 1（ロックの混みのほか）→ 標準エラーの 1 行をそのまま伝え、6.4 に従う。
- **要件**: 4.5、4.6、6.4、11.3
- **設計の箇所**: 「机の呼び方の約束」→「終わり方の表（どちらのスキルでも同じ）」

### 問題 3: 前のセッションの見張りを外す立て直し（2.8）が「参加を終えた」の印とぶつかる

- **何が**: 2.8 では、覚えの無い見張りが残っているとき `leave --id <ID>` で外してから立て直す。ところが会話が覚えるものに「参加を終えたか（`leave`・`merged` の後）」があり、表の見張りの 3 の行は「`leave`・`merged` の後なら何もしない」と読む。字のとおりだと、立て直しのための `leave` の後は、新しく立てた見張りが後で 3 で終わっても（`clear --repo`・回収など）何もしなくなり、2.9 の立て直しと 5.8 が効かない。その間は停止要請を受けず、マージの机を持っていたことにも気付かない。もう 1 つ、`leave` の直後は古い見張りがまだ居る印を握っている（1 秒ごとに読むので、終わるまで最大でおよそ 1〜2 秒）。すぐに立て直すと `already running` になりやすく、表の「もう 1 回だけ」も同じ一瞬に当たると、そこで手が尽きる。
- **なぜ困る**: 2.8 は、セッションが入れ替わった後の最初の実行で必ず通る道である（アプリを立ち上げ直して、残った見張りが生きているとき）。そこで参加が黙って切れると、負荷テストを待つ側が乱れた機械で測る。
- **直し方**: (a) 「参加を終えた」の印を立てるのは実行の終わりの `leave` と `merged` だけで、2.8 の立て直しの `leave` では立てない、と書く。(b) 3 の読み分けは「どの見張りが終わったか」で行う。会話が覚えている今の見張りの実行の番号と違う見張りの 3 は、古いものの終わりとして何もしない。(c) 2.8 の立て直しは、`leave` と `watch` を 1 本のバックグラウンドのコマンドにつなぎ、間に 2〜3 秒置く（`leave …; sleep 3; watch …`。バックグラウンドの中なら待ってよい）。これで「もう 1 回だけ」の分を使わずに済む。
- **要件**: 2.8、2.9、2.10、5.8
- **設計の箇所**: 「終わり方の表」の見張りの 1（`already running`）と 3 の行・表の下の 3 つ目の注・「State Management」

## 良いところ

1. **約束を 1 つにまとめ、書く場所を分けた**: 「いつ呼ぶか」はスキルごと、「どう呼び、どう読むか」は共通の表、「どう置くか」は道具 1 本。アプリのソースに触らず、終わりの知らせを出力の文で読むので、会話の覚えが消えても前置きと表だけで戻れる。包みのスクリプトを足さない判断は、トークンの負荷を先に抑える方針（要件 10）とも合う。
2. **置き方の道具が壊さない順で動く**: 写す → 改名 → 改名、失敗したら元へ戻す、の順で、置き場所の実行ファイルが半端な形で残らない。確かめに `status` でなく `--help` を使い、壊れた状態ファイルで置けたものが失敗に見えないようにしている。状態のファイルに触らない線も、`clear` を呼ばない線もはっきりしている。

## 判定

- **決定: GO**
- **訳**: アプリとの約束（出力の文・終了コード・回収の決まり・Windows での入れ替え）は、ソースと突き合わせて食い違いが無い。3 点はどれも表と確かめの手順に文を足せば済み、形を変える必要は無い。
- **次にすること**:
  1. `/kiro-design-discussion areka-P0-impl-watch-skills` で上の 3 点を議題にし、決まった文を `design.md` へ入れる。
  2. そのあと `/kiro-spec-tasks areka-P0-impl-watch-skills` でタスクを作る。問題 1 の手当ては、確かめのタスクの最初の決まりとして書く。
- **気付いたが重要でないもの（議題にしなくてよい）**:
  - 置き方の道具は cargo の JSON の出力を値として読む。steering の決まりでは、子の出力を値として読む所は `Invoke-Utf8Child` で読む（`tools/roadmap-overview.ps1` の前例）。実装のときにそれに合わせれば足りる。
