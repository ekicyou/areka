## 要旨

設計は、今のマニフェストと同じ道（`build.rs` から `areka` の bin にだけ届くリンカへの指示）に資源のファイル `icons.res` を 1 つ足すだけの小さな形で、依存も `Cargo.lock` も `crates/areka/src/` も変えない。要件 1〜6 の全項目に受け持ちがあり、組んだ exe・`.ico`・手で整えた PNG をバイトで突き合わせる結合テストで埋め忘れと作り直し忘れの大半を拾える。残る詰めは、小さい寸法の絵の整え方と開発者の目での合否の時機、縮めた絵のバイトが机によって変わる点、うにゅうの輪郭の権利の書き方の 3 つである。

## 重い指摘（3 点）

### 指摘 1: 通知領域用の 16〜48 の「手で整えた絵」の作り方と、開発者の目での合否の時機が決まっていない

- **困りごと**: 設計は `tray-16.png`〜`tray-48.png` の作り方を「実装に任せる」とし、道具はファイルが在ることと寸法・形式しか見ない。縮めただけの絵を置いても道具もテストも通る。1024 の原画の二重の縁取り（内側の白・外側の灰）は細く、16 ピクセルに縮めると 1 画素に満たず消えるので、縮めただけでは要件 2.4（明暗どちらの地でも 16 ピクセルで輪郭が見分けられる）を満たせない見込みが高い。開発者が目で見るのは README の実機の確かめ（要件 6.3）だけで、絵を作ってコミットする前に見る段が無い。
- **影響**: 実装の終わりの実機の確かめで「見分けにくい」となれば、絵を作り直して道具・コミット・確かめを回し直す手戻りになる。エージェントだけで絵の良し悪しを決める形にもなりかねない（要件 1.6 の趣旨）。
- **直し方の案**: 設計に最小の作り方を書く（例: 影を寸法の枠に 1 画素の余白で合わせる・不透明度を 0.5 で二値にする・外側の灰の線を 1 画素で描き直し、内側の白は 24 以上で足す、など）。あわせて、6 枚を明暗 2 つの地に並べて拡大した見本の絵を `target\` の下に作り、開発者が見て選んでからコミットする段をタスクに置く、と書く。アプリ用の 16〜48（縮めただけ）も同じ見本に並べ、見分けにくければ `app-<寸法>.png` を置く判断をこの時点でする。
- **要件**: 2.2・2.4・1.6
- **設計の箇所**: 「アイコンのフォルダ」の Responsibilities & Constraints（「作り方は実装に任せ」）・「説明の文書」の「実機の確かめ方」

### 指摘 2: 縮めた 10 枚のバイトが GDI+ の版で変わり、「同じ入力から同じバイト」が机の中でしか成り立たない

- **困りごと**: アプリ用の 8 寸法と通知領域用の 64・256 の計 10 枚は、道具が回るたびに GDI+ で 1024 から縮めて PNG に書く。設計も「同じ机・同じ OS の版で」と断っている。別の机や Windows の更新の後に道具を回すと、入力を変えていないのに `.ico`・`.res` に差分が出る。
- **影響**: 要件 5.5 の狙い「差分が出たら、入力が変わったと分かる」が、机が変わると崩れる。絵を 1 枚だけ直したつもりのコミットに、無関係な 10 枚の差分が混ざる。
- **直し方の案**: 縮めた絵も入力のファイルとしてコミットし（`<名>-<寸法>.png` を 16 枚とも置く）、道具の作り直しは「PNG を並べて `.ico` と `.res` に組むだけ」にする。縮める処理は、足りない寸法の PNG を 1 度だけ作る別の口（例: `-Seed`）に分ける。こうすると組む処理はどの机でも同じバイトになり、結合テストの「exe の絵と PNG のバイトの一致」が 16 枚すべてに効く。今の形のまま残すなら、README の注意書きで足りるかを討議で決める。
- **要件**: 5.5・5.4
- **設計の箇所**: 「作り直しの道具」の Batch / Job Contract（寸法ごとの PNG・Idempotency & recovery）・「作り直しの流れ」

### 指摘 3: うにゅうの輪郭まで「areka 本体（MIT）の一部として配る」と書くと、持っていない権利を与えるように読める

- **困りごと**: README の「出どころと権利」は、絵全体を「areka 本体（MIT）の一部として配る」と書く設計である。女の子（生成した絵）と組み合わせ方は areka の作であるが、うにゅうの輪郭は元祖の伺かの相方の形をなぞったもので、その形を MIT で誰にでも使わせる権利を areka が持つとは限らない。使うこと自体は開発者が判断して要件で確定しているので、ここでは書き方だけを問題にする。
- **影響**: 要件 5.3 は「誰がどの条件で使い・配ってよいか」を書くことを求める。うにゅうの輪郭を MIT で再配布してよいと読める記述は、受け取った人を誤らせる。
- **直し方の案**: README で 2 つを分けて書く。① 女の子の絵・2 人の組み合わせ・色と縁取り＝areka 本体（MIT）の一部。② うにゅうの輪郭＝元祖の伺かの相方の形に由来し、開発者の判断（2026-10-16）で areka のアイコンに使うもので、areka はその形の元の権利を持たず、MIT の許諾は元の形の権利に及ばない。`dist/README.txt` には足さない今の判断（要件 5.9）は変えない。
- **要件**: 5.3・5.2
- **設計の箇所**: 「説明の文書」の「出どころと権利」・Security Considerations

## よい点

1. **今ある道に 1 本足すだけの小さな形**: 資源の形を知るのは道具 1 か所、`build.rs` は場所を渡すだけ、テストは読むだけと、受け持ちがはっきり分かれている。`rustc-link-arg-bins` で他の exe（MCP の中継・32 ビットの補助）に届かないこと、MSVC でなければ今と同じく何もしないことを、今のコードの形のまま使っている。依存・`Cargo.lock`・`crates/areka/src/`・`tools/test-all.ps1` を変えない。
2. **バイトで突き合わせる結合テスト**: 組んだ exe の 16 枚を `.ico` と手で整えた PNG にバイトで突き合わせ、欠けを全部集めてから組の番号・寸法・絵の番号を名指して落ちる。`.res` を外した状態と PNG を 1 画素変えた状態で一度ずつ赤を立ててから緑にする手順も書かれている。arm64 の exe も環境変数 1 つで同じ検査に通せる。

## 小さな気付き（重い指摘には入れない）

- 道具の書き込みは 3 つとも一時ファイルへ書けてから置き換えるが、置き換えの途中で失敗すると 3 つが揃わない。結合テストが不一致を拾うので害は小さい。
- `extra_exe_has_app_and_tray_icons` は環境変数が無いと 1 行出して通る。全体テストでは毎回この行が出るので、README の arm64 の手順と合わせて読めば足りる。
- `.kiro/steering/structure.md` の「`build.rs` は 0 件」は本 spec の前から古い。設計どおり完了のときに直せばよい。
