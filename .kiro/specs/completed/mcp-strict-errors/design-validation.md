# 設計の確かめ: mcp-strict-errors

> 2026-10-29 `/kiro-validate-design`（`/kiro-design` の中の段・対話なし）。読んだもの: `spec.json`・`requirements.md`・`design.md`・`doc/ssp-mcp/areka-tools.md`（`research.md` は rmcp の節だけを引いた。`brief.md` と steering は読み直していない）。設計が名を挙げた型・関数・行のうち、手早く見られるものはコードで確かめた（下の「コードで確かめたこと」）。

## まとめ

設計は、`strict` の印を台本の始めの知らせに載せて翻訳の後まで運び、誤りの判定を各層の受け取りの場で、`check_script` と同じ関数で行う形で、要件 1〜7 のすべてに行き先がある。依存の向き・前例（出どころの運び方・`\!` の汎用の運び手）・rmcp の直し方は、今のコードと食い違わない。直すべき点は 3 つあるが、どれも形を作り直すものではなく、討議で決めるか、設計の一部を書き足せば済む。

## 大事な指摘（3 件）

### 指摘 1: SSP の実測（要件 6.8）が設計の段で済んでいない

- **中身**: 要件 6.8 は「設計の段で SSP の MCP で測る」と定めているが、設計は許しを取れなかったので実装の最初のタスクへ回している（`design.md` の「DiffDocs・SspMeasurement」）。測った答えで決まるはずのこと（要件 3.8 の別の台本へ及ぶか、3.10 の `raise_event` の答えの文、記録の表示の語と本文の形、4.6 の「SSP との違い」）は、いま既定の値で仮に決めてある。
- **困ること**: 実測が既定と違えば、`KanadeStrictFlag`（`talk_origin::of_shown` での引き継ぎ）・`raise_event` の答え・文書が、タスクを作った後に変わる。タスクの並びと見積もりが崩れる。
- **直し方**: 討議で次のどちらかに決める。(a) タスクを作る前に、開発者の許しを取って 4 つを測り、`survey.md` に書いてから設計の既定を確定する。(b) 要件 6.8 の「設計の段」を「実装の最初のタスク」に改め、測った答えに依るタスク（3.8・3.10・文書）をその後ろに置くことをタスクの約束にする。
- **要件**: 3.8・3.10・4.6・6.8
- **設計の箇所**: 「Revalidation Triggers」・「DiffDocs・SspMeasurement」・「要件の読み」4

### 指摘 2: 名前の形の `\b[名前]` の記録が、要件 2.5・2.7・7.1 の文と合わない

- **中身**: 設計は、名前の形の `\b[名前]` の箱が無いことを文字の層が UI のスレッドで決めて記録する（検出点 `BalloonBoxMissing`）。このため (1) `check_script` は名前の形を診ないので、要件 2.7 の「同じ集まり」がその台本では成り立たない。(2) 記録の前後が台本の順と違うことがあり、要件 2.5 の「当たった順」と読み違えうる。(3) `areka-tools.md` ⑶ の 8 行目は `\b[名前]` を「出ない台本」に挙げているが、箱が無ければ再生では `missing_balloon` が残る。設計は (1)(2) を「要件の読み」1・3 で認めているが、要件の文は直っていない。
- **困ること**: 要件のとおりに作るとこの検出点は置けず、設計のとおりに作ると要件 2.7・7.1 のテストの読み方が人によって変わる。⑶ の 17 行のテストは文字の層を通さないので、食い違いがテストに映らない。
- **直し方**: 討議で要件を直す。2.7 の条件に「名前の形の `\b[名前]` で箱が見つからない所を持たない」を足す。2.5 に「文字の層で決まる記録は、ほかの記録との前後が台本の順と違うことがある」を足す。7.1 の 8 行目の「出ない台本」は、今のサーフェスに在る箱の名前で確かめると書く。
- **要件**: 2.5・2.7・4.2・7.1
- **設計の箇所**: 「TextProbe」・「検出点の表」の `BalloonBoxMissing` の行・「要件の読み」1・3

### 指摘 3: 命令と合図を「番号」で結ぶ形が、`compile` の後の手直しと合っていない

- **中身**: 設計は「命令の走査の頭の `cues.len()`」で、命令の誤りと位置を合図の番号に結び、`StrictTap` は `emit` の回数で番号を進める（「CompileStrict・StrictTrace」「StrictTap・StrictDrive」）。ところが今の `compile` は、走査の後で先頭に全部を消す合図を差し込む（`crates/areka-sakura/src/compile.rs` 337 行の `cues.insert(0, …ClearAll)`）。また選択待ちの区切りも同じ列に積むが、これは sink へは配られない（`dola` の `Entry::Barrier`）。このままでは番号が 1 つずれ、位置・綴り・順が崩れる。あわせて、最後の合図より後ろの命令の誤りは「自然に終わったとき」にしか書かないので、選択肢で終わる台本が選ばれて打ち切られると、再生が通り過ぎた所の誤りが落ちうる（要確認）。
- **困ること**: 要件 2.3（位置）・2.5（順）・2.7（`check_script` と同じ集まり）が崩れる。設計の「配った順と `cue_spans` の順が一致する」テストで気付けはするが、対応の決め方そのものが書かれていない。
- **直し方**: 対応表は、先頭の差し込みの後の最終的な列から、sink へ配られる合図（`Command` のもの）だけを数えて作ると設計に書く（エピローグは今のとおり数えない）。最後の合図より後ろの命令の誤りは、最後の合図を配った時点で書くか、選択待ちに入った時点で書くかを決めて書き足す。
- **要件**: 2.3・2.5・2.7・3.6
- **設計の箇所**: 「CompileStrict・StrictTrace」の不変条件・「StrictTap・StrictDrive」の 1〜3 と `finish`

## 良いところ

- **物差しを 1 つにしている**: 文面の定数と `\s`・`\b`・`\f` の判定の関数を下の crate へ移し、`check_script` と再生の両方が同じ関数を使う。そのうえで、文書の表を印で挟んでテストが読む形にしたので、要件 2.4 の「1 字も違わない」を写しでなく文書との突き合わせで判定できる。検出点の表に「書かない分岐とその理由」まで並べてあり、漏れの見落としが起きにくい。
- **strict でない台本の道を 1 つも変えない**: `emit_with` の既定が `emit` を呼ぶだけなので、今の sink は直さずに動き、判定と記録は台本のスレッドの合図の順で行うので UI を塞がない。rmcp の直しも、3.5.0 の `tower.rs` の `jsonrpc_http_status`（646 行）・`is_legacy_request`（390 行）・`expect_json` の 415 まで調べてあり、直す所が狭く決まっている。
