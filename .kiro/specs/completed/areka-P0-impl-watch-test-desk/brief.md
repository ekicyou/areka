# Brief: areka-P0-impl-watch-test-desk

> 起票: 2026-10-17（`/kiro-discovery`・開発者「負荷テストが始まると他の実装も全部止めちゃうよね？そうじゃなくて、『全体テスト・UIテスト』は、同時に他のテストが走らないようにしたいだけで、実装を止める必要はないんだ」）。きっかけは、並んで走るセッションのうち 2 本が同時に areka を立てていたこと（開発者「arekaが2つ起動したりしてた」）。机の模型は同じ日の開発者の指示（下の「机の模型」）。区分 A（開発者が起票を頼んだ）。

## Problem

- **開発者**: 並んで走る実装セッションが、全体テスト（`tools/test-all.ps1`）や実機の UI テスト（`areka.exe` やゴーストを実際のデスクトップに立てる・`SendInput` や computer-use で操作する）を同時に回すと、次のことが起きる。
  - areka が 2 つ立って、窓・入力・前面を取り合う。テストが偽の赤になるか、何を確かめたのか分からなくなる。
  - 全体テストどうしはメモリとビルドを取り合う（`memory allocation ... failed`・`E0463`／`E0786` の偽の赤は、`kiro-complete` の「よくある失敗」に載っている）。
- **今の道具で防ごうとすると重すぎる**: 机の貸し出しのアプリ `areka-impl-watch.exe` の「負荷テストの机」は、取ると**ほかの参加者全員に停止要請**を出し、実装そのものを止めてしまう。全体テストや UI テストに要るのは「同じ種類のテストが同時に走らないこと」だけで、ほかのセッションの実装（コードを書く・クレートのテストを回す）は続けてよい。

## Current State

- `areka-impl-watch.exe`（`crates/areka-impl-watch`・完了 `impl-watch`・`impl-watch-skills`・`impl-watch-residue`）が持つ机は 2 種類（`doc/impl-watch.md` の「机は 2 種類」と「決まり 7 つ」）。
  - **マージの机**（リポジトリごとに 1 つ）: 停止要請を出さない。`kiro-complete` が完了の手順の全部を、この机の番の中で回す。全体テストもこの中で回る。
  - **負荷テストの机**（マシンに 1 つ）: 番が来る前に、持ち主とマージの机の参加者以外の全員へ停止要請を出す。負荷テストの机が持たれている・待たれている間は、どのリポジトリでもマージを始めない。
  - 「実装している」ことは机ではなく、参加者の見張り（`watch`）と状態（作業中・停止要請中・止まった）で表している。
- スキル `kiro-impl` は、負荷テストの机が要る段を「静かな CPU での計測・わざと負荷をかける再現・時間の比べ」の 3 つに限り、「ふつうのテスト（クレートのテスト・clippy・`tools/test-all.ps1`）は数えない」と書いている（`.claude/skills/kiro-impl/SKILL.md` の Desk timing 2）。
- そのため、次の 3 つは、今どの机も取らずに回る。
  1. `kiro-impl` の最後の検証（`/kiro-validate-impl` が全体テストを回す）
  2. タスクの中の実機の UI テスト（`#[ignore]` の実機テストを `--ignored` で回すものを含む）
  3. `kiro-complete` のステップ 5 の全体テスト・`/release` の全体テスト。マージの机はリポジトリごとなので、別のリポジトリや別のセッションの全体テストとは重なりうる。
- 2026-10-17 に、`kiro-impl` の段を負荷テストの机へ寄せる直しを一度書いたが、上の「実装まで止める」の理由で開発者が差し戻した（コミットは捨てた・main には無い）。

## 机の模型（2026-10-17 開発者の指示・この spec の正本）

机は 3 種類。

| 机 | 数 | 乗り方 |
|---|---|---|
| **実装の机** | マシンに 1 つ | 実装が走る机。実装のタスクはいくつ乗ってもよい |
| **排他テストの机** | マシンに 1 つ | 同時に 1 つだけ。テストを行う実装が取る |
| **マージの机** | リポジトリに 1 つ | マージの作業が取る |

排他の決まり。

| する事 | 取る机 |
|---|---|
| 実装 | 実装の机に乗れたら実装する |
| 全体テスト・UI テスト | 排他テストの机 |
| 負荷テスト | 排他テストの机と、実装の机（ひとり占め）。全部止める |
| areka のマージ | マージの机と、全体テストをするので排他テストの机 |
| pasta のマージ | マージの机だけ |

- 実装の机は「大勢で乗れるが、負荷テストがひとり占めできる」机。今の「参加者」と「停止要請」は、この机への乗り降りとして読み替える。
- 全体テストや UI テストの番を待つ間も、持っている間も、ほかのセッションの実装は止まらない。
- 負荷テストは排他テストの机も取るので、全体テストや UI テストの最中には計測が始まらず、計測の最中には全体テストや UI テストが始まらない。
- areka のマージも排他テストの机を取るので、完了の全体テストはほかの全体テスト・UI テスト・負荷テストと重ならない。

## Desired Outcome

- `areka-impl-watch.exe` が上の 3 つの机と排他の決まりを持ち、`status` と `doc/impl-watch.md` で、だれがどの机に乗り・持ち・待っているかが読める。
- 机を使う全部のスキルが、上の表どおりに机を取り、終わったら返す。
  - `kiro-impl`: タスクの中の全体テストと UI テスト・最後の検証の全体テストは排他テストの机を取る。負荷テストは今どおり全部を止める。
  - `kiro-complete`（areka）: マージの机と排他テストの机を取る。
  - `/release`: 全体テストの前後で排他テストの机を取る（マージの机をどう扱うかは要件で決める）。
  - pasta のマージの手順: マージの机だけ（今のまま）。
- 1 回の申し込みで複数の机を指定でき、全部そろったときに一度に渡る。2 つの机を取る者どうしが互いに待って止まること（行き詰まり）が起きない。
- アプリはリポジトリの名前で振る舞いを変えない。areka と pasta の違いは、各リポジトリのスキルが申し込みに並べる机の違いだけで出る。

## Approach

- 机の模型は開発者が決めた（上の表）。要件の段では、この模型を `areka-impl-watch.exe` の状態・番の決め方・コマンドへ落とす。
- 呼び方は今の机にならい、申し込み（`--wait` で番が来るまで終わらない）と返す（済んだ）の 2 つ。名前は要件で決める。
- **1 回の申し込みで、欲しい机をコマンドラインに並べて指定できる**（2026-10-17 開発者「要求に『机Aと机Bが欲しい』的に、コマンドラインで複数指定できるようにしておけばよい」）。例: 負荷テスト＝排他テストの机＋実装の机のひとり占め／areka のマージ＝マージの机＋排他テストの机。並べた机は**全部そろって空いたときに一度に渡す**（一部だけ持って待つことが無いので、2 つの机を取る者どうしが互いに待って止まらない。取る順を決める必要も無い）。返すときも、持っている机をまとめて返せる。
- **areka と pasta の違いは、スキルの組み立てだけで出す**（同じ日の開発者「スキルの組み立てだけで違いを出せないか？」）。アプリはリポジトリごとの決まりを持たず、どの机を取るかは呼ぶ側のスキルが申し込みに並べる。areka の `kiro-complete` は「マージの机＋排他テストの机」、pasta のマージの手順は「マージの机」だけを申し込む。
- 今の負荷テストの机は「排他テストの机 ＋ 実装の机のひとり占め」へ組み直す。今の停止要請・止まった・再開の仕組みは、実装の机のひとり占めの中身としてそのまま使う。

**採らなかった案**:

- **負荷テストの机に「止めない」印を足す**: 「静かな CPU を守る」と「同じ種類のテストを 1 本にする」が 1 つの机に混ざり、負荷テストの机の決まり（マージを始めない など）が全体テストにもかかってしまう。
- **`tools/test-all.ps1` の中で、マシン全体の名前つきの鍵（ミューテックス）を取る**: 呼ぶ側を直さずに全部の全体テストを覆えるが、実機の UI テスト（`cargo test -- --ignored`・spec ごとの実機の走行の道具）は覆えない。`status` に出ず、負荷テストとも連動しない。
- **スキルの文だけで負荷テストの机を使う**: 実装まで止まる（開発者が差し戻した形）。

## Boundary Candidates

- 机の状態と番の決め方（`state.rs`・`plan.rs`）: 3 つの机・複数の机をそろえて一度に渡す番の決め方・実装の机のひとり占めと停止要請。
- コマンドの口と待ち（`cli.rs`・`wait.rs`）: 申し込み・返す・`--wait` の終わり方の終了コード。

- スキルの机の段（`kiro-impl`・`kiro-complete`・`release`）と手順書（`doc/impl-watch.md`）。

## Constraints

- **トークンの負荷が最優先**（開発の道具の決まり）: 待ちは「番が来たら終わるコマンド」1 本。ポーリングや時間で回すループを足さない。出力は終了コード＋ASCII の数行。
- 道具が端末へ出す文は ASCII だけ（文字化けの決まり）。
- 実機テストの子プロセスの置き場所は、ワークツリーの `target\` の下の Windows 形の絶対パスで上書きする（開発者の機械には本物の置き場所が環境変数で設定されている）。
- 置き場所は全リポジトリ・全セッションで共有する。状態ファイルの形が変わるなら、古い形の状態ファイルを読んだときの扱いを決める。走っている古い版の実行ファイルと新しい版が混ざる間の扱いも決める。
- 規模の見立て: M（12〜16 タスク・アプリ 7〜9＋スキルと手順書 3〜4＋実機の確かめ 1）。20 を超えそうなら、アプリとスキルで 2 本に分ける（要件の段で測り直す）。要件は Opus で足りる（先例＝今の 2 つの机と停止要請の仕組み）。

## 要件の段で決めること

1. **複数の机の申し込みの細部**（指定できること自体は決まり・上の Approach）: 机の名前の書き方（例: `--desk merge --desk test`）・同じ机を 2 度並べたとき・一部の机だけ先に返せるか・今のコマンド（`merge`・`loadtest`）を残して中で読み替えるか、1 つの申し込みのコマンドへまとめるか。待ち行列の順（一度に渡すので、後から来た 1 つだけの申し込みが先に通ってよいか・2 つを待つ者が待たされ続けないか）。
2. **pasta のマージと負荷テスト**: pasta のマージは排他テストの机を取らないので、負荷テストと重なりうる。今の決まり（マージの机の持ち主は止めない・負荷テストの机が持たれている間はマージを始めない）を残すか。
3. **areka のマージで排他テストの机を持つ長さ**: 完了の手順の全部か、ステップ 5 の全体テストの間だけか。推し: 全体テストの間だけ（回し直し〔ステップ 7-4〕でも取り直す）。
4. **「全体テスト・UI テスト」の判定の基準**: タスクの文からどう読み取るか（`#[ignore]` の実機テスト・実機の走行の道具・`SendInput`・computer-use）。クレートのテスト（`cargo test -p`）は数えない（実装の机の上で回る）でよいか。
5. **`/release` の机**: 全体テストの前後で排他テストの机を取るほかに、版上げの PR のマージでマージの机を取るか。
