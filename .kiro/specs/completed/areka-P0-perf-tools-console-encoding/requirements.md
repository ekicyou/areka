# Requirements Document

## Project Description (Input)

性能改善ループの道具（`tools/perf/` の PowerShell のスクリプト 7 本）は、子の PowerShell でスクリプトを回すとき、子へ `-Command` で「端末の出力の文字コードを UTF-8 に書き替えてからスクリプトを起動する」文を渡している（`tools/perf/perf-loop.common.ps1` の `Invoke-PwshChild`）。注記は「端末そのもののコードページは変えない（子の中だけ）」と言うが、子は親と同じ端末を分け合っているので、この書き替えは共有の端末の出力のコードページを変えうる。スクリプトが終わった後も開発者の端末に残りうる。

困っているのは性能改善ループを回す開発者。開発者の方針（2026-10-05）は「文字化けは端末の文字コードを変えて逃げず、読む側を直す」「道具が端末へ出す文は ASCII だけ」で、完了 spec `tools-utf8-child-output` が `tools/*.ps1` と CI の段に当て、`tools/encoding-check.ps1` で判定している。`tools/perf/` はそのとき範囲外として残した（判定の対象からも外してある）。

書き替えが要った理由は、PowerShell が渡された出力先へも端末の出力の文字コードで書くため、書き替えないとコードページ 932 の端末から回した子の出力が 932 で来て、親の UTF-8 の読みと食い違うこと。親の読む側（`Invoke-Child`）は、すでに端末に依らず UTF-8 で読む正しい形になっている。

変えたいこと: `tools/perf/` のどの道具も端末の文字コードを書き替えない（子の中の書き替えも、共有の端末に効くなら不可）。932 の端末から回しても、子の出力の日本語が化けずに親へ届く（読む側で直す）。端末へ出す文の扱いを `tools/*.ps1` と揃え、`tools/encoding-check.ps1` の対象に `tools/perf/` を入れて判定を緑にする。出どころの詳細は `brief.md`。

## Introduction

本書は、性能改善ループの道具が端末の文字コードを書き替えずに子の出力を正しく受け取り、端末へ出す文を ASCII だけにするための要件を定める。対象は、`tools/perf/*.ps1` の 7 本（`perf-loop.ps1`・`perf-loop.common.ps1`・`perf-loop.measure.ps1`・`check-quiet.ps1`・`invoke-cpu-sample.ps1`・`invoke-followup-checks.ps1`・`invoke-perf-run.ps1`）の子の起こし方と読み方、7 本が端末へ出す文、`tools/encoding-check.ps1` の対象、932 の条件で子の出力が届くことの判定、そして注記と文書である。段は**その他**（中身はバグ寄り）。

**要件の段で決めたこと（brief の候補の選び方）**

- **候補 3 を採る**（端末へ出す文を ASCII だけにする）。あわせて、子の中の書き替えを撤去し、子の出力は端末に依らず読む側で正しく受ける（候補 2 の芯）。理由: steering `tech.md` の決まり「道具が端末へ出す文は ASCII だけ・端末の文字コードを書き替えない」は `tools/` のスクリプトに掛かり、`tools/perf/` を外していたのは「前の spec の範囲外として残した」からで、外し続ける理由が無い。揃えれば `encoding-check.ps1` の対象に入れられ、書き替えや日本語の文が戻ったときに判定で捕まえられる。
- **候補 1 は採らない**（子を自分だけの端末で起こし、子の中の書き替えはその端末だけに効かせる形）。道具の中に端末の書き替えが残り、方針の字面に沿わない。`encoding-check.ps1` の規則（子の PowerShell へ渡す文の中の書き替えも赤）にも当たるので、対象に入れられない。
- **候補 2 だけで止めない**（書き替えを消すが、端末へ出す日本語の文は残す形）。端末へ出す文を揃えない理由が立たず、`encoding-check.ps1` の対象に入れられない。
- **手間**: 規模は brief の見立てどおり S（5〜8）から M（10〜14）へ上がる（端末へ出す文の書き直しが 7 本にまたがる）。ウェーブ C7 の空き席の条件（見立ての上限 16 以下）の内に収まる。
- **要件の議論で決めたこと（2026-10-16・全議題を推奨案で確定）**: (1) 子のプロセスの中でその子自身の出力先だけを UTF-8 の書き手に替えることは端末の書き替えに当たらない（要件 1.1）。(2) OS の一時フォルダを使う 3 か所と、判定の規則 D の穴を、この spec で一緒に直す（要件 5.7・要件 10）。(3) 「どの端末でも同じ結果」に含めるのは、ファイルに値として残る物まで（要件 1.3）。規模は M のまま、上限 16 の内。

## Boundary Context

- **In scope**:
  - `tools/perf/*.ps1` の 7 本が子のプロセス（PowerShell・Python・`cargo`・`git`・`xperf` ほか）を起こして出力を受け取る所（値として読む所・人のために端末へ写す所）
  - `Invoke-PwshChild` の子の中の端末の書き替えの撤去と、撤去の後も子の出力の日本語が化けずに届くこと
  - 7 本が自分で端末へ出す文（進みの表示・失敗の文・判定の結果の行・投げる例外の文）を ASCII だけにすること
  - `tools/encoding-check.ps1` の対象に `tools/perf/*.ps1` を入れること
  - コードページ 932 の条件で子の出力の日本語が届くことの合否の判定
  - `tools/perf/*.ps1` が OS の一時フォルダに作っている一時ファイルと作業用のフォルダを、ワークツリーの `target\` の下へ移すこと（要件 10）
  - 判定の規則 D が、引数を変数で渡す素の `cargo` の呼び出しを見逃す穴を塞ぐこと（要件 5.7）
  - 注記と文書: `tools/perf/README.md`・`perf-loop.common.ps1` の頭書と子を起こす所の注記・steering `tech.md` の該当の 2 行・スキル `perf-loop-iteration` の古くなる注記 1 か所
- **Out of scope**:
  - 性能改善ループの判定・計測の中身（`judge-*.py`・`perf-*.py` ほか Python のスクリプトの計算と、それらが出す文）と見本（`tools/perf/fixtures`・`tools/perf/fixtures-loop`）
  - Python の子へ渡す環境変数（`PYTHONIOENCODING`・`PYTHONUTF8`）。端末を書き替えないので今のまま
  - `tools/perf/` の外の `tools/*.ps1`（前の spec で済み）と CI の workflow
  - 端末へ出さずファイルにだけ書く文の中身（日本語のままでよい）。同じ文を端末とファイルの両方へ出す所は端末へ出す文として扱う（要件 4.6）。ただしスクリプトの字句は文字コードの判定の規則（注記の外の字句に ASCII の外の字を書かない）に従うので、日本語の中身をどう書き表すかは設計で決める（要件 4.7 の突き合わせの文字列も同じ）
  - スクリプトの注記と README の地の文（端末へ出ないので日本語のままでよい）
- **Adjacent expectations**:
  - `tools/utf8-child.ps1` の `Invoke-Utf8Child`: 引数と戻り値を変えない（`tools/*.ps1` と CI が頼っている）。性能改善ループの道具から使うかどうかは設計で決める。
  - `tools/test-all.ps1` の段 `encoding check`: 判定の対象が広がる。段の名前・順・終了コードの約束は変えない。
  - スキル `perf-loop-iteration` とエージェント `perf-*`: 判断は ASCII の行（`PERF-LOOP RESULT <sub> code=<n> dir=<path>` ほか）で行っており、その字面は変えない（要件 4.4）ので、手順は変わらない。
  - 計測の spec（`present-emit-tail-latency`・保留の `tick-gate-adoption`）: 道具が途中で変わると前後の数が比べられないので、同じウェーブに置かない。

## Requirements

### Requirement 1: 端末の文字コードを書き替えない

**Objective:** As a 性能改善ループを回す開発者, I want 道具が共有物である端末の設定を書き替えないこと, so that 道具を回した後も同じ窓で続けて自分で PowerShell を打てる

#### Acceptance Criteria

1. The 性能改善ループの道具 shall 親の中でも子のプロセスの中でも、端末の文字コードの設定（出力の文字コード・入力の文字コード・コードページ・PowerShell が子へ渡す文字コード）を書き替えない（子が親と端末を分け合う形では、子の中の書き替えも共有の端末に効くので不可）。なお、子のプロセスの中でその子自身の出力先だけを UTF-8 の書き手に替えること（端末には触れない。Python の子へ `PYTHONIOENCODING` を渡して UTF-8 で書かせるのと同じ考え）は、ここで言う書き替えに当たらない。
2. When 開発者が `tools/perf/` のどの道具を回し終えたとき, the 端末 shall 回す前と同じ文字コードの設定のままである（道具が失敗して止まったときも同じ）。前と後の比べは、プロセスが前に読んで覚えている値ではなく、その時点の端末の設定を OS から読んだ値で行う（.NET は端末の文字コードを一度読むと覚えておくので、同じプロセスの中の値では子の書き替えに気付けない）。
3. While 端末の文字コードが ANSI・OEM のどのコードページであっても（932・437・65001 など）, the 性能改善ループの道具 shall 同じ結果（合否・読み取った値・終了コード・機械が読む行）を出す。同じ結果に含めるのは、ファイルに値として残る物まで（OS の道具から読んだ値も含む。例: `run-meta.txt` の `power_scheme` は端末に依らず字まで同じ）。人が読むためだけに写す OS の道具の文（xperf の失敗の文など）は、読む側で化けさせなければ足りる（道具そのものが端末に無い字を落とすのは、その道具の性質）。

### Requirement 2: 子の出力を読む側で正しく受け取る

**Objective:** As a 性能改善ループを回す開発者, I want 932 の端末から回しても子の出力の日本語が化けずに親へ届くこと, so that 字面の比較や判定が偽の不一致にならない

#### Acceptance Criteria

1. When 道具が子の PowerShell でスクリプトを回すとき, the 性能改善ループの道具 shall 端末の文字コードに依らず、子が出した字（日本語などの ASCII の外の字を含む）を 1 字違わず受け取る。
2. When 子のスクリプトがさらにその子（孫）の出力を受け取って写すとき, the 性能改善ループの道具 shall 孫が出した字を端末の文字コードで解き直して化けさせることなく、親まで届ける。
3. When 道具が子の Python のスクリプト・`cargo`・`git` ほかの出力を読むとき, the 性能改善ループの道具 shall 今と同じく端末の文字コードに依らずに読む（今の正しい読み方を後退させない）。
4. Where 子の出力をそのまま端末へ写す所, the 性能改善ループの道具 shall その中身を書き替えずに写す（中身は子の物）。

### Requirement 3: 子の出力を受け取る所の棚卸

**Objective:** As a 開発者, I want 7 本の中に端末に頼る読み方が残っていないことを確かめたい, so that 書き替えを消した後にほかの所で化けが出ない

#### Acceptance Criteria

1. The 棚卸 shall `tools/perf/*.ps1` の 7 本すべてについて、子のプロセスの出力を受け取る所（値として読む所・人のために写す所）を挙げる。
2. When 棚卸で、子の出力を端末の文字コードで解く所（素の呼び出しの出力を受け取る所・パイプで受けて写す所など）が見つかったとき, the 該当のスクリプト shall その所を要件 2 を満たす読み方にする。
3. The 棚卸の結果 shall 調べたスクリプトの名前と、所ごとの扱い（直した・もとから端末に依らない・端末を通らない（ファイルを介して受け取る）・ASCII しか来ない など）を、該当が 0 件のスクリプトも 0 件と明示して、この spec の文書に残す。

### Requirement 4: 道具が端末へ出す文は ASCII だけ

**Objective:** As a 性能改善ループを回す開発者, I want 道具が自分で端末へ出す文が ASCII だけであること, so that どのコードページの端末でも、端末を書き替えずに表示を読める

#### Acceptance Criteria

1. The 性能改善ループの道具 shall 自分で端末へ出す文（進みの表示・失敗の文・判定の結果の行・投げる例外の文・子を起こせないときに持ち帰る文）を ASCII の字だけで書く。
2. Where 端末へ出す文に値（パス・子の出力の行・目標の名前など）を埋め込む所, the 性能改善ループの道具 shall その値を書き替えずに埋め込む（ASCII の決まりは道具が自分で書く文面に掛かる）。
3. When 日本語の文を ASCII に書き替えるとき, the 書き替え shall 文の意味（どの段の・何が・どの値で失敗したか・次に何をするか）を落とさず、終了コードを変えない。
4. The 性能改善ループの道具 shall 機械が読む行（`PERF-LOOP RESULT`・`SELFTEST RESULT`・`FOLLOWUP RESULT`・`selftest <道具> ok|NG code=<n>`・`available=`・`capabilities=` ほか `key=value` の形の行）の字面を変えない。
5. The 性能改善ループの道具 shall ほかの道具（判定器・台帳・順位表・スキル `perf-loop-iteration`）が読むファイルの中身の形を変えない。
6. Where 同じ文を端末とファイルの両方へ出す所, the 性能改善ループの道具 shall その文を端末へ出す文として ASCII だけで書く。
7. Where 子の Python のスクリプトが出す日本語と字面で突き合わせる所（例: 自己較正が `goal-text` の報告の字数を読む所）, the 性能改善ループの道具 shall 今と同じ突き合わせの結果を出す（Python のスクリプトが出す文は変えない）。

### Requirement 5: 文字コードの判定の対象に入れる

**Objective:** As a 開発者, I want `tools/perf/` も文字コードの判定で調べること, so that 端末の書き替えや端末へ出す日本語の文が戻ったら気付ける

#### Acceptance Criteria

1. The 文字コードの判定（`tools/encoding-check.ps1`） shall `tools/perf/*.ps1` を対象に入れ、`tools/*.ps1` と同じ規則で調べる。
2. When この直しの後に文字コードの判定を回すとき, the 文字コードの判定 shall 緑で終わる。
3. If `tools/perf/*.ps1` に端末の文字コードの書き替え（子の PowerShell へ渡す文の中の書き替えを含む）が入る, the 文字コードの判定 shall 不合格になる。
4. If `tools/perf/*.ps1` が自分で端末へ出す文に ASCII の外の字が入る, the 文字コードの判定 shall 不合格になる。
5. The 文字コードの判定 shall 今の対象（`tools/*.ps1`・workflow の `run:` の本文）への合否と、自分の較正を、今のまま保つ。
6. The 文字コードの判定 shall 今の約束（何も書き出さない・端末へ ASCII だけを出す・判定を回す端末の文字コードを書き替えない）を保つ。
7. If 素の `cargo` の呼び出しが `metadata`・`nar-sample-path` を変数に入れた引数で渡す（例: `& cargo @cargoArgs`）, the 文字コードの判定 shall 不合格になる（今の規則 D は引数の定数しか見ないので見逃す）。今の対象への合否は要件 5.5 のとおり保つ。

### Requirement 6: 932 の条件で子の出力が届くことを判定で固定する

**Objective:** As a 開発者, I want コードページ 932 の条件で子の出力の日本語が届くことを合否で判定したい, so that 子の起こし方が端末に頼る形へ戻ったら気付ける

#### Acceptance Criteria

1. The 判定 shall コードページ 932 の端末（またはそれと同じ条件を作った子のプロセス）から、性能改善ループの道具が子の PowerShell を回すのと同じ起こし方で子を回し、子が出した日本語を含む決まった見本が 1 字違わず届けば合格、違えば不合格とする（表示するだけでなく合否を付ける）。
2. If 子の起こし方が端末の文字コードに頼る形へ戻される, the 判定 shall 不合格になる。
3. The 判定 shall 見本が 932 の条件で端末に頼る読み方をすると壊れることを先に確かめ、壊れない条件では「戻りを捕まえられない」として不合格にする（偶然に頼らない）。
4. The 判定 shall 判定を回す端末の文字コードの設定を書き替えない。932 の条件は、判定のために起こす窓の無い子のプロセスだけが持つ端末に作る。
5. The 判定 shall 判定を回す機械の ANSI・OEM のコードページが何であっても（開発者の PC でも CI のランナーでも）、同じ合否を出す。
6. Where 判定が一時ファイルを作る, the 判定 shall それをワークツリーの `target\` の下だけに作る。

### Requirement 7: 手元での確かめ

**Objective:** As a 性能改善ループを回す開発者, I want 932 の端末のまま道具を軽く回して確かめたい, so that 判定だけでは見えない所にも化けや書き替えが無いことを実物で確かめられる

#### Acceptance Criteria

1. While 端末の文字コードがコードページ 932 のまま, when `perf-loop.ps1 selftest` を回すとき, the 性能改善ループの道具 shall 緑（終了コード 0）で終わり、回す前と後で端末の文字コードの設定が同じである。
2. While 端末の文字コードがコードページ 932 のまま, when 出力先の根（`-OutRoot`）をワークツリーの `target\` の下に向けて `perf-loop.ps1 preflight` と、子の PowerShell を起こす計測のサブコマンドを 1 つ以上 `-DryRun` で回すとき, the 性能改善ループの道具 shall 直す前と同じ終了コードで終わって末尾に `PERF-LOOP RESULT` の行を出し、回す前と後で端末の文字コードの設定が同じである。
3. The 確かめ shall 自己較正と試験用の空回し（`-DryRun`）と要件 5・6 の判定だけで行い、実機を何分も回す計測を要しない（静かな机も要らない）。
4. The 確かめ shall その結果（端末の文字コード・回したコマンド・終了コード・回す前と後の端末の文字コードの設定。要件 1.2 と同じく、その時点の端末の値）をこの spec の文書に残す。

### Requirement 8: 注記と文書を実際の動きに合わせる

**Objective:** As a 開発者, I want 注記と文書が道具の実際の動きと食い違わないこと, so that 次に道具を直す人が誤った説明を信じない

#### Acceptance Criteria

1. The `tools/perf/README.md` shall 子の出力の受け取り方（端末を書き替えずに、読む側で端末に依らず正しく受け取ること）と、道具が端末へ出す文が ASCII だけであることを、実際の動きと食い違わずに書く。
2. The `perf-loop.common.ps1` の頭書と子を起こす所の注記 shall 実際の動きと食い違う記述（「子の中で端末の文字コードを切り替える」「端末そのもののコードページは変えない（子の中だけ）」など）を残さない。
3. The steering `tech.md` の段 `encoding check` の説明と「道具が端末へ出す文は ASCII だけ」の行 shall 判定の対象に `tools/perf/` が入ったことに合わせる（「`tools/perf/` を除く」を残さない）。
4. The スキル `perf-loop-iteration` の注記 shall 直しの後に古くなる記述（「説明文の日本語は端末の文字コードで化けることがある」）を、なお化けうる範囲（道具が端末へ写した子の中身。例: Python の判定器の日本語の報告）だけに狭めて書き直す（道具が自分で出す文は ASCII になるので化けない。判断を `code=` で行う手順そのものは変えない）。

### Requirement 9: 変えないもの

**Objective:** As a 開発者, I want 直しの範囲の外にあるものが変わらないこと, so that 性能改善ループの手順やほかの道具と衝突しない

#### Acceptance Criteria

1. The 性能改善ループの道具 shall サブコマンド・引数・終了コードの約束・出力先の配置を変えない。
2. The 直し shall `tools/perf/` の Python のスクリプトと見本（`fixtures`・`fixtures-loop`）に触れない。

5. The 直し shall 依存を足さない。

### Requirement 10: 一時ファイルはワークツリーの `target\` の下だけ

**Objective:** As a 開発者, I want 道具の一時ファイルと作業用のフォルダがワークツリーの `target\` の下だけにあること, so that 掃除漏れが OS の一時フォルダに残らず、一時ファイルの置き場の決まりがどの道具にも同じく効く

#### Acceptance Criteria

1. The 性能改善ループの道具 shall 一時ファイルと作業用のフォルダ（自己較正 `perf-loop.ps1 selftest` の作業用のフォルダ・`invoke-cpu-sample.ps1` の xperf の出力の受け皿と `-Probe` の作業用のフォルダ）を、ワークツリーの `target\` の下だけに作る（OS の一時フォルダは使わない）。
2. When `target\` が無いとき, the 性能改善ループの道具 shall 外へ逃がさずに `target\` の下を作り直して使う。
3. The 性能改善ループの道具 shall 出力先の根（`-OutRoot` と既定の `%LOCALAPPDATA%\areka-diag\perf-loop`）の決め方を変えない（出力先は一時ファイルではない。要件 9.1）。
