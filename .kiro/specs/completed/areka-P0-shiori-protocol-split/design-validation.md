# 設計検証レポート: areka-P0-shiori-protocol-split

> 対象: `design.md`（FINALIZED）／典拠: `requirements.md`・`research.md`・`spec.json`（language=ja）・`.kiro/steering/`。
> 種別: 非破壊の物理／符号化形リファクタ（契約セマンティクス不変）。
> 実行モード: 非対話（検証判定のみを提示。ユーザーへの質問なし）。

## 設計レビュー要約

設計は完了仕様 `areka-P0-shiori-protocol` の単一 TOML 正本を、契約セマンティクスを一切変えずにフラグメント群（論理 SSOT）＋keyed/inline 符号化形へ再編する非破壊リファクタを、要件 1–9 へ一意にトレースしつつ、結合順の単一真実源（DD-1＝明示マニフェスト）・同値ゲート 8 要素＋正規化規則（DD-2）・使い捨て一回限り変換/検証（DD-3）・C-2 削除（DD-4）・kind 別レイアウト（DD-5）・要件改訂継承（DD-6）・README/典拠整合（DD-7）まで単一権威で確定している。ディスカッション裁定（要件7=削除／要件9.5=一回限り検証プログラム）はそのまま反映され、未決ギャップは無い。総じて実装着手可能な品質。

## 重要課題（Critical Issues・最大3件）

検証フォーカス（同値ゲートの厳密性／単一真実源化／削除の非破壊順序／completed 不変／provenance 整合／スコープ健全性）を精査した結果、GO を覆す重大課題は検出されなかった。以下は実装前に潰しておくと品質が上がる軽微〜中程度の指摘（いずれも GO を妨げない）。

🟡 **Issue 1（中）: 同値ゲートに「キー集合の網羅性（漏れ落ち）」検査が明文化されていない**
**Concern**: DD-2 の 8 要素は entry/field/共有/silence/description/provenance/封筒/予約ヘッダの「値一致」を厳密化しているが、field の inline table が持つ任意キー（`response_meaning`/`silence_ref`/`reference_variadic`）を「欠如 vs 値」で一致条件にする一方、未列挙の新規キーや想定外キーが両側に現れた場合の「比較対象に含まれないキーはゼロであること（残差キー＝空）」を明示する規則が無い。緩いと「比較対象外のキーに契約情報が紛れる」抜け穴が残り得る。
**Impact**: 9.4 の「差分検出時は不合格」が、列挙外キーに対して空振りする理論的リスク。
**Suggestion**: ゲート判定に「両側の全キー集合が DD-2 の 8 要素＋正規化規則で被覆され、未被覆キーが存在しないこと（残差ゼロ）」を 1 行追加（受け入れ基準の閉包条件化）。
**Traceability**: 3.4 / 9.2 / 9.4
**Evidence**: design.md §「Batch / Job Contract（同値ゲートの判定基準・DD-2）」比較対象 8 要素・正規化規則。

🟡 **Issue 2（軽）: `[mapping]` 記述データ改訂（4.6）の同値判定が「共有テーブル値一致」と「意味保存」で二重基準になり得る**
**Concern**: 4.6 は `canonical_key`/`alias_key` 等を新キー表現へ「意味不変で更新」する。一方 DD-2 の比較要素3（共有テーブルの各キー・値）は素直な値一致を要求する。`[mapping]` だけは値そのものが新表現へ変わるため、要素3 の素直な値比較では `[mapping]` が差分判定されかねず、「意味保存（値キー⇄テーブルキー対応の同一性）」という別基準が必要になる。
**Impact**: `[mapping]` を要素3 にそのまま含めると正当な改訂を不合格化、除外すると 4.6 の意味保存が無検証になる境界。
**Suggestion**: 同値ゲートで `[mapping]` を「意味保存（対応関係の同一性）」として別正規化する旨を要素3 の例外として明記（Testing Strategy の「マッピング意味保存」項を受け入れ基準側へ昇格）。
**Traceability**: 4.6 / 3.4
**Evidence**: design.md §Testing Strategy「マッピング意味保存」と §DD-2 比較要素3 の関係。

🟡 **Issue 3（軽）: 削除の不可逆性に対する baseline 保全先が「エビデンス」として粒度不明**
**Concern**: 7.2/9.5 は「変換前 parse を baseline 捕捉→ゲート合格後に削除」を規定し非破壊順序は正しい。ただし削除後に旧ファイルが tree から消えるため、後日ゲートを再現したい場合の baseline（旧 parse スナップショット or 旧ファイルの git 履歴ポインタ）を「合否エビデンス」のどこに残すかが粒度として未確定。
**Impact**: 監査・将来の再検証時に旧形の再現手段が git 履歴頼みになり、エビデンスの自己完結性が下がる。
**Suggestion**: エビデンスに「baseline の所在（削除コミット直前の blob ハッシュ／旧 parse の正規化ダンプの保存先）」を 1 項目含める旨を明記。
**Traceability**: 7.2 / 9.5 / 6.3
**Evidence**: design.md §System Flows「capture parse of old toml as baseline」「delete old toml」・§Monitoring。

## 設計の強み（Strengths）

1. **非破壊の証明経路が単一権威で閉じている**: 「論理 SSOT＝フラグメント群→マニフェスト順 merge→8 要素同値ゲート合格→削除」という一本道を、DD-1（結合順の単一真実源＝マニフェスト・接頭辞は従属）と DD-2（reference/variadic/任意キー正規化）で曖昧さなく確定。要件 3.3/3.4/9.4/9.5 の「契約不変の証明可能性」がフロー・Traceability・Testing Strategy の三層で裏打ちされている。
2. **スコープ規律が明確**: 恒久的な Rust codegen・doc/Web 生成器・常設バリデータ・正準ビュー常設をすべて Out of Boundary に置き、In scope を「フラグメント群＋共有＋マニフェスト＋一回限り検証＋要件/README 改訂」へ限定。completed/ 履歴不変（DD-6）と ukadoc provenance 整合（DD-7・6.3）も literal 改変を禁じる形で正しく扱われている。

## 最終判定

- **判定: GO**
- **根拠**: ディスカッション裁定（要件7=削除／要件9.5=一回限り使い捨て検証）と DD-1/2/5/6/7 がいずれも単一真実源へ解決され、同値ゲートが「契約不変」を証明する受け入れ基準として機能する水準にある。検出された 3 件はいずれも受け入れ基準の文言精緻化レベルで、設計の骨格・境界・非破壊順序を覆さない（許容リスク）。
- **次ステップ**: GO のまま `/kiro-spec-tasks areka-P0-shiori-protocol-split` へ進めてよい。Issue 1–3 は設計ディスカッションで「同値ゲートの閉包条件・`[mapping]` 例外正規化・baseline エビデンス粒度」の 3 点を受け入れ基準へ 1 行ずつ追記して取り込むことを推奨（任意・実装着手は阻害しない）。
