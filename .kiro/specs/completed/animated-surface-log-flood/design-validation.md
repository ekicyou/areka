# 設計の検証: animated-surface-log-flood

> 2026-10-30・`/kiro-validate-design`（対話なしで実行）。入力: `spec.json`（language=ja）・`requirements.md`・`design.md`・`research.md`・steering（`product.md`・`tech.md`・`structure.md`・`logging.md`）。設計の主張は、ブランチ `claude/animated-surface-log-flood-54fed6`（`54f49385b`）のコードと突き合わせた。実機・SSP・areka のプロセスには触れていない。

## まとめ

設計は、記録の出し分け（コマ送りだけの適用は DEBUG）と、命令列の比べで決めた矩形だけを重ね直す口の 2 本で、要件 1〜4・8 にまっすぐ届いている。画素が同じになる理屈・下敷きの絵の安全・`reveal` の渡し方は、コードと突き合わせて正しいと確かめた。残る心配は「CPU が本当に下がるか」を作る前に測っていないことと、隣の spec との行の合わせが済んだ記録が無いことの 2 点で、どちらも設計を作り直さずに討議とタスクで片づく。判定は **GO**。

## コードと突き合わせて確かめたこと

- **命令列の比べで画素が同じになるか**: 動く絵のコマは、コマごとに別の `ElementId` の命令になる（`plan_always.rs:53` の `ElementId(picture)`）。だからコマが替わると命令が違うものになり、矩形に入る。全透明のコマは命令ごと消える（同 54 行目）が、設計の「先頭と末尾の同じ並びを除いた残り」の求め方は、命令の数が違っても成り立つ。置き場の矩形（`transform.offset() + trim_offset`、幅と高さは `uv_rect`）は `blit.rs:111-114` の書き先と同じで、重ね方は画素ごとに独立している（SourceOver）。矩形の外の画素は前の絵と同じになる、という設計の理屈は正しい。
- **`Overlay` 以外の命令でいちから合成へ倒れること**: `is_implemented()` は `Overlay` だけ（`method.rs:142`）。pattern の側は plan で選り分けられていて、element の側は `research.md` §3.4 の表でぱすたの面 1002 は全部重ねるだけ。倒れる条件は面 1002 では起きない見込み。
- **下敷きの絵の安全（`partial_base`）**: 合成器は対象ごとに 1 つ（`target.rs:54`）なので、`base_ops` をほかの窓に書き替えられることは無い。下敷きは控えの中の `last_show` の絵を読むだけで、書く先は合成先の席（`show.rs:102` の `native_scratch`）。控えから追い出す `take_recycled` は合成と記録が成功した後（`show.rs:168`）で、`last_show` の絵はそのとき最近使った側にいる。失敗で戻る道（`GraphicsCore` が無い・表示の記録の失敗・合成の失敗・全透明の縮退）は、どれも合成の前に `partial_base` を偽にしたあとに通るので、次は必ずいちから合成になる。控えに当たった回と `InvalidateCache` の後も偽になる。抜けは見つからなかった。
- **`apply_show` の呼び手と `reveal`**: 呼び手は 4 か所だけ（`hub.rs:197`・`visibility.rs:108`・`refresh.rs:121`・`replace.rs:124`）。`show_target` は呼ぶ前に `was_visible` を取っている（`visibility.rs:97`）ので `!was_visible` を渡せる。差し替えは新しい対象で `last_show` を引き継がない（`replace.rs:107-113`）ので、要件 1.4 のとおり INFO になる。
- **失敗の間引きで既存のテストが壊れないか**: `presenter_display_failure_tests.rs` の 4 点を回す輪（457・508・588 行目）は、失敗の点ごとに文脈の文字列が違う（`display.rs:90-96`）。間引きの鍵が「文脈＋HRESULT」なので、どの回も ERROR がちょうど 1 本のまま通る。`device_err` を使うのは emo-present の中では `display.rs` だけで、emo-text は自分の `device_err` を持つ（`draw.rs:823`）。
- **新しい DEBUG の行と道具**: 性能の道具は行を文言 `apply(ShowSurface): 表示・マスクを更新` で丸ごと拾う（`judge-perf.py:507`・`judge-followup.py:115`・`perf-rank.py:118`・`invoke-followup-checks.ps1:137`）。新しい行 `apply(ShowSurface): 重ね直しの範囲` とは混ざらない。表示の行と perf の行が隣り合うことを縛るテスト（`presenter_perf_log_tests.rs:176`）にも、新しい行が表示の行の前に出る形なら当たらない。

## 大事な指摘（3 件）

### 指摘 1: CPU が下がるかを、作る前に測っていない

- **心配**: 直すのは合成だけで、当たりのマスクの作り直し（`budget.rs:504`・面の全体の画素をなめる）・GPU へ上げる絵の作り直し（`record_display`・1.5 MB）・wintf の全面の描き直しは残る（判断 D4）。release 版の 20% のうち合成がどれだけかは測っていない（`research.md` の調べ物 ⑴・設計の Performance & Scalability）。見積もりでは、面 1002 の合成は 1 回あたりおよそ 60 万画素で、release 版では 1 コアの数 % ぶんにしかならないかもしれない。さらに新しい道は、前の絵を消してから全部写すので、1.5 MB を 2 回なめる。
- **なぜ困るか**: 要件 6.2（release 版・debug 版とも中央値を直す前より下げる）は必須の線なのに、下がらなかったときの道が設計に無い。設計にあるのは要件 6.3（SSP を上回ったら仰ぐ）の道だけ。実装を全部終えてから実機で「下がらない」と分かると、マスクを矩形にする（wintf に触る）かどうかを、そこから決め直すことになる。
- **直し方**: タスクの最初に、コードを変えずに測る段を置く。ぱすたの面 1002 を `areka_emo_present=debug` を足して短く走らせ（release 版と debug 版）、perf の行の `t_compose_us`・`t_mask_us`・`t_upload_us`・`t_total_us` の割合を読む（どれも今ある行・道具）。合成の割合が小さく、要件 6.2 に届く見込みが無ければ、実装の前に開発者に仰ぐ。設計には「要件 6.2 に届かなければ、段ごとの所要を添えて止まり、開発者に仰ぐ」と 1 行書き足す。前の絵の写しは、消してから写すのでなく、写すだけで済む形にできないかを実装で確かめる（`composed.rs` は境界の外なので、今ある口で足りるときだけ）。
- **要件**: 6.2・6.3・3.1
- **設計の箇所**: 「Non-Goals」・「Performance & Scalability」・「実機の測り」の合格の線

### 指摘 2: `seriko-pattern-calls` と触る行を合わせた記録が無い

- **心配**: 要件の Boundary Context と要件討議の決め 5 は「設計に入る前に、触る行を `seriko-pattern-calls` のセッションと合わせる」としている。設計は触る行の表（emo-compose で触る所）を作ったが、`research.md` の設計の段の記録を見ると、向こうのブランチの `requirements.md` と `research.md` を読んだだけで、向こうのセッションに見せて答えをもらってはいない。向こうは `plan_extent.rs` にも触る見込みで、`move` で合成の外形がコマごとに替わるようになると、下敷きの絵と外形が合わず、毎回いちから合成へ黙って倒れる（正しさは保つが、CPU の効き目が消える）。
- **なぜ困るか**: 要件が求める段取りが抜けている。並んで走るウェーブで重なりが後から分かると、片方を作り直すことになる。
- **直し方**: 設計討議の中で、触る行の表を `seriko-pattern-calls` のセッションへ送り、次の 2 点の答えをもらって `research.md` に書く: ⑴ `lib.rs` の `build_plan` の引数を変えるか、⑵ `move` で合成の外形（`Extent`）がコマごとに替わるか。⑵が「替わる」なら、Revalidation Triggers の書き方を「重さの見込みが変わる」から、本 spec の効き目が消える場面として、はっきり書き直す。
- **要件**: Boundary Context（Adjacent expectations）・3.1
- **設計の箇所**: 「emo-compose で触る所」・「Revalidation Triggers」

### 指摘 3: 失敗の間引きが、コマ送りでない適用にも効く

- **心配**: 設計は装置の失敗の間引き（2 回目からは DEBUG）を、コマ送りだけの適用に限らず、同じ対象・同じ原因・成立をはさまないあいだのすべての適用に効かせる（「装置の失敗の記録」の節）。たとえば GPU が失敗し続けているあいだに面が替わったときも、その失敗は既定の水準では見えなくなる。要件 1.6 は「失敗したら今と同じ水準・同じ文言」、要件 4.3 は「コマ替えのたびに積み上げない（同じ窓・同じ原因につき、続くあいだは 1 回）」で、設計は 4.3 を広く読んでいる。
- **なぜ困るか**: 答えでコードが変わる。間引く範囲を「コマ送りだけの適用」に絞るなら、`device_err` に渡す値を `frame_step` で切り替える形になる。今の形のままなら、要件 1.6 の読み方を要件か設計に書き残しておかないと、後のレビューで食い違いとして挙がる。
- **直し方**: 設計討議で、どちらにするかを決める。推奨は今の設計のまま（最初の 1 回は今と同じ ERROR で出るので、記録の無い失敗の道は作らない。原因が同じなら、面が替わっても知らせる中身は同じ）。そのうえで、要件 1.6 と 4.3 の読み合わせを設計の Error Handling の表に 1 行で書く。
- **要件**: 1.6・4.3
- **設計の箇所**: 「装置の失敗の記録（`command.rs`・`display.rs`）」・「Error Handling」

## 良いところ

1. **動く層を種類で見分けず、命令列の比べで矩形を決める**。動く絵のコマ・SERIKO のコマ・着せ替え・面の替わり（外形が同じなら）・後から来る `move` のどれにも、同じ仕組みが効く。正しさの理屈が「矩形の外の画素に重なる命令の並びは同じ」の 1 行で言えて、コードの重ね方（画素ごとに独立した SourceOver）とも合っている。`blit.rs`・`plan.rs` を 1 行も変えずに済む。
2. **下敷きの安全を 1 つの真偽（`partial_base`）にまとめ、合成の前に偽にする**。失敗の道を全部たどっても、壊れた下敷きを使う形が作れない。控えの容量 3 の LRU・席の交代・失敗し得る呼び出しを回収より前に置く順など、今ある決まりを 1 つも崩していない。
