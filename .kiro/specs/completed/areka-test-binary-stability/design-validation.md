# 設計の確かめ: areka-test-binary-stability

> 2026-11-01 `/kiro-validate-design`（対話なしで実行）。枝 `claude/kiro-start-areka-test-binary-stability-dec94e`（`a431f186`）の `design.md`・`requirements.md`・`research.md`・`brief.md`・steering を読み、設計が挙げた関数・行・ファイルの長さをコードで確かめた。テスト・ビルド・負荷の走行は回していない。

## まとめ

設計は「名指しの仕掛けを先に入れて較正する → 決めた条件で測る → 原因の候補ごとに決めた直しを当てる → 待ちを揃える → 最後に 1 度だけまとめて確かめる」という段の構成で、要件 1〜10 の全項目を部品へ割り当てている。挙げた行と形はコードとほぼ合っている（下の「コードとの突き合わせ」）。ただし、落ちたテストを名指す仕掛けが、落ちたスレッドがテストのスレッドでない場合（ドライバ・COM・足場のスレッド）に、並走するテストの中から犯人を絞れない。測りの回数も「2 回目からは赤のテストに絞る」の決まりに沿っていない。この 2 点と、許可の待ちの上限の 1 点を直せば、実装へ進める。

## 重大な指摘（3 件）

### 指摘 1: 落ちたスレッドがテストのスレッドでないとき、どのテストかを名指せない
- **問題**: `CrashReport` が書くのは「落ちたスレッドの名前」と「生きているスレッドの名前の一覧」だけ。落ちる候補 B〜D（COM の物の解放・ドライバのスレッド・作ったのと別のスレッドでの捨て）では、落ちるのは名前の無いドライバや COM のスレッドになりやすい。既定のスレッドの数（論理 CPU の数）で回すと一覧には十数本のテストの名前が並び、そのうちどれが GPU の装置を持っていたのかが分からない。較正のテストは `--ignored --exact` で 1 本だけ回すので、一覧に自分の名前が出るのは当たり前で、並走の下で名指せるかは確かめていない。また、GPU の DLL（`d3d11`・ドライバ）が読み込まれた後に誰かが最後の受け手を差し替えても、較正では気づけない。
- **影響**: 要件 1.1 の「落ちたスレッドの名前（＝テストの名前）」が、肝心の候補のときに満たせない。名指せなければ、スレッドの数を絞る手（要件の目的）も、要件 9.3 の「赤のテストに絞る」も使えない。
- **提案**: `GpuSlots` の `take`／`Drop` で、許可を持つスレッドの名前を小さな表（上限 4 本）に載せ降ろしする。落ちの報告で `AREKA-CRASH-HOLDER name="..."` の行として書く（割り当ての無い固定の配列で足りる）。較正のテストは、許可を 1 つ取り、`GraphicsCore` を作った後に、名前の無いスレッドで `RaiseException` を起こす形にする。これで「持ち手の行に自分の名前が出ること」と「GPU の DLL を読み込んだ後も受け手が生きていること」を 1 回で確かめられる。`wintf` の lib は並ぶテストが少ないので、今の一覧のままでよい。
- **対応する要件**: 1.1・1.2・9.3
- **設計の箇所**: Components「CrashReport」の Service Interface（較正のテスト）と Implementation Notes、Testing Strategy「結合」の較正

### 指摘 2: 測りの回数と範囲が「2 回目からは赤が出たテストに絞って短く」に沿っていない
- **問題**: 「測りの条件」の表で、X2・X3 の範囲・負荷・回数がどれも「X1 と同じ」（frame の族の約 28 ファイル・論理 CPU の 2 倍の負荷・10〜20 回・1 回 10 分まで）になっている。X1 も、最初に落ちて報告が採れた時点で止める決まりが無い。最悪の場合は、負荷の下の走行が X1 20 回＋X2 20 回＋X3 20 回になる。落ちの報告が名指した組へ X2・X3 を絞る段取りも無い。
- **影響**: 開発者の決まり（高負荷のテストを何度も回さない・2 回目からは赤のテストだけ）と要件 9.3 から外れる。机を何時間も占めるので、ほかのセッションを待たせる。
- **提案**: ① X1 は、報告つきの落ちが 1 回出たら止める（目的は報告を採ること）。② X2・X3 の範囲は、X1 の報告の持ち手の行と生きているテストの一覧に出たテストのモジュールに絞る（落ちに並走が要るなら、並走の相手として X1 の範囲を残す理由を `load-repro.md` に書く）。③ 止め方を左右で分ける。「落ちが残る」は 1 回落ちた時点で決まるので止める。「落ちが消える」は決めた回数（20 回＝見逃しの見込み約 1%）を回す。④ 走行の系列ごとに「回数×1 回の見込み」の所要時間を、始める前に記録して伝える。
- **対応する要件**: 1.3・1.4・9.2・9.3
- **設計の箇所**: System Flows「測りの条件」の表と、その下の「回数の訳」

### 指摘 3: 許可の待ちの上限は、檻が確かめる道と本物の道が分かれる。負荷の下で新しい「許さない赤」を生みうる
- **問題**: `take_with(now, pause, idle)` は休みを `pause: FnMut(Duration)` として受ける。一方、本物の休みは「`freed` の時間つきの待ち」で、これは Mutex の握り（guard）を渡さないと書けない。そのため、本物の `take` は `take_with` と別の書き方になり、檻（偽の時計）が本物の道を通らない。さらに、許可の待ちの `［止まった］` は「許す赤の項に入れない」と決めている。負荷の下で GPU のテスト 4 本がそれぞれ `GPU_PERMIT_IDLE` より長く許可を持てば、最後の負荷 5 回（要件 9.6）で、許さない赤として出る。
- **影響**: 要件 6.3 の檻が本物の待ちを確かめない。最後の確かめの門（9.6）が、上限の値の選び方しだいで赤になる。
- **提案**: 決め手を純粋な関数にする（例: `judge(now, last_return_at, returned, idle) -> Continue | Stalled | Capped`）。本物の `take` は、`freed.wait_timeout_while` の輪の中でその関数を呼ぶだけにし、檻はその関数と `try_take` の組で確かめる。`GPU_PERMIT_IDLE` の決め方（例: X1〜X2 で測った許可の持ち時間の最大の 2 倍以上で、`SPIN_WAIT` の 30 秒を下回らない）は、件 1 の直しの前に設計に書いておく。値を決めるのは要件 6.6 のとおり直しの後でよい。
- **対応する要件**: 6.1・6.2・6.3・6.6・9.6
- **設計の箇所**: Components「GpuSlots」（`take_with` の形と Risks）、Error Handling「赤が出たときの読み方」の許可の待ちの行

## 設計の良いところ

1. **原因が分かる前に直しの形を決めない**: 段 1〜5 の順と「原因ごとの直し」の表（候補 A〜D ごとに、見分ける印・直し・所要時間の線を決めている）で、測りの結果から直しが機械的に決まる。候補 A・C は 1.20 倍の線を越える見込みが高いと先に書き、越えるならその場で止まって裁定を仰ぐ（要件 9.11）。前の測り（許可 2 つで中央値 95.2 秒÷64.1 秒＝約 1.48 倍・`spine_wait.rs` 403〜405 行の説明）と数字が合っている。
2. **檻を実時間から外し、揺れの元そのものを無くす**: 短い掴みの檻は、放す側のスレッドと 200 ms の眠りをやめる。代わりに、拒みを観測した同じスレッドの `#[cfg(test)]` の継ぎ目で掴みを放す。`rename_patiently`（`install.rs` 642〜654 行）は期限を拒まれた時にだけ確かめるので、放した後の次の試しは必ず通り、本番の間隔も上限も変わらない。件 4 は `remove_dir` そのものを消す。空の `balloon\` は `subdirs`（`catalog.rs` 374 行）で 0 件として扱われる。どちらも sleep も締切の延長も足さずに根本を消している（要件 5.1〜5.4・8.1・10.1）。

## コードとの突き合わせ（確かめた事実）

- 行とファイルの長さは設計どおり: `spine_wait.rs` 462 行（`join_bounded` 385 行・`GpuSlots::take` 420 行は `wait_while` で上限なし）、`frame_test_support.rs` 974 行（`manual_balloon_runtime` 915 行・許可を取らない・呼び手 4 ファイル）、`spine.rs` 937 行（出し直し 367〜371 行・`call_count` 345 行）、`mod.rs` 828 行、`spine_conformance_support_tests.rs` 959 行、`ghost_switch_test_support.rs` 722 行（`remove_dir` 223 行）、`install_commit_tests.rs` 857 行、`main.rs` 986 行。`spin_wait_until(` の直の呼び出しは 15 か所で、設計の WaitMigration の表と一致する。`install/` の写しの `join_bounded` は 2 つ（`desk_pick_tests.rs` 60 行・`fetch_url_tests.rs` 80 行）。
- `.CRT$XCU` の据え付け: `areka` は bin だけのクレート（`emo2_boot` は `main.rs` の子）で、`cargo test -p wintf --lib` も lib が根の実行ファイルになる。どちらも根のクレートに置く `#[used]` の静的な値なのでリンクで落ちない。MSVC の CRT は自分の受け手を `.CRT$XCAA` で据えるので、`XCU` の方が後に走って上書きする（前の受け手へ回す設計で、C++ の例外の扱いも保たれる）。EXE の初期化子はローダーの錠の外で走るので、候補 B の `CoIncrementMTAUsage` も呼べる。std が据えるのはスタックの溢れのための vectored handler だけで、最後の受け手とは競らない。いずれも較正で確かめる前提のままでよい。
- `[dev-dependencies]` の機能の足し（resolver 2）: 本番のビルドの機能は変わらない（設計の主張どおり）。`Win32_System_Diagnostics_Debug` は `areka-ghost` が通常の依存で既に有効にしているので、`areka` には実質の変化が無い。

## その他の気づき（重大でない・実装の段で拾えばよい）

- `Win32_System_Diagnostics_ToolHelp` を dev だけで足すと、`windows` クレートの機能の組が `cargo build` と `cargo test` で分かれる。初めての `cargo test` で `windows` とその上の全クレートが別の成果物として組み直され、`target` も太る（`tools/test-all.ps1` の中では `cargo test --workspace` だけなので分かれない）。3 つの関数（`CreateToolhelp32Snapshot`・`Thread32First`・`Thread32Next`）を、テスト専用のファイルで `windows_targets::link!` か `extern "system"` で直に宣言すれば、`Cargo.toml` に触らずに済む。議題 3 の裁定の範囲内なので、どちらでもよい。
- X1 の範囲の `frame_scale_notice_integration_tests` はファイルの名前で、libtest のモジュールの道は `emo2_boot::frame::…::scale_notice_integration_tests`。絞り込みとしては 0 本に当たるが、`emo2_boot::frame` に含まれるので害は無い。数え直しで並べるときはモジュールの道で書く。
- `GPU_SLOTS` を `LazyLock` にしても `&'static GpuSlots` は取れる。ただ、檻用の `GpuSlots::new(2)` を `const fn` のまま保つため、`returned: AtomicU64` を足しても `const` で作れる形を守ること。
- タスクの数: 移行の順 ⓪〜⑽ で、⑵ と ⑻ が 2〜3 タスクずつに割れる見込み。合わせて 18〜20 になり、上限の 20 に近い。候補 D で本番の直しが要るときの切り出し（要件 1.8）の判断を、⑹ の入口に置いておくとよい。
