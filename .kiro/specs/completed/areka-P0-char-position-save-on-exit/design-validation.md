## 1. まとめ

### 2.1 (a) `Some` と「記憶なし」の一致

`default_char_pos` を触る本番コードは次の 4 か所だけだった（`crates/areka/src` をテスト以外で検索）。

- 作る: `placement/spawn.rs:566`（窓を作るとき、全スコープを `Some(既定の位置)` で始める行）。
- `None` にする: `ghost_session.rs:272`（記憶から戻したスコープの既定の位置を消す行）の 1 か所だけ。
- `Some` を書き直す①: `emo2_boot/frame/drain_resnap.rs:383`（並べ直しで動かしたスコープの既定の位置を新しい位置へ揃える行）。動かす対象は `placement/chain_finalize.rs:121`（既定の位置が今の位置と同じスコープだけを動かす条件の行）で選ばれるので、もともと `Some` のスコープにしか届かない。
- `Some` を書き直す②: `placement/follow/window_move.rs:860`（基盤が置き直したとき既定の位置を一緒に運ぶ行）。直前の `window_move.rs:850`（`None` なら何もせず戻る行）があるので、`None` を `Some` に戻すことは無い。

つまり `None` → `Some` へ戻る経路は無く、`Some` → `None` は記憶から戻したスコープに対する 1 か所だけ。設計が `main.rs:734`〜`739`（値の比較で集合を作る所）を「記憶に x・y の両方があるか」へ改めれば、`None` と「記憶に位置がある」はちょうど同じになる。

- ゴーストの切り替え: 窓の束 `GhostWindows` ごと外して作り直す（`app_exit.rs:171`）。作り直しは起動と同じ `prepare_ghost_windows`（`ghost_session.rs:340` で `reopen_ghost_windows` が委譲する行）を通るので、同じ規則で `None`／`Some` が決まる。
- シェルの切り替え: `placement/reseed.rs` は `default_char_pos` に触らない（検索で 0 件）。窓も作り直さない。

### 2.2 (b) 読む位置は動かした後の位置

`move_window_to`（`window_move.rs:45`）→ `enqueue_window_set_pos`（`window_move.rs:633`）は、同じ呼び出しの中で窓の位置の写し `WindowPos.position` を書き換える（`window_move.rs:731`〜`739`）。設計が呼び出しを置く `drain_resnap.rs:388`（印 `ChainFinalized` を置く行）の直後は、移動のループ（`drain_resnap.rs:358`〜`371`）の後なので、同じフレームの中で動かした後の位置が読める。

窓の大きさについても、並べ直しは「全スコープの窓の大きさが出ている絵の大きさと同じ」ことを確かめてから走る（`drain_resnap.rs:471`〜`477`）。だから「下端の中央の x」へ直すときに使う幅は、実際に出ている絵の幅である。

あわせて、書いた値が次の起動で同じ場所に戻るかも追った。書くとき `左上 x ＋ 出ている幅/2`（`persist.rs:53`）、戻すとき `記憶の x − 準備のときの幅/2`（`persist.rs:64`・`persist.rs:358`〜`363`）、そのあと絵が出て大きさが変わるとき下端吸着の窓は中央を保って付け替える（`window_move.rs:296`〜`305`）。3 つを通すと左上 x は元の値に戻る（整数の割り算の端数も打ち消し合う）。準備のときの幅と出ている幅が違う（＝今まで相方が並べ直されていた）場合でも、相方は前回と同じ場所に立つ。

### 2.3 (c) 1 度だけ・シェルの切り替えでは通らない

- 呼び出しは印の確認（`drain_resnap.rs:327`）を通った後にしか置かれない。
- 印を外すのは `app_exit.rs:172` だけ（検索で 1 件）。その関数 `close_windows_for_restart` を呼ぶのは `ghost_switch.rs:671` と `ghost_switch.rs:725` の 2 か所だけ（検索で 2 件）。どちらもゴーストの切り替え。
- 拡大率が変わった後の解き直し（`placement/chain_realign.rs`）は印を外さない（`chain_realign.rs:17` の説明と本文）。だからそこでも書く口は通らない。

### 2.4 (d) 切り替えで書く先

`boot_into`（`ghost_switch.rs:775`）は、窓の準備（`ghost_switch.rs:818`・新しいゴーストの根で記憶を読む）→ 起動（`ghost_switch.rs:823`）→ 窓の投函（`ghost_switch.rs:827`）を 1 つの呼び出しの中で順に進める。起動の中で `ghost_session.rs:806`（`on_boot_ok` を呼ぶ行）→ `main.rs:770`（記憶の送り口を差し替える行）が走る。窓は投函の後の段で初めて生える（`ghost_session.rs:322`〜`324`）ので、並べ直しが走る時点の送り口は必ず新しいゴーストのもの。前のゴーストは `ghost_switch.rs:656` で降ろし終えている。

### 2.5 (e) 既定と同じ値の記憶

集合に入ったスコープは `ghost_session.rs:272` で `None` になり、`chain_finalize.rs:121` の条件（`default_x != Some(current_x)` なら動かさない）で必ず対象から外れる。設計の `has_saved_char_pos` が `merge_scope` の分かれ道（`persist.rs:354`）と同じ読み取りを使うかぎり成り立つ。

### 2.6 (f) 今あるテスト

- `placement/follow_drag_tests.rs:626`（`non_dragend_operations_leave_persist_store_byte_invariant`）は、`move_window_to`・`resize_window_to`・重ねる関数・ドラッグ中だけを動かしていて、並べ直しは呼ばない。新しい口を足しても結果は変わらない。設計は説明文だけを直すとしており、それで足りる。
- 並べ直しを通す今あるテスト（`emo2_boot/frame_chain_finalize_tests.rs`・`frame_chain_finalize_restart_tests.rs` など）は、記憶の送り口を置いていない（`emo2_boot` のテストで `PersistWiring` を検索して 0 件）。新しい口は「送り口が無い」の 1 行を出すだけで、記憶には触らない。
- 注意: `frame_chain_finalize_tests.rs:273`〜`283`（待っている間の水準ごとの行数を数える所）は並べ直しの前なので当たらない。並べ直しの後の行は文言を指定して数えている（`frame_chain_finalize_tests.rs:295`〜`303`）ので、行が 1 つ増えても通る見込み。ほかの 10 ファイルほどの並べ直しを通すテストは 1 つずつは見ていない（設計の Risks のとおり、実装のときに回して確かめる）。

## 3. 重要な指摘（3 件）

### 議題 1: 拡大率が変わった後の並べ直しが、2 回目の起動から誰にも効かなくなる（設計に記載なし）

- **気になる点**: 拡大率が変わると全員の幅が変わり、隣り合っていた 2 人の間に隙間が開く。これを直す仕組み（`placement/chain_realign.rs`・完了 spec `areka-P0-dpi-transition-atomicity`）は、起動の最後の並べ直しと同じ判定を使い、`default_char_pos` が `None` のスコープを必ず対象から外す（`chain_realign.rs:27`〜`30` の説明・`chain_realign.rs:156`）。今は一度もドラッグしていない相方が `Some` なので、拡大率が変わっても相方は本体の隣へ戻る。この設計を入れると、2 回目の起動からは全員が `None`（記憶あり）になり、この仕組みは初めての起動の回にしか働かなくなる。
- **影響**: 実機の実測では 200% → 100% で 359px の隙間が開く（`chain_realign.rs:12`〜`13`）。2 回目の起動からは、この隙間が開いたままになる。今は直っている動きなので、利用者から見ると後退に見える可能性がある。一方で「記憶にある位置は勝手に動かさない」という要件 1.2・3.2 の考え方には沿っている。
- **提案**: 設計ディスカッションで裁定する。案ア＝受け入れる（記憶のある窓は動かさない、で統一。設計の Revalidation Triggers と `doc/COMPAT_ARCHITECTURE.md` の記録に 1 行足す）。案イ＝受け入れない（拡大率の解き直しの対象の決め方を別にする。この spec の範囲を越えるので、別の spec として起票する）。どちらでも、この設計の本体は変わらない。
- **要件**: 1.2・2.1・3.2
- **設計の該当箇所**: 「Revalidation Triggers」「RestoredScopes の Risks」（どちらにも記載が無い）

### 議題 2: 並べ終える前に SHIORI の移動の指示で動いた窓は、動いた後の位置が記憶に残る

- **気になる点**: 起動の台本が `\![move]` を出し、相方の絵がそろう前にそれが効くと、並べ終えた時点で読む位置は「台本が動かした後の位置」になる（`emo2_boot/frame.rs:354` の移動の取り出しは `frame.rs:374` の並べ直しより前）。記憶が無ければそれが書かれ、次の起動からはその窓は「記憶あり」として固定される。要件の Introduction は「SHIORI の移動の指示で動いた位置は、今までどおり覚えない（その回かぎり）」と書いている。設計は要件 1.1 の字面に従ったと明記し、`research.md` の 10.4 でも議題の候補に挙げている。
- **影響**: 台本を後で変えても、最初の起動で台本が置いた位置が残り続ける。時間つきの移動は今は即時に反映される（`emo2_boot/move_cue.rs:30` の説明）ので、移動の途中の位置が残ることは無い。
- **提案**: 設計ディスカッションで裁定する。案ア＝設計のまま（並べ終えた時点に見えている位置を書く）。案イ＝「既定の位置と今の位置が同じスコープだけ書く」へ条件を 1 つ足す（台本やドラッグで動いた窓は書かない。ドラッグの分はドラッグの確定がもう書いている）。案イなら要件 1.1 に一言足す。
- **要件**: 1.1・1.4・3.2・Introduction の裁定の段
- **設計の該当箇所**: 「FinalizeHook」の「設計へ送られていた確認の答え」の 4 行目

### 議題 3: 再起動のテスト（13・14）が「準備のときの幅と出ている幅が違う」形を通ると決めていない

- **気になる点**: この崩れは、準備のときの幅と実際に出た絵の幅が違って相方が並べ直される、という形で起きる。直した後に相方が前回と同じ場所へ戻ることは、書くとき・戻すとき・絵が出て大きさが変わるとき、の 3 つの計算が打ち消し合うことで成り立つ（2.2）。テスト 9 は「相方が動く大きさ」と決めているが、再起動のテスト 13・14 は大きさの条件を書いていない。同じ幅のまま組むと、3 つの計算を通らずに緑になる。
- **影響**: 「相方は 1 回目の位置に立つ」（要件 2.1・2.3・5.1・5.2）が、実機で起きる形では固定されないおそれがある。
- **提案**: テスト 13・14 に「2 回目の World も、準備のときの幅で窓を作り、出ている幅への置き直し（再スナップ）を回してから並べ直しを回す。幅は 1 回目と同じく準備と違う値にする」と一言足す。タスクを作るときに反映すれば足り、設計の作り直しは要らない。
- **要件**: 2.1・2.3・5.1・5.2
- **設計の該当箇所**: 「Testing Strategy」の 13・14

## 4. 良い点

- **足す状態が 0**。「記憶に位置が無い」の見分けに今ある `default_char_pos` を、「1 度だけ」に今ある印 `ChainFinalized` をそのまま使っている。2.1 と 2.3 で確かめたとおり、どちらも意味がちょうど合っている。同じことを表す状態を 2 つ持たないので、ずれる余地が無い。
- **閉じる経路に触らない**。書く時機を起動の最後にしたことで、終了・Windows の終了・ゴーストの切り替えの順序（書き手が止まった後に送ると捨てられる、という罠）を丸ごと避けている。きれいに終わらなかった回でも並びが保たれる（要件 2.2）ことが、仕組みの形だけで成り立つ。
