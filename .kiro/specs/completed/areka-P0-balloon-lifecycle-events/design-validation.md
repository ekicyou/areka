## 3. 重要な指摘（3 件）

### 🔴 指摘 1: 最後まで流れたトークの起点が「占有区間の終端」にならないことがある（設計の説明が自分と食い違う）
- **問題**: 「時刻の扱い」は「完了は占有区間の終端に達した後なので…式は終端を返す（5.3 は式の帰結）」と書いた直後に「止まった時刻が終端よりわずかに早く読まれることがある」と書いている。実物では、`TalkClock` の起点は「cue の到着の壁時刻 − cue の時刻」の**最大値**（いちばん遅れて届いた cue に合わせる）で、talk スレッドの刻みは 50 ミリ秒。自然な終わりの止まった時刻は「終端を過ぎた最初の刻み」、起点の遅れは「cue が届いた刻みの遅れの最大」で、どちらも 0〜50 ミリ秒ほどの幅を持つので、**最後まで流れたトークでも `min` が止まった時刻の方を採る場合が珍しくない**（割合は測っていない。読んだ式からの見立て）。表示の側は「中断で終わったか・最後まで流れたか」を知らない（`TalkEnded` は終わり方を運ばない）。
- **影響**: ⑴ 要件 5.3（最後まで流れたら終端が起点）と字面で食い違う（ずれは最大で刻み 1 つ分ほど。実時間で見れば本当の終端より前にはならず、今より正確な側に寄るので害は無い）。⑵ 要件 7.3 の記録が、中断していないトークで「止まった時刻を採った」と出る。実機の確認（8.3）で記録を照合するときに「中断した覚えが無いのに中断の起点」と読み違える。⑶ テスト 3（直前・ちょうど・直後）は式を固定するだけで、5.3 を固定しない。
- **提案**: 終わり方を受け口まで運ぶには dola か sakura の約束を変える必要があり、釣り合わない。**式はそのままにして、読みを確定する**——⒜「5.3 は式の帰結」の一文を消し、「止まった時刻は本当の終端より前にはならない。表示の側の時刻の物差しでは終端より最大で刻み 1 つ分ほど早く読まれることがあり、そのときは止まった時刻を採る（実時間では正確な側）」と書く。⒝ 記録の語から「中断」を外し、「起点＝止まった時刻／占有区間の終端／止まった時刻なし」の 3 値にする。⒞ 互換対応表の起点の行に areka 裁量として書く。⒟ 5.3 の檻は「止まった時刻 ≧ 終端なら終端」、5.1 の檻は「止まった時刻 < 終端なら止まった時刻」と名付けて分ける。
- **対応する要件**: 5.1・5.2・5.3・7.3・8.1
- **根拠**: design.md「時刻の扱い」「VisibilityCore の計測の変更点（記録）」／`talk_clock.rs` の `observe_cue`・`ticker.rs` の既定の間隔・`drive.rs` の `settle_after_tick`

### 🔴 指摘 2: 表 B〜D と「行き違い」の表に載っていない経路が 2 つある
- **問題 ⒜（完了を通らずに相が変わる経路）**: 中断の控えと預かった時間切れの知らせは「現行トークの完了」でしか裁かれない。ところが、中断を受け入れた後・預かった後に、完了の知らせより先に `ForceQuit`・`ShioriDown`・切替の送り出しの台詞の期限切れ・翻訳の輸送路の失敗が来ると、相は `on_talk_done` を通らずに終了系列へ進む。控えと預かりは黙って捨てられ、「送る場面に当たったが送らなかった」の記録が出ない。
- **問題 ⒝（cue を 1 つも出さないトーク）**: 台本が空・`\e` だけ・無視されるタグだけのとき、コンパイルは空の楽譜を返し（冒頭の全消去も付かない）、受け口は 1 度も呼ばれない。kanade の控え（`State.shown`）はそのトークへ進むのに、表示の側の番号と画面の文字は前のトークのまま残る。その後に前のトークのバルーンが時間切れになると、知らせは表 D の D2 で「次のトークが既に始まっていた」として捨てられ、読み終えたバルーンのダブルクリック（表 C）では Reference0 が中身の無い側の台本になる。設計はこの種のトークを、数を数える案を退ける理由としてだけ挙げ、「残る行き違い」には載せていない。
- **影響**: ⒜ は要件 7.2（送らなかった理由を記録する）と Error Handling の「送らない分岐・捨てる分岐はすべて記録を残す」の穴。⒝ は要件 2.2・3.2（隠れた／閉じたバルーンに出ていた台本）と食い違い、`OnBalloonTimeout` が 1 回失われる。起きる頻度は低い見込み（⒜ は終了の間際、⒝ は中身の無い台本を返すゴーストだけ）。
- **提案**: ⒜ 終了系列へ入る共通の所（選択の帳簿を掃除している所と同じ場所）で、控えと預かりが残っていれば理由つきで 1 行記録して捨てる、を `balloon_events` の小さな関数として足す（`schedule/mod.rs` の足し分が 60 行の閾値の内に収まるかを数え直す。触る腕が `mod.rs` の外に出るなら設計に書く）。⒝ は直すには「楽譜が空だった」を kanade へ戻す口が要り釣り合わないので、「残る行き違い（記録して許す）」に 1 項足し、互換対応表に書き、表 D の D2 の檻に「間に cue の無いトークが挟まった」場合を 1 本足して振る舞いを固定する。
- **対応する要件**: 2.2・2.6・3.2・4.5・7.2
- **根拠**: design.md「規則の優先順位」表 B・D／「スレッドをまたぐ行き違い」／「Error Handling」／`schedule/mod.rs` の `force_quit`・`to_unloading_fault`・`change.rs` の `on_talk_wait` の期限の腕・`compile.rs` の冒頭の全消去の前置の条件

### 🔴 指摘 3: 既存のテストの直しが 1,000 行の上限に当たる所と、触るファイルの見立ての漏れ
- **問題**: 行数の決まりはテストのファイルにも掛かる。「時間切れを期待する檻に、占有終端の後へトークの終わりを届ける」直しの対象のうち、`balloon_visibility_tests.rs` は今 **982 行**（余裕 18 行）で、補助 `display_end` を使う所が 7 つある。1 か所 1 行で済まなければ超える。設計の行数の見立ては本体のファイルだけで、テストのファイルの余裕を見ていない。あわせて、§2 の `schedule_variant_tests.rs` が触るファイルに無い。`msg.rs` の変種の網羅のテストと `actor.rs` の振り分けは `areka-P0-mcp-get-status` も同じ並びへ行を足す見込みなので、後からマージする側の足し直しが要る（数を手で書いている所があれば、取り込んだ後に数え直す）。

## 4. 行き違いを具体的な並びで追った結果（問題なし）

| 並び | 追った結果 |
|---|---|
| 時間切れの知らせ N が、完了 N より先に kanade へ届く | 表 D の D5 で預かり、完了で表 B の B5 が送る。完了の後が定常でなければ B2 で捨てて記録。預かりは控えの中の印なので、次の再生の開始で控えごと置き換わり、永久には残らない |

| ダブルクリック（kanade では再生中）→ 止める指示より先にトークが自分で終わる | 控えが立ち、完了は `Ended` で届く。表 B の B4 で `OnBalloonClose`（設計で決めたこと D7） |
| ダブルクリックの 2 通目（同じトーク） | 既存の「二重に止めない」で控えは増えず、取り出しは完了の 1 回だけ |
| 中断を受け入れた後、完了の前に別の応答がトークを置き換える | 控えは次の現行トークの完了で取り出され、相手が違うので捨てて記録。`OnBalloonBreak` は出ない（要件 1.5 に合う） |

| `balloontimeout` の指定と中断 | 指定もトークの終わりも同じ受け口・同じ線なので、配られた指定は必ず終わりの合図より前に並ぶ。配られる前に止まった指定は届かない（9.8） |
| ゴーストの切替・終了の最中に知らせが飛ぶ | 相が定常でないので D1 で捨てて記録。置き場にゴーストが居なければ表示の側で送らず記録 |

確かめ切れなかった点（議題にはしないが実装で見る）:
- トークの番号はゴーストごとに 1 から数え直す。古いゴーストの表示の状態が出した知らせが、新しいゴーストの kanade へ届くことがあるなら、番号の照合は偶然に合いうる。表示の状態（`Emo2Wiring`）と置き場（`GhostSlot`）の入れ替わりの順は読んでいない。送出の檻（Integration 3）で「切替の直後のフレーム」を 1 本見ておくとよい。
- トークの終わりの合図を取り出したフレームの時刻が、止まった時刻よりわずかに前のことがありうる（フレームの時刻の採取が先）。そのフレームでは計測が立たず、次のフレームを起こすのは合図の送出の起床の印と定期の見回りだけ。`\![set,balloontimeout,…]` の小さい値で、実機の記録に「立つのが遅い」が出ないかを 8.3 の ⑷ で見る。

## 5. 設計の良い点

- **判断を「完了の振り分けが済んだ後の相」1 か所で見る形**（設計で決めたこと D3）。定常へ戻る 3 経路に同じ判断を書かずに済み、`steady.rs`・`change.rs` に触らず、要件 1.6 の「送らない」場面がすべて「相が定常でない」の 1 条件で外れる。実物の腕と突き合わせても漏れが無かった。
- **トークの番号を表示の側まで届け、計測をトークの終わりの後にだけ立てる組み合わせ**（D5・D6）。「番号が合う知らせ＝終わったトークのバルーンが消えた」と言い切れるので、預かりが必ず完了で裁かれる。時刻の軸も、受け口が落ちる時点では次のトークの cue が観測されていないので、止めたトークの軸で読める。

## 6. 設計の討議の議題（設計者が確認を求めたもの・research §11.4）

指摘とは別に、開発者の確認が要る判断。意見を添える。

1. **同じウェーブの約束の外の 3 ファイル（`msg.rs`・`actor.rs`・`spine.rs`）に触る**。要件の「開発上の制約」は「触る必要が出たら止めて報告」。
   - 意見: `msg.rs`・`actor.rs` は設計の形（専用のメッセージ）に賛成。汎用の入口に「kanade が中身を補う」特別扱いを混ぜる案は、後で MCP の `raise_event` と決まりが 2 つになる。足すのは変種 1 つと腕 1 本で、後からマージする側が足し直せる。`areka-P0-mcp-get-status` は `.kiro/specs/` の直下に残っており、まだ完了していない見込みなので、どちらが後になるかを決める。
   - `spine.rs` は 1 行の置き換えで行数は変わらない。避ける形（時刻源を後から差す）は、検査用の起動だけが「時刻が届かない」道を通ることになるので、設計の形でよい。`areka-P0-ghost-session-test-load-flake` の持ち主へ 1 行の変更を知らせる。
2. **計測の成立条件に「トークの終わりが届いていること」を足す**。要件は「時間切れの判断の規則は変えない（起点だけを変える）」。
   - 意見: 賛成。起点（終端と止まった時刻の早い方）はトークが終わらないと決まらないので、起点を変える以上は避けられない。最後まで流れたトークの満了の時刻は変わらない（指摘 1 のずれを除く）。変わるのは「話の途中の隙間で計測が立つ」ことが無くなる点だけ。互換対応表の既定の待ち時間の行の説明を合わせることと、完了 spec の檻の直しを最初の方のタスクに置くことを条件にする。
3. **中断を出したのにトークが自分で終わっていた場合は `OnBalloonClose`（D7）。箱でも同じ行き違いなら `OnBalloonClose`**。要件 3.1 は「シェルの中のバルーンを除く」。
   - 意見: 普通のバルーンは賛成（何も送らないと出来事が消える）。箱は、表示の側が「話している」と判定して箱を隠した直後にトークが終わっていた、という狭い行き違いに限られ、シェルへのダブルクリックも出ていないので、送る側でよい。要件 3.1 の補足に 1 文足すか、互換対応表に areka 裁量として書く。
4. **（設計者は「形を変えない」とした点）ダブルクリックの合図にトークの番号を載せるか**。
   - 意見: 今回 `msg.rs` に触り、表示の側が番号を持つようになるので、載せれば「残る行き違い」の 2 つ（読み終えたバルーンのダブルクリックが、始まったばかりの次のトークを止めて `OnBalloonBreak` になる／Reference0 が新しい方の台本になる）を閉じられる。ただし中断の受理の規則（完了 spec `areka-P0-balloon-break`）と `input_events/` に手が入り、本 spec の境界の外。**今回は載せず、互換対応表に行き違いを書き、要望が出たら起票**でよい。
5. **終了の要求を保留している間は 3 つとも送らない（D8）・控えが無いときは Reference0 を空で送る（D9）・1 つのトークにつき `OnBalloonTimeout`／`OnBalloonClose` は高々 1 回（D10）**。
   - 意見: どれも賛成。互換対応表に areka 裁量として載る（設計の「文書・台帳」に入っている）。
6. **範囲の外で見つけた問題の起票**（選択肢を含む台詞のバルーンが、選んだ後も時間切れにならない）。
   - 意見: `/kiro-discovery` での起票を controller が行う。本 spec の実機の確認（8.3）の検体は、選択肢の無い台詞で組む。
