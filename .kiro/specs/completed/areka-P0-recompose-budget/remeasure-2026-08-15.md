## 5. 残る不合格 2 件の位置づけ

### ⑵ 進行境界スキップ（catch-up）: dev 21 件・release 28 件（目標 0 件）

ベースラインから半減した（dev 78 → 21・release 41 → 28）が 0 ではない。1 コマの所要が
コマ待ち（150ms／22ms）を超えると発生するので、**⑶ が 0 になっても 1 コマ 5.7ms では
消えない**種類の指標ではない——5.7ms は 22ms 待ちにも収まる。したがって残る 28 件は
定常の p50 ではなく**裾**（p95 9.1ms・最大 11.4ms でも 22ms には収まる）以外の要因、
つまり talk 再生や複数面の同時更新が重なった瞬間に出ていると読むのが自然である。
**未確定**であり、7.2 の長時間走行で件数の推移を見てから判断する。

### ⑷a アイドル CPU: 8.94%（目標 3.0% 未満）

24.9% → 8.94% で **2.8 倍の改善**だが目標には届かない。定常の分布は
最小 3.1%・p50 9.3%・p95 14.0%・最大 15.6%・平均 8.9%。平均と p50 が近いので、
1 回の長い非アイドル区間に引きずられた値ではない。

残る 8.94% の主因は §3 のとおり毎コマの再合成である。容量裁定が下りれば
キャラ面の 56.2% が省かれる見込みで、そのぶん CPU も下がるはずだが、
3.0% に届くかは**実測しなければ分からない**。

### ⑶ dev の 5 件は再利用の破綻ではなく暖機である

内訳は `alloc_resample_dst=2`・`alloc_mask=3`。**全 5 件が `TargetId(2)`（ケロ）の
`surface=2100` に集中し、06:40:56.182 / 06:40:57.131 / 06:40:57.175 の約 1 秒間の
バースト**で、形は `[0,1,0,1] → [0,1,0,1] → [0,0,0,1]`。これは裁定済みの
**「回る実体が 1 適用ずつずれて伸びる」暖機の指紋そのもの**であり、以降の約 280 適用は
確保 0 のままである。release では同じ暖機が 60 秒の除外窓の内側で済んだため 0 になった。

**判定スクリプトは正しく動いている**——「遅れて始まった対象の暖機」と「定常の churn」を
ログから区別する手段が無いため、除外窓の外に出た確保はそのまま計上される。

ただし**容量 3 が暖機を 4 倍に伸ばした**ことは事実で（表示バッファ 3 本＋マスク 4 本が
1 適用ずつずれて立ち上がる）、**固定 60 秒の除外窓では、途中からアニメが始まる対象の
暖機を覆いきれなくなった**。これは較正値 `WARMUP_EXCLUDE_SEC` の見直し対象である。

### ⚠ CPU は下がらなかった——これが本測定の最大の発見

| | 容量 1 | 容量 3 |
|---|---:|---:|
| 最小 | 3.1% | 1.6% |
| **p50** | **9.3%** | **9.3%** |
| p95 | 14.0% | 18.7% |
| 最大 | 15.6% | 23.3% |
| 平均 | 8.94% | 10.38% |

**中央値は 9.3% で完全に一致する。** 平均と裾だけが動いており、n=24 でこの差を
「悪化」と読むのは無理がある。**正直な読み方は「CPU は動かなかった」**である。

これは重い意味を持つ。**1 コマ適用の中央値を 78% 削っても、CPU の中央値は 0.0 ポイントしか
動かなかった。** すなわち **`apply_show` はもはやアイドル CPU の主因ではない**。

3.2 のベースライン以来、本 spec は「1 コマ適用が重い」という前提で 3 段の是正を積んできた
（定常アロケーション 0・ゼロ埋め除去・リサンプル計算・キャッシュ容量）。1 コマは
22,210µs → **1,240µs（18 分の 1）** になった。それでも CPU は 24.9% → 約 10% で止まり、
最後の 4 分の 1（8.94 → 10.38、p50 は不動）は**是正の効果が 1 ポイントも現れていない**。

**残る 10% は `apply_show` の外にある。** 候補は本 spec の観測範囲外である——GPU の提示、
進行のティッカー、SHIORI の IPC、合成器、窓の管理など。**要件 4.4 の 3.0% 未満は、
本 spec の設計が持つ手段（表示 1 コマの適用経路）では到達できない**と読むべき実測である。

### ⑵ は改善した（release 28 → 17 件）

1 コマが 1.2ms まで下がったので、コマ待ち（150ms／22ms）を超える経路はさらに減った。
残る 17 件は定常 418 適用に対して 4% で、talk 再生や複数面の同時更新が重なる瞬間に出る。
