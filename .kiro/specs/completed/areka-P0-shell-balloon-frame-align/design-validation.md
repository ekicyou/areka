# 設計レビュー: areka-P0-shell-balloon-frame-align

## レビューの要約

設計は、絵・箱の置き場所・普通のバルーンの窓の表示と非表示・`Status` の届けの 4 つを「表示層がいま表示している絵の番号」1 つから同じフレームの中で導く形で、1 フレーム遅らせる手当てを使わずに要件を満たしている。今のコードについての記述（3 か所の読み口・相の並び・番号が `None` になる時機）はソースと一致した。実装へ進めてよいが、要件 1.8 の読み方と、直すテストの一覧の漏れの 2 点を設計討議で片付けたい。

## 重要な指摘（2 件）

### 🔴 指摘 1: 要件 1.8 を設計が狭く読んでいる。しかも普通の台本がその場合に当たる

- **懸念**: 要件 1.8 は「窓も箱も表示されていないフレームを作らない」と無条件に書いている。設計は「移る先に、そのフレームで見えている文字があるときだけ成り立つ」と読み、移る先が空なら絵が替わるフレームで前の側だけを消す。これは隅の場合ではない。`\s[箱の無い面]つづきの文字` のような普通の台本では、`\s` と次の 1 字のあいだに文字送りの待ちがあるので、絵が替わったフレームでは移る先にまだ 1 字も無いことが多い。
- **読みの妥当性**: 読みそのものは要件 1.2（絵が替わるフレームで箱の表示をやめる）・1.9（行き先に表示するのは絵が替わったフレーム）・2.3（どちらも出ていなければそのフレームで外す）と矛盾しない。逆に「移る先に文字が出るまで前の側を出し続ける」と読むと要件 1.2 に反し、新しい絵の上に前の箱の文字が残る。空の窓・空の箱を出さない既存の規則とも合う。直す前も同じ姿（窓は `\s` で消え、箱は 1 字目で出る）なので後退ではない。
- **影響**: このままだと実装の検証で「要件 1.8 の文面に反するフレームがある」と読める。また枠の檻の場面 3 は両側に文字を持たせた形だけなので、移る先が空の場合の振る舞い（前の側が消えるフレーム・`balloon(ID群)` から外れるフレーム・1 字目で出るフレーム）はどのテストにも固定されない。
- **提案**: 設計討議で開発者にこの読みを確かめる。受け入れるなら、(a) 要件 1.8 に「移る先に見えている文字がある場合」の但し書きを足すか、設計の読みを要件の注記として残す、(b) 枠の檻に「移る先が空」の場面を 1 つ足し、絵が替わるフレームで前の側が消えて組から外れ、文字が届いたフレームで移る先に出て組に戻ることを固定する。
- **対応する要件**: 1.2・1.8・1.9・2.2・2.3・4.1
- **設計の該当箇所**: System Flows「要件 1.8 の読み方」・Testing Strategy「枠の檻」の 3・`research.md`「Decision: 要件 1.8 は…と読む」

### 🔴 指摘 2: 直すテストの一覧に漏れがあり、「可視性の相の檻は変わらない」という記述が事実と違う

- **懸念**: `balloon_visibility_phase_box_tests.rs` の `glyph_count_is_the_one_shown_in_the_balloon_window` は、`\s` の cue だけを当てて `collect_observations` の文字の数が 0 になることを見ている。この檻の表示層は `attach_headless` でバルーンの窓だけを装着し、シェルの窓は持たない。設計どおり絵の番号を基準にすると、シェルの絵の番号が `None` なので数は 0 でなく 2 になり、この檻は赤になる。ところが設計の Modified Files にこのファイルは無く、Testing Strategy は「直すのは箱の檻だけ: `frame_shell_box_integration_tests.rs` の 3 本・文字の層の箱の檻・`status_report_tests.rs` の箱だけの 1 本」と言い切っている。
- **影響**: タスクの見積もりから 1 本抜ける。加えて、GPU を使わない表示層にシェルの絵の番号を持たせる手段が areka クレートの檻には無い（番号を直接書ける道具は emo-present の中のテスト用で、外から呼べない）ので、「どう直すか」を決めておかないと実装で止まる。
- **提案**: 次を設計に書き足す。
  1. `balloon_visibility_phase_box_tests.rs` を Modified Files に入れる。数の判断そのものは文字の層の檻の 5（`balloon_shown_glyphs` は絵の番号に従う）が持つので、この檻は「相が表示層の番号を渡している」ことの確かめに絞り、枠の檻（GPU 付き）へ移すか、GPU 付きの表示層で絵を確立する形に直す。
  2. `collect_bindings` の引数が増えるので、`status_report_tests.rs` の既存の呼び出しは全部が形だけ変わる（期待値は変えない）ことを明記する。
  3. 枠の檻は `Cage` の道具の追加（シェルの文面の引数・絵を送る口）が前提なので、「既存の道具だけで書ける」は「テストの足場だけを足せば、直す前のコードで走る」に改める。最初のタスクで、足場の追加 → 面 10 が検体で合成できることの確かめ → 赤の記録、の順を踏む。
  4. `frame/wiring.rs` は触らない約束だが、`Emo2Wiring` の説明文 2 か所（「可視性の相が消費する 6 つ」に `balloon_status` が入っている・欄 `balloon_status` の「可視性の相の終わりの報告が使う」）が事実と合わなくなる。説明文だけ直すことを約束の例外にするか、古いまま残して後で直すかを決めて書く。
- **対応する要件**: 4.1〜4.5
- **設計の該当箇所**: File Structure Plan「Modified Files」「触らないファイル（約束）」・Testing Strategy 冒頭の方針と「変えないテスト（要件 4.5）」

### 小さな気付き（判断は変わらない・記録だけ）

- 枠の檻が見るのは絵の番号・写しの四角・窓の可視・届いた組で、画素そのものではない。置き場所が替わるとき箱の面は片付けて同じフレームの提示で作り直すので、新しい面が絵と同じ合成に乗るかは檻では分からない。ただしこの道（drain と付け替えが同じフレーム）は、完了 spec の実機の確かめで揃っていた 16 回中 14 回と同じ道であり、新しい危険ではない。任意の実機の確かめで足りる。
- 要件 1.3（`\s[-1]`）は文字の層の檻（絵の番号が `None` なら登録を外す）だけが持ち、`run_text_scale_phase` が「差し込み口はあるが番号は無い」を `None` として渡す所は檻に入らない。`spine_text_scale_tests.rs` の `text_scale_phase_syncs_boxes_on_the_shell_window` に `Hide` の 1 歩を足せば安く固定できる。
- 届けの相の「文字の層を借りられない」腕は、提示の相が借用を返した直後に走るので本番では到達しない見込み。記録を残す方針（ログ無しの失敗経路を作らない）には合っているので、そのままでよい。

## 設計の良い点

1. **番号の写しを増やさずに 0 フレームで解いている**。絵の番号を文字の層に覚えさせず、結線が毎フレーム引数で渡す。`box_still_shown` は条件を足すのでなく外すだけで済み、新しい型も新しい状態も無い。「実装後に `actor_box.rs` が受け取った `\s` の番号を 1 か所も読まない」という機械で確かめられる線引きも付いている。
2. **既にある並びを崩さない**。可視性 → 箱の同期 → 提示の並び（時間切れで隠したフレームに画素も消える支え）を動かさず、届けだけをフレームの終わりへ移した。窓と箱の入れ替わりは可視性の判断（`decide`）を変えずに、入力の数え方を替えるだけで今ある腕に乗る。届く順の 2 通りを `apply_cue` と `present_tx` で決定論に組む檻も、本番で届く道と同じ入口を踏んでいる。

## 最終判定

**GO**（指摘 2 件を設計討議で片付けることを条件とする）

- **理由**: 構造上の食い違いは無く、4 つの表示が同じフレームの同じ番号から決まることをソースの相の並びで確かめられた。残る 2 点は、要件の文面と設計の読みの合わせ（指摘 1）と、直すテストの一覧の漏れ（指摘 2）で、どちらも設計の骨組みを変えずに書き足せる。
