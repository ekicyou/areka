# 設計の検証: areka-P0-mcp-dump-images-residue

> 2026-10-05・本ブランチのコードと照らして、対話なしで書いた。対象は [design.md](design.md)・[requirements.md](requirements.md)・[research.md](research.md)・[brief.md](brief.md) と `.kiro/steering/`。コードは「何の定義か」で指す。

## 要約

設計は、後始末 5 件を「1 フレームで済まない仕事を、後から答える置き場で毎フレーム覗く関数の状態として持つ」1 つの形にまとめた。MCP の共有のファイルにも、記録を捕まえるテストの道具にも触らずに要件を満たす道筋が立っている。名前を挙げた関数・型・D3D11 の口は実在し、GPU を扱う呼び出しはすべて UI スレッドに残っている。描画を飛ばす危険も、要件と食い違う点も見当たらない。直すべき点は 3 つあるが、どれも設計の文書を少し直せば済む大きさなので、**GO** とする。

## コードで確かめた設計の主張

| 設計の主張 | 確かめた結果 |
|---|---|
| `D3D11_MAP_FLAG_DO_NOT_WAIT`・`DXGI_ERROR_WAS_STILL_DRAWING`・文脈から装置を引く `GetDevice` が使える | `windows` 0.62.2 の定義に 3 つとも在る（`GetDevice` は `Result<ID3D11Device>` を返す）。`Map` の第 4 引数に渡すのは `D3D11_MAP_FLAG_DO_NOT_WAIT.0 as u32`（0x100000） |
| GPU の文脈を UI スレッドの外で触らない | `Map`・`Unmap`・`CopyResource`・`Flush` はどれも `drain` の中の覗く関数（UI スレッド）から呼ばれる。今の `read_back` を呼んでいるのと同じ所なので、D2D と文脈を共有していることによる新しい危険は無い。札は文脈の参照を持つだけで、`Send` を求めない置き場（`McpLater`）に入る |
| 写し先を呼び出しごとに作ると要件 1.3 を満たす | D3D11 は、積んだ写しを後から積む書き込みより先に終える。`flip` の後に元の front 面へ描いても、写し先の中身は積んだ時点のまま。テストの `read_back` は `TextSurface` の 1 枚の写し先を使うので、互いの中身を書き替えない |
| ゴーストの見分けは名前とルートフォルダで比べる | `resolve.rs` の `ActiveGhost` は `name`・`root` の 2 つの欄を持ち、`Clone`・`PartialEq`・`Eq` を備える |
| 待つ側が去ったら覗く関数ごと落ちる | `mod.rs` の `poll_later` は、`ReplyTo::is_abandoned`（`Pending` を落とすと立つ）が立っていれば覗かずに捨てる。`close` は置き場ごと外す |
| 窓の無い `SwitchRig` で装着の前を作れる | `boot_ghost` は窓が無くても `Emo2Wiring` を World に入れる（`emo2_boot/mod.rs` の手順 6）。`ghost_session::register_systems` が `mcp::register` を呼ぶので、`Input` の段を回すと `drain` も回る |
| 符号化のスレッドで `error!` を出しうるのは `finish` の中だけ | 重ね合わせ（`dump_balloon_overlay.rs`）と PNG（`dump_surface_image.rs`）には `error!` も `warn!` も無い。配布用のビルドの設定は `panic = 'unwind'` なので、`catch_unwind` が効く |
| ファイルの行数 | `surface.rs` は今 817 行。2 つの口と 2 本のテストを足しても、見込みは 1,000 行を下回る。front 面の中身を往復させる WARP のテスト `readback_roundtrips_source_tex_contents` が手本として既に在る |
| フレームが回り続ける | 画面の更新を省く仕組み（`AREKA_TICK_GATE`）は既定で切れている。切れているかぎり、覗く関数は毎フレーム呼ばれる |

## 直すべき点

### 🔴 1. `ui_us` に、UI スレッドで符号化のスレッドを起こす時間が入らない

- **何が問題か**: 設計の「時間の数え方」では、符号化のスレッドを起こす直前に `max(ui_max, ここまで)` を測り、その値を仕事に渡す。このため、UI スレッドで行う `std::thread::Builder::spawn` と手渡しの時間が `ui_us` に入らない。今の `reply_elsewhere` も、起こす前に時間を測っている。
- **なぜ困るか**: 要件 1.1 は「その呼び出しが UI スレッドを塞ぐ時間」の上限で、合否は `ui_us` で決める（7.2 ⑴）。判定の値が本当の時間より少なくなる。時刻は正確に扱うのが設計の大原則である。今の見込みでは 2 ms の上限まで余裕があるが、判定の値そのものが欠けていてはいけない。
- **直し方**: 時間は、スレッドを起こして手渡しが済んだ後に測る。測った値は、すでにある手渡しの経路（`(Job, 届け先)` の組に `Duration` を加える）で符号化のスレッドへ渡す。`finish` の引数の形は変えなくてよい。`reply_elsewhere` も同じ関数に寄せるので、装着の後の `dump_surface` も一緒に直る。
- **要件**: 1.1・5.3・7.2 ⑴
- **設計の箇所**: Components「`Wait`・`Stage`」の時間の数え方と、「`encode_elsewhere`・`finish`・`send_back`」

### 🔴 2. 要件 1.2 の括弧書き「文字の面の大きさで伸びない」の読み方が、設計に書かれていない

- **何が問題か**: 設計では、写し先の作成（呼び出しのフレーム）と、読めたフレームでの行ごとの写し（文字の面の大きさに比例するメモリの写し）を UI スレッドに残す。Performance の節は、これを「背景の写しと同じ種類の仕事（裁定 3）」と説明している。一方、要件 1.2 の括弧書きは字面では「UI スレッドの時間が文字の面の大きさで伸びない」と言っている。設計は、この括弧書きを「GPU を待つ分が伸びない」と読んでいるが、その読み方をどこにも書いていない。
- **なぜ困るか**: 実機確認で大きなバルーンの `ui_us` が伸びたとき、合格か不合格かの線が人によって変わる。research.md 14 節の手当て（`Map` を開いたまま、行ごとの写しを符号化のスレッドで行う）は、実機で 2 ms を超えたときにだけ取ることになっている。
- **直し方**: 設計ディスカッションで、次の 2 つのどちらかを選ぶ。⑴ 「1.2 の括弧書きは GPU を待つ分のことで、写しは 1.1 の 2 ms で抑える」と設計に明記し、実機確認の記録に、その機械で撮ったバルーンの大きさ（物理 px）も残す。⑵ 14 節の手当てを最初から設計に入れて、行ごとの写しを UI スレッドの外へ出す（`Map`・`Unmap` は UI スレッドのまま）。今の見込み（前の spec の実機で、読み戻しを含めても 2 回目以降は最短 1.4 ms。写しは 2 つのフレームに分かれる）なら ⑴ で足りる。
- **要件**: 1.1・1.2・7.2 ⑴
- **設計の箇所**: Performance & Scalability、Components「待たない読み戻しの口」の Implementation Notes の「危険」

### 🔴 3. 答えで判定する方法の較正が無い（要件 5.2）

- **何が問題か**: 要件 5.1 を満たす方法は 2 つある。仕事を直接捕まえる方法と、答えで判定する方法である。Testing Strategy の要件 5.2 の較正（Unit Test 2）が確かめるのは前者だけで、テストのスレッドで `finish` を回して数える関数を較正している。本番の入口を通る GPU のテストは「答えが `NG:` でない」で判定するが、この判定の関数が、本物の符号化のスレッド（`mcp-encode`）での失敗に対して赤になることは、どのテストでも確かめていない。Integration Test 2（装着の前の panic）は本物の符号化のスレッドで失敗を起こすが、確かめているのは文言の一致で、GPU のテストが使う判定とは別のものである。
- **なぜ困るか**: 要件 5.2 は「符号化のスレッドで意図して失敗させたとき、検査が赤になること」を求めている。判定する関数を較正しないと、その関数が誤っていても見逃したまま緑になりうる。
- **直し方**: GPU のテストの「画像つきの成功か」の判定を 1 つの関数にまとめる。そして Integration Test 2（本物の `mcp-encode` で panic させる）の答えをその関数に通し、赤（成功でない）を返すことを同じテストの中で確かめる。トレーサビリティの表の 5.2 の行にも、このテストを加える。
- **要件**: 5.1・5.2・7.1 ⑺
- **設計の箇所**: Testing Strategy「符号化のスレッドの記録の判定」・Unit Tests 2・Integration Tests 2、Requirements Traceability の 5.2 の行

## 良いところ

1. **境界を守ったまま、答えの遅れと描画を切り離している**。`mod.rs` の `later` は、覗く関数が状態を持てて `Send` を求めない。設計はこの形をそのまま生かし、装着待ち・読み出し待ち・符号化待ちを 1 つの列挙にまとめて、2 本のツールで共用している。GPU の文脈を UI スレッドの外で触る案は理由を付けて捨てており、写し先を呼び出しごとに作ることで、使用中かどうかの印を持たずに要件 1.3 を満たしている。
2. **失敗の記録の決まりを形で守っている**。文字の層の新しい 2 つの口は記録を出さず、記録は呼び手の `fail` が 1 か所で 1 件だけ出す。判断の文言は型 `Refusal` にして、想定外の失敗の関数 `fail` へは渡せないようにした。ゴーストが替わる場合のテストは、本物の切り替えの手順（台本の `\![change,ghost,B]`）を通し、届く経路を実際に踏む形になっている。

## 判定

**GO**

- **理由**: 既存の構造との食い違いも、要件の抜けも無く、GPU とスレッドの扱いも正しい。上の 3 点は、測る位置を変える・読み方を書き足す・判定の関数を較正する、という設計の文書の小さな直しで片付く。
- **次の手順**: 設計ディスカッション（`/kiro-design-discussion areka-P0-mcp-dump-images-residue`）で 1〜3 を決めて design.md に反映し、その後 `/kiro-spec-tasks areka-P0-mcp-dump-images-residue` でタスクを作る。

## 補足（直すべき点ではないもの・記録として）

- 画面の更新を省く仕組み（`AREKA_TICK_GATE=1`）を有効にすると、何も変わらないフレームは省かれる。そのとき、預けた覗く関数が呼ばれるのは心拍（30 フレームに 1 回）のときだけになり、答えが 0.5 秒ほど遅れうる。描画は遅らせず、10 秒の上限にも届かないので要件 1.4 の内に収まる。装着の前に預ける今の経路も同じ振る舞いである。
- GPU のテスト 1（要件 1.3）は、`answer` と `Reader` を直接呼び、`start`・`Wait` を通らない。WARP では、預けた直後の覗きで読み終わってしまうことがあり、「台詞が進んだ後に読む」状態を本番の経路では決まった形で作れないためで、理由は妥当である。`start` から `Wait` を経て読み出しに至る配線は、待ち方を替えた既存のバルーンのテスト（GPU のテスト 4）が踏む。
