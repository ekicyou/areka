### 2. 関連の種別 `queries` を、凍結契約と逆向きに読み替えて 30 本張る

**重大度: 中（上流との擦り合わせが要る）**

上流 4.3 は `queries` を「タグ・イベント→プロパティ」と向きつきで凍結している。本設計は台帳の項目（＝矢の終点）側に `{ kind = "queries", to = "<タグ・イベントの id>" }` を書き、「この項目は当該タグ・イベントから照会される」と**逆から読む**取り決めを新たに置いている（SET 有効 26 件＋ext 4 件の計 30 本が対象）。上流 6.7 が両端の実在しか見ないため機械検査は通るが、これは「仕訳の規則を再定義しない」（要件 1.3・境界節）に触れる読み替えであり、いま提案として書き添えるだけだと、他 3 本の台帳が別の読み方で書いた場合に統合時点で意味が割れる。加えて `\![set,property,...]` は**書き込みの経路**なので、「照会」を意味する `queries` を当てること自体も 4.3 の 6 種に無い用途への拡張になっている（6 種に「書き込まれる」に当たる語が無いための苦肉であることは理解できる）。

**手当ての案（どれか 1 つ）**: ⑴ 台帳の側からは張らず、矢の始点を持つ sakura-script／shiori の台帳に張らせる（本 spec は備考の「値の源／書込先」1 行だけにする）。⑵ 向きが対称な `same-feature` を使い、`queries` は始点側の台帳に譲る。⑶ 現案を維持するなら、**提案としてではなく「上流 4.3 の解釈確認」として先に上げ、返事が来るまでは当該 30 本を書かない**段取りにする。

### 3. ソースに置くコメントの形が、凍結契約の記入例（`/// ukadoc: <URL>`）と違う

**重大度: 低〜中（後で他 spec の検査が赤くなる可能性）**

設計は `vec![...]` の要素に `///` を付けられないという正しい理由から `//` の行コメントを各要素の直前行に置く形を採り、開発者裁定にも沿っている。ただし上流 5.1 は証拠を「doc コメント」と呼び、付録 A.3 は `/// ukadoc: <正典 URL>` を記入例として凍結している。上流 5.5 は「ソース全域を走査して正典 URL を集める」と書かれているので `//` でも拾える読みが自然だが、**道具はまだ設計も実装もされていない**。もし収集側が `///` を目印にする作りになると、上流 6.6（`implemented` の行に証拠が 1 つ以上ある）が本ドメインの 2 件で赤くなり、直せるのは本 spec が完了した後になる。

**手当ての案**: ブリーフィング ⑸ 節の「上流 README への提案」を 2 件から 3 件に増やし、「**定義箇所が `///` を取れない位置（配列やベクタの要素）では `//` の行コメントを同じ扱いにする**」を明記する。合わせて、証拠の収集は URL の出現で拾い、コメントの記号で絞らないことを上流へ申し送る。

## Design Strengths

1. **数字が全部引き直せる**。188／2・7・179／26／25／35／98・21 種／7 件の縮退 id／5 本の相手 id ——設計が書いた件数と id 文字列を独立に数え直して、**1 件の食い違いも出なかった**（例外は危うさの段の説明文 1 か所と「ukadoc」の語の件数 1 か所で、いずれも台帳の中身を動かさない）。とくに「21 名が指す 25 id のうち正典が SET 有効とするのは 21 id、26 との差 5 件」という検算が成立し、その 5 件が既存 brief の「21→26」の中身と一致することまで再現できたのは、この設計が実測から立っている強い証拠である。
2. **判断の余地を 1 か所へ集めて、そこだけを明文化している**。規則 0（葉だけの id をどう読むか）が唯一の解釈点であり、採らなかった読み方と、その場合に何件がどう動くか（16 件が「未対応」へ落ちる）まで書いてある。おかげで、後からこの読み方が覆っても差し替えるのは規則 1 の 2 行だけで済む。同じ配慮が「登記があるかどうかだけが縮退 7 件と語彙のみ 179 件の差である」という但し書きにも現れており、読者が「7 件だけ壊れている」と誤読するのを先回りで防いでいる。
