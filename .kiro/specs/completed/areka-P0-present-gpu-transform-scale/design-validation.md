## レビュー要約

裁定 D（wintf のコマンドリスト経路へ戻す）を、wintf のコード変更 0 で成立させる筋道は **コード上で成立している**——k を surface entity 自身の `Arrangement.scale` に置く判断・`Visual::on_add` に乗る spawn・`ceil` と `scaled_extent` の丸め差 ≤1 px・perf 必須集合の縮小・テスト台帳の実数（撤去 44／再導出 34／新設 8／不変 127）は、いずれも実装の定義と一致した。残る懸念は 3 つで、いずれも「設計の筋道」ではなく「**要件との字義の食い違いと、檻が本当に赤になれるか**」に関するものである。判定は **GO（条件付き）**——下の Critical 1〜3 を設計ディスカッションで裁定・反映してからタスク生成へ進む。

## Critical Issues（≤3・重要度順）

### 🔴 Critical Issue 1: 絵の着地が +1 tick になる帰結が、要件 2.4／3.1 の字義と食い違ったまま「既知の帰結」として設計に固定されている

- **Concern**: 設計 §Existing Architecture Analysis「スケジュール順」と Non-Goals 末尾は、`apply_show` が tick 末尾の `FrameFinalize` で走り、挿した `GraphicsCommandList`／`Arrangement` が**次の tick** の `PostLayout → PreRenderSurface → RenderSurface` で描かれるため、見た目の着地が現行（同 tick の `Present(0)`）より 1 tick 遅れ、面切替のコマで**絵が文字より 1 コマ遅れて見える**と書く。これは新しい可視挙動であり、要件 2.4「同一フレーム内で新しい k の表示を成立させ」・3.1「**同コマで** wintf の `render_surface` が行う全面再描画の代金を合わせて 16.7 ms 以下」の字義と食い違う。設計は 2.4 を「表示成立点（状態・`info!`・照会値）が同一 tick」と読み替え、3.1 の再描画分は「次の tick の `transition`／`tick_diag` から読める範囲で併記」に落としているが、この読み替えは要件側に反映されていない。
- **Verified**: `crates/wintf/src/ecs/world/mod.rs` `try_tick_world`（`Input … RenderSurface → Composition → CommitComposition → FrameFinalize` の固定順）／`crates/areka/src/emo2_boot/mod.rs`（`add_systems(FrameFinalize, emo2_frame_system.before(apply_zorder_chain))`）／文字層は `crates/areka-emo-text/src/actor.rs` の描画終端で `render.surface.present()`（自前 swap chain へ直接 `Present(0)`）——主張は**正しい**。
- **Impact**: 利用者の症状は「文字がまとめて出る」だったが、修正後は「面切替のコマで絵が文字より 1 コマ遅れる」という別の見え方が常時入る。受け入れ判定（3.1 の物差し）の「同コマ」も測り方が変わる。要件を直さず実装へ進むと、実機サインオフで「要件どおりか」を誰も言えない。
- **Suggestion**: 設計ディスカッションで次のどちらかを裁定し、要件の文言へ反映する。(a) **受容**——2.4 を「表示成立点は同一 tick・画素の着地は次の tick」と明記し、3.1 を「`t_total_us`（apply の tick）＋次 tick の `render_surface` の代金を**別々に**報告し、合否は前者 16.7 ms」に書き換え、実機サインオフ手順 3 の「1 tick 遅れて見えるか」を**合否項目**（見えて許容か／見えたら不合格か）にする。(b) **解消**——`emo2_frame_system` の drain 相を `Draw` より前の schedule へ動かす（`apply_zorder_chain` との順序制約を設計で解く）。設計は (b) を範囲外と宣言しているので、(a) を採るなら要件改訂を、(b) を採るなら File Structure Plan に areka の frame 配線を加える。
- **Traceability**: Requirement 2.4・3.1（および 8.7 の two-tick-bounce への申し送り）
- **Evidence**: design.md §Existing Architecture Analysis（スケジュール順）・§Non-Goals 最終項・§実機 2 水準サインオフ 手順 3／4・research.md §7.2・§9

### 🔴 Critical Issue 2: `read_back` が合成メモのバイト列を返す形になると、k=1 の「読み戻し＝合成」golden から GPU 往復が消えるのに、設計は「主張不変」とだけ書き、供給の成功経路を固定する檻を置いていない

- **Concern**: 設計 §read.rs は `read_back` を「`last_show` のキーで引いたエントリの `composed.bytes()`」と定義する。すると `presenter_display_tests.rs` `golden_match_read_back_equals_direct_compose` は「合成 → メモへ保存 → メモから読む」の配線検査になり、**GPU に 1 度も触れずに緑になる**。現行はこの 1 本が `SwapChainPresenter::upload → read_back` の往復（供給面の pitch・寸・premultiplied の整合）を k=1 で固定していた。新設 `display_fault_tests.rs` は**失敗**分岐（4 注入点）しか見ないので、`record_display` の成功経路——`CreateBitmap(D2D_SIZE_U{w,h}, bytes, pitch=stride, props)` の寸と pitch・宛先矩形・`Close`——を赤にできる決定論の檻が**設計上 0 本**になる。pitch を 1 つ間違えても実機サインオフまで発見されない。
- **Verified**: `crates/areka-emo-present/src/presenter/read.rs` `read_back`（現行は `t.chain.as_ref()` → `chain.read_back()`＝供給面から `Map`）／`presenter_display_tests.rs` `golden_match_read_back_equals_direct_compose`（`make_world_with_gpu` 型）／設計 T-N1 は `DisplayRecipe`（純関数の値）のみで、`record_display` の `Ok` 側は「`Close` 済みで再利用可能」と Postcondition に書くだけで檻が無い。要件 6.5 は「GPU を要する確認はオフスクリーン readback の既存の型に限る」と**許している**（プロジェクト記憶「GPU 描画検証はオフスクリーン D2D ターゲット」）が、research §7.7 はこれを「資源生成のみ・画素は読まない」と狭く読み替えている。
- **Impact**: 要件 6.1「k=1 の `read_back` 比較をバイト単位で不変に保つ」は名前だけ残って中身が空になる（「母数 0 の緑は恒真」）。供給経路の退行は実機サインオフでしか捕まらず、GPU 補間を檻に入れない方針（6.6）と相まって「原寸 bitmap が正しく上がったか」を誰も機械で確かめない。
- **Suggestion**: (1) 設計 §Testing Strategy に「`golden_match_read_back_equals_direct_compose` は GPU 非経由の配線検査になる」と正直に書く。(2) 要件 6.5 が許す**オフスクリーン D2D ターゲットの既存の型**で、成功経路の檻を 1 本足す: `record_display` が返した閉じたリストを恒等変換（k=1）でオフスクリーン `ID2D1Bitmap1`（CPU_READ）へ `DrawImage` し、読み戻したバイト列が `Composer::compose` の原寸バイトと一致すること（k=1 なので補間は恒等・決定論）。これが旧往復 golden の正当な後継であり、pitch／寸／premultiplied／`Close` を 1 本で固定する。(3) 少なくとも `record_display` の `Ok` が `command_list().is_some()` かつ `!= GraphicsCommandList::empty()` であることを `display_fault_tests.rs` の成功側に置く。
- **Traceability**: Requirement 6.1・6.2・6.5・7.2
- **Evidence**: design.md §emo-present／漏斗・照会・観測「`read.rs`」・§Testing Strategy「既存 GPU 型の再導出」3 項目目・§付録 A′ #18・research.md §7.7

### 🔴 Critical Issue 3: T-N2（`Visual::on_add` に乗る証拠）は「`Window` の無い bare entity では on_add が graphics を挿さない」ことを緑の根拠にしており、赤になれない

- **Concern**: 設計 T-N2 は「attach 後の entity が `VisualGraphics` を持たない（bare entity の窓では `on_add` が graphics を挿さない＝自前で入れていないことの証拠）」と書く。この檻が赤にできるのは「attach が自前で `VisualGraphics` を入れた」場合の**半分だけ**である。`on_visual_add` は `owner_window_exists`（`ChildOf` を辿って `Window` を探す）が偽なら**そもそも何も挿さない**ので、親が bare entity の世界では、**設計の本命である「`Window` 配下で on_add が `VisualGraphics`／`SurfaceGraphics`／`SurfaceGraphicsDirty` を挿し、`deferred_surface_creation_system` の query（`&VisualGraphics, &GraphicsCommandList, &GlobalArrangement, &mut SurfaceGraphics, &mut SurfaceGraphicsDirty`）を満たす」ことを一切固定できない**。設計全体がこの連鎖に依存しているのに、その成立を証明する決定論の檻が無く、「証拠」という言葉が実際に固定する性質より強い。
- **Verified**: `crates/wintf/src/ecs/graphics/visual.rs` `on_visual_add`（`has_owner_window && world.get::<VisualGraphics>(entity).is_none()` のときだけ挿す）／`crates/wintf/src/ecs/graphics/systems/surface.rs` `deferred_surface_creation_system`（上記 5 component を必須に持つ query）／hook の順序は bevy_ecs 0.19.1 `BundleInserter::insert`（`write_components` の後に `trigger_on_add`）で、同一 bundle の `ChildOf` は on_add 時に見える。wintf 自身の `tests/graphics/dcomp_integration_test.rs` が `(Visual::default(), ChildOf(window_entity))` の 1 bundle spawn で 3 component の挿入を検証している（既存の証拠あり・GPU 不要）。
- **Impact**: 「檻に入れるのは判断分岐のみ」の判断分岐がここ（自前 `VisualGraphics` を入れるか否か）である。恒真の檻を置くと、将来誰かが `VisualGraphics::new` を戻しても緑のまま、面が作られず絵が出ない退行が実機まで届く。
- **Suggestion**: T-N2 を「親を `Window::default()` 付きの entity にして attach → `world.flush()` 後に `VisualGraphics`／`SurfaceGraphics`／`SurfaceGraphicsDirty` が**存在**し（既定値・`!is_valid()`）、`GraphicsCommandList`／`HitTest::alpha_mask`／`AlphaMaskResource`／`Arrangement`（論理・k）も揃う」に改める（`dcomp_integration_test.rs` の型・GPU 不要）。対照として「親が `Window` を持たなければ 3 component は入らない」を**もう 1 本**置いて較正する（片方だけでは恒真）。
- **Traceability**: Requirement 1.2・6.5（新設分岐の GPU 非依存檻）・9.5
- **Evidence**: design.md §mount::VisualMount「Responsibilities & Constraints」第 1 項・§新設の檻 T-N2・research.md §7.4

## Design Strengths（1〜2）

1. **失敗点を回収より手前へ集約した前状態維持**（§Flow 1 キー決定・§Error Handling）: `record_display` を `take_recycled` より前に置くことで、失敗時に表示・メモ・`GraphicsCommandList`・`Arrangement`・マスク・可視性・`applied`／`native_size`／`last_show`／`pending_resize` の全てが適用前のままになる。現行 `show.rs`（`chain.upload` が挿入後に走り `resized` を読む）より構造的に強く、要件 7.1 を「言葉」でなく「順序」で満たしている。
2. **ゼロの明示と台帳の実数が正確**: wintf の swap chain ヘルパを撤去しない理由（`crates/areka-emo-text/src/surface.rs` が `create_composition_swap_chain`／`create_composition_surface_for_swap_chain` を消費）・wintf コード 0／doc 3 行・W13 共有 0 が明示され、付録 A′ の 44／34／8／127 は `#[test]` の実数えと**完全一致**した（下表）。丸めの一致表も `calculate_surface_size_from_global_arrangement` の `ceil` と `Mul` の `size × result_scale`（f32）で再現できた。

## 最終判定

**GO（条件付き）**。設計の骨格（k＝surface entity の `Arrangement.scale`・`Visual::on_add` に乗る spawn・原寸 bitmap のコマンドリスト・メモから k を外す・perf 必須集合の同時更新）は現行コードの定義と整合し、実装への道筋は明確である。ただし Critical 1（要件 2.4／3.1 の字義との食い違い＝裁定と要件改訂が要る）・Critical 2（供給の成功経路を固定する檻が 0 本）・Critical 3（T-N2 が恒真）は、いずれもタスク生成前に設計ディスカッションで裁定し design.md（と 1 は requirements.md）へ反映すること。反映後に `/kiro-spec-tasks` へ進んでよい。

## 軽微所見（非阻却・ディスカッションで仕分け・≤5）

1. **デバイス再初期化と合成メモ内の `GraphicsCommandList` の陳腐化（ゼロを明示せよ）**: wintf には `GraphicsCore::invalidate` → `init_graphics_core` の再生成（`HasGraphicsResources` に `set_changed`）があるが、`crates/wintf/src/ecs/graphics/systems/window_pos.rs` `invalidate_dependent_components` の NOTE(W3b-V) が言うとおり WUC 系（`VisualGraphics`／`SurfaceGraphics`）は無効化されず復旧しない。メモが旧デバイスの D2D bitmap を抱えるリストを保持し続ける点は**同じ穴の同じ側**なので阻却ではないが、設計 Non-Goals に「デバイスロスト後の復旧は wintf 既存の穴（W3b-V）と同格・`invalidate_all` は配線しない」と**ゼロを書く**こと。
2. **窓移動時の全面再描画が毎 tick 走る**: `mark_dirty_surfaces` は `Changed<GlobalArrangement>` で dirty を立てるため、ドラッグや `![move]` 系で窓の `Arrangement.offset` が変わる tick ごとに `render_surface` が 764×1094 の面を `Clear → DrawImage` し直す（swap chain 経路には無かった定常代金・設計見込み 0.2〜1 ms／tick）。`deferred_surface_creation_system` は寸が同じなら作り直さない（`surface_graphics.size == (width, height)` で continue）ので面の再生成は無い。Performance 表に「窓移動中の tick」行を足し、実機サインオフでドラッグ中の `tick_diag` を 1 度読む。
3. **`offset = 0` が暗黙の不変条件**: `visual_property_sync_system` は `Arrangement.offset × 自 entity の累積スケール（k 込み）` を WUC へ書き、`impl Mul<Arrangement> for GlobalArrangement` は `offset × 親スケール（1.0）` で bounds を出す。両者は offset が 0 のときだけ一致する。`logical_arrangement` の doc と T-N2 に「offset は 0 でなければならない（理由: wintf の 2 系統が k 込みか否かで食い違う）」と書き残す。
4. **T-N3 は本番と同じ式で**: 設計は `GlobalArrangement::from(logical_arrangement)`（単体変換）で bounds 幅を検査するが、本番は `窓 GA × Arrangement`（`Mul`・`self.bounds.left + scaled_offset + size × result_scale`）である。T-N4 が既に `Mul` 形なので、T-N3 も窓 GA（scale 1.0・offset 任意）を掛けた形に揃える（差は無いはずだが檻は本番の式を通すべき）。
5. **付録 A′ の数え方の単位**: #23 `frame_dpi_tests.rs` は 8 本中 1 本だけを「不変 1」と数え、他の行は file の全本数を数えている（例 #3 27・#21 9）。集計の合計は合っているが、「k≠1 を読むテストだけを数える行」と「file 全数を数える行」が混在するので、脚注 1 行で規則を明記する。あわせて `judge-perf.py` の「14 個」註釈は `J_PERF_STAGE_FIELDS` 直上の 1 か所だけ（設計の記述どおり）。
