# 設計検証レポート: areka-P0-sakura-tag-word-boundary

> 実施: 2026-09-13（`/kiro-validate-design`・非対話）。対象は `design.md`（HEAD `4cd0434f`）。設計の主張はすべてブランチ `claude/sakura-tag-word-boundary-e6d12b` の現物（`crates/areka-parsers/src/sakura/*.rs`・`.kiro/steering/roadmap.md`・同ウェーブ `text-decoration-canon` の作業ブランチ）で照合した。

## 検証の要約

設計の中核——`scan_tag` の語走査を最大 3 文字で頭打ちにし、既存の `bare_tag_len` で長さを確定してから `[` の有無を判定する（案 δ）——は、現行コードの構造と正確に噛み合っており、要件 1〜4 の全形について現物で追跡した結果が設計の決定表（行 A〜H）と一致した。既存の依存方向（`model ← lexer ← decode ← parse`）を変えず、新しい型・依存・失敗経路を作らない点も適切である。ただし「全数 grep 済み」と書かれた 2 つの目録（差し替え対象の既存テスト・訂正対象の注記）に漏れがあり、そのまま実装へ進むと既存テストが赤になるうえ、計画外のファイルに手を入れることになる。いずれも設計文書の訂正で閉じる規模であり、設計の方向性を変えるものではない。

## 現物で確かめた項目（設計の主張の裏取り）

| 確認項目 | 結果 |
|---|---|
| 短縮形 `\w`/`\b`/`\p` ＋ 数字の形は語走査へ到達しない | **成立**。短縮形判定（`SHORTHAND_WORDS.contains(&first) && 次が 1 桁 && その次が [ でない`）は語走査ループの手前で `return` する。語走査へ落ちる「短縮対象語＋数字」は判定式の第 3 項が偽の場合、すなわち数字の直後が `[` の場合だけであり、設計の例外（行 E・`word` は必ず 2 文字で直後は `[`）はこの構造から一意に導かれる |
| 頭打ち 3 文字の下で角括弧経路が要件どおり動く | **成立**。`\_l[x,y]`: 走査 `_`,`l` → `[` で停止 → `bare_tag_len("_l")=2` → 確定位置が `[` → `Tag{"_l",["x","y"]}`（不変）。`\__q[OnTest]`: 3 文字で頭打ちした位置がちょうど `[` → `Tag`（不変）。`\_[x]`: `bare_tag_len("_")=1` → `[` → `Tag{"_",["x"]}`（既存 T10 不変）。`\foo[`: 走査 `f`,`o`,`o` で頭打ち → 長さ 1 → 確定位置は `o` → `Bare("f")` ＋ 本文 `oo[`（要件 4.11 の意図的非互換・設計 L12 と一致）。`BracketScan::Unclosed` の吸収は「確定位置の直後が `[`」の形（`\e[注です`・`\b1[`）にだけ残る（要件 3.2／4.7） |
| 既存テストの綴り差し替え `\foo` → `\i` が守っていた意図を保つ | **成立**。`decode_tag` に `"i"` の腕は無く `decode_passthrough_tag` → `Raw` へ落ちる（現物で確認）。4 本とも「正典形の未知タグは 1 単位に区切られ隣を壊さない／未閉じ吸収が前の命令を欠落させない」の意図と期待値の形が不変。旧実装でも `\i[a,b]` は `Tag{"i",…}` に区切れるため、変異手順 ⑴ の「差し替え後の 4 本は旧実装でも緑」も正しい |
| `parse.rs` への 3 行接続と W13 の共有ファイル 0 の規律 | **成立**。`text-decoration-canon` の作業ブランチが `areka-parsers/sakura` で触るのは `decode.rs`・`decode_font_tests.rs`・`model.rs` の 3 つ（`git diff --name-only main...`）。本設計が触る `lexer.rs`・`parse.rs`・`lexer_tests.rs`・`decode_tests.rs`・`parse_tests.rs`・新規 2 ファイルとは重ならない。roadmap の干渉台帳（「`sakura-tag-word-boundary`（`lexer.rs`）⇄ `text-decoration-canon`（`decode.rs`・`compile.rs`）」）とも整合する。設計のリスク ⑵ が案じるテストファイルの rebase 面も、現時点では生じていない |
| 要件 5.1 の「31 綴り」と設計 L1 の 30 綴りループ | **実質的に完全**。`\_` の直後に本文が続く形（`\_本文[注]`）は先行 spec の規則で `\_本`（2 文字形）として読まれるため、「`\_` が 1 文字タグとして本文を従える形」は入力として構成できない。`\_` が 1 文字の綴りとして現れる形（末尾・`\`／`%` の直前・直後 `[`）は既存の T8／T6／T7／T10 が固定している。したがって被覆に穴は無く、要件文言側の「31」が 1 つ多い。設計は本件を設計ディスカッションへ申し送っており、扱いは適切 |
| `bare_tag_len` の不変条件「4 文字目以降は結果に影響しない」 | **成立**（`take(3)` で数え止め）。頭打ち 3 が同関数の入力として十分という設計の根拠は正しい |
| `lexer.rs` の現行行数 338・変更後の見積 | 一致（338 行）。1,000 行の規律に対して余裕がある |

## 重大な問題（最大 3 件）

### 🔴 重大な問題 1: 差し替え対象の既存テストが 4 本でなく 6 本（`validation_tests.rs` の 2 本が漏れている）

- **懸念**: 設計は「架空の多文字綴り `\foo` を入力に使う既存テストは 4 本（`lexer_tests.rs` 1・`decode_tests.rs` 2・`parse_tests.rs` 1）」「`validation_tests.rs` は不変」と書く。しかし `validation_tests.rs` には `parse(r"\foo[a,b]")` → `Raw("\foo[a,b]")` を期待する `syntax_unknown_tag_is_syntactically_split_and_kept_raw` と、`parse(r"\e\foo[")` の要素数 2 を期待する `lenient_passthrough_keeps_instructions_around_malformed_token` の 2 本があり、`mod.rs` の `#[cfg(test)] mod validation_tests;` で常に走る。是正後は前者が `[Raw("\f"), Text("oo[a,b]")]`、後者が要素数 3（`End`・`Raw("\f")`・`Text("oo[")`）になり、どちらも赤になる。設計の「不変」判定は `include_str!` の有無を grep した結果であって、`\foo` の使用箇所の全数 grep ではなかった。
- **影響**: 実装タスクがこの 2 本の赤に突き当たり、計画に無いファイルを編集することになる（要件 6.5「範囲外のファイルを編集しない」に対する計画の不整合）。変異手順 ⑴ の前提「既存の全テストが緑」も成り立たない。
- **提案**: Modified Files に `validation_tests.rs`（2 本・綴り `\foo` → `\i` の差し替え・期待値の形は不変）を追加し、「既存テストの入力差し替え」の本数を 6 に訂正する。あわせて `research.md` §9 の「4 本」の訂正記録も 6 本へ改める。`model_tests.rs` の `Instruction::Raw("\\foo[a,b]")` は `parse` を通さない直接構築なので対象外（そのままでよい）。
- **トレーサビリティ**: 要件 5.11（対象範囲とワークスペース全体のテストが緑）・6.5（範囲外ファイルの非編集）・5.7（変異手順の前提）
- **根拠**: design.md「File Structure Plan › Directory Structure」（`validation_tests.rs # 不変` の行）・「Modified Files」・「Testing Strategy › 既存テストの扱い」・「変異手順」手順 1〜2

### 🔴 重大な問題 2: 訂正対象の注記が 4 か所でなく 7 か所（「`[` がワード終端」の記述 3 か所が漏れている）

- **懸念**: 設計は要件 6.6 のために `lexer.rs` の注記 4 か所を書き直すと定めるが、是正後に実装と食い違う注記が他にも 3 か所残る。①モジュール doc の「正準タグ（`\` ＋ word ＋ `[args]`）— `[` がワード終端」、②`Token::Tag` の doc「word は `[` まで」、③`scan_tag` の doc「`\word[args]` → `Token::Tag`（`[` がワード終端）」。是正後は「`[` がワード終端」ではなく「タグ名は `bare_tag_len` の規則で終端し、その確定位置に `[` があれば角括弧経路」になる（`\foo[a,b]` では `[` の位置で語が終わらない）。
- **影響**: 要件 6.6「実装の実際の振る舞いと食い違う説明注記を残さない」が未達のまま実装レビューへ進む。読み手が `Token::Tag` の doc から「word は `[` の手前まで任意長」と誤読し、設計が新設した不変条件（`word` は 1〜3 文字で本文を含まない）と矛盾する。
- **提案**: 「注記訂正（要件 6.6）」の表に上記 3 か所を追加し、いずれも「タグ名の長さは `bare_tag_len` の規則で決まり、確定位置の `[` で角括弧経路へ入る（`Tag.word` は 1〜3 文字）」の趣旨に揃える。実装タスクには「`[` がワード終端」「word は `[` まで」を `lexer.rs` 全体で grep して 0 件にする完了条件を付ける。
- **トレーサビリティ**: 要件 6.6・設計の不変条件（`Token::Tag.word` は 1〜3 文字）
- **根拠**: design.md「Components and Interfaces › 注記訂正（要件 6.6）」の表（4 行）・「Data Models › 新しい不変条件」

### 重大な問題 3: なし

上記 2 件のほかに、設計の方向性・境界・依存・テスト戦略に是正を要する点は見つからなかった。

## 設計の強み

1. **既存の規則を「移す」だけで新しい語彙を持ち込まない**。`bare_tag_len` は既に案 δ の規則そのものであり、設計はそれを `[` の判定より手前へ移す 15 行前後の差分に閉じている。字句層に既知綴りの一覧を作らないため、意味層との二重管理も依存方向の逆転も生じない。現物で各行を追跡した限り、決定表 A〜H は現行コードから機械的に導ける。
2. **是正を戻すと赤になる対と、その赤の内訳まで先に書いてある**。変異手順 ⑴⑵ で「どのテストが赤になるはずか」を列挙し、例外判定の 3 通りの誤実装（常に走査結果／例外を省く／頭打ち 2）をそれぞれ別のテストが捕まえる形になっている。既存テストが担う不変も新規側で重複させず名前で列挙しており、実装レビューの物差しがそのまま使える。

## 最終判定

**判定: GO（条件付き）**

**理由**: アーキテクチャ・境界・依存方向・要件の対応付けは現物と一致し、実装経路も明確である。見つかった 2 件はいずれも設計文書の目録の漏れであり、設計の方向性や決定表を変えずに数行の追記で閉じる。実装に着手する前に設計ディスカッションで `design.md` へ反映すれば、以降のタスク生成に支障はない。

**次のステップ**:
1. 設計ディスカッションで問題 1・2 を `design.md` に反映する（Modified Files に `validation_tests.rs` を追加・注記訂正の表を 7 行へ・`research.md` §9 の本数訂正）。
2. 要件 5.1 の「31 綴り」は「30 綴り（`\_` は 2 文字形として読まれるため本文後続形が存在しない）」へ文言を合わせるか、設計の申し送りどおり注記で扱いを固定する（被覆そのものに穴は無い）。
3. 反映後に `/kiro-spec-tasks areka-P0-sakura-tag-word-boundary` でタスクを生成する。実装タスクには「`lexer.rs` 内の `[` がワード終端／word は `[` まで の記述 0 件」と「`\foo` を `parse`/`lex`/`dec` に通す既存テスト 0 件」の 2 つを機械で数える完了条件を持たせると、同種の漏れを再発させない。
