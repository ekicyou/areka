# 案 A 実機可否ゲート 実行手順書（タスク 4）

この手順で G1〜G8 を判定し、結果を同じディレクトリの `plan-a-gate.md` に判定表として書き出す。
判定表が確定すると、以降の分岐（案 A 継続／補助浮上の追加／切離しの強化／案 B へ切替）が一意に決まる。

**判定は「所感」ではなくログか目視の一次事実で行う。** 迷ったら FAIL ではなく「判定不能」として、
何が足りなかったかを書くこと。判定不能のまま先へ進めるより差し戻すほうが安い。

---

## 0. 前提

### 必要なもの

- **拡大率の異なる 2 台のディスプレイ**（例: 100% と 150%）。同じ拡大率の 2 台では G5・G6 の
  移動シナリオが意味を持たない。
- ゴースト窓をクリック・ドラッグできる操作環境（リモートデスクトップ経由でも可だが、
  DPI 仮想化が挟まると測定が濁るので実機推奨）。

### ビルド

```bash
cargo build -p areka
```

`release` ではなく `debug` を使う。`release` は `windows_subsystem = "windows"` でコンソールを
持たず、本手順のログ判定ができない。

### 起動コマンド（雛形）

fixture は**必ず絶対パス**で渡す。相対パスだと `pasta.dll` の LOAD が `0x8007007E` で落ちる。

```bash
AREKA_APP_SMOKE_EXIT_MS=120000 RUST_LOG=info,wintf::ecs::window::zorder_pair=debug,areka=debug ./target/debug/areka.exe "C:/home/maz/git/areka/.claude/worktrees/ghost-window-zorder-0055fb/crates/pilot/examples/shiori-host-32/fixtures/emo2" "C:/home/maz/git/areka/.claude/worktrees/ghost-window-zorder-0055fb/crates/pilot/examples/shiori-host-32/fixtures/emo2/emo2-kakukaku" > gate.out 2> gate.err
```

- `AREKA_APP_SMOKE_EXIT_MS` は**必ず付ける**（有界自動終了）。操作を伴う項目では 120000（2 分）程度、
  ログだけ見る項目では 8000 で足りる。
- ログは必ずファイルへ落とす。端末のスクロールバックで判定しないこと。

### ログの読み方（2 段 grep）

`scope` は wintf 側のレコードに載らない。`declared`（areka 側）で scope ↔ entity を引いてから、
wintf 側のレコードを entity で突き合わせる。

```bash
grep '\[zorder-pair\]' gate.out
```

起動直後に出るはずの並び:

```
[zorder-pair] declared scope=0 char_entity=<A> balloon_entity=<B>
[zorder-pair] declared scope=1 char_entity=<C> balloon_entity=<D>
[zorder-pair] owner-established entity=<B> peer=<A> owned_hwnd=… owner_hwnd=… measured_prev=…
[zorder-pair] owner-established entity=<D> peer=<C> owned_hwnd=… owner_hwnd=… measured_prev=…
[zorder-pair] fix   entity=… peer=… insert_after=… measured_next_after_fix=…
[zorder-pair] skip  entity=… peer=… reason=AlreadyAdjacent
```

**判定は必ず「実測」側の欄で行う。** `fix` レコードは同じ 1 行に指令（`insert_after=`）と
その後の実測（`measured_next_after_fix=`）を載せている——指令が出たことではなく、
実測が期待どおりだったことを見ること。

**隣接は「最も近い可視の隣」で測る**（2026-08-13 の裁定）。不可視の窓（スレッド既定の IME 窓など）は
読み飛ばして判定する。実装がすでにそうなっているので、ログの実測値をそのまま信じてよい。

## 1. 判定項目

判定は **G1 → G8 の順**に行う。**G1〜G6 のいずれかが FAIL した時点で案 B 確定**であり、
残りの項目は案 B の構成で再実施する（案 A のまま残りを測っても意味がない）。

### G1 描画の生存（ログ＋目視）

**やること**: 起動して 10 秒放置する。

**PASS 基準**: owner を張った後も両窓が描画され続ける。黒窓・消失・デバイスロストが無い。
`gate.err` にデバイス関連のエラーが出ていない。

**FAIL の帰結**: 案 B へ切替。

---

### G2 クリック透過の生存（目視・要操作）

**やること**: キャラの**透明部分**（立ち絵の外側）をクリックする。次に**不透明部分**（立ち絵の上）を
クリックする。

**PASS 基準**: 透明部のクリックが背後のアプリへ届き（背後のアプリが活性化する）、不透明部の
クリックはゴーストが受ける（ゴーストが反応する）。要件 5.1／5.2。

**FAIL の帰結**: 案 B へ切替。

---

### G3 クリック透過トグルの生存（目視・要操作）

**やること**: G2 を数回繰り返し、透明部 → 不透明部 → 透明部と行き来する。

**PASS 基準**: owner を張った後もトグルが機能し続ける（一度不透明部を掴むと透過が効かなくなる、
といった固着が起きない）。要件 5.3。

**FAIL の帰結**: 案 B へ切替。

---

### G4 タスクバー／Alt+Tab 非露出（目視）

**やること**: タスクバーを見る。Alt+Tab を押す。

**PASS 基準**: ゴースト窓がタスクバーにもアプリ切り替え一覧にも現れない（現行の見え方が不変）。
要件 5.5。**owner を張ったことでバルーン窓だけが現れる**といった変化が無いことを特に見ること。

**FAIL の帰結**: 案 B へ切替。

---

### G5 ドラッグとバルーン追従（目視・要操作）

**やること**: ① キャラ窓をドラッグして動かす。② バルーン窓を単独でドラッグして動かす。
③ 再びキャラ窓をドラッグし、バルーンが追従することを見る。

**PASS 基準**: いずれも現行どおり動く。ドラッグが効かない・追従が止まる・掴んだ窓が飛ぶ、が無い。
要件 5.4。

**FAIL の帰結**: 案 B へ切替。

---

### G6 キャラ窓の活性化でペアが浮上し隣接する（ログ・要操作）★中核保証

**やること**: **各スコープのキャラ窓を順にクリックする**（emo2 は 2 スコープ＝キャラ窓 2 枚）。
クリックの前に、他のアプリ（メモ帳など）を活性化してゴーストを一度背面へ回しておくと、
浮上そのものも同時に見られる。

**PASS 基準**: **各スコープについて**、クリック後の実測レコードで
「そのキャラ窓の**最も近い可視の手前**がそのスコープのバルーン窓である」ことが確認できる。
要件 1.1／1.2。

**判定式**:

```bash
grep '\[zorder-pair\] fix' gate.out
```

`fix` の `measured_next_after_fix=` が、`declared` と `owner-established` から引いた
**そのペア自身のキャラ窓 HWND** と一致すること。

**注意 ①**: 起動時の記録では判定しない。G6 が問うのは「**キャラ窓をクリックした後**」である。

**注意 ②**: 是正が要らないスコープは `skip … reason=AlreadyAdjacent` になり、**実測値を記録に残さない**。
これでは肯定的な証跡にならないので、**各キャラ窓を順に活性化して、スコープごとに `fix` を出させること**。
他アプリを挟んで背面へ回してからクリックすると確実に是正が走る。

**FAIL の帰結**: **案 B へ切替**（案 A の中核保証の不成立）。ただし FAIL と判断する前に、
上の注意 ①② の取り違えでないことを必ず確認すること。

---

### G7 バルーン窓の活性化でキャラも浮上する（目視・要操作）

**やること**: 他のアプリを活性化してゴーストを背面へ回してから、**バルーン窓をクリックする**。

**PASS 基準**: バルーン窓だけでなくキャラ窓も一緒に手前へ出る（キャラ窓が他アプリの窓の背後に
残らない）。要件 1.3。

**FAIL の帰結**: **案 A は継続**し、補助浮上（raise assist）を有効にする分岐へ進む
（タスク 5.1 → 5.3 → 5.4）。案 B へは倒さない。

---

### G8 破棄順序の双方向で異常終了しない（ログ・要操作）

**やること**: ① 通常の終了（有界自動終了に任せる）。② 可能ならキャラ窓側・バルーン窓側の
どちらが先に消える経路も試す。

**PASS 基準**: どちらの順でもプロセスが継続し、異常終了しない。要件 5.9。
`gate.err` にクラッシュの痕跡が無く、終了コードが正常。

**判定式**:

```bash
grep -c '\[zorder-pair\] owner-detach' gate.out
echo "exit code: $?"
```

**注意**: 現在の実装では、**4 窓が 1 バッチで despawn する通常の終了経路では切離しが走らない**
（`OwnerLink` を持つ側も同時に消えて走査対象から外れるため）。よって `owner-detached` が
0 本でも、それ自体は FAIL ではない——**プロセスが異常終了しないこと**が判定基準である。

**FAIL の帰結**: 切離しの適用時点を早める分岐（タスク 5.2）。それでも塞げない場合のみ案 B へ切替。

---

## 2. 判定表の書き出し

`verification/plan-a-gate.md` に以下の形で記録する。**根拠ログの実際の行を貼ること**
（「PASS した」だけでは後から再検証できない）。

```markdown
# 案 A 実機可否ゲート 判定表

- 実施日:
- 実施環境: ディスプレイ 2 台（拡大率 __% / __%）・解像度 __ / __
- ビルド: debug / コミット <hash>
- fixture: emo2（emo2-kakukaku）

| # | 判定項目 | 結果 | 根拠 |
|---|---|---|---|
| G1 | 描画の生存 | PASS / FAIL / 判定不能 | |
| G2 | クリック透過の生存 | | |
| G3 | 透過トグルの生存 | | |
| G4 | タスクバー／Alt+Tab 非露出 | | |
| G5 | ドラッグとバルーン追従 | | |
| G6 | キャラ活性化でペア浮上＋隣接 | | |
| G7 | バルーン活性化でキャラも浮上 | | |
| G8 | 破棄順序の双方向で異常終了なし | | |

## 結論と次の分岐

- （G1〜G6 全 PASS かつ G7 PASS）→ 案 A 確定・補助浮上なし。タスク 5.1 は既定のまま。
- （G1〜G6 全 PASS かつ G7 FAIL）→ 案 A 継続・補助浮上を有効化。タスク 5.1 → 5.3 → 5.4。
- （G8 FAIL）→ タスク 5.2（切離しの適用時点を早める）。
- （G1〜G6 のいずれか FAIL）→ 案 B 確定。タスク 5.1 → 5.5 → 5.6 → 5.7。

## 根拠ログ（抜粋）

（`[zorder-pair]` の行と、判定に使った entity ↔ HWND の対応表をここに貼る）
```

## 3. 判定後に走るタスク

判定表が確定したら、**指した分岐のタスクだけ**を実施する（実施されなかった分岐は
タスク 6.1 の前提にも含めない）。

| 判定 | 実施するタスク |
|---|---|
| 全 PASS | 5.1 のみ（既定のまま） |
| G7 FAIL | 5.1 → 5.3 → 5.4 |
| G8 FAIL | 5.2 |
| G1〜G6 いずれか FAIL | 5.1 → 5.5 → 5.6 → 5.7 |

その後は共通で 6.1（決定論的テストの仕上げ）→ 6.2（実機サインオフ）／6.3（回帰の固定）。

## 4. 既知の落とし穴

- **起動時の記録で G6 を判定しない。** G6 は「キャラ窓クリック後」の実測を問う。
- **`skip AlreadyAdjacent` を肯定的証跡として数えない。** このレコードは実測値を持たず、
  隣接がどちら向きで成立したかも復元できない。
- **不可視窓の割り込みは判定に影響しない**（実装が読み飛ばす）。もしログの実測値に
  身に覚えのない HWND が現れたら、その窓のクラス名・可視性・owner を調べてから判断すること
  ——過去にスレッド既定の IME 窓を「隣接保証の不成立」と読み違えかけた事例がある。
- **`target/` の成果物キャッシュを疑うこと。** 古い成果物で健全なソースに対し決定論的な赤が
  8 回連続再現した事例がある。驚く結果を見たら `cargo clean -p areka` から測り直す。
- **単一モニタでは G5・G6 の移動シナリオが意味を持たない。** 拡大率の異なる 2 台を用意すること。
