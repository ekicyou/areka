# 設計の検証レポート: areka-P0-ghost-session-test-load-flake

- 対象: `design.md`（587 行・`spec.json` の phase は `design-generated`）
- 検証の日: 2026-10-05
- やり方: 設計の文をそのまま信じず、設計が挙げた既存のコードを実物のファイルで読んで突き合わせた。cargo のビルドとテストは回していない（他のセッションと机を共有しているため）。ソースとコミットには触っていない。

## まとめ

待ちの芯を 1 つにまとめ、打ち切りを「待ち始めからの総時間」から「相手が進まなかった時間」へ変える、という骨組みは筋がよく、既存の呼び名を保つので影響も小さい。既存のコードについての設計の記述は、読んで確かめた範囲でほぼ正しかった。ただし、芯の要である**進みの目印の数え方に、実物のコードと合わない点が 1 つ**あり、このままだと「止まった」の判定がほとんど働かない。あわせて、要件 2.6 の読み替えと、目印を持たない待ちが対象の族に残る点は、討議で決めてから先へ進むのがよい。

## 判定

**GO（条件つき）** — 骨組みと境界は妥当で、作り直しは要らない。下の重大な指摘 1 は設計の文の小さな直しで済むが、直さずにタスクへ進むと要件 3.2 を満たせないので、設計の討議で 3 点を決めて `design.md` へ反映してからタスク生成へ進むこと。

## 重大な指摘（3 件）

### 指摘 1: 進みの目印が「状態の問い合わせ」を数えるので、止まっていても増え続ける

- **問題**: 設計は足場の目印を「起こした回数＋偽の SHIORI が受けた呼び出しの数（**状態の問い合わせも含む**）」と決めている。しかし SHIORI のアクターは、手が空いている間ずっと 500 ms ごとに状態を問い合わせる。
  - `crates/areka-kanade/src/shiori/real.rs` の `run_shiori_loop` は、`recv_timeout(IDLE_INTERVAL)` が時間切れになるたびに `report_exit_once` を呼び、その中で `backend.status()` を呼ぶ。定数 `IDLE_INTERVAL` は 500 ms。
  - 偽の SHIORI の `ScriptedShioriBackend::status` は、呼ばれるたびに `RecordedCall::Status` を記録へ足す（`emo2_boot/spine.rs`）。
  - 既存の `ScriptedShioriHandle::non_status_calls` の doc も、これを「死活監視ノイズ」と呼んで除いている。
- **影響**: 台帳にあるゴーストが 1 体でも生きていて手が空いていれば、何も進んでいなくても目印は 0.5 秒ごとに増える。すると
  - 欠陥で止まった待ちが `［止まった］` にならず、300 秒待ってから `［進んではいた］…負荷で遅い` と出る（要件 3.2 に反し、3.1 の「相手が進んだか」も嘘になる）。
  - 設計の読み分けの表はこの文言を「負荷で遅い→足場の同時の数を絞る（2.7）」へ導くので、欠陥を負荷と読み違える。
  - 本当に赤のテストが 1 本あたり 30 秒（`wait_steady` は 20 秒）でなく 300 秒かかる。
- **もう 1 つの穴（逆向き）**: 「起こした回数」は起動の台帳 `boots` の長さだが、台帳へ足すのは `FakeShiori::Scripted`（毎回）と `ScriptedThenConnectFail`（最初の 1 回）だけである（`ghost_switch_test_support.rs` の `GhostBootInputsSource` の閉包）。`ConnectFail`・`WiringFail`・`BalloonMissing` で起こした回は数に入らない。設計の「戻ったときには起こした回数が増えているので進んだと数えられる」は、切替の失敗から既定ゴーストへ戻るテスト（赤を観測した族そのもの）では成り立たない。
- **直し方の案**:
  1. `call_count()` は状態の問い合わせを除いた数（`Get`・`Notify`・`Unload`）にする。
  2. 「起こした回数」は台帳の長さでなく、作り口の閉包が呼ばれた回数（どの `FakeShiori` でも 1 つ増える数え）にする。
  3. 檻を 1 本足す: 偽の SHIORI の `status()` を何回呼んでも目印が増えないこと（時間を待たずに確かめられる）。
- **要件**: 2.1・3.1・3.2
- **設計の場所**: 「設計の決定」論点 3、「SwitchRig の待ち」の `progress_probe()` と `call_count()`、「System Flows」の 2 つ目の箇条書き、「LoadRepro」の読み分けの表

### 指摘 2: 要件 2.6 は、書かれたとおりには満たしていない（読み替えの裁定が要る）

- **問題**: 要件 2.6 は「注入する合成の時刻を、相手がそれまでの時刻を処理し終えた観測より先へ進めない」。設計は進め方（実時間 1 ms ごとに 100 ms・上限なし）を変えず、「時刻の受け手に合成の締切が無い」という構造で括弧書きの目的だけを満たす、と読み替えている。設計自身も「討議で確かめる点」と書いている。
- **確かめた事実**:
  - 設計の根拠は実物と合っている。`DispatcherState::on_tick` は再生中の台詞へ経過秒を渡すだけで kanade へは送らない。`KanadeMsg::Tick` を送るのは `areka-ghost/src/ticker.rs` と `spine_conformance_support.rs` の `StageSink for SpineHarness` だけ。足場は `TickerMode::Disabled`。
  - 「知らせを待つ形は本番に手を入れないと作れない」も正しい。`DispatcherMsg` には返事を受け取れる種類が無い。
  - 一方、`spine.rs` の `SPIN_WAIT` の doc（設計が `spine_wait.rs` へ doc ごと移すと言っている文）は「追い越しうる時刻には必ず上限（頭打ち）を置くこと」と定めており、設計の「数値の頭打ちは置かない」とぶつかる。設計は「`spine.rs` の doc が定める規律を保つ」とも書いているので、文書の中で食い違う。
  - 設計が挙げた害は「kanade の合成の締切が切れる」だけだが、過去に実際に起きた害は「時刻が先へ進んで、待っている条件そのものが壊れる」（同じ doc の実測）である。今の `pump_talking_until` の呼び手（9 ファイル）の条件は「呼び出しの記録が増えた」「切替の予約が下りた」など後戻りしないものだったので、今は当たらない。ただし檻 8 が固定するのは kanade の締切の経路だけで、こちらは固定されない。
- **影響**: 要件の文と設計が合わないままタスクへ進むと、実装のレビューで 2.6 の合否が決められない。
- **直し方の案**（どちらかを討議で選ぶ）:
  - A. 要件 2.6 の文を、設計の読み（「合成の時刻を受け取る相手が、締切も後戻りする状態も持たない構造に限る」）へ改める。あわせて移す doc に「足場の時計はこの例外」と理由つきで書き、`pump_talking_until` の doc に「条件は後戻りしない観測だけを渡す」と書く。
  - B. 文のとおりに満たす。境界を広げて dispatcher に処理済みの知らせを足す（本番のコードに触る）。
- **要件**: 2.6
- **設計の場所**: 「2.6 の満たし方」、「設計の決定」論点 6、Testing Strategy の檻 8

### 指摘 3: 目印を持たない待ちが対象の族に残り、2.1 を「満たした」と言える範囲が狭い

- **問題**: 追跡表は 2.1 を `Progress::Count` で満たすと書くが、目印が渡るのは足場の `pump_*`・`wait_steady`・`shutdown` と `SpineHarness::shutdown_bounded` だけである。対象の族が直接呼ぶ待ちは「目印なし」（総時間 30 秒・文言は `［進みは不明］`）のまま残る。
  - `spin_wait_until` を直接呼ぶ対象の族: `ghost_session_switch_fallback_tests.rs`（2 か所）・`session_end_sync_send_tests.rs`（2 か所）・`shell_balloon_switch_session_tests.rs`（2 か所）・`shell_balloon_switch_session_lap_tests.rs`（1 か所）・`spine_*_tests.rs`（合わせて約 20 か所）。
  - `ghost_session_restart_tests.rs` の `run_input_until` も「目印なし」へ寄せる。変わるのは総時間 10 秒→30 秒と、休みが入ることだけ。
  - `join_bounded("spine seriko join", 10 秒)` と、古い呼び名の `run_bounded` の呼び手は総時間のまま。
- **影響**: これらは相手が進んでいても実時間だけで赤になり（2.1）、文言は進んだかどうかを言えない（3.1）。設計は「再現で赤になったものだけ加える」としているが、再現しなかった場合（6.4 の道）は 6.1 の確かめも無いので、直らないまま完了になる。要件 6.4 は「コードの定義の名前で確かめられる欠けは再現を待たずに直す」と定めており、これらは名前で確かめられる欠けに当たる。
- **直し方の案**:
  - 足場か偽の SHIORI の観測口が手元にある直接の呼び手（切替・戻り・終了の同期送り・シェルとバルーンの切替）には、再現を待たずに目印を渡す形（例: 足場に「条件だけを待つ」口を足す、または目印つきの `spin_wait_until` を用意する）を既定の作業にする。
  - 目印を作れない待ち（作業プールを待つ `run_input_until`・`spine` の Tick 注入の待ち）は、「2.1 の例外」として理由つきで設計に名指しし、追跡表の 2.1 の行にもそう書く。
- **要件**: 2.1・3.1・6.4・7.3
- **設計の場所**: 「Requirements Traceability」の 2.1 の行、「Modified Files」の条件つきの行、「SwitchRig の待ち」の Implementation Notes、「古い呼び名の中身」

## 良い点

1. **既存の事実の読みが正確**。`spin_wait_until` の 30 秒と 100 万回の空回し、`wait_steady` の 20 秒、`run_input_until` の 10 秒と `yield_now` だけの空回し、`frame_ghost_quit_switch_tests.rs` の自前の `wait_steady`、`WorkDir` の破棄の順（札を閉じる→木を消す→札を消す）と `discard_tree` の `gc-` の木に札が無いこと、待ちが `false` を返すことを期待するテストが 0 件であること。いずれも実物と合っていた。空回しの予算を回数から時間へ変える理由（負荷の下では 100 万回が 30 秒に収まらず、休みへ落ちない）も実物の数字と合う。
2. **境界と進め方が堅い**。古い呼び名を保って呼び手を触らない、最初は中身を変えずに移すだけ、「直す前」の測定を先に取る、os error 5 と同時の数の絞りは記録が条件を満たしたときだけ、という順は、並走の机でも取り違えにくい。檻を偽の時計で作り、実時間を待たせない方針も、この spec が直そうとしている病を檻に持ち込まない。

## 小さな気付き（重大ではない）

- `spine.rs` の移した後の行数の見込み「850 行前後」は少なめである。移るのは定数と doc と `spin_wait_until`（約 65 行）と `run_bounded`・`join_bounded`（約 25 行）で、足す分（子モジュールの宣言・`call_count`）を入れると 920 行前後になる。上限 1,000 行は守れるが、余裕は 80 行ほどと見ておくこと。ほかに触るファイル（`ghost_switch_test_support.rs` 426 行・`frame_ghost_quit_switch_tests.rs` 287 行・`ghost_session_restart_tests.rs` 424 行・`devroot.rs` 666 行・`devroot_sweep_tests.rs` 604 行）は余裕がある。
- 足場を使うファイルの数は、この検証の粗い `grep` では 30 本（足場のファイル自身を含む）で、起票時の 28 本と近い。差は要件 1.4 の数え上げで記録すれば足りる。
- `bool` を返す包みが文言を標準エラーへ出すときは、テストの実行器が拾える出し方（`eprintln!`）に限ると設計に書いておくとよい。
- 要件の ID（1.1〜7.3 の 30 項目）は追跡表に全部載っている。抜けは無い。
