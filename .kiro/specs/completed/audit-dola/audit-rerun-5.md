# audit-dola かけ直し 21・5 回目（ponytail-audit・範囲 `crates/dola/`）

**この範囲がしていること:** dola は 2 つのエンジンを持つ。1 つは宣言したアニメ（変数・遷移・キーフレーム・ストーリーボード）を検証してコンパイルし、`DolaRuntime` が時刻を受けて値の差分を購読者へ配るもの。もう 1 つは cue（`CueSheet` → `TimedSchedule` → `CuePlayer`）で、さくらスクリプトの台本を絶対時刻で全部の受け手へ配るもの。

**想定した負荷:** 1〜4 回目と同じ。1 つのプロセスの UI スレッドが 60fps 前後で `tick` を呼ぶ。インスタンスは十数個、cue は台本 1 枚で数百。文書はゴーストの作者が書く（＝作者の書き損じや極端な値が入りうる入口）。PC のスリープの後などに、1 回の tick で時刻が大きく飛ぶことがある。

**今の本番で動いているもの:** cue の側だけ（`areka`・`areka-sakura`・`areka-emo-text`・`areka-seriko`・`areka-ghost` が `CuePlayer`・`CueSink`・`to_talk_schedule`・`sum_on_ms_grid`・`clock::now` を使う）。アニメの側（`DolaRuntime`）は、wintf の `DolaAnimator` と `tick_dola_animators` が公開されているだけで、本番のどこにも System として組まれておらず、`start` を呼ぶ所も無い（grep で確かめた。呼ぶのはテストだけ）。

**対象:** HEAD `6622020c`。4 回目の 3 件の直し（`6622020c`）と tasks.md の「## Implementation Notes」を読んだうえで、新しい指摘と、直しが持ち込んだ欠陥だけを挙げる。

## Should fix（1 件）

### R5-01 トリガーなしの無限のループは、tick の中のトリガーの時点でまだ前の周回のままなので、子とぶつかって終わるときの確定値がコマの刻みで変わる（4 回目の「指摘にしなかったもの」の読み違い・3 回目の直しの前からある）
- **重さ:** should-fix
- **必ず直すか:** いいえ（must-fix ではない）。今の本番の振る舞いに当たらないため。ただし audit 系の決め（指摘は全部直す）に従って直す。
- **本番の振る舞いに触るか:** いいえ。今の本番は `DolaRuntime` を動かしていない（wintf の `tick_dola_animators` はどこにも組まれず、`start` の呼び手はテストだけ）。直すと、トリガーで起こした子が無限のループとぶつかったときの確定値が変わる（`DolaRuntime` を使い始めたら当たる所）。
- **場所:** `crates/dola/src/runtime/facade.rs:335-345`（`update_internal` の出来事の繰り返し。Step 1.5 の `process_triggers(t)` が先で、トリガーなしの無限のループを進める `process_loop_ends(t)` は後）・`:379-381`（トリガーなしの無限のループの `end_time` は出来事に入れない）・`src/runtime/conflict_resolver.rs:437-452`（Cancel・Trim は `evaluate_all_for_group`、Conclude は `collect_current_segment_final_values` で、終わらせる側の全部の変数の値を `start_time` で測る）・`src/runtime/subscription_manager/mod.rs:99-114`（評価が `None` の変数は凍結値を配る）
- **何が悪いか:** トリガーなしの無限のループは、出来事の時刻ごとの Step 2 でだけ周回を進める。なので、ある出来事の時刻 t に Step 1.5 で子を起こすと、その時点の無限のループは「前の出来事の時刻まで」しか進んでいない。60fps なら前のコマまで進んでいるが、tick を大きく飛ばすと周回の起点が何周も前のまま。子とぶつかって Cancel・Trim・Conclude で終わるとき、確定値はこの古い起点で測られる。
  - 4 回目は「確定値は `last_values` へ入るだけで、同じ変数は起きた子の項目が必ず評価を取るので、配る値は変わらない」とした。これはぶつかった変数（子も触る変数）でだけ正しい。終わらせられるインスタンスがほかに持つ変数（子が触らない変数）は、終わった後は項目が無く、`evaluate` が `None` を返すので、この確定値がそのまま配られる。
  - 例: 無限のループ L（Cancel・1 秒・x と y を 0→1）と、親 P（a を 3 秒・2.5 秒に子 C を起こす）を 0 秒に起こす。C は x だけを 5→6。60fps で 0〜3 秒を回すと、2.5 秒に L が終わり、y は **0.5**（3 周目の半ば）で止まる。tick を 0.0 → 3.0 にすると、L の起点は 0 秒のままなので、y は **1.0**（周回の長さを過ぎた扱いで最後の値）で止まる。作業場の外（scratchpad）に crate を写してこの台本を回し、2 つの値を確かめた。
  - Conclude の方針でも、1 周に同じ変数のセグメントが 2 つ以上あると「今のセグメントの終わりの値」が変わる（古い起点では最後のセグメントを選ぶ）。
  - 有限のループとトリガーを持つループは周回の終わりが出来事なので、この形にならない（R3-01・R4-01 で直った所）。残るのは、出来事に入れないトリガーなしの無限のループだけ。
  - 外から `start()` を tick の間に呼ぶときも、無限のループは前の tick のままで測られる。これは呼び手の時刻の渡し方の問題で、(b) の決めに近いので、ここでは数えない。
- **直し:** 出来事の繰り返しの頭（Step 1 の前でも Step 1.5 の前でもよい）で、Playing・`loop_count == -1`・トリガーなし・`end_time < t` のインスタンスを、t より前に終わる周回の分だけ進める。`end_time < t` を「より小さい」で比べるのは、t ちょうどに終わる周回は 60fps でも Step 1.5 の時点ではまだ進んでいない（前のコマは t より前）から。`process_loops(inst, t, rng)` をそのまま呼ぶと、進めた後の `end_time` がちょうど t になったときもう 1 周進む（`>=` で回る）ので、その分だけ「より小さい」で止める。作業場の外の写しで、`end_time < t` で選んで `process_loops` を呼ぶ形を足すと、上の台本は 60fps も一度に飛ばすのも y が 0.5 になり、`cargo test`（全部）は緑のまま。
  - 檻 1 本（`tests/trigger/event_order_test.rs`）: 上の台本を 60fps と 0.0 → 3.0 の 2 通りで回し、どちらも最後に配った y が 0.5。今の HEAD は全部のテストが緑なので、この形を縛る檻は無い。
- **触る所:** `DolaRuntime::tick` の中の、トリガーで起こした子が無限のループを終わらせるときの確定値（今の本番は通らない）。

### R5-02 トリガーの循環は拒むが、枝分かれは数えない。小さな文書で、1 回の `start` が 1 回の tick に起こす子の数が 2 のべき乗で増える（前からある）
- **重さ:** nice-to-have
- **必ず直すか:** いいえ（must-fix ではない）。今、作者の書いた dola の文書を読み込む道が本番に無いため。
- **本番の振る舞いに触るか:** いいえ（今の本番は `DolaRuntime` を動かしていない）。直しが注だけなら、振る舞いは何も変わらない。検証を足すなら、今は通る文書の一部が読み込みで拒まれるようになる。
- **場所:** `crates/dola/src/validate/rules.rs:651-684`（`validate_trigger_cycles` は循環だけを見る）・`src/runtime/facade.rs:417-426`（`process_triggers` は発火が無くなるまで回す）
- **何が悪いか:** V15t は循環を拒むので、トリガーの鎖は必ず止まる。ところが、循環の無い鎖でも枝分かれすると、起こす子の数は掛け算で増える。例: S0〜S(n−1) の n 個のストーリーボードがあり、それぞれ次の S を開始の時刻に 2 回起こす（変数なし・長さ 0）。`start("S0", 0.0)` の後の 1 回の `tick` が、2^n − 2 個の子を起こし、同じ数の `TriggerResult` を積む。手元の release の build で: n=12 で 4,094 件・約 11 ms、n=16 で 65,534 件・約 0.17 秒（作業場の外の写しで測った）。1 段ふえるごとに倍なので、n=24（エントリ 46 個の文書）なら 1 回の tick に約 45 秒と見込む。60fps でも一度に飛ばしても同じ（コマの刻みの問題ではない）。ループの親なら周回ごとに繰り返す。データは壊れない。
- **直し:** 今は文書を書くのが areka の開発者だけなので、注で限界を残す（`shortcut:` の形・コードは変えない）。例（`validate_trigger_cycles` の頭）: 「`shortcut:` トリガーの枝分かれの数は数えない（16 段 × 2 本で 1 回の tick に約 6.5 万件・0.17 秒、1 段ごとに倍）。作者の文書を読み込むようになったら、循環の無いことを確かめた後に、1 回の start が起こす子の数（1 ＋ 起こす先の数の和・飽和で足す）に上限を置く」。上限を今入れるなら、同じ関数の中で、ストーリーボードの名前ごとの数を覚えて 1 回ずつ足すだけで済む（循環が無いので止まる）。
- **触る所:** 注だけ（上限を入れるなら検証の規則が 1 つ増える）。
