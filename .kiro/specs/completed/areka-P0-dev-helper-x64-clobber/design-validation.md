# 設計の検証: areka-P0-dev-helper-x64-clobber

- 検証日: 2026-10-16
- 対象: `design.md`（要件 `requirements.md`・調べ `research.md` と照らし合わせた）
- 進め方: `kiro-validate-design`（分析 → 大事な問題 → よい点 → GO／NO-GO）。対話なしで判定まで行った。

## まとめ

設計は小さく、要件 1〜3 のすべての項目に部品と確かめ方が対応している。判定と記録を helper を起こす関数 `spawn` の入口の 1 か所に置き、全体テストの側は「終わったときの状態」だけで合否を決める形で、既存の失敗の道・段の並び・同じウェーブの他の spec の席を崩さない。下の 3 点は設計を作り直すほどではなく、タスクを作るときに決めておけば足りる。

## 大事な問題（3 点）

### 1. 全体テストの揃えの段の失敗の分かれ道に、繰り返し回せる確かめが無い

- **問題**: 揃えの段の分かれ道（揃っていた・写した・写し元が無い・置き換えが断られた・一時ファイルの後始末）は、実装のときの一回きりの確かめでしか見ない。毎回の全体テストで通るのは「既に揃っていた」の道だけになる。
- **影響**: 後で誰かが段を書き替えたとき（同じファイルを触る `clippy-199-lints` など）、失敗の道で終了コードを立て忘れる・一時ファイルが残る、といった壊れ方に気付く仕組みが無い。決定論のテストを網羅するという決まりとも食い違う。ただし、段は写した後に置き先をもう一度見て合否を決めるので、壊れても「黙って緑」にはなりにくい。
- **提案**: どちらかを設計の議論で決める。⑴ 段の中身を置き先と写し元を引数に取る関数にして、`target\` の下の小さな偽のファイルで 4 つの道を回す自分の検査を足す（ほかの道具の `-SelfTest` と同じ形）。⑵ 一回きりの確かめで済ませると明記し、その結果（分かれ道ごとの端末の文と終了コード）をタスクの記録に残す。軽さを優先するなら ⑵ でよい。
- **要件**: 1.3・1.5・2.1
- **設計の箇所**: 「SyncI686HelperStep」の Implementation Notes（Validation）・「Testing Strategy」の全体テストのスクリプトの項

### 2. 実機の確かめの順番と後片付けが書かれていない

- **問題**: 実機の確かめは 2 回ある。1 回目はわざと x64 版の helper を `areka.exe` の隣に置いて記録を見る。2 回目は実装の最後の全体テストの後に、写す手間なしで claudia を起こす。1 回目を全体テストの後に行うと、2 回目の前提（隣が i686 版）が崩れる。1 回目の後に x64 版が隣に残ったままにもなる。
- **影響**: 確かめの順を取り違えると、2 回目が `0x800700C1` で落ちて、設計の不具合と見分けがつかなくなる。全体テストの回し直し（重い回）を招く。
- **提案**: タスクで順番を決めて書く。「x64 版を置いての確かめ」→「実装の最後の全体テスト 1 回」→「写さずに claudia を起こす確かめ」。1 回目の後は、i686 版を写して戻すか、続く全体テストに戻させることを明記する。実機の根は `target\` の下の短い絶対パスにする（設計どおり）。
- **要件**: 1.4・3.1〜3.4
- **設計の箇所**: 「Testing Strategy」の実機の項

### 3. 記録の宛先の名前 `host32-helper` が、記録を出す側と合っていない

- **問題**: 記録を出すのは areka の側（`shiori-host32-host`）だが、宛先の名前は helper のプロセスを指す `host32-helper` になっている。同じクレートの既存の宛先は `shiori-charset`、kanade の側は `shiori-actor` で、どれも「出す側」の名前である。
- **影響**: 宛先と `event` の名前は、実機の確かめや後の spec がログを検索するときの決めごとになる（設計の Revalidation Triggers にもある）。helper のプロセス自身の記録（標準エラー）と取り違えやすく、後から名前を変えると検索の読み替えが要る。
- **提案**: 決める前に一度だけ確かめる。宛先を出す側に合わせた名前（例: `shiori-host32`）にするか、今の名前のままにするかを設計の議論で決め、決めた名前を定数にして既存の `LOG_TARGET` と同じ書き方にする。検索は `event=helper_not_i686` で行えるので、どちらを選んでも働きは変わらない。
- **要件**: 3.1・3.2・3.5
- **設計の箇所**: 「HelperImageCheck」の記録の規則の表・「Monitoring」

## よい点

1. **判定を置く場所が 1 か所で、境界を守っている**。helper を起こすすべての道が通る `spawn` の入口に置くので、呼び手ごとに足さずに済む。`real_connect`・kanade・`boot_config.rs` を触らず、同じウェーブの `baseware-root-list` と重ならない。判定はバイト列だけを見る純粋な関数と記録の関数に分かれていて、ファイルを作らずに合成したバイト列で全部の分かれ道を確かめられる。
2. **全体テストの段の合否が「終わったときの状態」だけで決まる**。写した後にもう一度置き先を見るので、途中のどこで失敗しても赤として表に出る。i686 のビルドが赤でも前の i686 版を置いて二重に赤にしない、という要件 1.3 の決めごとをそのまま形にしている。端末の文は固定の英文だけで、.NET の例外の本文（日本語に訳されることがある）を出さない配慮も入っている。

## 判定

- **判定: GO**
- **理由**: 既存の作りとの食い違いは無く、要件のすべての項目に部品と確かめ方がある。上の 3 点はどれもタスクの書き方か名前の選び方で片付き、設計の骨組みを変えない。
- **次にすること**:
  1. 設計の議論（`/kiro-design-discussion areka-P0-dev-helper-x64-clobber`）で 3 点を決める（1＝自分の検査を足すか一回きりで済ませるか、2＝実機の確かめの順と後片付け、3＝宛先の名前）。
  2. その後にタスクを作る（`/kiro-spec-tasks areka-P0-dev-helper-x64-clobber`）。
