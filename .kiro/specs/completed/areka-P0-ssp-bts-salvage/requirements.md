# Requirements Document

## Project Description (Input)
SSP の課題管理（MantisBT・https://bts.shillest.net/ ）には、利用者とゴースト作者が長年出してきた要望が溜まっている。areka が次に何を作るかを考える開発者と、起票や棚卸を手伝うエージェントにとって価値の高い材料だが、いまは誰も通読しておらず、areka の側に写しも索引も無い。要望は 1 件ずつ頁を開かないと中身が分からず、「SSP では実装済み」「却下された」「未対応のまま」の区別も、areka の既存の spec・裁定との重なりやぶつかりも、照らし合わせないと分からない。起票時（2026-10-10）の実測では全 808 件、うち深刻度「要望」が 187 件、それ以外が 621 件で、深刻度の欄は当てにならない（要望でない深刻度で出されていても中身は要望や質問のものが混じる）。この spec は 1 回きりの調査として、エージェントが一覧を全件通読し、要望 187 件のすべてと、それ以外から「中身が要望・質問のもの」「仕様どおりなどで閉じられ、正典（ukadoc）が黙っている挙動を作者が説明していそうなもの」だけを拾って中身を読み、areka の目線で整理した台帳を spec のフォルダの `bts-ledger.md` に書く。各行から SSP 側の結末と areka との関係（実装済み・brief あり・未着手・方針とぶつかる・対象外）が分かり、先頭にいつ・どこまで見たかがあり、末尾に起票の候補の短い一覧がある。完了すると spec ごと `.kiro/specs/completed/` へ移り、steering の `structure.md` には完了後のパスで在りかを 1〜2 行だけ書く。取得や分類の道具は作らず、コードには触らず、起票そのものもしない。BTS は閲覧だけで、頁は 1 つずつ順に開く。

## Introduction

SSP の課題管理（以下 BTS・https://bts.shillest.net/ ）は、SSP の作者が運営する外部のサーバーで、匿名で閲覧できる。起票時（2026-10-10）の実測では、解決済みを含めて全 808 件（最新の番号は 0000808）、うち深刻度「要望」が 187 件、それ以外（マイナー・メジャー・クラッシュ・表示・微調整など）が 621 件あった。一覧は 1 頁 50 件で、各課題の頁では深刻度・ステータス・解決状況・修正済バージョン・説明・コメントが読める。

areka の側には、正典（ukadoc）の拾い残しを追う一式（`doc/ukadoc-coverage/`＝台帳 `ledger/*.toml` と報告 `report/`）と、SSP の MCP を調べた文書（`doc/ssp-mcp/survey.md`）がある。BTS を扱った文書は無い（steering の `structure.md` にも BTS の記述は無い）。

本 spec は、BTS の要望を 1 回だけ通読し、areka の目線で整理した台帳を作る調査である。足すのは文書だけで、コードも道具も足さない。台帳は本 spec のフォルダに置き、完了のときに spec ごと `.kiro/specs/completed/areka-P0-ssp-bts-salvage/` へ移る。そこが最終の置き場になる（完了済みの spec に調査の記録を残す先例は `completed/areka-P0-ghost-session-test-load-flake` の `load-repro.md`）。

本要件は、台帳に何が書いてあり、どこにあり、調査が何を守るかを定める。主題の分け方の中身・欄の並べ方・読む順番の区切り方は設計で決める。

## Boundary Context

- **In scope**:
  - BTS の一覧の全件の通読と、中身を読む課題のふるい分け。
  - 対象の課題の頁の読み込みと、台帳（本 spec のフォルダの `bts-ledger.md`）の作成。
  - areka の既存の spec・裁定・ukadoc の網羅の台帳との照らし合わせ。
  - 台帳の末尾の、起票の候補の一覧。
  - `.kiro/steering/structure.md` への在りかの案内（完了後のパスで 1〜2 行）。
- **Out of scope**:
  - 起票（brief を作ること・`roadmap.md` に行を足すこと）。候補を挙げるところまでで、起票は開発者が `/kiro-discovery` で行う。
  - コードの変更と、取得・分類・更新を自動で行う道具（スクリプト・クレート）の追加。
  - 定期的に見直す仕組みと、完了の後の続きの拾い直しそのもの。
  - SSP を動かして挙動を確かめること。
  - BTS への書き込み（ログイン・コメント・課題の登録）。
  - ukadoc の網羅の台帳（`doc/ukadoc-coverage/`）の書き替え。
  - SSP の実装の不具合（areka の不具合ではないもの）の読み込み。
  - SHIORI（里々・YAYA など）とゴースト個別の課題の精査。
- **Adjacent expectations**:
  - BTS は閲覧だけで使う外部のサーバーで、本 spec は BTS の側に何も求めない。
  - `areka-P0-coverage-roadmap-refresh`（ukadoc の網羅の台帳と roadmap の突き合わせ）とは扱う相手が違う。本 spec は BTS だけを扱い、ukadoc の網羅の台帳と重なる行には参照を書くだけにする。
  - 台帳を使うのは、開発者の `/kiro-discovery`（台帳から選んで起票する）と、棚卸で起票の材料を探すときである。本 spec はその材料を置くところまでを受け持つ。
  - 完了の手順の参照パスの修正は、spec の文書とソース（`crates`）だけを探し、steering は探さない。`structure.md` の案内のパスが移動後の台帳を指していることは、本 spec の側（タスクと、完了への申し送り）で確かめる。
  - 同じウェーブで並走する spec とは、steering の `structure.md` への 1〜2 行のほかにファイルが重ならない。

## Requirements

### Requirement 1: 一覧の通読とふるい分け

**Objective:** As a 開発者, I want BTS の一覧が全件読まれ、中身を読む課題が決まった決まりで選ばれていること, so that 台帳に載らなかった課題が「見落とし」でなく「決まりで外したもの」だと分かる

#### Acceptance Criteria

1. The 本 spec の調査 shall BTS の一覧を、解決済みの課題も含めて、最初の番号から通読を始めた時点の最新の番号まで全件読み、課題ごとに番号・要約・カテゴリ・深刻度・ステータス・解決状況を取る（解決状況が一覧の画面の列に無いときは、CSV や一覧の絞り込みなど、課題の頁を開かない手段で取る）。
2. When 一覧を読み終えたとき, the 本 spec の調査 shall 一覧の総数・深刻度「要望」の件数・最新の番号を数え、起票時の実測（全 808 件・要望 187 件・最新 0000808）と違えば、その差を台帳の先頭に書く。
3. The 本 spec の調査 shall 深刻度「要望」の課題をすべて、台帳の行にする対象とする。
4. The 本 spec の調査 shall 深刻度が「要望」でない課題のうち、一覧の要約と解決状況から次のどちらかに当たると読めるものだけを、対象に加える: ⑴ 中身が要望・質問であるもの ⑵「仕様どおり」「修正不要」に当たる結末で閉じられていて、ukadoc が定めていない挙動を SSP の作者が言葉で説明していそうなもの。
5. The 本 spec の調査 shall 対象に入らなかった課題（SSP の実装の不具合）の頁を開かず、台帳の行にもしない。
6. While 調査の途中で BTS に新しい課題が増えた, the 本 spec の調査 shall 通読を始めた時点の最新の番号までを範囲とし、それより後の番号を台帳に加えない。
7. The 本 spec の調査 shall 修正済バージョンを、対象の課題についてだけ取る（一覧の取得で得られなければ、対象の課題の頁から取る）。対象に入らなかった課題の修正済バージョンは取らない。

### Requirement 2: 対象の課題の読み込み

**Objective:** As a 開発者, I want 対象の課題が、題だけでなく説明とコメントまで読まれていること, so that SSP 側の結末と要望の中身を、頁を開き直さずに台帳から知ることができる

#### Acceptance Criteria

1. The 本 spec の調査 shall 対象の課題（次の項の課題を除く）について、課題の頁を開いて説明とコメントを読み、要望の中身と SSP 側の結末を確かめてから台帳の行を書く。
2. Where 対象の課題が SHIORI（里々・YAYA など）またはゴースト個別のものである, the 本 spec の調査 shall 課題の頁を開かず、一覧の情報だけで行を書き、areka との関係を「対象外」とする。
3. If 対象の課題の頁が読めない（閲覧が許されていない・取得に失敗した）, the 本 spec の調査 shall その行に、頁を読めなかったことと理由を書き、一覧の情報だけで書いた行であることが分かるようにする。
4. When 深刻度が「要望」でない対象の課題を読んで、要望・質問でも ukadoc が定めていない挙動の説明でもないと分かったとき, the 本 spec の調査 shall その課題を台帳の行から外し、「読んだが外した」件数に数える。

### Requirement 3: 台帳の行と主題

**Objective:** As a エージェントと開発者, I want 台帳が主題ごとにまとまり、どの行も同じ欄で書かれていること, so that 主題から要望を引き、SSP 側の結末と areka との関係を行ごとに読み取れる

#### Acceptance Criteria

1. The 台帳 shall 対象の課題 1 件につき 1 行を持ち、各行に BTS の番号（`BTS 0000709` の形）・要約（題）・SSP 側の結末・種別・areka との関係・ひと言（自分の言葉で 1〜2 文にまとめた中身）を書く。
2. The 台帳 shall 各行から BTS の課題の頁へ辿れるようにする（行に URL を書くか、番号から URL を作る決まりを先頭に書く）。
3. The 台帳 shall SSP 側の結末を、先頭で定めた語彙のどれか 1 つで書く。語彙は少なくとも「実装済み」「未対応」「却下」を区別し、実装済みで修正済バージョンが分かるものにはその版を添える。
4. The 台帳 shall 種別を、先頭で定めた語彙のどれか 1 つで書く。語彙は少なくとも「要望」「質問」「ukadoc が定めていない挙動の説明」を区別する。
5. The 台帳 shall areka との関係を、「実装済み」「brief あり」「未着手」「方針とぶつかる」「対象外」の 5 つのどれか 1 つで書く。
6. The 台帳 shall 行を主題ごとにまとめ、主題の一覧を先頭に置き、どの行もちょうど 1 つの主題に入れる。
7. The 台帳 shall 日本語で書き、英語で出された課題もひと言は日本語で書く。
8. The 台帳 shall 設定や機能の名前を ukadoc の用語で書き、areka の spec は名前で指す。
9. The 台帳 shall 課題の説明やコメントを丸写しにせず、番号・要約（題）・URL のほかは、自分の言葉でまとめた中身だけを載せる。

### Requirement 4: areka との照らし合わせ

**Objective:** As a 開発者, I want 各行の「areka との関係」が、今ある文書と裁定に照らして決められ、根拠が行から辿れること, so that 重なる spec や、ぶつかる方針を、照らし合わせをやり直さずに確かめられる

#### Acceptance Criteria

1. The 本 spec の調査 shall areka との関係を、ukadoc の網羅の台帳（`doc/ukadoc-coverage/`）・`.kiro/steering/roadmap.md`・`.kiro/specs/`（完了分を含む）・開発者の裁定（steering と spec の文書・`doc/COMPAT_ARCHITECTURE.md` の「沈黙ルール対応表」、およびエージェントの記憶に残るもの）に照らして決める。
2. When areka との関係を「実装済み」または「brief あり」と書くとき, the 台帳 shall その行に、根拠となる spec の名前、または ukadoc の網羅の台帳の項目を書く。
3. When areka との関係を「方針とぶつかる」と書くとき, the 台帳 shall その行に、ぶつかる方針または裁定が何かを書く。
4. When areka との関係を「対象外」と書くとき, the 台帳 shall その行に、対象外とした理由を書く。
5. The 本 spec の調査 shall 行に書く spec の名前と文書のパスが実在することを、実物のファイルで確かめてから書く。
6. If 照らし合わせた資料からは関係を 1 つに決めきれない, the 本 spec の調査 shall その行を「未着手」とし、何が決めきれなかったかをひと言に書く。
7. The 本 spec の調査 shall ukadoc の網羅の台帳を書き替えず、重なりを見つけたときは本 spec の台帳の行に参照を書くだけにする。

### Requirement 5: 起票の候補の一覧

**Objective:** As a 開発者, I want 台帳の末尾に、起票してよさそうな要望だけが短くまとまっていること, so that 台帳の全行を読まずに、次に起票するものを選べる

#### Acceptance Criteria

1. The 台帳 shall 末尾に起票の候補の一覧を持ち、次の 3 つをすべて満たす課題だけを挙げる: ⑴ areka との関係が「未着手」である ⑵ areka の方針とぶつからない ⑶ デスクトップマスコットの枠に収まる。
2. The 起票の候補の一覧 shall 候補ごとに、もとになった BTS の番号（同じ話の課題はまとめてよい）と、何を作る話かを 1〜2 行で書く。
3. Where 候補のもとになった行が、areka との関係を決めきれずに「未着手」としたものである, the 起票の候補の一覧 shall 決めきれなかった点をその候補に添える。
4. If 3 つの条件を満たす課題が 1 件も無い, the 台帳 shall 起票の候補が 0 件であることを末尾に明記する。
5. The 本 spec の調査 shall 起票（brief を作ること・`roadmap.md` に行を足すこと）を行わない。

### Requirement 6: 置き場と steering の案内

**Objective:** As a 開発者, I want 台帳がふだんは目に付かない場所にあり、要るときだけ steering の 1〜2 行から辿れること, so that ふだんの spec 作業の邪魔をせず、「BTS の台帳を見て」と頼めばエージェントが台帳へ辿り着ける

#### Acceptance Criteria

1. The 台帳 shall 本 spec のフォルダの `bts-ledger.md` の 1 ファイルに置き、`doc/` の下には置かない。
2. The `.kiro/steering/structure.md` shall 台帳の在りかと使いどころ（SSP の BTS の要望を調べるときに読む）を 1〜2 行で書き、在りかは完了後のパス `.kiro/specs/completed/areka-P0-ssp-bts-salvage/bts-ledger.md` で書く。
3. The steering shall 台帳の中身（行・主題・起票の候補）を写さず、在りかと使いどころだけを持つ。
4. When 本 spec が完了して spec のフォルダが `completed/` へ移ったとき, the `structure.md` の案内のパス shall 実在する台帳を指す。
5. The 本 spec の変更 shall main に入る時点で、`structure.md` の案内が指す先に台帳が無い状態を残さない。

### Requirement 7: 見た範囲の記録と、続きの扱い

**Objective:** As a 開発者とエージェント, I want 台帳の先頭に、いつ・どこまで・どういう決まりで見たかが書いてあること, so that 台帳の古さを判断でき、後で続きの番号から同じ決まりで拾い直せる

#### Acceptance Criteria

1. The 台帳 shall 先頭に、通読した日付・通読を始めた時点の最新の番号・一覧の総数を書く。
2. The 台帳 shall 先頭に、件数の内訳（深刻度「要望」から行にした件数・それ以外の深刻度から行にした件数・読んだが外した件数・対象に入らなかった件数）を書き、内訳の合計が一覧の総数に一致するようにする。件数が 0 の項目も 0 と書く。
3. The 台帳 shall 先頭に、読み方（各欄の意味と語彙）と採り方（ふるい分けの決まりと、読まなかった課題の種類）を書く。
4. The 台帳 shall 先頭に、本 spec が 1 回きりの調査であり、定期的に見直す仕組みを持たないことを書く。
5. The 台帳 shall 先頭に、続きを拾い直すときの決まりを書く: 続きは新しい spec として起票し、先頭に書いた最新の番号の次から同じ決まりで拾い、行は新しい台帳を作らずこの台帳に書き足して、先頭の見た範囲（日付・最新の番号・件数の内訳・照らし合わせた時点）を更新する。
6. The 台帳 shall 先頭に、areka の側の文書（`roadmap.md`・spec・ukadoc の網羅の台帳）をどの時点で照らし合わせたか（日付と、もとにした main のコミット）を書く。

### Requirement 8: 相手のサーバーへの配慮と、足すものの限り

**Objective:** As a 開発者, I want 調査が、SSP の作者のサーバーに負担と迷惑をかけず、areka のリポジトリには文書だけを足すこと, so that 外部の運営者との関係を損なわず、並走する他の spec の邪魔もしない

#### Acceptance Criteria

1. The 本 spec の調査 shall BTS を閲覧だけで使い、ログイン・コメント・課題の登録を行わない。一覧の表示の切り替え（解決済みの課題も表示する・表示件数・絞り込み）は閲覧に含める。
2. The 本 spec の調査 shall BTS の頁を 1 つずつ順に開き、同時に複数の取得を投げない（読み手を複数に分けて並べて読ませることを含む）。
3. The 本 spec の調査 shall 一覧を CSV の 1 回の取得で読むことを本線とし（2026-10-10 開発者の了承）、実際に取得する直前に、ファイルの名前・取得元・大きさを開発者へ伝えて確かめる。取得したファイルはワークツリーの `target\` の下に置き、コミットしない。
4. If 取得の直前の確かめで開発者が断った、CSV が匿名の閲覧では取得できない、または CSV に解決状況が入っていない, the 本 spec の調査 shall 一覧を頁で順にめくって読む。
5. If BTS が応答しない、または取得を拒む, the 本 spec の調査 shall 間を置かずに取得を繰り返さず、どこまで読めたかを記録して止め、開発者へ報告する。応答しないときに限り、60 秒以上あけて同じ頁を 1 回だけ取り直してよく、それでも応答しなければ止める（2026-10-10 開発者の了承）。取得を拒まれたときは取り直さない。
6. The 本 spec の調査 shall SSP を動かして挙動を確かめない。
7. The 本 spec の変更 shall 本 spec のフォルダの文書と、`.kiro/steering/structure.md` の 1〜2 行だけを足し、コードと、取得・分類・更新のための道具を足さない（完了の手順が定型で行う `roadmap.md`・`focus.md`・`spec.json` の更新は、ここでいう「足すもの」に数えない）。
