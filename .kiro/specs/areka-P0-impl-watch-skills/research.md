### 2.1 ソースや手順書と要件の食い違い（具体的に）

1. **`resume` の `already running`**（要件 3.7）: 見張りが `already stopped; …` で終わったとき、すでに再開の待ち（`stopped --wait` か `resume`）が走っていれば、要件どおり `resume` を呼ぶと `a resume wait for <識別> is already running` で 1 になる（`cli.rs:626-629`・`doc/impl-watch.md:267`）。要件 6.4 の「上の 3 つ以外の 1」に落ちるが、害の無い 1 であり、手順書 5 節の表にも行が無い。
2. **2 本目の `stopped --wait`**: 完了した spec の実走（`completed/areka-P0-impl-watch/tasks.md:316`）で、再開の待ちが走っている間の 2 本目の `stopped --wait` は 1 になり、何も記録しないと分かっている。要件 3.6 は前の待ちが終わった後に呼ぶので当たらないが、要件 3.3（作業していないときの停止要請）で、前の `stopped --wait` が残っていると当たりうる。
3. **手順書 5 節の終了コード 1 の表**（`doc/impl-watch.md:285-294`）: 見張りの `already running` の 1 行だけで、`merge`・`load`・`resume` の種類の行が無い。要件 9.3（スキルと食い違わない）を満たすには足すことになる。
4. **`merge --wait` の 3**: 手順書 5 節は「申し込みが消えた。`status` で訳を見て、`watch` を立ててから申し込み直す」（`doc/impl-watch.md:274`）。要件 5 は、机を持っている間の見張りの 3（5.8）と `merged` の 3（5.7）だけを書き、並んでいる間の `merge --wait` の 3 と、自分で `cancel`（5.6）した後の 3 を書いていない。要件 10.2 は `status` をふだん読まないので、手順書の「`status` で訳を見る」とも食い違う。

## 3. 作り方の案

どの案でも、アプリのソースと `Cargo.lock` には触らない（要件 11.4）。

### 案 A: 今のファイルを書き替えるだけ（スキルの文に机の段を全部書く）

- 書き替え: `kiro-impl/SKILL.md` の 1 節・`kiro-complete/SKILL.md` の前置きステップとチェックリスト・`kiro-watch-clear/SKILL.md` の説明と案内・手順書の 1〜5 節と 7 節。

- 削除: `.claude/skills/kiro-watch/` の 3 ファイル。
- 良い所: ファイルが少ない。スキルを読めば全部分かる。
- 悪い所: 識別・リポジトリの求め方、環境変数と実行ファイルの確かめ、終了コードごとの扱いが 2 つのスキルに重なって載る。片方だけ直して食い違うおそれ（要件 1.2）。スキルは会話に読み込まれるので、文が長いほどトークンが増える。

### 案 B: 机の段を 1 か所にまとめる（共有の文か、小さな包みのスクリプト）

- 共有の文: 机の段の約束（識別の求め方・立てる時機・終了コードごとの扱いの表）を 1 つの参照ファイルに置き、2 つのスキルはそこを読む。手順書 4 節をその正本にする手もあるが、手順書は 400 行あり、全部を読むとトークンが重い。
- 包みのスクリプト: 「環境変数の確かめ → 実行ファイルの確かめ → 識別とリポジトリを求める → コマンドを呼ぶ」を 1 本の Bash か pwsh にまとめ、`skip: no-home`・`skip: no-exe` のような短い 1 行と、アプリの終了コードをそのまま返す。スキルの文は「何をいつ呼び、どの終わり方で何をするか」だけになる。
- 良い所: 求め方が 1 か所で、要件 1.2 を構造で守れる。確かめ（要件 11.3）でコマンドの並びをそのまま流せる。
- 悪い所: ファイルが増える。包みのスクリプトは環境変数を書き替えない・`cd` しない（要件 6.5）を自分でも守る必要があり、確かめの対象も増える。スクリプトが標準エラーを混ぜる・混ぜないで、スキルが読む文の形が変わる。

### 案 C: 両方を少しずつ（スキルの文は短く、求め方だけを共有）

- スキルには、時機と終了コードごとの扱いだけを短い表で書く（それぞれのスキルで要る行だけ）。
- 識別・リポジトリ・環境変数・実行ファイルの確かめは、4〜5 行の決まった Bash の断片として、2 つのスキルに同じ字で書く（`kiro-watch-clear` の判定の形を流用）。字が同じであることは確かめで見る。
- 置き方は `tools/` の pwsh 1 本。手順書 2 節・3 節と `kiro-watch-clear`・2 つのスキルの「実行ファイルが無い」の案内は、どれもこの 1 本を指す（要件 7.9）。
- 良い所: 新しいファイルは道具の 1 本だけ。スキルの文は案 A より短い。
- 悪い所: 断片の重なりは残る（短いので食い違いは見つけやすい）。

## 4. 手間と危うさ

- **手間: S（1〜3 日）**。Rust のコードは書かない。書き替えはスキル 3 つ・手順書 1 つ、新しく道具 1 本、削除 3 ファイル。タスクの数は roadmap の見立て（8〜12）に収まる。

## 5. 設計で調べること

1. **バックグラウンドの実行の寿命**: Bash のバックグラウンドで立てた見張り・待ちが、ターンの終わり・会話の圧縮・`/clear`・アプリの立ち上げ直しの後にどうなるか。終わりの知らせが圧縮の後にも届くか。手順書 6 節（`doc/impl-watch.md:339-341`）は「アプリを閉じても残ることがある」と書く。
2. **標準エラーの読み方**: バックグラウンドの実行の出力に標準エラーが入るか。入らないなら、`already running`・`gone:` の文を読むために `2>&1` を付ける形にする（要件 2.6〜2.8 は標準エラーの文で分岐する）。
3. **走っている実行ファイルの改名と削除**: Windows で、待ち・見張りが走らせている `areka-impl-watch.exe` を改名でき、新しいものを同じ名前で置け、古いものは走っている間は消せないこと（要件 11.2 の 4 つの場合で記録する）。
4. **サブエージェントを走らせている間の知らせ**: 実装係が走っている間に見張りが終わったとき、主の会話がその知らせをいつ受けるか（実装係の終わりの後か）。要件 3.1 の「コミットまで進めてから止まる」の書き方に関わる。

## 6. 設計で決めること（要件の討議へ渡す）

1. **置き方の手順の形**: `tools/` の pwsh 1 本にするか（前例どおり）、スキルにするか。名前。全体テストに自分の検査を入れるか。
2. **入れ替えの順と古い実行ファイルの名前**: いつも同じ道（一時の名前 → 改名 → 改名 → 消してみる）にするか、手順書 3 節の 2 通りを残すか。古いものは `.old.exe` の 1 つか、時刻つきで何本でもか（1 つだと、前の古いものが走っている間は入れ替えられない）。手順書 7 節の表も合わせる。
3. **机の段の文の置き場**: 2 つのスキルに全部書く（案 A）／1 か所の共有の文か包みのスクリプト（案 B）／短い決まった断片を同じ字で 2 つに書く（案 C）。
4. **「このセッションが立てた見張り」の見分け方**（要件 2.2・2.3・2.7・2.8）: 会話の中で覚えた実行の番号に頼るか。会話の圧縮やセッションの入れ替えで覚えが消えたときは、要件 2.8（`leave` してから立て直す）に倒すのか。そのとき、まだ生きている前のセッションの見張りを外してしまう恐れをどう扱うか。
5. **同じ作業木で 2 つのセッションが動いたとき**（要件 1.1・1.2）: 識別が同じになり、片方の `leave` と立て直しで、もう片方の見張りが 3 で終わり、また立て直す、の往復になりうる。「1 つの作業木で机を使うセッションは 1 つ」と書くだけにするか。
6. **見張りの 1 の立て直しの上限**（要件 2.6 と 6.4 の境）: `state.lock is busy`・`state file version mismatch`・`state file is broken` のように、立て直しても同じ 1 で終わる失敗で、立て直しが止まらなくならないようにする。1 回だけ立て直し、2 度目の 1 は要件 6.4 に倒す、などの線。
7. **負荷テストの段を含むタスクの見分け方**（要件 4.1 と 1.6）: 計測は実装係が行うのに、机を呼ぶのは主の会話だけ。(a) 主の会話がタスクの文（`tasks.md` の記述）を読んで前もって申し込む／(b) 実装係が「机が要る」と返したら主の会話が申し込み、番が来てから任せ直す／(c) 机の要る段だけは主の会話が自分で走らせる。`kiro-spec-tasks` に印を足すのは、この spec の範囲の外。
8. **要件に無い終わり方の扱い**: (a) 再開の待ちが走っている間の `resume`・`stopped --wait` の `already running`（種類は `resume`）を害の無いものとみなすか（2.1 の 1・2）。(b) 並んでいる間に `merge --wait`・`loadtest --wait` が 3 で終わったとき（自分の `cancel` の後なら何もしない・それ以外は見張りを立ててから申し込み直す、など）。要件 10.2 で `status` をふだん読まないことと、手順書 5 節の「`status` で訳を見る」（`doc/impl-watch.md:274`）をどう合わせるか。
9. **マージ後のコミットの取り方**（要件 5.5）: `gh pr view <番号> --json mergeCommit` の値か、`git fetch` の後の既定の枝の先頭か。どちらも `--sha` の形（16 進 7〜40 字）に合う。
10. **バグの印の読み方**（要件 5.2）: brief の区分の書き方が spec ごとに揺れている（「優先度の区分: B」「優先度の区分**: B（…」「区分 B」、再測定の追記で区分が書き直されることもある）。brief の最後の区分の行を読むか、roadmap の区分の列を読むか。
11. **置き方の手順の確かめに使うコマンド**（要件 7.1）: `--help`（置き場所に触らない）か `status`（置き場所が使えることまで見る）。
12. **`kiro-next` の「静かな机」の文**（`.claude/skills/kiro-next/SKILL.md:36`・`:114`）: 調停役の名前は出ないが、メッセージで止まって「停止しました」と返す形のまま残る。`kiro-next` は範囲の外と要件にあるので、このまま残すか、要件 8.3 に照らして一言だけ直すか。
13. **手順書 5 節の終了コード 1 の表に足す行**（要件 9.3・6.4）: `a resume|merge|load wait for <識別> is already running` の行と、そのときスキルがすること。
14. **過去の記録の扱いの線**（要件 8.4）: 生成済みの俯瞰の HTML（`doc/roadmap-overview-2026-10-16.html`）と見本 `tools/release-notes-fixture/subjects.txt:10` に `kiro-watch` の字が残る。どちらも過去の記録・見本として書き替えない側に数えるか。

15. **番が来たときの既定の枝の取り込み**（要件 5.4・2.1 の 8）: `kiro-complete` のステップ0 の `sync_with_base_branch` は、資格情報つきの URL のために断られる。机の段の取り込みを `git fetch` と `git merge` にするか。

17. **`clear --repo` の形**（要件 12・`areka-P0-impl-watch-residue` の要件 11・あちらの `b6521f86`、10-16 に知らせを受けた）:

### 8.3 総合（一般化・作るか使うか・簡素にする）
- **一般化**: 2 つのスキルの机の段は「前置き → 呼ぶ形 → 終わり方の表 → スキルごとの時機」の 4 つに分かれ、前の 3 つは共通。共通の部分を 1 つの約束として設計に置き、スキルごとの差は時機の表だけにした。
- **作るか使うか**: `cargo install --root` は `bin\` の下へ置き、走っている実行ファイルを置き換えられないので採らない。置き方は pwsh の道具を作る。バックグラウンドの待ちは Claude Code の Bash のバックグラウンド実行をそのまま使う。
- **簡素にする**: 包みのスクリプト（案 B）は作らない（ファイルと確かめの対象が増え、環境変数を書き替えない決まりを自分でも守る必要が出る）。道具の `-SelfTest`、テンプレートの書き替え、`workflow.md` の 1 節、`/release` の参加は足さない。

### 8.4 危うさ
- Claude Code のバックグラウンド実行の終わりの知らせが、会話の圧縮・サブエージェントの実行中にいつ届くか（設計は届く時機が遅れても壊れない形にした。本物のセッションでの届き方は最初の実運用で見る）。
- 前もって見分けられない負荷テストの段は、実装係の返しに頼る。
- 手順書 6 節の一文の削除は、`areka-P0-impl-watch-residue` が窓を閉じることに頼る。
