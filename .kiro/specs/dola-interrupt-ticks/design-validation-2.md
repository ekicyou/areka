理由: dola の側（型・丸め・倍率の写し・時刻の表・再生機・知らせの形・終わりの予定の時刻・コンパイルの結果）と、依存の辺と段取りは、今のコードと突き合わせて破れなかった。1 回目の重大 3 件と、そのほかの 18 件は、どれも設計に入っている。残るのは、受け手の側の決まり（`areka_sakura::held` の列と、その使い方）の 2 つである。1 つは本番で起きる（文字の層の列とバルーンの寿命の列が、別の線で別の時に物を受けるので、起点の替わるフレームがずれる）。もう 1 つは、この spec が固めると言う「知らせの受け方」の決まりが、受け付けると書いた呼び出しの列で破れる（最初の起点の知らせ）。どちらも、直す所は列の決まりと `areka-runtime` の後半の 1 家族の中で、dola の口の形・crate の分け方・段の並びは動かない。ただし、後半のタスクが実装する中身（どの線で何を運ぶか・列の決まり）が変わるので、タスクを切る前に設計へ入れる。

## 重大な指摘（2 件）

### 重大 1: 文字の層の列とバルーンの寿命の列は、同じフレームで同じ起点を持つとは限らない

**設計の所**: 「areka-runtime」の「フレームの台本の時刻」（「2 つの列は同じ起点を持つので、同じ値である」）と「バルーンの寿命」（「同じ知らせを同じ順に受け、同じフレームの時刻で進むので、同じ起点を持つ」）・D13・Requirements Traceability の 12.8。

**コードの事実**: 2 つの受け口は別の線で送る。文字の層は UI のスレッドのメッセージの線で（`crates/areka-emo-text/src/actor.rs:676`・`crates/areka-actor/src/ui.rs:90`）、フレームの外で受け取る。バルーンの寿命は `std::sync::mpsc` で（`crates/areka-runtime/src/talk_lifecycle.rs:40`・`:203-213`）、可視性の相がフレームの中で取り出す（`crates/areka-runtime/src/balloon_visibility_phase.rs:96`）。フレームの時刻は、進める回の頭で読む（`crates/wintf/src/ecs/world/mod.rs:561`）。今は、2 つの相が同じ 1 つの `TalkClock` を読むので、台本の時刻はいつも同じである（`balloon_visibility_phase.rs:92`・`frame/scale_text.rs:230`）。

**起きる列**:

1. 刻み役が時刻 O2 を読み、刻みを送る。
2. UI のスレッドで、フレーム k が始まる（フレームの時刻 H は O2 以上）。
3. トークのスレッドが、次の台詞の再生機を作り、受け口を登録する。文字の層の受け口は最初の起点の知らせを UI の線へ送り、寿命の受け口は同じ知らせを mpsc へ送る。
4. フレーム k の可視性の相が mpsc を取り出す。寿命の列は、効く時刻 O2 が H 以下なので、このフレームで起点を O2 に替える。文字の層の列は、同じ知らせをまだ受け取っていない（UI の線は、フレーム k の後に読まれる）。
5. フレーム k では、寿命の時計の台本の時刻は「H − O2」（0 に近い）、文字の層は前の台詞の起点のままである。可視性の相が、今の読み方（`balloon_visibility_phase.rs:311`）のまま、自分の台本の時刻で文字の層の字の数を読むと、前の台詞の字が全部出ているのに、「現れた字は 0 に近い」と読む。

受け口の登録の順と UI のスレッドの巡りによっては、逆（文字の層が先に替わる）も起きる。どちらも、台詞の始まりごとに、フレームの頭から可視性の相までの間に登録が当たった時に起きる。

**なぜ重いか**: 要件 12 の 8（寿命の時計は、文字の層の時計と同じ台本の時刻を読む）が、設計の言う理由では成り立たない。D13 は「起点を列の外に別に持つと、起点だけが先に替わり、食い違う」と言って起点を列に入れたが、同じ事が 2 本の列の間で起きる。フレームが見せる物（バルーンを出すか・隠すか）が、知らせの届いた時で変わるので、Goals の「フレームが見せる物を、台本と、起点の知らせの列と、フレームの時刻だけで決める」にも当たる。今のコードには無い食い違いである。

**直し方の案**: 起点を持つ所を 1 つにする。

- 案 1（勧める）: バルーンの寿命の時計を、seriko と同じ「絶対の時刻で持つ受け手」にする。寿命の知らせは、合図の発火時刻から作った絶対の時刻（表示の終わりは `fire_time + duration`）で運び、期限も絶対の時刻で持ち、フレームの時刻と直に比べる。置き直しの知らせは、seriko の決まり（効く時刻より後の時刻だけを、動いた長さだけ動かす）で当てる。寿命の列は起点を持たない。可視性の相が字の数を読む時の台本の時刻は、文字の層の `advance` が返した値を使う。「2 つの持ち方は、同じ時刻を指す」の節の理由が、そのまま使える。
- 案 2: 寿命の知らせを、文字の層と同じ線で運び、同じ 1 本の列に並べる（`advance` が出した寿命の知らせを、可視性の相へ渡す）。`areka-emo-text` が、寿命の知らせを運ぶ口を持つ事になる。

どちらでも、テスト（「受け手の追従」）に「片方の線だけが先に届いたフレームで、2 つの相の読む台本の時刻が同じ」を足す。

**要件**: 12.8・12.10・18.1

### 重大 2: 最初の起点の知らせの決まりが、2 つの列で破れる

**設計の所**: 「`TimedSchedule`」の `OriginNotice::first`（効く時刻は起点）・「知らせの受け方」（「列が待つのは、頭の物だけである」「前の再生と、次の再生の間」「2 つの持ち方は、同じ時刻を指す」）・「areka-talk・areka-sakura」の `HeldQueue::pop_due`・「areka-seriko」の「知らせ」。Revalidation Triggers は、知らせの受け方の決まりを「変える時は確かめ直す」に挙げている（この spec が固める所である）。

**(a) 起点が来る前の置き直しで、列の頭が詰まる**。置き直しの知らせの効く時刻は、呼び手の現在の時刻である。最初の起点の知らせの効く時刻は、起点である。だから、届いた順と、効く時刻の順が合わない列が作れる。

1. 起点 O が先の時刻（今 + 10 秒）の台本から再生機を作り、受け口を登録する（要件 18 の 4 の形）。文字の層の列に「最初の起点（効く時刻 O）」が入る。
2. 1 秒後（now1）に `reanchor(now1, now1, 0)` を呼ぶ（設計は「最初の刻みの前でも、置き直しは受け付ける」と書く。「使い手の居ない口の確かめ」の早送りの形）。知らせ（効く時刻 now1・新しい起点 now1・前の起点 O）が列の後ろに入る。
3. `tick(now1)` で、台本の時刻 0 の合図が、発火時刻 now1 で配られる。
4. seriko は、届いた時に、発火時刻 now1 で当てる。文字の層の列は、頭の「最初の起点」の効く時刻 O が来ていないので、後ろの知らせも合図も出さない。9 秒の間、文字の層とバルーンの寿命は前の姿のままで、O が来たフレームで、溜まった物が一度に当たる。

設計は、同じ形の別の列（起点が来る前に台本を捨てて、次の台本を始める）を「この spec に無い使い方」として、後の spec に列の口を足させると書く。しかし、起点が先の時刻の台本は、大前提の使い方そのもの（同じ起点を複数の受け手へ配る）で、要件 11 の 3・11 の 8・18 の 4 が受け付ける。その列で、受け手ごとに姿が分かれる（要件 12 の 4・18 の 1）。

**(b) 次の再生の最初の起点で、前の再生の残りの字の扱いが、2 つの持ち方で違う**。文字の層は、字の現れる時刻を台本の時刻で持つので、次の再生の起点に替わると、前の再生のまだ現れていない字は「新しい起点 + 元の台本の時刻」に現れる（設計もそう書く）。seriko は、最初の起点の知らせでは何も動かさないので、同じ字は「前の起点 + 元の台本の時刻」のままである。

- 設計は「残るのは、内容の無い台本が続いた時だけ」と書くが、合図の無い台本は再生機を作らず、知らせも出ない（`crates/areka-sakura/src/drive.rs:259-263`）。残るのは、後始末の合図だけの台本である。後始末は、コンパイルの後に足すので、頭の全部の消去が付かない（`crates/areka-sakura/src/compile.rs:446-452`・`drive.rs:253-256`）。
- 列: 台詞 1（起点 O1）が、40 字・2 秒の塊を配った後、0.5 秒で中断される。0.6 秒の時刻（O2）に、後始末だけの台詞 2 が始まる。文字の層は、14 字目（台本の時刻 0.65 秒）を O2 + 0.65 秒 = O1 + 1.25 秒に現す。seriko の口パクは、同じ字を O1 + 0.65 秒に数える。字と口が 0.6 秒ずれる。今のコードは、文字の層も seriko も、同じ形の見積もりで起点を替えるので、字と口は一緒に動く。

**なぜ重いか**: 「2 つの持ち方は、同じ時刻を指す」「届き方に依らない」は、再生の途中の置き直しについては成り立つ（下の「確かめて成り立った事」）。最初の起点の知らせについては、成り立たない。知らせの形（`OriginNotice`）は変えずに済むが、受け方の決まりは、この spec が固める物である。

**直し方の案**:

- (a): 列の決まりに 1 つ足す。「時刻の来た知らせより前に届いた物は、自分の時刻に依らず、その知らせより先に、届いた順に当てる」（後から出た知らせが効く時には、前に届いた物は済んでいる）。こうすると、起点が来る前の置き直しでも、起点が来る前に捨てた台本でも、頭で詰まらない。後の spec に列の口を足させる必要も無くなる。テスト（「届いた物を持つ列」）に、この 2 つの列を足す。
- (b): 最初の起点の知らせ（前の起点が無い＝新しい再生）での、前の再生の残りの字の決まりを、2 つの持ち方で同じに書く。勧める形は、絶対の時刻を保つ事である。文字の層は、知らせが当たる時に、まだ現れていない字の現れる時刻から「新しい起点 − 前の起点」を引く（効く時刻までに現れる字は、`before` で確かめてあるので、引いた値は負にならない）。seriko は今の決まりのままで合う。「前の再生と、次の再生の間」の括弧の中（内容の無い台本）も、後始末だけの台本へ直す。

**要件**: 11.3・11.8・12.4・12.5・12.6・18.1・18.4

## そのほかの指摘

タスクの前に、字面か設計を直す物:

1. **要件 18 の 1・18 の 5 の字面が、口パクの限界と合わない**（「受け手ごとの追い付き方」の「どれだけ厳しく時刻に合わせるか」）。18 の 1 は「字と口パクが、どこまで現れるか」を名指しで、届いた時刻に左右させないと言う。設計は、合図や知らせが刻みより後に届いた時の違いを許し、テストにしない。開発者の決めのとおりなら、18 の 1 と 18 の 5 から口パクを除く言い方へ直す（18 の 6 の「種類ごとに決まりを書く」へ寄せる）。

## 確かめて成り立った事
