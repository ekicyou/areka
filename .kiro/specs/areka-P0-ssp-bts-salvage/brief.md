# Brief: areka-P0-ssp-bts-salvage

## Problem
SSP の課題管理（MantisBT・https://bts.shillest.net/ ）には、利用者とゴースト作者が長年出してきた要望が溜まっている。areka が次に何を作るかを考えるときの材料として価値が高いが、いまは誰も通読しておらず、areka の側に写しも索引も無い。

- 要望は 1 件ずつ頁を開かないと中身が分からず、起票のたびに探し直すことになる。
- 「SSP では実装済み」「却下された」「未対応のまま」の区別が一覧からは読み取りにくい。
- areka の既存の spec・裁定と重なるもの、ぶつかるものが、照らし合わせないと分からない。

## Current State
- 2026-10-10 の実測（匿名で閲覧・解決済みも表示）: **全 808 件**、うち深刻度「要望」が **187 件**、それ以外（マイナー・メジャー・クラッシュ・表示・微調整など）が 621 件。最新の番号は 0000808。
- カテゴリは `SSPBT：本体(SSP)` が大半で、ほかに `SSPBT：ゴースト`・`SSPBT：その他`・`整備班：里々` などがある。
- 一覧は 1 頁 50 件で、CSV エクスポートの入口（`csv_export.php`）が匿名でも見えている。各課題は `view.php?id=N` で、深刻度・ステータス・解決状況・修正済バージョン・説明・コメント・履歴が読める。
- 深刻度の欄は当てにならない。要望でない深刻度で出されていても、中身は要望や質問のもの（例: 0000795「表示前にサーフェスの幅を知りたい」）が混じっている。
- areka の側には、正典（ukadoc）の拾い残しを追う `doc/ukadoc-coverage/`（台帳と報告）と、SSP の MCP を調べた `doc/ssp-mcp/survey.md` がある。BTS を扱った文書は無い。

## Desired Outcome
この spec のフォルダの中に、BTS の要望を areka の目線で整理した台帳がある。完了すると spec ごと `.kiro/specs/completed/areka-P0-ssp-bts-salvage/` へ移り、そこが最終の置き場になる。

- エージェントが「BTS の台帳を見て」と言われれば、steering の 1 行から `.kiro/specs/completed/areka-P0-ssp-bts-salvage/bts-ledger.md` へ辿って、主題ごとに要望を引ける。
- 各行から、SSP 側の結末（実装済みとその版・未対応・却下など）と、areka との関係（実装済み・brief あり・未着手・方針とぶつかる・対象外）が分かる。
- 台帳の先頭に、いつ・どこまで（最新の番号）を見たかが書いてあり、後で続きから拾い直せる。
- ふだんの spec 作業では読み込まれず、開発者の目にも付かない。steering の `structure.md` に在りかと使いどころを 1〜2 行だけ書く。

## Approach
**1 回きりの調査として、エージェントが読んで台帳を書く。取得や分類の道具（クレート・スクリプト）は作らない。**

1. **一覧の通読（全 808 件）**: 番号・要約・カテゴリ・深刻度・ステータス・解決状況・修正済バージョンを取る。CSV エクスポートが使えれば 1 回の取得で済ませ、使えなければ一覧を 17 頁めくる。
2. **ふるい分け**: 深刻度「要望」の 187 件はすべて対象。それ以外の 621 件は、一覧の要約と解決状況だけを見て、次の 2 種類だけを拾う。
   - 中身が要望・質問であるもの（深刻度の付け違い）。
   - 「仕様どおり」「修正不要」などで閉じられていて、正典（ukadoc）が黙っている挙動を作者が言葉で説明していそうなもの。
   それ以外のバグ（SSP の実装の不具合）は、areka の不具合ではないので読まない。
3. **中身を読む**: 対象の課題だけ、頁を開いて説明とコメントを読む。
4. **台帳を書く**（spec フォルダの `bts-ledger.md`）: 1 件 1 行。areka との関係は、`doc/ukadoc-coverage/` の台帳・`.kiro/steering/roadmap.md`・`.kiro/specs/`（完了分を含む）・記憶にある開発者の裁定と照らして決める。
5. **起票の候補を挙げる**: 「未着手で、areka の方針とぶつからず、デスクトップマスコットの枠に収まる」ものを、台帳の末尾に短い一覧として挙げる。起票そのものはしない。

置き場所の判断（2026-10-10 開発者「目立つところに置きたくない。spec の最終置き場〔completed〕へ移ることを前提に、steering に指示を出す」）:
- **本体はこの spec のフォルダの中**（`bts-ledger.md`。読み方・採り方・見た日付と最新の番号は同じファイルの先頭に書く）。完了のときに spec ごと `completed/` へ移る。完了済みの spec に調査の記録を残す先例がある（`completed/areka-P0-ghost-session-test-load-flake` の `load-repro.md`）。`doc/` の下には置かない（目立つ）。
- **steering には本体を置かず、在りかの指示だけ書く**。`structure.md` に「SSP の BTS の要望を調べるときはここを読む」と、**完了後のパス**（`.kiro/specs/completed/areka-P0-ssp-bts-salvage/bts-ledger.md`）で書く。完了のときのフォルダ移動でパスがずれないよう、初めから移動後のパスで書き、完了の手順の参照パス修正で実在を確かめる。

却下した案:
- 取得と分類の道具を `ukadoc-survey` のように作る案 — 正典の増減を自動で追う仕組みは持たない、という決まりに反する。1 回の調査に対して大きすぎる。
- 621 件のバグをすべて読む案 — SSP の実装の不具合は areka に当たらず、挙動は SSP の実測でなく ukadoc から決める、という方針とも合わない。
- 見つけた要望をそのまま全部起票する案 — roadmap が要望の写しで埋まる。起票は開発者が台帳を見て選ぶ。

## Scope
- **In**:
  - 全 808 件の一覧の通読と、上のふるい分け。
  - 対象の課題の読み込みと、台帳（spec フォルダの `bts-ledger.md`）の作成。先頭に読み方・採り方・見た日付と最新の番号を書く。
  - 起票の候補の短い一覧（台帳の末尾）。
  - `.kiro/steering/structure.md` への在りかの指示（完了後のパスで 1〜2 行）。
- **Out**: 下の「Out of Boundary」。

## Boundary Candidates
- 一覧の取得とふるい分け（どの課題を読むかを決める段）。
- 台帳の行の形（番号・要約・SSP 側の結末・種別・areka との関係・ひと言）と、主題の分け方。
- areka の既存の spec・裁定との照らし合わせ。
- 起票の候補の選び方。

## Out of Boundary
- **起票**（brief・roadmap の行を足すこと）。候補を挙げるところまで。起票は開発者が `/kiro-discovery` で行う。
- **コードの変更**。この spec は文書だけを足す。
- 取得・分類・更新を自動で行う道具や、定期的に見直す仕組み。
- SSP を動かして挙動を確かめること（実測）。
- BTS への書き込み（ログイン・コメント・課題の登録）。閲覧だけ。
- ukadoc の台帳（`doc/ukadoc-coverage/`）の書き替え。重なりを見つけたら、こちらの台帳に参照を書くだけにする。
- SHIORI（里々・YAYA など）やゴースト個別の課題の精査。一覧の段で「対象外」と書いて終える。

## Upstream / Downstream
- **Upstream**: BTS（外部・閲覧のみ）。照らし合わせの相手として `doc/ukadoc-coverage/`・`.kiro/steering/roadmap.md`・`.kiro/specs/`。
- **Downstream**: 開発者の `/kiro-discovery`（台帳から選んで起票）。棚卸（`/kiro-next`）で「ukadoc の拾い残し」「夢」の区分の材料を探すとき。

## Existing Spec Touchpoints
- **Extends**: なし。
- **Adjacent**: `areka-P0-coverage-roadmap-refresh`（ukadoc の台帳と roadmap の突き合わせ。こちらは BTS だけを扱い、ukadoc の台帳は書き替えない）。

## Constraints
- **相手のサーバーへの礼儀**: BTS は SSP の作者が運営する外部のサーバー。頁は 1 つずつ順に開き、同時に何本も投げない。サブエージェントを並べて一斉に読ませない。一覧は CSV の 1 回の取得を優先する。
- **ファイルの取得は開発者の了承を得てから**（CSV エクスポートはファイルのダウンロードに当たる）。了承が無ければ一覧を頁でめくる。
- **本文を丸写ししない**。台帳には、番号・要約（題）・URL と、自分の言葉で短くまとめた中身だけを書く。説明やコメントの長い引用は載せない。
- **用語**: 設定や機能の名前は ukadoc の用語で書く。spec は名前で指し、台帳の行は BTS の番号（`BTS 0000709` の形）で指す。
- **言語**: 台帳は日本語。英語で出された課題も、まとめは日本語で書く。
- **規模の目安**: 一覧 808 行、頁を開いて読むのは 250〜300 件ほど（要望 187 件＋バグから拾う分）。
