## Critical Issues

### 🔴 Critical Issue 1: 非接触の証跡（V2）が比較基準を持たず、現時点で既に成立しない

**Concern**: V2 は「ブランチの変更ファイル一覧を取得し、`.kiro/specs/areka-P0-present-write-coherence/` と `.kiro/steering/roadmap.md` 以外が含まれないことを確認」とだけ書き、**何と比較するか（`origin/main...HEAD` か・作業ツリーを含むか）を定めていない**。実測すると当ワークツリーは `vendors/pasta`（サブモジュールのポインタ）が **modified のまま**であり、許可集合のどちらにも属さない。作業ツリーを含めれば V2 は**今日この時点で失敗**し、含めなければ「本当にコードを触っていないこと」の証跡としては弱い。加えて Out of Boundary の「本仕様の差分集合は `.kiro/specs/areka-P0-present-write-coherence/` 配下に限る」という文と、V2 が `roadmap.md` を許可する記述が**互いに食い違う**（実測の `origin/main...HEAD` は spec 4 ファイル＋`roadmap.md` の 5 件）。

**Impact**: V2 は本仕様の中心的主張「是正コード 0 行」を支える**唯一の機械的証跡**である。基準が未定義だと、⑴ サブモジュールの汚れで偽の赤が出て「無関係だから」と手で通す運用が生まれる、⑵ 逆に緩い基準を選んで接触を見逃す、のどちらにも倒れる。要件 8.3（未達を消す方向の変更を禁じる）の守り手が、守り手として機能しない。

**Suggestion**: V2 の手順を機械で再実行できる形へ確定する——⑴ 比較基準を `git diff --name-only origin/main...HEAD` と明記し、⑵ 作業ツリーの汚れは `git status --porcelain` で別建てに検査し、⑶ 許可集合を「spec 配下 ＋ `.kiro/steering/roadmap.md`」と一箇所で定義して Out of Boundary の文言をそれに合わせ、⑷ `vendors/pasta` のサブモジュールポインタは**着手前の状態へ戻すか、差分に含まれない状態で完了させる**ことを明示する（本仕様が触っていないポインタを巻き込んで squash させない）。

**Traceability**: 要件 6.1-6.7・8.3、設計 D2
**Evidence**: `design.md` Boundary Commitments「Out of Boundary」第 1 項 ／ Testing Strategy「残余検証」V2 ／ Overview「Impact」

### 🔴 Critical Issue 2: 要件 4.6 の不適用扱いが設計側にしか無く、要件文書と食い違ったまま閉じる

**Concern**: 設計は要件 4.6（完了宣言に実機採取と決定論テストの双方を要求）を「**是正の合格を宣言する場合の**要求」と読み替え、その読みを `design.md`「完了報告の規律」に明示している。読み自体は妥当である（そう読まないと要件 3 の不適用と 4.6 が矛盾する）。しかし `requirements.md` 末尾の「見送りにより不適用となる要件」節は要件 2・3・5・7・6・9・8.4 を列挙する一方で、**4.6 には一言も触れていない**。要件文書だけを読む者にとって 4.6 は「発動中の、そして永久に満たされない完了条件」として残る。

**Impact**: 要件 8.4 は「裁定によって要件文書を改訂したとき、設計文書・境界節・steering まで同じ裁定を追随させる」と定める。本件はその**逆向きの片肺**——設計だけが裁定の帰結を持ち、正本であるはずの要件文書が持たない。過去に同じ形（`revise-design-not-just-requirements`）を踏んでいる。本仕様は「未達が仕様の内側から見えること」を目的とする仕様であるから、その内側に読み手が矛盾と読む条項が残るのは目的そのものと衝突する。

**Suggestion**: 要件文書の「見送りにより不適用となる要件」節へ 4.6 の 1 行（「4.6 は合格を宣言する場合の要求であり、本仕様は合格を宣言しないため発動しない」）を追加する。要件は確定済みで本フェーズでは改訂できないため、**設計ディスカッションで開発者の裁定を仰いだ上で**追記する（裁定が下りない場合は、design.md の当該読みが正本である旨を要件側から参照できる形にするだけでも片肺は解消する）。

**Traceability**: 要件 4.6・8.4・8.5
**Evidence**: `design.md`「完了報告の規律」末尾の「要件 4.6 の読み」 ／ `requirements.md`「見送りにより不適用となる要件」 ／ `research.md` §10.3 の 3 つ目の Decision

### 🔴 Critical Issue 3: V1 の完了ゲートが前提条件を持たず、Error Handling の「無関係」条項が逃げ道になる

**Concern**: 設計は Technology Stack で「本仕様の完了確認は `cargo test --workspace` のみで足りる（**GPU・実窓・実 DPI・実機操作をいずれも要しない**）」と書く。しかし当プロジェクトのワークスペーステストは GPU 実描画＋readback を素の `#[test]` として含み（`areka-no-ci-gpu-tests-in-cargo-test`）、また **i686 の host-32 成果物が先に無いと DoD ゲートが赤になる**（`workspace-test-needs-i686-host32-artifacts`）。括弧書きの主張は「本仕様が新たに要求しない」の意味なら正しいが、「ゲートを走らせる環境が要求しない」の意味では**事実に反する**。さらに Error Handling 第 1 項は「本仕様の差分は仕様文書のみであるから、赤は本仕様に由来し得ない」と先に結論を置いており、環境・前提条件由来の赤を「無関係」として通す経路が開いている。

**Impact**: 本仕様で生きている完了条件は要件 7.7 ただ 1 本である。その 1 本のゲートが前提未整備で赤くなり、しかも設計文が「本仕様に由来し得ない」と保証しているため、**唯一の完了条件が実質的に検査されないまま完了する**形になり得る。「全緑は十分性の証拠にならない」を繰り返し踏んできた本プロジェクトにとって、逆向き（赤を十分に調べない）の同型の穴である。

**Suggestion**: ⑴ V1 に前提条件を 1 行足す——i686 (`i686-pc-windows-msvc`) の host-32 成果物をビルド済みにしてから `cargo test --workspace` を走らせる、⑵ Technology Stack の括弧書きを「**本仕様が新たに要求しない**」と限定した文言へ改める（ゲート自体が GPU テストを含む事実は残す）、⑶ Error Handling 第 1 項の順序を反転させ、「赤は本仕様に由来し得ない」を前提ではなく**file 単位で示した後の結論**として書く（同項が既に要求している「無関係であることを file 単位で示す」を、逃げ道を塞ぐ順序で書く）。

**Traceability**: 要件 7.7
**Evidence**: `design.md`「Technology Stack」 ／ Testing Strategy「残余検証」V1 ／ Error Handling 第 1 項

## Design Strengths

### ✅ Strength 1: Revalidation Triggers が「見送り」を再監査可能な状態にしている

見送りの裁定は放置すると「なぜ直さなかったか」が失われ、再着手のたびに検討費用が丸ごと再発生する。本設計はそれを **却下理由 ↔ 構造的事実 ↔ 失効条件**の 3 点セットで縛った——「窓書込の刻印位置が変わったら R1 の根拠が失効」「flush の駆動位置が変わったら R2 の前提が失効」と、**何が起きたら見送りの根拠が消えるか**を先に名指ししてある。将来の読み手は差分を確認するだけで再着手の要否を判断できる。さらに同表の最終行「上限 16,667µs の変更は**失効ではなく要件 8.3 違反**である」は、未達を消す最も安易な手（上限を緩める）を先回りで塞いでおり、本仕様の目的（未達が仕様の内側から見えること）に対する最も本質的な守りになっている。

### ✅ Strength 2: 将来への手渡し「罠①」が、本プロジェクト固有の失敗形を先回りで潰している

罠①（可視化を書込の後ろへ回すと `visualize_to_write_us` が飽和して **0＝満点**になる）は、本検証で現物を確認した（`transition_judge.rs:817`）。これは「未測定」でも「違反」でもなく**満点として通る**——是正の実体が無くても PASS が出せる形である。しかも上限へ届く唯一の置き場（`EndDeferWindowPos` の後）が、まさにこの落とし穴の上にある。設計はこれを単に記録するのではなく「**置き場を決めるより先に、合格の意味をどう保つかを裁定すること**」という順序の指示として渡している。「全緑は十分性の証拠にならない」を繰り返し踏んできた履歴に対して、次の周回で同じ穴に落ちることを構造的に防ぐ手渡しである。罠②（`t_us` は tick 起点＝規模が 1 桁ずれる）も同様に現物確認済みで、どちらも実在の根拠を持つ。
