# Requirements Document

## Project Description (Input)

**誰の問題か**: areka（伺か互換ベースウェア）を実機で使う利用者と、その表示品質を保証する開発者。

**現状**: 画面の拡大率（DPI）を切り替えたとき、**絵は旧寸のまま・窓の位置だけ新しい**という食い違った中間状態が画面に見える（開発者の実機目視・2026-08-22）。先行仕様 `areka-P0-dpi-transition-atomicity`（以下 atom）は窓書込の逐次適用を消し（4 窓の書込が散らばる幅 93,152〜157,684µs → 40〜101µs）決定論テストは 8 遷移すべて PASS させたが、**atom 要件 4.2「窓矩形と描画内容（サーフェス寸）が食い違う状態を可視フレームとして提示しない」は実機では未達**のまま閉じた。残っているのは**可視化（`set_visible`／`set_bounds`）と窓書込のあいだの隙間**で、実測 `visualize_to_write_us` は 210,329〜306,301µs＝提示 1 コマ（16,667µs）の 12.6〜18.4 倍、上限以下で終わった窓は 32 窓中 1 つも無い。なお**「どちらが先に見えるか」は未特定**——アプリ側ログの時刻順は「寸が先・位置が後」で、開発者の目視申告（位置が先）とは向きが逆のまま是正前後の 2 採取で再現している。

**何を変えるか**: 絵と窓が同じ提示フレームで揃うようにする。機械側の完了条件は atom の判定器をそのまま流用し `visualize_to_write_us ≤ 16,667µs`。手段は atom 設計 C8 の候補表の内側に限り、B-3（可視化の 2 相化＝可視化を窓書込の直前まで遅らせる）と B-4（遷移中だけサーフェスを窓内下端中央へ置く補償）から選ぶ。ただし開発者裁定 2026-08-22 により **M1 の完成を妨げない優先度**であり、**tick 構造の大改造に及ぶなら B-4 へ落とすか着手を見送る**（atom 要件 9.3 に従い分割を再裁定）。

## Introduction

本仕様は atom が**決定論では満たし実機では満たさずに**閉じた要件 4.2 の、実機側だけを引き受ける。

atom は観測チャネル・レコード語彙・判定器・実機サインオフ手順書・確定台帳を着地させており、**本仕様はそれらを新設せず流用する**。是正の候補も atom 設計 C8 の候補表の内側（B-3／B-4）に限る（atom 要件 3.4 の縛りを継承）。

本仕様の特徴は、**着手そのものが裁定の対象である**ことである。開発者裁定 2026-08-22 は「大改造が必要なら無理に治さなくて良い」であり、steering の編成表（`roadmap.md` W6.95）も「要件段階でまず規模を見積もり、tick 大改造に及ぶなら見送りも正」と記している。したがって本仕様は「必ず直す」ことではなく、**⑴ 規模を測る → ⑵ 採否を一意に裁定する → ⑶ 採ったなら実機で合否を出す／採らないなら未達が仕様の内側から見える形で登記する**という順序そのものを要件にする。

**起点の実測**（正本＝atom 確定台帳 `mechanism-ledger.md` §11。`atom-73-signoff-1`・release・遷移 8 回・全遷移の域）:

| 量 | 値 |
|---|---|
| 絵が新寸になる（`kind=surface stage=visualize` の `t_us`・32 件） | 22,297 … 73,104 |
| 窓が動く（`kind=write` の `t_us`・32 件） | 253,890 … 339,998 |
| `visualize_to_write_us`（8 遷移 × 4 窓＝32 窓） | 210,329 … 306,301µs（上限 16,667µs の **12.6〜18.4 倍**・上限以下の窓は 0） |
| `flush_total_us`（8 遷移） | 143,231 … 231,910µs |
| 実機専用系統の違反 合計 | **40 件**（`visualize_to_write_us` 32 ＋ `flush_total_us` 8） |

> **註（2026-08-27 実測）**: `t_us` はプロセス開始からではなく**当該 tick の開始からの経過**である。したがって上表の 22,297〜339,998µs はすべて 1 つの tick の内側で起きており、遷移 1 回の tick は 340ms 級に伸びている。この読み替えを持たないと規模見積りが 1 桁ずれる（ギャップ分析 §0-2）。

**B-2b（一括書込）は隙間を縮めなかった**（`flush_total` 平均 192,247 → 188,711µs＝**−1.8%**。遅さの過半は OS 側＝台帳 L7）。むしろ全窓の書込がバッチ末尾へ揃ったため**窓ごとの隙間は +27% 伸びた**（平均 201,478 → 255,345µs）。これは欠陥ではなく同時性と引き換えの設計上の帰結だが、要件 4.2 の観点では隙間が均一に長くなったことを意味する。

### 裁定の記録（要件段階で解決した上流の食い違い 3 件）

1. **候補の順序**: atom 設計 C8 の候補表は梯子であり採用条件の順は **B-4 → B-3**（B-3 は「B-4 でも上限超が残る場合の最後の手段」）と書く。一方 atom 要件・atom tasks・steering `roadmap.md` W6.95 行は **B-3 を第一候補・B-4 を緩和**と書く。本仕様はこれを次のように読む——**「規模を先に測る対象は B-3」（効果を出せるのは B-3 だけであり、測らないと裁定できないため）／「採否は Requirement 1 の裁定で B-3・B-4・見送りの中から一意に決める」**。梯子の順序は採否の先取りではなく評価順の記述として扱い、本仕様は評価順ではなく裁定で決める。
2. **合否に載せる量**: atom の実機専用系統（`SIGNOFF-BOUNDS`）は `visualize_to_write_us` と `flush_total_us` の 2 量を含むが、後者は OS 側の所要が過半（台帳 L7）で C8 の候補表に減らす手が無く、討議の出発点（brief）も Desired Outcome に前者だけを挙げ、後者に相当する「OS 側の `SetWindowPos`／`EndDeferWindowPos` の所要」を対象外と明記している。よって**本仕様の合否量は `visualize_to_write_us` のみ**とし、`flush_total_us` は測るが合否に載せず残違反として登記する（Requirement 4）。
3. **観測点の追加**: brief は一方で「必要なら提示側の観測点を足すところから始めること」と述べ、他方で「観測チャネル・レコード語彙・判定器・サインオフ手順書の**新設**」を対象外と述べる。本仕様はこれを「**既存チャネルの内側へ観測点を足すことは可・並行する別系統を新たに立てることは不可**」と読む（Requirement 5）。
4. **B-3 の適格性（要件討議 #1・開発者裁定 2026-08-27）**: 窓書込の刻印は OS 呼出（`EndDeferWindowPos`）が戻った後に発行され、OS 呼出自体が 143,231µs 以上を占めるため、**文言どおりの B-3（可視化を窓書込の直前へ）では上限 16,667µs に構造的に届かない**（ギャップ分析 §1.4）。上限へ届く唯一の形＝flush 完了後に可視化の反映を駆動する形（B-3′）は、flush の後ろへ新しい駆動を足す行為であり、**要件 1.2⑵「tick の駆動と窓書込 flush の駆動の関係を変更する」に該当すると裁定**。よって要件 1.3 により **B-3（B-3′ を含む）は候補から落ちる**。採否（要件 1.5）の残る選択肢は B-4 か見送りであり、その裁定は討議 #2 で行う。なお開発者は同日、本仕様が「必ず直す必要のある仕様ではない」（モニタ DPI の切替は稀であり、この程度の問題は無視できる優先度）であることを再確認した。

## Boundary Context

- **In scope**:
  - 可視化の段と窓書込のあいだの提示順序、およびその隙間 `visualize_to_write_us`。可視化の段の実体は `apply_show` 末尾の一続き（供給面の入れ替え・寸の直接反映・`set_visible`／`set_bounds`）である。画面を即時に変えるのは供給面の入れ替え（upload の内側の提示）と `set_bounds` の内側の寸の直接反映であり、`set_visible` の効き（不透明度）は次 tick の Composition 相で反映される（2026-08-27 実測＝ギャップ分析 §1.1–1.2）
  - `crates/areka-emo-present/src/presenter/show.rs` の `apply_show` 末尾の可視化の段
  - B-4 を採る場合の、遷移中のみの窓内オフセット（下端中央）とその解除点
  - 実機での `visualize_to_write_us` の再採取と是正前後の比較
  - 着手の可否そのものの裁定（規模見積り → 採否 → 未達の登記）
- **Out of scope**:
  - 窓書込そのものの回数・順序・同時性（atom が着地済み。合流・一括・整合ゲート・連鎖再解決を含む）
  - OS 側の `SetWindowPos`／`EndDeferWindowPos` の所要、および `flush_total_us` の合否
  - 観測チャネル・レコード語彙・判定器・上限・サインオフ手順書の**新設**
  - tick の門（`AREKA_TICK_GATE`）の本採用と既定の変更
  - フレーム駆動の CPU 負荷（`draw-load-parity` の担当）
  - バルーン追従オフセットの k 倍（`balloon-offset-dpi` の担当）
- **Adjacent expectations**:
  - atom（completed）が着地させた判定器・観測語彙・実機サインオフ手順書・確定台帳を**そのまま使えること**を前提とする。上限 16,667µs は本仕様が動かさない確定値である。
  - `collision-dpi-hittest`（completed）が確定させた当たり判定の原点は**読むだけで変えない**。B-4 を採る場合のみ、壊していないことの確認が要る。
  - `recompose-budget`（completed）の定常アロケーション 0 と段階別計時ログを壊さない。
  - `test-cage-determinism`（completed）が整えた `apply_show` 鎖のテストと、一本化されたログ捕捉・一時パスの道具立てを前提とする。
  - 同ウェーブ（W6.95）の `balloon-offset-dpi`・`scope-zorder-pinning`・`balloon-vertical-canon` とは改変集合が交差しない前提で並走する。ただし B-4 を採ると配置契約で `balloon-offset-dpi` の関心事に意味論上近接する。
  - 実機採取は**人手（開発者）の作業**であり、エージェントは実行できない。

## Requirements

### Requirement 1: 出発点の確定と規模の見積り

**Objective:** As 開発者, I want 是正に着手する前に B-3 の規模を測り「大改造」の判定基準を機械で読める形で持つこと, so that 「大改造なら無理に治さなくて良い」という裁定を憶測ではなく事実の上で行使できる

#### Acceptance Criteria

1. The 本仕様 shall 是正の実装に着手する前に B-3（可視化の 2 相化）の規模見積りを作成し、接触するファイルと関数、破ることになる既存の順序制約、追加が必要になる仕組みを列挙して要件文書または設計文書へ記録する。
2. The 本仕様 shall 「tick 構造の大改造」を次のいずれかに該当することとして定義する——⑴ tick が回すスケジュールの順序または構成を変更する、⑵ tick の駆動と窓書込 flush の駆動の関係を変更する、⑶ 窓書込 flush の呼出位置をスケジュールの内側へ移す。
3. If 規模見積りが 1.2 のいずれかに該当すると判定されたとき, then the 本仕様 shall B-3 を採らず、atom 要件 9.3 に従って分割を再裁定し、その結論（B-4 へ落とす／着手を見送る／別仕様として起票する）と根拠を要件文書へ記録する。
4. The 本仕様 shall 採用候補を atom 設計 C8 の候補表の内側（B-3・B-4）に限り、表の外の手段を採らない。
5. The 本仕様 shall 規模見積りの結果として B-3・B-4・見送りのいずれか 1 つを採否として一意に裁定し、採らなかった候補それぞれについて採らなかった理由を記録する。
6. If 上流文書のあいだで候補の順序の記述が食い違っているとき, then the 本仕様 shall 「規模を先に測る対象は B-3・採否は 1.5 の裁定で一意に決める」という読みを採り、その読みを要件文書に明記する。

### Requirement 2: 絵と窓が同じ提示フレームで揃うこと

**Objective:** As 拡大率を切り替える利用者, I want 絵と窓が同じ提示フレームで揃うこと, so that 旧寸の絵が新しい窓矩形の中に見える中間フレームが現れない

#### Acceptance Criteria

1. Where B-3 または B-4 を採用したとき, the areka アプリケーション shall 拡大率の遷移においてキャラ窓・バルーン窓のすべてについて `visualize_to_write_us` を 16,667µs 以下にする。
2. Where B-3 を採用したとき, the areka アプリケーション shall 可視化を当該遷移の窓書込と同一の flush 区間の内側で行う。
3. Where B-4 を採用したとき, the areka アプリケーション shall 遷移のあいだサーフェスを窓の内側の下端中央に置き、窓書込の完了後にその一時配置を解除して原点へ戻す。
4. The areka アプリケーション shall 一時配置の解除点を明示的に持ち、遷移が完了した後の定常状態に一時配置を残さない。
5. If 一時配置の解除が行われないまま定常状態に入ったとき, then the areka アプリケーション shall その事実をログへ出し、定常の配置契約を静かに壊さない。
6. If 1.5 で見送りを裁定したとき, then the 本仕様 shall 2.1 を課さず、Requirement 8 の登記へ替える。

### Requirement 3: 実機サインオフによる合否

**Objective:** As 開発者, I want 合否を実機の採取で出すこと, so that 決定論テストが全部緑でも実機で直っていないという atom と同じ形を繰り返さない

#### Acceptance Criteria

1. The 本仕様 shall 合否を atom のサインオフ手順書に従った実機採取で判定し、決定論テストの結果だけでは合格としない。
2. The 実機採取 shall 拡大率の低→高・高→低をそれぞれ 3 回以上含み、キャラ窓の各スコープについてログから数えられる状態にする。
3. The 本仕様 shall 判定を atom が着地させた既存のサインオフ判定（生ログの絶対パスを環境変数で与えて明示実行する既存テスト）で行い、その全出力を記録票へ保全する。
4. The 本仕様 shall 上限 16,667µs を変更せず、目視の所見に合わせて上限を緩めない。
5. If 判定量が未測定として返ったとき, then the 本仕様 shall それを合格へ丸めず「まだ判っていない」として扱い、理由と対象窓を記録票へ書く。
6. The 実機採取 shall 人手の作業であることを前提とし、採取条件（コミット識別子・ビルド構成・ログ濾過設定・拡大率の 2 水準・tick の門の状態・ゴーストとバルーンの絶対パス・生ログの絶対パスと行数）を記録票へ明記する。
7. The 本仕様 shall 目視所見（跳ねの有無）と機械判定の一致／食い違いを記録し、食い違いのまま閉じる場合は症状に対応する量の名前と引受先を名指しする。
8. The 実機採取 shall 是正の前後で同じ手順・同じ 2 水準で行い、比較できる形で両方を保全する。

### Requirement 4: 合否に載せる量と載せない量

**Objective:** As 開発者, I want どの量で合否が決まり、どの量が測るだけなのかが一意であること, so that 片方の PASS を全体の合格と読み違えたり、届かない量で永久に不合格になったりしない

#### Acceptance Criteria

1. The 本仕様 shall `visualize_to_write_us` を本仕様の合否量とする。
2. The 本仕様 shall `flush_total_us` を測るが本仕様の合否には載せない。
3. If 採取後も `flush_total_us` の違反が残るとき, then the 本仕様 shall 残違反の件数と値を記録し、引受先の有無を明示して登記する。
4. The 本仕様 shall 決定論系統の PASS（窓ごとのフレーム差が 0 であること等）を、絵と窓が同じ提示フレームに載った証拠として読まない。
5. The 本仕様 shall 是正前後の比較に、一括書込の前後で意味が変わった量（1 件あたりの呼出所要）を用いず、区間の総所要・一括適用の成否・`visualize_to_write_us` で比較する。
6. The 本仕様 shall 完了の宣言に実機採取と決定論テストの双方の結果を要求し、片方だけの結果で完了としない。

### Requirement 5: 見え方の順序を断定しないこと

**Objective:** As 開発者, I want 「絵と窓のどちらが先に見えるか」を未特定のまま正しく扱うこと, so that 観測していない順序を前提に是正して見当違いの方向へ進まない

#### Acceptance Criteria

1. The 本仕様 shall 「絵と窓のどちらが先に画面へ出るか」を未特定として扱い、アプリ側ログの時刻順を見え方の順序として読まない。
2. Where 見え方の順序を名指しする必要が生じたとき, the 本仕様 shall 提示側の観測点を追加してから名指しし、観測を持たないまま断定しない。
3. Where 提示側の観測点を追加するとき, the 本仕様 shall atom の既存の観測チャネルとレコード語彙の規約の内側で追加し、並行する別系統の判定器・上限・サインオフ手順書を新設しない。
4. The 本仕様 shall 既存のレコード語彙（サーフェスの可視化段・窓書込・一括適用の可否・書込経路・flush の開始と終了）の文言とフィールド名を変更しない。
5. The 本仕様 shall 追加した観測点が既定で無効であり、有効化しない限り実行時の費用を持たないようにする。
6. If 観測点を追加したのに 1 行も記録が出ないとき, then the 本仕様 shall それを静かな成功として扱わず、点灯の確認を採取手順の中で明示的に行う。

### Requirement 6: 既存の確定物を壊さないこと

**Objective:** As 開発者, I want 先行仕様が確定させた形が本仕様の是正で崩れないこと, so that 直したはずの隣の欠陥が黙って戻らない

2. The 本仕様 shall 当たり判定の原点と、バルーン追従の基準（窓左上相対・追従オフセットを補正しない）を変更しない。
3. Where B-4 を採用したとき, the 本仕様 shall 当たり判定の原点が遷移中も遷移後も規約どおりであることを確認し、その確認結果を記録する。

5. The 本仕様 shall 可視化の段を含む既存の決定論テストを壊れたまま残さず、本仕様の変更で成立しなくなったテストは退役か更新かを判断して記録する。
6. The 本仕様 shall tick の門の既定（無効）を変更せず、門の本採用を行わない。
7. The 本仕様 shall 起床旗と観測の相名を読むだけで変更しない。

### Requirement 7: 決定論テスト

**Objective:** As 開発者, I want 決定論で検査できる部分を漏れなく檻に入れること, so that 実機採取が人手で高価であっても、退行を実機を待たずに捕まえられる

#### Acceptance Criteria

1. The 本仕様 shall 是正で新たに生じる判断分岐を純関数として切り出し、決定論テストで網羅する。
2. Where B-4 を採用したとき, the 決定論テスト shall 窓寸とサーフェス寸から下端中央のオフセットを導く判断と、一時配置の解除が行われることを検証する。
3. Where B-3 を採用したとき, the 決定論テスト shall 可視化が窓書込と同一の flush 区間の内側で行われることを検証する。
4. The 決定論テスト shall 是正前に赤・是正後に緑となる形を持ち、是正の有無に関わらず緑のままのテストを是正の証拠として数えない。
5. The 決定論テスト shall 本番ファイルの中に本体を書かず、同一ディレクトリの兄弟ファイルへ置く。
6. The 決定論テスト shall 実機の目視でしか判らない効果（跳ねて見えるか否か）を決定論で合格判定しない。
7. The 本仕様 shall ワークスペース全体のテストが通る状態で完了する。

### Requirement 8: 見送り・縮小したときの登記

**Objective:** As 開発者, I want 直さない／直しきれない場合でも未達が仕様の内側から見えること, so that テストが全部緑のまま未達が誰にも見つからないという過去の形を繰り返さない

#### Acceptance Criteria

### Requirement 9: 並走する仕様との境界

**Objective:** As 開発者, I want 同じウェーブで並走する仕様との責務の切れ目が明示されていること, so that 同居する仕様どうしで同じファイルを取り合ったり、確定済みの契約を二重に決めたりしない

#### Acceptance Criteria

1. The 本仕様 shall 可視化の段（いつ絵を見せるか）を自身の担当とし、窓書込の駆動（tick の相順）を担当しない。
2. Where B-4 を採用して配置契約に触れるとき, the 本仕様 shall 同ウェーブでバルーン追従オフセットを担当する仕様の要件と相互に照合してから設計を確定する。
3. The 本仕様 shall フレーム駆動の CPU 負荷とバルーン追従オフセットの k 倍を担当しない。
4. When tick の門が有効な状態で採取したログを扱うとき, the 本仕様 shall フレーム番号を鍵にした突合の意味が変わることを前提に集計の妥当性を再確認する。
5. The 本仕様 shall 着手時に上流の実測アンカー（可視化の段の位置）を実測で再確認し、ずれていれば本文書の記述を更新する。
