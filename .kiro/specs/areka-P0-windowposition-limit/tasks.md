- [x] 4.5 実機サインオフで見つかったキーワード基本位置のずれを是正する
  - 症状: `windowposition.x,center` の scope で、バルーンがシェル画像の中央から 26px 右へずれ、右端では作業領域を越えて実行時の関門にクランプされていた（画面上で明らかに偏る）

  - 是正: キーワード由来のバルーン基本位置を**実表示寸が確定した一度だけ**導出し直す。配置結果へ再導出の素材（キーワード種別と作者指定の調整量）を運ぶ枠を足し、キャラ窓へ使い切りの部品として焼き込み、キャラ窓の寸が最初に変わった書き込みで消費して除去する
  - キーワードの幾何は**関数を1本に切り出して**初期解決と再導出の両方が同じ式を呼ぶ（書き写すと片方だけ直したときに静かに割れる）
  - 数値指定・未指定の scope には素材が構造的に付かず、出力は1ビットも変わらない
  - 保存された相対位置が効いている scope では復元の合流処理が素材を落とし、再導出が保存値を上書きしない（保存値優先の順位は不変）
  - テスト: 採寸寸と実表示寸を**別々に与える**行列（中央上・中央下 × 調整量の有無）、一度きりの消費（2度目は動かない）、寸が変わらない書き込みでは素材を温存すること、実表示寸を運ぶ経路が複数あっても最初の1つで効くこと、数値指定は不変、保存値がある scope では素材が落ちること、バルーン寸が解決できないときは警告のうえ無変更
  - _Requirements: 4.2, 4.3, 4.5, 4.7, 5.2_

- [x] 4.6 機能検証で見つかった「保存値優先が起動時にしか効かない」欠陥を是正する
  - 症状: キーワード指定の scope で、利用者がバルーンをドラッグしてずらしたあと、面替え・再吸着・拡大率変更などでキャラ窓の寸が変わると、バルーンがキーワードの中央位置へ跳ね戻る（保存された値そのものは壊れず、セッション中の表示だけが戻る）
  - 原因: 4.5 が入れた「保存された相対位置があるなら再導出の素材を持たせない」規則を、**起動時の復元合流にしか置いていなかった**。要件 4.7 は状態の条件（保存された相対位置が存在する**間**）であり、その状態はセッション中にも生まれる——バルーン単独ドラッグの確定書き込みがまさにそれである
  - これが通常経路であること: 再解決は寸が同じ書き込みを飛ばすため、採寸した寸と実際に表示される寸が一致するふつうのゴーストでは素材が起動時に一度も消費されず、装填されたまま残り続ける
  - 是正: 相対位置が永続へ書き込まれるのと**同じ観測点**（バルーン単独ドラッグの確定ハンドラ）で素材を退役させる。起動時の規則と同一の条件（保存された相対位置の存在）で動かし、退役点が別々の条件を持つ形にしない
  - ドラッグ中の連続ハンドラでは退役させない（判断と理由は Implementation Notes に記載）
  - 素材を持たない窓（数値指定・保存値が効いた scope・消費済み）は完全な無操作で、警告も出さない
  - テスト: 再現手順そのもの（素材が残った状態で本番のドラッグハンドラを通し、その後にキャラ寸を変える書き込みを起こして、相対位置がドラッグ値のままであること）、確定ハンドラが素材を実際に取り除くこと、数値指定の scope でのドラッグが無操作であること（警告なし・異常終了なし）、起動時の振る舞いが不変であること（既存テストを無改変で維持）
  - doc: 沈黙ルール対応表へキーワード中央揃えの追従方針を1行追加し、既存行の実装ポインタ（幾何の所有者）を現状へ是正する

## Implementation Notes

- 4.7: **却下した設計を説明するコメントは、コメントが無いより悪い。** 今回の 2 箇所は「実表示寸が判る唯一の瞬間は特定の経路である」と断言していたが、実装はまさにその案を却下して寸の変化を契機にしている。読み手は自然言語の断言のほうを信じるので、次にこの周辺を触る人は「経路で絞られているはず」という誤った地図を持って入ることになり、寸の判定を「冗長な最適化」と読んで削りに来る。却下した案は、却下した事実と理由ごと書くか、書かないかのどちらかにすること。今回はどちらの doc にも却下の理由（実表示寸を運ぶ経路が複数あり、順序が相の並びに依存する）を添えた。
- 4.7: **サインオフの記録には「どのビルドで採ったか」を必ず書く。** 水準①の証跡はコミットを一切記していなかったため、後から入った是正（4.5）が証明書の一部を静かに無効化しても、記録を読む限り全項目が合格に見えた。しかも同じ走行の中に矛盾の証拠が入っていた——記録されたキャラ寸が採寸値のちょうど 2 倍で、後の走行が実測した実表示寸とは違う。**証跡の有効期限は、その証跡が依存している判断が変わった瞬間に切れる。** 記録側に「どの実行体か」が無いと、その瞬間を誰も特定できない。今回は失効した項目を消さずに区分（有効／失効）と理由を添える形で開示した——合格印そのものは当時の観測事実であり、取り消すと今度は「観測しなかった」という別の嘘になる。
- 4.7: 記録の齟齬は**単独では小さく見えるものほど、他の記述と突き合わせて初めて誤りと判る**。「非ゼロの調整量では観測できなくなる」は単体では筋が通っており、同じ文書の別の節が「その状態で PASS」と書いていることに気付いて初めて矛盾になる。1 文書内の相互参照（節番号・観測された走行・合否表）を明示的に書いておくと、この種の齟齬が検出可能になる。
- 4.6: **起動時の規則だけでは足りなかった理由**。要件 4.7 は「永続化された相対位置が存在する**間**」という状態の条件であって、起動時に一度評価すれば済む条件ではない。4.5 は素材を落とす判断を復元の合流処理（起動時に読み込んだ保存値の有無）にだけ置いたため、**セッション中に生まれた保存値**——バルーン単独ドラッグの確定書き込み——に対応する退役点が存在しなかった。片方だけ実装した状態は静的にも見つけられる形で、実際「素材を取り除く箇所がコード中に1つしかない」ことが手掛かりになった。
- 4.6: **通常経路であって隅の症状ではない**。実表示寸確定の再解決は寸が同じ書き込みを飛ばすため、採寸した寸と実際に表示される寸が**一致する**ゴーストでは素材が起動時に一度も消費されない。つまり装填されたまま残るのが既定の姿であり、面替え・再吸着・拡大率変更のいずれかが来た時点で発火する。4.5 の実機サインオフで問題が出なかったのは、その走行が「採寸寸 ≠ 実表示寸」の側だったからにすぎない。
- 4.6: **退役点はドラッグの確定側に置いた**（連続側には置かない）。理由は3つ。⑴ 要件 4.7 の条件は「**永続化された**相対位置」であり、その状態が生まれる観測点は確定側の書き込みだけである（1ドラッグ1書き込みの規律）。起動時の規則と同じ条件で動く形になり、退役点が二つの別々の条件を持たない。⑵ 連続側の穴は自己修復する——ドラッグ中に寸法変化が挟まって再導出が走っても、利用者はまだバルーンを掴んでおり、次のカーソル移動で相対位置が引き直され、続く確定書き込みがその値を保存する。確定側の穴（本欠陥）はセッションが終わるまで残る。⑶ 連続イベントごとに部品の付け外しを試みるのは、「持たない窓は1ビットも触らない」という既存の流儀に反する。
- 4.6: 追従元のキャラ窓が解決できない場合の警告は**足していない**。確定ハンドラは保存値の導出に同じキャラ窓を要するため、退役処理へ到達した時点で対象は既に確定しており、解決に失敗する余地がない（解決できない場合は手前で記録のうえ打ち切っている）。素材を持たない窓は異常ではなく正常な無操作なので、ここで警告を出すと数値指定のバルーンをドラッグするたびに無害な警告が積もり、本物の異常を埋める。
- 4.6: 部品の doc が主張していた「保存された相対位置が効いている間は素材が居ない」という不変条件は、是正前は**配置時にしか成立していなかった**。是正で実行時にも成立するようになったので、配置側と配置結果の doc を実態へ合わせた（退役点が2つあること、どちらも「保存値が生まれた事象」に結び付いていること）。

## 後日対応（本仕様の範囲外だったが同ブランチで消化・2026-08-14）

実装中に本仕様の範囲外として起票した 2 件を、開発者の指示により同ブランチで解決した。

### (1) ログ捕捉ハーネスの間欠フレーク（根治）

**症状**: `cargo test --workspace` の並行負荷下でのみ `capture_logs` が空文字列を返し、
テストが約 1/3 の頻度で落ちる。単独実行は常に緑。

**根因**: `tracing::subscriber::with_default` が差し替えるのはスレッドローカルの既定
dispatcher だが、**callsite の interest キャッシュはプロセス大域**で、その callsite を
最初に踏んだスレッドが勝つ。subscriber を持たないスレッドの既定 `NoSubscriber` は
`register_callsite` で `Interest::never()` を返すため、`never` が大域キャッシュへ焼き付き、
以後そのイベントは早期 return で捨てられる。各ハーネスの doc が主張していた
「各テストが自分のコードのみを包む限り並行実行でも干渉しない」は**誤り**だった。

**対策**: `crates/areka/src/placement/test_support.rs` で確立済みの構造的対策を移植——
プロセス寿命の probe dispatcher を 2 個常駐させて `has_just_one` を恒久的に偽にし、
捕捉窓の内側で `rebuild_interest_cache` を 1 回叩いて probe 導入前の毒を解く。

**適用先（5 ハーネス / 3 クレート）**:
- `crates/areka-emo-atlas/src/log_capture.rs`（実際に落ちていた当事者）
- `crates/areka-emo-compose/src/log_capture.rs`（同一構造の姉妹実装＝同じ脆弱性）
- `crates/areka-seriko/`（`actor_test_support.rs` / `looper_tests.rs` / `state_test_support.rs`
  の 3 コピー。probe 本体は新設 `src/log_interest_probe.rs` へ集約し 3 箇所から共有）

**検証**: 修正前は `--workspace` 10 走中 3 走が失敗（atlas 2・seriko 1）。修正後は連続走行で
再現せず。**seriko 側は修正作業中に新たに露見したもので、memory の「seriko capture_logs
未硬化」申し送りと同一の問題**。

**W6.9 `test-cage-determinism` への申し送り**: probe の実装が 3 クレートに重複している。
Rust はクレート跨ぎでテスト専用コードを共有できないため dev-dependency 用の
テストヘルパークレート新設が本筋だが、それは同 spec の領分として残す。
