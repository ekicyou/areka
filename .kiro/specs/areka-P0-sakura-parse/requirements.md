# Requirements Document

## Project Description (Input)

areka（x64 最小 SSP 互換ベースウェア）が emo2 を「そのまま」会話させるには、SHIORI 応答の `Value:` に載って返るさくらスクリプト本体を、シェル／バルーン演出エンジンが実行できる形へ解析する層が要る。現状 `crates/areka` にさくらスクリプトの parser は存在しない。この層が無ければ、host-32 が `OnBoot` の Value を受領できても誰も喋れない・誰も動けない。

本ユニットは、emo2 の boot script（および emo2 が実際に使うタグ subset を含む任意のさくらスクリプト）を入力すると、完全に decode 済みの型付き命令列（構造化 AST）を返す純粋関数を提供する。下流の `areka-P0-sakura-engine` はこの命令列をそのまま実行（タイムライン再生）するだけで、文字列を二度と解析しない。全ての字句解析・構造化・値デコードを本パーサが所有する。実物スコープの正本は `doc/emo2-conformance-scope.md` §3、設計判断の正本は `doc/COMPAT_ARCHITECTURE.md`。

## Introduction

本機能（以下「さくらスクリプトパーサ」）は、さくらスクリプト文字列を入力として受け取り、値まで完全にデコードされた型付き命令列（構造化 AST）を出力する純粋関数である。emo2 適合に必要なタグ subset（`doc/emo2-conformance-scope.md` §3）を意味の確定した命令ノードへ変換し、下流の再パースを不要にする。待ち時間・割合改行・選択肢・移動引数などの値正規化はすべてパーサ段階で完了させる。未知タグ・不正トークンは寛容にパススルーして解析を継続し、実ゴーストを止めない互換ベースウェア向きの頑健性を持つ。本パーサは host 非依存・純粋・単体テスト可能であり、emo2 の boot script を題材にした単体テストが green になることを単一の完了基準とする。

## Boundary Context

- **In scope**:
  - emo2 タグ subset（§3）の字句解析と完全デコード＝型付き命令列（構造化 AST）の生成。
  - `\w[n]` / `\wN` / `\_w[ms]` の待ち時間正規化（Duration へ統一）。
  - `\n[percent]` の割合（比率）デコード、素の `\n` の既定比率付与。
  - `\q[disp,target]` の disp/target 分離（型付き Choice 命令）。
  - `\![move,...]` の引数デコード（型付き Move 命令）。
  - `\p[n]`（話者スコープ）、`\s[...]`（中身は不透明文字列のまま保持）、`\_l[x,y]` / `\e` / `\c` / `\-` の各型付き命令化。
  - `%username` のシステム変数トークン化（展開はしない）。
  - タグ間プレーンテキストの Text run 命令化。
  - 寛容パススルー（未知タグ・不正トークンの raw/unknown 命令としての保持）。
  - boot script を題材にした単体テスト（host 不要）。
- **Out of scope**:
  - 命令の意味解釈・タイムライン再生・wait 実行（→ `areka-P0-sakura-engine`）。本パーサは命令を実行しない。
  - `%username` の実展開（実ユーザ名置換・実行時コンテキスト要 → engine/runtime）。
  - `\s[...]` 中身の数値解釈・エイリアス→ID 解決（→ surface 層 / `areka-P0-shell-parse`）。
  - `\![move]` の窓移動実行（→ render / window-placement）。
  - charset 変換（UTF-8 前提。Shift_JIS は M2 の生態系拡張）。
  - 脳（`.pasta` / `.lua` / budoux / 縦書き設定）の解釈（pasta.dll の責務・areka 不介入）。
  - バルーン定義の解析（→ `areka-P0-balloon-parse`）、パッケージ配置解決（→ `areka-P0-package-mount`）。
- **Adjacent expectations**:
  - 入力文字列は host-32 / conductor 経由で SHIORI Value から到来するが、本パーサはこれらにコード依存しない純粋関数である（並走安全・依存は M-boot のみ）。
  - 出力する型付き命令モデルは下流 `areka-P0-sakura-engine` と共有する I/O 契約の片側であり、エンジンは命令列をそのまま実行できることを期待する（エンジンは再パースしない）。
  - `\s[...]` の不透明な中身は surface 層が解釈することを前提に、本パーサはその文字列を改変・解釈せず素のまま受け渡す。

## Requirements

### Requirement 1: さくらスクリプトの命令列への変換（純粋関数契約）

**Objective:** 下流エンジン開発者として、さくらスクリプト文字列を入力すると値まで完全に decode 済みの型付き命令列が返ることを期待する。これにより、下流エンジンは文字列を再解析せず命令列をそのまま実行できる。

#### Acceptance Criteria
1. When さくらスクリプト文字列がさくらスクリプトパーサに渡された場合, the さくらスクリプトパーサ shall その文字列を字句解析・構造化し、順序を保持した型付き命令列（構造化 AST）を返す。
2. The さくらスクリプトパーサ shall 字句解析・構造化・値デコードのすべてを自身の責務として完了し、下流が再解析を要する未デコードの文字列断片を命令列に残さない。
3. When 入力に複数のタグとプレーンテキストが混在する場合, the さくらスクリプトパーサ shall 入力に現れた順序のとおりに各命令を整列した命令列を返す。
4. The さくらスクリプトパーサ shall 命令を実行・解釈せず（タイムライン再生・wait 実行・surface 指令の発行を行わず）、命令列の生成のみを行う。
5. When 空文字列が渡された場合, the さくらスクリプトパーサ shall 空の命令列を返す。

### Requirement 2: 話者スコープとサーフェス指令

**Objective:** 下流エンジン開発者として、話者切替とサーフェス指令が型付き命令として得られ、かつサーフェス指定の中身は不透明文字列として保持されることを期待する。これにより、エイリアス／ID 解決を surface 層へ委譲できる。

#### Acceptance Criteria
1. When `\p[n]` が現れた場合, the さくらスクリプトパーサ shall 話者スコープ番号 n を持つ型付きの話者スコープ命令を生成する。
2. When `\s[...]` が現れた場合, the さくらスクリプトパーサ shall 角括弧内の中身を不透明文字列としてそのまま保持した型付きサーフェス命令を生成する。
3. While `\s[...]` の中身を保持する間, the さくらスクリプトパーサ shall その中身を数値として解釈せず、エイリアスを ID へ解決せず、文字列を改変しない。

### Requirement 3: 待ち時間の正規化

**Objective:** 下流エンジン開発者として、複数の待ち時間表記が単一の正規化済み待ち時間（Duration）へ統一されることを期待する。これにより、エンジンは表記の差異を意識せず待ち時間を再生できる。

#### Acceptance Criteria
1. When `\w[n]` が現れた場合, the さくらスクリプトパーサ shall n を正規化済みの待ち時間（Duration）へ変換した型付き待ち命令を生成する。
2. When 短縮形 `\wN`（N は 1 桁の数字）が現れた場合, the さくらスクリプトパーサ shall N を正規化済みの待ち時間（Duration）へ変換した型付き待ち命令を生成する。
3. When `\_w[ms]` が現れた場合, the さくらスクリプトパーサ shall ms を絶対ミリ秒として正規化済みの待ち時間（Duration）へ変換した型付き待ち命令を生成する。
4. The さくらスクリプトパーサ shall `\w` 系・`\_w` 系のいずれの表記も、出力上は同一の型付き待ち命令（正規化済み Duration）として表現する。

### Requirement 4: 改行と割合改行

**Objective:** 下流エンジン開発者として、改行と割合改行が比率値付きの型付き命令として得られることを期待する。これにより、エンジンは行送り量を比率として再生できる。

#### Acceptance Criteria
1. When `\n[percent]` が現れた場合, the さくらスクリプトパーサ shall percent を比率値へデコードした型付き改行命令を生成する（例: `\n[150]` は 1.5 行ぶんの比率）。
2. When 引数なしの `\n` が現れた場合, the さくらスクリプトパーサ shall 既定比率を持つ型付き改行命令を生成する。

### Requirement 5: 選択肢

**Objective:** 下流エンジン開発者として、選択肢が表示文字列（disp）と選択 ID（target）に分離された型付き Choice 命令として得られることを期待する。これにより、エンジンは選択肢を再構成せず提示・確定できる。

#### Acceptance Criteria
1. When `\q[disp,target]` が現れた場合, the さくらスクリプトパーサ shall disp（表示）と target（選択 ID）を分離して保持する型付き Choice 命令を生成する。
2. When 選択肢マーカー `\![*]` が選択肢に伴って現れた場合, the さくらスクリプトパーサ shall 当該選択肢を型付き Choice 命令として構造化し、未デコードのマーカー文字列を命令列に残さない。

### Requirement 6: カーソル位置と制御命令

**Objective:** 下流エンジン開発者として、カーソル絶対位置と終端・クリア・終了の各制御が型付き命令として得られることを期待する。これにより、エンジンはメニュー配置や描画制御を文字列解析なしに実行できる。

#### Acceptance Criteria
1. When `\_l[x,y]` が現れた場合, the さくらスクリプトパーサ shall x と y を保持した型付きカーソル絶対位置命令を生成する。
2. When `\e` が現れた場合, the さくらスクリプトパーサ shall 型付きの終端命令を生成する。
3. When `\c` が現れた場合, the さくらスクリプトパーサ shall 型付きのクリア命令を生成する。
4. When `\-` が現れた場合, the さくらスクリプトパーサ shall 型付きの終了命令を生成する。

### Requirement 7: キャラ移動と汎用 `\!` コマンド

**Objective:** 下流エンジン開発者として、`\![move,...]` のみ引数が decode された型付き Move 命令となり、それ以外の `\!` は汎用コマンド命令として通ることを期待する。これにより、移動はそのまま実行でき、未対応コマンドでも解析が止まらない。

#### Acceptance Criteria
1. When `\![move,dx,dy,...,base,base]` が現れた場合, the さくらスクリプトパーサ shall 引数を decode した型付き Move 命令を生成する。
2. When move 以外の `\!` コマンドが現れた場合, the さくらスクリプトパーサ shall それを汎用コマンド命令として保持し、解析を継続する。
3. The さくらスクリプトパーサ shall `\![move]` 以外の `\!` コマンドについて引数の意味解釈・構造化を行わず、コマンド種別と生引数を保持した汎用コマンド命令として表現する。

### Requirement 8: システム変数トークン化

**Objective:** 下流エンジン開発者として、`%username` が展開されないシステム変数トークンとして得られることを期待する。これにより、実値展開を実行時コンテキストへ委譲できる。

#### Acceptance Criteria
1. When `%username` が現れた場合, the さくらスクリプトパーサ shall 展開を行わず、型付きのシステム変数トークン命令を生成する。
2. While システム変数トークンを生成する間, the さくらスクリプトパーサ shall 実ユーザ名などの実値置換を行わない。

### Requirement 9: テキストラン

**Objective:** 下流エンジン開発者として、タグ間のプレーンテキストが Text run 命令として得られることを期待する。これにより、エンジンは表示テキストをそのまま描画できる。

#### Acceptance Criteria
1. When タグ間にプレーンテキストが現れた場合, the さくらスクリプトパーサ shall そのテキストを保持した型付き Text run 命令を生成する。
2. When 連続するプレーンテキストが現れた場合, the さくらスクリプトパーサ shall 当該テキストを命令列内で元の文字順を保ったまま表現する。

### Requirement 10: 寛容パススルー（エラー方針）

**Objective:** 互換ベースウェア利用者として、未知タグ・想定外タグ・不正トークンが現れても解析が止まらず、実ゴーストが動き続けることを期待する。これにより、未対応構文を含むスクリプトでも破綻しない。

#### Acceptance Criteria
1. If 未知の `\!` コマンド・想定外タグ・不正トークンが現れた場合, then the さくらスクリプトパーサ shall それを raw/unknown 命令として保持し、解析を中断せず後続を継続する。
2. While 寛容パススルーで raw/unknown 命令を保持する間, the さくらスクリプトパーサ shall エラーを送出して解析全体を失敗させない。
3. When 解析対象の途中に不正トークンが含まれる場合, the さくらスクリプトパーサ shall 不正トークンの前後にある正常な命令を欠落させず命令列に含める。

### Requirement 11: 拡張シーム

**Objective:** 保守開発者として、M1 未使用タグを後日 variant 追加で対応できる開いた命令種別を期待する。これにより、最小実装を保ちつつ将来のタグ追加を低コストにできる。

#### Acceptance Criteria
1. The さくらスクリプトパーサ shall 命令種別を将来の variant 追加に対して開かれた形で表現する。
2. Where M1 未使用タグ（例: `\b` `\_b` `\i` `\j` `\&` `\f[]` `\x` 等・追加の `\!` 系）が入力に含まれる場合, the さくらスクリプトパーサ shall それらを寛容パススルーの対象として扱い、専用の構造化デコードを行わない。

### Requirement 12: 入力前提・純粋性・テスト可能性

**Objective:** ユニット開発者として、本パーサが UTF-8 前提の純粋・host 非依存・単体テスト可能な関数であることを期待する。これにより、host を起動せず並走安全に検証できる。

#### Acceptance Criteria
1. The さくらスクリプトパーサ shall 入力 charset を UTF-8 として扱い、Shift_JIS 等の charset 変換を行わない。
2. The さくらスクリプトパーサ shall 同一入力に対して常に同一の命令列を返す純粋関数として振る舞い、外部状態や host 環境に依存しない。
3. When emo2 の boot script が入力された場合, the さくらスクリプトパーサ shall host を起動せずに期待どおりの命令列へ変換し、その変換が単体テストで検証可能である。
