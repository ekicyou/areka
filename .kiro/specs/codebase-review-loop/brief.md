# Brief: codebase-review-loop

## Problem
リポジトリ全域には、テスト網羅の偏り・過剰な複雑度・潜在的な脆弱性が蓄積しうる。これらを「挙動を変えずに」継続的に検出・改善する標準フローが存在しない。手動レビューはメインエージェントのコンテキストを枯渇させ、大規模リポジトリでは完走できない。改善の途中中断や、デバッグ不能時の不安定な巻き戻しも、品質と再現性を損なう。

## Current State
- 対象は Rust マルチクレートワークスペース（`crates/areka`, `crates/dola`, `crates/wintf`）。`vendors/pasta` はパッチ依存の外部submoduleでレビュー対象外。
- `wintf` は COM ラッパー層 + ECS 9 サブシステム群 + 非推奨メッセージ層を持つ大規模crate。`structure.md` が責務マップを提供済み。
- `dola` は定義層〜実行時層の段階的モジュール構成。`areka` は小規模な統合バイナリ。
- テストは `cargo test`（統合テスト + in-source テスト）基準。網羅性・過不足は未測定。
- 改善作業を「領域 × 観点」で系統的に回し、各サイクルをコミットで保全する仕組みがない。

## Desired Outcome
- リポジトリ全域が「レビュー領域 × レビュー内容」のマトリクスで漏れなく分解され、各セルが**サブエージェントに委譲**されて実行される。
- 各改善サイクルが完了するたびにコミットされ、デバッグ不能時は直近コミットへ安全に巻き戻して次タスクへ進む（途中中断ゼロ＝全タスク完走保証）。
- 改善の前後で挙動破壊が無いことが、自己レビューと検証コマンド（build/test）で確認される。
- 全作業完了後に改善内容レポートが生成される。
- この仕様は**言語非依存**で設計され、別プロジェクト（任意言語/ビルドシステム）へコピーしても同等の効果が得られる。

## Approach
「レビュー領域 × レビュー内容」のマトリクスを単一仕様の中でタスク化し、1回の実装指示で完走させる。

- **レビュー内容（普遍・固定の観点列）**:
  1. ユニットテスト網羅性調査（不足の追加 / 不要の慎重な除外）
  2. コードのシンプル化（`/karpathy-guidelines` 準拠検証と改善）
  3. 脆弱性レビューと対策コード投入（挙動変更時は厳格に根拠記録）
  4. 改善前後の挙動非破壊確認（検証コマンド）
  5. 設計時に追加提案される改善フロー（拡張枠）
- **レビュー領域（行）**: 詳細なギャップ分析で発見する。最低でも「レビュー単位（Rustならcrate）」とし、領域が大きすぎてサブエージェント実行に支障が出る場合はさらに細分化する。領域分解は普遍手順として抽象記述する。
- **委譲方針**: 最低でもタスク（マトリクスのセル）単位でサブエージェント実行し、メインエージェントはオーケストレーションに徹してコンテキスト枯渇を防ぐ。
- **サイクル安全機構**: 各サイクル＝自己レビューで非破壊確認 → 検証コマンド成功 → コミット。失敗かつデバッグ完遂不能なら直近コミットへ巻き戻して次セルへ。途中中断は禁止。
- **言語非依存化**: レビュー領域の発見、検証コマンド（build/test/lint）、領域分解の粒度判定を抽象スロットとして定義し、プロジェクト固有設定（このリポジトリでは Rust/cargo）を差し込み式にする。

## Scope
- **In**:
  - `crates/` 配下の自作crate（areka, dola, wintf）全域のレビューと改善
  - Cargo.toml / CI / ビルド設定など横断的プロジェクト設定のレビュー
  - レビュー領域 × レビュー内容マトリクスのタスク設計とサブエージェント委譲フロー
  - サイクルごとのコミット、巻き戻し、自己レビュー、最終改善レポート生成
  - 言語非依存な普遍フローとしての設計記述
- **Out**:
  - `vendors/pasta` および外部依存crateのレビュー
  - 新機能の追加や挙動の意図的変更（既存 P0 機能specの領域）
  - 挙動を変える脆弱性修正の即時実装（厳格に記録し、必要なら別タスク提案に留める）
  - 大規模アーキテクチャ再設計（普遍的レビュー作業の範囲を超えるもの）

## Boundary Candidates
※ 最終確定は設計フェーズのギャップ分析で行う。以下は `structure.md` 由来の初期候補。
- レビュー単位 = crate（最小粒度）: `areka` / `dola` / `wintf`
- `wintf` 細分化候補: COM ラッパー層 / ECS-common / ECS-window(+window_proc) / ECS-graphics / ECS-layout / ECS-input(pointer+drag) / ECS-cue / ECS-dola / ECS-world / app / 非推奨メッセージ層
- `dola` 細分化候補: 定義層(document/storyboard/transition/easing/variable/value) / builder / playback / validate / compile / cue / runtime
- 横断: ワークスペース設定（Cargo.toml, profile, CI/ビルド設定）
- マトリクス軸: 上記「領域（行）」× 固定「レビュー内容（列）」

## Out of Boundary
- `vendors/` 配下の外部コードへの変更
- 挙動を変更する機能改修・最適化・API変更
- レビュー観点に含まれない一般的リファクタリング以外の大規模改変

## Upstream / Downstream
- **Upstream**: `.kiro/steering/`（product/tech/structure が領域マップと規約を提供）、`/karpathy-guidelines` スキル（シンプル化の判定基準）、`kiro-review`・`kiro-debug`・`kiro-verify-completion` スキル（レビュー・デバッグ・完了検証プロトコル）
- **Downstream**: 改善内容レポート（成果物）。将来、各 P0 機能specの実装品質ベースラインとして参照されうる。別プロジェクトへのコピー利用。

## Existing Spec Touchpoints
- **Extends**: なし（既存の機能specを更新しない、独立した横断レビュー仕様）
- **Adjacent**: `areka-P0-*`, `wintf-P0-*` 各機能spec。これらが所有するコードをレビュー対象とするが、機能仕様自体は変更しない（挙動非破壊原則で境界を守る）

## Constraints
- **挙動非破壊（厳格）**: 外部観測可能な挙動は原則不変。脆弱性修正で挙動変更が不可避な場合のみ、根拠を明記しレポートに必ず記録する。
- **言語非依存設計**: 領域発見・検証コマンド・分解粒度を抽象化し、別言語/ビルドシステムへコピー可能にする。具体適用先（Rust/cargo）は差し込み式。
- **サブエージェント委譲**: 最低でもタスク単位でサブエージェント実行。メインはオーケストレーションに徹する。
- **完走保証**: 全タスクを完遂。中断時は直近コミットへ巻き戻して次タスクへ進む（途中放棄禁止）。
- **サイクル＝コミット**: 各改善サイクル完了ごとにコミット。
- **タスク粒度**: サブエージェント実行に支障が出ない大きさに分解する（大領域は細分化）。
- **設計の普遍性**: 設計でソース参照は可。ただし「やるべきこと」は普遍作業として記述する。
