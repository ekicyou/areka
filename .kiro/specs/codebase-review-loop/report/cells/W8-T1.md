## フレーキー安定化（重要な追加成果物）

**実施: `crates/wintf/tests/ecs/cue_performance_test.rs` の実時間ベンチアサーション除去・決定論化（適用済み）**

- **対象と確定根拠**: フェーズ0実測で確定済みの `cue_performance_test::bench_pop_ready_empty_queue` を含む、同ファイルの **全 5 テスト**が `std::time::Instant::elapsed()` の壁時計しきい値（`elapsed.as_millis() < N` / `as_micros() < 1000`）を持つ実時間ベンチだった。特に空キュー pop を 10,000 回ループして `< 1ms` を要求する `bench_pop_ready_empty_queue` は、OS スケジューラのプリエンプション（並列テスト実行・CI・バックグラウンド負荷）で容易に偽陽性となる**負荷依存フレーキー**。
- **置換方針（挙動非破壊＝同じ正当性を非タイミング依存で検証）**: 各テストが検証していた 2 要素のうち、(a) 正当性アサーション（`queue.len()==N`・`commands.len()==N`・`queue.is_empty()`）はそのまま維持・強化し、(b) 実時間しきい値アサーション（`elapsed < Nms`）を完全除去した。正当性の検証内容を弱めず、むしろ「全件が Text("bench") として欠損なく復元される」「部分到達時に未来エントリが残る」「空キューは常に空を返し状態が健全」という決定論的検証を追加した。
- **置換後の内訳（5→6件）**: `bulk_insert_100_all_retained` / `bulk_insert_1000_all_retained`（全件保持）、`bulk_pop_ready_100_drains_all`（全消費→Completed）、`bulk_pop_ready_1000_drains_all`（全消費＋内容欠損なし）、`bulk_pop_ready_partial_time_leaves_future_entries`（**新規**: 部分到達で未来エントリ残置の決定論検証）、`empty_queue_pop_ready_is_noop_and_stable`（10,000 回 pop が常に空・状態健全）。実時間依存はゼロ（残存する `Instant`/`elapsed` 文字列は除去経緯を説明する doc コメントのみ＝実行コードに皆無、grep 実証）。
- **特性化中の発見（挙動非破壊で固定）**: 空キューは最初の tick で `schedule.is_completed()==true` となり **Completed へ遷移**する（旧版は実時間のみ見て状態未検証だった）。新版はこの真の挙動を `state()==Completed` で固定した。
- **安定化の確認（複数回実行で解消確認）**:
  - 隔離 5 回連続実行: 全 `6 passed / 0 failed`。
  - **並列負荷 5 多重実行**（旧フレーキーが顕在化した条件を模擬）: 5 並列とも `6 passed / 0 failed`。実時間しきい値が無いため負荷下でも揺れない。
  - `tests/ecs` バイナリ 3 回連続: 各 `102 passed / 0 failed`。

**`tracker_timeout` 容疑の判定（research.md の容疑は偽陽性と確定）**

- research.md が容疑として挙げた `cue_tracker_lifecycle_test::tracker_timeout`（`cue_tracker_lifecycle_test.rs:115`）を精査した結果、**タイミング依存ではない**ことを確定した。当該テストは `QueueSnapshot { timed_out: true/false }` という**プレーンな bool 入力値**を tracker.update に渡すのみで、`std::time::Instant`・`thread::sleep`・実時間 elapsed を一切使用しない（grep 実証: `cue_tracker_lifecycle_test.rs` に時間 API ゼロ）。`timed_out` フラグは本番では `CueQueue::check_timeout(current_time)` が算出するが（systems.rs:31）、テストでは固定 bool を直接注入するため完全決定論的。よって安定化対象外（既に決定論的）であり、見送りではなく「対象外＝改修不要」と判定。本セルでは tracker のタイムアウト写像（Click/Choice 両バリア × Timeout 応答→Timeout 結果）を in-source で更に固定した。

## テスト不能箇所・深掘り所見（R2.8）

1. **dispatch.rs の実 WindowHandle 経路は存在せず、デバイス依存ゼロ** — dispatch は純粋に bevy World + Query/SystemState 操作であり、Win32/GPU 依存はない。既存 cue_dispatch_e2e_test(6件) が配送先分配・複数演者独立消費・RouteSwitch ルーティング・ブロードキャスト・未登録アクタースキップ・絶対時刻変換を E2E で網羅しており、in-source 追加は同一挙動の重複となるため見送った（不足なし・過剰回避）。なお `RouteRemove` は本番で「full impl deferred」（dispatch.rs:78-86、key を算出するが `let _ = key` で破棄）であり、現状はログのみで registry を変更しない（将来実装の placeholder）。E2E では RouteSwitch のみ駆動され RouteAdd/RouteRemove は未駆動だが、いずれも registry 更新かログのみの単純分岐で挙動変更を要さないため提案化しない（現行仕様）。

2. **systems.rs（update_cue_sheet_trackers）の System 全体駆動は `Res<FrameTime>` 構築を要するが、本質ロジックは tracker 側で網羅** — 当該 System は (a) snapshot 収集（read-only query）、(b) `tracker.update(&snapshots)`、(c) TrackerAction 適用（resolve_click/skip_barrier/clear を query 経由で）の 3 フェーズ。本質的な判定ロジック（バリア解決・完了・キャンセル・エラーの写像）は `tracker.update`/`resolve_barrier` に集約されており、本セルの tracker in-source 11件がこれを直接固定した。System 全体（FrameTime リソース + 実 Schedule 駆動）の統合は cue_tracker_lifecycle_test の snapshot 直接注入で代替検証されている。TrackerAction→CueQueue 操作の結線（systems.rs:40-65）は bevy World 上の決定的処理だが、これを駆動するには World + FrameTime + 複数 CueQueue の組み立てを要し、tracker.update の写像が決定論的に固定されているため別途の System 統合テストは過剰（提案化不要）。

3. **CueQueue の `tick` 完了後挙動は「Playing 以外で early-return」のため冪等でない** — 特性化中に発見（`tick_after_completion_clears_ready`）。全エントリ消費で state が Completed に遷移（queue.rs:275）した後、次 tick は line 212 の `!matches!(state, Playing)` で early-return し `filtered_ready` をクリアする。TimedSchedule 単体の冪等性ガード（schedule.rs:144、ready_buffer 非空時の同一時刻再 tick で保持）は **CueQueue が完了遷移する場合には観測されない**（CueQueue 層が先に状態判定で弾く）。これは欠陥ではなく「完了後はバッファを保持しない」という現行の正当な挙動であり、未完了キース（後続エントリ残あり）でのみ TimedSchedule 冪等性が CueQueue 経由で観測される（`tick_is_idempotent_at_same_time_when_not_completed`）。両面を特性化して固定した。挙動変更を要さないため提案化しない。

4. **別 World から生成した「最初の entity」は同一ビットになり取り違える（テスト作法上の注意）** — tracker テスト作成中、別々の `World::new()` から各々最初の entity を生成すると index/generation が一致し `Entity` 値が衝突する点に留意した（`error_state_takes_priority_over_completion` は同一 World から 2 体生成して `e1 != e2` を保証）。本番コードの欠陥ではなく、テストで複数の区別ある Entity が必要な場合は同一 World から生成する必要があるという作法。`distinct_entities_roundtrip_distinctly` も同一 World で 3 体生成している。

## proposals へ回した候補
なし（新規採番なし）。`ecs/cue/` のキュー/トラッカー/レジストリ ロジックは **挙動変更を要する欠陥・脆弱性・削除候補を検出せず**、デバイス非依存に高くテスト可能であった（EntityRef bit 往復・tick 冪等性の正負両面・capacity アトミック性・バリア写像・完了/キャンセル/エラー優先順位を全面特性化、初回はバグ検出ゼロ＝後述 RED 代替を参照）。所見1〜4 はいずれも (a) 既存 E2E での網羅、(b) FrameTime 構築コスト、(c) 現行の正当な完了挙動、(d) テスト作法であり、新規仕様化を要しない。`RouteRemove` の「full impl deferred」は P1 拡張（registry 名前空間統合）の将来実装枠であり、本ループの挙動非破壊対象外（既存機能 spec 領域）。proposals.md 末尾は **P66**（変更なし。次セルの新規採番は P67 から）。

## RED フェーズ代替の検証
in-source 32件は既存挙動の characterization のため原則 GREEN by construction。期待値は実装と独立に各ソース仕様/代数から導出した:
- **queue.rs**: `push_entity_command` の `entity.to_bits()`→`EntityRef(bits)`（queue.rs:139-146）と `resolve_entity_ref` の `Entity::from_bits`（:156-161）から往復恒等を導出。`tick` の Playing ガード（:212）・schedule 委譲（:217）・Choice 分離（:221-234）・Completed 遷移（:275-277）と TimedSchedule の冪等性ガード（schedule.rs:144）から tick の正負両面を導出。`insert`/`extend_entries` の capacity 検査（:165-169/:188-192）と Completed→Playing 復帰（:174-176/:197-199）から境界・再活性化を導出。`reset_schedule`（:125-132）から全リセットを導出。
- **tracker.rs**: `receive_barrier` の first-valid + Skipped 無視（:89-99）、`update` の優先順（result 確定 :107 → cancel :112 → error :118 → バリア検知 :126 → timeout :143 → 解決 :153 → 完了 :158-169）、`resolve_barrier` の (response,kind) match 全アーム（:179-205）、despawn の `unwrap_or(true)`（:164）から各写像を導出。
- **registry.rs**: `register`/`register_actor` の HashMap insert 後勝ち（:38-40/:65-67）、`routes_for_actor` の `EntityKey::Actor` filter_map（:50-62）、`resolve` の get+copied（:70-72）から後勝ち・名前空間フィルタ・往復を導出。

**初回失敗 1 件の深掘り（特性化の正常収束）**: `tick_is_idempotent_at_same_time` は当初「単一エントリで同一時刻再 tick→ready 保持」を期待したが GREEN とならず（ready が 0）。深掘りの結果、単一エントリ消費で CueQueue が **Completed へ遷移**し（schedule.is_completed→state=Completed）、次 tick が Playing ガードで early-return して ready をクリアする真の挙動を特定。TimedSchedule 単体の冪等性は CueQueue が完了遷移する場合観測されないため、テストを (a) 未完了キュー（後続エントリ残）での冪等性、(b) 完了後の ready クリア、の 2 テストへ分割し真の挙動を固定した（プロダクション挙動は不変・テスト前提を実挙動へ修正）。これは特性化テストが実装の隠れた挙動を炙り出した正常な収束であり、バグ検出ではない（完了遷移は正当な現行仕様）。
