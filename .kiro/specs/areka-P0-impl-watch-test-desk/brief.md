# Brief: areka-P0-impl-watch-test-desk

> 起票: 2026-10-17（`/kiro-discovery`・開発者「負荷テストが始まると他の実装も全部止めちゃうよね？そうじゃなくて、『全体テスト・UIテスト』は、同時に他のテストが走らないようにしたいだけで、実装を止める必要はないんだ」）。きっかけは、並んで走るセッションのうち 2 本が同時に areka を立てていたこと（開発者「arekaが2つ起動したりしてた」）。区分 A（開発者が起票を頼んだ）。

## Problem

- **開発者**: 並んで走る実装セッションが、全体テスト（`tools/test-all.ps1`）や実機の UI テスト（`areka.exe` やゴーストを実際のデスクトップに立てる・`SendInput` や computer-use で操作する）を同時に回すと、次のことが起きる。
  - areka が 2 つ立って、窓・入力・前面を取り合う。テストが偽の赤になるか、何を確かめたのか分からなくなる。
  - 全体テストどうしはメモリとビルドを取り合う（`memory allocation ... failed`・`E0463`／`E0786` の偽の赤は、`kiro-complete` の「よくある失敗」に載っている）。
- **今の道具で防ごうとすると重すぎる**: 机の貸し出しのアプリ `areka-impl-watch.exe` の「負荷テストの机」は、取ると**ほかの参加者全員に停止要請**を出し、実装そのものを止めてしまう。全体テストや UI テストに要るのは「同じ種類のテストが同時に走らないこと」だけで、ほかのセッションの実装（コードを書く・クレートのテストを回す）は続けてよい。

## Current State

- `areka-impl-watch.exe`（`crates/areka-impl-watch`・完了 `impl-watch`・`impl-watch-skills`・`impl-watch-residue`）が持つ机は 2 種類（`doc/impl-watch.md` の「机は 2 種類」）。
  - **マージの机**（リポジトリごとに 1 つ）: 停止要請を出さない。`kiro-complete` が完了の手順の全部を、この机の番の中で回す。全体テストもこの中で回る。
  - **負荷テストの机**（マシンに 1 つ）: 番が来る前に、持ち主とマージの机の参加者以外の全員へ停止要請を出す。
- スキル `kiro-impl` は、負荷テストの机が要る段を「静かな CPU での計測・わざと負荷をかける再現・時間の比べ」の 3 つに限り、「ふつうのテスト（クレートのテスト・clippy・`tools/test-all.ps1`）は数えない」と書いている（`.claude/skills/kiro-impl/SKILL.md` の Desk timing 2）。
- そのため、次の 3 つは、今どの机も取らずに回る。
  1. `kiro-impl` の最後の検証（`/kiro-validate-impl` が全体テストを回す）
  2. タスクの中の実機の UI テスト（`#[ignore]` の実機テストを `--ignored` で回すものを含む）
  3. `kiro-complete` のステップ 5 の全体テスト・`/release` の全体テスト。マージの机はリポジトリごとなので、別のリポジトリや別のセッションの全体テストとは重なりうる。
- 2026-10-17 に、`kiro-impl` の段を負荷テストの机へ寄せる直しを一度書いたが、上の「実装まで止める」の理由で開発者が差し戻した（コミットは捨てた・main には無い）。

## Desired Outcome

- 全体テストと実機の UI テストは、**マシンの中で一度に 1 本だけ**走る。2 本目は番を待つ。
- 番を待つ間も、持っている間も、**ほかのセッションの実装は止まらない**（停止要請を出さない）。待っているセッションも、テストの要らないタスクは進められる。
- 負荷テスト（静かな机）との関係が決まっている。負荷テストの最中に全体テストや UI テストが走らず、全体テストや UI テストの最中に負荷テストの計測が始まらない。
- 机が要る段を、`kiro-impl`（タスクの中と最後の検証）・`kiro-complete`（ステップ 5 の全体テスト）・`/release`（全体テスト）が漏れなく取り、終わったら返す。
- `status` と `doc/impl-watch.md` で、今だれがこの机を持ち、だれが待っているかが読める。

## Approach

**推し: `areka-impl-watch.exe` に 3 つ目の机（仮称「テストの机」・マシンに 1 つ・停止要請を出さない）を足す。**

- 呼び方は負荷テストの机にならい、申し込み（`--wait` で番が来るまで終わらない）と返す（済んだ）の 2 つ。名前は要件で決める（例: `testrun`／`testdone`）。
- 番の決め方は申し込みの早い順。持ち主が落ちたら（見張りが消えたら）今の仕組みで外す。
- 負荷テストの机とは互いに排他にする（片方の持ち主が居る間は、もう片方の番を出さない）。どちらを先に通すかは要件で決める。
- スキルの側は、机が要る段の定義を「全体テスト・実機の UI テスト」（テストの机）と「負荷テスト」（負荷テストの机）の 2 つに分け、実装係への決まり文句も分ける。

**採らなかった案**:

- **負荷テストの机に `--no-stop` の印を足す**: 呼ぶ数は減るが、「静かな CPU を守る机」と「同じ種類のテストを 1 本にする机」が混ざり、負荷テストの机の持ち主が居る間の決まり（マージを始めない など）が全体テストにもかかってしまう。
- **`tools/test-all.ps1` の中で、マシン全体の名前つきの鍵（ミューテックス）を取る**: 呼ぶ側を直さずに全部の全体テストを覆えるが、実機の UI テスト（`cargo test -- --ignored`・spec ごとの実機の走行の道具）は覆えない。`status` に出ず、負荷テストの机とも連動しない。
- **スキルの文だけで負荷テストの机を使う**: 実装まで止まる（開発者が差し戻した形）。

## Scope

- **In**:
  - `crates/areka-impl-watch` に 3 つ目の机を足す（状態・番の決め方・負荷テストの机との排他・落ちた参加者の後始末・コマンドの口・`status` と `status.md` の表示・常時テストと実機テスト）。
  - `doc/impl-watch.md` の机の表・決まり・コマンドの表・終わり方の表。
  - スキル `kiro-impl`（机が要る段の定義・タスクの前の申し込み・最後の検証の前後・実装係と直し係への決まり文句）、`kiro-complete`（ステップ 5 の全体テストの前後）、`release`（全体テストの前後）の机の段。
  - 「実機の UI テスト」の判定の基準（タスクの文・`_Boundary:_`・設計の確かめの記述から、どう読み取るか）。
- **Out**:
  - 負荷テストの机とマージの机の今の決まりそのもの（停止要請の出し方・マージの順）。排他の決まりを足すところだけ触る。
  - 全体テストのスクリプト `tools/test-all.ps1` の中身。
  - 実機の UI テストそのものの直し（テストの中で areka を 1 つに限る仕組み など）。
  - 実行ファイルの置き方の道具 `tools/impl-watch-install.ps1`（版が上がったら入れ直すだけ）。

## Boundary Candidates

- 机の状態と番の決め方（`state.rs`・`plan.rs`）: 3 つ目の机と、負荷テストの机との排他。
- コマンドの口と待ち（`cli.rs`・`wait.rs`）: 申し込み・返す・`--wait` の終わり方の終了コード。
- 表示（`status.rs`）: 3 つ目の机の 1 行・数の行。
- スキルの机の段（`kiro-impl`・`kiro-complete`・`release`）と手順書（`doc/impl-watch.md`）。

## Out of Boundary

- 停止要請と再開の仕組み（3 つ目の机は使わない）。
- ほかのリポジトリの道具や、`areka-impl-watch` を使わない手作業のテスト。机は助けで、使えないときは今と同じく机の段を飛ばして作業を続ける。

## Upstream / Downstream

- **Upstream**: 完了 `impl-watch`（アプリ本体）・`impl-watch-skills`（スキルの机の段）・`impl-watch-residue`（拾い残し）。
- **Downstream**: 机を使う全部のスキル（`kiro-impl`・`kiro-complete`・`release`）。実機の UI テストを持つこれからの spec（`real-run-input-guard-observations`・`emo2-real-run-stability` など）は、この机が着地した後なら番を取って回せる。

## Existing Spec Touchpoints

- **Extends**: 完了 `impl-watch`・`impl-watch-skills`（完了した spec は直さず、この spec が新しい決まりを持つ）。
- **Adjacent**: `areka-test-binary-stability`・`present-emit-tail-latency`・`install-live-target-hazards`・`real-run-input-guard-observations`（負荷テストの机や実機の走行を使う spec。机の名前や呼び方が変わったら、その brief の記述を合わせる）。

## Constraints

- **トークンの負荷が最優先**（開発の道具の決まり）: 待ちは「番が来たら終わるコマンド」1 本。ポーリングや時間で回すループを足さない。出力は終了コード＋ASCII の数行。
- 道具が端末へ出す文は ASCII だけ（文字化けの決まり）。
- 実機テストの子プロセスの置き場所は、ワークツリーの `target\` の下の Windows 形の絶対パスで上書きする（開発者の機械には本物の置き場所が環境変数で設定されている）。
- 状態ファイルの形が変わるなら、古い形の状態ファイルを読んだときの扱いを決める（置き場所は全リポジトリ・全セッションで共有）。
- 規模の見立て: S〜M（10〜14 タスク・アプリ 6〜8＋スキルと手順書 3〜4＋実機の確かめ 1）。要件は Opus で足りる（先例＝負荷テストの机の形にならう）。

## 要件の段で決めること

1. **「ほかのテスト」の範囲**: 番を待たせるのは全体テストと実機の UI テストどうしだけか。ほかのセッションのクレートのテスト（`cargo test -p`）も待たせるか（待たせると、ほとんどのタスクが番待ちになる）。推し: 全体テストと実機の UI テストどうしだけ。
2. **負荷テストの机との順**: 両方に申し込みがあるときにどちらを先に通すか。負荷テストの持ち主が居る間は、ほかの参加者は止まっているので、そもそもテストの机の申し込みが出るか。
3. **`kiro-complete` での取り方**: マージの机の番の中で、さらにテストの机を取る形（取る順を固定して行き詰まりを防ぐ）でよいか。
4. **実機の UI テストの判定の基準**: タスクの文からどう読み取るか（`#[ignore]` の実機テスト・実機の走行の道具・`SendInput`・computer-use）。
