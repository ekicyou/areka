# Implementation Plan

> 設計は `design.md`、要件は `requirements.md`。触ってよいファイルは design.md の File Structure Plan と requirements.md の Boundary Context（2026-10-31 要件討議の議題 2）に挙げたものだけ。`crates/areka/src/install/` は `install-before-boot` の持ち物なので、赤になっても直す前にそのセッションと合わせる。

- [x] 1. 試験の道具を areka-actor から使えるようにする
  - areka-actor の試験だけの依存に、共有の捕捉の部品（log-capture-kit）をワークスペースの中の道で 1 行足す。理由の一言をほかの crate の書き方に揃えて添える
  - 本番の依存（`[dependencies]`）には足さない。ロックファイルは道具の自動の追随だけで、手で書かない（外のクレートは増えない）
  - 完了の姿: areka-actor の試験のビルドが通り、ロックファイルの差分が areka-actor の依存の並びの 1 行だけで、areka-actor の本番の依存の並びは変わっていない
  - _Requirements: 6.3, 5.1_

- [x] 2. 捕捉の窓の受け手が、開いているあいだだけ目印に答えるようにする
  - 窓専用の受け手を足し、中に今の集める受け手をそのまま持たせる。上書きは design.md の 8 つ（有効の判定・区間の作成・値の記録・因果の記録・記録・入る・出る・型の問い合わせ）だけで、記録は開いているときだけ渡し、有効の判定は閉じた後も真のまま
  - 型の問い合わせは、自分の型には今と同じに答え、目印の型（`[(); 0x6172_656B]`）には開いているときだけ自分を指す印を返す。印の健全さの理由（大きさ 0・整列 1）を 1 行のコメントで書く
  - 窓を閉じた印は、結果を取り出した後に（panic で抜けるときも）立つ番で立てる。番兵・取り出しの時点・自己検査の手順と、全スレッドの捕捉・濾過つきの捕捉の受け手は変えない
  - 窓の説明（呼んだスレッドだけ・他スレッドは入らない）を、引き継ぎの条件と閉じた後の扱いに合わせて直す。窓の関数の説明と、部品の入口（`log-capture-kit` の `lib.rs` 116〜118 行）の説明の両方を直す（`lib.rs` のコードは変えない）
  - 完了の姿: log-capture-kit の既存の自己試験がすべて緑のまま（窓の中でアクターを起こさないテストの結果は変わらない）
  - _Requirements: 1.4, 1.5, 2.3, 2.4, 3.6, 5.2_

- [x] 3. アクターの起動が、窓の中で起こしたときだけ窓の受け手を子へ渡す
- [x] 3.1 起こす時点の判定と、子のスレッドの先頭で受け手を据える 1 行を足す
  - 目印の型を 2 と同じ形で書き、「2 か所は同じでなければならない・ずれると対照の試験 ⑴ が赤」をコメントで書く
  - 判定は起こす側の今の受け手に目印を尋ねる 1 回だけで、答えた（開いている窓の）ときだけその写しを返す。スレッドを起こす前に 1 度だけ判定する
  - 子の閉包の最初の束縛で据える（actor の区間とフックより前・本体の終わりまで持つ）。据える呼出は番人の走査語に当たる形のまま書き、関数の名前だけを渡す形にしない。据える値は判定の答え以外から来ない
  - 区間・フック・join・起動失敗の扱いには触らない。ビルドの種類・機能の旗・環境変数を読まない
  - 冒頭と起動の関数の説明に、引き継ぎの条件・本番では据えないこと・窓より前に起きたアクターは入らないことを書く
  - 完了の姿: areka-actor の既存の試験（名前・panic の写し・受信ループ 3 本・フック）がすべて緑のまま。log-capture-kit の番人（共有の部品の外の直の呼出の検査）は、3.2 で例外表に載せるまで赤になるのが正しい
  - _Requirements: 1.1, 1.2, 1.3, 2.1, 2.2, 2.5, 3.1, 3.2, 3.3, 3.4, 3.6, 4.1, 4.2_

- [x] 3.2 番人の例外表に、アクターの起動の据える呼出を理由つきで足す
  - 例外表に 1 件（理由の骨子は design.md の GuardException）を足し、件数の約束を 4 から 5 にする。理由の文の中に走査語を続けて書かない
  - 依存の陽性の確かめの表（10 件）は触らない
  - 3.1 より先に足すと、当たりの無い例外として陳腐化の検査が赤になる。3.1 の後に行う
  - 完了の姿: 番人の試験（例外の陳腐化の検査・製品側の依存に現れない検査を含む）が緑で、ここで初めて log-capture-kit の試験が全部緑になる
  - _Depends: 3.1_
  - _Requirements: 5.3, 5.1_

- [x] 4. 引き継ぎが効くこと・効きすぎないことを areka-actor の中の試験で固める
- [x] 4.1 窓の中で起こしたアクターと、その子の記録が窓に入る試験を作る
  - areka-actor の中に兄弟の新しい試験のファイルを 1 本作り、起動のファイル（`spawn.rs`）に `#[cfg(test)]` の `#[path]` つきの試験の接続宣言を 1 つ足して繋ぐ（3.1 に続く `spawn.rs` の 2 度目の手）。捕捉はすべて共有の部品の窓口を通し、試験の中で受け手を直に差さない
  - 宛先は本ファイル専用の 1 つにし、各試験の主張はどれも「本ファイルの宛先＋項目 `probe` の値」で絞った記録だけを数える（結果の全件を数えない）。プロセスに 1 度のフックが導入済みだと（4.4）、ここで起こすアクターのフックの記録も窓に入るため
  - 待ちは受信（上限 10 秒）か join だけ
  - ⑴ 窓の中で起こしたアクターが warn と trace を 1 件ずつ出し、済みを受けてから閉じる。2 件とも水準・宛先・本文・項目が出した形のまま結果にある
  - ⑵ そのアクターが本体の中で起こした子が warn を出し、親が子を join してから済みを返す。子の記録が結果にある
  - 完了の姿: ⑴⑵ が緑。判定を常に「渡さない」にすると ⑴⑵ が赤になる
  - _Requirements: 1.1, 1.2, 1.4, 1.5, 6.1, 6.2, 6.3, 6.5_

- [x] 4.2 窓の外のアクター・ほかの窓・閉じた後の記録が入らない試験を足す
  - ⑶ 窓を開く前に起こしたアクター・窓の無い別のスレッドが起こしたアクター・別のスレッドが自分の窓の中で起こしたアクターに、窓の開いているあいだに記録を出させ、済みを受けてから閉じる。どれも結果に無い。隣で同じ窓の中で起こしたアクターの記録が入ることと、別のスレッドの窓にはその記録が入ることを確かめる
  - ⑷ 窓 A の中で起こしたアクター X の記録が A に入る（対照）。A を閉じ、窓 B の中で X に出させた記録は B に無く、B の中で起こしたアクター Y の記録は B に入る。最後に全 Sender を落として X が正常に終わる
  - 完了の姿: ⑶⑷ が緑で、「入らない」の主張ごとに隣の「入る」の対照が同じ試験の中にある
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 6.2, 6.4, 6.5_

- [x] 4.3 本番の形の行き先と、閉じた後に引き継がないことの試験を足す
  - ⑸⒜ 判定を直に確かめる: 「受け手なし」と、試験の中の目印に答えない最小の受け手のどちらでも渡さない。窓の中では渡す（対照）
  - ⑸⒝ 窓の無いスレッドから起こしたアクターの中の既定が、起こした側の既定と同じ答えになる
  - ⑹ 窓 A の中で起こしたアクターが、A の中では既定が目印に答え、A を閉じた後は答えない。閉じた後にそのアクターが起こした孫の既定が「受け手なし」
  - 完了の姿: ⑸⑹ が緑。判定を「受け手なしでなければ渡す」に変えると ⑸⒜ が赤になる
  - _Requirements: 2.1, 2.5, 3.5, 3.6, 6.2, 6.5_
