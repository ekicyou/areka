## 判定

**GO（条件つき）** — 選んだ形は実物のコードと合っていて要件を満たせる。ただし下の 3 件を設計討議で決めてから、タスク生成へ進むこと。3 件とも設計の作り直しは要らず、設計書の数か所の直しと開発者の裁定で済む。

## まとめ

設計は、brief の「子サーフェスへ分解する」形をやめ、合成の入力（`PatternState`）に「動く絵 → 今のコマの番号」の欄を足して、`Composer::compose_into` が命令の絵の番号をコマへ替える形を選んだ。やめた理由（`plan.rs` に触らずには要件を満たせない）は、実物を読んだかぎり正しい。位置・重ね順・外形・切り詰めのずれも、この形で崩れない。一方で、**同じウェーブで並走する別の spec のファイルに触る計画になっている**こと（設計は気付いていない）と、開発者の裁定が要る点が 2 つ残っている。

## 重大な指摘（3 件）

### 1. 同じウェーブで並走している spec のファイルに触る（設計は「約束を守る」と書いているが、見ているのは 7 か所だけ）

**何が起きているか**

設計の「File Structure Plan」は次の 3 ファイルを変える。

- `crates/areka/src/emo2_boot/mod.rs`（テストの接続宣言）
- `crates/areka/src/emo2_boot/frame/wiring.rs`（知らせの台帳の欄 1 つ）
- `crates/areka/src/emo2_boot/frame.rs`（相の呼び出し 1 行）

steering `roadmap.md` のウェーブ C4 の行では、この 3 つは並走中の別の spec の持ち物である。

- `emo2_boot/mod.rs` と `frame/wiring.rs` は `balloon-lifecycle-events`（C4-⑩）が触るファイルの一覧に載っている。同じ行の約束は、ほかの spec にこの 2 つを触らせていない（「④ は `emo2_boot/mod.rs`・`spine.rs`・`frame/wiring.rs` に触らない」「⑮ は `emo2_boot/mod.rs`（⑩）に触らない」）。
- `emo2_boot/frame.rs` は `char-position-save-on-exit`（C4-④）が触る候補に載っている。

本 spec（C4-⑫）に書かれた約束の 7 か所には入っていないので、字面の約束違反ではない。しかし roadmap が ⑫ の触るファイルとして挙げているのは seriko の `table`・`looper`・`parts`・`timeline`、compose の `world.rs`・`atlas_bind.rs`・新しいモジュール、台帳だけで、`emo2_boot` の結線は 1 つも入っていない。並走の照合はこの一覧で行われたので、このまま進むと ⑩・④ と同じファイルで当たる。

**直し方の案（設計討議で決める）**

バルーンの窓の知らせを、新しい相にせず、今ある届けの相に載せる。

- `run_status_report_phase`・`report_balloons`（`crates/areka/src/emo2_boot/frame/status_report.rs`）は、すでに装着済みのバルーンのスコープを昇順に回し、表示層の照会 2 本（`target_visible`・`current_surface_id`）を読んでいる。設計の新しい相が読むものと同じである。
- 台帳 `BalloonStatusLedger`（同ファイル）は `Emo2Wiring::balloon_status` としてゴーストごとに新しく作られる。「前に seriko へ知らせた値」の欄はこの型の中に足せる。
- こうすると `frame.rs`・`frame/wiring.rs` の変更は 0 になり、新しいファイル `stage_note.rs` も要らない。
- 注意: `run_status_report_phase` は文字の層を借りられないフレームで早く戻る。seriko への知らせはその手前に置く（知らせは文字の層を使わない）。
- E2E のテスト（`film_playback_e2e_tests.rs`）の接続宣言は `mod.rs` に置かず、本 spec が触るファイル（`status_report.rs` か、本 spec の新しいファイル）の子として `#[path]` で宣言する。これで `mod.rs` の変更も 0 になる。

**あわせて直すもの**: roadmap の C4 の行の ⑫ の触るファイルの一覧。設計は seriko の `state.rs`・`actor.rs`・`lib.rs`、compose の `pattern.rs`・`lib.rs` にも触る（どれも C4 のほかの spec の一覧には無いことを確かめた）。一覧に無いファイルを黙って増やさないこと。

### 2. brief の確定した案から離れる判断（開発者の裁定が要る）と、後続 `animated-image-import` への申し送りの抜け

**離れた理由は正しいか — 正しい（実物で確かめた）**

| 設計の主張 | 実物 | 結果 |
| --- | --- | --- |
| コマが空のとき、着せ替えでない animation の絵は 1 枚も描かれない | `flatten_surface`（`crates/areka-emo-compose/src/plan.rs`）が重ねる対象は「有効な着せ替えの pattern0」と「この段にコマを持つ番号」だけ | 正しい |
| element は必ず描かれ、コマはその上に重なるだけ | `push_static_element_ops`（同上）は束縛と位置の在る画像の element を必ず命令にする。コマは静的な層の後に積まれる | 正しい（1 枚目を element に残すと透ける） |
| 着せ替えでない animation のコマは外形に数えない | `flatten_extent`（同上）が数えるのは element と、着せ替えの種類の animation の pattern0 だけ | 正しい（動く絵だけのサーフェスは 0×0 → `build_plan` が `EmptyComposition` を返す） |
| 描画メソッドは `overlay` だけが動く | `ComposeMethod::is_implemented`（`method.rs`）。置き換える描き方は今は無い | 正しい（「コマで 1 枚目を置き換える」逃げ道は `method.rs` に触らないと作れない） |

つまり「1 枚目を element に残す」と透け、「残さない」と外形が消えて最初の表示が欠ける。`plan.rs`・`method.rs` に触らない約束の下では、子サーフェスの形は要件 1.7・「絵が欠ける瞬間 0 回」を満たせない。

**3 つ目の時計になっていないか — なっていない**

時計の持ち主は seriko の `PartClocks`（`crates/areka-seriko/src/parts.rs`）のままで、進めるのは seriko の刻み（`LoopRuntime::on_tick`・`looper.rs`）だけである。表示層・合成の側は時刻を持たない。アニメーションの仕組みは「台本の再生」と「サーフェスのアニメーション」の 2 つのままと言える。

**それでも裁定が要る理由**

brief の Approach 1 は開発者が言葉で確定した形（「読み込み時にサブエレメント分解して…ながれできれい」）である。設計は自分でも議題 1 に挙げているので、ここでは裁定の材料を足す。

**後続 `animated-image-import` が得るもの・失うもの**

- 得るもの: コマの番号の欄、差し替え（`film::substitute`）、`film_frame_at` がそのまま使える。サーフェスの番号の空間を新しく作らずに済む。
- 失うもの ⑴: 子サーフェスの形なら、`import` は「pattern定義が合成のサーフェスを指す」だけで今の `flatten_surface` に載った。本設計の形では、`import` の側が「pattern定義の絵を命令にする所」を `plan.rs` に新しく作る必要がある（設計の申し送りの文面にも書いてある）。
- 失うもの ⑵（**申し送りに書かれていない**）: 絵のコマの欄は「動く絵 1 つにつきコマの番号 1 つ」である（要件 3.4 のために正しい）。しかし `import` は始まりの時刻が別（冒頭の待ち＋ animation の interval）で、繰り返し回数も使わない。同じ画像ファイルを element定義で自動再生しつつ `import` でも使うと、1 回の合成の中で同じ絵に 2 つの違うコマの番号が要る。今の欄の鍵（動く絵の番号だけ）では表せない。`import` の側で欄の鍵を広げる（設計の Revalidation Triggers の 1 行目に当たる）ことになる。

**求めること**: ①開発者の裁定（この形でよいか／約束を解いて `plan.rs` を直す道を取るか）。②この形で進むなら、申し送りの文面の「`areka-P0-animated-image-import` に足すこと」に、失うもの ⑵（欄の鍵が絵 1 つにつき 1 つであること・同じファイルを 2 通りに再生するなら鍵を広げること）を足す。要件 5.2 は完了の時点で食い違い 0 件を求めている。

### 3. 「1 フレーム遅らせる解は取らない」「時刻は正確に扱う」との関係が、設計書の中で裁定待ちとして並んでいない

設計は表示そのものは遅らせていない（面の切り替えの指令に経過 0 の絵が載る。これは今の `refresh_parts`〔`looper.rs`〕が `apply` の指令を差し替えて 1 件だけ出す形の延長で、実物と合う）。しかし次の 3 つは、開発者の決まり（1 フレーム遅らせる解は取らない／時刻は正確に扱う＝要件 2.4・2.9 の裁定）や要件 6.4 の字面と擦れる。設計は 1 つ目を「StageNote 相」の Risks に、3 つ目を Open Questions に分けて書いており、2 つ目はどこにも裁定待ちとして出ていない。

1. **バルーンの窓が出た直後、終わりなしの絵が古いコマのまま 1〜2 フレーム見える**。窓を出すのは可視性の相の `show_target`（`crates/areka/src/emo2_boot/balloon_visibility_phase.rs`）で、表示層は最後に確立した入力（`PresentTarget.last_show`・`crates/areka-emo-present/src/presenter/show.rs`）で描く。隠れている間 seriko はバルーンの面を評価しないので、その入力は隠れる直前のコマである。知らせが seriko に届いて正しいコマの指令が戻るまで、古いコマが見えてから飛ぶ。要件 3.3（見えなかった間も進んでいたものとして続きから）とは、最初の 1〜2 フレームだけ食い違う。
2. **隠れている間に合成が走る**。窓が閉じたとき、回数つきの絵を 1 枚目へ戻す指令を 1 回出す（設計「バルーンの窓の知らせ」）。外から所有される窓への `ShowSurface` は「見えるようにしない」だけで、合成と表示の記録は行う（`apply_show`・同上）。さらに、閉じた知らせが seriko に届くまでの刻みでコマが進めば、その分の指令も出る。要件 6.4 は「コマが進むことを理由に描き直さない」なので、戻す 1 回は字面の外だが、届くまでの刻みの分は字面に当たる。
3. **時計は「見えた最初の刻み」に始まる**。表示の指令から最初の刻みまで（ふつう 16 ミリ秒以内、刻みが空く機械ではその分）1 枚目が長く見える。積み上がりはしない（要件 1.6 は満たす）。要件 2.9 の裁定の例（1 秒に 1 回の更新なら 1 秒ぶん進む）に対しては、始まりだけが最大 1 刻み遅れる。

**見立て**: 3 つとも、seriko が別スレッドのアクターで、時刻を刻みでしか知らないことから来る。今ある `\s`・`\b`・まばたきの指令も同じ道（seriko → 橋 → 表示層）を通るので、本 spec だけの遅れではない。表示層（`areka-emo-present`）に触らない約束の下で 0 フレームにする形は見つからなかった（表示層の側で経過からコマを決めると、それが 3 つ目の時計になる）。

**求めること**: 開発者に 3 つをまとめて見せ、受け入れるか決めてもらう。受け入れるなら、①対応表（`doc/COMPAT_ARCHITECTURE.md` §8）に 1・2 も書く（設計は 3 だけを書く予定）、②決定論テストで上限を固定する（「窓が開いた知らせの後の最初の指令は、経過どおりのコマを運ぶ」「閉じた知らせを受けた後の刻みは指令 0 件」）、③要件 6.4 の読み方（戻す 1 回は数えない）を設計書に 1 行で明記する。

## そのほか気付いたこと（重大ではない・タスクの段で拾う）

- **バルーンの面で部品と `always` を回す経路は、今は誰も通れない**。バルーンの面は `element0,overlay,<実ファイル名>` だけのサーフェスへ書き直される（`synthetic_surfaces_txt`・`crates/areka-emo-present/src/balloon.rs`）ので、部品も animation も持てない（設計自身が「バルーンの表は今は必ず空」と書いている）。バルーンで要るのは動く絵の時計だけである。部品の経路をバルーンへ広げる分（`LoopRuntime` の手順 2・「着せ替えの集合は空として渡す」）は、本物の検体で踏めない行になる。足すなら理由を書くか、動く絵の分だけに絞る。
- **合成の結果を覚える席**: 席は表示の対象ごとに 3 つ（`ComposeCache`・`CAPACITY`・`crates/areka-emo-present/src/cache.rs`）。鍵 `ComposeKey` は `PatternState` を丸ごと等しさで比べるので、欄を足すだけで鍵に入る（表示層の変更は要らない・設計の主張どおり）。コマが 4 枚以上の絵は、コマが替わるたびに合成し直しになり、同じ面のまばたきの命中も崩す。`emo2` の大きさの合成は、完了 `areka-P0-recompose-budget` の測定で 1 コマ 1.2〜5.7 ミリ秒だったので、16 ミリ秒には収まる見込みだが、バルーンと大きな絵は測ってから判断する（設計の方針どおりでよい）。
- **テストの抜け**: ⑴ 要件 1.13（透ける形が表示中のコマに従う）を固定するテストが計画に無い（「既存の仕組みで満たす」とだけある）。合成の結果からマスクを作る所は表示層に在るので、`areka` の側の E2E で 1 つ踏む。⑵ 要件 2.9 は `always` にも当てはまるが、`always_at` のテストの一覧に「経過が飛んだとき」が無い。⑶ 要件 6.2（文字の配置が動かない）は Risks に「確かめる」とあるだけで、どのテストが判定するかが無い。
- **束縛の付け替えの安全**: 束縛（`AtlasBinding`）を読む本番のコードは `plan.rs` だけだった（テストを除いて全クレートを探した）。付け替えで困る読み手は居ない。
- **行数**: 設計の「今」の数字は 12 ファイルとも実物と一致した（`spine.rs` が 1,000 行ちょうどで触らない判断も正しい）。いちばん増える `looper.rs`（528 → 約 680）は `on_tick` 1 本がすでに 260 行あるので、実装で 1,000 行に近づいたら動く絵の分を `film.rs` へ寄せる。
- **記録の回数（要件 8.4）**: 表を作る本番の呼び手は `assets.rs` の 2 か所（シェルは 1 回・バルーンはスコープごと）だけで、設計の「読み込み 1 回・原因 1 つにつき 1 回」は成り立つ。

## 確かめて正しかった主張（設計を信じてよい所）

- 命令 `BlitOp` は絵の番号と位置だけを持ち、切り詰めのずれと頁の位置は転写のとき絵の番号から引く（`execute`・`crates/areka-emo-compose/src/blit.rs`）。命令の絵の番号を替えれば、位置・重ね順はそのままで、コマごとの切り詰めのずれは正しく効く。位置の無い（全透明の）コマは `execute` も読み飛ばす。
- 外形は束縛した絵の原寸で数える（`flatten_extent`）。全コマの原寸が同じことを FilmBinder が検査するので、付け替えても外形は同じ。
- `build_plan` を呼ぶのは `Composer::compose_into`（`crates/areka-emo-compose/src/lib.rs`）の 1 か所。
- 同じ `PatternState` なら指令を出さない（`ScopeStates::commit_pattern`・`crates/areka-seriko/src/state.rs`）。
- seriko は `areka-emo-atlas` に依存していない（`crates/areka-seriko/Cargo.toml`）。`AnimationTable::from_world` の署名を変えずに済む。
- バルーンの窓は外から所有され、`ShowSurface` は見えるようにしない（`apply_show`）。コマの指令で隠れたバルーンが出ることは無い（要件 6.3）。
- `table.rs` のテスト `only_random_and_bindrandom_are_recorded_others_debug_logged` は「採らない語」の例に `always` を使っており、書き換えが要る。`LoopTrigger` の腕を 2 つと決め打つ所も設計の挙げたとおり在る。
- 回数つきの絵の始め直し（要件 2.3・2.7・2.8）は「見えなくなった評価で時計を捨てる」で成り立つ。評価は刻み・面の切り替え・着せ替えの変化・窓の知らせの全部で走るので、刻みの間に「行って戻る」場合も捨てられる。pattern定義の先（まばたきのコマのサーフェスなど）に置いた絵も、見える部品の求め方（`NestTable::visible_parts`・`crates/areka-emo-compose/src/nesting.rs`）がコマをたどるので数に入る（要件 1.9）。

## 設計の強み

1. **空の `PatternState` が「全部の動く絵が 1 枚目」と同じ意味になる**（0 番は欄に載せない）。装着・差し替え・採寸が空のコマで出す絵と、seriko が 1 枚目を指した絵が同じ鍵になり、動かないシェルでは面の表も合成も今と同じ行だけを通る。要件 7 を作りで満たしている。
2. **今のコマを「開始の時刻からの経過」だけの純粋な計算で決める**。持ち越す状態が無いので、遅れの積み上がり・待ち時間 0・更新が空いたときの進み方（要件 1.6・2.4・2.9・2.6）が作りから出る。回数つきで止まった状態も別に持たず、経過から求まる。
