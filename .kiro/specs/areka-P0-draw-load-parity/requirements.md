# Requirements Document

## Introduction

areka（ukadoc 互換ベースウェア）は、同一マシン・同一ゴースト（emo2）・同一拡大率（200%）・同一手順の 25 分走行で、アイドル時 CPU が SSP の **3.6 倍**（平均 10.97% 対 3.05%・1 コア換算）、発話中は **4.4 倍**（頂 20.42% 対 4.64%）を消費する（2026-08-15 実測・出典 `brief.md` `## Problem`・`.kiro/steering/roadmap.md` 追記(68)）。デスクトップマスコットは常駐が前提なので、この差はバッテリー・発熱・他アプリへの圧迫として日常的に効く。

先行 spec `areka-P0-recompose-budget`（2026-08-15 完了）は表示 1 コマの適用経路を 22,210µs → 1,240µs（18 分の 1）まで削ったが、**同経路はアイドル CPU の 3.3% しか占めておらず**、CPU の中央値は 9.3% のまま動かなかった（`completed/areka-P0-recompose-budget/remeasure-2026-08-15.md` §5.7）。残る負荷は表示 1 コマの適用経路の**外**にある。同 spec の使い捨て計測は、その主役が wintf のフレーム駆動——ECS の tick が毎秒 120 回・1 回あたり約 578µs で 13 本のスケジュールを全部回し、tick の 98% は表示に変化が無い——であり、上位 2 本（FrameFinalize 182µs・Draw 143µs）で 56% を占めると示した。同 spec は合格判定式のうち **⑵ catch-up 0 件**と **⑷a release アイドル CPU 3.0% 未満**を未達のまま送り出し、引受先を本 spec と登記した。本 spec はこの 2 件を引き受ける。

### 本 spec の目的（2026-08-22 開発者指示で確定）

**本 spec の最重要事項は「目標（goal）を置き、そこに至るまでの調査・実装ループをエージェント自身が自走で回す仕組みを作り、実際に回すこと」である。** 開発者の裁定や開発者の作業（静寂確認・実機サインオフの立会い・大改造の可否判断など）を途中に挟まない。エージェントが「どこが重いかを測って突き止める → 直す → 測り直して採否を決める」を目標達成まで繰り返す。したがって、**「どこが重くなっているか」をどう調査するか**（計測手段・解析手順・結果の読み方）が要件・設計の中心である。負荷の削減そのものは、この仕組みを回した結果として得る。

### 本要件が依拠する現況（2026-08-22・現行ツリーで file:line を裏取り済み）

brief の性能数値と機序の読みには、要件として据える前に訂正すべき点がある。

- **⚠ brief の全性能数値は更新前の実測である。** main に Bevy 0.19／Taffy 0.13 への更新（`bf2d7950`・2026-08-19・実行器改稿を含む）が着地した。`try_tick_world` 1 tick 578µs・壁時計 6.85%・FrameFinalize 182µs／Draw 143µs・SSP 比較の areka 側 10.97% は**いずれも更新前（2026-08-15 以前）**の値で、実行器が変わったため傾向すら持ち越せない。本書はこれらを「更新前の参考値」とのみ扱い、現況の確定はループの 1 周目（ベースライン）に委ねる。ワークスペースの `Cargo.toml:48-49` は `bevy_ecs = "0.19"` を宣言している（steering `tech.md:22-23` の「0.18.0」は陳腐化。ローカルの `Cargo.lock` は gitignore 対象で権威ではない）。
- **tick は 1 系統であり、120 回/秒は画面の更新周期そのものである。** フレーム駆動は `crates/wintf/src/runtime/tick_bridge.rs:114-134` の vblank 検出スレッド（`DwmFlush` 待ち→全リスナ起床）と、起床ごとに 1 フレームを回す UI スレッドの非同期ループ（同 `:218-236`）の 1 系統だけで、同 `:142-146` が「固定周期ではない。実効のフレーム周期は画面の更新周期である（120Hz の実機なら約 8.3ms）」と明記している。brief 候補 C が疑った「16ms 設定なのに 120 回/秒＝二重起床」は現行ツリーに根拠が無い——wintf に 16ms の定数も Win32 タイマも無く、旧経路 `try_tick_on_vsync`（`crates/wintf/src/ecs/world/mod.rs:580`）は起床カウンタの生産者が撤去済みで常に tick しない（`ecs/world/vsync.rs:17-22` の注記）。
- **1 tick の中身に早期脱出は無い。** `EcsWorld::try_tick_world`（`ecs/world/mod.rs:488-566`）は、システム未登録の場合を除き、毎 tick 無条件にフレーム番号を進め、13 本のスケジュールを固定順に `try_run_schedule` する（`:548-560`・順序不変の既存テスト `:657`）。「変化が無い tick を見分ける」判断は現在どこにも存在しない。
- **13 本のうち 7 本は多スレッド実行器で走る。** ワークスペース `Cargo.toml:48-56` が `bevy_ecs` の `multi_threaded` を有効化しているため `Schedule::new` の既定実行器は多スレッドであり、`ecs/world/mod.rs:104-160` が `SingleThreadedExecutor` へ固定しているのは UISetup／GraphicsSetup／PreRenderSurface／RenderSurface／Composition／CommitComposition の 6 本だけ（同 `:117,135,141,146,151,156`）。Input／Update／PreLayout／Layout／PostLayout／Draw／FrameFinalize の 7 本は tick のたびにタスクプールの scope を開く多スレッド実行器のまま（`bevy_ecs-0.19.1` `executor/multi_threaded.rs:274`）。この固定費の大きさはループの計測で確定する（更新前の実測には内訳が無い）。
- **FrameFinalize の中身は大半が areka 側である。** `emo2_frame_system`（`crates/areka/src/emo2_boot/frame.rs:158-233`）が毎フレーム走り、talk の時刻起点が一度確立すると文字層の提示 `present_actor`（`crates/areka-emo-text/src/actor.rs:744-805`）が**毎フレーム行レイアウトを再計算**する（swap chain の Present は変化時のみ）。`visual_hierarchy_sync_system`（`graphics/systems/visual_sync.rs:25-70`・全 visual を毎回走査）・`clear_transient_pointer_state`（`pointer/systems.rs:17-31`・毎回書込）も定常で本体が走る。
- **クリック透過の評価は tick と独立に vblank 起床で動く。** `crates/wintf/src/runtime/mod.rs:230-236` は「(b) VSync tick 毎の再評価（静止カーソルでも表示更新＝αマスク変化に追随／R2.4）」を理由として記し、vblank ごとに評価ループを起こす中継を `:296-330` に持つ。評価ループ（`crates/wintf/src/ecs/clickthrough/controller.rs:421-457`）はこの vblank 起床とカーソル監視（`clickthrough/monitor.rs:34`・12ms 周期）の二重起床で動く。tick を省略しても中継と評価は変わらず動く。
- **catch-up は ECS の tick ではなく進行のティッカーが出す。** 判定式⑵ が数える文言 `ticker catch-up: skipped multiple boundaries, firing once`／`loop ticker catch-up: …` の発行元は `crates/areka-ghost/src/ticker.rs:205,225,307`（dispatcher／kanade／SERIKO ループの 3 系統）で、周期は系統ごとに異なる——dispatcher `base_interval = 50ms`（同 `:61`）・kanade `kanade_interval = 1000ms`（同 `:62`）・SERIKO ループ `16ms`（同 `:262`）。ティッカーは UI スレッドではなく自前のアクタースレッドで `recv_timeout` により起きる（同 `:194,297`）ので、catch-up は「ティッカースレッドが 1 周期以上遅く起きた」ことを意味し、フレーム駆動の負荷は CPU 競合による起床遅延としてしか効かない（間接）。ループ ticker の 16ms は Windows 既定のタイマ分解能（約 15.6ms）に近く、起床遅れだけで 2 境界を跨ぎ得る。
- **一括 flush の前提は atom 着地後の実形である。** 窓書込は同一窓のジオメトリ指令が積む時点で合流し（`crates/wintf/src/ecs/window/command.rs:514-560`）、1 バッチで一括適用され（同 `:349-440`・`SetWindowPosCommand::flush` は `:723`）、Z 専用指令は合流の対象外で順序・結果が不変である（brief 追記(71)⑶・(74)⑷・(78)⑺）。
- **観測・計測の道具。** 既定 OFF の観測チャネル `wintf::transition`（`crates/wintf/src/ecs/window/transition_diag.rs:54`・前置ガード `:622` で既定水準の費用 0）、`perf(apply_show)` 段階別計時行（`crates/areka-emo-present/src/presenter/timing.rs:56,221`・末尾 `frame` 込み 16 フィールド）、採取ランナー `tools/perf/invoke-perf-run.ps1`（短時間 7 分／長時間 25 分・`-ConfirmQuiet` 必須・プロセス単位の `% Processor Time`）、判定スクリプト `tools/perf/judge-perf.py`（0.3.2・`IDLE_CPU_MAX_RELEASE_PCT = 3.0`・`WARMUP_EXCLUDE_SEC = 60.0`・`LONG_RUN_MIN_SPAN_SEC = 1200`・自己較正 fixture 17 件）。**スレッド別・関数別の帰属を出す道具は現状無い。** 一方、測定マシンには **Windows Performance Toolkit（`wpr.exe`・`xperf.exe`）が実在**し（2026-08-22 確認・`C:\Program Files (x86)\Windows Kits\10\Windows Performance Toolkit\`）、CPU サンプリングと呼出スタックの採取が可能である。release ビルド（`Cargo.toml:96-102`・`opt-level='z'`・`lto=true`・`strip=false`）はデバッグ情報の指定が無く PDB が出ないが、ビルド時の環境変数 `CARGO_PROFILE_RELEASE_DEBUG`（例 `line-tables-only`）で `Cargo.toml` に触れずに関数名を引ける形にできる。
- **SSP 側の値は 2026-08-15 の実測（アイドル 3.05%・発話の頂 4.64%）を参考値として使い、SSP の描き方は調べない**（2026-08-22 開発者裁定＝議題 2）。

### ウェーブ配置と同居裁定

本 spec は **W6.9** で `areka-P0-test-cage-determinism`（cage）と並走の予定だが、**2026-08-22 時点で本 spec 以外にコード修正を伴う spec は動いていない**（開発者裁定＝議題 1）。同居裁定: **`crates/wintf/src/ecs/window/command.rs` は丸ごと本 spec 所有**。`SELF_INITIATED_DEPTH`（同 `:49`・プロセス共有の `AtomicI32` だが意味論はスレッド局所＝テスト間の状態汚染源）のスレッド局所化も本 spec が実施し、着地形を cage へ申し送る。

## Boundary Context

- **In scope**:
  - **自走改善ループの仕組み**（目標の定義・1 周の手順・記録・停止条件。起動口は組み込み `/goal`）の構築と、その実施
  - **「どこが重いか」を突き止める計測手段**（プロセス→スレッド→関数→フレーム駆動の相、の順に絞る解析手順と道具）の整備
  - フレーム駆動の周期と、表示に変化が無いときの早期脱出（wintf のフレーム駆動＝`runtime`／`ecs::world`・一括 flush の駆動を含む）
  - 上位に出た処理の是正。**調査の範囲は制限しない**（2026-08-22 開発者裁定）。是正も、担当する生存 spec が無い場所であれば本 spec で行ってよい。直した場所は改訂欄に登記する。将来の spec が予定しているファイル（`present-write-coherence`＝`presenter/show.rs`・`mount.rs`／`balloon-offset-dpi`＝`placement/follow` 系・`windowposition.rs`・`persist.rs`／`test-cage-determinism`＝テストハーネス）に触った場合は、その spec の brief へ申し送る
  - 見た目の追随（クリック透過・αマスク・ドラッグ・DPI 追随・バルーン追従・Z 順）を劣化させないことの固定
  - 目標（CPU の絶対値）と SSP 参考値の登記（測り方の記録を含む）
  - `command.rs` 1 ファイルの所有（`SELF_INITIATED_DEPTH` のスレッド局所化を含む）
- **Out of scope**:
  - 合成アルゴリズム本体（`build_plan`／`blit::execute`）の作り直し
  - メモリ常駐量の削減・スレッド数の削減（計測で CPU との因果が出た場合は是正対象に入れてよい）
  - 発話（talk）そのものの処理コスト（山の高さは発話の実装に依存）。ただし計測では切り分けて記録する
  - DPI 遷移フレームの窓書込所要（窓書込呼出の内側・1 遷移 143,231〜231,910µs）——遷移フレームは「定常状態の CPU」とは別の山であり、平均に混ぜない。遷移中の「絵が先・窓が後」は `present-write-coherence` 所有
  - SSP との完全一致、および **SSP の描画方式（実描画か引き伸ばしか）の調査**（2026-08-22 開発者裁定＝調べようがない。目標は画素数で正規化せず CPU の絶対値で置く）
  - テストハーネスの一本化・テスト間の状態汚染の全面硬化（cage 所有。本 spec は `command.rs` 側の 1 行のみ）
- **Adjacent expectations**:
  - `areka-P0-recompose-budget`（完了）: 測定基盤 `tools/perf/`（採取ランナー・判定スクリプト 0.3.2・fixture 17 件）と判定式⑴〜⑷b・「2 分以下の窓を採らない」「比較は同一セッション内の交互取得」「実時間閾値はテストコードへ持ち込まず判定スクリプト側の較正値とする」をそのまま継承する
  - `areka-P0-dpi-transition-atomicity`（完了）: 一括 flush の実形（合流・1 バッチ適用・Z 指令不合流・観測チャネル `wintf::transition`・perf 行末尾 `frame`）を前提とし、設計前に origin/main の実形へ rebase する。同 spec の決定論 8 遷移は本 spec 着地後も PASS のままであること。未特定の 47.5% 区間と文字層再構築（遷移フレーム内）は申し送りとして受けるが、遷移フレームの山であり本 spec の合否には載せない
  - `areka-P0-test-cage-determinism`（W6.9 並走予定）: `command.rs` は本 spec 所有。`SELF_INITIATED_DEPTH` の着地形（または見送り）を本 spec から cage へ申し送る
  - `areka-P0-present-write-coherence`（W6.95）: 本 spec が着地させた tick の実形の上で規模を見積もる。本 spec が tick 構造を変えた場合は申し送る
  - `areka-P0-emo2-conformance-e2e`（W7）・`ghost-window-zorder`（完了）: Z 指令の適用順と結果が現に決まる場所は一括 flush であり本 spec の In-scope にある。本 spec は Z 順の不変条件を壊さない責務を負う
  - `collision-dpi-hittest`（完了）: クリック透過の評価タイミングを共有する。「VSync tick 毎の再評価」（R2.4）の前提を本 spec が調停する

## Requirements

### Requirement 1: 自走改善ループの仕組み（goal 駆動）

**Objective:** As a 開発者, I want 目標を 1 か所に置き、そこへ至るまでの「測る→突き止める→直す→測り直す」をエージェントが自走で繰り返す仕組みがほしい, so that 私が裁定や作業で途中に入らなくても、負荷の是正が目標達成まで進む

#### Acceptance Criteria

1. The 改善ループ shall 目標（goal）を機械判定できる形で 1 つの定義ファイルに置く（内容: 判定式⑴〜⑷b と release アイドル CPU 3.0% 未満・判定スクリプトの版・測定水準）。ループはこの定義だけを読んで合否を決め、人の判断を合否に使わない
2. The 改善ループ shall 1 周を次の順で回す: ⒜ 計測（Requirement 2 の手段で採取）→ ⒝ 解析（重い場所の順位表を作る）→ ⒞ 仮説と変更の選択（順位表の上位から 1 つ）→ ⒟ 実装 → ⒠ テスト（ワークスペース全テスト緑・見た目の追随テスト緑）→ ⒡ 再計測（変更前後を同一セッション内で交互に比べる）→ ⒢ 採否（改善すれば採用しコミット、改善しなければ元へ戻す）→ ⒣ 記録。**どの段階でも開発者の裁定・確認・作業を要求しない**
3. The 改善ループ shall 各周の記録（周番号・日時・仮説・変更したファイル・前後の数値・採否とその根拠・所要時間）を spec ディレクトリの台帳 1 ファイルへ追記し、後から誰が読んでも同じ結論に至れる形にする
4. The 改善ループ shall 停止条件を持つ: ⒜ 目標達成（長時間水準＝25 分の最終判定で全判定式 PASS）、⒝ 連続 N 周（既定 3）で採用に至る改善が無い（頭打ち）、⒞ 安全上の理由（テストが赤で元へ戻せない・計測の道具が壊れた・周数が上限〔既定 30・目標定義ファイルの `[stop]` で変更可〕に達した）。停止したら理由と到達点（どこまで下がったか・残る最大項は何か）を報告する
5. While ループが回っている, the 改善ループ shall 開発者の関与を「開始の指示」と「停止後の報告の受領」の 2 点に限り、静寂確認・実機サインオフの立会い・大改造の可否判断・目標の置き直しを途中で開発者に求めない（必要な判断はルール化してループ内で行い、判断の根拠を台帳に残す）
6. The 改善ループ shall 起動口として Claude Code の組み込み **`/goal`** を使う（2026-08-22 裁定・公式文書 `code.claude.com/docs/en/goal.md` で確認: 条件文は 4,000 字以内・毎ターン終了時に小型モデル（既定 Haiku）が**会話に現れた内容だけ**を見て「未達／達成／不可能」を判定・背景実行中は判定を後回しにし終了結果を新しいターンとして届ける・30 分で check-in（`CLAUDE_CODE_GOAL_CHECKIN_MINUTES` で変更可）・再開時に条件を復元・`-p` 非対話でも動く・主モデルを問わない＝**Opus 5 で実行できる**・hooks が無効だと使えない〔本リポジトリの設定に `disableAllHooks` 無し＝使える〕）。`/loop` は間隔駆動で目標判定を持たず 7 日で失効するため採らない。本 spec は `/goal` を新設せず、`/goal` に渡す目標文（テンプレート）と 1 周の手順（プロジェクトスキル）と道具を用意する。目標定義と道具は本 spec の性能目標に限らず、別の目標でも同じ手順で回せる汎用の形を保つ
7. If ループの 1 周で「変化前後の差が計測のばらつきの範囲内」と判定された, the 改善ループ shall その変更を採用せず元へ戻し、台帳に「差なし」として残す（ばらつきの大きさは同一形を 2 回測って得た差を基準にする）
8. The 改善ループ shall 1 周ごとに origin/main との乖離をコミット単位で残し（採用した変更だけが残る）、途中停止しても採用済みの改善と台帳が失われない
9. The 改善ループ shall 1 周の終わりに、判定に要る事実（判定スクリプトの合否行・前後の数値・採否・周番号・残り周数）を**決まった書式の 1〜数行で会話に表示**する（`/goal` の判定役は会話に現れたものしか見ないため。ファイルに書いただけでは判定されない）。達成条件の文は、この表示行の文言をそのまま確認できる形で書く
10. The 改善ループ shall 1 周の手順を、メインのモデルを問わず（Fable でも Opus 5 でも）毎ターン同じ順で実行できるようプロジェクトスキル（`.claude/skills/` 配下）として明文化し、`/goal` の条件文からそのスキル名を指す。手順の判断はすべて台帳と道具の出力に基づき、会話の記憶に頼らない（再開・要約後でも台帳から続きが回る）
11. While 計測を背景で走らせている, the 改善ループ shall 計測の所要（7 分・25 分）が check-in 間隔を超えないよう `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` を設定し、計測の結果行が背景タスクの終了で会話に届く形（標準出力へ結果行を印字）にする

The 改善ループ shall モデルの使い分けを仕組みで固定する——メイン（`/goal` の各ターンを回し、判断と采配を行う側）はセッション起動時の設定に従い（README に「Fable で起動」を記す。spec の中からは変えられない）、重い作業（計測の実行・プロファイルの順位表作成・実装とテスト・差し戻し判定）は役割別のサブエージェント定義（`.claude/agents/` 配下・frontmatter `model: opus`）へ委ね、**サブエージェントは誰が呼んでも Opus 以下で動く**ようにする。サブエージェントは結論だけを返し、メインの文脈を小さく保つ（2026-08-22 開発者指示＝トークン節約・重要な判断とオーケストレーションは Fable）

### Requirement 2: 「どこが重いか」を突き止める計測手段

**Objective:** As a エージェント, I want 人の勘に頼らず、計測だけで「重い場所」を順位付けできる道具と手順がほしい, so that ループの ⒝ 解析を毎周同じやり方で機械的に行える

#### Acceptance Criteria

1. The 計測 shall 「プロセス全体 → スレッド別 → 関数・コード領域別 → フレーム駆動の相別」の 4 段で CPU の帰属を絞り、各段の順位表（上位 N・占有率・1 秒あたりの回数）をテキストで出す。エージェントはこの順位表だけを読んで次の仮説を選ぶ
2. The 計測 shall プロセス全体の CPU を既存の採取ランナー（`% Processor Time`・1 コア換算）で採り、判定スクリプト 0.3.2 の判定式と較正値をそのまま使う
3. The 計測 shall スレッド別の CPU 時間を同じ走行から得る（候補: `GetThreadTimes`／`QueryThreadCycleTime` を走行終了時または周期的に記録、または ETW のコンテキストスイッチ記録）。スレッドには役割名（UI・vblank 検出・カーソル監視・ticker 3 系統・タスクプール）を付けて読める形にする
4. The 計測 shall 関数・コード領域別の帰属を **CPU サンプリング＋呼出スタック**で得る。道具は測定マシンに実在する Windows Performance Toolkit（`wpr.exe`／`xperf.exe`）を第一候補とし、採取→記号解決→上位スタックの一覧（テキスト）まで**1 コマンド**で出す。release ビルドの記号は `CARGO_PROFILE_RELEASE_DEBUG` 等のビルド時指定で付与し、`Cargo.toml` には触れない
5. The 計測 shall フレーム駆動の相別の所要（tick 1 回の所要・13 本のスケジュール別・「表示に変化が無い tick」の割合・tick 回数/秒）を既定 OFF の観測行として出し、有効化していないときは組立も計時も行わない（前置ガード）
6. The 計測 shall 壁時計（経過時間）と CPU 時間を区別して記録し、GPU 待ちなどの待ち時間が混入する量を「壁時計」と明記する
7. The 計測 shall 測定の窓を二水準で使い分ける: 順位付け（⒝）と 1 周の採否（⒡）は短時間水準（7 分・同一セッション内の交互取得）、ベースライン（ループの 1 周目）と最終判定は長時間水準（25 分）。2 分以下の窓は採らない（同一条件で 5.37% と 18.57% に振れた実測あり）
8. The 計測 shall 静寂確認を自動化する——採取の前後でマシン全体の CPU と既知の重いプロセス（ビルド・テスト・別の areka）の有無を記録し、閾値を超えていれば採取をやり直す。人に確認を求めない
9. When catch-up（判定式⑵）を数える, the 計測 shall 発行元 3 系統（dispatcher／kanade／SERIKO ループ）別に数え、各発生の時刻と同時刻の状況（発話再生中か・表示 1 コマの適用直後か・tick 所要の山と重なるか）を突合できる形で記録する。「フレーム駆動の負荷が CPU 競合でティッカーの起床を遅らせる」という因果は仮説であり、成立・不成立を数値で記す
10. The 計測 shall 全段の採取・集計・順位表出力を 1 つの入口（スクリプト）から回せるようにし、出力のフォーマットを決定論的（同じ入力なら同じ文面）にする
11. If 計測の道具が壊れている（採取が空・記号解決が失敗・判定スクリプトの自己較正が赤）, the 計測 shall 黙って続けず、エラーを記録してその周を「計測失敗」として止める（既知ケースで毎回赤も作って道具を較正する）
12. When 新たな計測行を出す, the 計測 shall 1 行に同じフィールド名を 2 度出さず、既存の perf 行・遷移観測行のフィールド名・順序・文言を動かさず、追加は末尾に限る（判定スクリプトの `parse_fields` が後勝ちで上書きするため）

### Requirement 3: 是正の自律実行（候補の選び方と安全側の規則）

**Objective:** As a エージェント, I want 順位表の上位から仮説を選んで直し、効かなければ戻す規則を持ちたい, so that 開発者の裁定を待たずに是正を進められ、悪化を持ち込まない

#### Acceptance Criteria

1. When 仮説を選ぶ, the 改善ループ shall 順位表の最上位から順に選び、選ばなかった理由（別 spec が現に動いている場所・Out of scope・既に試して差なし）を台帳に残す
2. The 改善ループ shall 「表示に変化が無い（表示 1 コマの適用・入力・アニメ境界の跨ぎ・窓ジオメトリ変更・DPI 変更・Z 順変更のいずれも無い）とき、フレーム駆動が 13 本のスケジュールを全部回す費用を払わない」を候補の 1 つとして持つ。採る場合、変化が生じたら次の画面更新までに反映し（遅れの上限は 1 画面更新周期＝120Hz 実機なら約 8.3ms）、判定の入力を列挙して文書化し、疑わしいときは回す
3. The 改善ループ shall 「多スレッド実行器 7 本の見直し」「毎フレーム走る areka 側の処理（文字層レイアウトの再計算・全 visual の走査・ポインタ状態の毎回書込）の変化時のみ化」「tick 外の周期処理（カーソル監視 12ms・ループ ticker 16ms）の見直し」を候補として持ち、順位表の結果で選ぶ
4. The 改善ループ shall 13 本のスケジュールの実行順序と、スケジュール間・スケジュール内の既存の順序不変条件を、変化が有る tick において変えない
5. When 一括 flush の駆動・間引き・順序に手を入れる, the 改善ループ shall Z 専用指令の適用順と結果（合流の対象外・畳めない指令は同一窓の仕切り）を変えず、既存の不合流テスト群を緑のまま保つ。「ウィンドウプロシージャ側が Z 指令を積まない」という現状の前提（コードが強制していない）を文書化し、改変がこれに依存する場合は依存を明記する
6. If 変更が大きい（スケジュール構成や駆動モデルの作り直しに及ぶ）, the 改善ループ shall 開発者裁定を待たずに次の規則で決める——⒜ 全テスト緑 ⒝ 見た目の追随（Requirement 4）を保つ ⒞ 交互比較で改善が計測のばらつきを超える、の 3 つを満たせば採用し、満たさなければ元へ戻す。規模とリスクの見立ては台帳に残す
7. If 是正の実装に失敗経路（判定の入力が取れない・観測が組めない等）がある, the フレーム駆動 shall 黙って省略せず、ログを残して安全側（回す）へ倒す
8. While 表示に変化が無い, the フレーム駆動 shall 既定で観測の費用を払わない（新設する観測は既定 OFF）

### Requirement 4: 見た目の追随を劣化させない

**Objective:** As a ユーザー, I want 省電力化のあとも、クリックの通り抜け・ドラッグ・DPI 切替・バルーンの追従・窓の前後関係が今までどおり即座に反応してほしい, so that 軽くなった代わりに反応が鈍くなったと感じない

#### Acceptance Criteria

1. When 表示内容が変わって透明画素の分布（αマスク）が変わる, the クリック透過 shall 変化した画面更新の次の画面更新までに新しいマスクで判定する（現行の「VSync tick 毎の再評価」と同等。静止カーソルでも追随する）
2. When カーソルが動く, the クリック透過 shall 現行と同じ周期（カーソル監視の周期）で再評価し、フレーム駆動の間引きに引きずられて遅れない
3. While 窓をドラッグしている, the フレーム駆動 shall 変化ありとして毎画面更新で回り、窓とバルーンの追従が現行と同じ滑らかさを保つ
4. When DPI 遷移が起きる, the フレーム駆動 shall 変化ありとして回り、`dpi-transition-atomicity` が固定した決定論 8 遷移がすべて PASS のままであること
5. When バルーンの表示・非表示・位置追従・Z 順の維持が要求される, the フレーム駆動 shall 変化ありとして回り、`ghost-window-zorder`／`scope-chain-gap`／`windowposition-limit` が固定した既存テストがすべて緑のままであること
6. When 発話（talk）が再生中である, the フレーム駆動 shall コマ境界・タイプライタ進行・表情の切替を現行と同じタイミングで反映する（判定式⑴ コマ適用間隔の p95 が退行しない）
7. When 1 周の採否を決める, the 改善ループ shall クリック透過（透明画素上のクリックが別プロセスへ通り抜ける／不透明画素上では通らない）・ドラッグ追従・DPI 切替・バルーン追従を、有界の自動終了付き実走とログ照合で**エージェントが自分で**確認し、目視や開発者の立会いに頼らない

### Requirement 5: 目標と合格判定（機械判定）

**Objective:** As a 開発者, I want 目標を CPU の絶対値で置き、是正の効果を先行 spec と同じ判定スクリプトで機械判定したい, so that 合否に人の目視や主観が要らず、目標が議論で動かない

#### Acceptance Criteria

1. The 開発プロセス shall 目標を **CPU の絶対値**で置く——release ビルドでゴースト放置時のアイドル CPU（1 コア換算・定常状態の平均）が **3.0% 未満**（先行 spec 4.4 の較正値 `IDLE_CPU_MAX_RELEASE_PCT = 3.0`・狭義の未満比較を継承）。画素数や描画方式の差で正規化した目標は置かない（2026-08-22 開発者裁定: SSP は GDI 描画・areka は D2D 描画であり、areka が負けるわけにはいかない）
2. The 開発プロセス shall SSP の描画方式を調査の対象にせず、目標の根拠にも使わない（同裁定: SSP について分かっているのは CPU が 3% 台であることだけで、調べようがない）。SSP 側の参考値（2026-08-15 実測・アイドル 3.05%・発話の頂 4.64%）は判定スクリプトの較正値の注記と `tools/perf/README.md` に登記し、SSP 側の再採取を要件としない
3. The 判定スクリプト shall 先行 spec の判定式をそのまま適用する: ⑴ コマ適用間隔の p95 が指定間隔＋許容率以内（退行しない）⑵ 定常状態の catch-up 0 件 ⑶ 定常状態の表示用バッファ新規確保 0 件（退行しない）⑷a release アイドル CPU が 3.0% 未満 ⑷b 20 分超で単調上昇しない。⑴〜⑶ を dev・release 両ビルドに、⑷a・⑷b を release に適用する
4. The 開発プロセス shall 発話中の CPU の頂を SSP 参考値の頂（4.64%）と並べて記録し、合否には載せない。頂が参考値を大きく超える場合は機序を記録する
5. The areka 実行体 shall メモリリークと負荷の単調上昇を再発させない（Private メモリ・ハンドル数・スレッド数が 25 分走行で増加傾向を示さず、⑷b の収束判定を満たす）
6. When 最終判定を行う, the 改善ループ shall 長時間水準（25 分）で release／dev を採取し、判定スクリプトの出力を spec ディレクトリへ保存する
7. If ループが頭打ちで停止し判定式⑵ または ⑷a が未達のまま残る, the 開発プロセス shall 未達を本 spec の requirements.md に改訂欄として登記し、残る最大項と引受先を明記する（「未達が spec の内側から見えない」形を繰り返さない）
8. When 較正値（`WARMUP_EXCLUDE_SEC` ほか）を見直す, the 判定スクリプト shall 見直しの根拠を較正値の注記に残し、自己較正 fixture で既知ケースの合否が変わらないことを確かめる
9. The 開発プロセス shall 目標（CPU 絶対値 3.0% 未満）とその根拠を `doc/COMPAT_ARCHITECTURE.md` へ「areka 裁量の性能目標」として登記する

### Requirement 6: 判断分岐の決定論テスト

**Objective:** As a 開発者, I want 「変化の有無の判定」「回すスケジュールの選択」「ループの採否規則」といった判断分岐を実機なしで全網羅したい, so that 実機でしか分からない領域を最小にして回帰を固定できる

2. The テスト shall 省略した tick の直後に変化が生じたとき、次の tick で反映されること（省略が反映の遅れとして残らないこと）を決定論テストで固定する
3. The テスト shall 13 本のスケジュールの実行順序の不変条件（既存テスト）を維持し、省略経路でも順序が入れ替わらないことを固定する

6. When `SELF_INITIATED_DEPTH` をスレッド局所化する, the テスト shall 並列実行でテスト間の状態汚染が起きないことを固定し、錠 `lock_self_initiated_for_test()` の退役可否を cage へ申し送る
7. The テスト shall ループの採否規則（改善あり／差なし／悪化・テスト赤・計測失敗）と解析の順位表生成（入力ログ→順位表）を、実機ログの fixture を使った決定論テスト（判定スクリプトの自己較正と同じ形）で固定する
8. The テスト shall 新規・既存とも 1 ファイル 1,000 行以下の目安と、テストファイルを本番ファイルの兄弟として置く接続規約に従う
