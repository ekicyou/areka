# Brief: wintf-visual-damage-redraw

> 2026-10-21 `/kiro-discovery` で起票。下の「推す形」と「議題」は、着手のときの要件の段で覆してよい。
>
> 出どころ（2026-10-21 開発者）: 「現在、`crates\wintf\src\ecs\visual` 層のコード群は実装準備されているが採用されていない。これらを新しいビジュアル層・描画層として取り込んでほしい。D2D合成の多様化に必要と考える。このコード群で実現可能と思われる機能を推測し、必要な改善を行うスペックを起票せよ。実施フェーズはwintf/dola改修のタイミングとする。」
> 同じ日の答え: 起票は 2 本に分ける（`wintf-visual-tree`＝描画の木を本番へ上げる・本 spec＝差分の描き直し）。

## Problem

- `wintf-visual-tree` が着地すると、描画面ごとに描画の木を 1 枚へ描けるが、描くのは毎回全部（木の 1 節が変わっても、描画面の全部を描き直す）。emo のシェルの合成を描画の木へ移す（`draw-methods-canon`）と、まばたき 1 コマのたびに全部の部品を描き直すことになる。
- 開発者が `ecs/visual/` に用意した構想（`draw/README.md`「visual描画戦略」・`version.rs` の注記）は、この無駄を避けるためのもの: 前フレームと今フレームの描く列を `u64` の hash の列として比べ、最長増加部分列（LIS）で足された・消えた・動いた件を見つけ、変わった範囲だけを描き直す。見た目の版（`VisualVersion`）は変形では上げず、スクロールは写し（blit）で済ませる。今はどれも宣言だけで、作りは無い。

## Current State（起票時の実測・main `213a3747`）

- `draw/README.md`（48 行）は戦略の宣言と列挙の型だけ。比べ・描き直す範囲・写しの作りは無い。`crates/wintf/Cargo.toml` に LIS の依存は無い。
- `VisualVersion`（`version.rs`）は「描く中身・切り抜き・旗」の版で、変形では上げない約束（上げるとスクロールのたびに全部の節が変わったことになり、写しの段が意味を失う）。`Matrix3x2Ext::moved`（`numerics/matrix3x2.rs`）が許容つきで変形の動きを見る。
- `DrawItem` は `hash`・世界の行列・実体・世界の外接矩形を持つ（`draw/command.rs`）。hash の取り方の傷（COM の番地）は `wintf-visual-tree` が直す。
- **WUC の描画面は部分の矩形の `BeginDraw` を断る**（`ecs/graphics/systems/render.rs:60-61`・実測）。部分だけ描き直すには、描き先を WUC の描画面でなく自前の入れ物（`wintf-d2d-composite-rules` が作る合成の入れ物のテクスチャ）にして、変わった範囲だけそこへ描き、描画面へは写すだけにする必要がある。
- 先例: 文字の層（`areka-emo-text` の `surface.rs`）は自前のスワップチェーンで、前の面から後ろの面への写しでスクロールを済ませている（wintf の描画の道の外）。

## Desired Outcome

- 描画の木を持つ描画面で、前フレームから変わった節（足された・消えた・動いた・見た目の版が上がった）の外接矩形の和だけを描き直す。変わらないフレームは描かない。
- 描き直しの答えは、毎回全部描いた答えと画素で一致する（決定論のテストで固定・WARP）。
- 木の一部が平行移動しただけ（スクロール）のときは、写しで済ませて露出した帯だけを描く（要件の段で範囲を決める）。
- 描き直しの量（描いた件数・面積）を記録して、`present-emit-tail-latency` などの計測で効きを見られる。

## Approach

**推す形**（要件の段で覆してよい）:

1. **前の列を持つ**: 描画面の根ごとに前フレームの `DrawCommand` の列（hash の列）を持ち、今の列と比べる。比べ方は README のとおり LIS で「動かなかった件」を求め、それ以外を足された・消えた・動いたとする。
2. **描き直す範囲**: 変わった件の前と今の世界の外接矩形の和（切り抜きの出入りの組も数える）。範囲の外の件は描かない。範囲を切り抜きにして、範囲と交わる件を画家の順で描き直す。
3. **描き先**: `wintf-d2d-composite-rules` の自前の合成の入れ物に描き、描画面へは写す。入れ物が無い描画面（今の WUC の描画面だけ）は全部描く。
4. **スクロールの写し**: 木の一部が同じ量だけ平行移動したときは、入れ物の中で写してから露出した帯を描く。
5. **決定論のテスト**: 比べ（LIS）と範囲の計算は純粋なテスト。描き直しの画素は「毎回全部描いた答え」と一致することを WARP で確かめる。

**採らない方向（起票時）**:

- WUC の描画面に部分の `BeginDraw` で描く（実測で断られる）。
- 前フレームの答えを推して 1 フレーム遅らせる形（「1 フレーム遅らせる解は取らない」）。

## Scope

- **In**: 前フレームの列の保持・比べ（LIS）・描き直す範囲の計算・範囲だけの描き直し・スクロールの写し（要件で範囲を決める）・描き直しの量の記録・決定論のテスト。LIS の作り（自前か依存か）。
- **Out**: 描画の木の本番化と傷の直し（`wintf-visual-tree`）／自前の合成の入れ物そのもの（`wintf-d2d-composite-rules`）／文字の層のスクロール（`areka-emo-text` の自前のスワップチェーン＝寄せるかは別件）／`VisualFlags` の `CACHE_AS_BITMAP`（部分木を絵に焼いて使い回す＝別の機能。要るなら別に起票）。

## Boundary Candidates

- 比べ（前と今の列 → 足された・消えた・動いた件）＝純粋な計算。
- 描き直す範囲（件 → 矩形の和）＝純粋な計算。
- 範囲だけの描き直しと写し（D2D の装置・自前の入れ物）。

## Out of Boundary

- 何を描くか（描画の木の中身・emo の合成）。
- 描画面へいつ出すか（WUC の commit・`dola` の時刻）。

## Upstream / Downstream

- **Upstream**: `wintf-visual-tree`（`DrawCommand` の列・`WorldVisual`・`VisualVersion`・hash の直し）・`wintf-d2d-composite-rules`（自前の合成の入れ物）。
- **Downstream**: `draw-methods-canon` 以後の emo のシェルの描画の負荷（まばたき 1 コマで描く量）。`tick-gate-adoption`（描かないフレームを作る話と組む）。

## Existing Spec Touchpoints

- **Extends**: なし（新しい spec）。
- **Adjacent**:
  - `wintf-d2d-composite-rules` — 自前の入れ物の形（大きさ・形式・描画面への写し方）を分け合う。あちらの後に着手する。
  - `compose-f16-precision` — 入れ物の形式が f16 になれば写しの形式も揃える。
  - `present-emit-tail-latency`（版に縛らない・測ることが本体）— 描き直しの量の記録を使える。

## Constraints

- **描き直しの答えは毎回全部描いた答えと画素で一致する**（ずれは欠陥）。決定論のテストは必達・WARP。
- **時刻は正確に扱う**・**1 フレーム遅らせる解は取らない**。
- **記録の無い失敗の道を作らない**。比べや範囲で困ったら全部描く方へ倒し、その理由を記録する。
- 依存（LIS の crate）を足すなら `tech.md` へ登記して開発者の承認を得る。数十行で書けるなら足さない。
- 1 ファイル 1,000 行の番人を越えない。

## 議題（着手のときに開発者へ・答えで作業が変わるもの）

1. **スクロールの写しを入れるか**: シェルの描画面にスクロールは無い。今の使い手で効くのは wintf のほかのウィジェット（将来のリストなど）だけ＝この spec に入れるか、使い手が出るまで外すか。
2. **描き直しの効きを測ってから入れるか**: emo のシェルを描画の木へ移した後（`draw-methods-canon` の後）に、全部描く負荷を測り、効きが小さければ据え置きにする選択肢。

## 件 1（2026-10-31 `animated-surface-log-flood` の申し送り）: ぱすたの面 1002 で、何もしていないあいだの CPU が SSP の約 3 倍

> 出どころ: `animated-surface-log-flood` の測り（`.kiro/specs/completed/animated-surface-log-flood/verification.md` のタスク 1 の「作る前の測り」の節〔「適用 1 回の所要を areka の CPU と比べる」〕と、タスク 5.2 の節〔「release の交互の測り直し」〕と、タスク 5.3 の「SSP の基準」）。同 spec の設計の判断 D4 は、wintf の全面の描き直しを縮めないと決めていた＝範囲の外として申し送る。場所と数は 2026-10-31 のもの＝着手時に引き直す。

### Problem

- ぱすた（`pasta-in-windows`）が面 1002（動く WebP の玉）を出したまま何もしていないあいだ、areka の release 版は 1 コアの約 15% を使う。同じ面の SSP 2.9.26 は約 5.6%。WorkingSet も areka 176 MB・SSP 94 MB と 2 倍近い。
- `animated-surface-log-flood` が直したのは記録の量と合成の範囲で、CPU の大半はそこに無かった。残りの大部分は、表示の適用（emo-present の `ShowSurface`）の perf の行が測る段の外で使われている。

### Current State（2026-10-31・`animated-surface-log-flood` の測り）

- areka の release 版・面 1002・何もしていないあいだの CPU（1 コアに対して・直す前と直した後を交互に 2 回ずつ）: 直す前 中央値 15.9%（最大 34.0%）・直した後 中央値 15.4%（最大 30.0%）。WorkingSet はどれも 176 MB のまま。
- SSP 2.9.26・面 1002（面の番号を SSTP で確かめた走り）: 中央値 5.6%・最大 7.2%（トークの行を除く 66 行）・WorkingSet 94 MB。
- 適用 1 回の所要（release 版・面 1002）: 全体 2,944 → 1,987 µs（合成 1,028 → 815 µs・当たりのマスク 203 → 178 µs）。コマ送りは毎秒約 14 回＝適用の全部で 1 コアの約 3%。areka の 15% のうち約 12 ポイントは適用の外にある。
- 適用の外で使われている所は測っていない。見込みは wintf の描画面の全面の描き直しと出す処理（present・DComp の commit）だが、動く絵のコマを進める処理（seriko・刻み）や記録を書く処理の分もありうる＝内訳は分からない。

### Desired Outcome

- 面 1002 で、何もしていないあいだの areka の CPU の内訳（emo-present の適用・wintf の描き直し・present・DComp の commit・seriko と刻み・そのほか）が数字で分かる。測りは `tools/perf/` の交互の手順で、単発の数字で判定しない。
- 内訳のうち描き直しと出す処理の分を本 spec の差分の描き直しで縮め、SSP の水準（中央値 5〜6%）を目標にする。届かなければ、残りの内訳と理由を数字で記録して開発者に仰ぐ。
- WorkingSet の差（176 MB と 94 MB）も内訳を測り、本 spec で縮められる分（描画面と入れ物の大きさ・形式）と、そうでない分を分けて記録する。

### Approach

1. **まず測る**: 面 1002 の何もしていない走りで、wintf の描画の系（`ecs/graphics/systems/render.rs` ほか）・present・DComp の commit・emo-present の適用・seriko の刻みに時間の印を足し、1 コマあたりの所要と CPU の割合を並べる。上の議題 2（効きを測ってから入れるか）の答えの材料にもなる。
2. 内訳で描き直しと出す処理が大きければ、本 spec の本体（変わった範囲だけを描き直す）でそこを縮め、前後を交互に測る。
3. 描き直しの外（刻み・seriko・記録）が大きいと分かったら、本 spec は測りと記録で閉じ、直しは別に起票する（`present-emit-tail-latency` の「分割の案」と同じ形）。

### Constraints

- 時刻は正確に扱う。コマ送りの回数を間引いて数字を下げる案は取らない（動く絵の再生の決まりは完了 `animated-image-playback` で確定）。
- 比べる相手は SSP の同じ面（面 1002）・同じ版（2.9.26 以上）。SSP の測りは `animated-surface-log-flood` の 5.3 の手順（面の番号を SSTP の `GetProperty` で毎行確かめる）で取り直してよい。
- 規模の見立て: 本文の 8〜12 に、測り 2〜3 タスク（印を足す・交互の測りと記録）を足す。
- 版: 本 spec は v0.2.0（`wintf-visual-tree`・`wintf-d2d-composite-rules` の後）。測りだけを先に取りたいときは、着手の前に開発者が決める（下の議題 3）。

### 議題（本文の議題に足す）

3. **測り（Approach の 1）を v0.2.0 の前に別に取るか**: 内訳が分かれば、描き直しが主因かどうか（＝本 spec で縮むか）が先に決まる。取らなければ、本 spec の着手のときに測る。
