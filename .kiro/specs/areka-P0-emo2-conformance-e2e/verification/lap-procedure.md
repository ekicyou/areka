## 0. 大前提（走行の前に読む）

### 0.1 消灯した観測点の沈黙を「起きなかったこと」の根拠に用いない（R5.7）

出力が 0 件であることは、それだけでは「起きなかった」を意味しない。**その観測点が本当に出力を出す状態だったのか**を先に確かめていなければ、0 件は「観測点が消えていた」と区別できない。

手順は次の 3 段で固定する。

1. **先に点灯を確かめる。** 判定に使うつもりの語ごとに、この走行の生ログの中に**その観測点が出した別の行**が 1 行でもあることを確かめ、記録の **§7 点灯確認**へ「観測点／点灯を確かめた方法／点灯していたか」を書く。
2. **確かめられたときだけ、0 件を根拠に使ってよい。**
3. **確かめられないときは、その 1 語だけを目視の宣言で代替し、代替したことを §7 に書く。** 代替を黙って行わない。代替を書かないまま次の項目へ進まない。

この規律が直に効くのは項目 20 の証跡 ⑴（接続失敗のログが 0 行）である。0 行を主張する欄なので、**同じ観測点が出す別の行**（後述 §5.7 の語の表）を先に見つけてから書く。

### 0.2 実測を目的とする他の仕様を並走させない（R5.9）

走行の間、この機械で**実測を目的とする別の仕様の走行を動かさない**。「動かしていないつもり」ではなく、**確かめる**。

この機械では複数の作業ツリーが同居しており（`git worktree list` で 10 本前後が並ぶ）、別のセッションがその一つで `cargo` を回していることがある。負荷は隣の作業ツリーからでも届く——本仕様の作業記録そのものが、高負荷のときに既存テストが名前つきで赤くなることを実測している（tasks.md「Implementation Notes」の負荷走行の項）。

確かめ方と記録:

1. `git worktree list` で作業ツリーを列挙し、
2. 走っている `cargo`／`rustc`／テスト実行体が 1 つも無いことを確かめ（**推測で `kill` しない**。自分が起こしたと確認できないプロセスは止めない）、
3. 記録の **§5 走行**の行「実測を目的とする他の仕様を並走させていないことの確認（R5.9）」へ、**確かめた方法と時刻**を書く。

**この作業ツリーで `cargo test` を回さない**ことも同じ理由で守る。決定論テストのゴースト検体は呼ばれるたびにゴースト側の永続状態を消す（`crates/areka/src/emo2_boot/spine.rs:483-489`）ため、走行 A と走行 B のあいだにテストを回すと**項目 12 の観測材料が消える**。

## 1. 証跡の分類（R5.4）

証跡は 3 種類あり、**混ぜて 1 つの欄に書かない**。記録 §8.1 の「根拠の種別」欄はこの 3 語のいずれかで埋める。

| 種別 | 何を書くか | 書いてはならないもの |
|---|---|---|
| **目視** | 誰が・いつ・何を見たか。段と操作を名指しする | 「たぶん出ていた」のような伝聞・推定 |
| **ログの引用** | 生ログの該当行の逐語と、その行が在るファイルと行番号 | 要約した言い換え |
| **機械判定の出力** | 判定の走行の出力（記録 §9 に全文を残し、§8.1 には結論の行を引く） | 出力を読んだ人の解釈 |

1 つの項目が 2 種以上の根拠を持つ場合は、**種別ごとに行を分ける**。3 語は記録 §0.2 の表と同じ語であり、**言い換えない**（言い換えると記録と手順書が静かにずれる）。

## 2. 準備

### 2.1 実行体を作り直す

サインオフの対象は**このコミットのビルド**である。古い実行体を黙って測ると「直っていないものを直った」と読む。走行の前に必ずビルドし直す。

```powershell
cargo build -p areka
```

ビルドしたコミットは記録 **§1 同定**の「コミット」へ書く。

### 2.2 32bit の橋渡し実行体を実バイナリの隣へ置く（**既知の罠・順序が効く**）

areka はゴーストの脳を、**自分の実行体と同じフォルダに置かれた** `shiori-host32-helper.exe` 経由で読み込む（`crates/areka/src/boot_config.rs:77-82`——`current_exe()` の親へこのファイル名を結合するだけであり、**別の場所を指させる環境変数は無い**。先例も同じことを書いている＝`crates/areka/src/placement/transition_judge_offset_signoff_tests.rs:62-65`）。この実行体は **32bit（i686）でなければならない**。

罠の姿はこうである。`shiori-host32-helper` はワークスペースの構成員なので、`cargo build --workspace` や `cargo test --workspace` を回すと **同じ名前の 64bit 版**が `target/debug/shiori-host32-helper.exe` へ上書きされる。64bit の実行体は 32bit の `pasta.dll` を読み込めないため、**ゴーストは起動するが一言も喋らない**。名前もパスも正しいまま中身だけが入れ替わるので、更新時刻やファイル名では気づけない。

ゆえに順序を固定する——**ワークスペースのビルド／テストを済ませた後に**、32bit 版を作って上書きする。

```powershell
cargo build -p shiori-host32-helper --target i686-pc-windows-msvc
Copy-Item "<リポジトリの絶対パス>\target\i686-pc-windows-msvc\debug\shiori-host32-helper.exe" "<リポジトリの絶対パス>\target\debug\shiori-host32-helper.exe" -Force
```

> **クロスターゲットのビルドは PowerShell で行う。** Git Bash から回すと GNU の `link.exe` が MSVC のリンカを覆い隠してリンクに失敗する。

置いた実行体の**中身**（PE ヘッダの machine 欄）で上書きを確かめる。**`014C` なら 32bit（i386）＝正しい。`8664` なら 64bit＝そのまま採取してはならない。**

```powershell
$HELPER = "<リポジトリの絶対パス>\target\debug\shiori-host32-helper.exe"
$fs = [IO.File]::OpenRead($HELPER); $br = New-Object IO.BinaryReader($fs)
$fs.Position = 0x3C; $pe = $br.ReadInt32(); $fs.Position = $pe + 4
'{0:X4}' -f $br.ReadUInt16()
$br.Close(); $fs.Close()
```

（手順と数値の出所: `crates/areka/src/placement/transition_judge_offset_signoff_tests.rs:79-94`）

確かめた値と、置いた実行体の絶対パスを記録 **§3 資産**の「実 32bit の脳」へ書く。

### 2.3 実拡大率を 96 dpi でない水準にする（R5.1）

ゴーストを載せるモニタの表示倍率を、**96 dpi でない水準**（125% / 150% / 200% など）に設定する。

**実効 DPI はアプリ自身のログで確かめる。** DPI 非対応のプロセスから読むと全モニタが 96 へ丸められ、200% の環境を 100% と読み違える（`crates/areka/src/placement/transition_judge_offset_signoff_tests.rs:24-25`）。走行後の生ログに現れる実効値を、記録 **§2 実機構成**の「各モニタの拡大率」へ書く。

モニタ台数・各モニタの解像度・作業領域の下端・主副の別・ゴーストが載っているモニタも同じ §2 へ書く。

### 2.4 記録置き場を新品にし、ゴーストの永続状態を消す

1. **ログの保存先**を新しい空のファイルにする（前回の採取が混ざると行数も引用も当てにならない）。絶対パスを記録 **§5 走行**へ書く。
2. **ゴーストスコープの永続状態を消す。** 消す対象は

   ```
   <ghost_root>\ghost\master\profile\areka\
   ```

   このフォルダには起動回数と窓位置が残る。残ったまま走ると boot が「2 回目起動」と判定して初回起動の系列が出ない（`crates/areka/src/emo2_boot/spine.rs:483-489`）。**項目 12 は「初回起動 → 再起動」の対比で観測する**ので、走行 A を初回起動にするためにここで消す。

   > **走行 A と走行 B のあいだでは消さない。** 消すと項目 12 の後半が観測できなくなる。§0.2 の「この作業ツリーで `cargo test` を回さない」も同じ理由である。

### 3.1 手順の出所

起動の正典手順は **`crates/areka/tests/emo2_real_run.rs` 冒頭のモジュール doc** に在る。本節はそこから導いたものであり、勝手に組み立てていない。

### 3.2 起動コマンド（逐語・そのまま貼れる形）

```powershell
$AREKA   = "<リポジトリの絶対パス>\target\debug\areka.exe"
$GHOST   = "<リポジトリの絶対パス>\crates\pilot\examples\shiori-host-32\fixtures\emo2"
$BALLOON = "<リポジトリの絶対パス>\crates\pilot\examples\shiori-host-32\fixtures\emo2\emo2-kakukaku"
$LOG     = "<記録置き場の絶対パス>\lap-run-a.log"

$env:RUST_LOG                = "info,kanade=trace,wintf::transition=debug,areka::placement::diag=debug,areka_emo_present=debug"
$env:AREKA_APP_SMOKE_EXIT_MS = "1800000"

& $AREKA $GHOST $BALLOON 2>&1 | Tee-Object -FilePath $LOG
```

**置き換える値**は 4 つだけである。

| 置き換える箇所 | 何を入れるか |
|---|---|
| `<リポジトリの絶対パス>` | サインオフ対象のコミットを持つ作業ツリーの絶対パス |
| `<記録置き場の絶対パス>` | §2.4 で新品にした保存先 |
| `$env:AREKA_APP_SMOKE_EXIT_MS` | 目視に要る時間。§5 の 20 段を一人で辿るには寛大に取る（例では 30 分） |
| `$env:RUST_LOG` | §3.3 の内訳を減らさない範囲で調整してよい。**実際に与えた文字列を逐語で**記録 §4 へ書く |

**すべて絶対パスで与える。** 相対パスだと脳の読み込みが `0x8007007E` で落ちる。ゴースト・バルーン・実バイナリの絶対パスは記録 **§3 資産**へ、起動コマンドの逐語は記録 **§5 走行**へ書く。

### 3.3 記録用の出力水準の内訳（なぜこの 5 語か）

| 指定 | 何を点灯させるか | 出所 |
|---|---|---|
| `info` | 既定の水準。接続失敗（`error!`）と正規の解放完了（`info!`）を捕らえる | `crates/areka/src/main.rs:136-141`（`RUST_LOG` 未設定時は `info` へ落ちる） |

## 5. 走行——20 項目の確認順

### 5.1 順序を決めている制約

順序を縛っているのは次の 6 つの制約である。ただし **6 つだけでは並びは一意に閉じない**——最終的に順序を一意に決めるのは下の A1〜A20 の表であり、各行の操作欄に理由を併記してある（理由を書けない隣り合わせが 2 組ある: A7 と A8、A12 と A13。どちらも入れ替えても制約に反しないが、表が並びを固定するので読み手が選ぶ余地は残らない）。

1. **項目 16 の直後に項目 19 を確かめる。** 拡大率の切替は再表示を伴うので、そこが再表示直後の重なり順を見る好機である（design D5 手順の 6・適合検証項目表 行 19 の末尾）。
2. **項目 18 は、こちらから窓を動かす前に見る。** 項目 18 の期待値には「操作で動かした窓を除く」但し書きが付いている（design.md の項目表 行 18 を見よ）。ゆえに項目 9（台本による位置調整）と項目 17（掴んで動かす）より**前**に置く。項目 18 は制約 1 の前後で 2 度見るので確認は 2 か所に分かれ、記録 §8.1 の行は**両方を見終えてから 1 度だけ**書く。
3. **項目 12 は再起動を跨ぐ。** 位置の永続化は「動かして終了 → 起動し直す」でしか観測できないので、**走行 A の終わり**と**走行 B**に分かれる。
4. **項目 7 の後半（選択肢の見た目の反転）は別走行にする。** 反転の注入は処理系の寿命で 1 度だけ焼き付く（`crates/areka/src/emo2_boot/hover_inject.rs:184-187` の `OnceLock`）ため、走行の途中で点けたり消したりできない。**走行 A・B では点けない**（design D5 環境変数の表）。点ける走行を**走行 C**として分ける。
5. **項目 20 は一点では成立しない。** 3 経路の同時成立を 3 つの証跡で示すので、走行 A 全体に跨がる（§5.6）。
6. **項目 16 の機械判定の入力は、一周とは別の専用採取で採る。** 7 行の合否ブロックの文法は「窓に一切触れず、2 つの拡大率水準を 3 往復以上切り替えるだけの採取」を前提にしている（`.kiro/specs/completed/areka-P0-dpi-transition-atomicity/signoff-procedure.md:309` の充足条件・同 `:317-322` の無効化チェック）。20 項目を触りながら回る一周のログはその前提を満たさない（理由は §5.4 の冒頭）。ゆえに拡大率遷移の機械判定の入力は**走行 D**（§5.4）で別に採り、走行 D は**走行 B の後・走行 C の前**に置く（design D5「走行の分割と走行 D」・2026-09-04 の開発者裁定）。**一周の側の項目 16（A9）は目視 1 回の観測としてそのまま残す**——走行 D の機械判定はそれを置き換えるものではなく、同じ項目 16 に対するもう 1 つの証跡である。

### 8.1 この表に載せない 2 つの変数（載せない理由）

`AREKA_WINTF_REAL_WINDOW_ZORDER`（`crates/wintf/src/ecs/window/zorder_pair_maintain_always_on_top_tests.rs:75`）と `AREKA_WINTF_VBLANK_DEADLINE`（`crates/wintf/src/runtime/tick_bridge.rs:307`）は、**この表に載せない**。

## 9. 中断したとき（R5.11）

走行が途中で成立しなくなったら、**そこで止める**。

1. **中断点**（どの走行の何番目の段か・何が成立しなかったか）を記録 **§13.3** へ書く。
2. **観測できたところまで**を §8.1 に残す。まだ見ていない項目の欄は `（未記入）` のままにする。
3. **中断した項目の結果は「中断」と書く。合格にも不合格にも数えない。**
4. **部分的な結果を合格として扱わない。** 1 段でも成立しなければ、その走行そのものが不合格である（R1.6）。

やり直すときは §2 の準備からもう一度行い、**新しいログの保存先**を使う。前の走行のログへ追記しない。
