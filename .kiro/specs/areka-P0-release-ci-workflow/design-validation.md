## まとめ

1 つの job・直列の段・公開を最後の段に置く形は、要件 8（成功 ⇔ 公開済み）をいちばん少ない仕掛けで守れており、配布スクリプトの約束（終了コード・置き場・名前）とも食い違いが無い。弱い所は「公開と後始末の段が初回の実走まで一度も動かない」ことと、その後始末が公開済みの Release も消す読み方の 2 点で、どちらも設計自身が残りとして書いている。足りないのは、消した後の扱いと、手元で先に通せる確かめの追加。

## 重要な指摘（3 件）

### 指摘 1: 後始末が公開済みの Release を消した後の扱いが書かれていない

- **気がかり**: S11 は、公開の直後に走りが取り消されたとき、4 つ揃って公開済みの Release も消す。要件 4.3 の条件は「作成または添付が途中で失敗した」で、公開まで済んだ物は字面ではこの条件に入らない。設計は要件 8.3（Release が在るのに結果が成功でない、を作らない）から読んでおり、筋は通るが、**消した後に同じタグの走りをやり直してよいか**が書かれていない。やり直すと S5 を通って公開し直すので、同じ版の zip が別の中身（別の SHA256）で出ることになる。`release-cycle` の「同じ版で出し直さない」とどう折り合うかが宙に浮いている。
- **効き**: 起きるのは人が取り消しを押した数秒の間だけで稀だが、消すのは取り返しのつかない操作。逆に消さない形にすると、Release は在るのに後段が永久に動かない（やり直しは S5 で止まる）ので、どちらを選んでも手当ての決まりが要る。
- **小さな穴**: 「成功以外で終わる走りは必ず無いへ戻す」は言い過ぎ。S10 が終わった後、`actions/checkout` の後処理の最中に取り消されると、S11 の条件はもう評価済みで動かず、Release は残って結果は取り消しになる。
- **勧め**: 設計の読み（下書きも公開も消す）のままでよい。次の 2 行を足す。①「S11 が消した後、同じタグの走りのやり直しは許す（一度も後段へ渡っていない版なので出し直しに当たらない）」か「許さず版を上げる」かを決めて書き、`release-cycle` へ申し送る。②「必ず」を「S11 が動いて成功した限り」に改め、後処理の最中の取り消しと S11 自身の失敗では残りうること、そのとき開発者が手で確かめることを Error Handling の表に足す。
- **要件**: 4.3・8.1・8.3・2.3
- **設計の場所**: 「公開と後始末の段（S10・S11）」の Responsibilities と Risks／「Release の状態」の図の下の 1 文／「Batch / Job Contract」の Idempotency

### 指摘 2: 初回の実走まで動かない部分のうち、手元で先に通せる物が残っている

- **気がかり**: 手元で回す確かめは S4 の 5 通りと S9 だけ。S5 の「一つ前のタグ」は、実行環境での走りの 1 点（`v0.0.1`）でしか確かめない。しかも比べ方が「PowerShell の版の型」としか書かれておらず、`[version]` で書くと `0.0.3-rc.1` の形の版（配布スクリプトは受け付ける形）を読めずに S5 が落ち、本番が止まる。S11 の「このタグの Release を探す」部分も S5 と同じ探し方なのに、別の本文として書かれ、一度も動かないまま初回を迎える。
- **効き**: S11 は消す操作を持つ唯一の段で、探し方を誤ると「消し漏れ」か「別の物を消す」になる。一つ前のタグを誤ると初回のノートが最初のコミットからの全部になる（要件 4.1）。どちらも初回の実走でしか見つからない。
- **勧め**: ① 版の比べは付記つきを読める型（PowerShell 7 の `[semver]`）と明記する。② S5 の一つ前のタグを決める部分を、タグの一覧を引数で受ける形にして手元で回す表を足す（`v0.0.1` だけ→`v0.0.1`／同じ版のタグしか無い→空／`v`・`vfoo` が混ざる→無視／付記つきの版）。③ S5 と S11 の「タグ名で Release を探す」呼び出しを 1 字違わず同じ行にし、静的な確かめに「2 か所が同じ」を足す。④ S11 の本文を、今の Release 0 件の状態で手元から 1 回回し「残っていない」で終わることを確かめる（読むだけで、何も消えない）。
- **要件**: 4.1・4.3・2.3・9.3
- **設計の場所**: 「検査の段（S4・S5）」の S5 の事後条件／Testing Strategy の「段の本文を手元で回す確かめ」「実走でしか確かめられない残り」

### 指摘 3: 作業の枝を押す前に確かめる前提が 1 つ抜けている

- **気がかり**: `.github/workflows/` の下のファイルを含む push は、押すのに使うトークンが workflow を書く権限（従来型なら `workflow` の範囲）を持たないと GitHub に断られる。手元の `gh` のトークンはこの範囲を持つ（`gh auth status` で確認）が、手元の origin が使うトークンは別物で、範囲は確かめていない（値に触れずには確かめられない）。設計の「実行環境での確かめ」は押すたびの了承だけを前提に書いている。
- **効き**: 断られると要件 9.1 の走りを始められず、最後の PR の push も同じ理由で止まる。トークンの範囲を変えるのは開発者にしかできない操作なので、実装の途中で初めて気付くと 1 往復ぶん止まる。失敗しても何も壊れない（押せないだけ）。
- **勧め**: 「実行環境での確かめ」の最初に「workflow のファイルを含む push が通ること。断られたら、どのトークンで押すかを開発者に決めてもらって止める（設定は変えない）」の 1 行を足す。あわせて、一時的なきっかけが在る間は workflow に関係の無い push でも数十分の走りが始まるので、「きっかけの行は、押す直前のコミットで足し、緑を見た次のコミットで外す」と順番を書いておく。
- **要件**: 9.1・9.2・6.1
- **設計の場所**: 「実行環境での確かめ」の Responsibilities & Constraints

## 小さな書き留め（話し合いの議題にするほどではない）

- 要件 6.2 の「リモートの URL を出さない」: `actions/checkout` は取り出しの記録に、トークンを含まない公開の URL（`https://github.com/{持ち主}/{名前}`）を自分で印字する。要件の趣旨（トークン入りの URL を出さない・一覧を印字する手順を持たない）には反しないが、静的な確かめ 2 では拾えないので、証跡に「出るのは公開の URL だけ」と 1 行書いておくとよい。
- S10 の `gh release create` は、取り出した作業ツリーのリモートから相手のリポジトリを推し量る。S5・S11 と同じく `GITHUB_REPOSITORY` を名指しで渡す（`--repo`）と、推し量りに頼らずに済む。
- 時間の上限を持たない段（S1・S2・S4・S7・S9）の分は「段の合計 130」に入っていない。余裕は 20 分あるので実害は無いが、「job の上限は段の上限より先に来ない」は「上限を持たない段が合わせて 20 分を超えない限り」と読むのが正しい。
- 日本語の印字の確かめは S4 の印字が最初の数分で出るので、化けていたら S8 を待たずに取り消して直せる（1 往復を短くできる）。

## 良い所

1. **公開を最後の普通の段に置き、後処理を持つ物を `actions/checkout` だけに絞った**。キャッシュを捨てたことで、要件 8.3（公開の後に失敗しうる手順を持たない）が「段の並びを見れば分かる」形になっている。時間切れを段ごとの上限で「段の失敗」に寄せた判断も、実行環境のソースで裏が取れる堅い選び方だった。
2. **実行環境での走りと最終の定義の差を「きっかけの行だけ」にする組み立て**。走りの種別を 1 つの値（`PUBLISH`）で分け、環境の記録の段を本番にも残すことで、要件 9.2 の確かめが `git diff` 1 回で済み、証跡の走りがそのまま本番の道（S1〜S9）の証明になる。
