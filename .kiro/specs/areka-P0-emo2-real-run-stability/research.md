# ギャップ分析: areka-P0-emo2-real-run-stability

> 2026-10-22・`kiro-validate-gap`。main `6e0ea8d8` の上のワークツリーで、確定した requirements.md と今のコードを突き合わせた。実機の走行・重いビルドはしていない（読むだけ）。

## 1. まとめ

- **件 1 は窓口の部品だけで書ける**。`real-run-kit` には「出力に文字列が出るまで待つ」`Run::wait_for`・「利用者と同じ閉じ方で閉じる」`Run::close`・終わり方の読み分け `EndedBy`（`UserClose`／`SafetyExit`／`Other`／`Unlogged`）・落ちた回の証拠が揃っている。試験 `crates/areka/tests/emo2_real_run.rs`（187 行）は今 `wait_exit()` で保険の自動終了 3 秒を待つだけなので、ここを `wait_for` → `close` に替えるのが本体。
- **保険の自動終了は「印まで」でなく「印まで＋別れの台詞まで」より長くする必要がある**。`real-run-mcp-kit` の記録では、閉じる知らせから `app_exit` まで emo2 の別れの台詞で約 22 秒かかる。別れの台詞の途中で自動終了が来ると、最初の終わり方が `Smoke` になり、試験は要件 1.3 で赤になる。
- **件 2 の有力な筋が 1 つ見つかった（確かめではない）**。emo2.nar には `ghost/master/profile/` が入っていないので、新しい写しの最初の LOAD では pasta.dll が必ず自分のスクリプトを展開する。pasta（`vendors/pasta`・09-20 の版）は「一時フォルダへ展開 → フォルダの名前を替えて差し込む」順で、名前替えが断られても「続ける」と記録して先へ進む。写したばかりのファイルをウイルス対策が掴んでいるとフォルダの名前替えが「アクセスが拒否されました (os error 5)」で断られる、というのは Windows でよくある形で、元の回の手がかりの文言と合う。差し込めなかったときはスクリプトが無いまま先へ進むので、LOAD が偽を返す筋が通る。
- **仲介が今より多く拾えるのは「OS の最後のエラー」1 つだけで、しかも約束のない手がかり**。SHIORI の `load` は真偽しか返さない。pasta が最後に呼んだ OS の関数の結果が残っていれば読めるが、pasta が後で別の関数を呼べば上書きされる。また、brief と要件が「今の記録」と呼ぶ `HRESULT(0x80004005)` の行は仲介の出したものではなく、areka.exe の `main` が終了コード 1 で終わるときに返す決まった値（`E_FAIL`）で、手がかりは何も持っていない。
- **「100% 相当」を OS の設定を変えずに作る確かな手は、今は無い**。areka は起動時に自分で「モニタごとに DPI を追う」宣言をする（`crates/wintf/src/runtime/mod.rs` 137 行目）。プロセスの環境変数で互換モードを掛ける手（`__COMPAT_LAYER`）は効くかどうか確かめられていない。100% のモニタが別に在れば使えるが、在るかは分からない。

## 4. 仲介の LOAD の失敗で拾える手がかり（要件 5.4 の下調べ）

- **OS の最後のエラー**: `loadu`／`load` が 0 を返した直後（`eprintln!` や `FreeLibrary` より前）に `GetLastError` を読めば、pasta が最後に呼んだ OS の関数の結果が拾える。名前替えの失敗（5＝アクセス拒否・32＝共有違反）がそのまま残っていれば強い手がかりになる。ただし:
  - SHIORI の約束に「失敗したら最後のエラーを置く」は無い。pasta は失敗の後に記録のファイルへ書く・ほかの関数を呼ぶので、0 や無関係の値に上書きされうる。**記録には「約束のない手がかり」と添える**のが正直。
  - 取る場所は `shiori_proxy.rs` の `encode_alloc_and_load` の中（`ret` を見た直後）。`ProxyError::LoadReturnedFalse` に値を持たせると、`main.rs` の記録の行・`main_load_ack_tests.rs`・`shiori_proxy_loadu_tests.rs` の照合（2 か所）も合わせて直す。
  - 試験用の DLL `shiori-host32-testdll-loadu` の失敗の注入に「最後のエラーを置く」を足せば、決まった値が行に出ることを i686 の試験で固定できる。
- **ほかに拾えるもの**: 仲介の側で拾える一般の情報はほぼ無い。pasta の記録（`profile/pasta/logs`）を仲介が読みに行くのは pasta だけの特別扱いになるので、仲介ではなく**試験の側（落ちた回の証拠）で読む**のが筋（決まり「shiori-host32 は後付け・特別扱いは最後の手段」）。
- **brief の記述の誤り**: brief が「仲介の標準エラー」として写した `Error: Error { code: HRESULT(0x80004005), message: "エラーを特定できません" }` は、areka.exe の `main`（`fn main() -> windows::core::Result<()>`・`main.rs` 197／289／412 行目）が終了コード 1 で終わるときに返す `E_FAIL` を Rust が出した行で、仲介の手がかりではない。要件 5.4 の「今の記録（`LoadReturnedFalse` と HRESULT）」は、実際には「`LoadReturnedFalse` だけ」。

## 6. 「100% 相当」の画面（要件 3.2 の下調べ）

- areka は起動時に `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` を呼ぶ（`crates/wintf/src/runtime/mod.rs` 137 行目・成否を必ず 1 行記録）。DPI を上書きする areka の環境変数や引数は無い（`AREKA_*` を全部見た）。
- **OS の設定を変えずに作れる確かな手は、今は無い**。候補と、それぞれ分かっていないこと:
  1. **子の環境変数で互換モードを掛ける**（`__COMPAT_LAYER` に DPI を追わないモードを入れる）。プロセスの環境変数だけで OS の設定（レジストリ）は触らない。効けば areka は 96 DPI として描き、画面への拡大は OS がする＝描く量は 100% と同じになる。**ただし、効くか・areka の宣言の呼び出しより強いかは確かめていない**（公式の文書に見当たらない）。効いたかは、上の宣言の行が `failed` になるかと、areka が記録する DPI で読める。
  2. **100% のモニタが別に在ればそこへ出す**。開発機の主モニタは 200%。2 枚目が在るか・その拡大率は分からない。
  3. **開発者が一時的に表示の拡大率を 100% に替える**。OS の設定を替えることになる（要件 8.6 が禁じるのはセキュリティの設定だが、今回の聞き方「OS の設定を変えずに」には当たる）。
  4. **確かめられなかったと書いて閉じる**（要件 3.2 を満たせない）。
- 1 は「本当の 100% の画面」ではなく「描く量が 100% と同じ」。要件 3 の狙い（画面の拡大の違いに左右されない）に足りるかは判断が要る。

## 7. 実装の形の案

### 案 A: 試験のファイルだけで書く（窓口に足さない）

- 件 1: `emo2_real_run.rs` を `wait_for("wrap=BudouxWordWrap")` → 印 3 つの確かめ → `close()` → `by == UserClose` と終了コード 0、に書き換える。印の前に子が終わったら `wait_exit()` で終わり方を取って panic。保険の自動終了は「測った印までの最大＋別れの台詞＋余裕」で締切 120 秒より短く。
- 件 2: 新しい試験のファイル（例 `crates/areka/tests/emo2_first_load_repeat.rs`）。別の環境変数で明示したときだけ走り、回数と比べの条件を環境変数で受ける。各回を `std::panic::catch_unwind` で包み、失敗の回は中で panic して窓口に証拠を残させる。印を待つ間は「出力に印が無く、子が生きている間 `dump_surface`・`dump_balloon` を呼ぶ」輪で回す（呼び出しが失敗すれば子が終わった印なので、輪は保険の自動終了で必ず止まる＝自前の締切を書かない）。
- 仲介: `LoadReturnedFalse` に OS の最後のエラーを足す（4 節）。
- ✅ 窓口を触らない・ほかの未完了の spec と触るファイルの重なりが 0。
- ❌ `catch_unwind` で証拠を残すのは「panic の途中なら残す」決まりへの寄りかかりで、読み手には分かりにくい。待つ間に呼び続ける輪が試験ごとの書き物になる。

### 案 B: 窓口に部品を足してから使う

- 窓口に「回を落ちた回として残す」明示の呼び口（例 `Run::keep_evidence()`）と、「印を待つ間に別のことをする」待ち（例 `wait_for_while`）を足す。くり返しの手続きも窓口に置く。
- ✅ ほかの実機の試験も同じ形でくり返せる。証拠の残し方が明示になる。
- ❌ 窓口の約束が増える（要件の Adjacent expectations は「窓口に部品を足す必要は今は見えない・足すなら設計で挙げる」）。窓口自身の偽の子の試験も足す。

### 案 C: 混ぜる

- 件 1 は案 A（試験だけ）。件 2 はまず案 A で回し、くり返しの形を書いてみて窓口へ寄せたほうが短くなるものだけ（たぶん「残す」の明示）を窓口へ足す。

## 8. 規模と危うさ

- **規模: S〜M**。件 1 は試験 1 本の書き換えと測り（1〜2 日）。件 2 はくり返しの試験・仲介の 1 行・記録の文書（2〜4 日）。areka の側で防ぐ直しが要れば M。
- **危うさ: 中**。件 1 は低い（部品が揃っている）。件 2 は再現するかが読めない（1 回見ただけ）・原因が pasta の中やウイルス対策ならこちらで確かめ切れない。「100% 相当」は確かな作り方が無い。
- **時間の見込み**（回す前に示す・要件 8.5）: 1 回は「印まで約 3〜7 秒＋別れの台詞約 22 秒＋起こしと後片付け」で約 30 秒。基本の条件 20 回で約 10〜12 分。外す比べを 3 条件 × 20 回足すと、さらに約 30〜36 分。件 1 の確かめ（200% と 100% 相当で 3 回ずつ）は約 3 分。

## 9. 設計の段へ持ち越す判断（議題の候補）

1. **保険の自動終了の値**: 別れの台詞（約 22 秒）を含めて決める必要がある。窓口の既定 45 秒をそのまま使うか、測った値から決めるか。締切 120 秒より短く保つ。
2. **測りの方法と書く場所**: 起動から各印までの時間を、試験の中の時計で取るか、記録の時刻から読むか。結果を書く「git に残る文書」をこの spec の中（例 `research.md` の追記）にするか、`doc/testing.md` にするか。
3. **くり返しの試験の形**: 案 A（試験だけ・`catch_unwind`）か案 B（窓口に「残す」と「待つ間に呼ぶ」を足す）か案 C か。
4. **くり返しの明示の仕方と条件の渡し方**: 件 1 と同じ `AREKA_EMO2_REAL_RUN` に回数を足すか、別の環境変数にするか。比べの条件（回の間を空ける・写した後に待つ・MCP を止める）と待つ秒数をどう渡すか。
5. **分け方の規則**: 「LOAD の失敗」を `[helper] LOAD 失敗` の行で決めるか、`event="connect_failed"` で決めるか、両方か。
6. **くり返し全体の成否**: 失敗が 1 回でも出たら試験全体を赤にするか、数を出すだけで緑にするか（調べの道具としては後者、試験としては前者）。
7. **仲介に足す手がかりの形**: `LoadReturnedFalse` に OS の最後のエラーを持たせるか、呼んだ直後に別の 1 行で出すか。「約束のない手がかり」と記録に添えるか。試験用の DLL に「最後のエラーを置く」注入を足して固定するか。
8. **「100% 相当」の作り方**: 互換モードの環境変数を試すか・2 枚目のモニタを探すか・開発者に一時的に拡大率を替えてもらうか・確かめられなかったと書くか。
9. **要件 6.4 の場面**: 起動の引数で渡したゴーストの LOAD の失敗は、今は台詞でなくメッセージボックス（`shiori-fault-notice` で確定・変えない）。「既定ゴーストの台詞で伝わる」のは、入れたばかりのゴーストへ切り替えて失敗し、既定ゴーストへ戻った場面。どちらで確かめるか。
10. **原因が名前替えの断りだったときの閉じ方**: pasta の中の直し（範囲の外・別のリポジトリへ頼む）として記録するか、areka が LOAD を 1 度試し直す（本番の振る舞いの変更）か。

> 要件の討議（10-22）での振り分け: 1〜7 は設計の段で決める。8〜10 は要件の討議で推奨案どおり確定した（8＝互換モードを先に試し、効かなければ開発者が一時的に拡大率を 100% へ・9＝入れて切り替えて落ちて既定へ戻る場面・10＝外の原因として記録し DLL の側への申し送りを残す。areka は LOAD を試し直さない）。回数（基本 20 回以上・件 1 は 3 回ずつ）もそのまま確定。1 には「混んだ時間の記録（印まで 6.26 秒・6.82 秒）も覆う」を足す（静かな時間に測った最大だけで決めると、混んだ時間に 1.3 で赤になる）。
