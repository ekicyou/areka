# Requirements Document

## Project Description (Input)
開発者と AI のエージェントは、`areka.exe` を同梱の検体 emo2 で本物の窓・GPU・32bit の仲介・pasta.dll と一緒に起こし、記録を読んで確かめる「実機の走行」を、v0.1.0 の自動の試験の土台として使う。今その走行が 2 つの形で赤になる。

- **件 1**: 明示したときだけ走る試験 `emo2_real_run`（`AREKA_EMO2_REAL_RUN=1`）が、折り返しの解決の印 `wrap=BudouxWordWrap` を待つ所で赤になる。試験は今も保険の自動終了 3 秒（`SAFETY_EXIT`）で子が自分で終わるのを待つ形のままで、200% の画面の debug 版や機械が混んだ時間には、pasta の読み込み（約 3 秒）が終わる前に自動終了が来る。`real-run-mcp-kit` の完了の記録（タスク 6.3）でも同じ赤が 2 回出ている。
- **件 2**: emo2 を新しい写しから起こした走行が、1 回だけ、SHIORI（pasta.dll）の LOAD の失敗で終わった（2026-10-10・`seriko-trigger-intervals` の実機の確かめ）。再現しておらず、原因は確かめていない。失敗した回の pasta.dll の側の記録（ゴーストの写しの中の `ghost\master\profile\pasta\` の下）は、写しごと消したので残っていない。areka の側の記録には「LOAD が成功の返事を返さなかった」までしか残らない。

この spec は、件 1 → 件 2 の順に直す。件 1 は、試験が印の出たことを観測してから利用者と同じ閉じ方で子を閉じる形にし、200% と 100% 相当の両方で緑にする。件 2 は、件 1 で安定した走行を足場に新しい写しからの最初の起動を数十回くり返して失敗の割合を数え、失敗した回の証拠が残る手順にし、原因を切り分けて、areka の側で防げるなら防ぎ、防げないなら記録して閉じる。どちらも実機の試験の窓口 `crates/real-run-kit/`（`real-run-mcp-kit` が 10-19 に着地）の上で書く。

## Introduction

emo2 の実機の走行は、areka を本物の窓と SHIORI で起こして確かめる唯一の自動の通しであり、MCP で実機を回すほかの spec（`mcp-kanade-tools` ほか）の確かめもこの走行に乗る。走行が理由の分からない赤を混ぜると、自動の試験をくり返すほど結果が読めなくなる。

本 spec は、件 1（待ち方の赤）を直して走行を安定させ、その走行の上で件 2（最初の LOAD の 1 回だけの失敗）を再現・記録・切り分ける。件 2 は確かめが本体で、結果によって閉じ方（防ぐ・外の原因として記録する・再現しないとして記録する）が変わる。

### 用語

- **窓口**: 実機の試験の共通の道具 `crates/real-run-kit/`。子の起こし方・出力の待ち方・利用者と同じ閉じ方・落ちた回の証拠の残し方を持つ。
- **走り**: 窓口が `areka.exe` を 1 回起こしてから終わるまで。
- **子**: 走りのために起こした `areka.exe` のプロセス。
- **印**: 子の記録に出る決まった文字列。本 spec で待つのは、wire 成立の印・装着の印・折り返しの解決の印 `wrap=BudouxWordWrap` の 3 つ。
- **利用者と同じ閉じ方**: 利用者がゴーストの窓を閉じたときと同じ道。ゴーストへ `OnClose` が届き、別れの台詞の後で areka が自分で終わる。
- **保険の自動終了**: 起動から決まった時間で子が自分で終わる仕組み。閉じ方が働かなかったときに子を残さないためだけに使う。
- **締切**: 窓口が待ちを打ち切って試験を赤にする時間。
- **新しい写し**: 走りの直前に、同梱の emo2 を `target\` の下へ写し直したもの（前の回の写しは使わない）。
- **LOAD の失敗**: 32bit の仲介が SHIORI の LOAD から成功の返事を受け取れず、子が「SHIORI 接続確立に失敗」を記録して終わること。
- **取り合いの相手**: 新しい写しへの最初の LOAD の書き込みと同じ時間にファイルを掴みうるもの。前の回の `areka.exe` や仲介のプロセスの終わり残り・写しを作った直後の掴み・走りの間の MCP の呼び出し・ウイルス対策の走査。
- **くり返しの手順**: 新しい写しからの最初の起動を、続けて何回も回して結果を数える手順。
- **100% 相当の画面**: areka が 96 DPI として描く画面。まず子の環境変数による互換モード（OS の設定に触らない）で作り、areka の記録に出る DPI が 96 であることで確かめる。互換モードが効かないときは、確かめの間だけ開発者が表示の拡大率を 100% へ替えた画面を使う（表示の拡大率は OS の設定なので AI は替えない）。

## Boundary Context

- **In scope**:
  - 件 1: 赤の再現・起動から印までの時間の測りと切り分け・試験の待ち方の直し（または、装着そのものが遅いと分かったときの遅さの原因の直し）・試験の頭の説明と人の目視の手順の書き直し・200% と 100% 相当での確かめ。
  - 件 2: くり返しの手順・失敗した回の証拠の残し方・仲介が LOAD の失敗で残す手がかりの見直し・取り合いの相手を 1 つずつ外した比べ・（areka の側で防げると分かったとき）その直し・（防げないとき・再現しないとき）根拠の記録・次に同じ赤が出たときの読み方の手引き。
- **Out of scope**:
  - 折り返しそのものの振る舞い（完了 `budoux-reveal-reflow` 系）。
  - 2 本の手順を常時のテスト（ふだんの `cargo test`・`tools/test-all.ps1`）へ組み込むこと（要るなら議題）。
  - emo2 の台本・pasta の SHIORI の振る舞い・pasta.dll の中の直し（別のリポジトリ）。
  - SHIORI の失敗の利用者への伝え方そのもの（完了 `shiori-fault-notice` で確定。変えない）。
  - areka 自身が書けない場所に在るときの伝え方（`write-failure-notice`）・置き場を入れ先の外へ出すこと（`user-data-root`）。
  - 負荷の下のテストの揺れ（`areka-test-binary-stability`）。
  - ウイルス対策や OS のセキュリティの設定を変えること（疑わしいときは根拠を記録するだけ）。
  - `areka.exe` の本番の起動・終了の振る舞いの変更（件 2 で areka の側で防げると分かったときの直しを除く）。
- **Adjacent expectations**:
  - 窓口（`real-run-kit`）の「出力にその文字列が出るまで待つ」「利用者と同じ閉じ方で閉じる」「子の終わり方（利用者と同じ閉じ方か、保険の自動終了か）を読み分ける」「落ちた回の写しと出力を残し、成功した回は消す」「回の置き場を `target\` の下に短い絶対パスで作る」は、今のまま使う。窓口に部品を足す必要は今は見えない。足すと分かったときは設計の段で挙げる。
  - areka 本体の印（wire 成立・装着・`wrap=BudouxWordWrap`）と、利用者と同じ閉じ方で `OnClose` を経て終了コード 0 で終わることは、今のまま使う。
  - 件 2 の調べで、SHIORI の `load` へ渡すフォルダのパスの形が効いていると分かったときは、未完了の `shiori4-api` へ渡す（`emily-ghost-verification` は完了済み）。
  - 実機の窓が出るので、走行は排他テストの机（`impl-watch-test-desk`・手順は `doc/impl-watch.md`）を借りて 1 本ずつ回し、負荷の走行と同じ時間に回さない。

## Requirements

### Requirement 1: emo2 の実機の試験を印の観測で待って閉じる（件 1）

**Objective:** As a 実機の確認を回す開発者と AI のエージェント, I want `emo2_real_run` が保険の自動終了の残り時間でなく、印が出たことの観測で待ってから閉じてほしい, so that 200% の画面の debug 版でも、pasta の読み込みが遅い回でも、試験が理由なく赤にならない

#### Acceptance Criteria

1. When `AREKA_EMO2_REAL_RUN` に空でない値を入れて試験を走らせたとき, the emo2 の実機の試験 shall 子の出力に `wrap=BudouxWordWrap` が現れるまで待ち、現れてから利用者と同じ閉じ方で子を閉じる。
2. When 子が終わったとき, the emo2 の実機の試験 shall 子が利用者と同じ閉じ方で終わったことと、終了コードが 0 であることを確かめる。
3. If 子が保険の自動終了で終わっていた場合, then the emo2 の実機の試験 shall 赤とし、保険の自動終了で終わったことを失敗の文に書く。
4. The emo2 の実機の試験 shall 今の 3 つの印の確かめ（wire 成立の印・装着の印・`wrap=BudouxWordWrap`）を落とさずに保つ。
5. The emo2 の実機の試験 shall 保険の自動終了の時間を、要件 2 で測った「起動から `wrap=BudouxWordWrap` までの時間の最大」と「閉じる知らせから子が終わるまで（別れの台詞）の時間の最大」の和より長く、締切より短くする（別れの台詞の途中で保険の自動終了が来ると、子の終わり方が保険の自動終了になり 1.3 で赤になるため）。
6. If 締切までに `wrap=BudouxWordWrap` が現れなかった場合, then the emo2 の実機の試験 shall 赤とし、待っていた印・待った時間・子の出力のファイルの場所を失敗の文に書き、その回の写しと出力を残す。
7. If `wrap=BudouxWordWrap` が現れる前に子が終わった場合, then the emo2 の実機の試験 shall 赤とし、終了コードと子の終わり方を失敗の文に書き、その回の写しと出力を残す。
8. While `AREKA_EMO2_REAL_RUN` が無い・空・空白だけのとき, the emo2 の実機の試験 shall 子を起こさずにすぐ素通りする（今のまま）。
9. The emo2 の実機の試験 shall 頭の説明と人の目視の手順の段を、新しい終わり方（印を見てから利用者と同じ閉じ方で閉じる・自動終了は保険だけ）に合わせて書き直し、「自動終了で終わる」という古い書き方を残さない。

### Requirement 2: 起動から印までの時間を測って遅さの在りかを切り分ける（件 1）

**Objective:** As a 件 1 を直す開発者と AI のエージェント, I want 起動から印までの時間を測って、遅いのが装着そのものか試験の待ち方かを数字で切り分けたい, so that 自動終了を延ばすだけの直しに逃げず、原因に合った直しを選べる

#### Acceptance Criteria

1. When 件 1 の直しに入る前に, the 開発の手順 shall 200% の画面で debug 版の emo2 の実機の走行を起こし、件 1 の赤が再現するかを確かめ、起動から wire 成立の印・装着の印・`wrap=BudouxWordWrap` のそれぞれまでの時間と、利用者と同じ閉じ方で閉じる知らせを送ってから子が終わるまでの時間を測る。
2. The 開発の手順 shall 測った時間と、遅さが待ち方（保険の自動終了の残り時間に頼ること）に在るか、装着そのもの（SHIORI の読み込みの待ちを除く areka 自身の処理）に在るかの結論を、git に残る文書に書く。
3. If 切り分けの結果、装着そのものが遅さの原因と分かった場合, then the 開発の手順 shall その遅さの原因を直し、直した後の時間を同じ条件で測り直して同じ文書に書く。
4. The 開発の手順 shall 保険の自動終了を延ばすだけの直しを、件 1 の直しとして採らない。

### Requirement 3: 200% と 100% 相当で緑を確かめる（件 1）

**Objective:** As a 実機の確認を回す開発者と AI のエージェント, I want 直した試験が画面の拡大の違いに左右されずに緑になることを確かめたい, so that どの開発機の画面でも同じ試験を信じて使える

#### Acceptance Criteria

1. When 件 1 を直した後, the 開発の手順 shall 200% の画面で debug 版の emo2 の実機の試験を続けて 3 回以上走らせ、すべて緑であることを確かめる。
2. When 件 1 を直した後, the 開発の手順 shall 100% 相当の画面で debug 版の emo2 の実機の試験を続けて 3 回以上走らせ、すべて緑であることを確かめる。
3. The 開発の手順 shall 確かめた画面の拡大・版・回数・結果・起動から `wrap=BudouxWordWrap` までの時間を、git に残る文書に書く。

### Requirement 4: 新しい写しからの最初の起動をくり返して数える（件 2）

**Objective:** As a 件 2 を調べる開発者と AI のエージェント, I want 新しい写しからの最初の起動を、同じ条件で続けて何回も回して結果を数えたい, so that 1 回だけ見た LOAD の失敗が、どのくらいの割合で起きるのか（起きないのか）を数字で言える

#### Acceptance Criteria

1. The くり返しの手順 shall 1 つのコマンドで、決めた回数だけ、新しい写しから emo2 を起こす走りを続けて回せる。
2. The くり返しの手順 shall 明示したときだけ走り、常時のテスト（ふだんの `cargo test`・`tools/test-all.ps1`）では子を起こさずに素通りする。
3. The くり返しの手順 shall 毎回、前の回の写しを使わずに新しい写しを取り、その写しの絶対パスでゴーストを起こす。
4. The くり返しの手順 shall 基本の条件として、元の失敗の回に在った取り合いの相手のうち手順で作れるもの（写しを取った直後に起こす・前の回の子が終わった直後に次の回を起こす・走りの間に別のプロセスから MCP で面とバルーンを読む）を含める。
5. The くり返しの手順 shall 基本の条件で 20 回以上回す。
6. The くり返しの手順 shall 各回を「成功」「LOAD の失敗」「ほかの失敗」のどれかに分け、終わったときに回数と各々の数を出力に示す。
7. The くり返しの手順 shall 各回で件 1 の確かめ（印・利用者と同じ閉じ方・終了コード 0）を使い、「成功」はその確かめが通った回とする。
8. If ある回が「LOAD の失敗」か「ほかの失敗」で終わった場合, then the くり返しの手順 shall その回の証拠を残したうえで、残りの回を止めずに続ける。

### Requirement 5: 失敗した回の証拠を残す（件 2）

**Objective:** As a 失敗の原因を読む開発者と AI のエージェント, I want 失敗した回のゴーストの写しと記録が、次の回に消されずに残ってほしい, so that pasta.dll の側の記録まで読んで、なぜ LOAD が断られたのかを確かめられる

#### Acceptance Criteria

1. If ある回が「LOAD の失敗」か「ほかの失敗」で終わった場合, then the くり返しの手順 shall その回のゴーストの写し（SHIORI 自身が写しの中に作る展開先・記録・一時の置き場を含む）と子の標準出力・標準エラーを、回ごとに別の名前で `target\` の下に消さずに残す。
2. When 証拠を残したとき, the くり返しの手順 shall 残した場所を出力に示す。
3. When ある回が「成功」で終わったとき, the くり返しの手順 shall その回の写しと出力を消し、くり返しで置き場がふくらみ続けないようにする。
4. The 開発の手順 shall 32bit の仲介が LOAD の失敗のときに、今の記録（`LoadReturnedFalse` だけ。元の回の標準エラーに在った `HRESULT(0x80004005)` の行は、areka.exe が終了コード 1 で終わるときの決まった値で、仲介の手がかりではない）より多く得られる手がかり（例: OS の最後のエラー）が在るかを調べ、調べた結果を git に残る文書に書く。
5. Where 32bit の仲介が LOAD の失敗のときに今より多くの手がかりを得られる, the 32bit の仲介 shall その手がかりを LOAD の失敗の記録の行に足す。

### Requirement 6: 原因を切り分けて閉じる（件 2）

**Objective:** As a 件 2 を閉じる開発者と AI のエージェント, I want くり返しの結果から原因を切り分け、防げるなら防ぎ、防げないなら根拠を残して閉じたい, so that 理由の分からない赤が自動の試験に混ざり続けない

#### Acceptance Criteria

1. When 基本の条件で LOAD の失敗が 1 回以上出たとき, the 開発の手順 shall 取り合いの相手を 1 つずつ外した条件（前の回の終わりから次の起動までを空ける・写しを取った後に待ってから起こす・MCP の呼び出しを止める）で、基本の条件と同じ回数ずつくり返し、失敗の数を比べる。
2. When 切り分けの結果、原因が areka の側で防げると分かったとき（例: 前の SHIORI のプロセスが終わりきる前に次の LOAD をしていた）, the areka shall その原因を防ぎ、失敗が再現した条件で同じ回数くり返して LOAD の失敗が 0 回であることを示す。
3. If 切り分けの結果、原因が areka の外（SHIORI の DLL の中・OS・ウイルス対策）に在ると分かった場合, then the 開発の手順 shall その根拠（比べた条件・回数・失敗の数・失敗した回の証拠から読んだこと）を git に残る文書に書いて閉じる。原因が SHIORI の DLL の中（例: pasta.dll がスクリプトを展開した後のフォルダの名前替えを OS に断られた）に在るときは、areka の側で LOAD を試し直す直しを入れず、DLL の側で直すための申し送り（起きた順・OS のエラー・直す場所の見立て）を同じ文書に書く。
4. If 原因が areka の外に在り、利用者に「入れたばかりのゴーストが最初の 1 回だけ起動に失敗しうる」形が残る場合, then the 開発の手順 shall 入れたばかりのゴーストへ切り替えて LOAD が失敗し既定ゴーストへ戻る場面で、その失敗が既定ゴーストの台詞で利用者へ伝わることを実機の走行で確かめて記録する。自然な失敗はまれなので、LOAD が成功を返さないゴーストで失敗を起こしてよい。起動の引数で渡したゴーストの LOAD の失敗の伝え方（メッセージボックス・完了 `shiori-fault-notice` で確定）は変えない。
5. If 基本の条件で LOAD の失敗が 1 回も出なかった場合, then the 開発の手順 shall 試した回数と条件を git に残る文書に書いて閉じる。
6. If 調べの中で、SHIORI の `load` へ渡すフォルダのパスの形が失敗に効いていると分かった場合, then the 開発の手順 shall その根拠を書き、`shiori4-api` へ渡したことを記録する。
7. The 開発の手順 shall 件 2 を、上の閉じ方（防いだ・外の原因として記録した・再現しないとして記録した）のどれで閉じたかを、根拠とともに git に残る文書に書く。

### Requirement 7: 次に同じ赤が出たときに原因を読める手引き（件 2）

**Objective:** As a 次に LOAD の失敗や待ちの赤に出会う開発者と AI のエージェント, I want 証拠がどこに残り、何から読めばよいかが手引きに書いてあってほしい, so that 同じ赤が出たとき、もう一度調べ直さずに原因に近づける

#### Acceptance Criteria

1. The 実機の試験の手引き（`doc/testing.md`） shall くり返しの手順の回し方（明示の仕方・回数の決め方・所要時間の見込み）を書く。
2. The 実機の試験の手引き shall 失敗した回の証拠が残る場所と、読む順（子の出力・32bit の仲介の記録・写しの中の SHIORI 自身の記録）を書く。
3. The 実機の試験の手引き shall 件 2 の閉じ方の結論と、その根拠を書いた文書の場所を示す。

### Requirement 8: 実機の走行の約束

**Objective:** As a 同じ開発機で並んで作業する開発者と AI のエージェント, I want 実機の走行がほかの作業や開発者の環境を乱さないでほしい, so that くり返しの走行を回しても、ほかのセッションの試験や手元の設定が壊れない

#### Acceptance Criteria

1. The 件 1 の試験とくり返しの手順 shall 根・ゴーストの写し・一時のフォルダ・記憶の置き場を、ワークツリーの `target\` の下だけに置く。
2. The 件 1 の試験とくり返しの手順 shall emo2 を、絶対パスかつ短いパスで渡して起こす。
3. The 件 1 の試験とくり返しの手順 shall 自分が起こしたと確かめられるプロセスだけを止める。
4. While 件 1 の試験かくり返しの手順を回している間, the 開発の手順 shall 排他テストの机を借りて実機の走行を 1 本ずつ回し、負荷の走行（`areka-test-binary-stability` ほか）と同じ時間に回さない。
5. When くり返しの手順を回す前に, the 開発の手順 shall 回数と所要時間の見込みを示す。
6. The 開発の手順 shall ウイルス対策や OS のセキュリティの設定を、切り分けのために変えない。
