# Requirements Document

## Introduction

開発者は、areka のコードに残っているバグ・危ない所・負荷に弱い所・テストの抜け・遅い所・要らないコードを、同じ物差しで一度まとめて直したい。物差しは、利用者全体に入れてある ponytail のプラグイン（5.3.2）の `/ponytail:ponytail-audit`。全 33 本の見直しのうち、この spec は **SERIKO（シェルのアニメーション）** を受け持つ。

この要件は「受け持つ範囲の audit の指摘を、3 つの組（必ず直す・直したほうがよい・できれば）とも全部直す」という**形だけ**を決める。指摘の中身はここには書かない。指摘はギャップ分析の段で audit をかけて洗い出し、要件の討議で直す対象を確定する（2026-10-19 開発者「原則、ギャップ分析でauditを実施して、設計以降で修正」）。

## Project Description (Input)

- **誰が困っているか**: areka の開発者。今までは各 spec が自分の触る所だけを見てきて、全体を同じ物差しで見直したことがない。
- **今の状況**: 受け持つファイルは `crates/areka-seriko/` 全部。起票のとき（main `e3c2cbe4`）は 60 ファイル・コード 7,172 行・テスト 15,894 行だった。着手のとき（2026-11-05・main `88eb0a43`）に測り直した今の正本は 84 ファイル（本番 22 ファイル・8,356 行／テスト 59 ファイル・20,008 行／テスト用の素材 2 ファイル・161 行／`Cargo.toml`）で、ギャップ分析（`research.md` の 1 節）に残した。
- **何が変わるべきか**: 受け持つ範囲の audit の指摘が 3 つの組とも全部直り、直した後にもう一度かけた audit で新しい指摘が 0 件になり、全体テストが緑で、直したバグ・危ない所の 1 件ごとにそれが壊れたら落ちるテストがある（開発者「とにかく指摘事項は全部直す方針です」）。

## Boundary Context

- **In scope**: `crates/areka-seriko/` の全ファイル（コード・テスト・テスト用の素材・クレートの設定）の audit と、その指摘の直し。直しのためのテストの追加と直し。直しのために要る、範囲の外の呼び出し元の直し（要件 7 の約束に従う）。
- **Out of scope**: 範囲の外の見直し（ほかの 32 本の持ち物）。新しい機能。`vendors/`。clippy の指摘の機械的な直し（`clippy-199-lints` の持ち物。ただし audit が同じ所を指したら、その指摘としては直してよい）。開発者の裁定（roadmap の「生きている決まり」・記憶の決めごと・完了した spec の要件）を覆す直し。
- **Adjacent expectations**:
  - `clippy-199-lints` は同じクレートに触るため、見直しのあいだは同じウェーブに並べない。
  - ウェーブ C17 の兄弟（`doc-tree-tidy` とほかの見直し 6 本）とは受け持つファイルが重ならない。呼び出し元へ直しが及ぶときだけ、相手のセッションと申し合わせる。
  - v0.2.0 の作り直しのうち触るファイルが重なる spec（`draw-methods-canon`・`draw-methods-blend`・`talk-anchor-interrupt-ticks`・`seriko-talk-clock-fidelity`・`tick-gate-adoption`）は、この見直しの着地を待つ。この spec はそれらの作り直しを先取りしない。

## Requirements

### Requirement 1: 受け持つ範囲への audit（ギャップ分析の段）

**Objective:** As a 開発者, I want 受け持つ範囲の全部を同じ物差しで漏れなく見直してほしい, so that 直す対象を省かずに確定できる

#### Acceptance Criteria

1. When ギャップ分析の段に入った場合, the 見直し shall `crates/areka-seriko/` だけを対象に `/ponytail:ponytail-audit` をかける
2. The 見直し shall audit の作法のうち「最大 20 件」の上限を外し、指摘を全件出して、省いた件を残さない
3. The 見直し shall audit の作法のうち「読まなかった所（Not checked）」を残さず、範囲のファイルを全部読む
4. The 見直し shall 指摘の一覧を、audit の番号をそのまま使い、3 つの組（必ず直す・直したほうがよい・できれば）のどれかを付けて、ギャップ分析の報告に残す
5. The 見直し shall 着手のときの範囲の大きさ（ファイル数・コードの行数・テストの行数）を測り直して、ギャップ分析の報告に残す
6. The 見直し shall ponytail のプラグインを利用者全体に入っているまま使い、リポジトリにプラグインのフックやスキルを写さない

### Requirement 2: 指摘を 3 つの組とも全部直す

**Objective:** As a 開発者, I want audit の指摘を組を問わず全部直してほしい, so that SERIKO の範囲に既知の問題が残らない

#### Acceptance Criteria

1. When 要件の討議で指摘の一覧を要件に落とした場合, the 見直し shall その一覧を直す対象の正本として確定し、設計・タスク・実装の段はその一覧に従う
2. The 見直し shall 確定した一覧の指摘を、必ず直す・直したほうがよい・できれば の 3 つの組とも全部直す（要件 3 で残すと裁定された件だけを除く）
3. The 見直し shall 指摘の直しを、その指摘を解消する最も小さな完全な変更とし、消せるものは消して、呼び出し元・テスト・テスト用の素材まで直し切る
4. If 指摘の数から 1 本の spec が 20 タスクを越えそうな場合, then the 見直し shall 要件の討議で、指摘の組ごとに同じ範囲の 2 本目の spec へ切り出すことを議題にする

### Requirement 3: 直さずに残してよい指摘

**Objective:** As a 開発者, I want 直さずに残す指摘を決まった 3 種類に限り、どれも自分の裁定を経てほしい, so that 「直さない」が黙って増えない

#### Acceptance Criteria

1. The 見直し shall 直さずに残す指摘を、次の 3 種類のどれかに当たり、かつ要件の討議で開発者が残すと裁定したものだけに限る
   - (1) 開発者の裁定（roadmap の「生きている決まり」・記憶の決めごと・完了した spec の要件）に反する直し
   - (2) わざと置いた先送りの印（実在の理由を書いた doc 付きで使われていないことを許した語彙の口と、`shortcut:`・`ponytail:` の注釈のうち、書かれた限界が今の負荷を越えていないもの）
   - (3) 外から見た振る舞いが変わる直しのうち、SSP との互換や ukadoc の正典に関わるもの
2. If ある指摘の直しが開発者の裁定を覆す場合, then the 見直し shall その指摘を直さずに要件の討議の議題にする
3. If ある指摘の直しが SSP との互換や ukadoc の正典に関わる外から見た振る舞いを変える場合, then the 見直し shall ukadoc で正典を確かめた結果を添えて、要件の討議の議題にする
4. When 開発者が指摘を残すと裁定した場合, the 見直し shall その指摘の番号・当たる種類・裁定・理由を spec の記録に残す
5. If 指摘が 3 種類のどれにも当たらない場合, then the 見直し shall その指摘を直す対象から外さない

### Requirement 4: 直したことを示すテストと全体テスト

**Objective:** As a 開発者, I want 直したバグ・危ない所が壊れたらテストで分かるようにしてほしい, so that 直しが後から黙って崩れない

#### Acceptance Criteria

1. The 見直し shall 直したバグ・危ない所の 1 件ごとに、それが元に戻ったら落ちるテストを 1 本以上置く
2. The 見直し shall 追加・変更するテストを決定論のテストにし、実行の時刻・順序・外の状態によって結果が変わらないようにする
3. Where 直しが GPU を使う処理に触れる場合, the 見直し shall その GPU のテストを実際の GPU で回す
4. Where テストが実機の根や一時フォルダを使う場合, the 見直し shall それらをワークツリーの `target` の下に置く
5. When 実装の段を終える場合, the 見直し shall 全体テスト（`pwsh -NoProfile -File tools/test-all.ps1`）が緑であることを確かめる

### Requirement 5: 直した後の audit で 0 件

**Objective:** As a 開発者, I want 直した後に同じ物差しでもう一度見直して新しい指摘が無いことを確かめてほしい, so that 直しが生んだ問題も残らない

#### Acceptance Criteria

1. When 確定した一覧の直しを全部終えた場合, the 見直し shall 同じ範囲へ、要件 1 と同じ作法（全件を出す・全部読む）で audit をかけ直す
2. If かけ直した audit で新しい指摘（直しが生んだ指摘を含む）が出た場合, then the 見直し shall その指摘も要件 2 と要件 3 に従って扱い、新しい指摘が 0 件になるまでかけ直す
3. The 見直し shall かけ直した audit の結果（新しい指摘が 0 件であること、残すと裁定された件の番号）を検証の記録に残す

### Requirement 6: 直しのあいだ守る決まり

**Objective:** As a 開発者, I want 直しがプロジェクトの決まりを崩さないようにしてほしい, so that 見直しが新しい負債を生まない

#### Acceptance Criteria

1. The 見直し shall 本番とテストのどのファイルも 1 ファイル 1,000 行の上限（見張りのテスト）を越えさせず、足す分が上限を越えるなら新しいファイルへ置く
2. The 見直し shall 記録の無い失敗の道を作らず、失敗の道ではエラーの記録（`error!`）と失敗の返し（`Err`）を揃える
3. The 見直し shall 終了の道を正規の実装にし、その場しのぎの細工で済ませない
4. If 文字化けに当たった場合, then the 見直し shall コンソールの文字コードを変えて逃げず、読む側を直す
5. The 見直し shall 依存を足さず、`Cargo.lock` を変えない（ウェーブ C17 の約束）
6. If 依存を足さなければ直せない指摘が出た場合, then the 見直し shall その指摘を直さずに議題にし、足すなら `tech.md` への登記と開発者の承認を得てからにする
7. The 見直し shall `doc/`・`docs/` を名指す行を足さず、変えない（ウェーブ C17 の約束）

### Requirement 7: 消す前の確かめと範囲の外の呼び出し元

**Objective:** As a 開発者, I want 消す直しや形を変える直しが範囲の外を壊さないようにしてほしい, so that 見直しのせいでほかの所が黙って壊れない

#### Acceptance Criteria

1. When コード・型・ファイル・設定を消す場合, the 見直し shall その前にツリー全体（テスト・テスト用の素材・設定・文字列での参照を含む）で使われていないことを確かめ、その確かめ方と結果を記録に残す
2. When 関数や型の形を変えた場合, the 見直し shall ツリー全体で呼び出し元を探して全部直す
3. If 直しが及ぶ呼び出し元が、走っているほかの見直しの spec の範囲にある場合, then the 見直し shall そのセッションと申し合わせてから触る
4. The 見直し shall 範囲の外のファイルでは、直しのために要る呼び出し元の直しだけを行い、そのファイルの別の問題は直さない
5. Where audit の指摘が clippy の指摘と同じ所を指す場合, the 見直し shall その所を audit の指摘として直し、それ以外の clippy の指摘の機械的な直しは行わない
