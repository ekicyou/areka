# Requirements Document

## Introduction

ゴーストを起動して放置しているだけで CPU を消費し続け、まばたき等のアイドルアニメーションがコマ送り（スロー再生）で目視できるほど描画が劣化している問題を根治する。デスクトップマスコットは常駐が前提であり、放置で 1 コアの 2 割を食う現状は製品として成立しない。また、この負荷は以後の全 spec の実機サインオフの妨げ（dev ビルドで 1 コア 45%・ドラッグ操作困難）にもなっている。

**実測（正本: brief.md）**:

| 指標 | dev ビルド | release ビルド |
|---|---|---|
| アイドル時 CPU（1 コア換算） | 45.3% | 13.4% → 21.6%（時間とともに上昇） |
| 表示 1 コマの適用所要 | 約 500ms | 約 143ms |
| 合成キャッシュ命中（アニメ再生中） | 0 件（7 分実走で 404 件すべてミス） | 同傾向 |

原因はコード読解で確定済み（詳細アンカーは brief.md が正本）: 表示の毎フレーム経路が、上流合成層が提供するバッファ再利用形の合成経路（上流要件「途中アロケーションを発生させない」の提供物）を一度も使わず、毎コマ合成先・リサンプル先・当たり判定マスクを新規確保している。合成キャッシュは承認済み要件により容量 1 であり、アニメ再生中は毎コマ必ずミスする。SERIKO 側の進行は壁時計どおりであり、遅いのは表示適用側単独である。

**対応方針（brief.md の段階的ループ設計を要件化）**: ⑴段階別計時ログの新設（観測基盤・恒久資産）→ ⑵ベースライン自動採取で「何が重いか」を数値確定 → ⑶毎フレーム経路の定常アロケーション是正 → ⑷同一手順の再測による効果の機械判定、のループで進める。特定から効果判定まで開発者の介在なしに自走で完結させ、目視必須の判定項目を作らない。

**前提の更新（2026-08-11）**: 「bind 集合の蓄積で合成要素数が単調増加する」仮説（CPU 時間上昇の候補 (a)）は、`areka-P0-bindoption-exclusivity` の完了により構造的に消滅した。今後の測定で時間上昇が残る場合は、活性アニメ集合の定常到達 (b) か未知の機序である。ベースラインは同日以降のログを正とする。

**ウェーブ配置（確定済み）**: W6.5（2026-08-14 開発者裁定で性能最優先の前倒し・roadmap 追記(66) が正本）。

## Boundary Context

- **In scope**:
  - 表示の毎フレーム経路における定常状態アロケーションの是正（マスクの下流供給の複製・リサンプル内部の作業領域を含む完全ゼロ。必要な範囲で上流クレートへの追加的 API——wintf のマスク再利用形・emo-compose のリサンプル作業領域受け取り形——を含む。既存 API の意味変更はしない）
  - ホットパスの段階別計時ログと、自動計測・機械判定の手順一式（以後の性能 spec が再利用する資産）
  - CPU が時間とともに上昇する機序の切り分け（定常到達か・未知機序か）
  - 定常状態アロケーション 0 を固定する決定論的な回帰テスト
- **Out of scope**:
  - 合成キャッシュ容量（承認済み要件で容量 1）の変更——開発者裁定が下りた場合のみ本 spec 内で実施（Requirement 7）
  - SERIKO のアニメ発火頻度・アニメ定義・ゴースト fixture の改変による負荷低減（ゴースト作者の意図であり互換性違反・症状を隠すだけ）
  - 合成アルゴリズム本体の最適化（要素数比例の計算量契約は満たされている前提・破れが見つかれば別途起票）
  - GPU 側（スワップチェーン・合成面更新）の最適化——CPU 側の確定分を潰してから測り直す
  - bind の意味論（`areka-P0-bindoption-exclusivity` で完了済み）・拡大率切替時の跳ね（`areka-P0-dpi-transition-atomicity` の所有）
- **Adjacent expectations**:
  - `areka-P0-scale-exact-rational`（W6.5 並走）: 主戦場は別ファイルだが、本 spec がリサンプル作業領域の API を emo-compose の拡大縮小処理ファイルへ追加するため同一ファイルに触れる（議題 1 裁定）。追加は関数の追加に限定し、先着した側の実形へ後着側が rebase で追随する
  - `areka-P0-dpi-transition-atomicity`(W6.75): 本 spec 着地後の再測で「残る跳ねコスト」を確定させる前提。本 spec は同 spec の観測対象へ干渉する変更を持ち込まない
  - `areka-P0-test-cage-determinism`（W6.9）: 本 spec が新設するテストの決定性検査を最後尾で統合する

## Requirements

### Requirement 1: 段階別計時ログの新設（観測基盤・恒久資産）

**Objective:** As a 開発者, I want 表示 1 コマ適用の所要時間の内訳をログから機械集計できる観測基盤, so that 「何が重いか」を推測ではなく実測で確定できる

#### Acceptance Criteria

1. When サーフェス表示の 1 コマ適用が実行される, the emo-present 層 shall 段階別の所要時間（少なくともキャッシュ照会・合成・リサンプル・当たり判定マスク生成・供給面への転写、および合計）を、grep 可能な固定文言と数値フィールドを持つログとして記録する
2. The emo-present 層 shall 計時ログを開発者向け詳細水準（debug）の常設ログとして提供し、実行時のログフィルタ設定でオンオフできる
3. When 1 コマ適用の中で表示用バッファの新規確保が発生する, the emo-present 層 shall その発生を機械集計可能な形で記録する（アロケーション発生点の計数）
4. The 自動テスト shall 計時ログの固定文言・ログ水準・全段の出現を検証する（計測手段自体が壊れていたら診断が全部誤りになるため、道具の較正を先に固定する）
5. The emo-present 層 shall 計時ログの有効・無効によって表示結果を変えない

### Requirement 2: ベースラインの自動採取と内訳の数値確定

**Objective:** As a 開発者, I want 是正前の性能内訳を人の介在なしに自動採取・自動集計したい, so that 是正の対象と順序を実測が決められる

#### Acceptance Criteria

1. When ベースライン採取を実行する, the 計測手順 shall 実機ゴーストの有界自動終了つき実走を短時間（7 分程度）と長時間（20 分超）の 2 水準で行い、人が画面を見る工程なしに完了する
2. When 実走ログが得られた, the 判定スクリプト shall 段階別所要時間の p50/p95・キャッシュ命中率・進行境界スキップ（catch-up）件数・コマ適用間隔・CPU 時系列を自動集計して出力する
3. The 計測手順 shall CPU 使用率の時系列を一定間隔で自動採取する
4. The 計測手順 shall 同一手順・同一 fixture で再実行でき、是正前後の比較が成立する再現可能な形で文書化される
5. If 判定スクリプトが必要なログ段の欠落を検出した, the 判定スクリプト shall 部分集計を黙って出さず、欠落をエラーとして報告する

### Requirement 3: 毎フレーム経路の定常アロケーション是正

**Objective:** As a エンドユーザー, I want ゴーストを放置してもアニメーションが軽く滑らかに再生されること, so that 常駐マスコットとして実用に耐える

#### Acceptance Criteria

1. While 定常状態（必要なバッファの初回確保が済んだ後）, when 表示 1 コマの適用が実行される, the emo-present 層 shall 合成先・リサンプル先・当たり判定マスクのバッファに加え、マスクの下流供給（複製）とリサンプル内部の作業領域も再利用し、新規確保を発生させない（上流合成層の「途中アロケーションを発生させない」契約の意図を消費側でも成立させる。キャッシュ命中時を含む毎コマ適用の全経路が対象＝完全ゼロ。ディスカッション議題 1 裁定 2026-08-14）
2. If 表示寸法が変化した（拡大率変更・サーフェス外形の変化）, the emo-present 層 shall 必要な再確保を一度だけ行い、以後の定常状態では再び新規確保なしで動作する
3. The emo-present 層 shall 是正の前後で、同一入力に対する表示結果（表示バイトと当たり判定マスク）をバイト等価に保つ（是正が絵と当たり判定を変えないこと）
4. The 本 spec shall 是正の着手順を第 1 段の実測内訳に従わせる（現時点の最有力仮説と異なる段が支配的と判明した場合は、そちらを先に是正する）

### Requirement 4: 是正効果の機械判定（再測と合格判定式）

**Objective:** As a 開発者, I want 是正の効果を同一手順の再測とあらかじめ定めた判定式で機械判定したい, so that 効果判定に人の目視や主観が要らない

#### Acceptance Criteria

1. When 是正後の再測を実行する, the 計測手順 shall ベースラインと同一手順・同一 fixture で採取し、判定スクリプトが合否を機械判定する
2. The 判定スクリプト shall 次の合格判定式を判定する: ⑴コマ適用間隔の p95 がアニメ定義の指定間隔＋許容率以内（スロー再生解消の機械判定）⑵定常状態での進行境界スキップ（catch-up）0 件 ⑶定常状態での表示用バッファ新規確保 0 件 ⑷アイドル時 CPU が目標値以下
3. The 判定スクリプト shall 判定式 ⑴〜⑶ を dev・release 両ビルドの実走に適用する（dev ビルドでの実機サインオフが操作に支障なく行えることの機械的代理）
4. The areka 実行体 shall release ビルドにおいて、ゴースト放置時のアイドル CPU（1 コア換算）を 3% 未満に収め、20 分超の走行で時間とともに単調上昇しない（根拠: 同一ゴースト emo2 を表示中の SSP（GDI 描画）を開発機で実測した定常値 2.2〜2.8%（2026-08-14）の同等圏。GPU 描画が GDI 描画に劣る理由はないという開発者裁定＝ディスカッション議題 2。dev ビルドには CPU の数値目標を課さない（4.3 の⑴〜⑶のみ適用）。未達の場合の経路は 4.6・Requirement 7）
5. The 判定スクリプト shall 実時間・CPU に関する閾値と許容率を判定スクリプト側の較正値として明記し、測定マシンの条件を判定結果に併記する（マシン差を較正値として扱い、テストコードへ実時間閾値を持ち込まない）
6. If 再測が合格判定式を満たさない, the 開発プロセス shall 残る最大内訳を特定して是正（Requirement 3）へ戻る。ただし残る最大内訳がキャッシュ不命中による再合成コストである場合は Requirement 7 の裁定ゲートへ回す

### Requirement 5: CPU 時間上昇の機序の切り分け

**Objective:** As a 開発者, I want CPU 使用率が時間とともに上がる現象（13.4% → 21.6%）の機序を確定したい, so that 欠陥として是正すべきか、正常な定常到達として容認できるかを判断できる

#### Acceptance Criteria

1. When 長時間（20 分超）の実走 CPU 時系列が得られた, the 判定スクリプト shall CPU 使用率が頭打ち（定常到達）へ収束するか、単調上昇を続けるかを機械判定する
2. If 是正後も CPU の時間上昇が観測され頭打ちに収束しない, the 開発プロセス shall 未知の機序として実測データを添えて記録し、本 spec の範囲で是正可能かを判定のうえ、範囲外であれば独立した課題として起票する
3. The 判定スクリプト shall 切り分けの判定根拠（収束判定の方法と閾値）を較正値として明記する

### Requirement 6: 回帰を固定する決定論テスト

**Objective:** As a 開発者, I want 是正後の状態を決定論的な自動テストで固定したい, so that 将来の変更で毎フレームアロケーションが静かに復活しない

#### Acceptance Criteria

1. The 自動テスト shall 定常状態での表示用バッファ新規確保が 0 であることを、アロケーション回数・呼出回数などの決定論的な量で検証する
2. The 自動テスト shall 実時間（経過ミリ秒等）を合否条件に使わない（実時間の閾値判定は実機実走の判定スクリプト側にのみ置く）
3. The 自動テスト shall 純 x64 の決定論テストとして常時のテスト実行に含まれる
4. The 自動テスト shall 是正後の毎フレーム経路の表示結果が是正前と同一入力でバイト等価であることを固定する

### Requirement 7: キャッシュ容量変更の裁定ゲート

**Objective:** As a 開発者, I want 承認済み要件である合成キャッシュ容量（容量 1）の変更が黙って行われないこと, so that 承認済み仕様の一貫性と変更手続きが守られる

#### Acceptance Criteria

1. The 本 spec shall 合成キャッシュの容量変更を、開発者の明示的な裁定なしに実装しない（自律ループの唯一の例外）
2. If 再測の結果、残る最大内訳がキャッシュ不命中による再合成コストである, the 開発プロセス shall 容量拡大の選択肢（容量の根拠・置換方式・上流の承認済み要件の改訂手続き）を実測データつきで開発者へ提示する
3. Where 開発者裁定で容量変更が承認された, the 本 spec shall その変更を本 spec 内で実施し、上流の要件文書・関連する宣言の改訂を追随させる
