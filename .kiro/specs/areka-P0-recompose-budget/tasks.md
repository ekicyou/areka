# Implementation Plan

> 段階ループ（design.md Flow 1）と 1:1 対応する。第 0 段（観測）と第 1 段（計測資産）は表示コードの挙動を変えない。是正（第 2 段）の着手順は第 1 段の実測が決める（3.2 のゲート）。

- [x] 1. 第0段: 観測基盤の導入（計時と確保計数・表示結果は不変）
- [x] 1.1 段階別計時の記録器とサマリ行の出力を新設
  - 1 回の表示適用について、キャッシュ照会・合成・リサンプル・当たり判定マスク生成・供給面転写・合計の所要を記録する器を表示層に置く
  - 行には段階別の所要に加え、適用対象の識別子・引き当ての可否・run 内で安定な合成キーのハッシュを持たせる（命中率とキャッシュ容量の裁定材料を後段が機械抽出できるようにする）
  - 計測は無条件に実行し、出力の有無のみログ水準のフィルタに委ねる（表示経路がログ設定で分岐しない）
  - 固定文言・全段フィールド常時出現（実行されなかった段は 0）・1 適用 1 行のスキーマで出力する
  - 観測可能な完了状態: 単体テストで、記録器が固定文言と全段フィールドを備えた行を 1 本生成し、実行されなかった段が 0 で出ることを確認できる
  - _Requirements: 1.1, 1.2, 1.5, 7.2_
  - _Boundary: FrameTiming_

- [x] 1.2 バッファ確保の計数シームを新設（席の再利用は第2段）
  - 毎フレーム経路の確保発生点（合成先・リサンプル先・リサンプル作業領域・当たり判定マスク）ごとのカウンタを持つ器を置く
  - 現時点では各発生点が確保のたびに計数する（是正後は同じシームが再利用の可否を計数する）
  - 適用単位の増分と累積の両方を露出し、増分は計時行のフィールドへ同居させる
  - 観測可能な完了状態: 単体テストで、確保が起きたときだけカウンタが増え、増分の取り出しでリセットされることを確認できる
  - _Requirements: 1.3_
  - _Boundary: FrameBudget_

- [x] 1.3 表示適用の毎フレーム経路へ計時点と計数を配線
  - 表示対象の状態に計数器の席を 1 つ持たせ、適用をまたいで存続させる（累積カウンタの所有者を確定する）
  - 各段の境界で所要を記録し、既存の表示成立点ログの直後に計時行を出力する
  - 早期復帰の経路では出力しない（成立点の対のみ）
  - 既存の表示成立点ログ（文言・水準・フィールド）と、面の入れ替えから供給面転写までの帯の分岐・呼出順序・エラー経路は変更しない
  - 観測可能な完了状態: 既存テストが全て通り、実走ログで表示成立行と計時行が同一適用の対として隣接して出る
  - _Requirements: 1.1, 1.3_
  - _Depends: 1.1, 1.2_

- [x] 1.4 計時ログの較正テストを追加
  - 計時行の固定文言・ログ水準・全段フィールドの出現を検証する
  - 既存の表示成立点ログの文言・水準・全フィールドが不変であることを同時に固定する
  - 「出ないこと」の主張は同一の捕捉スコープ内で陽性と陰性を対で観測する
  - 実時間を合否に使わず、純 x64 の常時テストに含める
  - 観測可能な完了状態: 計時行の文言やフィールドを 1 つ壊すと赤になり、既存の表示成立点ログを変えても赤になる
  - _Requirements: 1.4, 1.5, 6.2, 6.3_
  - _Depends: 1.3_

- [ ] 2. 第1段: 計測資産の新設（リポジトリ共通の恒久置き場・製品コード非接触）
- [x] 2.1 (P) 有界実走と CPU 時系列採取のランナーを新設
  - 短時間（7 分程度）・長時間（20 分超）の 2 水準と、開発ビルド・リリースビルドの指定で実走を起動する
  - 静寂状態の明示確認がない場合は起動を拒否する（測定条件の保証を機械化する）
  - 実行ログ・CPU 時系列・実行条件（ビルド種別・水準・開始終了時刻・マシン識別）を 1 つの出力先へ収める
  - 起動失敗・カウンタ取得失敗は即エラー終了し、部分成果を残さない
  - 観測可能な完了状態: 1 コマンドで実走が有界終了し、出力先に実行ログと CPU 時系列と実行条件が揃う
  - _Requirements: 2.1, 2.3, 2.6, 2.7_
  - _Boundary: invoke-perf-run_

- [ ] 2.2 (P) 集計モードを新設
  - 計時行から段階別 p50/p95・キャッシュ命中率・コマ適用間隔・確保計数を集計し、CPU 時系列から統計を出す
  - 進行境界スキップの件数は既存ログの実文言で数える
  - 必要なログ種の欠落・段フィールドの欠落は部分集計を出さずエラーとして報告する
  - 較正値（間隔の期待値・許容率・測定窓の定義・アイドル CPU 目標・文言一覧）をスクリプト冒頭に明記し、出力先頭にマシン条件を併記する
  - キャッシュ容量の裁定材料として合成キーの異なり数を集計する
  - 観測可能な完了状態: 実走ログと CPU 時系列を渡すと集計レポートが出て、段フィールドを 1 つ削ったログでは部分集計を出さずエラー終了する
  - _Requirements: 2.2, 2.5, 2.6, 4.5, 7.2_
  - _Boundary: judge-perf 集計_
  - _Depends: 1.1, 1.2_

- [ ] 2.3 判定モードを追加
  - 合格判定式のうち間隔・進行境界スキップ・確保計数を両ビルドへ、アイドル CPU をリリースビルドのみへ適用する
  - CPU 時系列が頭打ちへ収束するか単調上昇を続けるかを機械判定し、収束判定の方法と閾値を較正値として明記する
  - 観測可能な完了状態: 合格・不合格・判定不能・引数不正が終了コードで区別され、判定根拠が較正値つきで出力される
  - _Requirements: 4.2, 4.3, 5.1, 5.3_
  - _Depends: 2.2_

- [ ] 2.4 判定スクリプトの自己較正セットと手順書を用意
  - 合格・不合格・観測ゼロの 3 態を再現する既知ログ断片を用意し、期待どおりの終了コードを逐語再現する自己検査を持たせる
  - 手順書に 2 水準の使い分け（長時間はベースラインと最終判定のみ・中間の是正ループは短時間）・静寂確認の運用・同一手順再測の条件・較正値の所在・未知の機序を記録して独立課題として起票する手順を書く
  - 観測可能な完了状態: 自己検査が 3 態とも期待終了コードを逐語再現し、赤も必ず出る
  - _Requirements: 2.4, 2.6, 5.2_
  - _Depends: 2.1, 2.3_

- [ ] 3. 第1段実行: ベースライン採取と支配項の確定
- [ ] 3.1 ベースラインを 2 水準で採取
  - 開発者へセッションを渡して静寂状態の確認を得てから実走する
  - 短時間水準を開発ビルドとリリースビルドの両方で、長時間水準をリリースビルドで採取する
  - 観測可能な完了状態: 3 通りの実走の出力（ログ・CPU 時系列・実行条件）が揃い、集計モードが欠落なしで通る
  - _Requirements: 2.1, 2.7_
  - _Depends: 1.3, 2.1, 2.2, 2.4_

- [ ] 3.2 是正前の内訳を確定して着手順を裁定
  - 段階別所要・確保計数・命中率・間隔・CPU 時系列から支配項を特定する
  - 設計の仮説（確保と解放の繰り返しが支配的）と実測が食い違う場合は、支配項の是正設計を設計文書へ追補してから着手する
  - 観測可能な完了状態: 支配項の内訳表と着手順の根拠が spec 配下の成果物として残り、仮説と食い違った場合は該当段の是正設計が設計文書へ追補されている
  - _Requirements: 3.4_
  - _Depends: 3.1_

- [ ] 4. 第2段: 上流クレートへの追加 API（既存の意味は変えない）
- [ ] 4.1 (P) リサンプルの作業領域受け取り形を追加
  - 呼び手が作業領域を所有できる形を追加し、既存のリサンプルはその形へ委譲する（挙動不変）
  - 既存の項目・公開名は一切変更せず追加のみ行う（同一ファイルを並走 spec が編集するため・先着した側の実形へ後着側が追随する）
  - 作業領域の中身は外へ見せず、出力幅に到達した後は容量が成長しない
  - 既存形と追加形が同一入力でバイト等価であること、作業領域が再利用で成長しないことをテストで固定する
  - 観測可能な完了状態: 等価テストと容量非成長テストが緑で、既存のリサンプル利用箇所は無修正のまま通る
  - _Requirements: 3.1, 6.2, 6.3_
  - _Boundary: emo-compose 拡大縮小_
  - _Depends: 3.2_

- [ ] 4.2 (P) 当たり判定マスクの再生成と共有供給を追加
  - 既存バッファを再利用して内容を作り直す形を追加する（寸法が縮む方向でも前の内容が残らない）
  - マスク資源の内部表現を共有参照へ変え、共有供給の口を追加する（既存の設定・取得の見た目と挙動は不変）
  - 追加形と既存形が同一入力で等価であることをテストで固定する
  - 観測可能な完了状態: 等価テストが緑で、当たり判定の既存テストが全て無修正で通る
  - _Requirements: 3.1, 6.2, 6.3_
  - _Boundary: wintf 当たり判定マスク_
  - _Depends: 3.2_

- [ ] 5. 第2段: 表示側の再配線（定常アロケーション完全ゼロ）
- [ ] 5.1 合成キャッシュに容量回収を追加し、呼出側を最小追随させる
  - 追い出すエントリを取り出して容量を回収する口を設ける（容量 1・キー完全一致・表示とマスクの原子対という承認済みの意味論は不変）
  - マスクは生成済みのものを引数で受け取る形にし、エントリは共有参照で持つ
  - 呼出側（表示適用経路と既存のキャッシュテスト）を同一タスク内で最小限追随させる（クレートが常に緑のまま進む整合作業）
  - 観測可能な完了状態: 容量回収後の挿入でも承認済みの意味論が保たれ、回収したバッファの容量が引き継がれることがテストで固定され、クレート全体が緑で通る
  - _Requirements: 3.1_
  - _Depends: 4.2_

- [ ] 5.2 既存の席へ再利用バッファを足し、計数を再利用の可否へ切り替え
  - 合成先の常設席・リサンプル作業領域の席・マスクの輪番（2 スロット・空きスロットへ作り直し）を既存の計数器の席へ足す
  - 表示バッファはキャッシュから回収した容量で回す
  - 席が期待どおり再利用できない境界では黙って確保せず、必ず計数に現す
  - 観測可能な完了状態: 初回確保後の再取得で計数増分が 0 になり、寸法変化時は 1 回だけ増えてまた 0 に戻ることが単体テストで固定される
  - _Requirements: 1.3, 3.1, 3.2_
  - _Depends: 4.1, 4.2, 5.1_

- [ ] 5.3 表示適用の毎フレーム経路を再利用形へ再配線
  - 合成をバッファ受け取り形へ切り替え、拡大率が等倍のときは合成先と表示バッファを入れ替えで交代させる（複写しない）
  - 容量回収は合成成功後に限る（失敗時に表示とキャッシュが適用前のまま保たれる）
  - マスクの下流供給を共有参照の受け渡しへ置き換える（面の入れ替え帯の中は 1 文の置換にとどめる）
  - 面の入れ替えから供給面転写までの帯の構造・転写失敗の分岐・既存の表示成立点ログは不変に保つ
  - 観測可能な完了状態: 既存テストが全て通り、短時間実走のログで確保計数が定常状態で 0 になる
  - _Requirements: 3.1, 3.2_
  - _Depends: 5.2_

- [ ] 6. 第2段の固定: 決定論テスト
- [ ] 6.1 定常アロケーション 0 のテストを追加
  - 2 パターン交互適用（毎回引き当て外れ）で暖機した後、確保計数の増分 0・合成先と表示バッファの先頭位置不変・マスク輪番の 2 本集合不変を反復で検証する
  - 拡大率が等倍の経路（入れ替えで交代する 100% 表示の一般条件）でも同じ検証を行う（2 本集合の交互を許容する形）
  - 中身が空の実装で偽の合格が出ないよう、不透明画素が存在することを併せて確認する
  - 実時間を合否に使わず、純 x64 の常時テストに含める
  - 観測可能な完了状態: 再利用を 1 箇所でも壊すとテストが赤になる
  - _Requirements: 3.1, 3.2, 6.1, 6.2, 6.3_
  - _Depends: 5.3_

- [ ] 6.2 新旧経路のバイト等価テストを追加
  - 是正前の経路をテスト向けに残し、是正後の経路と同一入力で表示バイトと当たり判定マスクが一致することを固定する
  - 拡大率が等倍・非等倍の両方で行う
  - 既存の表示面往復テストが是正後もそのまま成立することを確認する
  - 実時間を合否に使わず、純 x64 の常時テストに含める
  - 6.1 と同じテスト接続宣言のファイルを編集するため並列実行しない（6.1 の後に行う）
  - 観測可能な完了状態: 是正が絵と当たり判定を 1 バイトも変えないことがテストで固定される
  - _Requirements: 3.3, 6.2, 6.3, 6.4_
  - _Depends: 6.1_

- [ ] 7. 第3-4段: 再測・機械判定・裁定ゲート
- [ ] 7.1 是正後の再測と合否判定
  - 静寂状態の確認を得たうえで、ベースラインと同一手順・同一 fixture で短時間水準の再測を両ビルドで行う
  - 間隔・進行境界スキップ・確保計数の判定を両ビルドへ適用する
  - 不合格なら残る最大内訳を特定して是正へ戻る。ただし残る最大内訳がキャッシュ不命中による再合成コストの場合は裁定ゲートへ回す
  - 観測可能な完了状態: 判定が終了コードで機械的に出て、合否と残る最大内訳が根拠つきで示される
  - _Requirements: 2.7, 4.1, 4.2, 4.3, 4.6_
  - _Depends: 6.1, 6.2_

- [ ] 7.2 長時間水準の最終判定と CPU 時間上昇の切り分け
  - 長時間水準で最終合格判定を行い、リリースビルドのアイドル CPU が目標を下回ることを確認する
  - CPU 時系列が頭打ちへ収束するか単調上昇を続けるかを機械判定し、判定根拠を較正値として残す
  - 収束しない場合は未知の機序として実測データを添えて記録し、本 spec の範囲で是正可能かを判定して範囲外なら独立した課題として起票する
  - 観測可能な完了状態: 長時間走行の判定が合格で、CPU の時間上昇について収束か未知機序かの結論が実測つきで残る
  - _Requirements: 2.7, 4.4, 5.1, 5.2, 5.3_
  - _Depends: 7.1_

- [ ] 7.3 キャッシュ容量の裁定ゲート運用
  - 再測の残余最大項が再合成コストの場合のみ、必要スロット数の実測（合成キーの異なり数）・置換方式・上流の承認済み要件の改訂手続きを添えて開発者へ提示する
  - 裁定が下りない限り容量を変更しない（本実装は容量 1 を前提に構築されており容量変更の経路を持たない）
  - 承認された場合のみ本 spec 内で変更を実施し、上流の要件文書と関連する宣言を追随改訂する
  - 観測可能な完了状態: 容量に触れずに合格した場合はゲート不発として記録が残り、提示に至った場合は実測つきの裁定材料が揃う
  - _Requirements: 7.1, 7.2, 7.3_
  - _Depends: 7.1_

## Implementation Notes

- **1.1 → 1.3 への申し送り（3 件）**:
  1. `timing.rs` の `compose_key_hash` は `PatternFrame.method` を `std::mem::discriminant` で混ぜているため、`Blend(Multiply)` と `Blend(Screen)` が同一ハッシュになる（系統的衝突・要件 7.2 の異なりキー数を過少に見積もる向き）。`method` が合成を駆動しない現状（`areka-emo-compose/src/pattern.rs:38`）ゆえ emo2 ベースラインでは到達しないが、1 行で修復可能（`if let ComposeMethod::Blend(mode) = &frame.method { discriminant(mode).hash(&mut hasher); }`）。1.3 の配線時に併せて入れ、等価テストへ `assert_ne!` 節を追加すること。
  2. ~~`timing.rs` の `AllocCounts` を 1.2 の `BudgetDelta` と統合すること~~ → **1.2 で解消済**（`AllocCounts` を削除し `budget.rs` の `BudgetDelta` に一本化。perf 行スキーマは `efc960b` とバイト同一であることをレビューで検証済み）。
  3. `timing.rs` 冒頭の `#![allow(dead_code)]` は未配線状態専用。1.3 の配線で必ず外すこと（外すと 14 件の dead_code 警告が出る状態＝全項目がテストで踏まれていることは検証済み）。
- **1.2 → 1.3 への申し送り（2 件）**:
  1. `budget.rs` 冒頭にも `#![allow(dead_code)]` がある（未配線専用・非 test ビルドで 7 件の警告、`cargo test --lib --no-run` では 0 件＝全項目がテストで踏まれていることを検証済み）。1.3 の配線コミットで `timing.rs` のものと併せて外すこと。
