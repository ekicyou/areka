## 3. 決定実験: リサンプル段の中身は「確保」か「計算」か

### 3.1 なぜ実験が要ったか

design.md の D2／D9／D10 と要件 3.1 は「毎コマ 4MB 級の確保と解放の繰り返しが支配的」という仮説の上に立つ。
実測はリサンプル段が支配的だと言うが、**リサンプル段の中には確保もゼロ埋めも計算も全部入っている**。
「リサンプル段が重い」だけでは仮説の当否は決まらない。要件 3.4 は推測ではなく実測で着手順を決めよと言っているので、
段の中身を確保と計算へ割る実験を行った。

### 3.2 実験の作り

`areka-emo-compose` のクレート内部に使い捨ての計測コードを置き、実測後に削除した（リポジトリには残していない）。
入力は実機と同じ 382×547 → k=2/1 → 764×1094（835,816 画素・3,343,264 バイト）。
`ComposedSurface::resize_and_clear` と `bytes_mut` はクレート内部からのみ届くため、クレート内に置く必要があった。

測った量:

| 記号 | 内容 |
|---|---|
| (A) | 毎回まっさらな `out` を起こして `resample`（確保＋ゼロ埋め＋写像表＋計算＋解放）＝**本番の毎コマの形** |
| (B) | `out` を使い回して `resample`（ゼロ埋め＋写像表＋計算・確保と解放なし）＝**是正後に相当** |
| (C) | `resize_and_clear` だけ（＝出力バッファのゼロ埋め） |
| (D) | リサンプルの内側 2 重ループだけ（＝計算そのもの。ゼロ埋めも写像表構築も含まない） |
| (E) | x 軸写像表の構築だけ |
| (F) | 3.3MB の `Vec` を確保＋ゼロ埋め＋解放するだけ |
| (G) | `vec![0u8; n]`（OS のゼロページを使う形）だけ |

(A) と (B) は**交互に測った**——連続して片方を回すと、クロックや温度の変化が片方だけに乗る。

### 3.3 道具が正しいものを測っている証拠（対照）

1. **(D) の内側ループは `resample` の逐語複製であり、同一入力に対する出力が `resample` とバイト等価であることを毎回検査した**（不一致なら試験は失敗する）。あわせて出力が全 0 でないことも検査した——空の計算を測って速いと言う経路を塞ぐため。
2. **確保と解放の代金を 2 通りの独立した方法で測り、値が一致した**: 引き算 (A)−(B) = 609〜634 マイクロ秒 と、3,343,264 バイトの確保・解放だけを 2,000 回測った直接測定 554〜629 マイクロ秒。
3. **(G) と (F) の差**（11.8 対 1,237 マイクロ秒・約 100 倍）が出ることで、この計測が「OS のゼロページで済む確保」と「本当にメモリを 0 で埋める確保」を区別できていることが分かる。区別できない計測なら両者は同じ値になる。
4. 同じ実験を 2 回繰り返し、結論の数字（下表）が再現することを確認した。

### 3.6 実験が確定させたこと

**リサンプル段の 74〜78% はリサンプルの計算そのものであり、確保と解放は 2〜8% にすぎない。**
言い換えると、**設計の仮説（確保と解放の繰り返しが支配的）は成立しない。**

release long の実測へ按分すると、1 コマ適用（合計 p50 = 14,917 マイクロ秒）の内訳は次のようになる。
（按分＝実測の割合 × 実測の段所要。この行だけは実測値そのものではなく計算値である。）

| 中身 | 1 コマあたり（マイクロ秒） | 合計に対する割合 | 根拠 |
|---|---:|---:|---|
| リサンプルの計算 | 約 7,400〜7,620 | **約 50%** | 段 9,938 × 74.5〜76.7% |
| 合成（blit）の計算 | 約 2,060 | 約 14% | 段 2,267 − 合成先のゼロ埋め 200 − 確保解放 6 |
| リサンプル出力のゼロ埋め | 約 924 | 約 6% | 段 9,938 × 9.3% |
| **是正対象の確保・解放の総額** | **約 568〜643** | **約 4%** | 3.5 節の直接測定の合計（A1 6.0＋A2 554〜629＋A3 5.6＋A4 ≒0＋A7 2.7） |
| マスク生成の計算・その他 | 残り | — | — |

補足 2 点:

- **表示バッファの確保は `t_resample_us`、その解放は `t_mask_us` に計上される**（解放は `cache.insert` のスロット置換で起きる）。3.5 節の「確保＋解放のみ」は両方を合わせた 1 組の値なので、二重に数えていない。
- 逆に言えば、`t_mask_us`（release long で 1,123 マイクロ秒）の中に 3.3MB の解放が含まれており、これが 550 マイクロ秒級だという 3.5 節の測定と矛盾しない。「4MB 級の確保と解放が 10 ミリ秒かかっているなら `t_mask_us` が 1.1 ミリ秒で収まるはずがない」という読みは、直接測定でも裏が取れた。

### 3.7 計算はなぜ遅いのか（測った範囲での事実）

- 計算だけで 6,111〜6,220 マイクロ秒／835,816 画素 = **1 画素あたり 7.31〜7.44 ナノ秒**（release）。
- 同じ 3.3MB の出力を単に 0 で埋めるだけなら 745.8〜757.7 マイクロ秒（1 画素 0.89〜0.91 ナノ秒）。
  つまり**計算は、自分の出力を 1 回書き潰すだけの作業の 8.1〜8.3 倍**の時間を使っている。出力の書き込み帯域で頭打ちになっているのではなく、計算で詰まっている。
- 実装（`crates/areka-emo-compose/src/scale.rs:455-463` の `resample`）は、出力 1 画素につき 4 チャンネルを個別のループで回し、1 チャンネルあたり 4 近傍のバイトを添字アクセスで読み（範囲検査つき）、**u32 の掛け算 4 回**（`p00·inv_wx`・`p01·wx`・`p10·inv_wx`・`p11·wx`）**と u64 の掛け算 2 回**（`top·inv_wy`・`bottom·wy`）、加算とシフトを行う。1 画素あたり **16 回の範囲検査つきバイト読み出しと 24 回の乗算**になる。
- 計測環境の断り: この実験は 1 スレッドで他の負荷なしに回した値である。実機の release long の `t_resample_us` p50 = 9,938 マイクロ秒に対し実験の (A) は 8,105〜8,207 マイクロ秒で、21% ほど実機のほうが重い（実機はアプリ全体が同時に動いておりキャッシュを分け合うため）。**割合の話には影響しない。** dev は実験 61 ミリ秒に対し実機 277 ミリ秒と 4.5 倍離れており、dev の絶対値は実機の代理にならない（割合は release と同じ形なので、割合の結論のみ dev にも使う）。

## 5. コマ適用間隔（判定式⑴）——現状の書き方では判定できない

### 5.1 何が起きているか

release short・窓 A・`TargetId(0)/surface_id=1000` の生の分布は
n=236・最小 8.5ms・**p50 145.2ms**・**p95 6,829.7ms**・最大 25,945.4ms である。
p95 が 6.8 秒なのは、この系列が性質の違う 3 種類の間隔を混ぜているからである。

1. アニメ 1 サイクルの中のコマ間隔（判定したいのはこれ）
2. サイクルとサイクルの間の待ち時間（まばたきは数秒に 1 回しか起きない。**この空白は正常**）
3. 会話などで別の絵に切り替わったときの間隔

ウォームアップ除外でも「複数アニメ重畳の除外」でも 2 は消せない。**空白そのものが正常な状態だから**である。

### 5.2 較正値 172ms はコマ間隔ではなくサイクル全長だった

emo2 のアニメ定義（`crates/pilot/examples/shiori-host-32/fixtures/emo2/shell/master/surfaces.txt`）を読むと:

| アニメ | 対象 | コマの待ち時間 | サイクル全長 |
|---|---|---|---:|
| `animation1400`（まばたき・通常） | キャラ `surface1000` | 0 → **150** → **22** | 172ms |
| `animation1401`／`animation1402`（半目・ジトー） | キャラ `surface1000` | 0 → **150** | 150ms |
| `animation0`（ベース 2100） | ケロ `surface2100` | 0 → **40** → **80** | 120ms |
| `animation0`（ベース 2110） | ケロ `surface2110` | 0 → **160** | 160ms |

**172ms は 150 と 22 の和であり、コマとコマの間隔ではない。** 実際のコマ間隔は 150ms と 22ms の 2 種類である。
実測の p50 が 145.2ms と 172 を下回っていたのはこのためで、異常ではない
（3 コマのサイクルは「22ms 級の間隔」「150ms 級の間隔」「サイクル間の空白」をほぼ 1:1:1 で生むので、中央値は 150ms の群に落ちる）。

要件 4.2⑴ の「アニメ定義の指定間隔」を単一の値と読む限り、**このアニメには当てはまる単一の値が存在しない**。これが⑴が現状のままでは評価できない第 1 の理由であり、第 2 の理由が 5.1 の混在である。

### 5.3 実装できる窓の定義（本書で確定させる案）

seriko の発火ログは対象と アニメ ID を持っている。実測で確認した内訳:

```
seriko: loop 抽選発火 … scope="0" slot=Shell animation_id=1400  212 件
seriko: loop 抽選発火 … scope="0" slot=Shell animation_id=1402   28 件
seriko: loop 抽選発火 … scope="1" slot=Shell animation_id=0     109 件
```

`scope="0"` がキャラ（`TargetId(0)`・`surface_id=1000`）、`scope="1"` がケロ（`TargetId(2)`）である。
これを使い、**発火を起点にサイクルの中だけを切り出す**。

> **判定式⑴の窓（確定案）**
>
> 判定対象の系列（`target_id` × `surface_id`）の連続する 2 回の適用時刻 (a, b) について、次を全て満たす間隔だけを判定に使う。
>
> 1. その系列に対応する `scope` の「loop 抽選発火」のうち、`a` 以前で最も新しいものの時刻を f とする（存在しなければ対象外）
> 2. `a − f ≤ CYCLE_SPAN_MS`（そのアニメ定義の**サイクル全長**。emo2 のキャラは 172ms）
> 3. 区間 (a, b] の中に新しい「loop 抽選発火」が無い
> 4. `a` と `b` の両方で、**1 と同じ `scope` の**推定活性アニメ本数が
>    `FRAME_INTERVAL_IDLE_MAX_ACTIVE`（=1）以下（task 7.1 準備で追加。下の注記を参照）
>
> 上限は `FRAME_MAX_WAIT_MS ×（1＋許容率）`。`FRAME_MAX_WAIT_MS` は**そのアニメ定義に現れる最大のコマ待ち時間**（emo2 のキャラは 150ms）。
> 許容率 15% なら上限は 172.5ms。

条件 3 がサイクル間の空白を落とし、条件 2 が「発火とは無関係な適用」を落とす。
停止ログは使わない——停止ログは最後のコマの適用より先に出ることがあり、窓の終端に使うと最後のコマが毎回落ちるため（実測で確認済み）。

### 5.5 この定義の弱点（隠さず書く）

- **遅くなるほど判定対象の本数が減る。** 条件 2 の起点合わせにより、コマが遅れるほど 2 コマ目以降が窓から外れる。dev では 272 本のうち 22 本しか残らず、較正値 `FRAME_INTERVAL_MIN_SAMPLES = 30` を下回る。
  自動選別のままだとこの系列が除外され、既定の規則（`FRAME_INTERVAL_EXCLUSION_BLOCKS_PASS`）により結果は「判定不能」になる——**合格に化けることはない**が、本当は不合格である走行を不合格と言えない。
  → **task 3.1 の較正として `FRAME_INTERVAL_JUDGED_SERIES` に `TargetId(0) × surface_id=1000` を明示指定し、`FRAME_INTERVAL_MIN_SAMPLES` を 20 以下へ下げること。** 明示指定すれば除外は意図的になり、合格・不合格の判定が再び意味を持つ（設計 D7 の規定どおり）。
- **ケロ側（`TargetId(2)`）はこの定義では判定できない。** ケロのアニメ ID は複数のベースサーフェスで同じ `0` であり、待ち時間もベースごとに違う（2100 は 40/80、2110 は 160）。さらに 1 サイクルの中でベースサーフェスが変わるため、`target_id` × `surface_id` の系列が 1 つのアニメ定義と対応しない。判定対象から外すのが正しい（回数も release short で 16 本と少なく、いずれにせよ判定に耐えない）。
- **同一鍵に 2 本のアニメが重畳する区間は、条件 1〜3 だけでは落とせない。**（task 7.1 準備で追記）
  系列鍵は `target_id × surface_id` でありアニメ単位ではないので、キャラの `surface1000` で
  `animation1400` と `1402` が同時に走ると、隣接差はどちらのアニメのコマ間隔でもなくなる。
  混ざり方の位相しだいで偽の不合格にも**偽の合格**にも倒れる。
  → 窓へ**条件 4**（両端の推定活性アニメ本数 ≦ `FRAME_INTERVAL_IDLE_MAX_ACTIVE = 1`）を追加して塞いだ。
  **数えるのは同じ `scope` のアニメだけである**——別 `scope` は別の系列鍵へコマを出すので、
  ケロが動いていることはキャラのコマ送りについて何も語らない（design.md §A6-2）。
  なおこの 3 走行では `1400` と `1402` が同時に走っていた区間は 1 つも無く、
  条件 4 が実際に落とした間隔は **0 本**である（この見張りは `P13`・`P14` の形が来たときに働く）。
  残るのは「発火ログを出さない書き換えが同一鍵へ混ざる形」だけである（fixture `P12` に記録）。
- 上の 3 点は**ログの持っている情報の限界**であって、窓の定義の失敗ではない。ケロまで判定したいなら発火ログにベースサーフェス ID を足す必要があり、それは本 spec の範囲外の改修になる。

### 5.6 較正値台帳への反映（task 3.1 の登記事項）

| 較正値 | 現在 | 確定すべき値 | 理由 |
|---|---|---|---|
| `FRAME_INTERVAL_EXPECTED_MS` | 172.0（コマ間隔として） | **150.0**（＝アニメ定義の最大コマ待ち） | 172 はサイクル全長であってコマ間隔ではない（5.2） |

| `FRAME_INTERVAL_MIN_SAMPLES` | 30 | 20 以下 | 5.5 |

## 7. 支配項と着手順の根拠

### 7.1 確定した支配項

**1 コマ適用の約 50% はリサンプルの計算そのものである。**
根拠は 3.4 節の決定実験（リサンプル段の 74〜78% が計算・確保と解放は 2〜8%）と、3.5 節の発生点ごとの直接測定（是正対象の確保・解放の総額は 1 コマあたり約 568〜643 マイクロ秒＝合計の約 4%）である。
2 通りの独立した方法が同じ値を出しており、対照（複製ループのバイト等価・ゼロページと実ゼロ埋めの区別）も取れている。

これは **design.md の D2／D9／D10 と要件 3.1 が置いた仮説の否定**である。要件 3.4 の定めにより、
支配項の是正設計を design.md へ追補した（「実測に基づく是正設計の追補（task 3.2）」節）。

### 7.2 着手順（提案とその根拠）

| 順 | 何を | 1 コマあたりの見込み | 根拠 | 前提 |
|---|---|---:|---|---|
| **0** | 要件 7 の裁定ゲートを開く（本書を材料として提示する） | 命中した適用は合成・リサンプル・マスクがまるごと消える。容量 3 で命中率 4.4% → 58.7% | 4 節 | **開発者の裁定が要る（要件 7.1）**。コードは書かない |
| **1** | 定常アロケーション 0（既定の tasks 4.x／5.x・設計変更なし） | 約 568〜643 マイクロ秒（合計の約 4%） | 3.5 | 承認済み要件 3.1。**2 の前提でもある** |
| **2** | リサンプル出力の冗長なゼロ埋めを止める | 約 924 マイクロ秒（合計の約 6%） | 3.4 (C) | **1 の完了が前提**（下記） |
| **3** | リサンプルの計算を速くする | 約 7,400〜7,620 マイクロ秒（合計の約 50%） | 3.4 (D)・3.7 | **Non-Goals の解釈が要る（7.3）** |

順の根拠:

- **0 を先に置く理由**: 3.0% という目標に対し現状は 24.9% であり、1〜3 を全部足しても届かない見込みが高い（1＋2 で約 10%、3 で計算が半分になってもさらに約 25%）。命中率の改善だけが桁を変えうる唯一の手であり、しかもこれは**コードではなく裁定**なので、着手の待ち時間が他の作業を止めない。裁定を待つ間に 1〜3 を進められる。
- **1 を 2 の前に置く理由（技術的な前後関係）**: ゼロ埋めを安全に省けるのは「バッファを使い回していて長さが既に一致している」場合だけである。安全な Rust では**新しく確保したメモリを初期化せずに使うことはできない**ので、毎コマ新規確保している現状ではゼロ埋めを外せない。バッファの使い回し（1）が入って初めて「長さが変わらないときは何もしない」形が成立し、そのとき初めて 2 の 924 マイクロ秒が消える。
  （念のため: 決定実験の (G) `vec![0u8; n]` が 11.8 マイクロ秒と極端に速いのは、OS のゼロページが**触られるまで実体化しない**からであって、ゼロ埋めが安く済むという意味ではない。実際に書き込めばページフォルトとして同じ代金を払う。ここを「安い確保に替えれば済む」と読んではならない。）
- **1 の効果は約 4% にすぎないが、大きさで判断しない理由**: **要件 3.1 は承認済みであり効果の大小を条件にしていない。** 要件 6.1 の回帰テストも定常確保 0 を固定するよう定めている。加えて 2 の前提でもあるので、1＋2 を一括で約 10% と見るのが実態に近い。
- **3 を最後に置いた理由**: 効果は最大（約 50%）だが、範囲の内外に開発者の判断が要る（7.3）。判断待ちで 1・2 を止める必要はない。

### 7.3 開発者の判断が要る点

**「リサンプルの計算を速くする」が Non-Goals の内側か外側か。**

design.md の `### Non-Goals` は「合成アルゴリズム本体（`build_plan`／`blit::execute`）の最適化」を除外している。
`resample` は `scale.rs` にあり、この列挙には**含まれていない**。`Boundary Commitments` の `This Spec Owns` には
「上流への additive API 追加: emo-compose `resample_with`」があり、`Out of Boundary` には
「`scale.rs` の既存項目の変更——追加は関数＋opaque 型のみ」とある。
文言どおりに読むと、**`resample` の中身を書き換えるのは `Out of Boundary` に触れる**（既存項目の変更にあたる）。

本書は範囲を勝手に広げない。判断は次の 3 択で、開発者に委ねる。

1. 本 spec の範囲に取り込む（`Out of Boundary` の「`scale.rs` の既存項目の変更」を改訂する）
2. 別 spec として起票する（本 spec は着手順 0・1・3 で着地させ、再測で残る最大内訳として引き渡す）
3. 現状のまま据え置く（3.0% 未満は本 spec では達成不能と確定させる）

なお着手順 1（冗長なゼロ埋めの除去）も `resample` の中身に触れるので同じ判断の対象になる。
