### 2.4 ソース走査の部品をどうするか（要件 5.5・6.5 の中核）

`crates/log-capture-kit/tests/workspace_scan/mod.rs` には欲しい部品が揃っている:

- `walk_workspace_sources()`（`:79`）＝ `crates/**/*.rs` を昇順・重複無しで列挙。
- `read_source()`（`:113`）＝ ワークスペース根からの相対パスで読む。
- `workspace_root()`（`:64`）＝ 根の求め方。

**しかし 2 つの壁がある**:

1. **場所**。これは `log-capture-kit` の `tests/` 配下のモジュールで、`src/` には無い（`crates/log-capture-kit/src/` の一覧に `workspace_scan` は無い）。テストバイナリが `mod workspace_scan;` で取り込んで共有している形（`file_length_guard_test.rs:45`）であり、**他のクレートからは引けない**。
2. **向き**。同モジュールの `strip_comments()`（`:154`）は**コメントを取り除く**関数で、`scan_tokens()`（`:333`）はコメントを除いた本文から語を探す。本 spec が探したい正典 URL は**まさにその消される doc コメントの中にある**。つまり中心の関数はそのまま流用できず、必要なのは逆向きの「コメントだけを見る」走査である。

選択肢:

- **⒜ 新クレートに自前で持つ**。列挙と読み込みは 40 行程度で書ける。重複はするが、依存が増えず、`log-capture-kit` の宣言された役割（ログ捕捉の硬化機構・`structure.md:340`）を広げずに済む。
- **⒝ 列挙の部分を共有クレートへ出す**。`log-capture-kit` の `src/` へ移すか、新しい小さなクレート（例: `workspace-scan-kit`）を建てて両者が引く。重複は消えるが、`log-capture-kit` のテスト 3 本を書き換えることになり、**本 spec が「既存クレート非接触」と宣言した範囲を越える**（要件 9.1・`roadmap.md:91` の改変集合宣言）。
- **⒞ ⒜ で始め、重複が問題になったら ⒝ へ**。

現時点の実測（`roadmap.md:104` の干渉台帳が「survey ⇄ toolkit は 0」と宣言していること）を踏まえると **⒜ が宣言と整合する**。ただし「同じ列挙が 2 か所にある」状態は将来の陳腐化の芽であり、設計で明示的に裁定すべき事項。

### 2.6 スナップショットの読み取り手段

スナップショットは 2.7MB の JSON。ワークスペースに JSON の読み取り手段は**共通依存としては無い**（`crates/dola/Cargo.toml:21` の `serde_json` は dola の任意機能）。

- **⒜ `serde_json` を新クレートの直接依存として引く**（版はクレート側に書く＝`dola` の前例に倣えばルートの `Cargo.toml` を触らずに済む）。`serde_json` は MIT または Apache-2.0 で、`deny.toml:27-28` の許可一覧に両方ある＝関門は通る見込み（未確認: 実際に `cargo deny check` を通していない）。
- **⒝ ワークスペース共通依存に追加する**。ルートの `Cargo.toml` が変わるので、`roadmap.md:91` の「行変更なし」宣言と食い違う。
- **⒞ 自前の最小 JSON 読み取り**。依存は増えないが、2.7MB・入れ子・エスケープを自前で扱うのは割に合わない。しかも壊れた入力のエラー（要件 1.8）の質が落ちる。

**本文ハッシュ**（要件 1.2・8.2）は別の判断が要る:

- 標準ライブラリの既定ハッシュは**版をまたいで同じ値を返す保証が無い**。カタログに焼き込む値としては使えない（要件 1.5・8.2 が壊れる）。
- 選択肢: ⑴ `sha2` などの外部依存を引く（`.kiro/specs/completed/areka-P0-shiori-protocol/ukadoc/SOURCES.md:11-13` が sha256 を使っている前例と揃う）⑵ 自前で単純な決定的ハッシュ（FNV など）を 20 行ほど書く ⑶ 本文の長さ＋先頭末尾の抜粋のような弱い指紋。
- ⑴ は前例と揃い、衝突の心配が実質無い。⑵ は依存 0 だが「自前実装が本当に決定的か」を自分でテストする責任を負う。⑶ は要件 8.2 の変更検出としては弱い。
- なお sha256 の 16 進 64 文字を 1 行に入れると、**カタログ 1 行の最大長は 611 文字**（実測）。読みやすさの上限として設計で意識すべき数字。

## 3. 設計判断が要る事項（要件ディスカッションへ送る）

### 3-1. カタログの行数と「新設ファイルは 1,000 行未満」がぶつかる

- 要件 1.1 は「1 項目 1 行の `doc/ukadoc-coverage/catalog.toml`」を求める。項目は 1,749 件で、要件 1.6 の冒頭情報を足すと**約 1,760 行**になる。
- 要件 9.6 は「新設するファイルをいずれも 1,000 行未満に保つ」と書き、その理由に「ワークスペースのファイル行数上限テストの対象に自動的に入るため」を挙げる。
- **理由の部分は事実と違う**。上限テストの走査は `crates/` 配下の `.rs` だけ（`workspace_scan/mod.rs:79-86`・`:103`）。`doc/ukadoc-coverage/*.toml` は**機械的には一切見られない**。
- したがって「機械に叱られるから」という根拠では catalog.toml を縛れない。しかし要件の文言は「いずれも」なので、文字どおり読めば縛られる。

選択肢:

- **⒜ 上限の適用範囲を「新クレートの `.rs` ファイル」に限り、`doc/ukadoc-coverage/` 配下のデータファイルは対象外とする**（機械の実態に合わせる）。カタログは 1 ファイル・約 1,760 行。
- **⒝ カタログをページ別または担当ドメイン別に分割する**（例: `catalog/shiori.toml` 677 行・`assets.toml` 542 行・`sakura-script.toml` 342 行・`property.toml` 188 行）。全ファイルが 1,000 行未満に収まり、台帳と 1 対 1 で並ぶので見通しも良い。代わりに「カタログは 1 ファイル」という要件 1.1 の文言から外れる。
- **⒞ 1 項目 1 行をやめ、より密な形にする**（読みにくくなるので推奨しづらい）。

**台帳側も同じ計算が要る**: 1 行 1 項目なら shiori 677・assets 542・sakura-script 342・property 188 でいずれも 1,000 行未満に収まる。ただし 1 行に 10 欄（id・状態・版・別名・後継・担当・優先度・テーマ・関連・備考）を詰めると人が編集しづらい。**1 項目を複数行の塊で書くと shiori.toml だけで数千行になる**ので、ここは行形式の凍結（要件 2.1）と直結する重要な選択である。

### 3-2. 報告ファイルが 4 つの調査 spec の「共有ファイル」になってしまう

- 要件 3.4 は「4 つの台帳ファイルを互いに独立して編集できる状態に保つ」と求め、4 本の brief はいずれも「共有ファイル 0 だから並走できる」を着手根拠にしている。
- ところが要件 7.3 は「整合検査は、repo 内の報告が現在の台帳から再生成したものと一致することを確かめる」と求める。
- この 2 つを素直に実装すると、**どの調査 spec が自分の台帳を 1 行編集しても、`report.md` を作り直して一緒にコミットしなければテストが赤になる**。`report.md` は 4 本が同時に書き換える単一ファイルになり、並走時に必ずぶつかる。

選択肢:

- **⒜ 常時の検査から報告の一致を外す**。報告は必要なときだけ作り、統合の担当（`ukadoc-coverage-roadmap`）が最後に一度作り直す。要件 7.3・7.4 の緩和が要る。
- **⒝ 報告をドメイン別に分ける**（`report/shiori.md` など＋統合時に束ねる）。共有が消えるが、要件 7.1 の「全体の分布」は統合時にしか出せない。
- **⒞ 報告を repo に置かない**（テストの中で作って捨て、内容の正しさだけを見る）。共有は消えるが、`ukadoc-coverage-roadmap` が「読める報告が repo にある」ことを前提にしている（brief 20 行目）ので、その期待が崩れる。
- **⒟ 4 本の並走を諦め、報告を触るときだけ順番に行う**（開発者の運用裁定）。

### 3-3. 改行コードで「再生成と一致」が新しい環境で赤になりうる

- この repo に `.gitattributes` は無く、`core.autocrlf` はシステム設定で `true`。実測では作業ツリーのテキストファイルは**復帰文字付き**（§1.5）。
- 生成の道具が改行だけを書けば、生成直後の作業ツリーのファイルは改行だけになる。git は取り込み時に改行だけへ揃えるので**差分は出ない**。
- ところが**新しく clone した環境では、git が復帰文字を足して取り出す**。そこで「repo の報告」と「今この場で作り直した報告」を 1 バイト単位で比べると**必ず食い違う**。要件 7.3 の検査がその環境で赤になる。
- 同じ罠は、カタログや台帳を読み込むときの見た目には出ないが（TOML の読み取りは改行の違いを吸収する）、**バイト単位で比べる場面すべて**にある。

選択肢:

- **⒜ `.gitattributes` を新設し、`doc/ukadoc-coverage/**` を改行固定にする**。確実だが、repo 全体の設定ファイルを新設することになる（本 spec の改変集合が 1 つ増える）。
- **⒝ 比べる前に改行を揃える**（復帰文字を落としてから比較する）。ファイルは 1 つも増えないが、「1 バイトも違わない」という言い方は使えなくなる。
- **⒞ バイトではなく中身で比べる**（表の値どうしを比べる）。頑丈だが、報告のような散文には向かない。
- 要件 1.5 の「2 回続けて実行して 1 バイトも違わない」は**同じ環境で連続実行する話**なので、この罠の影響を受けない。影響を受けるのは要件 7.3 だけである。

### 3-4. 常時走る検査が「空回り」する（初期状態では何も確かめていない）

- 本 spec が作る初期台帳は**全 1,749 行が「未分類」**（要件 3.3）。
- すると、要件 6.6（実装済みの行には証拠が要る）・6.7（関連の両端・別名の連鎖・版の矛盾）・6.8（テーマ名の実在）は、**確かめる対象が 1 件も無い状態で緑になる**。
- 同じ問題は既にこの repo で言語化されている。`file_length_guard_test.rs:29-43` は「違反 0 件なら緑」の形は**道具が壊れていても緑になる**と述べ、対処として ⑴ 表の全項目に実体があることを確かめる ⑵ 実測集合と表が完全一致することを確かめる ⑶ 既知の 1 件をわざと外すと赤になることを確かめる、の 3 本を置いている。
- **設計はこの 3 本立てに倣うべき**。具体的には、⑴ 見本データ（ごく小さなカタログと台帳）で各検査が**赤になること**を確かめる相棒テストを置く ⑵ 実データに対して「検査対象が 0 件でない」ことを確かめる（未分類 1,749 件・カタログ 1,749 件・ページ 38 種など）。

### 3-5. 検査の粒度と「壊れない」の両立（要件 6.11）

要件 6.11 は「実装が入れ替わっても正典 URL が定義箇所に残っていれば赤にならない」と求める。行番号を使わない（要件 5.1）ので原理的には満たせるが、**次の 2 つは設計で決める必要がある**:

- URL の書き方をどこまで厳密に見るか。フラグメント（`#...`）の有無・末尾の `:1`・`http` と `https` の別・全角文字の混入。厳しくすると誤って赤になり、緩くすると綴り違いを見逃す（要件 6.10 が名指しで求めている検出）。
- 同じ URL が複数のファイルに現れたときの扱い。要件 5.2 は「定義箇所だけ・呼び出し側には書かない」と規約で縛るが、**機械はこれを判定できない**。複数出現を許すのか、赤にするのか、証拠を全部並べるのか。

### 3-6. 名前による突き合わせの正規化規則（要件 5.4）

§1.6 の実測から、少なくとも次を決める必要がある:

1. **見出しから名前を取り出す規則がページごとに違う**。descript 系は最初の読点まで、`list_shiori_*` と `list_propertysystem` はそのまま、さくらスクリプトは「もしくは」で 2 つに割れるものや説明語（`ID番号`）を含むものがある。
   → ⒜ ページごとの取り出し規則を表で持つ ⒝ 取り出しは行わず、語彙表の要素が見出しの中に現れるかで見る ⒞ 対応表を人手で台帳に書く（機械は突き合わせを行わない）。
2. **見出しは一意でない**。同じページの中でも重複が 3 ページある（`descript_shell_surfaces` 1 組・`list_propertysystem` 2 組・`spec_shiori3` 2 組）。突き合わせが複数の id に当たったときにどうするか（赤にする／全部を証拠にする／人手の指定に委ねる）。
3. **空白の揺れ**。sylphya との照合で唯一食い違った 1 件は全角空白と半角空白の差だった（§1.2）。正規化するかしないかで結果が変わる実例が既にある。
4. **逆斜線を含む見出しが 316 件**。TOML に書くときの引用の仕方（二重引用符なら逆斜線を重ねる／単引用符の素の文字列なら 3 件の単引用符入り見出しが書けない）を決める必要がある。`toml` の書き出し機能に任せれば自動で処理されるが、手で書く台帳では規約として明記が要る。

### 3-7. 「未分類の件数の固定値」の運用方向

- 要件 6.9 は「固定値を上回ったら赤・**減少は常に許す**」。
- 既存の 2 つの前例はいずれも**完全一致**を求め、しかも陳腐化を積極的に赤にする: `file_length_guard_test.rs:200-220` は「表に載っているのに今はもう超過していない項目」を赤にし、`ledger_key_determinism_tests.rs:200-205` は件数を逐語で一致させる。
- 「減少は許す」だと、調査が進んで実際の未分類が 0 になっても固定値が 1,749 のまま残り、**誰も気づかないまま台帳の宣言が意味を失う**。
- 選択肢: ⒜ 要件どおり片方向にする（進めやすさ優先）⒝ 完全一致にして、調査 spec が自分の台帳を編集するたびに件数も直す（既存の作法と揃う・手間は増える）⒞ 片方向にしつつ「宣言値と実測の開きが大きいと警告を出す」。

### 3-8. カタログ・台帳の TOML の形と並び順

- **形の選択肢**: ⒜ id を鍵にした表の集まり（`["ukadoc:list_shiori_event:OnBoot:1"] = { ... }`）⒝ 配列の要素（`[[entry]]` を並べる）。
- ⒜ を `toml::Table` で組み立てると、鍵の並びは自動的に文字順に揃う（`toml` の表は並び順を持つ地図ではない）。**要件 1.5 の「行の順序を含めて同一」は自動的に満たされる**。反面、スナップショットの掲載順（正典の読み順）は失われる。
- ⒝ は掲載順を保てるが、並び順を自分で決めて自分で守る必要がある。
- id を鍵にすると 1 行が最大 611 文字（sha256 の場合）になる。カタログの見やすさをどこまで求めるか。
- **台帳の 1 行に 10 欄**（要件 2.1）を詰めるなら ⒜ の 1 行形式が現実的だが、備考（要件 4.9 が「壊れ方の根拠」を書けと求める）は長くなりがちで、1 行に収まらない。備考だけ別の書き方にするか、台帳は複数行形式にして行数上限を諦めるか（§3-1 と連動）。

### 3-9. `linkage.md` を作るのか

`ukadoc-coverage-roadmap` の brief は 42 行目で `report.md`・`linkage.md`・`briefing.md` の 3 つを成果物に挙げ、67 行目で toolkit の役割を「report/linkage の再生成」と書いている。一方、本 spec の要件 7.1 は `report.md` だけを挙げ、束の一覧はその一節として置く。

- ⒜ 要件どおり `report.md` の一節にする（統合担当の brief 側を後で直す）。
- ⒝ `linkage.md` を別ファイルとして作る（要件 7.1 の追加が要る）。
- どちらでも実装の手間は大差ない。**先に決めておかないと、統合担当が着手した時点で食い違いが露見する**。

### 3-10. 版番号の抽出規則（要件 1.2・6.7）

- 1 つの entry に相異なる版番号が 2 つ以上あるものが 23 件ある（最大 7 種）。
- 「本文から抽出した SSP 版番号」を 1 つだけ記録するなら、**どれを採るかの規則**が要る（最小＝最初に登場した世代／最大＝最後の変更／本文中の最初の出現）。
- 要件 6.7 の「記録された登場版がカタログの抽出値と矛盾しない」の「矛盾しない」も定義が要る。台帳が `2.3.53` と書き、カタログの抽出値が `2.8.82` のとき、これは矛盾か。
- 選択肢: ⒜ カタログには**すべての版番号を列として持つ**（1 つに絞らない）。台帳の値がその集合に含まれることを検査する＝「矛盾しない」が自然に定義できる。⒝ 最小のものだけを記録する。⒞ 抽出は候補提示に留め、台帳の値は人手が正とする（機械は検査しない）。

### 3-11. スナップショットの既定の場所

- 既定は `%APPDATA%\npm\node_modules\ukagaka-doc-mcp\data\index.json`。この形は Windows の npm グローバル配置に強く依存する。
- 要件 1.7 の環境変数が逃げ道になるが、**既定をコードに焼き込むか、環境変数を必須にするか**は決める必要がある。実測ではこの環境に実在する（§1.1）。
- 要件 6.2 が「スナップショット不在でもテストは赤にならない」と定めているので、**日常のテストはこの場所に一切触らない**設計にできる。触るのはカタログ再生成と差分算出のときだけ。

### 3-12. 新クレートの名前と steering への登記

- `roadmap.md:91` は改変集合を「新規 `crates/ukadoc-survey/`」と既に名指ししている。**この名前に揃えるのが素直**。
- `.kiro/steering/structure.md` はクレートごとに節を持つ（`:334` pilot・`:338` log-capture-kit・`:346` temp-path-kit など）。新クレートの節を足すかどうかは設計事項。要件 9.8 が触るなと言っているのは `roadmap.md` だけで、`structure.md` は禁じられていない。
- クレートの `publish = false`・ワークスペースの版を引き継ぐ書き方は `crates/log-capture-kit/Cargo.toml:2-10` が手本。

## 4. 実装方式の選択肢

### 方式 A: 新しいクレート 1 本（ライブラリ＋実行ファイル＋常時テスト）

`crates/ukadoc-survey/` に、⑴ カタログ生成 ⑵ 証拠収集 ⑶ 整合検査 ⑷ 報告生成 を置く。スナップショットを読む部分と差分算出は実行ファイル側（`src/bin/` または `[[bin]]`）に置き、常時走るテストはライブラリ側の純粋な関数だけを使う。

- **良い点**: 要件 6.1（標準のテスト実行に常時含める）を素直に満たす。要件 9.1（既存クレートから参照されない）も自然に成立する。ワークスペースのメンバー指定がグロブなのでルートの `Cargo.toml` を触らない（`Cargo.toml:2-4`）。`roadmap.md:91` の宣言とも一致する。
- **注意点**: 新クレートの `.rs` は行数上限テストの対象に**即座に入る**（`workspace_scan/mod.rs:79-86`）ので、最初から機能ごとにファイルを分ける必要がある。ファイル分割の作法は `structure.md:131-184` が定めている。
- **規模の見立て**: カタログ 200 行・証拠収集 250 行・台帳の読み書き 200 行・検査 250 行・報告 250 行・テスト 600 行程度。ファイル数 10〜14 本。

### 方式 B: テストだけのモジュール（新クレートを建てない）

既存のどこかのクレートの `tests/` に置く。

- **良い点**: 新しいクレートが増えない。
- **悪い点**: 要件 9.1（既存の実行時コードを変更しない・既存クレートから参照されない）と真っ向からぶつかる。カタログ再生成・差分算出は実行ファイルが要るが、テストからは起動しにくい。`roadmap.md:91` の改変集合の宣言とも食い違う。**推奨しない**。

### 方式 C: 補助タスク（xtask 方式）

`xtask` の慣習に倣い、生成・検査を別の実行ファイルに集約して `cargo xtask ...` で呼ぶ。

- **良い点**: 生成物と本体の分離が明快。
- **悪い点**: 要件 6.1 が「標準のテスト実行に**常時**含める」と明示しているので、検査は結局テストにも要る。二重管理になる。この repo に `xtask` の前例は無い（`crates/` の一覧に無い）。

### 方式 D（推奨の検討軸）: A を土台に、内部を 2 層に分ける

- **下層＝純粋な部分**（スナップショットにもファイルシステムにも触らない）: 台帳とカタログの読み書き・検査の判定・報告の組み立て。ここは見本データで完全にテストできる。
- **上層＝外に触る部分**: スナップショットの読み込み・ソースの列挙と読み込み・ファイルへの書き出し。
- この分け方は `workspace_scan/mod.rs:6-12` が既に言語化している作法（「ファイルシステムに触るのは 3 本だけ、残りは入出力だけで完結する純粋な関数」）で、**同じ理由で本 spec にも効く**——「違反 0 件だから緑」が道具の故障で起きていないことを、純粋な側の見本テストで別立てに示せる（§3-4）。

## 5. 規模とリスク

| 区分 | 見立て | 理由 |
|---|---|---|
| 規模 | **M〜L**（1 週間前後） | 機能は 4 つ（生成・収集・検査・報告）。個々は素直だが、決めるべき形式の判断が多い（§3 に 12 件）。初期台帳 1,749 行の生成そのものは自動なので手間ではない |
| 技術のリスク | **低** | 新しい技術は無い。TOML・JSON・ファイル走査だけ。前例が repo 内にある |
| 形式決定のリスク | **高** | 台帳の行形式は**要件確定の時点で凍結**され、調査 spec 4 本が実装完了を待たずに書き始める。後から形を変えると 4 本の作業が巻き添えになる。§3-1・§3-2・§3-8 は着手前に決着させたい |
| 既存への影響 | **極小** | 既存クレートを参照せず、参照もされない。改変集合は新クレート＋`doc/ukadoc-coverage/`＋`Cargo.lock`（`roadmap.md:91` の宣言どおり）。ただし外部依存を足すとライセンス関門（`deny.toml`・`about.toml`）に触れる |
| テストのリスク | **中** | 常時走る検査が初期状態では空回りする（§3-4）。改行コードの罠（§3-3）は**新しい環境で初めて赤くなる**種類なので、この環境だけで確かめても見つからない |

## 6. 設計フェーズへ持ち越す調べもの

1. **`cargo deny check` と `cargo about generate` を実際に通す**（依存を足したあと）。許可一覧に載っているはずだが、実行して確かめていない。
2. **`toml` 1.x の書き出しの細部**——表の並び順・文字列の引用の選び方・複数行文字列の扱い。要件 1.5 の「1 バイトも違わない」の裏取りに要る。実測は未実施。
3. **改行コードの罠の再現**。新しい clone を作って、生成した報告と repo の報告が食い違うかを実際に見る（§3-3）。
4. **さくらスクリプトの見出しから名前を取り出せるか**の実データ検証。342 件のうち何件が機械で名前に落ちるか（§3-6-1）。今回は形の違いを確認しただけで、変換の成功率は測っていない。
5. **`descript` 系 518 件の見出しの読点区切りが安定しているか**。`charset,文字コード` の形が全件に当てはまるかは未確認。
6. **ハッシュの選び方の最終決定**に必要な情報——`sha2` を足したときの依存の増分（推移的に何が入るか）。未確認。
7. **`doc/COMPAT_ARCHITECTURE.md:128-207` の 80 行**と、台帳の「縮退」行の対応の付け方。転記元として使えることは確認したが、id への対応付けは未着手。
