# Requirements Document

## Project Description (Input)
機械が重いとき（他のセッションの cargo・rustc・areka が十数本〜数十本並走しているとき）に `cargo test -p areka --bin areka` や全体テスト（`tools/test-all.ps1`）を回すと、ゴーストの切り替え・起こし直し・上書きのインストール・終了まわりのテストが、毎回違う組で 1〜10 件ほど赤になる。単独で回すと緑、静かな机の全体テストも緑で、コードの欠陥を示す赤ではない見込みが高い。困るのは開発者と実装の手順（`/kiro-impl` のレビュー・`/kiro-complete` の全体テスト）で、複数のワークツリーを並べて走らせるのが常のため、本物でない赤がレビューの判定を濁し、回し直しの手間と「関係ない赤」を見逃す癖を生む。疑いは、落ち着くのを待つテストの部品が壁時計の締切（30 秒・20 秒・10 秒）で待っており、負荷で締切を越えること、さらに同じテストの実行ファイルの中で多数のテストが空回しで CPU を取り合い、飢えを自分たちで強めていること。まず負荷をかけた条件で赤を再現する手順を 1 つ作り、どのテストがどの待ちで落ちるかを突き止める。締切を延ばしたり sleep を足したりせず、待つ条件を観測（状態の到達）へ置き換えるか、締切を越えたときの失敗の文言を「負荷で遅い」と「欠陥で止まった」とが見分けられる形にする。本物の競合が見つかればそれを直すテストを添えて直す。再現しなければ、何を試して赤が 0 件だったかを記録して据え置きへ移す。本番のゴーストの切り替えの振る舞いは、競合が見つかった場合を除いて変えない。種別はバグ（テストの揺れ）。

## Introduction

areka のテストの実行ファイル（`cargo test -p areka --bin areka`）には、ゴーストを実際に起こし、切り替え・起こし直し・降ろしが「落ち着く」まで待ってから確かめるテストが多数ある。これらは共通の待ちの部品を使う。

- `emo2_boot/spine.rs` の `spin_wait_until`（30 秒の締切・最初は空回しで待つ）と `run_bounded`（呼び手が締切を渡す・ゴーストの降ろしは 10 秒）。
- 切替のテストの足場 `emo2_boot/ghost_switch_test_support.rs` の `wait_steady`（20 秒の締切）と、台詞の時計を進めながら待つ `pump_talking_until`（実時間 1 ms ごとに台詞の時計を 100 ms 進め、上限が無い）。
- 起こし直しのテスト `ghost_session_restart_tests.rs` が自前で持つ待ち（10 秒の締切・空回しだけで待つ）。

どの待ちの部品も自分では失敗の文言を出さず、成否だけを返す。呼び手の確かめは、待ちの打ち切りと判定の食い違いを 1 つの比較にまとめているものがあり（例: 切替の失敗から既定ゴーストへ戻るテスト）、赤の文言からは負荷で遅かったのか欠陥なのかが分からない。

負荷の高い机では、これらの待ちを使うテストが毎回違う組で赤になる。これまでに赤を観測した族は次のとおり（いずれも単独・静かな机では緑）。

- ゴーストの切り替え・その失敗からの既定ゴーストへの戻り・起こし直し（`ghost_session_*_tests.rs`・`shell_balloon_switch_session_*_tests.rs`）。
- 切替の足場を使う他のテスト（上書きのインストール `install/desk_overwrite_tests.rs`・終了の同期送り `session_end_sync_send_tests.rs`・起動イベント付きの切替 `emo2_boot/ghost_switch_boot_event_tests.rs`・終了と切替の予約 `emo2_boot/frame_ghost_quit_switch_tests.rs`・MCP のテストの一部）。起票後の数え直しで、足場を使うファイルは 28 本。
- `emo2_boot::spine` の族（`spine_*_tests.rs`・`run_bounded` の 10 秒の締切での赤。`zorder-chain-residue` から引き取った）。
- サンプルゴーストの展開の後片付け（`target\nar-samples\work` の退避）の os error 5（同じ負荷の族と見て引き取った）。

`--test-threads=1` では同じ組が緑になった観測があり、同じ実行ファイルの中のテストどうしが CPU を取り合っている見込みがある（起票時の見立て・未確認）。

直し方の向き（待ちを観測の到達へ置き換える／締切を越えたときの文言で負荷と欠陥を見分ける）は、どちらか、または両方を設計で決める。本要件は、どちらを採っても満たすべき結果だけを定める。

## Boundary Context

- **In scope**:
  - 上の族のテストと、それらが使う待ちの部品の待ち方の見直し。
  - 負荷をかけて赤を再現する手順を 1 つ作り、記録すること。
  - サンプルゴーストの展開の後片付けの os error 5 の原因を調べ、同じ族なら直すこと。
  - 再現の中で本番の順序の取り違え（本物の競合）が見つかった場合に限り、その修正。
  - `emo2_boot/spine.rs` が 1 ファイル 1,000 行の上限ちょうどのため、待ちの部品を別のファイルへ出すこと。
- **Out of scope**:
  - 本番のゴーストの切り替え・起こし直し・降ろしの振る舞いの変更（本物の競合が見つかった場合を除く）。
  - 全体テストの手順（`tools/test-all.ps1`）の並列度の変更、回し直しの仕組みを足して赤を隠すこと（テストの実行ファイルの中で足場の同時の数を絞るのは、要件 2.7 の条件を満たすときだけ範囲に入る）。
  - `zorder-chain-residue` に残る族（実窓の重なり順の間欠赤・檻の片側性と文書）と、すでに隔離済みの wintf の vblank の締切。
  - `--test-threads=4` で実行ファイルごと落ちる件（`areka-test-threads-av` の範囲）。
  - 赤の観測が無い待ち（他の crate の同じ名前の `run_bounded`／`join_bounded`・`install/` が自前で持つ `join_bounded`・その他のテストのファイルが自前で持つ締切つきの待ち）。要件 1 の再現の手順で赤になったものだけを対象に加える。
- **Adjacent expectations**:
  - 同じウェーブで並走する spec の持ち物である本番のファイル（`emo2_boot/mod.rs`・`frame/` の下・`ghost_switch.rs`）は触らない。本物の競合の修正にこれらを触る必要が出たときは、触る前に止めて報告する。
  - ワークスペース全体の見張り（1 ファイル 1,000 行の番人とその例外表・テスト用一時パスの窓口の迂回の見張り）は、本 spec の後も緑のまま保ち、例外表は増やさない。
  - `areka-test-threads-av` とは同じテストの実行ファイルを測るため、同時に走らせない。

## Requirements

### Requirement 1: 負荷の下で赤を再現する手順

**Objective:** As a 開発者, I want 負荷をかけた条件で対象の族の赤を起こす手順が 1 つ決まっていること, so that どのテストがどの待ちで落ちるかを、回し直しの運でなく手順で確かめられる

#### Acceptance Criteria

1. The 本 spec の作業 shall 対象の族のテストを、CPU を食う並走の負荷を付けて回す手順を 1 つ定め、負荷の作り方・回す範囲・回数・1 回の上限の時間を、始める前に spec の記録へ書く。
2. When 再現の手順を回したとき, the 本 spec の作業 shall 赤になったテストの名前・失敗の文言・その時に待っていた部品と締切を、回ごとに spec の記録へ残す。
3. The 再現の手順 shall 一時のファイルと負荷の子プロセスの作業場所を、ワークツリーの `target\` の下だけに置き、終わったときに自分が起こした負荷の子プロセスを止める。
4. When 着手したとき, the 本 spec の作業 shall 待ちの部品（`spin_wait_until`・締切の定数 `SPIN_WAIT`・`run_bounded`・`join_bounded`・`wait_steady`・`pump_until`・`pump_talking_until`・`pump_input_until` と、テストのファイルが自前で持つ締切つきの待ち）を使うファイル（本番のファイルの中の利用を含む）と、切替の足場を使うファイルを全数で数え上げ、起票時の数（足場 28 本・`spin_wait_until` か `SPIN_WAIT` を名指しするファイル 20 本）と違えば差を記録する。

### Requirement 2: 負荷で遅いだけでは赤にならない

**Objective:** As a 開発者, I want 待っている相手が進み続けている限り、機械が遅いだけで対象のテストが赤にならないこと, so that 並走の机のレビューと完了の全体テストで出る赤を、本物の欠陥として扱える

#### Acceptance Criteria

1. While 待っている相手（ゴーストの起動・切り替え・降ろしの処理）が状態を進め続けている, the 対象の族のテスト shall 実時間の経過だけを理由に赤にならない。
2. The 対象の族のテスト shall 待つ条件を「目当ての状態に届いたこと」で判定し、確かめの内容（何が起き、何が起きないか）を弱めない。
3. The 修正 shall 一定時間の sleep を足すこと、締切の秒数を延ばすことだけ、1 フレーム遅らせることのいずれでも直さない。
4. The 修正 shall 対象の族のテストを無視の印で走らせなくすること、本数を減らすことで赤を消さない。
5. While 同じテストの実行ファイルの中で多数のテストが同時に待っている, the 待ちの部品 shall 待っている間に、待っている相手の進みを妨げるほど CPU を占めない。
6. While 待ちの部品が台詞の時計などの合成の時刻を注入しながら待っている, the 待ちの部品 shall 合成の時刻を送る相手を、届いた順に消化し、合成の締切も後戻りする状態も持たない相手に限る（相手が飢えている間に合成の締切だけが切れる赤、注入した時刻が待っている条件を壊す赤を作らない）。待つ条件には、後戻りしない観測だけを渡す。
7. Where 待ち方の直し（2.5・2.6）の後も、要件 6.1 の負荷の条件で待ちの打ち切りの赤が残る, the 修正 shall ゴーストを起こす足場を同じテストの実行ファイルの中で同時に生かしておける数を絞ってよい。ただし、絞る前のその赤の失敗の文言が「相手は状態を進めていた（負荷で遅い）」を示していたことを spec の記録に残した場合に限る。待ち方の直しより先に絞ることはしない。

### Requirement 3: 止まったときの失敗は見分けられる

**Objective:** As a 開発者, I want 待ちが目当ての状態に届かずに終わったとき、それが負荷で遅いのか欠陥で止まったのかが失敗の文言から分かること, so that 赤を見たときに回し直すか調べるかを、推測でなく文言で決められる

#### Acceptance Criteria

1. If 待ちが目当ての状態に届かないまま打ち切られたとき, then the 待ちの部品 shall 何を待っていたか・実時間で何秒待ったか・待っている間に相手が状態を進めたかどうかを、失敗の文言に含める。
2. If 待っている相手が一定の間まったく状態を進めなかったとき, then the 待ちの部品 shall それを「止まった」と分かる文言で赤にする。
3. The 待ちの部品 shall テストが果てしなく終わらない状態を作らず、どの待ちにも打ち切りの上限を持つ。

### Requirement 4: 本物の競合を直す

**Objective:** As a 開発者, I want 再現の中で本番の順序の取り違えが見つかったら、それを示すテストと一緒に直されること, so that 負荷の赤の中に隠れていた欠陥を見逃さない

#### Acceptance Criteria

1. If 再現の結果、赤の原因が本番の処理の順序の取り違えだと分かったとき, then the 本 spec の作業 shall 修正の前に赤になり修正の後に緑になるテストを 1 本以上添えて、その取り違えを直す。
2. Where 取り違えを時間待ちなしの決定論で起こせる形が無い, the 本 spec の作業 shall 取り違えの経路を、コードの定義の名前で spec の記録に書き、修正の後にその経路が成り立たないことを示す。
3. If 修正に同じウェーブの他の spec が持つ本番のファイルを触る必要があるとき, then the 本 spec の作業 shall 触る前に止めて開発者へ報告する。
4. The 修正 shall 本物の競合の修正を除き、本番のゴーストの切り替え・起こし直し・降ろしの振る舞いを変えない。

### Requirement 5: 展開の後片付けの os error 5

**Objective:** As a 開発者, I want サンプルゴーストの展開の後片付けの os error 5 の原因が分かり、同じ族なら直っていること, so that 全体テストの最中の後片付けの失敗が赤の雑音にならない

#### Acceptance Criteria

1. When 着手したとき, the 本 spec の作業 shall `target\nar-samples\work` を作る・使う・退避するテストを数え上げ、os error 5 がどの組の同時の走行で起きうるか、またその退避の失敗が同じ回の赤と関わるか（退避の失敗そのものは今は表示だけで赤にしない作り）を spec の記録に書く。
2. If os error 5 が同じ場所を複数のテストやプロセスが同時に使うことによると分かったとき, then the 修正 shall 同時に走っても後片付けが互いに妨げない形にする。
3. If os error 5 がテストの側の原因でないと分かったとき, then the 本 spec の作業 shall その結論と根拠を記録し、修正の対象から外す。

### Requirement 6: 直ったことを確かめる・再現しなければ記録する

**Objective:** As a 開発者, I want 修正の後に、赤を起こしたのと同じ負荷の条件で赤が出ないことが確かめられていること, so that 「回し直したら緑」でなく、原因を断ったと根拠をもって言える

#### Acceptance Criteria

1. When 修正の後に、修正の前に赤を観測したのと同じ負荷の条件と回数で再現の手順を回したとき, the 対象の族のテスト shall 待ちの打ち切りによる赤を 0 件で終える。
2. If 修正の後の再現の手順で 1 件でも赤が出たとき, then the 本 spec の作業 shall 修正を完了とせず、その赤の失敗の文言から原因を調べる（回し直しの緑で置き換えない）。
3. When 修正の後に静かな机で全体テスト（`tools/test-all.ps1`）を回したとき, the 全体テスト shall ワークスペース全体の見張りを含めて緑で終わる。
4. If 再現の手順を定めた回数と上限まで回しても対象の族の赤が 1 件も出なかったとき, then the 本 spec の作業 shall 何を試して赤が 0 件だったかを spec の記録に書き、コードの定義の名前で確かめられる待ちの部品の欠け（要件 2.5・2.6・3 に反する待ち方）は、時刻を差し替える決定論のテストを添えて再現を待たずに直す。再現でしか確かめられないもの（要件 4 の本物の競合・要件 5 の os error 5 の原因の確定）だけを、試したことの記録と一緒に据え置きへ回す。この場合、6.1 の負荷の下の確かめは行わない。
5. When 修正の前と後に静かな机で全体テストを回したとき, the 本 spec の作業 shall 全体テストと対象の族のテストの所要時間を spec の記録に並べて残す。If 修正の後に所要時間が目立って延びたとき（目安は設計で決める）, then the 本 spec の作業 shall 待ち方を調整してから完了とする。

### Requirement 7: ファイルの大きさと共通の見張りを保つ

**Objective:** As a 開発者, I want 待ちの部品を直しても 1 ファイル 1,000 行の上限と共通の見張りが守られていること, so that 本 spec の変更が別の番人の赤を生まない

#### Acceptance Criteria

1. The 修正 shall 触ったすべてのファイルを 1,000 行以下に保ち、1 ファイル 1,000 行の番人の例外表に行を足さない。
2. The 修正 shall テスト用の一時パスを、共通の一時パスの窓口を通して作り、その迂回の見張りを緑のまま保つ。
3. Where 待ちの部品の形を変える, the 修正 shall その部品を使う全てのテストを、同じ確かめの内容のまま新しい形へ移す。
