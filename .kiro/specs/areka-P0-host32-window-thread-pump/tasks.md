> 本計画は設計文書の C7（較正の 2 段階）に従う。**タスク 1〜3 は「直す前の構造」＝受信ループ無改変のまま進め、段階 1 のコミットは意図して赤のテストを含む**。待ちの形を変えるのはタスク 4 以降であり、この順序が較正（4.3・4.4・4.7・4.10）の前提そのものである。タスク 2 の各テストは「段階 1 で赤であること」が正しい完了状態であり、赤を消すために受信ループを先に直してはならない。

  - backend 契約に「アクターが手空きのとき backend に処理の機会を与える」通知を**既定実装（何もしない）つき**で追加する。説明文に「ブロックしない・失敗を返さない・異常は死活確認で報告する」を書く
  - 保守周期の定数を追加し、値の根拠（OS の応答なし判定の最も厳しい閾値の 1/10・速い決定論テストの上限との関係）を説明文に残す
  - 定数は**統合テストバイナリから参照できる公開項目**として置く（タスク 2.4 のコンパイル時 assert がこれを要求する）
  - 契約の説明文にも定数の説明文にも Win32 固有の語彙（窓・メッセージポンプ）を書かない
  - 完了状態: 既存の backend 実装 10 個のうち host32 のもの以外 9 個のソースが無改変のまま `cargo build --workspace` が通り、定数が crate 外から参照できる

  - _Boundary: C2_

  - 資材（イベント・スレッド・窓）を生成せず、失敗経路を持たず、ログを出さない
  - 説明文に「OS の応答なし判定の背景（プロセス生存の猶予と取り出し間隔の閾値）」と「往復の内側から呼ばないこと」を明記する
  - 完了状態: 部品が公開 API として追加され、host32 の既存テストが期待値を緩めずに緑のまま
  - _Requirements: 1.1, 6.2, 6.3, 7.6_
  - _Boundary: C4_
