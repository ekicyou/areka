## 0. 要約

- **骨格は今の鎖のままで足りる**。並びを書かれた順に変えるのは areka 側の純関数 2 つ（`normalize_scope_blocks` と `compose_chain`）だけでよい。鎖の合成は、今でも「同じスコープの（バルーン, キャラ）が隣り合う対」だけを鎖の繋ぎから外しているので、`s0,b0` のような逆向きの対はそのまま鎖の繋ぎ（`s0` を `b0` に持たせる）として出てくる。
- **欠けているのは「組の結び目を一時的に外す」仕組み**である。逆転・非隣接のスコープでは、組の結び目（`b0` を `s0` に持たせる）を残したまま鎖を張ると、⑴ `s0`→`b0` と `b0`→`s0` の**持ち主の輪**ができる、⑵ `b0` の持ち主の欄（1 つしかない）を鎖と組が奪い合う、のどちらかが起きる。今の wintf には、結び目を「相手が消えたとき」以外に外す道も、外した結び目を張り直す道も無い（張るのは窓のハンドルが付いた巡の 1 回だけ）。
- **一番の難所は 1 巡の中の順序**である。外すとき（組 → 鎖）は「組の結び目を外す → 鎖を張る」、戻すとき（鎖 → 組）は「鎖を外す → 組を張り直す」の順でないと、途中で持ち主の輪ができる。今の確定段の並び（組の確立 → 組の維持 → 鎖の適用）は前者には合うが後者には逆向きである。
- **利用者の操作（押す・他のアプリを選ぶ）は、鎖が 1 本の持ち主の鎖である限り OS が塊として扱う**（完了 spec の実測 §12.1・§12.5）。押したときの特別な処理は要らない見込みだが、押して活性化した場合の実機の確かめは要る。
- **wintf の公開の宣言 `KeepDirectlyAbove` の形（欄）を変えずに済む案が複数ある**。形を変える案（向きの欄を足す等）を採るなら、公開の約束を先例なしに変えることになり、brief の線引きどおり Fable の段の判断になる（下の議題 1）。

### 1.3 完了 spec から引き継ぐ実測（再実測不要の事実）

- 持ち主を張り替えただけでは重なりは動かない。**鎖の根を 1 回動かす後押し**で鎖全体が宣言の順に収まり、以後は OS が保つ（`scope-zorder-pinning` research §12.1・§13.3）。
- 鎖は**1 つの塊として動く**。鎖のどの窓を前へ出しても鎖全体が前へ出る（§12.5）。→ 要件 5.1・5.2・5.4 は構造で満たせる見込み。
- 持ち主の窓を壊すと持たれる窓も壊れる（下流へだけ伝わる）。**先に外してから壊せば封じられる**（§12.3）。逆転の繋ぎ `s0 ← b0` も、鎖の適用の「去る窓の切離し」（所有側が去った繋ぎを外す）がそのまま覆う。
- `clear_window_owner` は**持ち主の無い窓に当てると失敗を返す**（§12.6）。外す前に今の持ち主を読む作法が要る（組を一時停止で外すときも同じ）。
- 持ち主の鎖は**分岐が無い一直線**でなければ全順序にならない（§10.10）。**輪（循環）について Win32 がどう振る舞うかは測っていない**（下の Research Needed R1）。

### 1.4 バルーンの「再び表示」は既に重なりに触れない

`crates/areka/src/emo2_boot/balloon_visibility_phase_zorder_chain_tests.rs` が、バルーンの再表示（中身の絵の消去と再描画・窓の表示状態は不変）が鎖の計画を 1 ビットも変えないことを固定している。初版の「再表示の後に是正を促す引き金」は退役済みで、`ReassertZOrder` を挿す本番の呼び手は組の確立系だけである（areka の本番コードに挿入点は無い）。→ **要件 6.3 は、組の張り直しの契機を再表示に結び付けない限り、そのまま成り立つ**。

### 1.5 「バルーンが後から現れる」の areka での意味

areka はスコープごとにキャラの窓とバルーンの窓を**起動時に同時に作る**（`spawn_ghost_windows`）。片方が消えると `GhostWindowMarker` の除去のフックがスコープごと台帳（`GhostWindows`）から落とす。したがって要件 6.1・6.2 の「バルーンが指定の後に初めて現れる／破棄されて再び現れる」は、areka では主に⑴**窓のハンドル（HWND）が実体より遅れて付く**こと、⑵ゴーストやシェルの差し替えで窓の組が作り直されること、として現れる。⑴は鎖の適用が「ハンドル待ちの持ち越し」で既に扱っているが、**組の確立系がハンドルの付いた巡に結び目を張ってしまう**点が新しい穴になる（逆転を書いた descript の基底が起動時から有効な場合に必ず踏む）。

## 3. 主要なギャップの掘り下げ

### G1. 組の結び目を「書かれた順のため」に外し、後で張り直す道が無い

`s0,b0,s1`（補いで `s0,b0,b1,s1`）の鎖は「`s0` を `b0` に持たせる・`b0` を `b1` に持たせる・`b1` を `s1` に持たせる（組）」になる。このとき `b0` は**自分のキャラ `s0` ではなく `b1` に持たれ**、`s0` は `b0` に持たれる。組の結び目（`b0` を `s0` に持たせる）を残すと:

- `s0 ← b0` を張った瞬間に `b0 ← s0` と合わせて**持ち主の輪**になる。
- `b0 ← b1` を張ると `b0` の持ち主の欄が組から鎖へ黙って書き換わる。組の帳簿 `OwnerLink` は「`s0` に持たせた」と言い続け、相手が消えたときの切離しが**鎖の張った持ち主を外す**。

非隣接（`b1,s0,s1,b0`）でもスコープ 0・1 とも同じことが起きる。したがって**逆転・非隣接のスコープでは組の結び目を外すことが必須**である。外すべきスコープの判定は、鎖の合成が今使っている規則の裏返しで 1 本にまとまる——「実在する窓の並びで、そのスコープの（バルーン, キャラ）が連続していないスコープ」。片方だけ名指し（補いで必ず `bN,sN` の連続になる）・数値記法・後ろ側の参加は該当しない。

### G2. 1 巡の中の順序（輪を作らない）

| 遷移 | 輪を作らない順 | 今の確定段の並び（確立 → 維持 → 鎖） |
| --- | --- | --- |
| 組 → 逆転（タグの実行） | 組を外す → 鎖を張る → 後押し | 合う（組の系が鎖より前） |
| 逆転 → 組（解除・descript の読み直し） | 鎖を外す → 組を張り直す → 組の直上への是正（または鎖の後押し） | **逆**（組の系が鎖より前） |
| 逆転の並びの中での組み替え（グループの差し替え） | 撤去が全部先・付与が全部後（鎖の純関数の規則）を、組の外し・張り直しにも広げる | 鎖の内側だけは合う |

「1 フレーム遅らせる解は取らない」ので、戻りの順を次のフレームへ回す形は取れない。取りうる形は 3 つ（4 章の選択肢に対応）:

1. **鎖の適用を「外す段」と「張る段」に割り、組の系を間に挟む**（外す段 → 組の外し／張り直し・維持 → 張る段＋後押し）。`zorder_chain_apply.rs` を割る（上限の都合でも割りどき）・確定段の結線 `spawn.rs` の `wire_zorder_pair` を書き替える。
2. **鎖の適用が組の外し／張り直しを手順の中で呼ぶ**（撤去 → 組を外す → 組を張り直す → 付与 → 後押し）。組の帳簿 `OwnerLink` の書き換えは組の側の関数に置き、鎖の適用からそれを呼ぶ。確定段の並びは変えない。
3. **張り直しだけを鎖の後ろの新しい系で行い、その系が直上への是正まで同じ巡で出す**（再断行の要求を挿して次の巡の維持系に任せる形は 1 フレーム遅れになるので不可）。

いずれの形でも、組へ戻ったときに鎖がまだ残っていれば（他のグループや後ろ側の参加）**鎖の後押し 1 回が組の直上も含めて並べ直す**。鎖が無くなる場合（グループが 0 本）は後押しが出ないので、**組の直上への是正を同じ巡で出す手当て**が要る（今の確立系が張った直後に挿す `ReassertZOrder` と同じ是正を、同じ巡で消化できる位置で）。

### G3. 一時停止中の組を、組の系に見分けさせる口が無い

組の系の 3 か所が一時停止を知らないと誤動作する:

- **確立系**（`establish_owner_links`）: `Added<WindowHandle>` の巡に宣言があれば張る。descript の逆転が起動時から有効な場合、ハンドルが付いた巡に `b0 ← s0` を張り、同じ巡の鎖が `s0 ← b0` を張って輪になる（要件 1.3・6.1 の経路）。
- **維持系**（`apply_zorder_pair_maintenance`）: 一時停止中の組に再断行の要求が付くと、バルーンをキャラの直上へ直す（要件 5.2・5.5 の毀損）。今は要求の本番の挿入点が確立系だけなので実害は張り直しの経路から入る。
- **沈降の観測**（`observe_marked_pair_sinks`）: 一時停止中の組を「隣接していない」と debug 行に記録する（誤解を招く・要件 7.4）。

見分ける口の置き方が議題 1 の中身である（宣言を外す／一時停止の印を足す／鎖の計画に載せる／宣言を逆向きに付け直す）。

### G4. 張り直しの契機

今の確立系は `Added<WindowHandle>`（ハンドルが付いた巡）でしか判断しない。張り直しは「ハンドルは前から在る」状態で起きるので、契機を足す必要がある——宣言の付与（`Added<KeepDirectlyAbove>`）、一時停止の印の除去（`RemovedComponents`）、鎖の適用からの直接の呼び出し、のいずれか。どれを採るかは G2 の形と一緒に決まる。確立系の doc にある「確立はペアにつき 1 度きり・ゆえに検証待ちの要求を踏み潰さない」という前提は、張り直しを入れると成り立たなくなるので見直しが要る。

### G5. 記録の語彙

- 受理の行 `normalized=` は今「`scope:false`＝書いた順を採った／`scope:true`＝採らなかった／`+bN`・`+sN`＝補った」。本機能の後は `true` が出なくなり、代わりに「逆転のまま採った」「離したまま採った」を表す語が要る（要件 1.4・2.3）。完了 spec の実機の手順（`signoff-procedure.md`）と既存の檻は `0:false`・`1:false+s1` の綴りを読んでいる（要件 7.4）。`false` と `+bN` の綴りを残し、`true` の代わりに新しい語（例 `0:inverted`・`1:split`）を足すのが既存の読み手を壊さない形。
- 組を外した・張り直した事実の記録（debug）と、その失敗（error）。組の切離しの記録 `owner_detached_line` は理由の語 `PeerLoss`（`Despawned`／`HandleRemoved`）を持つので、理由を 1 語足す形が近い。マクロは `zorder_pair.rs` に置く決まり（残り 116 行）。
- 要件 7.3「どの窓をどの窓のすぐ手前へ繋いだかと、その直後に測った重なり」は、既存の `[zorder-chain] linked`（繋いだ対と区間）と `settled`（宣言と後押し直後の実測を 1 行）でそのまま満たせる。逆転の繋ぎも同じ行に出る。

### G6. ファイルの大きさと約束の範囲

- `zorder_pair.rs`（884）・`zorder_chain_apply.rs`（799）は上限に近い。前者には記録のマクロを足す決まりがあり、後者は G2 の形 1・2 で手順が増える。**新しい本番ファイルを足すなら `crates/wintf/src/ecs/window/mod.rs`（`mod`＋`pub use`）と `zorder_pair_deferred_vocabulary_tests.rs` の名簿の両方に行が要る**。
- 約束の一覧の外に出る可能性があるファイル（本質の形を曲げずに名指しする）:
  - `crates/areka/src/placement/spawn.rs`（`wire_zorder_pair` の並び）——G2 の形 1・3 を採る場合。後続の `stay-on-top-directives` も同じファイルを触る（直列の列）。
  - `crates/wintf/src/ecs/window/mod.rs`——新しい本番ファイルを足す場合。
  - `crates/wintf/src/ecs/window/zorder_pair_deferred_vocabulary_tests.rs`——同上（名簿）。
  - 今の挙動を主張している既存のテストのファイル（`zorder_group_ledger_tests.rs`・`zorder_group_branch_coverage_tests.rs`・`zorder_drain_tests.rs`・`zorder_descript_tests.rs`・`zorder_chain_compose_tests.rs` の前提の行）——陳腐化したテストの撤去・書き直し。
  - `ChainPlan` に欄を足す場合は、その構造体を字面で組んでいるテスト 11 ファイル（約 32 か所）。

## 4. 実装アプローチの選択肢

いずれの選択肢も、areka 側の 2 点（⑴ `normalize_scope_blocks` を「書かれた順のまま・補いだけ足す」へ、⑵ 合成が「組を外すスコープ」を求めて渡す）は共通である。分かれるのは**組の一時停止を wintf へどう伝え、1 巡の中で誰が順序を持つか**である。

### 選択肢 A — 宣言の付け外し（`KeepDirectlyAbove` を一時停止中は外す）

- areka の drain の相が、組を外すスコープのバルーンから `KeepDirectlyAbove` を外し、戻すときに付け直す（World を直に触れる相なので同じフレームの確定段から見える）。
- wintf: 「宣言が無いのに `OwnerLink` が残っている」窓の結び目を外す系を足す（外す前に今の持ち主を読む）。確立系の契機に `Added<KeepDirectlyAbove>` を足す。
- 順序（G2）は確定段の並びで解く必要がある＝形 1 か 3。
- ✅ 公開の型を 1 つも変えない・足さない。宣言の「在る＝組を保つ」という意味が素直。
- ❌ 宣言を付け直す層（areka）と、外した結び目を外す層（wintf）の連携が「欄が消えた」ことの検出に頼る。宣言の doc（「永続宣言」）の意味が「切り替わる宣言」へ変わる。`spawn.rs` の結線に触る見込み。

### 選択肢 B — 鎖の計画が「組を外すスコープ」を運び、鎖の適用が順序を一括で持つ

- `ChainPlan` に「組を外すバルーンの列」を足す（公開の構造体への欄の追加。`KeepDirectlyAbove` は変えない）。
- 鎖の適用が 1 つの手順で「撤去 → 組を外す → 組を張り直す → 付与 → 後押し（鎖が無ければ組の直上への是正）」を行う（G2 の形 2）。組の帳簿の書き換えは組の側の関数に置いて呼ぶ。組の確立系・維持系・沈降の観測は「外しているバルーン」を計画から読んで避ける。
- ✅ 輪を作らない順序が 1 か所（差分の純関数の「撤去が全部先・付与が全部後」の延長）に集まり、決定論の檻（替え玉の 6 窓口）でそのまま全分岐を固定できる。確定段の並びを変えない＝`spawn.rs` を触らない。
- ❌ 鎖の適用が組の帳簿へ手を伸ばす（責務の境界が太る）。`zorder_chain_apply.rs` は 799 行で、手順を足すなら割る必要がある。`ChainPlan` を字面で組んでいるテストの書き換え（約 32 か所・`..Default::default()` で吸収できるかは要確認）。

### 選択肢 C — 一時停止の印（新しい公開のコンポーネント）＋確定段の並びの組み直し

- wintf に「この組は一時停止中」を表す印（値を持たないコンポーネント）を足し、areka の drain の相が付け外しする。組の系 3 か所は印で避け、印の除去を張り直しの契機にする。
- 鎖の適用を「外す段」と「張る段」に割り、間に組の系を置く（G2 の形 1）。
- ✅ 宣言（`KeepDirectlyAbove`）は 1 バイトも変えず、意味も「永続宣言」のまま。一時停止という新しい状態が型として見える。組と鎖の責務が混ざらない。
- ❌ 公開の型が 1 つ増える（追加であって既存の形の作り替えではない）。確定段の系が 3 本から 4〜5 本になり、`spawn.rs` の結線と字面の檻（`spawn_zorder_chain_wiring_tests.rs`）を書き替える。

### 参考（推さない）— 選択肢 D: 宣言を逆向きに付け直す

隣り合った逆転（`s0,b0` が連続）では、`KeepDirectlyAbove { peer: b0 }` を**キャラの窓 `s0` に**付け直せば、組の系がそのまま「`s0` を `b0` に持たせ、`s0` を `b0` の直上へ」保つ。型の欄は変えないが、doc の約束（宣言はバルーンにだけ付く・`ExpectedOrder` の「通常はバルーン」）を変えることになり、**公開の約束の意味の作り替えに近い**。非隣接には効かない（どちらにせよ外す道が要る）ので、仕組みが 2 通りに割れる。

### 参考（推さない）— 選択肢 E: `KeepDirectlyAbove` の形を作り替える

向きや有効／無効の欄を足す形。wintf の公開の約束（他のクレート・`tooltip_demo` の例が使う）を先例なしに変える。**brief の線引きどおり、採るなら Fable の段の判断**。A〜C がどれも形を変えずに済むので、要る理由は今のところ見当たらない。

## 7. 設計の段への推奨（決めではない）

- 共通: `normalize_scope_blocks` は「書かれた順のまま・補いだけ足す」に変え、記録の型 `Normalization` の `reordered` は「逆転／非隣接／隣接」が分かる形へ（areka 内部の型なので自由に変えられる）。合成は「（バルーン, キャラ）の連続が実在の並びに無いスコープ」を組を外す対象として求める——鎖の繋ぎから組の対を除く今の規則と同じ 1 本の規則の裏返しにする。
- 順序は「撤去が全部先・付与が全部後」を組の結び目にまで広げるのが本質の形。それを 1 か所で持つ（選択肢 B）か、段の並びで持つ（選択肢 A・C）かが最大の分かれ目。
- `KeepDirectlyAbove` の形は変えない方向（A〜C）で設計できる。形を変える案（E）を検討に上げるなら Fable の段の判断として明示する。

## 8. 設計判断の項目（要件ディスカッションへ）

1. **組の一時停止を wintf へ伝える口**: ⑴ 宣言 `KeepDirectlyAbove` の付け外し（選択肢 A）／⑵ 鎖の計画 `ChainPlan` に「組を外すバルーン」の欄を足す（選択肢 B）／⑶ 一時停止の印を新しい公開のコンポーネントとして足す（選択肢 C）／⑷ 宣言を逆向きに付け直す（参考 D）。**どれも `KeepDirectlyAbove` の欄は変えない**。欄を作り替える案（参考 E）を採るなら、wintf の公開の約束を先例なしに変える＝Fable の段の判断になる。
2. **1 巡の中で輪を作らない順序を誰が持つか**: ⑴ 鎖の適用が「撤去 → 組を外す → 組を張り直す → 付与 → 後押し」を一括で持つ（確定段の並びは不変・`spawn.rs` は触らない）／⑵ 鎖の適用を外す段と張る段に割り、間に組の系を挟む（`spawn.rs` の結線を変える）／⑶ 張り直しだけを鎖の後ろの新しい系にし、直上への是正も同じ巡で出す。次のフレームへ回す形は取らない。
3. **組を外す範囲**: ⑴ 逆転・非隣接のスコープだけ（最小・要件 4.4 の「他のスコープは組のまま」に素直）／⑵ グループに名指しされた全スコープの組を鎖が引き受ける（仕組みは一様だが、逆転の無いグループでも組の付け外しが起き、記録が変わる）。
4. **鎖が無くなる解除（グループ 0 本）で組へ戻ったときの重なりの直し**: 鎖の後押しが出ないので、組の直上への是正（今の確立系と同じ是正）を同じ巡で出す。その是正の検証を今どおり次の巡の実測照合で行うか（是正そのものは同じ巡・確かめだけ次の巡＝今の作りと同じ）。
5. **記録の語彙**: 受理の行の `normalized=` で `scope:false` と `+bN`／`+sN` の綴りは残し、`true` の代わりに「逆転のまま」「離したまま」を表す新しい語を足すか（完了 spec の実機の手順と既存の檻が `false` の綴りを読んでいる）。組を外した・張り直したの記録の語（組の切離しの理由に 1 語足すか、新しい行にするか）と水準（成功 debug・失敗 error）。一時停止中の組を沈降の観測から外すか、「一時停止」と書いて残すか。
6. **持ち主の輪への守り**: 順序の論証だけで足りるとするか、付与の直前に相手の持ち主を辿って輪にならないことを読む守り（書く直前の 1 回の読み取り・周期の観測ではない）を足すか（R1 の結果次第）。
7. **張り直しの契機**: 宣言の付与・印の除去・鎖の適用からの直接の呼び出しのどれか（議題 1・2 と連動）。確立系の「ペアにつき 1 度きり」の前提を外すことの扱い。
8. **陳腐化するテストの扱い**: 要件 2.4（寄せる）を主張している既存のテスト（台帳の `t_zgp15`〜`t_zgp17` 付近・分岐の対応表・drain／descript の受理行の檻・合成の前提の行）を、既存のファイルの中で撤去・書き直すか。新しく足すテストは新しい兄弟のファイルへ置く（structure.md の決まり）。
9. **網羅台帳の行の持ち主**: `sakura-script.toml` の `\![set,zorder,…]` の行の `owner` を `areka-P0-scope-zorder-pinning` のまま説明だけ書き替えるか、本 spec へ移すか。
10. **SSP の測り（brief の議題 2・4）を設計の前に行うか**: 非隣接がその順に重なるか・片方だけ名指しで補われる窓の置き場（R5）。areka の作りは測りの結果で変わらない見込み（要件は正典の「書かれた順」で立つ）だが、互換の記録の根拠になる。
11. **押したとき（要件 5.1・5.2）は OS の持ち主の鎖に任せ、areka は何も書かない**ことを確かめで閉じる（R3）。areka 側の「押したらバルーンを上げる」明示の処理は今も無いので、決定論の檻は「押しても重なりを書く処理が走らない」ことの固定になる。

## 9. SSP の測り（2026-10-18・要件ディスカッションの前・R5 を閉じる）

> 測ったもの: SSP 2.9.x（開発機で起動中）の MCP で台本を送り、ssp.exe の最上位の窓を手前から順に読み（`GetTopWindow`／`GetWindow(GW_HWNDNEXT)`）、各窓の持ち主（`GWLP_HWNDPARENT`）を並べた。窓の位置・設定・ゴーストは変えていない。測った後に `\![reset,zorder]` で戻した。

### 9.1 ぱすた（`窓際のぱすたさんDEBUG`・起動中の実物・指定 `s0,b0,s1`）

| 手前から | 窓 | 持ち主 |
| --- | --- | --- |
| 1 | s0 ぱすた（表示） | b0 |
| 2 | b0 ぱすたのバルーン（表示） | s1 |
| 3 | b1 窓のバルーン（**非表示**） | s1 |
| 4 | s1 窓（表示） | ゴーストの親の窓 |

### 9.2 非隣接（悪役令嬢クローディア・`\![set,zorder,b1,s0,s1,b0]` を両方のバルーンを出した状態で）

- 持ち主: b1 ← s0 ← s1 ← b0 ← ゴーストの親の窓。**書かれた順のまま鎖を張る**（同じスコープの 2 枚を寄せない）＝要件 2.2 と一致する（brief の議題 2 の裏取り）。
- ただし実際の重なり（手前から）は s1 → b1 → s0 → b0 で、指定の 1.5 秒後に読み直しても同じだった。持ち主を張り替えただけで後押しをしないので、直前に手前にあった s1 が手前に残る（完了 `scope-zorder-pinning` の研究 §12.1「張り替えだけでは重なりは動かない」と同じ現象）。**SSP の癖**として写さない（要件 9.4）。

### 9.3 解除（同じゴーストで `\![reset,zorder]`）

- 持ち主が組の形（b0 ← s0・b1 ← s1・キャラはゴーストの親の窓）へ戻る＝要件 4.5 と一致する。

### 9.4 測らなかったもの

- 押したとき（要件 5・brief の議題 3）は、入力を送る許可が要るので測っていない。持ち主の鎖の中のどれかの窓が活性化すると OS は鎖ごと手前へ上げる、という完了 spec の実測（§12.5・`HWND_TOP` の書き込み）からの見込みに留まる＝R3 として設計と実機の確かめへ持ち越す。
