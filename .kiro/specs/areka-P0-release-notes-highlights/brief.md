## Problem

リリースの本文が、前の版からの PR の題名を全件並べた一覧になっている。読む人（areka を使う人・ゴーストを作る人）は、その版で何が良くなったのかを本文から読み取れない。

- 件数が多い。`v0.0.2` は 263 行で、34,525 字ある。
- 題名は開発者向けの言い回しで、頭に spec 名が付いている（`feat(areka-P0-shiori-com): …`）。
- 利用者に関係のない内部の作業（spec の起票・ロードマップの棚卸・スキルの文書）も同じ一覧に並ぶ。

## Current State

2026-10-11 の main（`09f4e33f`）と、公開済みの `v0.0.2` のリリースを見て確かめた。

- **作り方**: リリース CI は `.github/workflows/release.yml` の 1 本（補助スクリプトは無く、段の本文は workflow の中に書いてある）。段「Release を公開」が `gh release create v{版}` に `--generate-notes`（一つ前のタグが在れば `--notes-start-tag`）を付け、本文を GitHub に作らせている。
- **ノートの中身**: GitHub が作る「What's Changed」＝一つ前のタグからの PR の題名の一覧。main へは PR の squash でしか入らないので、1 PR が 1 行になる。種類で分けない。取捨選択はしない。除くものも無い。
- **次の版の内訳**: `v0.0.2` より後に main へ入った変更は 35 本（題名の頭の種類で、機能 15・直し 3・性能 1・文書 15・雑務 1）。文書の 15 本は、ほぼ内部の作業（`docs(discovery)`・`docs(roadmap)` など）である。
- **添付**: 4 つに決め打ち（x64 と arm64 の zip と、それぞれの `.sha256`）。段「4 つの確かめ」が 4 つの在ることと中身を見て、同じ 4 つを公開の段へ渡す。ノートは添付しない。
- **一つ前のタグ**: 段「既存の Release の検査」が決める（`Get-PrevTag`・結果は `prev_tag`）。
- **公開済みの Release**: そのタグの Release が既に在れば、ビルドの前に止まる（段「既存の Release の検査」）。`gh` は下書きで作り、全部を載せ終えてから公開する。途中で失敗したら、段「後始末」がこの走りの作った Release を消す（タグは消さない）。
- **タグの検査**: 段「版の検査」が、タグの版と `Cargo.toml` の版の一致を見る。ここで落ちれば、後ろの段は何も公開しない。
- **乾いた走り**: 同じ workflow を main で手で起こせる（公開しない）。そのときの版は main の `Cargo.toml` の版＝直前に公開した版になる。
- **リリースの手順**: 繰り返し spec `areka-P0-release-cycle`。版上げの PR に載せてよいファイルを要件 3.3・4.2 で数え上げている（根の `Cargo.toml` の 2 行・`Cargo.lock`・`THIRD-PARTY-NOTICES.md`・`dist/README.txt` の日付の行）。差分がその外に出たら止まる（要件 3.5・タスク 3.2）。公開の後の確かめは「4 つのファイルが添わっていること」（要件 6.1）。手順は workflow のファイルを書き換えない（要件 1.6）。
- **自動テスト**: `release.yml` を動かすテストは、リポジトリに無い（`release-ci-workflow` は、静的な確かめ・段の本文を手元で回す確かめ・乾いた走りで判定した）。
- **今の方式を書いている文書**: 完了した `areka-P0-release-ci-workflow` の設計（`--generate-notes`）、`areka-P0-release-cycle` の設計（Release の本文の比べる範囲の確かめ）。steering と説明書に、ノートの作り方を書いた所があるかは要件定義で洗う。
- **令嬢の口調の定義**: areka のリポジトリには無い。定義が在るのは pasta のリポジトリ（`book/AUTHORING.md` 第 1 節）である。areka の `README.md` と `vendors/sample_ghost/README.md` は、他の作者のゴースト「悪役令嬢クローディア（`claudia`）」を検体として載せている（議題 2）。
- **公開済みの版**: `v0.0.2` の 1 つだけ（2026-10-06）。

## Desired Outcome

- リリースの本文は、その版で特に注目に値するいくつかの内容を、日本語で紹介する文章である。spec 名を載せない。口調は pasta とそろえて Claudia（令嬢）にする（伝え聞きの決定・議題 2 で確かめる）。
- 見どころの見出しの末尾に、元になった PR の番号を付ける（例「### 範囲を選ぶ選択肢に対応しましたわ(#293)」）。GitHub が本文の `#番号` を PR へのリンクに変えるので、見どころから変更の中身へたどれる。
- すべての変更を並べた詳しいリリースノートは、Assets にドキュメントとして添付する。本文から、その添付へたどれる。詳しいリリースノートにも spec 名を載せない。
- 本文の文章は、公開する前に PR で読めて、git に残る。
- 見どころの無いリリースタグでは、リリース CI が何も公開する前に止まる。
- リリースの手順（`release-cycle`）が、見どころを書く段と、その確かめ方を持つ。

## Approach

**見どころをリポジトリのファイルとして書き、リリース CI がそれを本文に使う**（2026-10-11 開発者が pasta の側で決めた形。areka の起票の推しも同じ形だった）。

1. リリースの手順が、版上げの PR で、その版の見どころのファイルを書く。タグを打つ前に読める。
2. リリース CI が、ビルドの前の段で、その版の見どころのファイルが在ることを確かめる。無ければ、何も公開する前に止まる。
3. リリース CI が、一つ前のタグからの全件の一覧を、詳しいリリースノートとして Markdown のファイルにし、Assets に添付する（5 つ目の添付）。
4. リリース CI が、見どころのファイルに、詳しいリリースノートへのリンクを足したものを本文にする（`--generate-notes` をやめる）。

- **採らなかった案**:
  - 公開の後で本文を書き換える案（CI は定型文で公開し、その後に手順が `gh release edit` で差し替える）: 公開の通知メールは定型文のまま届き、差し替えに失敗しても気づきにくく、公開の前に読めず、git に残らない（pasta の側で開発者が比べて外した）。
  - 機械だけで短くする案（本文を新機能と直しの題名だけにする）: 紹介の文章にならず、口調を付けられない（同上）。
  - 根に `CHANGELOG.md` を置き、各 spec の PR が 1 行ずつ足す案: 同時に 8 本まで走る枝が、同じファイルの同じ場所を取り合う。
  - 変更履歴を作る専用の道具（git-cliff など）を CI に足す案: 道具が増える。`gh` と PowerShell の数行で足りる。
  - 見どころを workflow の中で AI に書かせる案: 公開の前に開発者が読めない。CI に鍵と費用が要る。

### pasta との違い（合わせない所）

- **一覧のもと**: pasta はコミットの件名を自前のスクリプトで並べている。areka は GitHub に PR の題名の一覧を作らせている。詳しいリリースノートを作る部分は、areka では新しく書く（どこに書くかは議題 9）。
- **添付の数**: pasta は 3 つから 4 つ。areka は 4 つから 5 つ。
- **再実行**: pasta の CI は、失敗した job を再実行すると足りないものだけを補う。areka の CI は、下書きに全部を載せ終えてから公開し、失敗したら自分の Release を消して頭からやり直す。areka はこの形を保つ（「足りないものだけ補う」は持ち込まない）。
- **乾いた走り**: areka にだけ在る。乾いた走りの版は直前に公開した版なので、その版の見どころのファイルが main に在れば、乾いた走りで本文と詳しいリリースノートの見た目を確かめられる（議題 10 と結び付く）。
- **公開済みの版**: pasta の仮定は「書き直さない」。areka は公開済みが `v0.0.2` の 1 つだけで、開発者が読みにくいと言ったのがその頁なので、「直す」を推す（議題 10）。

## Constraints

- **席**: リリースの実行中（`release-cycle` が版上げの PR を出してから見守りを終えるまで）は、`release.yml` を触るこの spec を main へ入れない。
- **問題があれば止める**: 見どころが無い・空である・版が合わないときは、警告で続けずに、公開の前に失敗させる。
- **タグは動かさない・同じ版で出し直さない**（`release-cycle` 要件 5.4・6.5）。見どころが欠けたままタグを打つと版を 1 つ無駄にするので、手順の側でも PR を出す前に確かめる。
- **`release.yml` の今の決まりを保つ**: 権限は `contents: write` だけ／段の入力は環境変数だけで、GitHub の式を段の本文に埋めない／タグの名前で Release を探す行は「既存の Release の検査」と「後始末」で 1 字違わず同じ／`gh` は下書きで作り、全部を載せ終えてから公開する／確かめの段が見た同じファイルを公開の段へ渡す。
- **文字コード**: 見どころと詳しいリリースノートは日本語の UTF-8。`gh` の出力を PowerShell で受けて整えるとき、端末の文字コードで解かない（読む側で UTF-8 として読む。端末の文字コードは変えない）。workflow が走りの記録へ出す自分の文は ASCII だけ。
- **道具を足さない**: `gh` と PowerShell 7 で作る。
- **技術的な正確さ**: 口調は飾りである。動きが変わる点は、口調のために読み違えられないように書く。
- **言葉**: 本文と詳しいリリースノートは使う人が読む。spec 名・開発の中の呼び名を出さない。
- **言語**: 本文は日本語。
