# Requirements Document

## Project Description (Input)
リリースの本文を、前の版からの PR の題名を全件並べた一覧から、その版で特に注目に値するいくつかの内容を日本語（Claudia の口調）で紹介する文章に替える。すべての変更を並べた詳しいリリースノートは、Markdown のファイルにして Assets に添付し、本文からたどれるようにする。spec 名は本文にも詳しいリリースノートにも載せない。

見どころは、版上げの PR でリポジトリのファイル（`doc/release-notes/v{版}.md`）として書き、リリース CI（`.github/workflows/release.yml`）がそれを本文に使う。見どころの無いリリースタグでは、リリース CI が何も公開する前に止まる。繰り返し spec `areka-P0-release-cycle` に、見どころを書く段とその確かめ方を足す。公開済みの `v0.0.2` の頁も同じ形に直す（zip・ハッシュ・タグは変えない）。

起票の経緯・今の状態の測定・pasta とそろえた決めごと・要件定義の議題 1〜10 は、同じフォルダの `brief.md` が正本である。

## Introduction

公開済みの `v0.0.2` のリリースの頁は、本文が PR の題名 263 行の一覧で、その版で何が良くなったのかを読み取れない（2026-10-11 開発者の指摘）。本 spec は、リリースの頁を次の形に変える。

- **本文**: その版の見どころ（いくつかの注目に値する内容）を、日本語で紹介する文章。語り手は Claudia（令嬢の口調）。
- **添付**: すべての変更を並べた詳しいリリースノート（Markdown）を 1 つ足す。添付は 4 つから 5 つになる。本文の末尾から、その添付へたどれる。

見どころは人（リリースの手順を回す AI と、それを承認する開発者）が版上げの PR で書き、リリース CI がそれを本文に使う。詳しいリリースノートは機械が作る。

### 本書で使う言葉

- **版・タグ・版上げの PR・乾いた走り**: `areka-P0-release-cycle` の要件の「本書で使う言葉」と同じ意味で使う。
- **見どころ**: その版で特に注目に値する内容の 1 つ。見出し 1 つと、紹介の文章から成る。
- **見どころのファイル**: 1 つの版の見どころをまとめた Markdown のファイル。リリースの本文のもとになる。
- **詳しいリリースノート**: 一つ前のタグからその版までに main へ入ったすべての変更を、1 変更 1 行で並べた Markdown のファイル。
- **変更**: main の本線に入った 1 つのコミット。今は main へ PR の squash でしか入らないので、1 PR が 1 コミットで、題名の末尾に PR の番号が `(#番号)` の形で付く。`v0.0.2` より前には、PR を通さずに入った古いコミットも在る（2026-10-11 の測定で、`v0.0.1` から `v0.0.2` までの 614 のうち 418）。
- **題名の接頭辞**: PR の題名の頭の「種類(スコープ): 」の部分（例 `feat(areka-P0-anchor-tag-canon): `）。
- **spec 名**: `areka-P0-` で始まる名前。
- **内部の作業**: 製品の中身を変えない変更（spec の起票・ロードマップ・steering・スキルの文書など）。機械は、題名のスコープが spec 名でない変更をこれと見なす。
- **リリース CI**: `.github/workflows/release.yml`。
- **リリースの手順**: 繰り返し spec `areka-P0-release-cycle` の手順。
- **見どころの検査**: 見どころのファイルが決まりの形を満たすかを見る検査（要件 2）。

## Boundary Context

- **In scope**:
  - 見どころのファイルの置き場所・名前・形・書き方の決まり。
  - 見どころの検査（手元とリリース CI の両方で同じ物）。
  - 詳しいリリースノートの作り方（題名の整形・区分け・内部の作業の扱い）。
  - リリース CI の変更（検査の段・詳しいリリースノートの生成と添付・本文の組み立て・乾いた走りでの見せ方）。
  - リリースの手順の文書（`areka-P0-release-cycle` の `requirements.md`・`design.md`・`tasks.md`）への、見どころを書く段の追加と、数え上げの直し。
  - 公開済みの `v0.0.2` の頁の直し（1 回きり）。
  - 今の本文の作り方を書いている、完了していない文書の更新。
- **Out of scope**:
  - 見どころの材料を、spec の完了のたびに溜めておく仕組み。
  - リポジトリの通しの変更履歴（`CHANGELOG.md`）。説明書 `dist/README.txt` への更新履歴の追加。
  - PR の題名の書き方の決まりの変更。
  - 英語の本文。
  - zip の中身（詳しいリリースノートは zip に入れない）。
  - crates.io への公開（`crates-io.yml`）・winget への PR・配布物のビルドと署名・版の決め方・タグの打ち方。
  - 完了した `areka-P0-release-ci-workflow` の文書の書き換え（公開の段の新しい形は、本 spec の設計に書く）。
  - pasta のリポジトリの文書。
- **Adjacent expectations**:
  - リリース CI は、段「版の検査」でタグの版と `Cargo.toml` の版の一致を見ており、段「既存の Release の検査」で一つ前のタグを決めている。本 spec はこの 2 つの結果を使い、決め方を変えない。
  - リリースの手順は、決まりを自分の文書の中に置く例外の spec である。見どころを書く段は同 spec の文書に書き、`workflow.md` や `kiro-complete` は直さない。
  - リリースの実行中（リリースの手順が版上げの PR を出してから見守りを終えるまで）は、本 spec を main へ入れない。
  - 新しい公開の段が本番で初めて動くのは、リリースの手順の次の回（`v0.0.3`）である。本 spec はそれより前に着地する。
  - `areka-P0-winget-release-automation` は、Release の添付から zip を名前で拾う。詳しいリリースノートの名前は、その拾い方に当たらない（要件 5.3）。
  - `areka-P0-release-code-signing` は `release.yml` のビルドと zip の間に段を挟む。同じファイルを触るので、本 spec とは直列に進める。

## Requirements

### Requirement 1: 見どころのファイルの形

**Objective:** As a areka を使う人・ゴーストを作る人, I want リリースの頁の本文で、その版の注目に値する内容を日本語の紹介として読みたい, so that その版で何が良くなったのかが、一覧を読まなくても分かる

#### Acceptance Criteria

1. The 見どころのファイル shall 版ごとに 1 つ、`doc/release-notes/v{版}.md` に置く（例 `doc/release-notes/v0.0.3.md`・UTF-8・日本語）。
2. The 見どころのファイル shall 見どころを 1 つ以上持ち、見どころ 1 つを「見出し 1 つと、その紹介の文章」の形で書く。
3. The 見どころの見出し shall 末尾に、元になった PR の番号を `(#番号)` の形で持つ（例「範囲を選ぶ選択肢に対応しましたわ(#293)」）。
4. Where 1 つの見どころが複数の PR にまたがる, the 見どころの見出し shall 末尾に、その PR の番号を `(#番号, #番号)` の形で並べる。
5. The 見どころのファイル shall spec 名を含まない。
6. The 見どころのファイル shall 全文を Claudia（令嬢）の口調で書き、語り手は「Claudia」と名乗ってよい。
7. The 見どころのファイル shall 最初に現れる「Claudia」を出典の URL へのリンクにし、出典の断り書きの段落は書かない。
8. Where その版に、使う人やゴーストを作る人が何かを直さなければならない変更（動きが変わる点）が在る, the 見どころのファイル shall それを見どころとして必ず載せ、何がどう変わるかを、口調に紛れない事実の文で言い切る。
9. Where その版が不具合の修正だけである, the 見どころのファイル shall 修正のうち使う人に効くものを見どころとして 1 つ以上載せる。
10. The 見どころのファイル shall 詳しいリリースノートへのリンクを自分では持たない（リリース CI が本文に足す・要件 5.1）。
11. The 見どころの書き方の決まり（形・口調・出典の URL・見どころの数の目安〔3〜5〕） shall areka のリポジトリの中の 1 か所に置き、pasta のリポジトリを読まなくても見どころを書ける。

### Requirement 2: 見どころの検査

**Objective:** As a 開発者, I want 見どころのファイルが決まりの形を満たすことを、タグを打つ前に機械で確かめたい, so that 見どころが欠けたままタグを打って、版を 1 つ無駄にすることがない

#### Acceptance Criteria

1. When 版を指して見どころの検査を回す, the 見どころの検査 shall 次のすべてを見る: その版の見どころのファイルが在ること、見どころが 1 つ以上在ること、すべての見どころの見出しの末尾に PR の番号が在ること（要件 1.3・1.4 の形）、spec 名が現れないこと、出典の URL へのリンクが在ること。
2. If 見どころの検査のどれかが欠ける, then the 見どころの検査 shall 欠けたものをすべて挙げ、失敗の終了コードで終わる。
3. When 見どころの検査がすべて通る, the 見どころの検査 shall 成功の終了コードで終わる。
4. The 見どころの検査 shall 読むだけで、見どころのファイルも、ほかのファイルも書き換えない。
5. The 見どころの検査 shall 手元でもリリース CI でも同じ物を使い、同じ入力に同じ合否を返す。
6. The 見どころの検査 shall その版の名前のファイルだけを見て、ほかの版のファイルを代わりに使わない。
7. The 見どころの検査 shall 画面と走りの記録へ出す自分の文を ASCII だけで書く。

### Requirement 3: 見どころの無いタグでは、公開の前に止まる

**Objective:** As a 開発者, I want 見どころの無いリリースタグで、リリース CI が何も公開せずに止まってほしい, so that 本文の無いリリースや、定型文のままのリリースが外に出ない

#### Acceptance Criteria

1. When リリース CI がタグの push で始まる, the リリース CI shall 配布物を組み立てる前に、その版の見どころの検査を回す。
2. If 見どころの検査が失敗する, then the リリース CI shall Release を下書きでも作らず、何も添付せず、失敗で終わる（警告で続けない）。
3. When リリース CI が乾いた走りで始まる, the リリース CI shall タグの走りと同じ見どころの検査を同じ場所で回し、同じ合否で進むか止まる。
4. If 見どころの検査が失敗する, then the リリース CI shall 欠けたものを走りの記録から読めるようにする。

### Requirement 4: 詳しいリリースノート

**Objective:** As a areka を使う人・ゴーストを作る人, I want その版に入ったすべての変更を、読みやすく整えた 1 つの文書で読みたい, so that 見どころに載らなかった変更も、必要なときに確かめられる

#### Acceptance Criteria

1. The 詳しいリリースノート shall 一つ前のタグからその版までに main へ入ったすべての変更を、1 変更 1 行で載せる（取捨選択をしない。行の数は変更の数と一致する）。
2. If 一つ前のタグが無い, then the 詳しいリリースノート shall 最初のコミットからその版までのすべての変更を載せる。
3. The 詳しいリリースノートの各行 shall 題名から題名の接頭辞を外したものと、その PR の番号（題名の末尾に `(#番号)` が在るとき）を持つ。題名の末尾に PR の番号の無い変更は、番号なしで載せる（落とさない）。
4. The 詳しいリリースノート shall `areka-P0-` という字の並びを含まない（題名の接頭辞の外に残ったものは、その字の並びを外す）。
5. The 詳しいリリースノート shall 製品の変更（題名のスコープが spec 名の変更）を、種類ごとの見出し（新しい機能・不具合の修正・性能の改善・そのほか）に分けて並べる。
6. The 詳しいリリースノート shall 内部の作業を、製品の変更の後ろの別の見出しにまとめる（除かない）。
7. If 変更の題名が「種類(スコープ): 」の形でない, then the 詳しいリリースノート shall その変更を落とさず、題名をそのまま内部の作業の見出しに載せる。
8. While ある見出しに入る変更が 0 件である, the 詳しいリリースノート shall その見出しを出さない。
9. The 詳しいリリースノート shall 冒頭に、版と、どのタグからの変更かを示す。
10. The 詳しいリリースノート shall UTF-8 で、題名の日本語を 1 字も変えずに持つ（実行する端末の文字コードに左右されない）。
11. When 開発者または リリースの手順が、タグを打つ前に手元で一覧を求める, the 詳しいリリースノートを作る部分 shall 一つ前のタグから今の枝の先頭までの変更を、リリース CI が作る物と同じ形で出す。
12. The 詳しいリリースノートを作る部分 shall 同じ変更の並びから、いつも同じ中身を作る。

### Requirement 5: Release の本文と添付

**Objective:** As a areka を使う人・ゴーストを作る人, I want リリースの頁で、見どころを本文として読み、詳しいリリースノートを添付から開きたい, so that 短い紹介と全件の一覧を、同じ頁から読み分けられる

#### Acceptance Criteria

1. When リリース CI が Release を公開する, the リリース CI shall 本文を「その版の見どころのファイルの中身」と、その後ろの「詳しいリリースノートの添付へのリンク」だけで組み立てる（GitHub に作らせた一覧を本文に入れない）。
2. When リリース CI が Release を公開する, the リリース CI shall 5 つを添付する: x64 と arm64 の zip、それぞれの `.sha256`、詳しいリリースノート。
3. The 詳しいリリースノートの添付 shall `release-notes-v{版}.md` という名前にする（`.zip` で終わらない）。
4. The リリース CI shall zip と `.sha256` の名前・中身・作り方を変えず、zip に詳しいリリースノートを入れない。
5. The リリース CI shall Release を下書きで作り、5 つを載せ終えてから公開し、途中で失敗したらこの走りの作った Release を消す（タグは消さない）、という今の形を保つ。
6. If 詳しいリリースノートを作れない、または本文を組み立てられない, then the リリース CI shall Release を公開せずに失敗で終わる。
7. When リリース CI が乾いた走りで配布物の確かめまで進んだ, the リリース CI shall 何も公開せずに、組み立てた本文と詳しいリリースノートを、その走りの結果の頁から読めるようにする。
8. The リリース CI shall 今の決まりを保つ: 権限は `contents: write` だけ／段の入力は環境変数だけで、GitHub の式を段の本文に埋めない／タグの名前で Release を探す行は段「既存の Release の検査」と段「後始末」で 1 字違わず同じ／走りの記録へ出す自分の文は ASCII だけ／端末の文字コードを書き替えない。
9. The リリース CI と詳しいリリースノートを作る部分 shall 今の道具（`gh`・`git`・PowerShell 7）だけで動き、新しい道具を足さない。

### Requirement 6: リリースの手順に、見どころを書く段を足す

**Objective:** As a 開発者, I want リリースの手順が、版上げの PR で見どころを書き、PR を出す前に確かめてほしい, so that 見どころを公開の前に PR で読めて、git に残り、欠けたままタグを打たない

#### Acceptance Criteria

1. The リリースの手順の文書 shall 版を上げた後・版上げの PR を出す前に、一つ前のタグからの変更の一覧を手元で出し（要件 4.11）、見どころを選んで、その版の見どころのファイルを書く段を持つ。
2. The リリースの手順の文書 shall 版上げで書き換えてよいファイルの数え上げに、その版の見どころのファイル 1 つ（`doc/release-notes/v{版}.md`）を加える。ほかの版の見どころのファイルは加えない。
3. The リリースの手順の文書 shall 版上げの PR を出す前に見どころの検査を回し、失敗したら PR を出さずに止まって開発者へ報告する段を持つ。
4. The リリースの手順の文書 shall 版上げの PR の説明に、見どころのファイルの所在を書き、開発者がマージの承認の前に見どころを読めるようにする。
5. The リリースの手順の文書 shall 公開の後の確かめを「5 つのファイル（x64 と arm64 の zip・それぞれの SHA256・詳しいリリースノート）が添わっていること」と「本文がその版の見どころであること」に改める。
6. The 本 spec shall リリースの手順の文書のうち、版上げの数え上げと「4 つのファイル」に従っている所（要件・設計・タスク）をすべて洗い出し、直した所と直さなかった所を、理由を添えて記録する。
7. The 本 spec shall リリースの手順の繰り返しの形を保つ: `tasks.md` のチェックはすべて未完了のまま、`spec.json` の段は変えず、タスクの並びは毎回同じに回せる。
8. The リリースの手順 shall 見どころを書く段を足した後も、workflow のファイルと `tools/` のスクリプトを書き換えない（リリースの手順の要件 1.6 を保つ）。

### Requirement 7: 公開済みの `v0.0.2` の頁の直し

**Objective:** As a areka を使う人・ゴーストを作る人, I want 公開済みの `v0.0.2` の頁も、見どころの本文と詳しいリリースノートの添付の形で読みたい, so that いま公開されているただ 1 つの版の頁が読める

#### Acceptance Criteria

1. The 本 spec shall `v0.0.2` の見どころのファイル（`doc/release-notes/v0.0.2.md`）を、要件 1 の形で書き、見どころの検査を通す。
2. When `v0.0.2` の頁を直す前, the 本 spec shall 直す前の本文と、添付の一覧（名前・大きさ・ハッシュ）を証跡として保存する。
3. The 本 spec shall `v0.0.2` の頁の本文の差し替えと添付の追加を、開発者が見どころの文章を読んで明示で承認した後に行う。
4. When `v0.0.2` の頁を直す, the 本 spec shall 本文と詳しいリリースノートを、リリース CI と同じ作り方（要件 4・要件 5.1）で作った物にする。
5. When `v0.0.2` の頁を直した, the 本 spec shall 次を確かめて記録する: 本文が見どころであること、添付が 5 つであること、もとの 4 つの添付の名前・大きさ・ハッシュが直す前と同じであること、タグが同じコミットを指していること、Release が公開の状態のままであること。
6. The 本 spec shall `v0.0.2` の zip・`.sha256`・タグを書き換えず、Release を作り直さない。
7. When 本 spec が main へ入る, the `v0.0.2` の頁の本文 shall main の `doc/release-notes/v0.0.2.md` から作った物と一致している（承認の後に見どころを直したら、頁も直し直す）。

### Requirement 8: 文書と検査

**Objective:** As a 開発者, I want 今の本文の作り方を書いている文書が新しい形に合い、一覧の整形が檻に入っていてほしい, so that 文書が古い方式を語り続けたり、整形の決まりが黙って崩れたりしない

#### Acceptance Criteria

1. The 本 spec shall 完了していない文書（steering・`doc/`・根の `README.md`・リリースの手順の文書）のうち、リリースの本文の作り方または添付の数を書いている所をすべて洗い出し、新しい形に合わせる。
2. The 本 spec shall 完了した spec（`.kiro/specs/completed/`）の文書を書き換えない。
