# Requirements Document

## Project Description (Input)

- **困っている人**: シェルの作者。目や口などの部品を 1 つのサーフェスにまとめ、いくつもの表情のサーフェスから使い回したい。今は部品の画像を表情ごとに element定義で並べ直すしかなく、部品にまばたきなどのアニメーションを持たせると、表情ごとに同じアニメーションを書き写すことになる。
- **今の状況**: areka の設計文書は「element定義からサーフェスを指す入れ子」を前提にしているが、実装されていない。element定義は画像しか置けない。ファイル名の欄に数字だけを書くと、その名前の画像を探して見つからず、部品が描かれないまま読み込みの失敗が記録される。pattern定義が指すサーフェスは重ねられるが、その内側のアニメーションは止まった絵になる。サーフェスを切り替えると、その窓のアニメーションはすべて最初からになる。
- **変えたいこと**: element定義のファイル名の欄に数字だけを書くと、その番号のサーフェスを部品として置けるようにする。入れ子は何段でもよい。子のサーフェスのアニメーションは親の中で動き、親のサーフェスを切り替えても巻き戻らない。areka 独自の仕様である。確定事項の詳細は同じフォルダの `brief.md`（2026-10-01 起票・2026-10-04 再測定）にある。

## Introduction

本 spec は、シェルの surfaces.txt の element定義に、サーフェスを部品として置く書き方を足す。

```
surface1
{
  element0,overlay,body.png,0,0
  element1,overlay,100,40,60
}

surface100
{
  element0,overlay,eye_open.png,0,0
  animation0.interval,sometimes
  animation0.pattern0,overlay,101,50,0,0
  animation0.pattern1,overlay,-1,50,0,0
}
```

`surface1` の `element1` は、ファイル名の欄が数字だけなので、サーフェス 100 を X=40, Y=60 に置く。サーフェス 100 のまばたきは `surface1` の中で動く。

以下、element定義で置かれる側のサーフェスを「子」、置く側のサーフェスを「親」、`\s[...]` などで窓に直接表示されているサーフェスを「一番上のサーフェス」と呼ぶ。

正典との関係は次のとおり。

- ukadoc の element定義は `element*,描画メソッド,ファイル名,X座標,Y座標(,オプション...)`（`ukadoc:descript_shell_surfaces` の element の項）。本 spec は欄の並びも描画メソッドも変えず、**ファイル名の欄が数字だけのときに限り、サーフェスの番号として読む**。
- 前例は ukadoc の pattern定義 `animation*.pattern*,描画メソッド,サーフェス番号,ウェイト,X座標,Y座標`。描画メソッドを残したまま、欄でサーフェスの番号を指す。
- element定義からサーフェスを指す書き方は正典に無い areka 独自の語である。SSP は数字の名前の画像を探して見つけられず、その部品を描かないだけになる（本 spec は SSP での見え方を保証しない）。
- ukadoc の element定義の項「element定義されたサーフェスをアニメーションパーツとして用いた場合も、一枚の画像のように振る舞う」は、element定義で組んだサーフェスを pattern定義で指しても、組み上がった 1 枚の絵として重なる、という話である。指された側のサーフェスに書かれたアニメーションが動くかどうかを、正典は定めていない。本 spec はここを次のように定める: サーフェスは、element定義で置かれても pattern定義で指されても、自分の時計を持つ独立した部品であり、親のアニメーションはそれを出したり消したりするだけである（2026-10-04 開発者裁定）。

## Boundary Context

- **In scope**:
  - `surface*`ブレス・`surface.append*`ブレスの element定義で、ファイル名の欄が数字だけの行をサーフェスの番号として読み、そのサーフェスを部品として置くこと。何段でも入れ子にできること。
  - 無い番号・循環する参照を、ログに残して安全に読み飛ばすこと。
  - 子のサーフェスの当たり判定の領域（collision）を親へ持ち込むこと。
  - 子のサーフェスのアニメーションを親の中で動かすこと。子の時計を一番上のサーフェスの切り替えから独立させること。
  - pattern定義が指すサーフェスの内側のアニメーションを、element定義で置いた子と同じ時計で動かすこと。
  - 子のサーフェスに書かれた描画メソッド `balloon` の element定義を、警告を残して無視すること。
  - 決定論的なテストと、入れ子を持つ試験用シェル（リポジトリ内の検体）。areka 独自の語の登記（`doc/COMPAT_ARCHITECTURE.md` §8）。
- **Out of scope**:
  - 動く画像（GIF・APNG・WebP）を子のサーフェスへ自動で分解して置くこと（`animated-image-playback`）と、その読み込み（`animated-image-decode`）。
  - 子のサーフェスの中でシェル内バルーンを使えるようにすること。
  - 台本の再生と `\s[...]`・`\i[...]` の意味の変更。`\i[ID]` は今までどおり一番上のサーフェスのアニメーションだけを指す。
  - element定義のオプション（`--clipping` ほか）と、`overlay` 以外の描画メソッドの対応を広げること。画像を置く element定義で今動く範囲が、サーフェスを置く element定義でも動く。
  - `balloon` の element定義を並び順どおりの重ね順で描くこと、および窓の中の部品どうしの重なり順の裁定（`balloon-element-order`）。
  - SSP での見え方。
- **Adjacent expectations**:
  - `shell-balloon`（着地済み）: 描画メソッドが `balloon` の element定義は、ファイル名の欄が数字だけでも箱の名前として読まれる。本 spec はこの読み方を変えない。
  - `animated-image-playback`: 本 spec の「数字だけの element定義」と「独立した子の時計」の上に載る。本 spec は動く画像を扱わない。
  - `animated-image-decode`・`mcp-expression-table`: 同じ時期に並走する。本 spec はこれらが扱う振る舞い（動く画像のコマの読み込み・表情の説明の読み取り）を変えない。
  - 子のサーフェスで動くアニメーションの種類は、そのサーフェスを一番上に表示したときに今動く種類と同じである。今動かない間隔の語（`talk`・`always` ほか）は子でも動かず、後続の spec が一番上のサーフェスで実装した時点で子でも動く。

## Requirements

### Requirement 1: element定義でサーフェスを部品として置く書き方

**Objective:** As a シェルの作者, I want element定義のファイル名の欄に数字だけを書いてサーフェスを部品として置けること, so that 部品を 1 つのサーフェスにまとめて、いくつもの表情のサーフェスから使い回せる

#### Acceptance Criteria

1. When `surface*`ブレスの element定義のファイル名の欄が半角の数字（0〜9）だけで書かれている場合, the areka shall その欄を十進のサーフェス番号として読み、その番号のサーフェスを部品として置く
2. When `surface.append*`ブレスの element定義のファイル名の欄が半角の数字だけで書かれている場合, the areka shall 対象のサーフェスに、`surface*`ブレスに書いた場合と同じ規則でサーフェスを部品として置く
3. When element定義のファイル名の欄に数字以外の文字が 1 つでも含まれる場合, the areka shall その欄を今までどおり画像のファイル名として読む
4. When element定義の描画メソッドが `balloon` の場合, the areka shall ファイル名の欄が数字だけでも、今までどおりシェル内バルーンの名前として読む
5. While シェルのフォルダに数字だけの名前の画像ファイルがある場合, the areka shall 数字だけの欄をサーフェス番号として読み、その画像ファイルを element定義の画像として使わない
6. The areka shall サーフェスを置く element定義の数に、1 つのサーフェスあたりの上限を設けない
7. The areka shall 同じ番号のサーフェスを、1 つの親の中の複数の位置にも、複数の親にも置けるようにする
8. When 数字だけの欄が指すサーフェスが、ブレスを持たずファイル名の慣習（`surface<数字>.png`）だけで建つサーフェスである場合, the areka shall そのサーフェスを、ブレスで定義されたサーフェスと同じく部品として置く
9. If 数字だけの欄が、サーフェス番号として扱える範囲を超える大きさの数である場合, the areka shall その欄を画像のファイル名として読まず、シェルに無い番号を指した場合（要件 3.1）と同じに扱う

### Requirement 2: 入れ子の絵の合成

**Objective:** As a シェルの作者, I want 置いた子のサーフェスが、単独で表示したときと同じ絵で、指定した位置と重ね順に描かれること, so that 部品のサーフェスを作り直さずに親の絵へ組み込める

#### Acceptance Criteria

1. When 親のサーフェスが表示される場合, the areka shall サーフェスを置く element定義の位置に、子のサーフェスの絵を、子の画像の左上が親の X,Y（サーフェス画像のピクセル単位）に来るように重ねる
2. The areka shall 子のサーフェスの絵を、親の element定義の番号の順（番号の大きいものが手前）に従って、画像を置く element定義と同じ規則で重ねる
3. When 子のサーフェスがさらにサーフェスを置く element定義を持つ場合, the areka shall 段数に上限を設けずに内側のサーフェスまで重ね、各段の X,Y を足し合わせた位置に描く
4. When 親のサーフェスの `element0` がサーフェスを指し、親に対応する `surface*.png` がある場合, the areka shall 画像を指す `element0` のときと同じく `surface*.png` の内容を破棄し、`element0` の子のサーフェスの絵で置き換える
5. The areka shall 親のサーフェスの外形（窓の大きさのもとになる範囲）に、子のサーフェスを置いた範囲を含める
6. While 子のサーフェスのアニメーションのコマが進んでいる間, the areka shall 親のサーフェスの外形を、一番上のサーフェス自身のアニメーションのときと同じ規則で安定させる
7. When pattern定義が指すサーフェスが、サーフェスを置く element定義を持つ場合, the areka shall 子のサーフェスの絵を、element定義で置いたサーフェスの中の子と同じ規則で重ねる
8. When 一番上のサーフェスの表示の拡大率が変わる場合, the areka shall 子のサーフェスの絵と位置を、親の絵と同じ拡大率で追従させる

### Requirement 3: 無い番号と循環する参照

**Objective:** As a シェルの作者, I want 書き間違えた参照が、ログで分かる形で安全に読み飛ばされること, so that 1 行の間違いでゴーストが止まったり、原因の分からない欠けた絵になったりしない

#### Acceptance Criteria

1. If サーフェスを置く element定義が指す番号のサーフェスがシェルに無い場合, the areka shall 親のサーフェスの番号・element定義の番号・指した番号を警告としてログに残し、その element定義だけを描かずに、同じサーフェスの他の element定義は描く
2. If サーフェスを置く element定義をたどると、たどっている途中のサーフェスへ戻る（自分自身を指す場合を含む）場合, the areka shall 循環に関わるサーフェスの番号を警告としてログに残し、戻る参照だけを描かずに、それ以外の部分は描く
3. If 循環する参照がある場合, the areka shall 停止も異常終了もせずに、そのサーフェスの表示を続ける
4. The areka shall 循環していない参照（同じ子を別々の経路から 2 度置く場合など）を、循環として扱わずに描く
5. When 数字だけの欄が正しくサーフェスを指している場合, the areka shall その欄について画像の読み込みの失敗を記録しない

### Requirement 4: 子のサーフェスの当たり判定

**Objective:** As a ゴーストの作者, I want 子のサーフェスに書いた当たり判定の領域が、親の中でも置いた位置で効くこと, so that 部品のサーフェスに領域を 1 度書けば、どの表情でも同じ反応を返せる

#### Acceptance Criteria

1. When 親のサーフェスが表示されている場合, the areka shall 子のサーフェスの当たり判定の領域（collision）を、各段の X,Y を足し合わせた位置へずらして、親のサーフェスの領域として扱う（親に同じ名前の領域がある場合を除く。要件 4.8）
2. When ポインタが子から持ち込んだ領域の上にある場合, the areka shall 子のサーフェスに書かれた領域の名前を、親に直接書いた領域と同じ形で SHIORI へのイベントに載せる
3. While 複数の子から持ち込んだ領域が重なっている場合, the areka shall 親の element定義の番号が大きい子の領域を手前として扱う
4. While 1 つの子の中で領域が重なっている場合, the areka shall その子を単独で表示したときと同じ手前奥で扱う
5. While 親のサーフェスに直接書かれた領域と、子から持ち込んだ領域が重なっている場合, the areka shall 親に直接書かれた領域を手前として扱う
6. If 参照が要件 3 により描かれなかった場合, the areka shall そのサーフェスの領域を親へ持ち込まない
7. When pattern定義が指すサーフェスの中に子がある場合, the areka shall 当たり判定の扱いを、pattern定義が指すサーフェスについての今までの扱いから変えない
8. While 親のサーフェスに直接書かれた領域と同じ名前の領域が子にある場合, the areka shall 子のその名前の領域を親へ持ち込まず、親に直接書かれた領域だけを有効にする（重なっていない場所でも持ち込まない）
9. When 入れ子が 2 段以上ある場合, the areka shall 要件 4.8 の規則を段ごとに当てはめる（孫の領域は、子に同じ名前の領域があれば子へ持ち込まれず、子へ持ち込まれた領域は、親に同じ名前の領域があれば親へ持ち込まれない）
10. While 親に直接書かれていない同じ名前の領域を複数の子が持つ場合, the areka shall それらをすべて親へ持ち込み、手前奥を要件 4.3 に従って扱う

### Requirement 5: 子のサーフェスのアニメーションと独立した時計

**Objective:** As a シェルの作者, I want 子のサーフェスのアニメーションが親の中で動き、親を切り替えても途切れないこと, so that まばたきなどを部品のサーフェスに 1 度だけ書けば、表情を替えても自然に続く

#### Acceptance Criteria

1. While 子のサーフェスが element定義で置かれて表示されている間, the areka shall 子のサーフェスに書かれたアニメーションを、そのサーフェスを一番上に表示したときに動くものと同じ種類・同じ規則で、親の絵の中で動かす（着せ替えのアニメーションを含む。要件 5.12）
2. When 子のサーフェスがさらに内側の子を持つ場合, the areka shall 内側の子のアニメーションも、段数によらず同じ規則で動かす
3. The areka shall 子の時計を「スコープ × 子のサーフェス番号」ごとに 1 つ持つ
4. While 同じ子のサーフェスが、表示中の絵の中の複数の位置に置かれている間, the areka shall それらを同じ時計で揃えて動かす
5. When あるスコープで子のサーフェスが初めて表示された場合, the areka shall その子の時計を動かし始める
6. When 一番上のサーフェスが、同じ子を置いている別のサーフェスへ切り替わった場合, the areka shall その子のアニメーションを巻き戻さず、切り替えの前の続きから動かす
7. When 一番上のサーフェスが、その子を置いていないサーフェスへ切り替わり、後でその子を置いているサーフェスへ戻った場合, the areka shall その子の時計を、見えなかった間も止まらずに進んでいたものとして扱い、最初から動かし直さない
8. When シェルが切り替わる、またはゴーストが降りる場合, the areka shall そのスコープの子の時計をすべて捨てる
9. When 一番上のサーフェスが切り替わった場合, the areka shall 一番上のサーフェス自身に書かれたアニメーションを、今までどおり最初から動かす
10. While あるサーフェスが一番上のサーフェスとして表示されている間, the areka shall そのサーフェス自身のアニメーションを、同じ番号のサーフェスが子として持つ時計とは別のものとして扱う
11. While 子のサーフェスがどこにも表示されていない間, the areka shall その子の時計が進むことを理由に画面を描き直さない
12. While スコープで着せ替え（bind）が有効になっている間, the areka shall 子のサーフェスに書かれたその着せ替えのアニメーションを、そのサーフェスを一番上に表示したときと同じ規則で子の中に描き、有効な間だけ動くアニメーション（`bind+random` ほか）は子の時計で動かす
13. While pattern定義が指すサーフェスがコマとして表示されている間, the areka shall そのサーフェスに書かれたアニメーション（その中の子のものを含む）を、element定義で置いた子と同じ規則で動かす
14. The areka shall pattern定義が指すサーフェスの時計を、element定義で置いた同じ番号の子の時計と同じ 1 つのもの（スコープ × サーフェス番号）として扱い、コマが消えても捨てない

### Requirement 6: 子のサーフェスの中のシェル内バルーン

**Objective:** As a シェルの作者, I want 子のサーフェスに書いたシェル内バルーンが使われないことをログで知れること, so that 文字が出ない理由を自分で突き止められる

#### Acceptance Criteria

1. If 子として置かれたサーフェスに描画メソッド `balloon` の element定義がある場合, the areka shall 親のサーフェスの番号・子のサーフェスの番号・箱の名前を警告としてログに残し、その箱を親の中に置かない
2. While 子として置かれたサーフェスに描画メソッド `balloon` の element定義がある場合, the areka shall 子のサーフェスの残りの element定義（画像・サーフェス）を描く
3. When 描画メソッド `balloon` の element定義を持つサーフェスが一番上のサーフェスとして表示される場合, the areka shall その箱を、今までどおり置いて使えるようにする
4. The areka shall 親のサーフェスに直接書かれた箱の振る舞いを、子のサーフェスを置いているかどうかで変えない

### Requirement 7: 入れ子を使わないシェルを変えない

**Objective:** As a 既存のゴーストの利用者, I want 入れ子を使っていないシェルが今までと同じに見え、同じ軽さで動くこと, so that この機能が入っても手元のゴーストに影響が出ない

#### Acceptance Criteria

1. While シェルにサーフェスを置く element定義が 1 つも無く、pattern定義が指すサーフェスのどれもアニメーションを持たない場合, the areka shall すべてのサーフェスを本 spec の前と同じ絵・同じ外形・同じ当たり判定で表示する
2. While シェルにサーフェスを置く element定義が 1 つも無く、pattern定義が指すサーフェスのどれもアニメーションを持たない場合, the areka shall 絵を合成し直す回数を本 spec の前から増やさない
3. While シェルにサーフェスを置く element定義が 1 つも無く、pattern定義が指すサーフェスのどれもアニメーションを持たない場合, the areka shall アニメーションの動き出しと面の切り替えのときの扱いを本 spec の前から変えない
4. The areka shall 適合の検体（`emo2` を含む）の表示を、本 spec の前と同じ結果に保つ

### Requirement 8: 記録・登記・確かめの手段

**Objective:** As a areka の開発者, I want 入れ子の振る舞いが決定論的なテストと検体で固定され、独自の語として登記されていること, so that 後続の spec（`animated-image-playback` ほか）が安心して上に載せられる

#### Acceptance Criteria

1. The areka shall 無い番号・循環する参照・子の中の `balloon` の element定義のいずれについても、ログに何も残さずに読み飛ばす経路を持たない
2. The areka shall 入れ子を持つ試験用シェルをリポジトリ内の検体として持ち、その検体は少なくとも「2 つの親が同じ子を置く」「2 段以上の入れ子」「子がアニメーションを持つ」「子が当たり判定の領域を持つ」「pattern定義が指すサーフェスがアニメーションを持つ」を含む

## 要件ディスカッションで確かめる点

`brief.md` が「要件で確かめる」とした点と、起草で既定を置いた点。上の要件は次の既定で書いてある。

1. **子の時計の持ち方**（要件 5.3〜5.8・5.11）: discovery の推しのとおり「スコープ × 子のサーフェス番号に 1 つ・初めて表示されたときに動き出し、シェルが替わるかゴーストが降りるまで捨てない」。見えない間は進んでいたものとして扱う。**確定（2026-10-04 開発者裁定）**。見えない間の進め方（抽選を回し続けるか、戻ったときに経過時間から求めるか）は見え方が同じなので設計で決める。
2. **pattern定義が指すサーフェスの内側**（要件 2.7・4.7・5.13）: **確定（2026-10-04 開発者裁定）**。動かす。子サーフェスの挙動は独立で、pattern定義で指しても部品として動く。親のアニメーションは部品を出したり消したりするだけで、部品の時計には関わらない（正典に定めの無い所を areka が定めた）。時計は element定義で置いた同じ番号の子と共有する。当たり判定は今までどおり持ち込まない（要件 4.7）。
3. **着せ替え（bind）**（要件 5.12）: **確定（2026-10-04 開発者裁定）**。子の中でも効く。部品はどこに置かれても単独で表示したときと同じに振る舞い、着せ替えの有効・無効はスコープに 1 組で、子も同じものを見る。
4. **親に直接書いた領域と子から持ち込んだ領域の手前奥**（要件 4.5）: **確定（2026-10-04 開発者裁定）**。親に直接書いた領域が手前。さらに、子・孫からは「親が持たない名前の領域」だけを持ち込む（親子の両方に `head` があれば、親の `head` だけが有効）。要件 4.8〜4.10。
5. **数字の読み方**（要件 1.1）: 半角の数字だけを十進の整数として読む（`0100` は 100）。符号つき・全角の数字は画像のファイル名として読む。
