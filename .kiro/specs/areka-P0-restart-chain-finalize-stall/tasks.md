# Implementation Plan

> 順序は設計の Testing Strategy のとおり「新しいテストを書いて直す前の赤を見る → 本番の仕分けを直す → 全体の後退を確かめる → 実機で 1 回確かめる」。赤の確認（3.3）は本番を直す前にしか取れないので、1 と 2 は 3 より先に済ませる。

- [x] 1. 直す前の赤を立てる（新しい決定論テスト）
- [x] 1.1 (P) 起こし直しの側の新しいテスト 2 本を書き、直す前のコードで赤を見る
  - 窓を本番と同じ閉じ方で閉じた後、窓なしで初期配置の確定の処理を 600 巡回し、WARN が 0 件・見送りの数の記録が無い・確定の印が無いことを判定するテストを足す（T1）
  - 窓を閉じる → 窓なし 600 巡 → 新しい窓の一式を生やす → 相方が未表示のまま 600 巡（scope 0 は窓の寸どおりに表示済み・scope 1 だけ未表示＝既存テストと同じ偽の寸。scope 0 を食い違わせると走査が scope 0 で先に躓き、この区間が数えられてしまう）→ 全スコープ表示済みで areka 自身の理由（scope 0 の実表示寸だけを窓の寸と食い違わせた再アンカーが未 landing）の見送りを 599 巡 → さらに 1 巡、を 1 本で歩くテストを足す（T2）。判定は 599 巡目まで WARN 0 件・600 巡目でちょうど 1 件（本文に scope 0 と「再アンカーが未 landing」）・その後さらに 600 巡回しても増えない
  - 既存の偽の寸・偽の窓・記録の捕捉の道具だけで組み、テスト支援のファイルには手を入れない
  - 完了の状態: 直す前のコードで T1 は「600 巡目に WARN 1 件・数の記録が {600, 報告済み} で残る」、T2 は「窓なしの 600 巡目で WARN が出る」で赤になる
  - _Requirements: 1.1, 1.3, 1.4, 2.1, 2.2, 2.3, 3.1, 3.3, 3.5, 3.7_
  - _Boundary: 起こし直しの確定テスト（frame_chain_finalize_restart_tests）_

- [x] 1.2 (P) 確定の側の新しいテストを書き、既存 2 本を areka 自身の停滞の形へ置き換える
  - 相方のシェルが一度も表示されないまま確定の処理を 1200 巡回し、その捕捉に WARN・INFO・DEBUG が 0 件・TRACE がちょうど 1200 件・見送りの数の記録が無いことを判定し、続けて全スコープが表示された寸で 2 巡回して確定がちょうど 1 回行われ相方の位置が初回と同じ値になることを判定するテストを足す（T3）
  - 「相方が表示されない」形で停滞を作っている既存の 2 本（停滞を一度だけ報せる・有界の待ちの内なら無音）を、areka 自身の理由（scope 0 の実表示寸と窓の寸の食い違い＝再アンカーが未 landing）で停滞を作る形へ置き換え、WARN 本文の判定を scope 0 と「再アンカーが未 landing」へ変える（T4・T5）
  - 「1 巡だけ見送って揃えば確定する」既存テストは数えることを前提にしていないので変えない
  - 完了の状態: 直す前のコードで T3 は「600 巡目に WARN 1 件」で赤になり、置き換えた T4・T5 は直す前のコードでも緑（areka 自身の停滞は今日も数えられる＝対照）
  - _Requirements: 1.2, 1.3, 1.5, 1.6, 2.1, 2.2, 2.3, 3.2, 3.3, 3.4, 3.6, 3.7, 3.8_
  - _Boundary: 確定テスト（frame_chain_finalize_tests）_

- [ ] 2. 見送りの理由を「ゴースト待ち」と「areka 自身の待ち」に仕分ける

  - 完了の状態: 1.1・1.2 の T1〜T5 がすべて緑になり、既存の確定・起こし直し・遷移後の解き直しのテストも緑のまま通る
