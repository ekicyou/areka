# Requirements Document

## Project Description (Input)

**誰の問題か**: areka を ukadoc 互換ベースウェアとして使うゴースト作者・利用者（および M1 で適合対象としている実ゴースト emo2）。

**現状**: areka には選択肢を「選んだ後」の経路が存在しない。選択確定を SHIORI へ届ける実装は production Rust に 0 件で、kanade の入力種には選択系のアームが無い。上流側の材料は揃っており、選択の発生源（選択確定通知＝`ChoiceSelection{id, label, scope, references}` とその受け口）、トーク側の選択待ちバリア解除機構、`Status` ヘッダの実行状態語彙（`choosing`）はいずれも実在するが、それらを結ぶ駆動側が空である。結果として emo2 のメニュー（ダブルクリック→メニュー→項目選択→サブメニュー→もどる→閉じる）は一周しない。

**何が変わるべきか**: 選択の確定が SSP/ukadoc 準拠のカスケード（`OnChoiceSelectEx` → `OnChoiceSelect`、および `\q` の ID に書かれた `On` 始まりの任意名イベントの直接発火）で SHIORI へ届き、応答が既存のトーク開始経路へ合流し、同時にトーク側の選択待ちバリアが解除されて会話が継続する。選択待ち中は `Status` ヘッダに選択待ちであることが載り、選択肢のタイムアウト規律（トーク表示完了を起点としたカウント→`OnChoiceTimeout`→無応答なら選択解除）が確定する。1 回の選択は 1 回のカスケードのみを起こし、解除後の遅延クリックは棄却される。決定論テスト（mock SHIORI・注入選択確定通知・注入時刻）で全経路を網羅し、実 emo2・実 pasta.dll・実 DPI でメニューが一周することを人間がサインオフする。

## Introduction

本仕様は、バルーン上で確定した選択肢を SHIORI へ ukadoc 準拠のカスケードで届け、その応答を既存のトーク起動経路へ合流させ、同時にトーク側の選択待ちバリアを解除して会話を継続させる、対話ユニットの最終段である。選択待ち中の実行状態表示（`Status` の `choosing`）と、選択肢タイムアウトの規律（起点・既定値・無応答時の解除）も本仕様で確定する。到達目標は「メニューが一周する」ことであり、決定論観測（mock SHIORI・注入選択確定通知・注入時刻）と実機サインオフの双方で確認する。

本仕様は選択肢の**表示・hover・クリック解決**を持たない。それらは上流で確定済みであり、本仕様は上流が発行する**選択確定通知**（選択肢 ID・表示ラベル・発生元 scope・付随参照列を持つ・順序番号は非露出）を受領する消費側である。

## Boundary Context

- **In scope**:
  - 選択確定通知の受領・一回性の保証・遅延／stale 通知の棄却。
  - 選択肢 ID と付随参照列から発火イベント列を決定するカスケード判定（正典形／`On` 始まり任意名形の双方）。
  - 各イベントの Reference 割付（`OnChoiceSelectEx` / `OnChoiceSelect` / 任意名イベント / `OnChoiceTimeout`）。
  - SHIORI 応答の既存トーク起動経路への合流と、選択待ちトークが占有する単一 slot の調停。
  - トーク側の選択待ちバリア解除と、解除後の台本再開／トーク完了。
  - 選択待ち中の実行状態 `choosing` の導出と、選択待ち中の自発トーク抑止。
  - 選択肢タイムアウト（起点＝トーク表示完了、既定時間、`OnChoiceTimeout` 発行、無応答時の選択解除）。
  - 正典が沈黙する分岐の裁定記録（対応表）と、既存の適合スコープ文書の誤記訂正。
  - 決定論観測（全判断分岐）＋実機サインオフ（メニュー一周）。
- **Out of scope**:
  - 選択肢の表示・行ジオメトリ・hover 状態・実ポインタからのクリック解決（上流が所有し、本仕様は選択確定通知を消費するのみ）。
  - `\q` などのさくらスクリプトタグの解釈・cue へのコンパイル（上流が所有）。トーク台本中のタイムアウト指定タグ（タイムアウト無効化指定・タイムアウト時間指定）の**解釈**も本仕様の範囲外であり、M1 に実際に流れる経路は既定値のみである（値の入口は保持する＝要件 7.7）。
  - `script:` 前置 ID による選択肢からのスクリプト直接実行（M1 未対応カテゴリとして明示縮退・要件 2.7）。
  - アンカー選択（`\_a` 系）イベント、`OnChoiceEnter` / `OnChoiceHover`、選択肢のホイール操作、owner-draw メニュー。
- **Adjacent expectations**:
  - **上流（選択肢の対話層）**: 有効なクリックに対して選択確定通知を高々 1 回発行し、選択肢消滅後や stale 行のクリックでは発行しない。本仕様はその保証に**依存しつつ、自身の側でも重複・遅延を棄却する**（二重防御）。
  - **上流（トーク再生層）**: 選択待ちバリアは正規の型付き入力経由でのみ解決でき、トークの絶対終了時刻（duration 権威）が talk 完了の horizon を定める。本仕様は独自の時間基準やバリア状態を新設せず、これらを消費する。
  - **上流（共通ヘッダ層）**: 実行状態語彙・カンマ連結順序・状態が空のときのヘッダ行省略の規律は既に確定済みであり、本仕様は `choosing` を**アクティブとして導出する**のみで再定義しない。
  - **消費側ゴースト（emo2 / 実 pasta）**: 自発トーク抑止を `Status` 値の完全一致比較で行うため、非 `talking` 単独値や複合値では消費側の抑止が fail-open する。本仕様は抑止を areka 側の調停で成立させ、複合値 wire の消費側互換を実機観測で確認する。
  - **下流（適合 e2e）**: メニュー一周そのものの適合判定は下流の e2e が担う。本仕様は決定論観測＋単体の実機サインオフまでを負う。

## Requirements

### Requirement 1: 選択確定の受領と一回性

**Objective:** As a ゴースト利用者, I want 選択肢のクリックがちょうど 1 回だけ会話へ反映されること, so that メニュー操作が二重発火や取りこぼしなく先へ進む

#### Acceptance Criteria

1. When 選択確定通知（選択肢 ID・表示ラベル・発生元 scope・付随参照列）が発行された, the areka 選択確定配送経路 shall 当該通知を受領し、対応する SHIORI カスケード発火と選択待ちの解決をそれぞれ高々 1 回だけ実行する。
2. While 未処理の選択確定通知が滞留している, the areka 選択確定配送経路 shall 到着順に処理し、通知を暗黙に捨てず、後続の通知処理を停止させない。
3. If 選択待ちが既に終了している（解決済み・タイムアウト済み・トーク切替により選択肢が消滅済み）状態で選択確定通知を受領した, then the areka 選択確定配送経路 shall 当該通知を棄却し、SHIORI イベント発行と選択待ちの解決のいずれも行わず、棄却を警告として記録して処理を継続する。
4. If 選択確定通知の選択肢 ID が現在の選択待ちの候補集合に一致しない, then the areka 選択確定配送経路 shall 当該通知を棄却して選択待ち状態を変更せず、棄却理由を警告として記録し、処理を継続する。
5. The areka 選択確定配送経路 shall 選択確定通知の表示ラベルおよび付随参照列を、表示層へ再照会せず、受領した内容を改変しない不透明な文字列として扱う。
6. The areka 選択確定配送経路 shall 選択確定通知の処理過程で発生した棄却・失敗のいずれについても、無記録のまま処理を打ち切らない。

### Requirement 2: カスケード判定（発火イベント列の決定）

**Objective:** As a ゴースト作者, I want `\q` の書き方ごとに発火する SHIORI イベント列が正典どおり決まること, so that 既存の伺か資産の選択肢が書き換えなしで動作する

#### Acceptance Criteria

1. When 選択肢 ID が `On` で始まる, the カスケード判定 shall 当該 ID と同名の SHIORI イベントを発火候補列に含め、当該イベントの Reference0 起点に付随参照列を割り付ける対象とする。
2. When 選択肢 ID が `On` で始まらない, the カスケード判定 shall `OnChoiceSelectEx` を先行段、`OnChoiceSelect` を後続段とする発火候補列を決定する。
3. If 発火候補列のある段が応答スクリプトを返さなかった（204）, then the areka 選択確定配送経路 shall 次段のイベントを発行する。
4. If 発火候補列のある段が応答スクリプトを返した, then the areka 選択確定配送経路 shall 以降の段を発行しない。
5. The カスケード判定 shall 選択肢 ID と付随参照列のみから発火候補列を一意に決定し、同一入力に対して常に同一の列を導く。
6. The areka 選択確定配送経路 shall ゴースト作者が `\q` の ID に書いた任意のイベント名を、事前の固定登録を要さずに発行できる。
7. If 選択肢 ID が M1 で未対応のカテゴリ（`script:` 前置など、イベント発火以外の意味を持つ形式）に該当する, then the areka 選択確定配送経路 shall SHIORI イベントを発行せず、未対応である旨を警告として記録したうえで選択待ちの解決は実行し、会話を停止させない。
8. Where 正典（ukadoc）が挙動を明示していない、または正典の記述間に字面の揺れがある分岐が存在する, the areka 選択確定配送経路 shall 採用した挙動を対応表に記録し、記録どおりに動作する。対象は少なくとも次を含む — `On` 始まり ID における `OnChoiceSelectEx` / `OnChoiceSelect` の先行発火の有無、先行段が応答スクリプトを返した場合に後続段を発行しないこと、カスケード最終段が 204 を返した場合の扱い、選択解決後に選択肢集合を維持するか破棄するか。

### Requirement 3: Reference 割付（正典 layout）

**Objective:** As a ゴースト作者, I want 選択関連イベントの Reference が ukadoc の定義どおりに並ぶこと, so that 既存辞書が参照位置を書き換えずに動作する

#### Acceptance Criteria

1. When `OnChoiceSelectEx` を発行する, the areka 選択確定配送経路 shall Reference0 に表示ラベル、Reference1 に選択肢 ID、Reference2 以降に付随参照列を記述順で割り付ける。
2. When `OnChoiceSelect` を発行する, the areka 選択確定配送経路 shall Reference0 に選択肢 ID を割り付ける。
3. When `On` 始まり ID の任意名イベントを発行する, the areka 選択確定配送経路 shall Reference0 以降に付随参照列を記述順で割り付け、表示ラベルと選択肢 ID を Reference に含めない。
4. When `OnChoiceTimeout` を発行する, the areka 選択確定配送経路 shall Reference0 にタイムアウトした選択肢を含むトークのスクリプトを割り付ける。
5. If 付随参照列が空である, then the areka 選択確定配送経路 shall 付随参照列に対応する Reference 位置を付与せず、空文字で埋めない。
6. The areka 選択確定配送経路 shall 選択関連イベントの発行時にも、既存の共通リクエストヘッダ規律（実行状態ヘッダを含む）を欠落させない。
7. The areka 選択確定配送経路 shall 選択確定通知の発生元 scope を Reference に載せず、解決対象の選択待ちを特定する用途にのみ用いる。

### Requirement 4: SHIORI 応答の既存トーク起動経路への合流

**Objective:** As a ゴースト利用者, I want 選択の応答が既存のトーク再生と同じ経路で再生されること, so that 選択後に次のシーンが確実に表示される

#### Acceptance Criteria

1. When 選択由来のイベントが応答スクリプトを返した, the kanade engine shall 一意なトーク識別子を付与したトーク起動要求を既存のトーク起動経路で送出する。
2. When 選択由来のイベントが 204 を返した, the kanade engine shall トークを起動せず、既存の周期イベント送出を停止させない。
3. While 選択待ちのトークがトーク slot を占有している, when 選択由来の応答スクリプトを受領した, the kanade engine shall 当該応答を破棄せず、既存の単一 slot 調停規律に従って新しいトークへ差し替える。
4. The kanade engine shall 選択確定を既存入力種への additive な追加として受け取り、新しい調停規則を導入せず、既存の決定的状態機械の観測資産を変更しない。
5. If 選択由来のイベント発行が失敗した（送信不能・内部エラー）, then the areka 選択確定配送経路 shall 失敗をエラーとして記録し、無応答（204）と同じ扱いで処理を継続する。
6. The areka 選択確定配送経路 shall 1 回の選択確定に対して高々 1 つのトーク起動要求しか生じさせない。

### Requirement 5: 選択待ちバリアの解除とトーク継続

**Objective:** As a ゴースト利用者, I want 選択した瞬間に会話が止まらず続きが再生されること, so that メニュー操作が行き止まりにならない

#### Acceptance Criteria

1. When 有効な選択確定を処理した, the areka 選択確定配送経路 shall トーク側の選択待ちを当該選択肢 ID で解決し、後続の台本を再開させる。
2. When 選択待ちの解決後に後続の台本が残っていない, the areka 選択確定配送経路 shall 当該トークを完了として扱い、トーク完了の通知が行われる状態にする。
3. If SHIORI が 204 を返した、または SHIORI 呼び出しが失敗した, then the areka 選択確定配送経路 shall 選択待ちの解決を取りやめず、会話が選択待ちのまま停止しないようにする。
4. The areka 選択確定配送経路 shall 1 回の選択確定に対して選択待ちの解決を高々 1 回だけ実行する。
5. If 解決対象の選択待ちが存在しない（既に解決済み・待機中でない）, then the areka 選択確定配送経路 shall トーク状態を変更せず、その旨を警告として記録して処理を継続する。
6. The areka 選択確定配送経路 shall 選択待ちの解決をトーク再生層の正規の入力経路経由で行い、独自のバリア状態や再生状態を保持しない。

### Requirement 6: 選択待ちの実行状態表示と自発トーク抑止

**Objective:** As a ゴースト作者, I want 選択待ち中であることが SHIORI リクエストから判別でき、その間に自発トークが割り込まないこと, so that メニュー表示中に会話が上書きされない

#### Acceptance Criteria

1. While 選択待ちが継続している, the kanade engine shall 実行状態 `choosing` をアクティブとして導出する。
2. When 選択待ちが解決またはタイムアウトにより終了した, the kanade engine shall `choosing` を非アクティブへ戻す。
3. The kanade engine shall アクティブな実行状態の連結順序・区切り・状態が空のときのヘッダ行省略について、既存の共通ヘッダ規律に従い、`choosing` 単独値・複合値のいずれについても新たな書式を定義しない。
4. While 選択待ちが継続している, the kanade engine shall 当該トークを再生中（slot 占有継続）として扱い、周期イベントを通知として送出し、再生可否を表す Reference に「再生中」を表す値を設定し、当該通知への応答スクリプトを再生しない。
5. The kanade engine shall 選択待ち中の自発トーク抑止を、消費側ゴーストによる `Status` 値の比較結果に依存せず、areka 側の調停のみで成立させる。

### Requirement 7: 選択肢タイムアウト

**Objective:** As a ゴースト作者, I want 選択されないままの選択肢が正典どおりタイムアウトすること, so that 放置された会話が永久に選択待ちで固まらない

#### Acceptance Criteria

1. While 選択待ちが継続している, when 当該トークの表示が全て終わった, the areka 選択確定配送経路 shall タイムアウト時間の計測を開始する。
2. The areka 選択確定配送経路 shall タイムアウトの起点をトークの絶対終了時刻（duration 権威）から取得し、独自の時間基準を導入しない。
3. When 計測がタイムアウト時間に達した, the areka 選択確定配送経路 shall `OnChoiceTimeout` を発行する。
4. When `OnChoiceTimeout` が応答スクリプトを返した, the kanade engine shall 既存のトーク起動経路で当該スクリプトを再生する。
5. If `OnChoiceTimeout` が 204 を返した, then the areka 選択確定配送経路 shall 選択待ちを解除して当該トークを終了させ、以降に到着する当該選択待ち宛の選択確定通知を棄却する。
6. Where タイムアウト時間として無効化を表す値（0 または -1）が与えられる, the areka 選択確定配送経路 shall 計測を開始せず、選択待ちを無期限に継続する。
7. The areka 選択確定配送経路 shall タイムアウト時間を単一の入口値として扱い、既定値以外の値が与えられた場合も同一の規律で動作する（トーク台本からの時間指定の解釈は本仕様の範囲外であり、M1 に実際に流れるのは既定値のみである）。
8. The areka 選択確定配送経路 shall タイムアウト時間の既定値を単一の値として定め、正典が数値を規定していない旨とともに対応表へ記録する。

### Requirement 8: 互換記録と正典整合

**Objective:** As a areka 開発者, I want 正典由来の挙動と areka 裁量の挙動が区別可能に記録されること, so that 後続の適合作業が根拠を再調査せずに進められる

#### Acceptance Criteria

1. The areka 互換記録 shall 本仕様が採用した選択関連イベントの Reference 割付・カスケード順序・既定タイムアウト値を、正典（ukadoc）の該当記述と対応付けて記録する。
2. The areka 互換記録 shall 正典に根拠がある挙動と、正典が沈黙したため areka 裁量で決めた挙動とを区別可能な形で記録する。
3. When 既存の適合スコープ文書の記述が正典と矛盾している（選択確定イベントの Reference 割付が正典と逆に書かれている）, the areka 互換記録 shall 当該記述を正典に一致するよう訂正した状態で保持する。

### Requirement 9: 決定論観測と実機サインオフ

**Objective:** As a areka 開発者, I want 全ての判断分岐が実時間待ちなしに再現検証でき、かつ実機で一周が確認されること, so that 回帰を自動で検出しつつ、檻が隠す欠陥も捕捉できる

#### Acceptance Criteria

1. The areka 選択確定配送経路 shall 全ての判断分岐を、mock SHIORI・注入した選択確定通知・注入した時刻のみで実行検証可能とし、実時間の待機に依存しない。
2. When 決定論検証を実行する, the areka 選択確定配送経路 shall 次の全てを単一の pass/fail として観測可能にする — (a) `On` 始まり ID の選択で任意名イベントが発行され応答からトークが起動し選択待ちが解決されること、(b) 正典形の選択で `OnChoiceSelectEx`（Reference0=ラベル / Reference1=ID / Reference2 以降=付随参照列）が先行し、204 時に記録どおりの順序で次段が発行されること、(c) 選択待ち中の周期イベントに `choosing` が載り、解決後に消えること、(d) タイムアウトで `OnChoiceTimeout`（Reference0=スクリプト）が発行され、204 で選択が解除されること、(e) 1 回の選択が高々 1 回のカスケードと高々 1 回の選択待ち解決しか起こさず、解除後の遅延した選択確定通知が棄却されること。
3. When 実機サインオフを実施する, the areka 選択確定配送経路 shall 実 emo2・実 pasta・実 DPI の環境でメニューが一周すること（ダブルクリック→メニュー→項目選択→サブメニュー→もどる→閉じる）を人間が確認できる状態にする。
4. Where 複合の実行状態値が送出される, the areka 選択確定配送経路 shall 選択待ち中に消費側ゴーストの自発トークが漏れないことの実機観測を、受け入れ条件に含める。
