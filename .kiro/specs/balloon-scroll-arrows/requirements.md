# Requirements Document

## Project Description (Input)

- **だれが困っているか**: ゴーストの作者（ぱすた）と、そのゴーストの利用者。ぱすたの縦書きのバルーン `pasta_tategaki` は、スクロールの矢印の絵 `arrow0.png`・`arrow1.png` と、その位置 `arrow0.x,-12`・`arrow0.y,4`・`arrow1.x,-12`・`arrow1.y,-12` を持つ。
- **今の状況**: areka はこれらの鍵を読まない。長い台詞で文字が押し出されても矢印を出さず、矢印のクリックやホイールで読み返すこともできない（送りは自動だけで、いつも最新の行が見える位置に送られる）。SSP は矢印を出し、戻して読める。シェル内バルーン（箱）も同じで、矢印も読み返しも無い。areka が既定で入れるバルーン `areka-balloon` も `arrow0.png`・`arrow1.png` と `arrow0.x,303`・`arrow0.y,10`・`arrow1.x,303`・`arrow1.y,-20` を持つが、使われていない。
- **何を変えるか**: 押し出された文字が残っているとき、バルーンの descript が定める位置に `arrow0`・`arrow1` の矢印を出し、矢印のクリックとホイールで手動に戻して読めるようにする。横書きと縦書き、普通のバルーンとシェル内バルーンの箱の両方で同じ規則で出す。矢印の絵の名前の選び方（本体・相方・三人目以降と旧名）は、後に続く印（クリック待ち・状態の印）も同じ仕組みで解ける土台として作る。ぱすたの縦書きのバルーンで、SSP と同じ所に同じ矢印が出ることを実機で確かめる。

出どころは `brief.md`（2026-10-23 起票・2026-10-24 棚卸㉚の再測定を含む。後の節が前の節を上書きする）。区分は **A（開発者の指示）**、版は v0.1.0（ゴール「ゴースト『窓際のぱすたさん』が SSP と同じに動く」）。`balloon-markers` が持っていた「矢印と手動スクロール＋装飾の系列の土台」を切り出した spec である。

## Introduction

正典（ukadoc）が書いていること:

- descript.txt（バルーン）の `arrow0.x`・`arrow0.y`（スクロールマーカ上矢印の座標）・`arrow1.x`・`arrow1.y`（下矢印の座標）。既定値は「不明」。座標は脚注 *1 のとおり、マイナスの値はバルーンの画像の右下からの相対で、どうしてもマイナスの座標にしたいときは `--数値` と書く。
- `arrow.filename`（SSP 2.5.51〜）: 「スクロール用の矢印の画像ファイル名を指定する。拡張子は不要。」既定は `arrow`、個別の既定は `arrows`・`arrowk`・`arrowp*def`。
- バルーンのフォルダの構成: `arrow*.png` は「0が上向き、1が下向き」。`arrows*`（本体用・旧版のために `arrow` で代用を推奨）・`arrowk*`（相方用）・`arrowp*def*`（`\p[2]` 以降用）。
- `vertical,0/1`: 縦書きでも座標はバルーンの画像の左上を原点として書く。「arrow0（スクロール上）・arrow1（スクロール下）は、意味としてはそれぞれ右・左へのスクロールになる。画像と位置はバルーン側で用意すること。」

正典が書いていないこと（ukadoc で読めない点）: 矢印がどんな条件で出るか・1 回のクリックやホイールの 1 目盛りでどれだけ送るか・座標が書かれていないときの置き場・手動で戻している最中に新しい文字が来たときの扱い。これらは SSP の MCP で測ってから決める（要件 10）。brief の「縦書きの矢印の向きは ukadoc に明文が無い」は古い。今の ukadoc の `vertical` の項は向き（arrow0＝右・arrow1＝左）を書いている（完了 `balloon-vertical-canon` の SC10 の時点では間接に推すだけだった）。向きはこの明文で決め、測るのは出る条件と送る量に絞る。

この spec の言葉:

- **押し出された行**: 自動の送りで見える範囲の外へ出た行（縦書きでは列）。横書きでは上、縦書きでは右にある。
- **古い側・新しい側**: 押し出された行のある側を古い側、最新の行の側を新しい側と呼ぶ。横書きでは上が古い側、縦書きでは右が古い側。
- **手動の位置**: 利用者が矢印やホイールで戻した、見える範囲の位置。自動の送りが決める位置（最新の行が見える位置）と違うときだけある。

## Boundary Context

- **In scope**:
  - バルーンの descript（面ごとの設定ファイルを含む）とシェルの `balloon.*`ブレスから `arrow0.x`・`arrow0.y`・`arrow1.x`・`arrow1.y`・`arrow.filename` を読むこと。
  - 矢印の絵の名前の選び方（本体・相方・三人目以降と旧名 `arrow`）と、同じ仕組みをクリック待ちの印（`clickwait*`）にも使える土台にすること（クリック待ちの印を出すことはしない）。
  - 横書きと縦書き、普通のバルーンとシェル内バルーン（箱）で、押し出された行があるときに矢印を出すこと。
  - 矢印のクリックとホイールで手動に戻して読むこと（普通のバルーンの窓のホイールの受け口を新しく作る）。
  - 手動の位置と、新しい文字・消去・時間切れ・面の切り替え・拡大率・選択肢の当たりとの関係。
  - `\b[ID]` で面が替わったとき、その面の設定ファイルを重ねてバルーンの定義を作り直すこと（すべての鍵・議題 8）。
  - SSP での測り・記録（ログ）・`doc/COMPAT_ARCHITECTURE.md` §8 の行・網羅台帳 `doc/ukadoc-coverage/ledger/assets.toml` の 5 行（`arrow.filename` の持ち主を本 spec へ移す）と `doc/ukadoc-coverage/roadmap-draft.md` の数の行・決定論のテスト・ぱすたの実機の確かめ。
- **Out of scope**:
  - オンラインの印（`onlinemarker.*`）・数字（`number.*` と `\![set,balloonnum]`）・SSTP の印（`sstpmarker`・`sstpmessage`）・`\![*]` の印（`marker*`）。`balloon-markers` に残す。
  - クリック待ちの印（`clickwaitmarker`）を出すこと。`talk-fast-forward` が持つ（本 spec は名前の選び方の土台だけを作る）。
  - 押し出される行のフェード（`balloon-scroll-fade`）。
  - `balloon-canon-residue` の項目 2〜6。
  - 自動の送りの規則そのもの（いつ・どれだけ自動で送るか）。正典どおりのまま変えない。
  - 自動の送りを止める台本 `\![set,autoscroll,disable]`・`\![set,autoscroll,enable]`。正典は「手動でのスクロールは可能」と書き、本 spec の手動の送りと関わるが、網羅台帳の持ち主は空のまま（本 spec では引き取らない）。
  - 矢印の絵の名前で `.png` 以外（`.webp` など）を受けること。名前から絵を探す所をそろえる `balloon-webp-names` が持つ（ぱすたの矢印は `.png`）。
  - 横のホイール。
  - バルーンの窓の上のホイールを `OnMouseWheel` として SHIORI へ送ること（今も送っていない。変えない）。
  - バルーンの面の選び方・寿命（`balloon-canon-residue`・完了 `balloon-lifecycle-events`）。
- **Adjacent expectations**:
  - 自動の送り（最新の行が見える位置へ行単位で送る今の決まり）は保つ。本 spec は利用者が戻した間だけ、それと違う位置を見せる。
  - 選択肢とリンクの当たりは、今も「面に反映した送りの量」を通して見えている位置に合わせている。手動の位置もこの量を通して届ける（選択肢の当たりの決まり自体は変えない）。
  - バルーンの時間切れの数え方（台詞が終わってから数え、ドラッグ中とポインタがバルーンや箱の上にある間は数えない）は変えない。
  - キャラクターの窓のホイール（完了 `mouse-click-wheel-events`・`OnMouseWheel` の間引きと足し合わせ）は、議題 6 の箱の上の場合を除いて変えない。
  - 下流の `balloon-markers`（状態の印）・`talk-fast-forward`（クリック待ちの印）・`balloon-scroll-fade`（フェード・手動の送りとの整合）は、本 spec の名前の選び方の土台・印の置き方・手動の位置に乗る。
  - ぱすたの縦書きのバルーンは、ぱすたの書庫の直しが出るまでは手順書 `doc/pasta-real-run.md` の入れ方で入れる（働きの前提ではない）。

## Requirements

### Requirement 1: 矢印の鍵を読む

**Objective:** As a バルーンとシェルの作者, I want descript に書いた矢印の位置と名前を areka が読むこと, so that SSP 向けに作ったバルーンの矢印が areka でも同じ所に出る

#### Acceptance Criteria

1. When バルーンの descript.txt に `arrow0.x`・`arrow0.y`・`arrow1.x`・`arrow1.y` が書かれている, the areka shall それぞれを上（縦書きでは右）の矢印と下（縦書きでは左）の矢印の左上の位置として読む。
2. The areka shall 矢印の座標を、バルーンの画像の左上を原点として読み、0 以上の値は左上からの位置、マイナスの値は画像の右端・下端からの相対、`--数値` はマイナスの座標そのものとして扱う（正典の脚注 *1。マイナスを端からとする所は文字を描いてよい範囲などの座標と同じ。`--数値` は今どの座標の鍵も読めておらず、本 spec は矢印の鍵で読む。他の鍵へ広げることは範囲の外）。
3. When バルーンの面ごとの設定ファイル（`balloons*s.txt`・`balloonk*s.txt`・`balloonp*def*s.txt`）に矢印の鍵が書かれている, the areka shall その面を出す間は descript.txt の値をその値で上書きする（他の鍵と同じ上書きの決まり）。
4. When バルーンの descript.txt か面ごとの設定ファイルに `arrow.filename` が書かれている, the areka shall その値を矢印の絵の名前の元（拡張子を除いた名前）として読む（使い方は要件 2）。
5. If 矢印の座標の値が数として読めない, then the areka shall その鍵を書かれていないものとして扱い、鍵の名前と値を警告として記録に残す。
6. The areka shall 矢印の鍵を読むようになっても、矢印の鍵を持たないバルーンの既存の振る舞い（バルーンの絵・文字の置き場・折り返し）を変えない。ただし要件 1.7 により、面 0 以外の面ごとの設定ファイルを持つバルーンは、その面を出す間はその設定ファイルの値に変わる（正典どおりの姿への直し）。
7. When `\b[ID]` などでバルーンの面が替わった, the areka shall 替わった先の面の設定ファイルを descript.txt に重ねてそのスコープのバルーンの定義を作り直し、矢印の鍵に限らずすべての鍵（文字を描いてよい範囲・書体など）にその面の値を使う（議題 8。今は面 0 の設定ファイルだけを重ねている）。

### Requirement 2: 矢印の絵の名前の選び方（装飾の系列の土台）

**Objective:** As a バルーンの作者, I want 本体・相方・三人目以降で別々の矢印の絵を用意でき、用意しなければ共通の絵が使われること, so that 正典どおりの名前で作ったバルーンがそのまま動く

#### Acceptance Criteria

1. While `arrow.filename` が書かれていない, the areka shall 矢印の絵を、`0`（上・縦書きでは右）と `1`（下・縦書きでは左）のそれぞれについて別々に、スコープごとに次の順で探し、最初に見つかった名前の絵を使う（番号ごと。バルーンの絵の選び方と同じ規則。議題 7）: 本体＝`arrowp0def`→`arrows`→`arrow`、相方＝`arrowp1def`→`arrowk`→`arrowp0def`→`arrows`→`arrow`、三人目以降（`\p[n]`）＝`arrowp{n}def`→`arrowk`→`arrowp0def`→`arrows`→`arrow`（バルーンの絵の名前の探し方と同じ順に、旧名 `arrow` を最後に足したもの）。
2. Where `arrow.filename` が書かれている, the areka shall その名前の `0` と `1` を、本体・相方・三人目以降のどのスコープにも使う。
3. If `arrow.filename` に書かれた名前の絵がバルーンのフォルダに無い, then the areka shall 要件 2.1 の順で探し直し、書かれた名前の絵が無かったことを警告として記録に残す。
4. If 探した結果、矢印の絵が 1 枚も見つからない, then the areka shall そのスコープでは矢印を出さず、手動の送り（要件 5・6）だけを受け付ける。
5. If 要件 2.1 の順をすべて辿っても上の矢印と下の矢印のどちらか一方の絵だけが見つかった, then the areka shall 見つかった方だけを出し、もう一方の絵が無いことを記録に残す。
6. The areka shall 絵の名前を大文字と小文字を区別せずに照らし、拡張子 `.png` の絵を使う（今のバルーンの絵と同じ）。
7. The areka shall 矢印の名前の選び方を、クリック待ちの印（既定 `clickwait`・個別 `clickwaits`・`clickwaitk`・`clickwaitp*def`・名前の鍵 `clickwaitmarker.filename`）にも同じ規則で使える形で用意し、クリック待ちの名前の選び方が要件 2.1〜2.3 と同じ順で解けることを決定論のテストで示す（クリック待ちの印を出すことは本 spec ではしない）。

### Requirement 3: 矢印を出す条件と置き場

**Objective:** As a ゴーストの利用者, I want 押し出された文字があるときにそのことが矢印で分かること, so that 読み逃した台詞があると気付いて戻して読める

#### Acceptance Criteria

1. While バルーンの古い側に押し出された行がある, the areka shall 上（縦書きでは右）の矢印 `arrow0` を出す。
2. While 手動の位置にいて、新しい側に見えていない行がある, the areka shall 下（縦書きでは左）の矢印 `arrow1` を出す。
3. While 押し出された行も見えていない新しい行も無い, the areka shall どちらの矢印も出さない。
4. The areka shall 矢印を、バルーンの画像の左上に要件 1 の座標を足した位置に、矢印の絵の大きさのまま（拡大率はバルーンの絵と同じ率で）出す。
5. The areka shall 矢印をバルーンの絵より手前に出し、矢印が文字を描いてよい範囲の外にあっても、バルーンの絵の中にある分は切らずに出す。
6. The areka shall 普通のバルーンに出した矢印を、MCP の `dump_balloon` が返す絵に、画面に出ているのと同じ位置で写す。
7. If 矢印の座標が書かれていないのに矢印の絵が見つかった, then the areka shall SSP で測った置き場（要件 10）に矢印を出し、その置き場を `doc/COMPAT_ARCHITECTURE.md` §8 に記録する。
8. When 押し出された行の有無が変わった（自動の送り・手動の送り・消去で）, the areka shall 次に画面を描き直すときに矢印の表示を合わせる（古い表示を残さない）。

### Requirement 4: 縦書きの矢印

**Objective:** As a 縦書きのバルーンの作者（ぱすた）, I want 縦書きのバルーンでも矢印が正典どおりの向きで働くこと, so that 縦書きのバルーンでも読み返せる

#### Acceptance Criteria

1. While バルーンが縦書き（`vertical,1`）である, the areka shall `arrow0` を右（押し出された古い列の側）への送り、`arrow1` を左（新しい列の側）への送りとして扱う（ukadoc の `vertical` の項の明文）。
2. While バルーンが縦書きである, the areka shall 矢印の座標を横書きと同じく、バルーンの画像の左上を原点（マイナスは右端・下端から）として読む（座標の意味を縦書きで入れ替えない）。
3. When ぱすたの縦書きのバルーン `pasta_tategaki`（`arrow0.x,-12`・`arrow0.y,4`・`arrow1.x,-12`・`arrow1.y,-12`）で押し出された列がある, the areka shall SSP が同じ台詞で矢印を出す所と同じ所に同じ矢印を出す（実機と SSP の測りで確かめる・要件 10・11）。
4. If SSP の測りで、縦書きの矢印の出る条件が要件 3.1〜3.3 と違った, then the areka shall SSP に合わせ、その違いを要件の改訂として残す。

### Requirement 5: 矢印のクリックで手動に送る

**Objective:** As a ゴーストの利用者, I want 矢印をクリックして押し出された文字を読み返せること, so that 長い台詞を読み逃さない

#### Acceptance Criteria

1. When 出ている `arrow0` の上で左ボタンが押された, the areka shall 見える範囲を古い側へ 1 行（縦書きでは 1 列）送る（送る量は SSP の測りで確かめる・要件 10）。
2. When 出ている `arrow1` の上で左ボタンが押された, the areka shall 見える範囲を新しい側へ 1 行（縦書きでは 1 列）送る。
3. The areka shall 手動の送りを、一番古い行が文字を描いてよい範囲の始まりに来る位置より古い側へ、また自動の送りが決める位置より新しい側へ進めない。
4. When 手動の送りが自動の送りの決める位置に戻った, the areka shall 手動の位置を捨てて、自動の送りの状態に戻る。
5. When 出ている矢印の上で左ボタンが押された, the areka shall その押下を矢印の操作だけに使い、バルーンのクリックとしての働き（話している最中の早送り・中断、話し終えた後のバルーンを閉じる働き、選択肢やリンクの確定）を起こさない。
6. If 矢印が出ていない所（矢印の絵が無い・押し出された行が無い）で左ボタンが押された, then the areka shall 本 spec の前と同じバルーンのクリックとして扱う。
7. The areka shall 矢印の当たりを、画面に出ている矢印の位置と大きさに合わせる（拡大率が変わっても合う）。

### Requirement 6: ホイールで手動に送る

**Objective:** As a ゴーストの利用者, I want バルーンの上でホイールを回して読み返せること, so that 矢印を狙ってクリックしなくても戻して読める

#### Acceptance Criteria

1. When カーソルが普通のバルーンの窓の上にある間に縦のホイールが上（向こう側）へ回された, the areka shall 見える範囲を古い側へ送る（`arrow0` と同じ向き）。
2. When カーソルが普通のバルーンの窓の上にある間に縦のホイールが下（手前）へ回された, the areka shall 見える範囲を新しい側へ送る（`arrow1` と同じ向き）。
3. The areka shall ホイールの 1 目盛り（OS の単位で 120）ごとに 1 行（縦書きでは 1 列）送り、目盛りに満たない回転は足し合わせて次の回転に持ち越す（送る量は SSP の測りで確かめる・要件 10）。
4. The areka shall ホイールの送りにも要件 5.3・5.4 の限りと戻り方を当てる。
5. While 押し出された行も見えていない新しい行も無い, the areka shall バルーンの上のホイールで何も送らない。
6. The areka shall 矢印の絵が無いバルーン（要件 2.4）でも、ホイールで手動に送れるようにする。
7. The areka shall 普通のバルーンの窓の上のホイールを `OnMouseWheel` として SHIORI へ送らない（今と同じ）。横のホイールでは送らない。

### Requirement 7: シェル内バルーン（箱）の矢印

**Objective:** As a シェルの作者, I want シェル内バルーンの箱でも普通のバルーンと同じ規則で矢印が出て読み返せること, so that 箱に長い台詞を出しても読み逃しが無い

#### Acceptance Criteria

1. When シェルの `balloon.*`ブレスに `arrow0.x`・`arrow0.y`・`arrow1.x`・`arrow1.y`・`arrow.filename` が書かれている, the areka shall 要件 1 と同じ読み方で読み、原点を箱の左上、マイナスの値を箱の右端・下端からの相対とする。
2. The areka shall 箱にも要件 3 の出る条件と、要件 4 の縦書きの向きを当てる。
3. The areka shall 箱の矢印の絵を、要件 2 の名前の選び方で、シェルのフォルダを先に、無ければそのスコープが今使っているバルーンのフォルダを探して引く（議題 1）。
4. When 箱に出ている矢印の上で左ボタンが押された, the areka shall 要件 5 と同じく箱の見える範囲を送り、その押下を箱の選択肢の確定・中断・`OnMouseClick` などのクリックとして扱わない。
5. While 箱に押し出された行か見えていない新しい行がある, when カーソルがその箱の上にある間に縦のホイールが回された, the areka shall 要件 6 と同じく箱の見える範囲を送り、その回転を `OnMouseWheel` として SHIORI へ送らない（議題 6）。
6. While 箱に押し出された行も見えていない新しい行も無い, the areka shall 箱の上のホイールを本 spec の前と同じく `OnMouseWheel` として扱う。
7. If 箱の矢印の座標が書かれていないのに矢印の絵が見つかった, then the areka shall 要件 3.7 と同じ置き場の決まりを箱の大きさに当てる。

### Requirement 8: 手動の位置の保ち方と戻し方

**Objective:** As a ゴーストの利用者, I want 戻して読んでいる間とその後の見え方が予想どおりであること, so that 新しい台詞を見落とさず、読み返しの途中で表示が乱れない

#### Acceptance Criteria

1. When 手動の位置にいる間に、そのバルーン（箱）で新しい文字が見えるようになった（台本が届いた時でなく、見える字が増えた時）, the areka shall 手動の位置を捨てて、自動の送りが決める位置（最新の行が見える位置）へ戻る（議題 2）。
2. When バルーン（箱）の文字が消去された（`\c` などの消去・新しいトークの始まり）, the areka shall 手動の位置を捨てる。
3. When バルーン（箱）が消えた（時間切れ・トークの終わりでの片付け・ゴーストの切り替え）, the areka shall 手動の位置を捨て、次に出すときは自動の送りの位置から始める。
4. The areka shall 手動の送りのために、バルーンの時間切れの数え方を変えない（ポインタがバルーンや箱の上にある間は今も数えない）。
5. While 手動の位置にいる, the areka shall 選択肢とリンクの当たりを、画面に見えている位置に合わせる（戻した分だけずらす）。
6. When 手動の位置にいる間にバルーンの面が替わった（`\b[ID]` などで）, the areka shall 手動の位置を捨てて自動の送りの位置へ戻り、新しい面の矢印の鍵と絵で出し直す。
7. When 手動の位置にいる間に拡大率が変わった, the areka shall 一番古い側に見えていた行を同じく一番古い側に見せ続ける。
8. The areka shall 手動の位置をスコープ（バルーン・箱）ごとに別々に持ち、あるバルーンの送りで別のバルーンや箱の見える範囲を動かさない。

### Requirement 9: 記録と登記

**Objective:** As a areka の開発者, I want 矢印の解決と手動の送りの判断が記録と文書に残ること, so that 矢印が出ないときに原因（絵が無い・鍵が無い・条件を満たさない）を記録から見分けられる

#### Acceptance Criteria

1. When バルーン（箱）の矢印の絵を解決した, the areka shall スコープ・使った名前・見つかった絵（無ければそのこと）を debug の水準で 1 回記録に残す。
2. When 手動の送りを始めた・やめた（要件 5.4・8.1〜8.3・8.6）, the areka shall スコープとその理由を debug の水準で記録に残す。
3. The areka shall 矢印のクリックとホイールの 1 回ごとの送りを、既定の記録の水準（info 以上）で 1 行ずつ残さない。
4. If 矢印の絵が読めなかった（壊れた絵など）, then the areka shall ファイルの場所と理由を警告として記録に残し、その矢印を出さずに続ける（バルーン自体は出す）。
5. The 本 spec shall 正典が黙る所で areka が決めた点（矢印の出る条件・送る量・矢印のクリックをバルーンのクリックとして扱わないこと・座標が無いときの置き場・手動の位置と新しい文字の関係・箱の絵のフォルダ・箱の上のホイール・`arrow.filename` の名前の絵が無いときの戻り方）を `doc/COMPAT_ARCHITECTURE.md` §8 に登記し、SSP で測った点は測った版と答えを添える。§8 の既存の 2 行（「装飾族の接尾辞なしの旧名」・「`arrow0`／`arrow1` の縦書き再解釈」の「正典は未規定」）も、今の ukadoc の `vertical` の項の明文と実装の後の姿に直す。
6. The 本 spec shall 網羅台帳 `doc/ukadoc-coverage/ledger/assets.toml` の `arrow.filename`・`arrow0.x`・`arrow0.y`・`arrow1.x`・`arrow1.y` の 5 行の持ち主を本 spec にそろえ、状態と注記を実装の後の姿に直し、`doc/ukadoc-coverage/roadmap-draft.md` の数の行を合わせ、台帳の検査を緑にする。

### Requirement 10: SSP での測り

**Objective:** As a areka の開発者, I want ukadoc で読めない振る舞いを SSP で測ってから決めること, so that ぱすたのバルーンが SSP と同じに動く

#### Acceptance Criteria

1. The 本 spec shall 次の点を、開発者の許しを得て SSP の MCP と画面の操作で測る: ⑴ 横書きと縦書きで矢印がそれぞれどんな条件で出るか（`arrow1` は戻しているときだけか）、⑵ 矢印の 1 回のクリックとホイールの 1 目盛りで送る量、⑶ 手動で戻している最中に新しい文字が出たときの見える範囲、⑷ 矢印の座標が書かれていないときの置き場、⑸ ぱすたの縦書きのバルーンで矢印が出る位置（areka と見比べる絵）、⑹ 話している最中と話し終えた後に矢印をクリックしたとき、早送り・バルーンを閉じる働きが起きるか。
2. The 本 spec shall 測りのやり方（SSP の版・使ったバルーンと台本・操作）と答えを `research.md` に残す。
3. If 測りの答えが本文の推奨（要件 3・5・6・7・8）と違った, then the 本 spec shall 要件を SSP に合わせて改訂するか、areka の決めとして残すかを開発者に諮り、決めた結果を要件と §8 に残す。
4. The 本 spec shall 測りの間は画面の操作を排他テストの机で順を取り、測り終えたらすぐ手放す。

### Requirement 11: 受け入れの確認

**Objective:** As a areka の開発者, I want 矢印と手動の送りの振る舞いを決定論のテストと実機で確かめること, so that 後の変更で崩れたら気付ける

#### Acceptance Criteria

1. The 本 spec shall 鍵の読み取り（マイナスの座標・`--数値`・面ごとの上書き・`\b[ID]` で面が替わったときの定義の作り直し・読めない値）、名前の選び方（スコープごとの順・旧名・`arrow.filename`・絵が欠けたとき・クリック待ちの名前）、矢印の出る条件（横書き・縦書き・箱）、手動の送り（クリック・ホイール・限り・戻り方）、手動の位置と新しい文字・消去・面の切り替え・拡大率・選択肢の当たりの関係を、決定論のテストで固定する。
2. The 本 spec shall 矢印の鍵を持たないバルーンの既存のテストを、期待値を変えずに通す。
3. The 本 spec shall emo2 を写した検体（ワークツリーの `target\` の下）に既定のバルーン `areka-balloon` を置いた実機の走行で、長い台詞で `arrow0` が出ること・クリックとホイールで戻して読めること・新しい台詞で最新の行へ戻ることを、記録と MCP の `dump_balloon` の絵で確かめる。
4. The 本 spec shall ぱすたの縦書きのバルーン（手順書 `doc/pasta-real-run.md` の入れ方）で、矢印が SSP と同じ所に出ることを排他テストの机で確かめ、結果を spec の文書に残す。
5. The 本 spec shall シェル内バルーンの箱の矢印とクリック・ホイールを、箱を持つ検体のシェルで確かめる。
