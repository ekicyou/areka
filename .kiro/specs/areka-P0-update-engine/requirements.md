## Project Description (Input)

ゴーストの作者が出した修正を受け取りたい第三者（α の利用者の一周の 5 歩目）のために、ネットワーク更新の**エンジン**を新しいクレートとして建てる。入力は「更新先 URL（`homeurl`）の文字列」と「対象フォルダの絶対パス」だけで、`updates2.dau`／`updates.txt` を読み、ローカルの木との差分を MD5 で導き、要るファイルだけを一時的な場所へ落として照合し、**全部入るか 1 つも入らないか**の形で確定し、`delete.txt` を安全に適用し、結線する側が `OnUpdate*` の Ref を組み立てるのに足りる結果を返す。イベントは送らず、kanade・台本・メニュー・網羅台帳には触らない（それらは親仕様 `areka-P0-network-update` が持つ）。

## Introduction

### 誰が困っているか

ゴーストを入れた第三者。作者が辞書や絵を直して配布サイトを更新しても、areka では受け取れない。加えて、本エンジンを kanade の「更新」の相・台本の入口・メニューへ結線する `areka-P0-network-update` の実装者（本仕様の直接の読み手）。

### いま何が起きているか（2026-09-23 実測）

- **ネットワーク更新に当たる実装は 0 である。** 本番・テストの全ソース（`vendors/`・`doc/`・`.kiro/` を除く）で `WinHttp|WinInet` を綴るファイルは 0、`updates2|updates\.txt` は 0、`OnUpdate` は 0。`delete\.txt` は `crates/areka-parsers/src/package/validation_tests.rs` の 1 ファイルだけで、それは「読まないこと」を固定するテストである。
- **`homeurl` は語彙だけが在る。** `crates/areka-sylphya/src/vocab/shiori_resource.rs`（SHIORI リソース 41 件の 1 つ）と `vocab/dotted.rs` に名前があり、検体の `descript.txt`（`crates/areka-emo-text/examples/fixtures/*/descript.txt`）に値があるが、値を読んで使う経路は無い。
- **HTTP クライアントは 1 つも無く、MD5 も無い。** `Cargo.toml`（根・各クレート）・`deny.toml` に `md-5`／`md5`／`Win32_Security_Cryptography` の綴りは 0。根の `windows` の機能一覧（`[workspace.dependencies.windows]`）に `Win32_Networking_WinHttp` は無い。
- **ワークスペースの `members` は `crates/*` の一括指定**で、クレートを 1 つ足しても根の `Cargo.toml` に行は増えない。`crates/dola/Cargo.toml` は `windows` の機能（`Win32_System_Performance`）を**クレート自身の `Cargo.toml`** で足しており、根の機能一覧に触らない前例になっている。
- **前例 `areka-nar` の確定の部品は公開されていない。** `crates/areka-nar/src/install.rs` の `WorkArea`・`stage_placement`・`commit_all` はいずれも `pub(crate)` で、公開面は `NarArchive::open`／`manifest`／`install` と `InstallRequest`／`InstallOutcome`／`NarError` 系だけ（`lib.rs` の `pub use`）。加えて、その仕組みは「**フォルダ丸ごと**を作業フォルダで組み上げて宛先と入れ替える」形であり、更新に要るのは「**在る木の中の一部のファイル**を入れ替える」形である（同じ「作業場所で組んで最後に入れ替える」思想だが、単位が違う）。`crates/areka-nar/src/` は同じウェーブ A1 の `areka-P0-nar-install-hardening`（台帳 #52）が触る。
- **ライセンスの関門は整っている。** `deny.toml` の許可は MIT・Apache-2.0・Unlicense・Zlib・0BSD・BSD-2/3・Unicode-3.0。`THIRD-PARTY-NOTICES.md` は `cargo about` の生成物（`about.toml` あり）。
- **網羅台帳の `delete.txt` の項目**（`doc/ukadoc-coverage/ledger/assets.toml` の `descript_install` 「相対パス」）は `owner = "areka-P0-network-update"`・`status = "absent"`。`ukadoc-survey` の検査が持つ証跡の検査は `ImplementedWithoutEvidence`（状態が実装済みなのに定義箇所へ正典 URL の 1 行が無い）の**片側だけ**で、状態が `absent` のままソースに正典 URL の 1 行を置いても赤にはならない。

### 何を変えるか

新しいクレートに閉じたエンジンを建てる。エンジンは ⑴ 定義ファイルを取得して読む → ⑵ ローカルの木との差分を MD5 で導く → ⑶ 差分のファイルを一時的な場所へ落として MD5 で照合する → ⑷ 全件揃ってから全か無かで確定する → ⑸ `delete.txt` を安全に適用する、という一周を、外界との唯一の口（URL → バイト列）を差し替え可能にして回す。常時テストは偽の取得口だけで一周を回し、本物の取得口（OS の HTTP 機能）は実機の一周で確かめる。呼び出し側へは段ごとの進捗と最終結果を渡し、イベントの送出は呼び出し側に委ねる。

## Requirements

### Requirement 1: 更新定義ファイルの取得と読み取り

**Objective:** As a 結線する側の実装者, I want エンジンが更新先 URL から定義ファイルを取得し正典どおりに読めること, so that 作者が SSP 向けに置いた `updates2.dau`／`updates.txt` をそのまま受け取れる

#### Acceptance Criteria

1. When 更新先 URL と対象フォルダを受け取って一周を始める, the 更新エンジン shall まず `<更新先 URL>updates2.dau` を取得し、それが「無い」（見つからないという応答）ときに限り `<更新先 URL>updates.txt` を取得する（`manual_update`「どちらか一方があればよい（両方あっても問題ない）」・`dev_update`「updates2.dau を全て updates.txt に読み替え」）。
2. If `updates2.dau` の取得が「無い」以外の理由（名前解決・接続・応答待ちの上限・見つからない以外の失敗の応答）で失敗した, then the 更新エンジン shall `updates.txt` へ後退せず、その理由で一周を失敗にする（通信の失敗を「定義ファイルが無い」に化けさせない）。
3. If `updates2.dau` も `updates.txt` も無い, then the 更新エンジン shall 「定義ファイルが無い」を理由に一周を失敗にする。
4. If 受け取った更新先 URL の末尾が `/` でない, then the 更新エンジン shall `/` を補って進み、補ったことを警告として記録する（`descript_ghost` `homeurl`「url の末尾に / を忘れないように」）。
5. The 更新エンジン shall `updates2.dau` の各行を `ファイルパス\x01MD5\x01拡張フィールド…`（`\x01` はバイト値 1）として読み、行の終わりは CRLF を正とし LF だけの行末も同じく行の終わりとして受け入れる（`spec_update_file` 行フォーマット「改行は CRLF」）。
6. The 更新エンジン shall `updates.txt` を、行頭が `file,` の行はその後ろを `updates2.dau` と同じ形として読み、行頭が `charset,` の行は以降の行の文字コードの指定として読み、どちらでもない行は無視する（`spec_update_file` 行種別）。
7. The 更新エンジン shall 必須フィールドを「ファイルパス（位置 0・`/` 区切りの相対パス）」と「MD5（位置 1・32 文字の 16 進）」とし、位置 2 以降の `key=value` 形の拡張フィールドのうち `size=`・`date=` は読んでも振る舞いに影響させず、`charset=` は `updates2.dau` の先頭エントリの末尾にあるときだけ文字コードの判定に使い、それ以外の位置の `charset=` は無視する（`spec_update_file` 必須フィールド・拡張フィールド）。
8. When `updates2.dau` の先頭エントリの末尾に `charset=<名前>` がある, the 更新エンジン shall その名前を先に読み取り、ファイル全体（先頭エントリのパスを含む）をその文字コードで復号する。`updates.txt` では `charset,<名前>` 行が同じ役目を持つ。
9. While 定義ファイルに文字コードの指定が無い, the 更新エンジン shall 既定の文字コードで復号する。既定は**裁定候補 ⑵**で決める（正典は「OS デフォルトの charset」・brief の推奨は Shift_JIS 固定＝`charset-canon` の既定と同じ固定写像）。どちらに決まっても、OS のロケール設定を読む箇所は候補が「OS 既定」に決まった場合の 1 か所に限る。
10. If 文字コードの指定が解決できない名前である, then the 更新エンジン shall 警告を記録し既定の文字コードへ後退して読み続ける（`charset-canon` の後退規則と同じ）。
11. The 更新エンジン shall 次のエントリを**無効**として捨て、行番号と理由を警告に記録し、以降の処理に含めない: MD5 が無い、または 32 文字の 16 進でない／パスの末尾が `/` または `\`（フォルダのエントリ）／パスの区切り要素に `..` を含む（`spec_update_file` セキュリティチェック）。
12. The 更新エンジン shall 正典の 3 種に加えて次のエントリも無効として同じ扱いにする（第三者のフォルダを書き換える口の安全側）: パスが絶対パス（`/` または `\` 始まり・ドライブ文字付き・UNC）／パスが空、または空の区切り要素を含む／パスに NUL 文字を含む／パスが定義ファイル自身（対象フォルダ直下の `updates2.dau`・`updates.txt`）を指す（自分自身の MD5 は自己整合しない）。
13. The 更新エンジン shall パスの区切りとして `/` を正とし、`\` も同じ区切りとして扱う（`..\` を `..` の要素として捕まえるため。`spec_update_file` セキュリティチェックが `..\` を挙げている）。
14. If 同じローカルパスへ解決されるエントリ（大文字小文字だけの違いを含む）が複数ある, then the 更新エンジン shall 後の行を採り、先の行を捨てたことを警告に記録する。
15. The 更新エンジン shall 全エントリのパスが「パーセント符号化済み」（全文字が ASCII で、`%` は必ず 16 進 2 桁を伴う）であるときはパスを復号したものをローカルパスとし、URL にはそのまま使い、そうでないときはローカルパスを書かれたままとし、URL 側だけを符号化する（`spec_update_file` URL エンコード）。URL 側の符号化は、非 ASCII の文字と URL のパスに使えない文字を UTF-8 のバイト列としてパーセント符号化し、`/` は区切りのまま残す（正典が沈黙する符号化の文字コードは UTF-8 とする＝本仕様の決定）。
16. If 有効なエントリが 0 件である（空の定義ファイルを含む）, then the 更新エンジン shall 失敗にせず「差分 0」として一周を終える（Requirement 2.5）。

### Requirement 2: 差分の計算——取得が要るファイルだけを選ぶ

**Objective:** As a ゴーストを入れた第三者, I want 変わったファイルだけが取得されること, so that 更新が短く済み、作者が触っていない自分の手元のファイルが勝手に消えない

#### Acceptance Criteria

1. When 有効なエントリの一覧が得られた, the 更新エンジン shall 各エントリについて対象フォルダ配下のローカルパスを見て、ファイルが無ければ「要取得」、在れば内容の MD5 を計算して定義の MD5 と比較し、異なれば「要取得」、同じなら「対象外」とする。
2. The 更新エンジン shall MD5 の比較を 32 文字の 16 進の綴りで行い、大文字小文字の違いを同じ値として扱う。
3. The 更新エンジン shall 定義に無いローカルのファイルをいっさい触らない（`dev_update`「サーバにあるファイルでユーザ側にあるファイルを上書きすることであって、同期（ミラーリング）することではない」）。
4. If ローカルのファイルが在るのに読めない, then the 更新エンジン shall そのパスと理由で一周を失敗にする（比較できないものを「要取得」に化けさせない）。
5. If 「要取得」が 0 件である, then the 更新エンジン shall 対象フォルダに 1 バイトも書かず、「更新なし（差分 0）」として成功で終える（呼び出し側が `OnUpdateCheckComplete` 相当に写せる形）。
6. The 更新エンジン shall 「要取得」の一覧を定義ファイルの順で保ち、件数とパスの列を結果と進捗に含める（`OnUpdateReady` の Ref0＝総数−1・Ref1＝ファイル名の一覧に写せる形）。

### Requirement 3: 取得の境界——外界との唯一の口

**Objective:** As a 開発者, I want ネットへ出る箇所が 1 つの境界に閉じていること, so that 常時テストは偽の取得口だけで一周を回せ、本物の取得口は実機の一周でだけ確かめられる

#### Acceptance Criteria

1. The 更新エンジン shall 外界へ出る操作を「URL を受け取り、バイト列または理由付きの失敗を返す」1 つの境界に限り、定義ファイルも各ファイルも同じ境界から取得する。
2. The 本仕様 shall 境界の偽実装（URL からバイト列への固定表と、失敗の注入）を提供し、常時テストの全てがその偽実装だけを使う（ネットへ出るテストを常時テストに入れない）。
3. The 本仕様 shall 境界の本物の実装を 1 つ提供し、それは OS が備える HTTP クライアント機能を用いる（brief と roadmap の決定＝WinHTTP・新しい HTTP クレートを足さない）。
4. The 本物の実装 shall `http` と `https` の両方の URL を扱い、転送先を指示する応答（3xx）に追随し、成功の応答（2xx）の本文をバイト列として返す。
5. If 応答が成功でも転送でもない（4xx・5xx 等）, then the 本物の実装 shall 状態コードを含む理由で失敗を返し、「見つからない」（404）を Requirement 1.1 の後退の判定に使える形で区別する。
6. If 名前解決・接続・送受信に失敗した, or 応答が上限の時間内に届かない, then the 本物の実装 shall 失敗の種類を含む理由で失敗を返し、無限に待たない（上限の値は設計で決める）。
7. The 更新エンジン shall 呼び出し側のスレッドで同期に動き、自らスレッドを起こさない（UI スレッドの外で走らせる配線は呼び出し側の責務）。

### Requirement 4: 一時的な場所への取得と MD5 照合

**Objective:** As a ゴーストを入れた第三者, I want 落としたファイルが壊れていないと分かってから手元に入ること, so that 途中で切れた・改竄された・広告が混ざったファイルで手元のゴーストが壊れない

#### Acceptance Criteria

1. The 更新エンジン shall 「要取得」の各ファイルを対象フォルダの本番の位置には書かず、一時的な作業場所へ落とす（取得の間、対象フォルダの木は 1 バイトも変わらない）。
2. The 更新エンジン shall 各ファイルの URL を「更新先 URL＋定義のパス（`/` 区切り・Requirement 1.15 の符号化）」で組む。
3. The 更新エンジン shall 「要取得」を定義の順に 1 件ずつ取得し、各件の前に「ファイル名・番号（0 始まり）・総数」を進捗として知らせる（`OnUpdate.OnDownloadBegin` の Ref0〜Ref2 に写せる形）。
4. When 1 件を落とした, the 更新エンジン shall そのバイト列の MD5 を定義の MD5 と照合し（Requirement 2.2 と同じ比較）、「ファイル名・正しい MD5・落とした MD5・一致／不一致」を進捗として知らせる（`OnUpdate.OnMD5CompareBegin`／`Complete`／`Failure` の Ref0〜Ref2 に写せる形）。
5. If MD5 が一致しない, then the 更新エンジン shall その場で一周を失敗にし、以降のファイルを取得せず、失敗の理由に「MD5 不一致」とファイル名・正しい MD5・落とした MD5 を含める。
6. If 1 件の取得が失敗した（Requirement 3.5・3.6）, then the 更新エンジン shall その場で一周を失敗にし、以降のファイルを取得せず、失敗の理由にファイル名と取得の失敗の理由を含める。
7. The 更新エンジン shall 落としたバイト列を変換せず（改行・文字コードを触らず）に保持し、確定後のファイルの内容が落としたバイト列と同一である。
8. When 一周が終わった（成功・失敗のどちらでも）, the 更新エンジン shall 作業場所を片付け、片付けられなかった残骸のパスを結果に列挙する（黙って残さない）。ただし戻せなかったとき（Requirement 5.5）は元の内容が残る作業場所を片付けず、そのパスを結果に残す。

### Requirement 5: 全か無かの確定

**Objective:** As a ゴーストを入れた第三者, I want 更新の結果が「全部入った」か「何も変わっていない」のどちらかであること, so that 途中で失敗しても手元のゴーストが半端な状態にならず、そのまま使い続けられる

#### Acceptance Criteria

1. The 更新エンジン shall 「要取得」の**全件**の照合が済むまで対象フォルダを変えず、全件が揃ってから初めて確定に入る。
2. When 確定する, the 更新エンジン shall 各ファイルを対象フォルダ配下の定義どおりの位置へ置き、無い親フォルダは作り、既に在るファイルは新しい内容で置き換える。
3. When 確定する, the 更新エンジン shall 取得した定義ファイル（`updates2.dau` または `updates.txt`）も対象フォルダ直下へ同じ名前で置く（配布フォルダの形と揃える。`manual_ghost`・`manual_directory` はゴーストの木に定義ファイルが在る形を示している）。
4. If 確定の途中でいずれかのファイルを置けない（開かれている・書けない・権限が無い）, then the 更新エンジン shall 既に置いた分を確定前の内容へ戻し、対象フォルダの内容を一周の開始前と同一にして失敗を返す（利用者からは「全部入った」か「何も変わっていない」しか見えない）。
5. If 戻しにも失敗した, then the 更新エンジン shall 「戻せなかった」事実と、元の内容が残っている作業場所のパスと、戻せたファイル・戻せなかったファイルの一覧を結果と記録に残す（`nar-install` の `rolled_back` と `work` の欄と同じ考え方）。
6. The 更新エンジン shall 確定で置く各ファイルの実パスが対象フォルダの配下にあることを確定の前にも確かめ、外へ解決されるパスを決して作らない。
7. The 更新エンジン shall 起動中のゴーストのファイル（読み込まれた SHIORI 等）が開かれていて置き換えられないときも Requirement 5.4 の形で失敗し、SHIORI の解放を試みない（呼び出し側が先に解放する）。
8. When 確定が成功した, the 更新エンジン shall 置いたファイルの一覧（定義の順）と件数を結果に含める（`OnUpdateComplete` の Ref1・`OnUpdateResult` の件数に写せる形）。

### Requirement 6: `delete.txt` の安全な適用

**Objective:** As a ゴーストの作者, I want 不要になったファイルを更新で取り除けること, so that 名前を変えた辞書や配布に紛れた開発用ファイルが利用者の手元で肥大しない

#### Acceptance Criteria

1. When 確定（Requirement 5）が成功した, the 更新エンジン shall 対象フォルダ直下の `delete.txt` と `delete[数字].txt`（`数字` は 10 進 1 桁以上）を、`delete.txt` → 数字の昇順で読んで適用する（`manual_update`「delete1.txt（SSP のみ・delete[数字].txt を認識可）」）。無ければ何もしない。
2. The 更新エンジン shall 各行を「対象フォルダからの相対パス・`\` 区切り・末尾 `\` はフォルダ」として読み（`descript_install` 相対パス）、`/` も同じ区切りとして受け入れ、空行と空白だけの行を無視し、文字コードは定義ファイルと同じ規則（Requirement 1.8〜1.10）で復号する。
3. If 行が絶対パス（`\` または `/` 始まり・ドライブ文字付き・UNC）である, or 区切り要素に `..` を含む, or 解決した実パスが対象フォルダの外へ出る, then the 更新エンジン shall その行を無視し、行番号と理由を警告に記録する（3 種の拒否）。
4. When 行がフォルダ（末尾 `\`）を指す, the 更新エンジン shall そのフォルダを中身ごと取り除く。行がファイルを指すのにその位置に在るのがフォルダであるときは取り除かず警告に記録する（ファイルの行でフォルダを消さない）。
5. If 行が指す物が無い, then the 更新エンジン shall 何もせず失敗にもしない（既に消えている＝目的は達している）。
6. If 取り除けなかった, then the 更新エンジン shall そのパスと理由を警告に記録し結果に列挙し、更新の成否は変えない（確定は済んでいる＝「全か無か」は確定までの約束であり、削除は確定後の後始末）。
7. When 適用が終わった, the 更新エンジン shall 取り除いたパスの一覧を結果に含める。

### Requirement 7: 進捗の通知と結果の型——結線する側に足りる形

**Objective:** As a `network-update` の実装者, I want エンジンから段ごとの進捗と最終結果を受け取れること, so that `OnUpdateBegin` から `OnUpdateResult` までのイベント列と Ref を、エンジンに手を入れずに組み立てられる

#### Acceptance Criteria

1. The 更新エンジン shall 呼び出し側が渡した観測者へ、起きた順に次の進捗を知らせる: 定義ファイルを取得した（どちらの名前か）／差分が決まった（件数・パスの列）／1 件の取得を始める（名・番号 0 始まり・総数）／1 件を照合した（名・正しい MD5・落とした MD5・一致か不一致か）／確定した（置いた一覧）／削除を適用した（取り除いた一覧）。
2. The 更新エンジン shall 最終結果を「成功」と「失敗」の 2 形で返し、成功は「更新 0 件（差分 0）」と「更新 n 件」を区別して、置いたファイルの一覧・取り除いた一覧・取り除けなかった一覧・残骸の一覧を持つ。
3. The 更新エンジン shall 失敗の結果に「どの段まで進んだか（定義ファイル取得・差分・取得 k 件目／総数・照合・確定・削除）」「失敗の理由（閉じた語彙）」「原因のファイル名（分かるとき）」「戻せたか」「元の内容が残る作業場所（戻せなかったとき）」を持たせる（`OnUpdateFailure` の Ref0・Ref1 と `OnUpdateResult` の理由・ファイル名に写せる形）。
4. The 更新エンジン shall 失敗の理由を閉じた語彙で返し、少なくとも「定義ファイルが無い」「定義ファイルの取得失敗」「ファイルの取得失敗（名前解決・接続・時間切れ・状態コード）」「MD5 不一致」「ローカルのファイルが読めない」「確定で書けない」「戻せなかった」を含める。語彙の全数は設計で確定し、決定論テストが各項目に固定入力 1 つ以上が対応することを判定する。
5. The 更新エンジン shall SHIORI イベントを送らず、SHIORI・kanade・メニュー・台本のどれにも触らず、`descript.txt` も読まない（入力は更新先 URL の文字列と対象フォルダの絶対パスだけ）。
6. The 更新エンジン shall 番号を 0 始まりで返し、1 始まり（`useorigin1`）への読み替えを呼び出し側に委ねる。

### Requirement 8: 失敗の可視性——ログ無しの失敗経路を持たない

**Objective:** As a 開発者と実機で検証する全員, I want 更新が失敗したとき理由と進んだ段が記録に残ること, so that 「更新に失敗しました」の先を利用者の報告だけで追える

#### Acceptance Criteria

1. The 更新エンジン shall 一周を失敗にする全ての経路で、更新先 URL・対象フォルダ・進んだ段・理由・原因のファイル名（分かるとき）を含む error の記録を **1 件だけ**出し（二重記録しない）、同じ内容を失敗の戻り値でも返す（ログ無しの失敗経路 0）。
2. The 更新エンジン shall 捨てた無効なエントリ・解決できない文字コード・末尾 `/` の補い・`delete.txt` で無視した行・取り除けなかった物・片付けられなかった残骸を、それぞれ理由付きの warn の記録で残す。
3. The 更新エンジン shall 一周の開始（URL・対象フォルダ）と終了（成功／失敗・件数）を info の記録で残す。
4. The 決定論テスト shall 失敗 1 回につき error の記録が 1 件であることと、無効なエントリ 1 件につき warn の記録が 1 件であることを、件数で判定する（印字だけで済ませない）。

### Requirement 9: 決定論テストと実機の一周

**Objective:** As a 開発者, I want 一周の全ての分岐が実機もネットも無しに再現できること, so that 第三者のフォルダを書き換える仕事の安全性を毎回の `cargo test` で言い切れる

#### Acceptance Criteria

1. The 本仕様 shall 定義ファイルの読み取り（Requirement 1）を固定入力で決定論的に検証する: `updates2.dau` の拡張フィールドあり／なし・`charset=` あり（Shift_JIS の日本語パス）／なし・CRLF／LF・無効エントリ（MD5 なし・末尾 `/`・`..`）と追加の無効（絶対パス・NUL・空要素・定義ファイル自身）・重複・全エントリ符号化済み／未符号化、および `updates.txt` の `file,`・`charset,`・無視される行。
2. The 本仕様 shall 差分（Requirement 2）を「無い／同じ／違う／定義に無いローカルのファイル」の 4 形で検証し、定義に無いファイルが触られないことを判定する。
3. The 本仕様 shall 偽の取得口で「定義ファイル → 差分 → 取得 → 照合 → 確定 → 削除」の一周を回し、成功（更新 n 件）・差分 0・定義ファイルが無い・`updates2.dau` 無しで `updates.txt` へ後退・通信失敗で後退しない・取得失敗・MD5 不一致・確定の途中失敗（注入）→ 戻し、の各経路を検証する。
4. The 本仕様 shall 「全か無か」を、確定の途中失敗の後に対象フォルダの全ファイルの内容が一周の開始前とバイト単位で同一であることで判定する。
5. The 本仕様 shall `delete.txt` の 3 種の拒否・フォルダの行・ファイルの行がフォルダを指す・無い物・`delete[数字].txt` の順序を固定入力で検証する。
6. The 決定論テスト shall 純 x64 で走り、ネットへ出ず、実機・GPU・32bit helper を要さず、`cargo test` の一部として常時走る。
7. The 本仕様 shall 完了前に本物の取得口で実機の一周を行う: 手元の HTTP（ローカルに立てた配布フォルダ）または開発者の配布サーバに対し、検体ゴーストの複製を対象フォルダにして「差分あり → 更新 n 件」と「差分 0」の 2 周を、`[profile.release]`（`opt-level='z'`）の設定で走らせ、記録で段の順序と件数を確かめ、結果を検証報告に残す。実機の一周は常時テストに入れない。

### Requirement 10: 新規クレート・依存・登記の追随

**Objective:** As a 開発者と同じウェーブで並走する実装者, I want 本仕様が既存のソースに触らず、足した物が所定の場所に登記されること, so that 合流で競合せず、ライセンスの関門を落とさない

#### Acceptance Criteria

1. The 本仕様 shall エンジンを新しいクレート 1 つに閉じ、kanade・`emo2_boot`・`main.rs`・`menu`・`areka-nar` の**振る舞い**を変えない（既存ソースへの差分は裁定候補 ⑶ で `areka-nar` の公開範囲を広げると決まった場合のその変更に限る）。
2. When MD5 の出どころ（裁定候補 ⑴）が外部の crate に決まった, the 本仕様 shall `.kiro/steering/tech.md` へ「意図的依存追加＝日付・承認済」の形で登記し、`cargo deny check` が緑であることを確かめ、`THIRD-PARTY-NOTICES.md` を再生成して増える項目が足した依存とその推移的依存に限られることを差分で確かめる。
3. When MD5 の出どころが OS の機能または自前に決まった, the 本仕様 shall 外部の crate を 1 つも足さず、`tech.md` に「候補だった `md-5` は採らなかった」ことを登記する。
4. The 本仕様 shall OS の機能（HTTP・暗号）の機能フラグを新しいクレート自身の `Cargo.toml` で足し、根の `Cargo.toml` に差分を作らない（`crates/dola/Cargo.toml` の前例・並走 spec との共有 0）。
5. The 本仕様 shall `THIRD-PARTY-NOTICES.md` を依存の増減の有無にかかわらず再生成し、競合したときは手で直さず再生成する。
6. The 本仕様 shall `.kiro/steering/structure.md` のクレート一覧に新しいクレートを登記する。
7. The 本仕様 shall 網羅台帳（`doc/ukadoc-coverage/`）の状態・`owner`・`roadmap-draft.md`・生成物に触らない（roadmap 裁定 6）。`delete.txt` の読み手の定義箇所に正典 URL の 1 行（`// ukadoc:` の印）を置くことは許す——台帳の状態を動かすのは `network-update` の仕事であり、状態が `absent` のまま印だけがあっても `ukadoc-survey` の検査は赤にならない（2026-09-23 実測: 証跡の検査は `ImplementedWithoutEvidence` の片側だけ）。
8. The 新しいクレート shall 1 ファイル 1,000 行以下の目安を本番・テストの双方で守り、記録の捕捉の部品（`log-capture-kit`）を本番の依存に置かない。

## 要件段階の裁定候補（要件ディスカッションで決める）

本節の候補は**どれを選んでも上の受け入れ基準は変わらない**。答えで変わるのは、依存の登記（Requirement 10.2／10.3）・既存ソースへの差分の有無（10.1）・OS ロケールを読む箇所の有無（1.9）だけである。

### ⑴ MD5 の出どころ

| 案 | 中身 | 依存 | 登記・関門 | 備考 |
|---|---|---|---|---|
| ⑴ `md-5`（RustCrypto） | 純 Rust の crate | 外部 1 本（＋推移的依存 `digest` 系） | `tech.md` 登記・開発者承認・`cargo deny`・NOTICES 再生成 | MIT OR Apache-2.0＝`deny.toml` の許可内。棚卸⑭の仮裁定 5 で「承認待ち」 |
| ⑵ OS の CNG（`Win32_Security_Cryptography`） | OS の暗号 API で MD5 を計算 | 外部 0（`windows` の機能フラグ 1 行をクレート自身の `Cargo.toml` へ） | 登記不要 | **brief の推奨**。取得を OS（WinHTTP）に任せるのと筋が揃う。MD5 は OS 側で「安全用途には非推奨」だが、ここでは配布物の同一性の検算であり用途に合う |
| ⑶ 自前 | RFC 1321 を実装（`areka-nar` の `crc32.rs` と同じやり方） | 外部 0 | 登記不要 | 100 行前後＋既知ベクトルのテスト。brief は「今さら自前で書くものではない」と評価 |

**推奨（brief）**: ⑵。決定論テストは案に依らず「既知の入力 → 既知の 32 桁」の較正を 1 つ持つ。

### ⑵ 定義ファイル（と `delete.txt`）の既定の文字コード

正典は「デフォルトは OS デフォルトの charset」（`spec_update_file` 文字コード）。選択肢は ⒜ **Shift_JIS 固定**（`charset-canon` の既定と同じ固定写像・OS のロケールを読む箇所 0・日本語ゴースト前提）／⒝ OS 既定（`GetACP` 相当・非日本語 OS では別の文字コードになる）。**推奨（brief・棚卸⑭の裁定候補 ⑸）**: ⒜。理由: areka の既定は全層で Shift_JIS 固定写像であり、`charset=` を書かない配布物は日本語ゴーストがほぼ全てで、OS 既定にすると非日本語 OS で同じ配布物が読めなくなる。

### ⑶ `areka-nar` の確定の部品を再利用するか

**実測（2026-09-23）**: `areka-nar` の作業フォルダ（`WorkArea`）・組み上げ（`stage_placement`）・入れ替え（`commit_all`）は全て `pub(crate)` で、公開面は `install` 1 本である。しかも単位が違う——`areka-nar` は「フォルダ丸ごと」を組んで入れ替えるが、更新は「在る木の中の一部のファイル」を入れ替える。

| 案 | 中身 | 既存ソースへの差分 | 備考 |
|---|---|---|---|
| ⒜ `areka-nar` の部品を公開して使う | `pub(crate)` → `pub` にし、ファイル単位の入れ替えを足す | `crates/areka-nar/src/` を触る＝A1 で並走する `nar-install-hardening`（#52）と共有 | 「同じ仕組みを 2 つ作らない」に忠実。どちらが先に触るかを着手時に決める必要がある |
| ⒝ エンジンが自分のファイル単位の確定を持つ | 同じ思想（作業場所に落とす → 置き換える前に元を退避 → 失敗したら退避から戻す）を、ファイル単位で新しいクレート内に持つ | 0 | 仕組みの単位が違うので複製ではない。#52 との共有 0 を保てる。ただし「退避 → 戻す」の考え方は `areka-nar` と同じ言葉（`rolled_back`・`work`）で結果に写す |

**要件生成者の見立て**: ⒝。理由は単位の違いと並走の共有 0。brief の「同じ仕組みを 2 つ作らない」は思想と語彙の共有で満たす。開発者の裁定を待つ。
