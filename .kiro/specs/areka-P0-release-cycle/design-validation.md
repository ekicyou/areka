## 重大な指摘（3 件）

### 指摘 1: 承認 A の後に main を取り込んだときの「c の回し直し」が、書かれたコマンドでは実行できない

- **問題**: 「段 4: 版上げの PR」の 6 は、main が動いていたら「段 3 の a・b・c を回し直し、push する」と決めている。ところが「差分の範囲の判定（c）」の表のコマンドは全部 `git diff ... HEAD`（作業木と HEAD の比べ）で、段 4 の 1 で版上げをコミットした後は、4 ファイルの差分が 0 行になる。表の当たりの条件（「3 つが在り」「足した行 2・消した行 2」）は必ず外れる。同じ 6 の「版上げの 4 ファイルの差分が同じなら、承認 A は取り直さない」も、何と何の差分を比べるのかが決まっていない。
- **さらに**: 回し直した b（`-License`）が `THIRD-PARTY-NOTICES.md` を作り直して中身が変わった場合（段 1 の確かめの後に開かれてマージされた PR が依存を変えたとき）、その変更をコミットするのか止まるのかが書かれていない。「push する」だけでは、作業木に変更が残ったままマージへ進む。取り込みと回し直しの間に main がもう一度動いたときに繰り返すかどうかも書かれていない。
- **影響**: 要件 2.7（取り込んで回し直してからマージ）の経路だけ、範囲の判定（要件 3.5）が効かなくなる。全体テストに数十分かかるので、並走の spec が多い今の進め方では、この経路は珍しくない。
- **直し方**: 6 の回し直しでは、c の比べの相手を「取り込んだ後の `{remote}/main` と HEAD」（`git diff --numstat {remote}/main HEAD` と `-U0`）に読み替えると書く。取り込みの後はこの差分がそのまま PR の中身になるので、表の当たりの条件は変えずに使える。加えて「b の後に `git status --porcelain` が（`tasks.md` を除いて）0 行でなければ止まる」「マージの直前にもう一度 main を読み、動いていたら 6 を繰り返す」の 2 文を足す。
- **要件**: 2.7・3.5・4.2・4.3
- **設計の場所**: 「段 4: 版上げの PR」の 6、「段 3: 手元の確かめ」の「差分の範囲の判定（c）」の表

### 指摘 2: 「マージしたがタグを打っていない版」を、段 1 が見つけられない

- **問題**: 「再開のときの事実の読み方」は、版上げの PR を `gh pr list --head {枝}` で探す。鍵が作業の枝なので、同じワークツリーで打ち直したときしか効かない。設計は「マージの後にタグを打てなくなったとき、main の版は上がったまま待つ」（Error Handling）と、日をまたぐ待ちを認めている（初回は Trusted Publishing の設定待ちが実際に起こりうる）。その間にワークツリーが片付けられる、または別のワークツリーで `/kiro-impl areka-P0-release-cycle` を打つと、段 1 は新しい回として進む。「今の版」は `0.0.2`、「次の版」は `0.0.3`、タグ `v0.0.3` は無いので、どの確かめにも掛からずにもう一度版を上げる。`v0.0.2` は main に版だけ在ってタグの無い版として残る。
- **同じ節の小さな穴**: (a) 再開のとき `{版}` をどこから読むかが書かれていない（段 1 の「次の版」をもう一度当てはめると 1 つ先の版になる）。(b) 段 5 の 5 で手元のタグを作った後、push の前に切れると、再開の `git tag v{版} {sha}` が「既に在る」で失敗する。段 5 の 7 は消すことを禁じているので、手元のタグが `{sha}` を指していればそのまま push する、と書いておく必要がある。
- **影響**: 要件 1.1（実行 1 回＝リリース 1 回）と 5.1（squash のコミットにタグ）が、再開の場所しだいで破れる。版上げは取り消せない（main に入る）。
- **直し方**: 段 1 の表に 1 行足す。「今の版のタグが在る: `git ls-remote --quiet --tags {remote} refs/tags/v{旧版}` が 1 行。0 行なら、前の回がマージの後で止まっている。版を上げずに止まり、題が `chore(release): v{旧版}` のマージ済みの PR（`gh pr list --state merged --search`）の squash のコミットを読んで、段 5 から続けるかを開発者に聞く」。今のリモートには `v0.0.1` が在るので、初回はこの確かめを通る。再開の表には「`{版}` はマージ済みの PR の squash のコミットの `Cargo.toml` から読む」「手元にだけタグが在るときは、指す先が `{sha}` と同じことを確かめて push へ進む」を足す。
- **要件**: 1.1・3.7・5.1・5.4
- **設計の場所**: 「段 1: 前提の確かめ」の表、「再開のときの事実の読み方」、「Error Handling」の「マージの後にタグを打てなくなったとき」

### 指摘 3: 「初回かどうか」を決める事実が書かれておらず、初回の記録が main に入る前の 2 回目で食い違う

- **問題**: 設計は多くの段に「初回だけ」の枝を持つが、その回が初回かどうかを何で決めるかを書いていない。候補は 3 つ在る（`spec.json` の `phase`・`tasks.md` に「（初回だけ）」のタスクが在るか・`v0.0.2` のタグが在るか）。初回の後、`spec.json` の `phase` は版上げの PR で main に入るが、「（初回だけ）」のタスクを消す変更・README の 1 行・roadmap の小見出しは、記録のコミットとして「次に main へ入る PR」に相乗りするまで main に無い。段 1 は、前の回の記録が main に無くても「開発者へ知らせる。止まる理由にはしない」と決めている。その状態で 2 回目を始めると、main の `tasks.md` にはまだ「（初回だけ）」のタスクが在り、主文脈は乾いた走り・Trusted Publishing の確かめ・`first-run.md` の作成をもう一度行う。roadmap の小見出しは、前の回の相乗りと今回の記録で二重に作られ、相乗りのときに衝突する。
- **影響**: 要件 1.2（2 回目以降は毎回同じタスク）が、相乗りの時期しだいで破れる。取り返しのつかない害は出ないが、2 回目の手順が毎回同じ形にならず、記録が食い違う。
- **直し方**: 「初回」を 1 つの事実で決めると書く（例: 作業の枝の `tasks.md` に「（初回だけ）」のタスクが在る回が初回）。そのうえで段 1 に「`tasks.md` に『（初回だけ）』のタスクが在るのに、リモートに `v0.0.2` のタグが在るときは、初回の記録がまだ main に入っていない。版を上げずに止まり、相乗りを先に済ませるよう開発者へ頼む」を足す。2 回目以降の「記録が main に無い」は、今のとおり知らせるだけでよい。
- **要件**: 1.2・7.4・8.8
- **設計の場所**: 「段 1: 前提の確かめ」の箇条「前の回の記録が main に入っているか」、「段 7: 記録と受け渡し」の 4、「1 回の実行で作るコミット」の表

## 重大ではない気付き（判定には入れない）

- **版を上げた状態での公開前の確かめは、まだ一度も回っていない**: `tools/crates-io.ps1`（包むだけの形・`-Verify` の両方）は、`wintf` が頼る `dola` の版が crates.io に在る `0.0.1` でしか回っていない。`0.0.2` に上げると、crates.io に無い版の `dola` を頼る `wintf` を包むことになる。赤なら段 3 の b か e で止まり、何も外へ出ないので安全側だが、「初回の実走で確かめること」の一覧に 1 行足しておくと、赤のときに「道具の誤りか手順の誤りか」を迷わない。
- **起票のコミットの置き場が 2 か所で違う**: 段 1（乾いた走りの赤）は「別のセッションで `/kiro-discovery` を打つ」、段 6（見守りの赤）は「作業の枝に別のコミットとして置く」。どちらも理由は通るが、段 6 の起票のコミットは roadmap の台帳の数の行を触るので、相乗りの `git cherry-pick` で衝突しやすい。受け渡しの 1 文の「衝突したら、取り込む側を採って 1 行を足す」は記録の行にしか効かない。起票のコミットが在る回の受け渡しの文を 1 つ足しておくとよい。
- **乾いた走りの見つけ方**: 段 1 の `gh workflow run release.yml --ref main` は走りの番号を返さない。段 6 と同じように `gh run list --workflow release.yml --event workflow_dispatch` で拾う、と 1 行書くと迷わない。

## 設計の良い点

- **取り返しのつかない操作の前の事実の読み直しが具体的**: タグを打つ相手を `gh pr view --json mergeCommit` の squash のコミットに名指しし、main の先祖であること・そのコミットの `Cargo.toml` の 2 行・リモートにタグが無いことを確かめてから、`refs/tags/v{版}` の 1 本だけを push する。手元の `pre-rebase-5-1`・`pre-rebase-5-1b` を押し出さない理由まで書かれており、「タグを別のコミットに打つ」失敗の道が塞がれている。
- **`tasks.md` の `[x]` をコミットしないという 1 つの決めで、3 つの要件を同時に満たしている**: 版上げの PR に `tasks.md` が混ざらず（4.2）、main の `tasks.md` は常に未完了で（1.3）、チェックの戻しを運ぶ PR が要らない（7.4）。ほかの spec と分け合う決まりの文書を 1 つも直さずに済ませている（1.8）。
