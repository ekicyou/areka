- **判定**: **名簿の項目だけが増える**

## 手順

1. 走らせる前に `netstat -ano` で `127.0.0.1:9276` を握るプロセスが無いことを確かめた（無し）。`areka.exe` も起きていなかった。SSP（pid 33684）が 9801・9821 を握っていたので、areka の MCP は隣の 9802 で待ち受けた。
2. emo2 一式（`cargo run -p sample-ghost-kit --bin nar-sample-path -- emo2` の `folder=` の中身）を、ワークツリーの `target\tc\emo2` へ写した（短い絶対パス）。
3. `AREKA_*`・`WINTF_*` の環境変数を全部外したうえで、次を足して `Start-Process` で起こした（作業フォルダは `target\debug`）。
   - `AREKA_PERF_THREAD_REPORT_SEC=10`
   - `RUST_LOG=info,areka::perf=debug,wintf::thread_registry=debug`（`wintf::thread_registry` の行はこの版にはまだ無く、0 件）
   - `NO_COLOR=1`・`AREKA_NO_ALERT=1`
   - `AREKA_PROFILE_DIR`・`TEMP`・`TMP` はワークツリーの `target\tc\profile`・`target\tc\tmp`
   - 引数はゴーストの根 `...\target\tc\emo2` とバルーン `...\target\tc\emo2\balloon\emo2-kakukaku`（どちらも絶対パス）
   - 標準出力・標準エラー出力は `target\tc\logs\run.log`・`err.log`
4. 起こしたプロセスは pid 31000。`netstat` で 9802 の待ち受けがこの pid であること、MCP の `get_active_ghost_list` が「えも？？」を返すことを確かめた。
5. 起動直後の報告 1 枚の後に 1 対目を取った。以後、areka の MCP の `sakurascript` で `\0\s[0]スレッドの数を数えています。\e` を流し、`get_status` で `talking` が消えたのを見てから、次の報告（`perf(process)` の `snap=` が 1 つ進む）を待ち、その `threads=` と PowerShell の `(Get-Process -Id 31000).Threads.Count` を 1 対として取った。これを 6 回。`get_status` でトークの終わりはすべて見えたので、「1 枚を 2 つ待つ」形には倒していない。
6. 止めたのは、`Get-Process -Id 31000` のパスがこのワークツリーの `target\debug\areka.exe` であると確かめた pid 31000 だけ。止めた後に生き残っていないことも確かめた。走行のログに ERROR の段の行は 0 件。

areka にスレッドを列挙する機能は足していない。OS の数は、プロセスの外から PowerShell で数えた。

## 名簿に残った `sakura-talk-<番号>` の数

`snap=15` の `perf(thread)` の行には `sakura-talk-1` から `sakura-talk-12` までの 12 行が並び、`threads=` は起動直後の 16 から 11 増えた（起動直後の 16 には、再生中だった `sakura-talk-1` が既に入っている）。この版には名簿の登録の `debug!`（target `wintf::thread_registry`）が無いので、数は報告の行と、kanade がトークを始めたときの `talk_id=` の行から数えた。

MCP で流したトークは 6 回だが、名簿には 12 本ある。この 12 本は、走行中に始まったトーク（`talk_id=1`〜`12`）と 1 対 1 に対応している（トーク 1 つにつき `sakura-talk-<番号>` のスレッドが 1 本）。

| 起こし方 | `talk_id` | 本数 |
|---|---|---|
| 起動の挨拶（`boot_talk`） | 1 | 1 |
| MCP の `sakurascript`（`sstp_send_started`） | 2・4・6・7・10・11 | 6 |
| ゴースト自身の時刻のトーク（`steady_talk` origin=`OnSecondChange`） | 3・5・8・9・12 | 5 |
| 計 | | 12 |

- `talk_id=5` と `9` の時刻のトークは、直後に MCP のトークで差し替えられた（`talk_done_stale` の行あり）。差し替えられたトークのスレッドも名簿に残っている。
- `talk_id=13`（時刻のトーク）は `snap=15` の後の 13:12:20 に始まったので、表には入らない。
- 最後の 1 枚（`snap=15`）の時点で喋っていたトークは無い。走行のあいだに終わったトークの数は、12 本のすべてにあたる。

## 判定: 名簿の項目だけが増える

- 報告の `threads=` は、トークが始まるたびに 1 つずつ 16 から 27 まで増え、減らなかった。
- OS から数えたスレッドの数は、同じあいだ 87〜92 の幅で上下するだけで、トークの数に合わせて増えなかった（最初が 91、最後が 87）。
- 名簿に 12 本ある `sakura-talk-<番号>` のスレッドが生きていれば OS の数は 11 ほど増えるはずだが、増えていない。トークのスレッドは、自然に終わったときも差し替えられたときも OS の上では終わっていて、名簿の項目だけが残っている。
- OS の数（90 前後）が報告の数（16〜27）より大きいのは、名簿に載らないスレッド（OS や描画の部品が作るもの）があるからで、それらは報告では `unregistered_rest` に入る。今回の判定には、差ではなく増え方だけを使った。

## トーク以外の起こし方での増え方

今回はトーク（起動の挨拶・MCP・ゴースト自身の時刻のトーク）だけを流した。ゴーストの切り替えはしていない。トーク以外の起こし方で OS の数が同じ形で増えるところは見ていない。
