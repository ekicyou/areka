# Requirements Document

## Project Description (Input)

- **誰が困るか**: マスコットを何日も起動したまま喋らせる利用者と、スレッド別 CPU の報告（`perf(thread)`／`perf(process)` の行）で重さを調べる開発者。
- **今の様子**: 実機（emo2・debug ビルド）で、10 秒ごとのスレッド別 CPU の報告の `threads=` が、起動直後の 15 から終了前の 35 まで増えた。増えた分はすべて `sakura-talk-<番号>`（トーク 1 つにつき 1 本）で、MCP を呼ぶ前に終わった起動の挨拶の分も残っていた。報告の `threads=` はスレッド名簿の項目の数で、OS から数えた数ではない。名簿は、スレッドが走り始めに自分のハンドルを複製して預ける作りで、スレッドが終わった後も項目と複製したハンドルを持ち続ける（項目を外すのは同じスレッド番号が登録し直したときだけ）。名簿への登録は報告器の点灯によらず常に行われる。生きているスレッドの数を OS から数えた記録はまだ無い。
- **変えたいこと**: 長く起動していても、トークの数に比例してスレッド・名簿の項目・OS のハンドルが増えない。報告の数が実際に生きているスレッドと食い違わない（終わったスレッドを含めるなら、そう分かる形で出す）。終わったスレッドの CPU 時間が報告から黙って消えない。直した形を決定論テストで固定し、実機で数が増えないことを 1 回確かめる。

## Introduction

トークのたびに `sakura-talk-<番号>` のスレッドが 1 本ずつ起き、自然に終わるか中断されて抜ける。ところがスレッド名簿は終わったスレッドの項目と複製したハンドルを手放さないので、報告の数も OS のハンドルもトークの数だけ積み上がる。読む限りスレッドそのものは終わっている見立てが強いが、確かめはまだ無い。

本 spec は、まず実機で報告の数と OS から数えたスレッドの数を並べて、増えているのが名簿だけか生きたスレッドもかを切り分ける。そのうえで、名簿が終わったスレッドを手放し、その最後の CPU 時間を役割の系統ごとの合計へ畳んで報告に残す形へ直し、報告の `threads=` の意味を実際と合わせる。生きたスレッドも残っていると分かったときだけ、トークのスレッドの後始末も直す。直した形を決定論テストで固定し、実機で 1 回数え直す。

## Boundary Context

- **In scope**:
  - 実機での切り分け（報告の `threads=` と、プロセスの外から OS で数えたスレッドの数を、トークを繰り返しながら対にして数える）。
  - スレッド名簿の、終わったスレッドの項目と預かったハンドルの扱い（手放す・最後の CPU 時間を役割の系統ごとの合計へ畳む）。名簿の直しは役割によらず、名簿に載った終わったスレッドのすべてに効く。
  - 報告器の行の意味（`threads=` の数・畳んだ合計の行・名簿外の残り `unregistered_rest` の算出）。
  - 報告の行を読む順位表の道具 `tools/perf/perf-rank.py` の段②（区間の差・役割別の表）と、その自己テスト。
  - 説明の追随（報告器のモジュールの説明のうち差の取り方の古い記述、`tools/perf/README.md` の段②の「名簿は終了したスレッドの登録を消しません」などの記述）。
  - 切り分けで生きたスレッドも残ると分かったときだけ、トークのスレッドの後始末（自然な終わり・中断・差し替えの後にスレッドが終わること）。
  - 決定論テストと、直した後の実機の確かめ 1 回。
  - 終わったスレッドの項目が残ることを前提にした今のテスト（名簿のテストのうち、join の後も項目が残り CPU を読めることを確かめるもの）と、同じ前提の説明（名簿のモジュールの説明・報告器の名簿外の残りの説明）の書き直し。
- **Out of scope**:
  - 名簿の作りの置き換え（OS からスレッドを列挙する形へ替えること）と、`Cargo.toml` の機能や依存を足すこと。
  - トークの再生の振る舞い（台本・刻み・中断の意味）。
  - トーク以外のアクター（ゴーストの切り替えで起こし直すものなど）の寿命の見直し。名簿の直しはそれらの終わったスレッドにも効くが、各アクターの起こし方と終わり方は変えない。同じ形で生きたスレッドが増えるものが見つかったら記録に残す。
  - `areka-actor` の `spawn_actor`・`run_inbox` の約束（終わり方は `Break` と切断の 2 つ）と、走り始めのフックの型（`ThreadStartHook`）。
  - 報告器の時計の置き換え（`instant-to-interrupt-ticks` が扱う）。
- **Adjacent expectations**:
  - 同じウェーブの `talk-script-metadata` はトークの側のファイル（`crates/areka-sakura/src/drive.rs`・`crates/areka-ghost/src/dispatcher.rs`）に触る。本 spec はウェーブの約束により、名簿・報告器・`perf-rank.py`（と説明）だけを直す。トークの側の直しが要ると分かったら、`talk-script-metadata` の着地の後に回す。
  - 走り始めのフック（`crates/areka/src/thread_roles.rs`）は読むだけで、役割名の宣言の仕方は変えない（`actor-thread-log-capture` の持ち場）。
  - `perf(process)` 行を読むほかの道具（性能改善ループの比べと台帳・判定の道具 `judge-perf.py`）は、変えた後の行を読んでも止まらないことを期待する（`perf(process)` から読むのは `snap` と `cpu_us`）。
  - `instant-to-interrupt-ticks` は本 spec の着地の後に報告器の時計を替える。本 spec は報告器の時計に触らない。

## Requirements

### Requirement 1: 実機での切り分け

**Objective:** As a 開発者, I want トークを繰り返しながら報告の数と OS から数えたスレッドの数を並べて見たい, so that 増えているのが名簿だけか生きたスレッドもかを確かめてから、直す所を決められる

#### Acceptance Criteria

1. When 切り分けを行う, the 実機の確かめ shall 報告器を点けて周期を短くした（10 秒）同じ 1 回の起動の中でトークを 5 回以上流し、起動直後と各トークの終わりの後に報告が 1 枚出たときのそれぞれで、報告の `threads=` と、プロセスの外から OS で数えたそのプロセスのスレッドの数を対にして記録する。
2. The 実機の確かめ shall OS からの数えを OS の標準のコマンドでプロセスの外から行い、areka にスレッドを列挙する機能を足さない。
3. When 記録がそろった, the 実機の確かめ shall 結果を「名簿の項目だけが増える」「生きたスレッドも増える」のどちらかに判定し、数の表とともに spec の記録へ残す。
4. If トーク以外の起こし方（ゴーストの切り替えなど）でも OS から数えたスレッドの数が同じ形で増えると分かった, the 実機の確かめ shall その起こし方と増え方を記録に残し、本 spec では直さない。
5. While 実機を動かしている, the 実機の確かめ shall 実機の根・検体・一時フォルダをワークツリーの `target\` の下だけに置き、負荷テストの机と画面の操作をそのタスクの区切りの中だけで持ち、止めるのは自分が起こしたと確かめたプロセスだけにする。

### Requirement 2: 名簿が終わったスレッドを持ち続けない

**Objective:** As a 利用者, I want 何日起動したままでも名簿の項目と OS のハンドルがトークの数だけ増えない, so that 常駐が上限なく資源を積み上げない

#### Acceptance Criteria

1. When 新しいスレッドが名簿に登録された、または名簿が読み出された, the スレッド名簿 shall その時点で既に終わっているスレッドの項目と、そのために預かったハンドルを残していない。
2. While 報告器が消えている（既定の運転）, the スレッド名簿 shall トークを繰り返しても、項目の数と預かったハンドルの数をトークの数に比例して増やさない。
3. The スレッド名簿 shall 生きているスレッドの項目を、今と同じく役割名・OS 側の名前・スレッド番号つきで持ち、その CPU 時間を読み出せるようにしておく。
4. When 登録または読み出しで終わったスレッドの項目を手放し終えた, the スレッド名簿 shall 項目の数を、生きている登録済みスレッドの数と役割の系統の数の和で頭打ちにする（トークの回数によらない）。
5. The スレッド名簿 shall 登録と読み出しを、今と同じく描画の刻みの経路に入れない。

### Requirement 3: 終わったスレッドの CPU 時間を黙って落とさない

**Objective:** As a 開発者, I want 終わったスレッドが使った CPU 時間が報告に残り続けてほしい, so that 名簿から手放しても「どの役割が重かったか」の合計が崩れない

#### Acceptance Criteria

1. When スレッド名簿が終わったスレッドの項目を手放す, the スレッド名簿 shall 手放す前にそのスレッドの最後の CPU 時間を読み、そのスレッドの役割の系統ごとの合計へ足す。
2. The スレッド名簿 shall 役割の系統を、役割名の末尾の `-<数字>` を畳んだ名で決める（例: `actor:sakura-talk-17` は `actor:sakura-talk-*` の系統）。**前提（未確定）**: 畳み方は順位表の道具の役割別の表の畳み方（`actor:…-<数字>` を `-*` へ）と同じにする。
3. If 手放す前に最後の CPU 時間を読めなかった, the スレッド名簿 shall 読めなかったスレッドの番号と役割名を記録に残し、その分が名簿外の残りへ回ることが記録から分かるようにする。
4. If 終わったスレッドのスレッド番号が新しいスレッドの登録に使い回された, the スレッド名簿 shall 前のスレッドの最後の CPU 時間を役割の系統ごとの合計へ足してから置き換え、二重にも数えず、黙って捨てもしない。
5. If 生きている同じスレッドが登録し直した, the スレッド名簿 shall 前の項目を合計へ足さずに置き換える（同じスレッドの CPU を二重に数えない）。
6. The スレッド名簿 shall 役割の系統ごとの合計を、起動から終わりまで減らさない（累積）。

### Requirement 4: 報告の数と行の意味

**Objective:** As a 開発者, I want 報告の `threads=` が実際に生きているスレッドと食い違わず、終わったスレッドの分はそうと分かる形で読みたい, so that 報告の数を見てスレッドの漏れを誤って疑ったり、見逃したりしない

#### Acceptance Criteria

1. The 報告器 shall `perf(process)` 行の `threads=` に、そのスナップショットの時点で生きている名簿のスレッドの数だけを出す（畳んだ合計の行と名簿外の残りの行は数えない）。**前提（未確定）**: `threads=` の意味を「生きている名簿のスレッドの数」に改め、終わったスレッドの本数を別に出すかは設計で決める。
2. Where 役割の系統ごとの畳んだ合計がある, the 報告器 shall それを系統ごとに 1 行の `perf(thread)` 行として毎回のスナップショットに出し、生きたスレッドの行とも名簿外の残りの行とも見分けがつく形にする。
3. The 報告器 shall 名簿外の残り（`unregistered_rest`）を、プロセス全体の CPU から生きたスレッドと畳んだ合計の両方を引いた差として出し、終わったスレッドの CPU を名簿外の残りへ移さない。
4. While 同じ起動の中でトークを繰り返している, the 報告器 shall `threads=` と OS から数えたプロセスのスレッドの数の差を、トークの回数に応じて広げない。
5. The 報告器 shall 足す行と欄にも、1 行に同じフィールド名を 2 度出さない・値に空白を残さない、という今の行の語彙の約束を守る。
6. The 報告器 shall この spec が意味を変える所の外では、今の行の文言・フィールドの綴りと並び・1 枚の中の行の順（プロセス 1 行が先頭、名簿外の残り 1 行が末尾）を変えない。
7. The 報告器 shall 報告器が消えているときは、今と同じく報告スレッドを起こさない。

### Requirement 5: 順位表の道具と説明の追随

**Objective:** As a 開発者, I want 順位表の道具が、区間の途中でスレッドが終わって畳まれても正しい役割別の CPU を出してほしい, so that 性能改善ループの順位付けが名簿の直しで静かに嘘をつかない

#### Acceptance Criteria

1. When 差を取る 2 つのスナップショットの間にスレッドが終わって畳まれた, the 順位表の道具 shall その区間の役割別の CPU に、そのスレッドが区間の中で使った分だけを数える（区間より前の分を足さず、区間の中の分を落とさない）。
2. The 順位表の道具 shall 差の基準で、名簿外の残りを今と同じく「プロセスの差 − 名簿の差の合計」（負なら 0）で出し、名簿の差の合計には生きたスレッドの区間の分と畳んだ合計の区間の分の両方を入れ、区間より前の CPU を足して名簿の側を膨らませない。
3. When この変更より前の作りで出たログを読む, the 順位表の道具 shall 止まらずに、今と同じ順位表を出す。**前提（未確定）**: 性能改善ループは前後のビルドの走行を比べるので、古いログも読めることを求める。
4. The 判定の道具と性能改善ループの比べ・台帳の道具 shall 変えた後の行を読んで止まらない。
5. The 説明（報告器のモジュールの説明と `tools/perf/README.md` の段②） shall 名簿が終わったスレッドを手放すこと、畳んだ合計の行、`threads=` の意味、差の取り方の今の形（最後のスナップショットと 60 秒前のスナップショットの比べ・名簿外の残りはプロセスの差から出す）を、直した後の振る舞いのとおりに書く。

### Requirement 6: 生きたスレッドが残っていた場合のトークの後始末

**Objective:** As a 利用者, I want トークが終わったらそのトークのスレッドも終わってほしい, so that 何日喋り続けても生きたスレッドがトークの数だけ増えない

#### Acceptance Criteria

1. If 切り分けで、トークが終わった後もそのトークのスレッドが生きて残ると分かった, the トークの後始末 shall 自然な終わり・中断・差し替えのどの終わり方でも、トークのスレッドを終わらせ、トークを繰り返しても生きたスレッドの数をトークの数に比例して増やさない。
2. The トークの後始末 shall 台本の再生の振る舞い（台本・刻み・中断の意味）を変えない。
3. While 同じウェーブの `talk-script-metadata` が着地していない, the トークの後始末 shall トークの側のファイル（`crates/areka-sakura/src/drive.rs`・`crates/areka-ghost/src/dispatcher.rs`）に触らず、切り分けの結果を記録して、トークの側の直しを着地の後に回す。
4. Where 切り分けで生きたスレッドは残らないと分かった, the トークの後始末 shall 行わず、トークの側のファイルに触らない。

### Requirement 7: 決定論テストと実機の確かめ

**Objective:** As a 開発者, I want 直した形が決定論テストで固定され、実機でも数が増えないことを 1 回見たい, so that 後の変更で同じ積み上がりが黙って戻らない

#### Acceptance Criteria

1. The 決定論テスト shall 本物のスレッドを多数（100 本以上）、そのテストだけが使う役割の系統で登録して終わらせた後、その系統の項目の数が、その系統の生きている登録済みスレッドの数と系統の合計の 1 つの和を超えないことを固定する（名簿はプロセスで共有され、テストは並列に走るので、名簿全体の項目の数は当てにしない）。
2. The 決定論テスト shall そのテストだけが使う役割の系統の畳んだ合計が、手放したスレッドの最後の CPU 時間の和と一致し、減らないことを固定する。
3. The 決定論テスト shall スレッド番号の使い回しと、生きている同じスレッドの登録し直しの両方で、二重にも数えず捨てもしないことを固定する。
4. The 決定論テスト shall 報告の行（`threads=` の意味・畳んだ合計の行の見分け・名簿外の残りの算出・行の語彙の約束）を固定する。
5. The 決定論テスト shall 順位表の道具の区間の差が、区間の途中で畳まれたスレッドを含む場合と、変更より前の形のログの場合の両方で正しいことを、道具の自己テストで固定する。
6. The 決定論テスト shall 報告器が消えているとき（名簿の読み出しが無いとき）にも、そのテストだけが使う役割の系統でスレッドの登録と終わりを繰り返して、その系統の項目が積み上がらないことを固定する。
7. The 決定論テスト shall 手放す前に最後の CPU 時間を読めなかったとき、その失敗が記録に残ることを固定する。
8. When 直しが入った, the 実機の確かめ shall 要件 1 と同じ手順で 1 回数え直し、トークを繰り返しても `threads=` と OS から数えたスレッドの数のどちらもトークの数に比例して増えないことと、畳んだ合計の行が出ていることを記録に残す。
