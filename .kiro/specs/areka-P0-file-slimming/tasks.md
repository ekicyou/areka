# Implementation Plan

> **逐次実行**である。`(P)` マーカーは付けない。理由: (a) 全タスクが単一ワークツリーの共有 `target/` ディレクトリで cargo ビルド／テストを実行するため、並行実行はビルドロックで実質直列化する、(b) クレート単位コミットのゲート（要件 7.2）が「当該クレート緑」の逐次確認を前提にしている。クレート間の**ソース編集そのもの**は境界的に独立であり、対応表もクレート別フラグメント方式で競合しないが、上記 2 点により並行安全条件を満たさない。並列化するにはワークツリーとビルド出力先を分ける前提条件が要り、本計画はその条件を置かない。
>
> **テーマ分割タスクの共通手順**（設計「Tasks フェーズへの申し送り 1」）: 対象モジュールごとに ①テーマ案の確定（モジュール内部構造・コメントバナー・ヘルパ参照関係の確認）→ ②項目単位の分割（関数の中は割らない・識別子は改名しない）→ ③対応表フラグメントへの追記 → ④全単射検証とテスト名リスト一致、の順で進める。
>
> **コミット粒度**: 1 クレートが複数タスクにまたがる場合、各タスク完了時にも当該クレート緑を確認してコミットしてよい（移設は逐次的に緑を保てるため）。要件 7.1 が禁じるのは全変更の単一巨大コミットであり、クレート内での複数コミットは許容される。この運用により実コミット数は設計 Migration Strategy の 15 本形（12 クレート＋分割 2＋文書 1）を上回る（表示合成 2・テキスト描画 2・ゴースト実行 2・本体 最大 6）。設計の表と数が合わない点は意図的であり、完了時の突合ではコミット数ではなく**着地順序と各コミットの緑**を照合する。

## Implementation Notes

- **検証スクリプトの終了コードは 0 / 1 / 2 を必ず区別する。** `2` は引数不正（パスの打ち間違い等）であって「本文不一致」ではない。2 を 1 と読み違えて、壊れていないテストを直しに行かないこと。呼び出し方の逐語は `verification/notes.md` §11.2。
- **本文一致検証には代償措置の無い盲点が 1 つある**（§11.4）。複数行文字列リテラルの内部にある行頭空白は正規化で消えるため、変わっていても MATCH と判定される。`\` 継続でない行が該当。タスク 2.1 で唯一の実在箇所 `crates/wintf/src/ecs/window_proc/window_pos.rs:1137` は de-indent の例外として処理済み。**この件数はツールによる全域計測なので、各タスクは自分の担当ファイルで独自に走査し直すこと**（レビュー指摘）。
- **`Test-VerificationTools.ps1` の `TOKENIZER-EQUIV` は移設開始後は必ず赤になる**（§11.6）。移設前ツリー前提のケースであり欠陥ではない。再実行時は残る 23 ケースで判定する。
- **計測スキャナの走査からは `.kiro/` を除外済み。** 本 spec のフィクスチャが全域実測へ混入するため（619→627 ファイル）。タスク 7.4 は必ず修正後のスクリプトで実測すること。
- **設計の「テスト行」と移設後ファイルの行数は 3 行ずれる。** 設計値はブロック外枠（`#[cfg(test)]`＋`mod X {`＋`}`）を含み、移設後の本体は含まないため。乖離ではない。
- **`research.md` / `design.md:123` / `requirements.md` §3.4 の「26 宣言ファイル」は実測 30 が正**、`research.md` の全域 `src/` テスト行 92,868 は厳密計測で 92,777 が正（差 −91 の出所は `crates/dola/src/runtime/clock.rs:31` の `#[cfg(all(test, ...))]` 1 件）。必須対象 49 本には無影響。`verification/notes.md` §2.2 / §2.3 に記録済みで、本文の是正は完了時にまとめて判断する。
- **`///` doc コメント付きテストモジュールは接続宣言側へ残置する**（タスク 2.2 で裁定・`verification/notes.md` §14.3）。`mod` 項目に対する doc 属性であって設計判断 #2 が移送対象とするモジュール間バナーコメントではなく、移動には `///` → `//!` の書き換えが要り要件 2.4 に反する。intra-doc リンクの解決先も保たれる。**完了状態の「テストモジュール本体が 1 行も残らず」には抵触しない**（本体＝`{ … }` の中身）。
- **要件 1.4 の除外ファイル（既に本番ファイル外へ分離済み）は 1,000 行超でも分割しない**（タスク 3.1 で裁定）。例: `areka-emo-compose/src/golden_tests.rs` 1,356 行。根拠は 4 点——親から素の `#[cfg(test)] mod X;` で宣言済み／`excluded_inventory.csv` に登載／`#[cfg(test)] mod` ブロックを持たないので要件 1.1 の対象でない／要件 1.7 が縛るのは**移設先**のみ。design §Non-Goals も明示的に対象外としている。**クレート完了状態の「テストファイルがすべて 1,000 行以下」はこの除外を前提に読む。**
- **共有ヘルパは項目が 1 件でも `<stem>_test_support.rs` へ集約する**（タスク 3.1 で裁定）。複製すると本文一致検証が `ITEM-EXTRA` を出すため、集約が唯一の正解。2 行のファイルになっても設計適合。
- **共有ヘルパが本番項目と同名のときはグロブ import が衝突する**（タスク 3.3 で実測・`verification/notes.md` §17.5）。テストモジュールが本番項目を影付け（shadow）するブリッジヘルパを持っていた場合、それを `test_support` へ出すと `use super::*;` と `use super::test_support::*;` が両方その名前を供給して **E0659（曖昧）** になる。**共有ヘルパは明示 import で受けること**（明示 import はグロブより優先されるので影付けの解決順が移設前と一致する）。実例: `areka-sakura/src/compile.rs` の 1 引数 `compile` ブリッジ（本番 `compile` は 2 引数）。**引数の数が違えば誤結合はコンパイルエラーになるので気づけるが、同一シグネチャなら黙って別の関数を呼ぶ**——`areka`・`areka-emo-text`・`areka-kanade` は同名ヘルパを持つ可能性が高いので、移設前後で各呼び出し箇所の結合先が同じかを必ず確認すること。
- **⚠ リストのハッシュは必ず `[string[]]` へ型付けしてから序数整列する**——`$arr = [string[]]@(… | Where-Object …)` の**型注釈を省くと `[Array]::Sort(…, StringComparer::Ordinal)` が黙ってカルチャ順に落ちる**（パイプライン出力の要素は `PSObject` に包まれており、序数比較器の内部キャストが失敗して既定比較器へフォールバックする。`GetType()` は `System.String` を返すので目視では気づけない）。この取り違えは**すでに 3 通りの経路で起きている**——タスク 2.2 §14.5(b) と 3.4 §18.4(c) は素の `Sort-Object`、3.5 のレビューは型付け漏れ。3.4 では**実装者とレビュアーが揃って同じ誤りをしたため相互検証をすり抜けた**。判定自体は行単位の多重集合突合で整列順に依存しないので**成果物は無傷**だが、記録値が第三者に再現できない。**較正はコミット済み `before_default.txt` のハッシュ一致では不十分**（既に整列済みのファイルを読むだけでは整列器が動かない）——**未整列の生出力を序数と `Sort-Object` の 2 通りに整列し、digest が割れることを確認**してから値を載せること。逐語の手順は `verification/notes.md` §10.2 手順 3。
