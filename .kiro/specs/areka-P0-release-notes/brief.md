# Brief: areka-P0-release-notes

> 2026-10-11 `/kiro-discovery` で起票（開発者指示「リリース（https://github.com/ekicyou/areka/releases ）を読んでみたが、修正点の記載が多すぎて目に入ってこなかった。詳細なリリースノートに関して、Assets にドキュメントを入れてほしい。そのうえで、リリース文では特に注目に値するいくつかの内容について、日本語で紹介するようにしてほしい。spec 名は不要。」）。roadmap「テーマ別の決めごと」の「リリースノート」。本文のソースの指し先は起票時（main `09f4e33f`）の実測＝着手時に引き直すこと。

## Problem

GitHub のリリースの頁を読む人（areka を使う人・ゴーストを作る人・開発者自身）が、その版で何が変わったのかを読み取れない。

- `v0.0.2` の本文は、GitHub が自動で作った PR の題名の一覧がそのまま載っている。263 行・34,525 字。
- 題名は開発の中の呼び名（spec の名前）と開発の文書の直しを含み、使う人に関わる変更と関わらない変更が同じ重さで並ぶ。
- どれが注目に値するのかを示す文が 1 行も無い。

## Current State

- リリースを作るのは `.github/workflows/release.yml`。段「Release を公開」が `gh release create v{版}` に 4 つのファイル（x64 と arm64 の zip と、それぞれの `.sha256`）を渡し、本文は `--generate-notes`（一つ前のタグが在れば `--notes-start-tag`）で GitHub に作らせている。
- リリースに添えているファイル（Assets）は上の 4 つだけ。変更点の文書は無い。
- 一つ前のタグは同じ workflow の段「既存の Release の検査」が決めている（`Get-PrevTag`・結果は `prev_tag`）。
- リリースを打つ手順は繰り返し spec `areka-P0-release-cycle`。版上げの PR に載せてよいファイルを要件 3.3・4.2 で数え上げており、紹介文を書く段は無い。公開の後の確かめは「4 つのファイルが添わっていること」（要件 6.1）。workflow のファイルは書き換えない（要件 1.6）。
- 次の版（`v0.0.3`）に入る変更は、起票時で 35 本（題名の頭の種類で、機能 15・直し 3・性能 1・文書 15・雑務 1）。自動の一覧のままだと、半分近くが開発の文書の直しになる。
- 公開済みは `v0.0.2` の 1 版だけ（2026-10-06）。

## Desired Outcome

1. リリースの本文は、その版で特に注目に値する変更を数件、使う人に向けた日本語で紹介する短い文になる。spec の名前と開発の中の呼び名は出さない。
2. 変更点の全部を載せた詳細なリリースノートが、1 つのファイルとしてリリースの Assets に添わる。本文からそのファイルへたどれる。
3. これが毎回のリリースで、開発者の手作業を増やさずに回る。紹介文は `release-cycle` の中で AI が下書きし、開発者は版上げの PR で読んで承認する。
4. 公開済みの `v0.0.2` の頁も同じ形に直る（推し・要件の段で決める）。

## Approach

**紹介文はリポジトリの中の版ごとのファイル、詳細は workflow が作って添える**（推し・要件の段で覆してよい）。

- **紹介文**: 版ごとに 1 つのファイルをリポジトリに置く（置き場所と名前は設計で決める。例 `doc/release-notes/v{版}.md`）。`release-cycle` の版上げの段で、一つ前のタグからの変更を材料に AI が下書きし、版上げの PR に載せる。`release.yml` は `--generate-notes` をやめ、このファイルを本文として渡す（`--notes-file`）。
- **詳細**: `release.yml` が、今と同じ範囲（一つ前のタグからその版まで）の変更の一覧を GitHub から取り、1 つのファイルにして 5 つ目の Assets として添える。一覧は種類（新しい機能・直し・そのほか）で分け、題名からは spec の名前のかっこを落とす（どこまで整えるかは要件の段で決める）。
- **欠けたときの止め方**: 紹介文のファイルが無い・空のときは、`release-cycle` が版上げの PR を出す前に止まり、`release.yml` もビルドの前の段で止まる。タグは打った後に動かせないので、公開の段まで行ってから気付く形にしない。
- **乾いた走り**: main で手で起こす走り（公開しない）でも、本文と詳細のファイルを作るところまで回し、中身を走りの記録で読めるようにする。タグを打つ前に見た目を確かめられる。

**採らなかった案**

- 根に `CHANGELOG.md` を置き、各 spec の PR が 1 行ずつ足す — 同時に 8 本まで走る枝が同じファイルの同じ場所を取り合う。完了の手順も重くなる。変更の一覧は PR の題名から機械で作れる。
- 変更履歴を作る専用の道具（git-cliff など）を CI に足す — 道具が増える。PR の題名は既に種類を名乗っており、`gh` と PowerShell の数行で足りる。
- 自動の一覧を本文に残したまま折りたたむ — Assets に文書が欲しいという求めに合わない。本文が長いままになる。
- 紹介文を workflow の中で AI に書かせる — 公開の前に開発者が読めない。CI に鍵と費用が要る。

## Scope

- **In**:
  - 紹介文のファイルの形（置き場所・名前・何件くらい書くか・書いてよい語と書かない語・詳細への案内の 1 行）。
  - `release.yml` の直し: 本文を紹介文のファイルから渡す／詳細のファイルを作る段／5 つ目の Assets として添える／紹介文の有無の検査をビルドの前に置く／乾いた走りで中身を見せる。
  - `release-cycle` の要件・設計・タスクの直し: 紹介文を下書きして版上げの PR に載せる段を足す（要件 3.3・4.2 の数え上げ）、公開の後の確かめを 5 つのファイルにする（要件 6.1）、版上げの PR の説明に紹介文を読む旨を足す。
  - 公開済みの `v0.0.2` の頁の直し（紹介文を書いて本文を差し替え、詳細のファイルを添える。zip とタグには触らない）— 推し・要件の段で決める。
- **Out**:
  - 英語の本文。
  - リポジトリに通しの変更履歴（`CHANGELOG.md`）を持つこと。
  - PR の題名の付け方・ラベルの決まりを変えること。
  - zip の中身と説明書 `dist/README.txt`（詳細のファイルは zip に入れない）。
  - winget のマニフェストの変更点の欄（`winget-release-automation` の側）。crates.io。

## Boundary Candidates

- 紹介文のファイルの決まり（人と AI が書く物）。
- 詳細のファイルを作る段（workflow が作る物・一つ前のタグからの一覧を取って整える）。
- 公開の段の入れ替えと、ビルドの前の検査、乾いた走りでの見せ方。
- `release-cycle` の文書の直し（繰り返しの手順に 1 段を足す）。
- `v0.0.2` の頁の直し（1 回きり）。

## Out of Boundary

- 紹介する件を選ぶ基準を機械で決めること（選ぶのは下書きする AI と、読んで承認する開発者）。
- 完了済み `areka-P0-release-ci-workflow` の文書の書き換え（完了済みは動かさない。公開の段の今の形は本 spec の設計に書き直す）。
- 署名の段（`release-code-signing`）・winget への PR（`winget-release-automation`）。

## Upstream / Downstream

- **Upstream**: 完了 `areka-P0-release-ci-workflow`（`release.yml`）。`areka-P0-release-cycle`（初回 `v0.0.2` は実施済み）。
- **Downstream**: `areka-P0-release-cycle` の次の回（`v0.0.3`）— 本 spec が先に着地していること。新しい公開の段が初めて本当に動くのはその回。`areka-P0-winget-release-automation` — リリースのファイルが 5 つになる（zip を拾う絞り込み `\.zip$` に詳細のファイルは当たらないことを同 spec で確かめる）。

## Existing Spec Touchpoints

- **Extends**: `areka-P0-release-cycle`（要件 3.3・4.2・6.1、設計の版上げの PR の節、タスクの「版を上げる」「見守る」）。同 spec は決まりを自分の文書の中に置く例外の spec なので、足す段は同 spec の文書に書く。
- **Adjacent**: `areka-P0-release-code-signing`（`release.yml` のビルドと zip の間に段を挟む＝同じファイルなので直列）。`areka-P0-winget-release-automation`（`workflow_run` で `release.yml` の終わりを受ける）。`areka-P0-mcp-stdio-bridge-residue`（次のリリースの走りの結果を待っている）。

## Constraints

- **タグは動かさない・同じ版で出し直さない**（`release-cycle` 要件 5.4・6.5）。紹介文が欠けたまま公開の段まで進むと版を 1 つ無駄にするので、検査は PR を出す前と、ビルドの前に置く。
- **`release.yml` の今の決まりを保つ**: 権限は `contents: write` だけ／段の入力は環境変数だけで、GitHub の式を段の本文に埋めない（手元で同じ本文を回せる）／タグの名前で Release を探す行は「既存の Release の検査」と「後始末」で 1 字違わず同じ／`gh` は下書きで作り、全部載せ終えてから公開する／段「4 つの確かめ」が見た同じファイルを公開の段へ渡す。
- **文字コード**: 紹介文と詳細は日本語の UTF-8。`gh` の出力を PowerShell で受けて整えるとき、端末の文字コードで解かない（読む側で UTF-8 として読む。端末の文字コードは変えない）。workflow が走りの記録へ出す自分の文は ASCII だけ。
- **道具を足さない**: `gh` と PowerShell 7 で作る。依存も CI の道具も増やさない。
- **言葉**: 本文と詳細は使う人が読む。spec の名前・開発の中の呼び名を出さない。平易な日本語で書く。
- **確かめ方**: workflow は手元で動かせない。静的な確かめ・段の本文を手元で回す確かめ・main での乾いた走り 1 回、の 3 つで判定する（`release-ci-workflow` と同じ形）。公開の段そのものは `release-cycle` の次の回まで動かないので、その残りを証跡に明記する。

## 要件の段で決めること（推しを添える）

1. **詳細のファイルをどこまで整えるか**: 推し＝種類ごとに日本語の見出しで分け、題名から spec の名前のかっこを落とし、開発の文書と雑務は末尾の「そのほか」へ寄せる（消さない）。各行に PR へのリンクは残す。
2. **`v0.0.2` の頁を直すか**: 推し＝直す。開発者が読みにくいと言ったのがこの頁。本文の差し替えとファイルの追加だけで、zip・ハッシュ・タグは変わらない（winget-pkgs の PR が見ているのは zip の URL とハッシュ）。
3. **紹介は何件・どこまで書くか**: 推し＝3〜7 件、1 件につき 1〜3 文。末尾に詳細のファイルへの案内を 1 行。入れ方や既知の制限は説明書に任せ、本文に繰り返さない。
4. **詳細のファイルの形式と名前**: 推し＝Markdown で `areka-{版}-release-notes.md`（zip と同じ名前の付け方）。
5. **紹介文に書く事実の裏取り**: 下書きの各件に、もとになった PR を版上げの PR の説明の側で対応づける（本文には出さない）。

## 想定

- 規模は XS〜S（タスク 5〜7）。ソースコード（`crates/`・`tools/`）は触らない。触るのは `.github/workflows/release.yml`・紹介文のファイル（`v0.0.2` の分）・`areka-P0-release-cycle` の文書。
- 段＝優先・区分 A（配布と公開・開発者が起票を頼んだ）。
- 着地は `release-cycle` の次の回（`v0.0.3`）より前。`v0.0.3` は `user-data-root` の着地を待っているので、それまでに間に合えばよい。
