## 1. 判定

**条件つき GO。**

- 作りは成り立つ。「descript にブレスは書けない」はコードで確かめた。役の持ち方は `shell-multi-compose` の暫定の設計とそろっている。上位の決定の中身を変える差し戻しは、見つからなかった。
- 条件は 3 つ。⑴ 設計が仮定で外した開発者の決定（利用者による差し替え・錠・席の要件・「演劇である」の印・`play` の種別・取得先の提示）を、開発者に諮る。⑵ SSP が descript の知らないキーをどう読むかを、正式の要件の前に実機で 1 回測る（フェーズ 1 は、同じ .nar を今の SSP で動かす）。⑶ 借りたシェルの「どの側か」（`sakura`／`kero`／`char N`）を、`shell-multi-compose` と合わせて決める。

## 2. 重大な問題

### この単位の中で閉じる物

**問題 1: 開発者の決定を、仮定で外している（A3・A4・A8）。**

- 何が: 設計は「作らない」として、次の 6 つを暫定の要件（2 章の表）と規模（10 章）から外した。`play` の種別・「演劇である」の印（A3）・席の要件・「この席は替えさせない」の錠・利用者による差し替え（A4）・未導入のときに取得先を示すこと（A8）。
- どこで決まっていたか:
  - `doc/ideas/novel-platform.md`「決めたこと」5: 「利用者による差し替えも同じ規則。演劇の作者が『この席は替えさせない』と錠をかける側は要件の段で。」
  - 同 6: 「足りない分（ライセンス・支援先・シェルの role・『借りないで』・『演劇である』・席の要件）だけを areka の独自キーとして descript.txt に足す。」
  - 同 4: 「インストールの種別は、当面 `type,ghost` に『演劇である』印を足す見立て。新しい種別にするかは依頼書の『起動の形』と突き合わせて決める。」
  - brief の Desired Outcome: 「ゴースト・シェル・バルーン・演劇を、素材 ID（`種別:id`）で指せる。」「当たらなければ既定へ戻し、『未導入』と記録して、取得先があれば示す。」
  - roadmap の受け口（1726 行）: 「演劇のパッケージ（M2）: 種別（`type,ghost`＋印か、`/play/` の置き場か）は依頼書の『起動の形』で決める。」
- 設計の理由と、その強さ:
  - 「`/play/` の置き場を作らない」は、取り決めの brief「配布はゴースト（`.nar`）のまま」で裏が取れる。ここは妥当。
  - 「印を作らない」の理由は「読む側が居ない」。骨子 2.1（「ふつうのゴーストの途中から始められる」）と、取り決めの原則（「取り決めに…『演劇』…という言葉を入れない」）から、ベースウェアの実行時には読み手が居ない。けれど、実行時の外の読み手は残っている（`areka-usage-stats` の「演劇の信号」・roadmap の M3 の検査）。決める持ち主は、この単位でなく、演劇のパッケージの受け口である。設計の 6 章が `areka-usage-stats` へ「種別は 3 つ」と言い切るのは、持ち分を越えている。
  - 「席の要件・錠・利用者による差し替えを作らない」の理由は「使う側が骨子・取り決めに居ない」。利用者による差し替えは、ベースウェアだけで閉じる機能で、pasta との取り決めに出てこないのが当たり前である。骨子に居ないことは、外す理由にならない。pasta の `novel-areka-contract` のフォルダを「差し替え」「借り」で grep して、これを取り下げた決定は見つからなかった。出どころは、areka の側の見立て（`areka-novel-rollback-cast-nar-2026-11-19.md` 77 行「『演劇である』の印は、舞台の定義が在ること、で足りる」）で、開発者の言葉ではない。
- なぜ困るか: 正式の要件定義が、この暫定の設計を手本にすると、開発者の決定が黙って消える。規模の見立て（16〜21）も、戻すと 20 を超える（設計の 8 章の問い 5 は +3〜4 と書く）。
- 設計が隠したわけではない。8 章の問い 4・5 と 9 章の末尾に書いてある。足りないのは、「開発者の決定とぶつかる仮定である」という印と、A8 が brief の Desired Outcome を外していることの明記である。
- 直す向き: 「作らない」を「この暫定では形を置かない。開発者に諮る」に改める。素材 ID の種別の語 `play` は、予約の語として残す（後から足すと、U1 が写した規則が変わる）。

**問題 2: `accept` の無い `type,shell` を `free-shell\` へ入れる読み（A9）が、完了 spec の要件を改める。その記載が無く、ふつうのゴーストの世界の帰結も書いていない。**

- 何が: 設計の 4.3・4.7・A9。
- どこで: 今は失敗である（`crates/areka/src/install/judge.rs:40-48`・`procedure.rs:219-231`、理由は `invalid type`）。これは完了 `areka-P0-ghost-install` の要件 3.6（requirements.md 168 行）と要件 12.9（319 行）「暫定の確定 9: `accept` の無い `shell`／`supplement` を失敗とする。理由: 正典は『必ず用いる』と書く。名指しの無い物を起動中のゴーストへ入れない。」で決めた動きである。完了 `install-before-boot` の requirements.md 33 行にも同じ表が在る。設計が「改める完了 spec」に挙げたのは `baseware-root-layout` の要件 2.9 だけである。
- なぜ困るか: `accept` を書き忘れた、SSP 向けの追加シェルの書庫は、今は「失敗」と知らされる。設計の形では「成功」になり、`free-shell\` に入る。`free-shell\` を探すのは舞台の定義の引き当てだけなので、どのふつうのゴーストのシェルの切り替えのメニューにも出ない。「入ったのに使えない」になる。設計の 4.7 は「失敗でなく `free-shell\` へ入る」とだけ書く。
- 直す向き: 開発者に諮る（設計の問い 6 を上げる）。選ぶ道は 2 つ。⑴ この読みのまま進め、改める完了 spec の一覧に `ghost-install` の 3.6・12.9 と `doc/COMPAT_ARCHITECTURE.md` §8 を足し、入れた先が単体の置き場であることを入れた後の知らせで伝える。⑵ 単体のフリーシェルの印を別に持ち、印の無い物は今の失敗のままにする。`install-package-type` の種別の決め方と、同じ段で突き合わせる（その brief の 78 行の申し送り）。

**問題 3: 作者のページの枠（メニューの 13 個目）は、持ち分としては妥当だが、置く時期が開発者の方針と合うかを諮る要が在る。**

- 何が: 設計の 4.3（`Frame` と `Frame::ORDER` が 13 になる）・A11・問い 9。
- どこで: `crates/areka/src/menu/mod.rs:49-93`。枠は 12 個で、コメントは「宣言順がそのまま並び順（①〜⑫・要件 2.1）」。完了したメニューの spec の要件である。
- 見立て: 案内の入口は brief の Scope In（「作者の配布の場所・支援先への案内」）と Boundary Candidates（「案内の入口（メニュー・About）」）に在るので、この単位の持ち分である。ふつうのゴーストでも `craftmanurl` が在れば枠が出る、という変化も、brief の Desired Outcome（「メニューや About から…案内できる」）の内である。ただし、設計自身が A11 で「メニューの作り直しは windows-reactor 待ち」と書く。今の Win32 のメニューに枠を足すと、作り直しで捨てる仕事になる。
- 直す向き: 目録の欄（R10）は先に作る。枠（R11）は、「今のメニューに足す」か「作り直しを待つ」かを開発者に諮る。足すなら、改める完了 spec の一覧にメニューの要件 2.1 を足す。

### 単位をまたぐ物

**問題 4: 借りたシェルの「どの側か」が、どちらの設計にも無い。**

- 何が: ゴーストのシェルは、1 つのフォルダに 2 人ぶん（と 3 人目から）の絵と宣言を持つ。着せ替えの既定は、スコープ番号を鍵にして読む（`crates/areka-parsers/src/package/model.rs:44-49`「鍵はスコープ番号（0＝`sakura.*`・1＝`kero.*`・2 以上＝`char{N}.*`）」・`resolve_bind.rs:163-164`）。
- どこで: この設計の舞台の定義は `areka.stage.actor*,並びの名前,素材 ID…` で、側の欄が無い（4.2）。`shell-multi-compose` の暫定の設計は、舞台のアクターの鍵を `STAGE_SCOPE_BASE + 連番` にする（その 4.2）。シェルの中の番号（0／1／N）とのつながりが切れる。`shell-multi-compose` の暫定の設計を `sakura\.|kero\.|char\d|相方` で grep して、当たったのは Reference3 の引用の 1 行だけだった。
- なぜ困るか: 設計の例 `areka.stage.actor0,さくら,shell:sakura_ghost/master` で、借りた役者が、着せ替えの既定・最初のサーフェス・`sakura.balloon.*` を、`sakura` の側で読むのか `kero` の側で読むのかが決まらない。同じシェルから 2 人（さくらとうにゅう）を借りる形も書けない。
- 直す向き: 舞台の定義の行に、側の欄を足す（この単位）か、`shell-multi-compose` が「借りた役者は、いつも `sakura` の側」と決めるか。どちらにしても、取り決めの文書の「並びの名前からシェルを決める決まり」（設計の 9 章の 2）に、側を足す。借りたフォルダの着せ替えの宣言を読む口（`read_bindgroup_defaults` は `pub(super)` で、`ghost_root\shell\<名>` からしか呼ばれない・`resolve_shell.rs:180-192`）を、どちらが開けるかも、同じ所で決める。

**問題 5: SSP が descript の知らないキーを読み飛ばすこと（A10）は、フェーズ 1 の前提である。**

- 何が: 設計は A10 を「この単位でいちばん危ない仮定」と書く。その通りで、効く範囲は、この単位より広い。
- どこで: 取り決めの brief「フェーズ」: 「同じ台本を、SSP でも areka でも動かす。」同「舞台の窓と箱」: 「配布はゴースト（`.nar`）のまま。」「席の名前と位置の対応は、舞台の定義（`descript.txt` の areka の独自キー）に書く。」つまり、舞台の定義を書いた `ghost\master\descript.txt` と、役を書いたシェルの descript を、今の SSP が必ず読む。
- ukadoc の引き直し（5 章の表）: 知らないキーの扱いを書いた文は、無い。
- 直す向き: 正式の要件の前に、SSP の実機で 1 回測る（descript に `areka.role,background` と `areka.stage.seat0,窓際,1400,1080` を足したゴーストを SSP で起こし、起動・シェルの切り替えのメニュー・記録を見る）。崩れたら、設計の 9 章の 3 の通り、「舞台の定義を descript.txt に書く」が上位の決定への差し戻しになる。

**問題 6: 並びの名前の引き当ての 2 段目が、設計の自分の理由と食い違う。**

- 何が: 設計の 4.4 は、借り物を舞台の定義に限る理由を「台本の再生の途中に UI スレッドで（走査を）しない」と書く。同じ 4.4 の 2 段目は、舞台の定義に無い名前を、並びの命令が来た時に、同梱のシェルの `name` → フォルダ名で探す。
- どこで: 候補を作る `shell_candidates`（`crates/areka-runtime/src/shell_balloon_resolve.rs:91-105`）は、`list_shells` と `list_all_shells` を呼び、`shell\` の下の全フォルダの descript を 2 回読む（`crates/areka-ghost/src/catalog.rs:194-207`）。
- なぜ困るか: `shell-multi-compose` の暫定の設計は、読み込みを UI スレッドの外で行う（その 4.5）。引き当てもそこで行うなら困らない。けれど、どちらの設計にも「どのスレッドで引くか」の文が無い。
- 直す向き: 同梱のシェルの `name` の表も、起こした時に作る（引き当ての表を 1 つにする）。または、「引き当ては、シェルの読み込みと同じ、UI スレッドの外の仕事で行う」と 2 つの設計に 1 行ずつ書く。

## 5. 確かめてほしいと言われた 5 つの答え
