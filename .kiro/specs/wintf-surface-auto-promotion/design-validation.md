# 設計の検証: wintf-surface-auto-promotion

> 2026-11-16 `/kiro-validate-design`（対話なし・`/kiro-design` の中の段）。対象は `design.md`（コミット `b69498f9`）。要件・研究・steering と wintf のコードを照らした。

## 設計の検証のまとめ

設計は、純粋な規則（`promotion.rs`）・形の見分け（`promotion_shape.rs`）・置き場（`placement.rs`）を ECS の係から切り離し、係の登録を変えずに今の 6 つの係の中で呼ぶ形で、要件 1〜9 の全部の項に部品と流れが割り当たっている。コードと照らした主張はおおむね正しい。ただし、自動で上げてよい形の「収まり」の判定と描画面の大きさの決め方の組み合わせで、ふつうの部品がほとんど上がらなくなるおそれがある。この点は討議で直す。

## 重大な問題（3 件）

🔴 **重大な問題 1**: 収まりの判定ににじみの余白を足すと、ふつうの部品が上がらない
**懸念**: 見分けの 7 は、部分木の描く範囲を外向きに丸めて、にじみの余白（最近傍の補間でなければ `ceil(2 × 拡大)`・`diff.rs` の `item_bounds`）を足し、それが自分の描画面 `[0, own_px)` に収まるかを見る。ところが自分の描画面は持ち主の `GlobalArrangement.bounds` に右と下へ 1 ピクセル足しただけの大きさで、原点は持ち主の位置の切り捨て。持ち主の配置いっぱいに中身を描く部品（まばたきのコマ・動く絵）は、左と上で余白ぶん（2〜3 ピクセル）はみ出し、必ず `OutOfBounds` で見送られる。
**影響**: 自動の昇格がほとんど起きず、要件 1.1 の効きが出ない。WARP のテストも、余白の無い特別な形でしか上げた形を作れなくなる。
**提案**: 自動で上げた持ち主の描画面の矩形を、部分木の描く範囲（外向きに丸め・余白込み・親の描画面と祖先の矩形の切り抜きで切ったもの）から決め、原点をその矩形の左上の整数の物理ピクセルに置く（`surface.rs` の AutoSurfacePad を「1 ピクセル足す」から「範囲で決める」に替える）。収まりの判定は親の描画面と祖先の矩形の切り抜きに対してだけ行う。
**根拠となる要件**: 1.1・2.3・2.7・3.2
**設計の該当箇所**: PromotionShape の Responsibilities（にじみの余白を足す）と見分けの 7・AutoSurfacePad・原点の決め

🔴 **重大な問題 2**: 2 段の切り替えは要件 3.1 の字面と合わない
**懸念**: 要件 3.1 は「上げる・戻すと判断したフレームのうちに描画面の有無を切り替える（1 フレーム遅らせて合わせない）」。設計の D1 は、回 N に Preparing と判断し、画面の切り替えは回 N+2（描画面ができた次の回）。どの回の画素も一致するので、見た目の遅れは無い。それでも、要件の「判断」をどれと読むか（Prepare か Activate か）は書かれていない。また、用意中の回は親と自分の 2 か所で部分木を描く。
**影響**: 承認済みの要件と設計のあいだで解釈が割れたまま、タスクとレビューに進む。開発者の方針（1 フレーム遅らせる解は取らない）に触れるかの見極めが、レビュー係ごとに揺れる。
**提案**: 討議で 2 段を確かめ、要件 3.1 の「判断した」を「切り替える答え（Activate／Demote）を出した」と書き直す（`design.md` の前提 A を要件へ写す）。あわせて用意中の回の 2 重の描画を研究の Risks から設計の本文へ移す。
**根拠となる要件**: 3.1
**設計の該当箇所**: Key Decisions の D1・System Flows の「上げ下げのフレーム」・前提と未決の 1（前提 A）

🔴 **重大な問題 3**: 切り抜きの鍵に NaN を入れて当て直させるのは、触らない約束を避けるための回避の形
**懸念**: ClipSync は、置き場の切り抜きを合わせた持ち主と自動の持ち主について、`ClipKey` の幅に NaN を入れて控える（NaN は等しくならないので、見る変化のたびに当て直す）。`components.rs` に触らないために、鍵の意味をずらしている。
**影響**: 鍵が「同じなら当て直さない」の約束を黙って破る。節の下の持ち主は祖先が動くたびに切り抜きを作り直し、後で鍵を読む人が NaN の意味を取り違える。開発者の方針（ウェーブの「触らない約束」を理由に回避の形へ逃げない）にも触れる。
**提案**: `ClipKey` に置き場の切り抜き（`PlacementClip`・自動かどうか）を足す。`components.rs` の `pub(crate)` の型を 1 つ広げるだけなので、触るファイルの一覧に `components.rs` を足し、同じウェーブの兄弟と照らして決める。
**根拠となる要件**: 4.8・4.5
**設計の該当箇所**: Components の ClipSync・File Structure Plan の「触らないファイル」

## 設計の強み

1. 判断の規則（`RuleState::step`）・形の見分け（`check_shape`）・WUC へ写す補助（`wuc_host_of`・`wuc_children_order`・`wuc_transform`・`merged_clip`）を、ECS に依らない純粋な関数に分けた。要件 8.1・8.2・8.4 の決定論のテストを GPU なしで書け、係は配線だけになる。
2. 自動で上げた持ち主を「親の走査の列の連続した部分」として描く形にした。世界の行列は手動の持ち主からの DIP の 1 つに保たれ、持ち主自身の不透明度の層・切り抜き・変形も節のときと同じ D2D の命令で描く。そのため画素の一致（要件 3.2）が作りの上で成り立ち、WUC には整数の位置だけを写せばよい。

## 最終の判定

**判定: GO**（条件つき）

**理由**: 境界・依存の向き・係の順は今の作りと合い、要件の全部の項に割り当てがある。重大な問題 1〜3 は、どれも設計の一部を直せば済み（描画面の矩形の決め方・要件 3.1 の書き直し・`ClipKey` の足し）、作りの骨格は変わらない。

**次の手順**:
- 設計の討議（`/kiro-design-discussion`）で、重大な問題 1〜3 と、`design.md` の「前提と未決」A〜H（特に前提 B「前順で後の手動の持ち主との重なりも上げない」は要件 2.3 の例と違う形なので、開発者の確認が要る）を議題にする。
- 討議で直した後に `/kiro-spec-tasks wintf-surface-auto-promotion` へ進む。

## 補足（重大でない気付き）

- 見えない自動の持ち主を戻す照らし合わせ（「相が Node でない実体を全部の根を回した後に照らす」）は、`AutoPromotion` が全部の節に在るので、問い合わせで全部の節を歩くと要件 1.9 に触れる。自動の持ち主の集まりを係の `Local` に控えて照らすのがよい。
- 自分の子孫が持ち主の配置の外へはみ出す部品（影・はみ出す飾り）も、今の形では見分けの 7 で必ず見送られる。問題 1 の直しで描画面の矩形を部分木の範囲から決めれば、この形も上げられる。
