# 設計ディスカッション — Kiro Spec Design Discussion

設計（design.md）および設計分析レポートの完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集し、分類に応じて自動修正を行い、開発者確認の議題は推奨案付きで一括提示して、一括承認または指定された議題だけの個別ディスカッションで確定する。

## 前提条件

- `.kiro/specs/{feature}/design.md` が生成済み
- `.kiro/specs/{feature}/requirements.md` が生成済み（要件との整合確認用）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の正本）
3. `.kiro/specs/{feature}/design.md` を全文読み込み
4. `.kiro/specs/{feature}/requirements.md` を全文読み込み（要件との整合確認用）
5. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合、設計判断の解決確認用）
6. `.kiro/specs/{feature}/research.md` を全文読み込み（存在する場合、調査結果の反映確認用）
7. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）

### Phase 2: イシュー収集

design.md を中心に、関連ドキュメントとの整合性も含めて精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 設計内の矛盾、要件との不整合、gap-analysis の設計判断との齟齬
- **曖昧性**: what/why/how が不明確な設計、複数の解釈が可能な記述
- **要件カバレッジ**: requirements.md の要件・受入基準が設計で未対応
- **インターフェース不備**: コンポーネント間の契約・型・引数が不明確
- **過剰**: 要件スコープ外の設計、YAGNI 違反
- **テスト困難**: 設計上テストが困難な構造
- **リスク**: 未解決のリスク、gap-analysis で指摘されたリスクの設計側カバレッジ不足
- **設計判断未解決**: gap-analysis の設計判断項目が design.md で未解決のまま残っている

### Phase 3: イシュー分類

収集したイシューを以下の2カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・明らかな不整合・記述漏れなど、開発者確認不要 | 即座に修正してコミット |
| **B: 開発者確認** | what/why/how が曖昧、ドメイン知識依存、トレードオフ判断が必要 | 推奨案付きで一括提示 |

### Phase 4: 自明な修正の実行（カテゴリ A）

1. 修正内容を修正前→修正後の形で控える（Phase 5 の課題一覧で報告する）
2. design.md を更新
3. requirements.md に影響がある場合はそちらも更新
4. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in design`）

### Phase 5: 仕様の目的と議案一覧の一括提示

開発者は spec 名や設計の見出しを見ただけでは目的が分からないことが多い。カテゴリ A を処理し終えたら、**最初のメッセージ**で仕様の目的と議案のすべてを一度に提示する（イシューが 0 件でも仕様の目的は省かない）。

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。spec 名・要件番号・内部の符牒は使わず、専門用語は初めて出てきたときに一言説明を添える（設定ファイルの構造は ukadoc の用語で）
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコード、インターフェースのシグネチャ、データ構造の例など）
- コード例はインターフェース・使用イメージ・データ構造の説明に使う。実装本体の詳細には踏み込まず、アーキテクチャとインターフェースに集中する
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:
```
## 仕様の目的
**一言で**: 誰の・何が困っていて、終わると何ができるようになるか（2〜3 文）
**なぜ必要か**: brief.md の動機と、roadmap 上の位置（何の後・何の前か）を短く
**具体例**: 終わった後の使われ方を、シナリオ・入出力例・コード例で
**やること・やらないこと**: 「要件 n: 一行の要約」の並びと、範囲外として明記されたもの
**設計のあらまし**: どこをどう変えるかを、主な部品 2〜5 個とその役割・つながりで（型名やファイル名の羅列にしない）

## 課題一覧
### カテゴリA（自明な修正・修正済み）
- 修正前 → 修正後（n 件）
### 議案一覧（n 件）
#### 議題 1: タイトル
- **何を決めるか**: 対象の設計セクション・コンポーネントと、決まらないと何が困るか
- **現在の設計**: design.md が今どう書いているか（引用付き）
- **具体例**: シグネチャ・データ構造・使用イメージのコード
- **推奨案**: … — 根拠
- **他の選択肢とトレードオフ**: …
#### 議題 2: …

**ご判断ください**
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
```

**提示前のチェックリスト**:
- [ ] 仕様書の文言のコピペでなく、平易な言葉で書いたか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか
- [ ] 1 画面〜数画面で読める長さに収めたか

開発者確認が必要な議題（カテゴリ B）が 0 件のときは、仕様の目的と課題一覧を報告してから Phase 7 に進む。

### Phase 6: 開発者の回答に応じた確定

#### 6a. 一括承認された場合
1. 全議題を推奨案で確定し、design.md に反映する（必要に応じて requirements.md も更新し、決定の根拠を research.md に追記する）
2. 1 回のコミットにまとめる（コミットメッセージ: `docs({feature}): 全設計議題を推奨案で確定`）
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 6b. 特定の議題について議論を指定された場合
1. 指定されなかった議題を推奨案で確定して design.md に反映し（必要に応じて research.md に根拠を追記）、コミットする（コミットメッセージ: `docs({feature}): 設計議題{X,Y} を推奨案で確定`）。確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で詳細を提示する：

```
## 議題 M（残り K 件）: タイトル
- **対象**: どの設計セクション・コンポーネントに関わるか（引用付き）
- **何を決めるか**: 何が曖昧・不明確か
- **背景**: なぜ決める必要があるか（仕様の目的のどこに関わり、決まらないと何が困るか）
- **影響範囲**: 結論によって変わる部品・インターフェース・後続のタスク
- **現在の設計**: design.md が今どう書いているか
- **具体例**: 選択肢ごとの違いが見えるシグネチャ・データ構造・使用イメージのコード
- **推奨案**: … — 根拠
- **他の選択肢**: 考えられる設計方針や代替案とトレードオフ
- **質問**: 開発者に決めてほしいこと
```

3. 開発者の回答を受けて：
   1. design.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて requirements.md も更新）
   2. 変更をコミット（コミットメッセージ: `docs({feature}): resolve design discussion #{n} - {topic}`）
   3. **修正内容の要約**を報告し、「議題 M 完了 ✓」と残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（個別議題の完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 7: 完了報告

すべての議題が確定したら：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（開発者確認）: {n}件 確定済み（推奨案で確定: X 件 / 個別議論で確定: Y 件）
2. 次のステップを案内：
   - 「設計の精査が完了しました。次のコマンドでタスク分解に進めます: `/kiro-spec-tasks {feature} [-y]`」

## エラーハンドリング

- **design.md 未生成**: 「先に `/kiro-design {feature}` を実行してください」と案内して停止
- **requirements.md 未生成**: 警告を出しつつ design.md のみで続行
- **イシューなし**: Phase 5 の「仕様の目的」を出した後に「精査の結果、修正すべき点は見つかりませんでした。タスク分解に進めます」と即座に案内

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 一括承認: `docs({feature}): 全設計議題を推奨案で確定`（1コミット）
- 指定外議題の確定: `docs({feature}): 設計議題{X,Y} を推奨案で確定`（1コミット）
- 個別議題クローズ: `docs({feature}): resolve design discussion #{n} - {topic}`（議論した議題ごとに個別コミット）

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- コード例はインターフェース・使用イメージ・データ構造の説明に使う。実装本体の詳細には踏み込まず、アーキテクチャとインターフェースに集中する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
