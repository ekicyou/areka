# 要件ディスカッション — Kiro Spec Requirements Discussion

要件定義（requirements.md）およびギャップ分析（gap-analysis.md）の完了後に実行する精査・ディスカッションワークフロー。
修正点・疑問点・不安点をイシューとして収集し、分類に応じて自動修正・設計判断フラグ付けを行い、開発者確認の議題は推奨案付きで一括提示して、一括承認または指定された議題だけの個別ディスカッションで確定する。

## 前提条件

- `.kiro/specs/{feature}/requirements.md` が生成済み
- `.kiro/specs/{feature}/gap-analysis.md` が生成済み（推奨、なくても実行可能）
- ステアリングコンテキスト（`.kiro/steering/`）がロード可能

## ワークフロー

### Phase 1: コンテキストロード

1. `.kiro/specs/{feature}/spec.json` を読み、language と現在のフェーズを確認
2. `.kiro/specs/{feature}/brief.md` を全文読み込み（存在する場合。spec の動機・背景の正本）
3. `.kiro/specs/{feature}/requirements.md` を全文読み込み
4. `.kiro/specs/{feature}/gap-analysis.md` を全文読み込み（存在する場合）
5. `.kiro/steering/` 配下をすべて読み込み（product.md, tech.md, structure.md + カスタム）
6. `.kiro/settings/rules/ears-format.md` を読み込み（EARS形式検証用）

### Phase 2: イシュー収集

requirements.md と gap-analysis.md を精査し、以下の観点でイシューを網羅的に収集する：

**収集観点**:
- **矛盾・不整合**: 要件間の矛盾、ギャップ分析との不整合
- **曖昧性**: what/why が不明確な要件、複数の解釈が可能な記述
- **EARS形式違反**: 受入基準のEARS形式不備
- **欠落**: gap-analysis で指摘されているが requirements に未反映の項目
- **過剰**: 要件スコープ外の記述、実装詳細の混入
- **設計判断**: gap-analysis の設計判断項目（design decisions）の要件側への影響
- **テスト困難**: 検証が困難または不可能な受入基準
- **リスク**: gap-analysis で指摘されたリスクの要件側カバレッジ

### Phase 3: イシュー分類

収集したイシューを以下の3カテゴリに分類する：

| カテゴリ | 判定基準 | アクション |
|---------|---------|-----------|
| **A: 自明な修正** | 誤字・EARS形式修正・明らかな不整合など、開発者確認不要 | 即座に修正してコミット |
| **B: 設計判断** | how に関わる判断、アーキテクチャ選択、トレードオフ | 設計フェーズへ先送り（gap-analysis.md の設計判断セクションと統合） |
| **C: 開発者確認** | what/why が曖昧、ドメイン知識依存、優先度判断が必要 | 推奨案付きで一括提示 |

### Phase 4: 自明な修正の実行（カテゴリ A）

1. 修正内容を修正前→修正後の形で控える（Phase 6 の課題一覧で報告する）
2. requirements.md を更新
3. gap-analysis.md に影響がある場合はそちらも更新
4. 変更をコミット（コミットメッセージ: `docs({feature}): fix obvious issues in requirements`）

### Phase 5: 設計判断の整理（カテゴリ B）

1. 設計判断項目を一覧にまとめる（Phase 6 の課題一覧で報告する）
2. gap-analysis.md の設計判断セクションに未記載の項目があれば追記（新規ファイルは作らない）
3. 課題一覧では「これらは設計フェーズ（`/kiro-spec-design`）で解決します」と添える（議論の対象にしない）
4. 変更がある場合はコミット

### Phase 6: 仕様の目的と議案一覧の一括提示

開発者は spec 名や要件の見出しを見ただけでは目的が分からないことが多い。カテゴリ A・B を処理し終えたら、**最初のメッセージ**で仕様の目的と議案のすべてを一度に提示する（イシューが 0 件でも仕様の目的は省かない）。

**守るべき原則**:
- 仕様書の文言をそのままコピペせず、平易な言葉で言い換える。spec 名・要件番号・内部の符牒は使わず、専門用語は初めて出てきたときに一言説明を添える（設定ファイルの構造は ukadoc の用語で）
- 説明には必ず具体例かコードを付ける（シナリオ、入出力例、使用イメージのコード、さくらスクリプトや設定ファイルの断片など）
- どの議題にも必ず推奨案と根拠を示す。「どちらでもよい」で終わらせない

**出力テンプレート**:
```
## 仕様の目的
**一言で**: 誰の・何が困っていて、終わると何ができるようになるか（2〜3 文）
**なぜ必要か**: brief.md の動機と、roadmap 上の位置（何の後・何の前か）を短く
**具体例**: 終わった後の使われ方を、シナリオ・入出力例・コード例で
**やること・やらないこと**: 「要件 n: 一行の要約」の並びと、範囲外として明記されたもの

## 課題一覧
### カテゴリA（自明な修正・修正済み）
- 修正前 → 修正後（n 件）
### カテゴリB（設計フェーズに回す事項）
- 項目（n 件）— 設計フェーズ（`/kiro-spec-design`）で解決します
### 議案一覧（n 件）
#### 議題 1: タイトル
- **何を決めるか**: 対象の要件・受入基準（ID 付き）と、決まらないと何が困るか
- **具体例**: この議題が効いてくる場面の例やコード
- **推奨案**: … — 根拠
- **他の選択肢とトレードオフ**: …
#### 議題 2: …

**ご判断ください**
- 「承認」と答えれば、全議題を推奨案で確定します
- 「議題2と4を議論したい」のように答えれば、指定外の議題は推奨案で確定し、指定された議題だけを1つずつ議論します
```

**提示前のチェックリスト**:
- [ ] 仕様書の文言のコピペでなく、平易な言葉で書いたか
- [ ] 仕様の目的と各議題に、具体例かコードが付いているか
- [ ] 全議題に推奨案と根拠が付いているか
- [ ] 1 画面〜数画面で読める長さに収めたか

開発者確認が必要な議題（カテゴリ C）が 0 件のときは、仕様の目的と課題一覧を報告してから Phase 8 に進む。

### Phase 7: 開発者の回答に応じた確定

#### 7a. 一括承認された場合
1. 全議題を推奨案で確定し、requirements.md に反映する（必要に応じて gap-analysis.md も更新）
2. 1 回のコミットにまとめる（コミットメッセージ: `docs({feature}): 全議題を推奨案で確定`）
3. 一部の議題だけ結論を直接指定された場合（例:「議題3は他の選択肢で、残りは承認」）は、その議題は指定どおりに、それ以外は推奨案で確定する

#### 7b. 特定の議題について議論を指定された場合
1. 指定されなかった議題を推奨案で確定して requirements.md に反映し、コミットする（コミットメッセージ: `docs({feature}): 議題{X,Y} を推奨案で確定`）。確定した内容を報告する
2. 指定された議題のみ、1議題ずつ議論する。各議題は次の形で詳細を提示する：

```
## 議題 M（残り K 件）: タイトル
- **対象**: どの要件・受入基準に関わるか（ID 付き引用）
- **何を決めるか**: 何が曖昧・不明確か
- **背景**: なぜ決める必要があるか（仕様の目的のどこに関わり、決まらないと何が困るか）
- **影響範囲**: 結論によって変わる要件・後続の設計
- **具体例**: 選択肢ごとの違いが見える例やコード
- **推奨案**: … — 根拠
- **他の選択肢**: 考えられる解釈や方向性とトレードオフ
- **質問**: 開発者に決めてほしいこと
```

3. 開発者の回答を受けて：
   1. requirements.md を更新：議論で明らかになった点の記載、不要になった要件の集約・削除も実施（必要に応じて gap-analysis.md も更新）
   2. 変更をコミット（コミットメッセージ: `docs({feature}): resolve discussion #{n} - {topic}`）
   3. **修正内容の要約**を報告し、「議題 M 完了 ✓」と残り議題の**サマリーレポート**を提示してから次の議題へ

**サマリーレポート形式**（個別議題の完了後に表示）:
```
## 進捗サマリー
- 完了: {n}/{total} 議題
- 直前の解決: {topic} → {decision}
- 残り: {remaining_topics}
- 次の議題: {next_topic_preview}
```

### Phase 8: 完了報告

すべての議題が確定したら：

1. 最終サマリーを表示：
   - カテゴリA（自明修正）: {n}件 修正済み
   - カテゴリB（設計判断）: {n}件 設計フェーズへ
   - カテゴリC（開発者確認）: {n}件 確定済み（推奨案で確定: X 件 / 個別議論で確定: Y 件）
   - 設計フェーズへの申し送り: カテゴリB の項目を一覧で
2. 設計フェーズのモデルを推奨（**Fable 推奨**／**Opus で十分**のどちらか 1 つ＋根拠 1〜2 行）：
   - **Fable 推奨**: 設計に本質的な判断が残るとき — カテゴリB が重い（新しい境界・crate 間の責務分担・並行やスレッドの持ち方・時刻や順序の保証・プロトコルの形）、既存の型に倣えない新しい仕組み、複数の案から選ぶ分かれ目がある
   - **Opus で十分**: 既存の型に倣って埋めるだけのとき — カテゴリB が無いか軽い、触る範囲が 1 crate 内で狭い、先例の spec や実装がそのまま手本になる
   - 迷ったら Fable 推奨（設計の判断の質を下げない）
3. 次のステップを案内：
   - 「要件の精査が完了しました。次のコマンドで設計フェーズに進めます: `/kiro-spec-design {feature} [-y]`」（上のモデル推奨を併記）

## エラーハンドリング

- **requirements.md 未生成**: 「先に `/kiro-spec-requirements {feature}` を実行してください」と案内して停止
- **gap-analysis.md 未生成**: 警告を出しつつ requirements.md のみで続行（「ギャップ分析なしで精査します。`/kiro-validate-gap {feature}` の実行を推奨します」）
- **イシューなし**: Phase 6 の「仕様の目的」を出した後に「精査の結果、修正すべき点は見つかりませんでした。設計フェーズに進めます」と即座に案内

## コミット規約

- prefix: `docs({feature})`
- 自明修正は1コミットにまとめる
- 設計判断の追記は1コミットにまとめる
- 一括承認: `docs({feature}): 全議題を推奨案で確定`（1コミット）
- 指定外議題の確定: `docs({feature}): 議題{X,Y} を推奨案で確定`（1コミット）
- 個別議題クローズ: `docs({feature}): resolve discussion #{n} - {topic}`（議論した議題ごとに個別コミット）

## 注意事項

- 最初に仕様の目的を、具体例付きで説明する
- 議案は最初にまとめて提示し、全議題に推奨案を付ける
- 一括承認なら全議題を推奨案で確定する。議論の指定があれば、指定外は推奨案で確定し、指定議題だけを1つずつ議論する
- チャットで会話形式に進め、`AskUserQuestion` は使わない
