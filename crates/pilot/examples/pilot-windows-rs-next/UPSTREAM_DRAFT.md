## English body

> Draft only — not posted anywhere. All results below were measured on windows-rs master `f37e2f9046cf9710fe00285436c4d22ad6053d72` (2026-11-14), on Windows 11 x64 with a hardware GPU, on 2026-11-16..17. They may change once 0.101 is published.

We tried the 0.101 crates (`windows-bindgen`, `windows-core`, `windows-text`) inside a desktop-mascot app (areka) that today uses `windows` 0.62, by rebuilding a few real stages of the app in a throw-away pilot. The aim was to check each stage in a real app, as we said we would. Short version: every stage we tried went through; nothing blocked us. Details and the gaps we hit follow.

### Results confirmed in the real app, per stage

1. **Composition through `windows-bindgen` (no `windows-composition` crate).** DispatcherQueue → Compositor → DesktopWindowTarget → D2D device → composition graphics device → drawing surface → SpriteVisual all ran on a real window with bindings generated by `windows-bindgen` (default style). Every stage logged `ok`, exit code 0; the captured 256x256 window was fully magenta at 5 checked points (4 corners 4 px inside, plus the centre). What we had to learn:
   - Naming a WinRT class in the filter gives the type and `new()` but no methods; the class's default interface (`ICompositor`, `IVisual`, ...) must be named too. A missing name still builds, so it only shows up at the call site.
   - Interop entry points return interfaces (`ICompositionGraphicsDevice`, `IDesktopWindowTarget`, ...), so we `cast()` to the class (3 places).
   - Not a windows-rs issue, but worth noting for anyone testing this way: a process that is not DPI aware, on a 200% screen, places the window in logical coordinates while a screen-DC capture reads physical pixels. Every stage still logs `ok`; only the captured image is shifted. Declaring Per Monitor v2 awareness first fixed it.
2. **Vertical text with `windows-text`, compared pixel by pixel with our current renderer.** One vertical-rl column (`WritingMode::VerticalRightToLeft`, 20 px, `ja-JP`, uniform line spacing 20/10) was laid out with `windows-text` and drawn with our own D2D context through `as_interface::<IDWriteTextLayout>()` (borrowed, no QueryInterface, no raw pointers). We compared it with the same text drawn by our current `windows` 0.62 renderer, in the same process, on a 310x250 surface:

   | `windows-text` font features | differing pixels (same origin) | max difference | best shift (±8 px) | differing pixels at best shift |
   |---|---|---|---|---|
   | none | 651 | 255 | (0, 0) | 651 |
   | our 10 features (`ccmp locl mark mkmk rlig calt clig liga kern rclt`, value 1) | 0 | 0 | (0, 0) | 0 |

   With the same 10 features set through `set_font_features`, the output is byte-identical to our current renderer. The 0.62 and 0.101 COM types ran side by side in one process with no bridge between them (only read-back BGRA bytes crossed).
3. **Transparent balloon window with hit testing.** A vertical balloon (one text column with a colour emoji, plus two choice columns coloured by range) was drawn with our own D2D into a composition drawing surface on a real popup window (92x272). The colour emoji kept its colours (354 warm pixels) and the per-range colour survived composition (461 blue pixels). We then clicked each choice with `SendInput`; `hit_test_point` returned the expected UTF-8 range for both clicks (45..48 and 61..64), the click position matched the aimed pixel exactly, and both choices were identified correctly. `windows-text` layout and hit testing also worked on an ASTA thread created by DispatcherQueue.

### What windows-text lacks, and whether areka fills it itself or calls DirectWrite directly

Of the five gaps we expected (per-range colour, inline objects, letter spacing, tate-chu-yoko, per-character wrapping), only **per-range colour** was actually needed in this pilot. The other four were not needed by one column plus the balloon, so we did not test them and make no claim about them.

- **Per-range colour (hit).** There is no range-colour API. We borrowed the layout's `IDWriteTextLayout` via `as_interface` and called `SetDrawingEffect(solid red brush, DWRITE_TEXT_RANGE)`; D2D's `DrawTextLayout` picks the brush up. Measured: 299 red pixels (0 without the effect); black ink went from 731 to 432, i.e. exactly the 299 that turned red; no black inside the range and no red outside it. **Our plan: call DirectWrite directly** through the borrowed interface. This worked without friction, so it is a convenience request at most.
- **Looking up a font by its GDI name (hit, not in the list above).** Our font resolution falls back from family name to a GDI name (`CreateFontFromLOGFONT`). `windows-text` has no GDI-name lookup, so we called `IDWriteGdiInterop::CreateFontFromLOGFONT` from our own bindings. On this machine the candidate `游ゴシック Medium` was not found as a family name and resolved through the GDI name to `Yu Gothic`, weight 500. **Our plan: call DirectWrite directly.**
- **Font stretch (hit).** The text format fixes stretch to NORMAL, so a face whose stretch is not NORMAL cannot be matched; we skip such candidates. **Our plan: keep skipping for now**; a stretch parameter on the format would remove the gap.
- **Underline position (observation, not a gap).** `set_underline` + `decorations()` gave the underline rectangle in layout coordinates: x = -0.62..0.40, y = 120..180 (thickness about 1.02), while the column box is x = 0..20 — so DirectWrite places it on the **left** of a vertical-rl column, and the drawn ink matches that rectangle (61 pixels). This is the same side our current renderer uses for per-character font underlines. Our own rule for *choice* underlines is the right side of the column (our current renderer does not draw choice underlines yet). **Our plan: fill it ourselves** — use `decorations()` only to get the rectangle, mirror it inside the column box, and paint it with D2D (result x = 18.98..20.00). We are not asking for a change here.

### TextLayout::new panic

`windows-text` unwraps DirectWrite failures inside `TextLayout::new`. Checked with `catch_unwind`:

- layout box width NaN, width -1, or height NaN: `CreateTextLayout` fails with `E_INVALIDARG` (0x80070057) and `TextLayout::new` panics (`layout.rs:159`);
- a text format with font size NaN: panics in `CreateTextFormat`, which runs when the format is first used inside `TextLayout::new` (`format.rs:304`);
- width +infinity: no panic.

`TextFormat`'s doc comment already says that invalid settings panic on first use (`format.rs:108–113`), but `TextLayout::new`'s doc comment mentions negative sizes only, not NaN (`layout.rs:143–146`). On our side we will validate inputs before the call (font size positive and finite; box width and height not NaN and not negative; UTF-16 length fits in `u32`) and keep the call at one boundary. But some failures cannot be checked in advance (factory failure, out of memory), and in an app that must not crash, turning those into a panic is hard to handle well; catching the unwind at the boundary works but makes a panic the normal error path. **Wish:** a fallible constructor such as `TextLayout::try_new(...) -> windows_core::Result<TextLayout>` (and the same for the lazily created text format), with `new` kept as the panicking convenience. At minimum, `TextLayout::new`'s doc comment could also mention NaN.

### UTF-8 positions

There are three position units in play for us: our own positions (extended grapheme cluster index), `windows-text`'s UTF-8 byte offsets (`set_underline`, `range_bounds`, `hit_test_point`, ...), and DirectWrite's UTF-16 (`SetDrawingEffect` via the borrowed interface). We keep our cluster index as the source of truth and convert only at the call: cluster → byte for `windows-text`, cluster → UTF-16 for borrowed DirectWrite calls, byte → cluster for `hit_test_point` results. Cluster boundaries are always `char` boundaries, so we never hit the "not on a `char` boundary" panic. A test with an emoji fixes the split: cluster 10 = UTF-8 30..34 = UTF-16 10..12. The UTF-8 API itself is fine for us; the only friction is that mixing `windows-text` with borrowed DirectWrite calls needs both conversions.

### Opening-bracket position (as a confirmed result only)

Recorded as a result, not as a request (it will be reported separately). In vertical-rl, with no font features set, the opening corner bracket 「 is drawn 10 px higher than in our current renderer (ink y = 12..19 → y = 2..9). The shift is outside the ±8 px search and affects one glyph, so the best shift stays (0, 0) with 651 differing pixels; small kana ょ・っ also move up about 2..4 px. With our 10 features set, the bracket is in the same place (0 differing pixels in its cell, best shift (0, 0)). We did not check which of the default-on features causes this.

## 日本語の要旨

- どこにも投稿していない下書きである。出すのは開発者の承認の後。結果は windows-rs の master `f37e2f90`（2026-11-14）の上で 2026-11-16〜17 に測った物で、0.101 の公開の後に変わりうる。
- 実アプリで確かめた段: ⑴ `windows-bindgen` の既定の形の束縛で合成の全段（DispatcherQueue〜SpriteVisual）が実の窓で通った（全段が ok・終了コード 0・5 点がマゼンタ）。クラスの既定のインターフェースの名指しと相互運用の戻りの `cast` が要る。DPI を認識しない exe は 200% の画面で撮りがずれる（Per Monitor v2 で直る）。⑵ `windows-text` の縦書きの 1 列は、areka の 10 個の字形の指定で今の描き手とバイトまで同じ絵（違う画素 0）。指定無しでは 651 画素違う。新旧の COM の型は橋なしで同じ過程に並んだ。⑶ 透過の窓のバルーンで、カラー絵文字（暖色 354 画素）・範囲の色（青 461 画素）が出て、`SendInput` のクリック 2 つが `hit_test_point`（UTF-8 の 45..48・61..64）で狙いの選択肢に当たった。
- `windows-text` に無くて当たった物: 範囲の色だけ（借りた `IDWriteTextLayout::SetDrawingEffect` を直に呼んだ・赤 299 画素）。インラインオブジェクト・字送り・縦中横・文字単位の折り返しは要る所に当たらず、確かめていない。リストの外で当たった物は GDI の名前で書体を引く口（DirectWrite を直に呼んだ）と、書式の幅（stretch）が NORMAL に固定な所（その候補は飛ばす）。
- 下線: `decorations()` は列の左（x=-0.62..0.40）に出す。これは本線の今の字の下線（`underline.rs:8`）と同じ側。選択肢の下線を列の右に置くのは areka の正典の決まり（`draw.rs:36`）で、本線はまだ選択肢の下線を描いていない（`actor_decoration.rs:178-183`）。矩形を鏡に映して自前で塗る（x=18.98..20.00）。上流への頼みにはしない。
- `TextLayout::new` の panic: 箱の幅 NaN・-1・高さ NaN で `layout.rs:159`、字の大きさ NaN で `format.rs:304` が panic する（幅 +∞ は panic しない・`TextFormat` の注は不正な設定で panic すると既に書くが、`TextLayout::new` の注は負の大きさだけを書き NaN を書かない）。areka は入る前に値を確かめるが、確かめられない失敗が残るので `try_new`（`Result` を返す口）を望む、と書いた。
- UTF-8 の位置: areka の拡張書記素クラスタの序数を正本にし、`windows-text` へはバイト位置、借りた DirectWrite へは UTF-16 へ、渡す所でだけ換算する（絵文字でクラスタ 10＝UTF-8 30..34＝UTF-16 10..12）。
- 開き括弧の位置は確かめた結果としてだけ載せた（確定 7・開発者が上流へ別に報告する）: 字形の指定無しで 10 px 上がり（y=12..19 → 2..9）、areka の 10 個で今の側と同じ所に出る。
