# tools/perf — areka の性能を測って合否を出す道具一式

このフォルダには、areka を実際に動かして性能を測る道具と、測った結果から合否を機械的に
出す道具が入っています。**合否の判断に人の目視は使いません。** 人がやるのは「測ってよい
状態か」を確かめることと、出てきた結果を読むことだけです。

この文書だけを読めば計測を実行して結果を読めるように書いてあります。仕様書
（`.kiro/specs/areka-P0-recompose-budget/`）を読んでいなくても構いません。

| ファイル | 役割 |
|---|---|
| `invoke-perf-run.ps1` | areka を決まった時間だけ動かし、実行ログと CPU の推移を集める（採取） |
| `judge-perf.py` | 集めたものを集計し、あらかじめ決めた式で合否を出す（判定） |
| `fixtures/` | 判定の道具そのものが壊れていないか確かめるための、答えの分かっている入力 |
| `README.md` | この文書 |

対応する要件: 2.1・2.4・2.6・2.7・4.5・5.2、および設計の Key decision D7。

---

## 1. 早わかり

```powershell
# ① 測る（7 分。測定マシンが静かであることを自分で確かめてから -ConfirmQuiet を付ける）
pwsh -File tools/perf/invoke-perf-run.ps1 `
    -Profile short -Build release `
    -GhostRoot C:\絶対パス\emo2 `
    -OutDir C:\出力先\perf-001 `
    -ConfirmQuiet

# ② 中身を見る（合否は出さない。数字を並べるだけ）
python tools/perf/judge-perf.py C:\出力先\perf-001\run.log C:\出力先\perf-001\cpu.csv `
    --mode baseline

# ③ 合否を出す
python tools/perf/judge-perf.py C:\出力先\perf-001\run.log C:\出力先\perf-001\cpu.csv `
    --mode verdict --build release
```

判定の道具そのものを点検するときは次の 1 行です（測定は不要・数秒で終わります）。

```powershell
python tools/perf/judge-perf.py --selftest
```

`judge-perf.py` は Python 3 の標準ライブラリだけで動きます。追加インストールは要りません。
このフォルダは areka のビルドには関わりません（ビルドが通るかどうかとは無関係です）。

## 2. 測る前に — 測定マシンが静かであることの確認（要件 2.7）

`invoke-perf-run.ps1` は `-ConfirmQuiet` が付いていないと **起動しません**。

これは「測ってよい状態か」を人に確かめてもらうための関門です。並行して別の開発セッション・
ビルド・テスト・重いアプリが動いていると、集めた CPU の推移は areka の性能ではなく
マシンの混み具合を測ったものになり、そのあとの判定が丸ごと誤りになります。

測る前に、ご自身で次を確かめてください。

- 他の開発セッション（並行するビルドやテスト）が動いていないこと
- 重いアプリケーション（ブラウザの大量タブ・動画・仮想マシン等）を閉じたこと
- ウイルス対策ソフトの全体スキャンなど、定期処理が走っていないこと

確認できたら `-ConfirmQuiet` を付けて実行します。

**これは合否の判断に人の目を戻すものではありません。** 確かめているのは「測定条件」だけで、
測ったあとの合否は `judge-perf.py` が機械的に出します。人が数字を見て「まあ良さそう」と
決める余地はどこにもありません。

計測中はデスクトップにキャラクターが表示されます。計測は決めた時間で自動的に終わります
（画面を見ている必要はありません）。

起動せずに前提だけ確かめたいときは `-DryRun` を付けてください。areka を起動せずに、
パスや実行体の有無だけを検査して終わります（**測定にはなりません**）。

## 3. 2 つの水準と、その使い分け（要件 2.1・議題 4 裁定）

| 水準 | `-Profile` | 実走時間 | 使う場面 |
|---|---|---|---|
| 短時間 | `short` | 7 分 | **是正のたびの測り直し（中間ループ）はすべてこちら** |
| 長時間 | `long` | 25 分 | **最初のベースラインと、最後の合格判定の 2 回だけ** |

長時間水準は「20 分を超えて CPU が上がり続けないか」を見るためにあります。これは
最初と最後にだけ必要な問いなので、途中の測り直しで毎回 25 分を使うことはしません。

途中の測り直し（短時間水準）で見るのは、コマの間隔・取りこぼしの件数・新規確保の件数の
3 つです。CPU の数値目標は長時間水準の走行でしか結論を出しません。

`judge-perf.py` は `run-meta.txt` に書かれた水準（`profile`）を読みます。長時間水準として
始めた走行が途中で切れて 20 分に届かなかった場合、「短いから対象外」と黙って通すのではなく
**判定不能** にします。短い走行を「長時間の性質を確かめた」と読ませないためです。

## 4. 採取のしかた

```powershell
pwsh -File tools/perf/invoke-perf-run.ps1 `
    -Profile short|long `
    -Build dev|release `
    -GhostRoot <ゴースト一式のルート・絶対パス> `
    [-BalloonRoot <バルーンのルート・絶対パス>] `
    [-OutDir <出力先>] `
    -ConfirmQuiet
```

- **パスは必ず絶対パスで**。相対パスで起動すると SHIORI（`pasta.dll`）の読み込みに失敗します。
- `-GhostRoot` には、直下に `ghost\master\descript.txt` があるフォルダを指定します。
- `-BalloonRoot` を省略すると `<GhostRoot>\emo2-kakukaku` を補います。これは計測に使っている
  ゴースト emo2 に固有の値です。別のゴーストで測るときは明示してください。
- `-Build release` で測るには先に `cargo build -p areka --release` が要ります
  （`dev` なら `cargo build -p areka`）。
- `-OutDir` を省略すると `%LOCALAPPDATA%\areka-diag\perf-<日時>` に作られます。出力先は
  毎回まっさらな新規フォルダで、既に存在すると起動しません（過去の採取を上書きしません）。

採取が失敗した場合、作りかけの出力フォルダは `-FAILED` を付けた名前へ改名され、中に
`FAILED.txt`（失敗の理由）が置かれます。**この中身を測定結果として使ってはいけません。**

### 出てくるファイル

| ファイル | 中身 |
|---|---|
| `run.log` | areka の実行ログ（標準出力） |
| `run.stderr.log` | 標準エラー出力 |
| `cpu.csv` | CPU の推移（`timestamp,cpu_percent_1core`・15 秒ごと） |
| `run-meta.txt` | どのマシンでどう走らせたかの記録（起動する前に書き出されます） |

`judge-perf.py` に渡すのは `run.log` と `cpu.csv` の 2 つです。`run-meta.txt` は
`cpu.csv` と同じフォルダから自動で探します（別の場所にあるときは `--meta` で指定）。

## 5. 判定のしかた

```powershell
# 集計だけ（合否を出さない。数字の内訳を読むためのモード）
python tools/perf/judge-perf.py <run.log> <cpu.csv> --mode baseline

# 合否判定（--build の明示が必須）
python tools/perf/judge-perf.py <run.log> <cpu.csv> --mode verdict --build dev|release
```

合否判定で `--build` を必ず書かせているのは、どの判定式を当てるかがビルド種別で変わる
ためです（CPU の数値目標は `release` にだけ課します）。`run-meta.txt` から推測させると、
取り違えたまま静かに通ってしまいます。

出てくるレポートの先頭には、測定マシンの条件と使った較正値が必ず並びます（要件 4.5）。
これは「その数字がどの条件で、どの閾値と比べて出たのか」を、レポート 1 枚で追えるように
するためです。

## 6. 終了コード — **2 つの体系があります**

採取スクリプトと判定スクリプトは別の体系です。取り違えないでください。
（自動化して包む場合は、どちらのスクリプトの値かを必ず区別してください。）

### `invoke-perf-run.ps1`（採取）

| 値 | 意味 |
|---|---|
| 0 | 採取できた（`-DryRun` の検証完了を含む） |
| 1 | 実走の失敗（起動できない・異常終了・予定より早い終了・応答なし） |
| 2 | 静寂状態の確認がない（`-ConfirmQuiet` 欠落）＝起動拒否 |
| 3 | 引数・前提の不正（水準/ビルド種別の誤り・パス不正・出力先を作れない） |
| 4 | CPU の性能カウンタを取得できなかった |

### `judge-perf.py`（判定）

| 値 | 意味 |
|---|---|
| 0 | 合格 |
| 1 | 不合格 |
| 2 | 判定不能（観測がない・必要なログが欠けている・定常状態が空・データ不足） |
| 3 | 引数の誤り・ファイルを読めない |

**「判定不能（2）」は合格ではありません。** 測れていないという意味です。0 と 2 を
同じ扱いにすると、何も測っていない走行が合格として通ってしまいます。

**不合格（1）は判定不能（2）より優先します。** 判定式の 1 つが確定的に不合格で、別の
判定式が判定不能なら、総合は不合格です。直すべき欠陥が「測れなかった」の山に隠れないように
するためです。

## 7. 同じ手順で測り直す条件（要件 2.4）

是正の前後を比べるには、次がすべて同じでなければ比較になりません。

1. **同じゴースト**（`-GhostRoot` / `-BalloonRoot`）
2. **同じマシン**（`run-meta.txt` の `[マシン]` 節が一致すること）
3. **同じログ設定**（`RUST_LOG`。採取スクリプトが固定値を渡すので、手で上書きしないこと）
4. **同じ水準**（`-Profile`。短時間どうし・長時間どうしで比べる）
5. **同じ profile フォルダ**（下記）
6. **SHIORI ヘルパの有無が同じであること**（下記）

### 5 について — 窓の位置が前回の値を引き継ぎます

areka は前回の窓の位置を `run-meta.txt` の `areka_profile_dir` が指すフォルダに残します。
ここが違うと窓の初期位置が変わり、表示に関わる条件が変わります。測り直すときは前回と同じ
場所を使ってください（環境変数 `AREKA_PROFILE_DIR` で明示できます。省略時は実行体と同じ
フォルダの下の `profile\areka`）。

### 6 について — 発話の有無で別の条件になります

`run-meta.txt` の `shiori_helper_present` が `False` の走行は、32bit の SHIORI ヘルパが
無いために **実 SHIORI なしで動いた走行** です。キャラクターが喋らないので、喋る走行とは
別の条件です。この 2 つを並べて比べてはいけません。採取スクリプトは無いときに注意を
表示し、`run-meta.txt` にも記録します。

### 測り直しの流れ

```
① ベースライン（長時間水準・是正前）
        ↓
② 是正 → ③ 測り直し（短時間水準）→ 判定 → 直っていなければ ② へ戻る
        ↓
④ 最終判定（長時間水準）
```

## 8. 較正値（閾値・許容率・目印の文言）がどこにあるか（要件 2.6）

**判定側**: `judge-perf.py` の **ファイル冒頭**。上から順に、

1. ファイル先頭の説明書き（使い方・終了コードの意味・`run-meta.txt` の扱い・実ログの行の形）
2. その直後の `# 較正値バナー` 以下に並ぶ定数（`SCRIPT_VERSION` から `PERCENTILE_METHOD` まで）

この 2 つ以外の場所に閾値は書いてありません。**値を変えるときはここだけを書き換えます。**
バナーにある値はレポートの `[2] 較正値` にそのまま印字されるので、レポートを見れば
「そのとき何と比べたのか」が分かります。終了コードの表と総合判定の決め方も印字されます。

**ただし** ログの行を読み取るための正規表現（時刻の形・`名前=値` の切り出し方・色コードの
落とし方）はレポートには印字されません。ソースの中ほど、`# ログ行の解析` の節にあります。
ログの書式そのものが変わったときはそちらを直すことになります。

**採取側**: `invoke-perf-run.ps1` の冒頭。ヘッダのコメントに一覧があり、その下の
`# 較正値・調整値` ブロックが実体です。実走時間・CPU の採取間隔・`RUST_LOG` の値・
性能カウンタの名前などがここにあります。採取した値は `run-meta.txt` の `[較正値]` 節へ
そのまま書き出されるので、あとから条件を突き合わせられます。

### コマの間隔を見る判定式の較正値（task 3.2 の裁定で確定）

判定式のうち「コマの間隔」を見る式（⑴）は、次の 6 つの値で決まります。**うち 5 つは
ゴースト emo2 のアニメ定義から来ています**（`FRAME_INTERVAL_IDLE_MAX_ACTIVE` だけは
ゴーストによらない窓の性質です）。

| 較正値 | 値 | 意味 |
|---|---|---|
| `FRAME_INTERVAL_MAX_WAIT_MS` | 150.0 | そのアニメ定義に現れる**最大のコマ待ち時間**。上限の土台 |
| `FRAME_INTERVAL_CYCLE_SPAN_MS` | 172.0 | **サイクル全長**（コマ待ちの和）。判定の窓の条件に使う。**上限ではない** |
| `FRAME_INTERVAL_TOLERANCE` | 0.15 | 上限は 150.0 × 1.15 = **172.5 ミリ秒** |
| `FRAME_INTERVAL_IDLE_MAX_ACTIVE` | 1 | 判定の窓の条件 4。**その列に対応するグループ（`scope`）の中で**同時に走っているアニメの推定本数がこれを超える区間は使わない |
| `FRAME_INTERVAL_SERIES_SCOPE` | `TargetId(0)/1000 → scope="0"` | どの記録の列を、どのアニメの発火と結び付けるか |
| `FRAME_INTERVAL_JUDGED_SERIES` | `TargetId(0)/1000` | 判定対象の列。**列挙は全部か無しか** |

**以前の 172 ミリ秒は誤りでした。** emo2 のまばたき `animation1400` のコマ待ちは
0 → 150 → 22 で、172 はその**和＝サイクル全長**です。コマとコマの間隔は 150 と 22 の
2 種類であり、「単一の指定間隔」はこのアニメに存在しません。上限をサイクル全長に置くと、
本当は 150 ミリ秒で動くべきコマが 197.8 ミリ秒まで遅れても合格になります。

**判定の窓（窓 C）** は、アニメの発火の記録を起点に「サイクルの内側」だけを切り出します。
連続する 2 回の適用 a → b について、次を全て満たす間隔だけを判定に使います。

1. その列に対応する発火のうち、a 以前で最も新しいものを f とする（無ければ対象外）
2. `a − f ≤ 172 ミリ秒`（＝ a がサイクルの内側にある）
3. 区間 `(a, b]` に次の発火が無い
4. a と b の**両方**で、**その列に対応するグループ**（条件 1 と同じ `scope`）の中で
   同時に走っているアニメの推定本数が 1 本以下

条件 3 が「まばたきは数秒に 1 回しか起きない」という**正常な空白**を落とし、条件 2 が
発火と無関係な適用（会話で別の絵に切り替わる等）を落とします。
条件 4 は、**同じ列の上で 2 本のアニメが同時に走っている区間**を落とします。記録の列は
対象とサーフェスの組で分かれておりアニメ単位ではないので、2 本が重なると隣り合う差は
どちらのアニメのコマ間隔でもなくなります（次節）。
条件 4 が**同じグループのアニメしか数えない**のはこの理由がそのまま範囲を決めるからです。
別のグループ（例: ケロ）のアニメは**別の列**へコマを出すので、この列のコマ送りが
健全かどうかについて何も語りません。全グループを混ぜて数えると、
「別のアニメがこの列を汚している」と「マシンが忙しい」が区別できなくなります。
**停止の記録は窓の終わりに使いません**——停止は最後のコマの適用より先に出ることがあり、
終わりに使うと最後のコマが毎回落ちるためです。ただし停止の記録は条件 4 の本数の
数え上げには使います（窓の終わりに使うのとは別の話です）。

較正の検算（この値が出ないなら道具が壊れています）:

| 走行 | 判定対象に残った間隔 | 上位 5% | 上限超過 | 結果 |
|---|---:|---:|---:|---|
| 長時間・release | 309 本 | 164.018 ミリ秒 | 9 本 | 合格 |
| 短時間・release | 65 本 | 178.615 ミリ秒 | 5 本 | 不合格 |
| 短時間・dev | 22 本 | 821.971 ミリ秒 | 9 本 | 不合格 |

上限超過は 172.500 ミリ秒を超えた間隔の本数です（上位 5% がその中に入るかどうかが合否を
決めるので、超過が数本あっても合格になることがあります）。
条件 4 が落とした間隔は、この 3 走行ではどれも **0 本**です。emo2 の実走ではキャラの
`animation1400` と `1402` が同じ時刻に重なることが無かったためで、条件 4 は
`fixtures/P13` `fixtures/P14` の形が来たときにだけ働く見張りです。

> **一度この表が 267 / 64 / 22 本になっていました。** 条件 4 を足したとき、本数を
> グループをまたいで数えていたためです。落ちた 42 本（長時間 release）は
> 1 本残らず「キャラのアニメ 1 本＋**ケロ**のアニメ 1 本」で、キャラの 2 本重なりは
> 1 件もありませんでした。しかもその 42 本には上限超過が 1 本（173.997 ミリ秒）含まれ、
> 上限超過が 9 本から 8 本へ減っていました。短時間 release では、上限超過だった 5 本の
> 区間にケロの発火・停止を挟むだけで上位 5% が 178.615 → 161.928 ミリ秒へ下がり、
> 判定が**不合格から合格へ反転します**。数え方を同じグループに限る形へ直し、
> `fixtures/P14_other_scope_animation_overlap` でその反転を固定しました。

### この判定式が見つけられないもの

- **ケロは判定できません。** ケロのアニメ番号は複数の基準サーフェスで同じ 0 であり、
  待ち時間も基準ごとに違い、1 サイクルの中で基準サーフェスが変わります。記録の列が
  1 つのアニメ定義と対応しないので、判定対象から外してあります。
- **判定対象に書き漏らした列は、どれだけ遅くても合格を止めません。**
  列挙は全部か無しかです（`fixtures/H1b_unpinned_slow_series` に記録）。
- **同じ対象・同じサーフェスの上で 2 本のアニメが重なると、記録が 1 本の列に混ざります。**
  混ざった列の隣り合う差はどちらのアニメのコマ間隔でもなくなり、位相しだいで偽の不合格にも
  偽の合格にも倒れます。条件 4 が助けになるかは**2 本目がどこを覆っているか**で変わります。
  2 本目が判定区間の全域を覆っていれば、両方が発火の記録を出しているかぎり条件 4 が
  その区間を落とすので、偽の合格には倒れません（判定不能になります。
  `fixtures/P13_same_key_two_animations_pass_side` に記録）。**遅い区間だけを覆っている
  場合は落ちるのが遅い区間のほうなので、上位 5% が下がって合格に倒れます**（次の次の項）。
  実機の emo2 で `surface1000` に同居する `animation1400` と `1402` は、どちらも発火の
  記録を出し、3 走行とも同時に走っている区間はありませんでした（同時活性の最大 1 本）。
- **発火の記録を出さない書き換えが同じ列に混ざる形は、今も見つけられません。**
  条件 4 は発火と停止の記録の収支から本数を推定するので、記録を出さないものは数えられません
  （`fixtures/P12_same_key_two_animations` に記録）。塞ぐには記録側にアニメの識別子を
  足す必要があり、この spec の範囲外です。
- **同じグループの 2 本目が、遅い区間だけを覆って走っていると、その証跡は消えます。**
  条件 4 は間隔を落とすことしかしないので、落ちた中に上限超過が入っていればその分だけ
  上位 5% が下がります。同じ列の上の重なりでは落とすのが正しい（その差はどちらのコマ間隔
  でもない）のですが、遅い区間だけが覆われた場合と区別する術がありません。
  **別のグループのアニメについては数えないことでこの経路を塞いであります**
  （`fixtures/P14_other_scope_animation_overlap`）。

### ゴースト固有の値を他へ流用しないこと

較正値のうち「emo2 固有」と注記のあるものは、計測に使っているゴースト emo2 のアニメ定義や
実寸から来ています（例: 上の 5 つ、バルーンの既定位置）。別のゴーストで測るときは、
**アニメ定義（`shell/master/surfaces.txt`）のコマ待ちを読み直して**書き換えてください。

### 日本語版 Windows など、性能カウンタの名前が翻訳されている環境

CPU の採取には Windows の性能カウンタを使います。採取スクリプトが持っているカウンタ名は
**英語版の名称**です（`\Process(...)\% Processor Time` など）。名前が翻訳されている環境
ではカウンタが見つからず、採取スクリプトが終了コード 4 で止まります。その場合は冒頭の
較正値ブロックにあるカウンタ名を、そのマシンでの名称へ書き換えてください。

## 9. 道具そのものの点検（`--selftest`）

```powershell
python tools/perf/judge-perf.py --selftest
```

`fixtures/` にある「答えの分かっている入力」を、**実際の判定とまったく同じ入口**で走らせ、
終了コードが台帳どおりに再現されるかを確かめます。実行に測定は不要です。

期待値は各 fixture フォルダの `case.txt` に書いてあります。同じファイルに「この入力が何を
固定しているのか」の説明も入っているので、その 1 ファイルを読めば意図が分かります。
期待値をスクリプト側の表に持たせていないのは、fixture と期待値が別々に古びて静かに
ずれるのを防ぐためです。

**合格だけでなく、不合格・判定不能・引数の誤りも毎回再現させます。** 緑は道具が壊れていても
出ます。判定を丸ごと壊して何もかも不合格にすれば赤は出るので、赤だけでも足りません。
出力には「期待 0／1／2／3 のそれぞれについて、登録が何件で、実際に何件再現したか」を並べます。
赤（不合格・判定不能）を再現した fixture が 1 件も走らなかった場合、`--selftest` は
**それ自体を失敗**として終了コード 1 を返します（「全部通った」と「1 つも走らなかった」が
見分けられない点検には意味がないため）。

終了コードは 0（全件一致）／1（1 件でも食い違い）／3（`fixtures/` を読めない）です。

1 つもありませんでした**。そのため「条件 4 がグループをまたいで数えている」という誤りが
レビュー 3 回を素通りしました。`P14` では、上限を超えた 10 本の区間だけをケロのアニメが

健全な 140 本だけになり、**不合格（1）が合格（0）へ反転します**。

`H12`／`H12c` も対です。`H12c` は色コード入りで、判定の結果が色なしの `H12` と
**一字一句同じレポート**になることまで確かめます（終了コードだけ合っていて中身がずれている
場合を捕まえるため）。

fixture は `fixtures/generate.py` で作り直せます。作り直したあと `git status` が汚れなければ、
登録されている入力は生成条件どおりです。汚れたら、生成条件を変えたのか、fixture を手で
触ったのか、どちらかです（このリポジトリは取り出すときに改行を書き換える設定なので、
`fixtures/.gitattributes` でその書き換えを止めてバイトを固定しています）。

## 10. CPU が下がりきらず、理由も分からないとき（要件 5.2）

長時間水準の走行で CPU が頭打ちにならず上がり続けたら、`judge-perf.py` は「単調上昇（未知の
機序の候補）」と報告します。そのときは次の順で処理します。**放置も、口頭での申し送りも
しないでください。**

1. **測ったものを残す。** 出力フォルダ一式（`run.log`・`cpu.csv`・`run-meta.txt`）と、
   `--mode verdict` のレポート全文を保存します。レポートには測定マシンの条件と較正値が
   入っているので、これ 1 枚で条件を再現できます。
2. **傍証を読む。** レポートの収束判定の節に、窓ごとの CPU 平均・後半窓の傾き・
   アニメの発火と停止の件数の収支が並びます。発火が停止を上回り続けているなら、
   同時に走るアニメが増え続けている疑いです。件数の収支が 0 に戻らない走行では、
   まず停止のログが 1 本落ちていないかを疑ってください（1 本落ちると、そのアニメは
   以後ずっと走っている扱いになります）。
3. **同じ手順でもう 1 回測る。** 上の第 7 節の 6 条件をそろえて再現するか確かめます。
   1 回きりの観測を機序の根拠にしないでください。
4. **この spec の範囲で直せるかを判定する。** 直せる範囲は「表示 1 コマを適用する経路の
   バッファの使い回し」です。原因がキャッシュの容量政策にある場合は、この spec には
   容量を変える経路がないので裁定の対象になります（要件 7）。
5. **範囲外なら独立した課題として起票する。** 起票には次を必ず含めます。
   - 何が観測されたか（数値・窓ごとの平均・傾き・走行時間）
   - どの条件で測ったか（`run-meta.txt` の内容・ビルド種別・水準）
   - なぜこの spec の範囲外と判断したか
   - 再現手順（この文書のコマンドをそのまま）
   - 保存した出力フォルダの場所
6. **起票したことを記録に残す。** 担当する課題を名指しで書きます。「あとで見る」は
   担当者ではありません。

## 11. 読むときの注意（つまずきやすいところ）

- **`cpu.csv` の 1 行は約 1 秒幅の瞬時値です。** 15 秒間の平均ではありません
  （性能カウンタの仕組み上、1 回の採取に約 1 秒かかります）。15 秒は「採りにいく間隔」です。
  マシンが詰まって刻みを飛ばすと印を残さずに欠測するので、`judge-perf.py` は刻みを均等と
  仮定せず、行ごとの時刻の差から実際の間隔を出しています。
- **`cpu_percent_1core` は 1 コアを 100% とする換算値です。** 複数コアを同時に使えば 100 を
  超え得ます。マシン全体に対する割合ではありません。
- **`run.stderr.log` は必要なログの種類ではありません。** 標準出力と標準エラーは同じファイルへ
  流せないので、採取スクリプトが分けているだけです。無くても集計は成立します。
- **`judge-perf.py` は `run-meta.txt` を必要なログの種類に数えています。** 設計文書は必要な
  ログを 3 種（段階別計時・表示成立の記録・CPU の推移）と書いていますが、実装は 4 種目として
  `run-meta.txt` を要求します。要件 4.5 が求める「測定マシンの条件の併記」を書けない集計を
  通さないための、意図した強化です。
- **`run.log` に色コードが入っていることがあります。** 採取スクリプトは色を止める設定
  （`NO_COLOR`）を入れて起動するので、これから採る `run.log` には入りません。ただし手で
  起動した走行や、この設定を入れる前に採った走行には入っています。`judge-perf.py` は
  どちらも読めます（色を落としてから解析します）。
- **同じ入力でも、集計モードと判定モードで終了コードが違うことがあります。** 集計モードは
  合否を出さないので、定常状態が薄い走行でも警告付きで 0 で終わります。判定モードは同じ
  入力を判定不能（2）にします。これは意図した違いです。

### 数字の較正について、まだ埋まっていない穴

要件 4.4 が定める「CPU 3% 未満」という目標は、同じゴーストを表示中の SSP を開発機で測った
定常値 2.2〜2.8% を根拠にしています。ところが **その 2.2〜2.8% をどうやって採ったのかが、
要件にも設計にも記録されていません**（どのカウンタか・平均か瞬時値か・どれだけの長さを
見たのか・1 コア換算かマシン全体かが不明）。

つまり、いま areka 側で採っている値と、比較相手の SSP の値が **同じ物差しで測られている保証が
ありません**。areka 側は「1 コア換算・約 1 秒幅の瞬時値・定常区間の平均」です。
SSP を測り直して比べるときは、**先に採取方法をそろえてから**測ってください。そろえずに
比べた数字は、大小が逆に出ても気づけません。この穴は既知であり、埋めるまで残ります。

## 12. 測り直すたびに確かめること（コマの間隔を見る判定式）

「コマの間隔」を見る判定式の較正は、最初のベースライン（2026-08-14 の 3 走行）で
**確定済み**です。値と窓の定義は上の第 8 節にあります。以後の走行では、走行ごとに次を
確かめてください。**確かめずに出た合格は、測れていないだけかもしれません。**

1. **その走行に現れた列に対して、判定対象の指定が妥当かを毎回見直す。**
   列挙は全部か無しかです。ベースラインに無かった面が出た走行では、**指定漏れが無言で
   通ります**。レポートの「判定対象から外した系列」の一覧を必ず読んでください。
2. **指定した列が観測されていることは、判定スクリプトが関門として持っています。**
   指定した列が記録に 1 度も現れない走行・窓に間隔を 1 本も残さない走行は判定不能に
   なります（`fixtures/H20_judged_series_absent`・`H21_judged_series_outside_window`）。
   判定不能が出たら、まずこの一覧を読んでください。
3. **記録を出していない対象が紛れていないか確かめる。** 表示の記録だけ出して段階別計時を
   出さない対象は、この判定から見えません（ログ設定の絞り込みを誤って片方のゴーストの
   詳細ログが落ちた走行が、合格に見えます）。記録に現れた対象の数と、実際に動かした
   ゴーストの数を突き合わせてください。**これはまだ機械化されていません。**
4. **列が短いほど判定が粗くなる。** 判定に使う間隔が 20 本を切ると、判定スクリプトは
   上限内でも合格を返しません（判定不能）。ただし上限を超えていれば不合格を返します——
   確定的な違反を本数不足に埋もれさせないためです。
   遅くなるほど窓に残る間隔が減るので、この経路は鈍化と同じ向きに効きます。
   実測では dev の短時間走行で 22 本まで減りました。
5. **偽の不合格が出る帯がある。** 判定対象に指定した列に、コマ送りでない散発的な適用が
   混ざると、まばたきの間隔で裁かれて不合格になります。判定対象の指定から外すのが
   本筋です。**合格側へ倒れる誤りではありません。**
6. **同じ対象・同じサーフェスの上で 2 本のアニメが重なる区間は、判定に使いません**
   （窓の条件 4）。実機の emo2 でも、キャラの `surface1000` には `animation1400` と
   `1402` が同居します（長時間 release の走行で発火 212 回と 28 回。どちらも `scope="0"`）。
   この 2 本はどちらも発火の記録を出すので、**同時刻に重なれば** 落ちます。ただし
   2026-08-14 の 3 走行では、この 2 本が同時に走っていた区間は 1 つも無く、条件 4 が
   落とした間隔は **0 本**でした（309 / 65 / 22 本はいずれも条件 4 の前後で同じです）。
   **数えるのは同じグループ（`scope`）のアニメだけです。** ケロ（`scope="1"`）が動いて
   いることは、キャラのコマ送りが健全かどうかについて何も語りません。ここをまたいで
   数えると、上限を超えた区間をケロが覆っただけで不合格が合格へ反転します
   （`fixtures/P14_other_scope_animation_overlap` に記録。実際に一度そうなっていました
   ——第 8 節の検算表の注記）。
   **残っているのは、発火の記録を出さない書き換えが同じ列に混ざる形だけです**
   （`fixtures/P12_same_key_two_animations` に記録）。条件 4 は発火と停止の記録の収支から
   本数を推定するので、記録を出さないものは数えられません。
   窓の定義を変えたら、`P12`・`P13_same_key_two_animations_pass_side`・
   `P14_other_scope_animation_overlap` の期待値を全部見直してください。
   `P13` は条件 4 を外すと合格（0）に化け、`P14` は条件 4 の数える範囲を広げると
   合格（0）に化けます。
7. **条件 4 は間隔を減らすことしかしません。** 走行の相が変わって落ちる本数が増えれば、
   列は 20 本を切って**判定不能**へ倒れます（合格ではありません）。ただし「減るだけ」は
   「安全側」を意味しません——落ちた中に上限超過が入っていれば、残りの上位 5% は
   下がります。それが上で反転した経路そのものです。
